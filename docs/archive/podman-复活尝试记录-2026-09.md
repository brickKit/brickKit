## 背景

用户在一台日常开发机（Ubuntu 26.04，装了 Docker 29.7.1 + Podman 5.7.0，VS Code 通过 snap
安装）上问：能不能用 Podman 替代 Docker 来省内存/CPU，尤其是设想中 70 个 Go/Python 组件的规模。
借这个问题重新调查了 005 §7 记录的 Podman `down` 失败问题，想看看能不能满足 §7.5 的复活条件。

**结论先说：没有满足。而且过程中一次系统级操作把这台机器的 VS Code 搞到打不开了。**

---

## 发现 1：这台机器最初连 `podman info` 都跑不起来——但这和 Podman 本身无关

**现象：**

```
Error: database static dir "/home/zhijie/snap/code/254/.../containers/storage/libpod"
does not match our static dir "/home/zhijie/snap/code/264/.../containers/storage/libpod":
database configuration mismatch
```

**原因：** VS Code 是 snap 安装的，snap 会把这类应用启动的终端的 `$XDG_DATA_HOME` 重定向到
`~/snap/code/<revision>/...`。Podman 把 rootless 存储根目录记进了数据库，snap 升级 VS Code 的
revision 号之后，这个路径就和数据库里记的对不上了，Podman 出于自我保护直接拒绝启动。

**修法（已验证有效）：** 在 `~/.zshrc` 里显式覆盖，不让 snap 的注入值生效：

```bash
export XDG_DATA_HOME="$HOME/.local/share"
export XDG_CONFIG_HOME="$HOME/.config"
```

这条和下面的 `down` 失败问题**完全无关**，只是"从 VS Code 终端里测试 Podman"这件事本身自带的坑，
换一个不经过 VS Code snap 沙箱的终端大概率不会遇到。单独记在这里是因为它第一次出现时很容易被
误认成是 Podman 本身坏了。

---

## 发现 2：`down` 失败的真实根因——AppArmor 拦截了 podman 给 pasta 发的 SIGTERM

复现（rootless Podman + 自定义/bridge 网络）：

```bash
podman run -d --name t1 --network bridge alpine:latest sleep 30
podman rm -f t1
# → Error: ... rootless netns: kill network process: permission denied
```

内核审计日志给出了精确原因：

```
apparmor="DENIED" operation="signal" class="signal" profile="pasta"
comm="podman" requested_mask="receive" denied_mask="receive" signal=term peer="podman"
```

`pasta` 是 rootless Podman 用来做用户态网络翻译的辅助进程。`down` 要礼貌地给它发 `SIGTERM`
才能把这次部署的网桥、IP 分配、nftables 规则干净地拆掉。这台机器（Ubuntu 26.04）的 AppArmor
不允许 `pasta` 接收来自"podman"这个标签的信号，于是 kill 失败，`down` 报错。

这不是 BrickKit 代码的问题，也不是这台机器独有的巧合——上游 Podman 的
[containers/podman#27372](https://github.com/containers/podman/issues/27372) 和
[Debian #1100135](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1100135) 记录的是完全一样的
审计日志签名。Podman 维护者的结论："this does not seem like an upstream problem but rather the
distro level security policies"——是发行版打包 AppArmor 策略时的缺口，不是 Podman 自己的 bug。

Debian 那边的分析更进一步：根因是 Ubuntu/Debian 给 `podman` 二进制挂了一个**摆设性质**的
AppArmor 占位 profile（`/etc/apparmor.d/podman`，内容是 `flags=(unconfined)`，本身什么都不限制，
唯一作用是给进程挂个名字）。但正是这个挂名触发了 AppArmor 两个具名 profile 之间的信号仲裁——
pasta 的 profile 从没写过"允许来自 podman 这个名字的信号"，于是被拦。Debian 采纳的修法是**直接
删掉这个占位 profile**（进了 `apparmor` 4.1.0~beta5-4）。

## 发现 3：Debian 的标准修法，在这台机器上没有解决问题——原因没有查清

按 Debian 的方案执行：

```bash
sudo rm /etc/apparmor.d/podman
sudo apparmor_parser -R /etc/apparmor.d/podman
```

反复跑 10 轮 `run` + `rm -f` 生命周期，**10 次全部还是同一个错误**，内核审计日志里 `peer="podman"`
一字不差地继续出现——尽管确认了 `/etc/apparmor.d/podman` 文件已经删除、没有被谁悄悄恢复、
`/etc/apparmor.d/` 下也找不到第二份给 podman 挂名的 profile 文件。

**高度怀疑但未证实的原因：** 上面那两条命令的执行顺序本身可能有问题——`apparmor_parser -R <路径>`
需要**读取**这个文件才能知道要从内核卸载哪个 profile，而 `rm` 已经先把文件删了，第二条命令这时候
去读一个不存在的文件，很可能直接报错、什么都没真正从内核卸载。也就是说文件层面"删干净了"，
内核里那份旧 profile 可能从未被真正卸载过。**这一点没有最终验证**——按下面发现 4 的教训，没有
再继续深挖下去。

**结论：即使照抄 Debian 官方认可的修法，这台机器上 Podman 的 `down` 依然不可靠。** 005 §7.5
的第一条复活条件（"找到一台 `down` 本身能跑通的机器"）目前不满足。

## 发现 4（⚠️ 最重要，务必先读）：`aa-remove-unknown` 在装了 snap 应用的机器上是危险操作

为了解决发现 3 里"内核可能还残留旧 profile"的问题，尝试了 Ubuntu/Debian 自带的
`aa-remove-unknown`——这个工具按设计是用来清理"源文件已经不在了、但内核里还留着"的 AppArmor
profile 的，听起来正好对症。

**实际后果：它把 `snap-confine` 自己的 profile 也当成"孤儿"一起卸载掉了，导致这台机器上所有
snap 应用（包括 VS Code 本身）都无法启动。** snapd 启动任何 snap 应用都要求 `snap-confine` 的
AppArmor profile 必须在内核里加载着——这个连锁后果在执行前完全没有预料到，`aa-remove-unknown`
本身也没有先列出"我要删哪些"再让你确认的 dry-run 步骤。

**恢复用的命令（供参考，不代表这是标准做法，是当时摸索出来能用的）：**

```bash
sudo systemctl enable --now apparmor.service
sudo systemctl enable --now snapd.apparmor.service
sudo apparmor_parser -r /etc/apparmor.d/*snap-confine*
sudo apparmor_parser -r /var/lib/snapd/apparmor/profiles/snap-confine*
sudo systemctl restart snapd.apparmor
```

**⚠️ 给下一个人的明确警告：不要在装了 snap 应用的机器上运行 `aa-remove-unknown`（或任何"批量清理
AppArmor 残留 profile"类的工具），除非先确认清楚它会动到哪些 profile。** 如果一定要处理某个具体
profile 的残留，应该针对那一个名字做定向操作，而不是用扫全盘的清理工具。

## 附带产出：Docker vs Podman 引擎开销实测（70 组件规模外推）

调查过程中顺带在这台机器上测了这组数据（20 个空跑 alpine 容器，排除了机器上已有的其它 Docker
负载后取的干净差值）：

| | Docker | Podman (rootless) |
| --- | --- | --- |
| 常驻守护进程 | dockerd ~125MB + containerd ~107MB ≈ **232MB 固定开销** | 无常驻守护进程 |
| 每容器监督进程 | containerd-shim ≈ **10.9MB/容器** | conmon ≈ **2.2MB/容器** |
| 服务发现层 | 内嵌在 dockerd 里，无法单独拆分 | aardvark-dns：全项目共享 1 个进程，~4MB，不随容器数增长 |

按 70 个容器线性外推：Docker ≈ 995MB 引擎开销，Podman ≈ 158MB，差距约 800MB。另外实测确认：
容器间走同一 bridge 网络的流量不经过 `pasta`（走内核网桥，和 Docker 路径一样），`pasta` 只在流量
要跨"netns↔宿主机真实网络"这条边界时才被拉起——BrickKit 里最大头的"组件互相调 `*_ENDPOINT`"
流量，两个引擎的网络路径没有实质差别。

这组数字本身是真实可用的，但**跟"能不能部署"是两件事**——见下面的结论。

## 结论与给下一个人的建议

1. **005 §7.5 的复活条件目前不满足**——`down` 依然不可靠，连官方认可的修法都没能解决，真正原因
   还没查清楚。
2. **不要在日常开发机上继续做这类系统安全策略层面的实验。** 这次的教训是一个看起来"精准清理"
   的工具实际影响面比预想的大得多，而恢复只能靠人工 sudo 干预，这不是一个可以放心反复试错的
   环境。
3. 如果未来还想继续查这条路，应该换到**一次性、可以随便重建的环境**（虚拟机快照、云端临时
   实例），不要在装着 IDE 和其它项目容器的主力机器上做。
4. Docker vs Podman 的资源开销对比数据本身站得住脚，如果决策的目标就是"省内存/CPU"，这组数据
   可以直接用；但要不要真的切换引擎，还是得先有一台 `down` 能稳定跑通的机器，两件事分开判断。
