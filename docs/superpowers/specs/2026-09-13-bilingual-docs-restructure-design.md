# 文档体系重构：默认英文、中文对等服务、AI 优先的可发现结构

- 日期：2026-09-13
- 状态：设计已确认，待写实现计划
- 影响面：仓库根目录（README.md、AI-CONTEXT.md→AGENTS.md、llms.txt）、全部 `design/`、`试用指南/`、`开发进度/`、`开发计划.md`、四份根目录方法论文档（发布与分发/市场部署与运维指南/部署模式/组件合并部署）
- 触发：读完 `be-assembly-standard`（brickKit 的真实使用方）的经验反馈与其 `docs/standards/` 后，判断 brickKit 自身文档需要一次架构级重写，而不是局部修补

---

## 1. 背景与动机

brickKit 现在的文档默认中文、英文只在 README 末尾留一小节"In English"（内容是"全部文档是中文的，去读 AI-CONTEXT.md"）。这与两件事冲突：

1. **未来的主要读者是 AI**，而且很多场景下用户只会把仓库地址丢给 AI，自己完全不看文档——AI 能读懂什么、以什么顺序读，直接决定了 brickKit 能不能被正确使用。
2. **英文读者目前拿到的只有"入口 + 一句话打发"**，没有对等的深入材料。

同时，`design/`（14 本）和 `试用指南/`（23 篇）是 brickKit **自己开发过程中**沉淀的规范与验证记录，写法上偏"论证一个设计决策为什么这样定"，不是"教一个新读者怎么用好这个平台"。真机验证过 brickKit 的下游项目（be-assembly-standard）反过来证明了：这两类内容之外，还缺一整层"用 brickKit 能做到什么、怎么做好"的方法论（测试怎么分层、种子/测试数据怎么规划、组件边界怎么设计、部署怎么优化）——这层内容现在完全不存在。

这次重构一次性解决三件事：**默认语言换成英文、中文对等而非从属、新增一层方法论内容**，并且保证"用户把仓库地址丢给 AI"这条路径在新结构下依然可靠。

## 2. 目标与非目标

**目标**

1. 新建 `docs/en/` 与 `docs/zh/` 两棵完全对等的文档树，任何一份文档在两边都是独立可完整阅读的一等公民，不是互为翻译附属。
2. README.md 保持"用户向"定位（是什么/怎么装/怎么卸/基础命令/不做什么/怎么上手/仓库结构），默认英文，重写但不改变性质。
3. 新增 `docs/{en,zh}/patterns/`：把 be-assembly-standard 验证过的测试分层、种子/测试数据方法论、组件设计准则、部署与优化方案，改写成 brickKit 中性的推荐实践。
4. 保证"用户把 `https://github.com/brickKit/brickKit` 丢给 AI"这条路径在新结构下能让 AI 找到并读到它需要的一切（§5 详细设计)。
5. 旧的 `design/`（14 本）、`试用指南/`（23 篇）、`开发进度/`、`开发计划.md` 整体归档为历史记录，只保留中文原文，不再维护、不追求与新内容对等。

**非目标**

1. 不逐句机器翻译旧文档——新内容是重写，不是翻译旧内容。
2. 不改动 `internal/skills/assets/`（装进下游用户项目的 AI 技能包）——它服务的是下游项目而不是 brickKit 自身仓库的读者，单独排期。
3. 不在这一轮里把全部 14 本 architecture 文档、23 篇 guide 一次性写完——内容体量太大，本设计只定架构和骨架，具体每篇内容按后续多轮实现计划陆续补齐（§7）。

## 3. 已定决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 双语模型 | **对称双语**：`docs/en/` 与 `docs/zh/` 结构完全镜像，任何一份都能独立完整阅读 | 用户明确要求"问中文查中文文档，问英文查英文文档"，不是 be-assembly-standard 那种"少数入口双语、大头内容永远单语"的非对称模型 |
| 历史内容语言 | `docs/archive/` 下的东西永远只中文，不重写、不追译 | 决策记录、旧设计书、旧试用指南的价值是可追溯，不是给新读者理解平台用的；翻译成本大且几乎没人通读 |
| 目录命名 | 全部英文目录名（`architecture/`、`guide/`、`patterns/`），中文内容挪出仓库根目录，不再用中文做目录名 | 用户明确要求"文件夹肯定不能是中文名字" |
| AI 入口文件命名 | `AI-CONTEXT.md` 改名为 `AGENTS.md` + 一行 `CLAUDE.md`（内容 `@AGENTS.md`） | 对齐当前 AI 编码工具生态的通用约定（Cursor / Claude Code / 其他多家工具会自动读取 `AGENTS.md`），与 be-assembly-standard 自己的约定一致 |
| README 定位 | 保持用户向，不吸收 AGENTS.md 的压缩说明书内容 | 用户明确纠正："readme 还是以用户为主……具体内容用链接指引" |
| README 语言 | 根目录同时维护 `README.md`（英文，规范渲染的那一份）与 `README.zh.md`（中文），互相在顶部一行"Read this in: …"互链 | 用户明确要求"readme 记得也准备一份中文版本"——对称双语这条原则没有例外，入口文件也不能只有英文 |
| 语言范围 | 现在只做英文 + 中文两种，但目录/命名约定要能直接扩展到第三种语言，不能是只服务两种语言的硬编码结构 | 用户明确要求"未来得适配多种语言……我们准备构建或修改的文档，都应该有多种语言"——`docs/<lang>/` 与 `README.<lang>.md` 这两个约定天然支持新增语言代码，不需要改结构 |
| 新方法论内容位置 | 新增第三个顶层类别 `patterns/`，与 `architecture/`（回答"平台是什么"）、`guide/`（回答"怎么跑一遍"）并列 | 现有两类文档定位都不适合装"怎么用好"的方法论内容 |
| 旧 `design/`/`试用指南/` 的命运 | 整体挪进 `docs/archive/`，标注历史记录；核心内容重新提炼成 `architecture/`、`guide/` 下的新文档 | 用户明确表示"这两类内容都可能要完全重构"，旧内容归档而不是删除 |

## 4. 顶层目录蓝图

```
brickKit/
├── README.md                    英文，用户向入口，顶部一行语言切换链接
├── README.zh.md                 中文镜像，内容对等，顶部同样一行语言切换链接
├── AGENTS.md                    英文，AI 向压缩全貌 + 路由表
├── CLAUDE.md                    一行 @AGENTS.md
├── llms.txt                     机器可读全站索引，单文件，中英文分节（§5.3）
│
├── docs/
│   ├── en/
│   │   ├── architecture/        平台是什么、怎么工作——简洁、mermaid、真实代码
│   │   ├── guide/                动手教程，AI 与用户都能照着走
│   │   └── patterns/             测试分层、种子/测试数据方法论、组件设计准则、部署与优化方案
│   ├── zh/                       与 docs/en 逐目录逐文件对等
│   │   ├── architecture/
│   │   ├── guide/
│   │   └── patterns/
│   └── archive/                  冻结历史记录，只中文，不追求对等
│       ├── design/               旧 14 本设计书 + 附录 + 000 导航，原文不动
│       ├── guide/                 旧 23 篇试用指南，原文不动
│       ├── decisions/             开发进度/（决策索引 566 条 + 完成记录）
│       └── planning/              开发计划.md、发布与分发.md、市场部署与运维指南.md、部署模式.md、组件合并部署.md 的旧版原文
│
├── cmd/ internal/ market-server/ tests/ deploy/    不变
```

**语言扩展性**：`docs/<语言代码>/` 与根目录 `README.<语言代码>.md` 这两个命名约定本身不依赖"只有英中两种"——将来要加第三种语言，只需要新增一棵 `docs/<lang>/` 与一份 `README.<lang>.md`，不需要改任何现有结构。本轮只落地英文与中文两种，但命名约定从一开始就按这个可扩展形态写。

**四份根目录方法论文档的处理**（发布与分发/市场部署与运维指南/部署模式/组件合并部署）：性质上是"怎么部署好、怎么发布好"的实操方法论，不是历史记录，但内容需要重写才能达到新标准——旧版原文挪进 `docs/archive/planning/` 留痕，内容重写后归入 `docs/{en,zh}/patterns/deployment/` 或 `architecture/`（视具体内容归属，实现计划里逐篇判断）。

## 5. AI 可发现性设计（本轮新增的关键约束）

**要求**：用户把裸仓库地址 `https://github.com/brickKit/brickKit` 丢给 AI，AI 要能找到并读到它需要的一切。这条路径现在已经存在（README 顶部的"给 AI 的指令"块 + `AI-CONTEXT.md` + `llms.txt` 三件套），新结构必须原样保留这条链路，只是换了文件名和内容。

### 5.1 为什么这三份文件是这条链路的关键

- GitHub 渲染仓库主页时**必定**把 `README.md` 的内容显示出来——不管调用方是浏览器还是任何做网页抓取的 AI 工具，`README.md` 是唯一保证"给一个裸仓库地址就一定拿得到"的内容。这是整条链路的**起点**，不是可选项。
- `raw.githubusercontent.com` 的链接是纯文本，任何能发 HTTP GET 的工具都能读，不需要 JS 渲染、不需要登录、不需要理解 GitHub 的目录树 UI。README 里给 AI 的指令必须是这种链接，不能只写"去 docs/ 目录看看"这种依赖目录浏览的指引。
- `llms.txt` 是目前 AI 抓取工具认知度最高的"全站索引"文件名（llms.txt 约定），放在仓库根目录，本身也会被 README 的裸地址渲染出来（如果工具做了目录探测）或被 AI 主动尝试。

### 5.2 README 顶部固定一段"AI 指令块"

延续现有做法，位置不变（README 最上方，仓库简介之前），内容改写为英文，逻辑更新为：

1. 第一步，抓取 `AGENTS.md` 的 raw 链接——一份文件读完即可理解 brickKit 的全部核心理念与做法。
2. **判断用户提问所用的语言**：中文提问 → 之后所有细节都去 `docs/zh/` 下对应路径找；英文或其他语言提问 → 去 `docs/en/`。这条规则要在 AGENTS.md 里再重复一遍（不能只在 README 出现一次就假设 AI 记得，按 01-documentation-standard 的"AI 只会读到片段"原则）。
3. 需要更深细节时，抓取 `llms.txt`——完整的全站索引，每条都带绝对 raw 链接和一句话定位，中英文分两节列出。

### 5.3 llms.txt 的双语处理

不拆成 `llms.txt` / `llms.zh.txt` 两份——llms.txt 约定是"每个站点一份规范索引"，拆两份会让不知道要抓哪一份的 AI 多走一步。做法是**同一份 `llms.txt`，内部分两大节**：

```
# BrickKit

> 一句话定位（中英各一句）

## English documentation
- [Entry point](...AGENTS.md) - ...
- [Architecture](...docs/en/architecture/...) - ...
...

## 中文文档
- [入口文件](...AGENTS.md) - ...
- [架构](...docs/zh/architecture/...) - ...
...
```

AI 抓到这一份之后，按第 5.2 步已经判断出的语言，只需要看对应的那一节，不需要额外判断。

### 5.4 AGENTS.md 的角色

原 `AI-CONTEXT.md` 改名后角色不变：一份读完即可理解全平台的压缩文件（定位、术语表、原则、拒绝清单、核心机制、字段骨架、命令参考、"为什么"辩护）。新增两处更新：

- 开头加入与 README 一致的语言路由规则（§5.2 第 2 点），并给出 `docs/en/`、`docs/zh/` 的路径公式，不用"往回翻 README"这种引用。
- 第 11 节"仓库地图与深挖入口"整表更新为新路径，并新增指向 `patterns/` 各篇的行——现在的表已经有"想深挖什么 → 抓哪一份"的结构，直接扩展即可。

### 5.5 验证方式

新增一条 lint/check（放进现有 `make check-docs` 一类的门禁，具体命令在实现计划里定）：`llms.txt` 里列出的每条 raw 链接指向的文件必须真实存在；`README.md`/`AGENTS.md` 里出现的每个 `docs/en/...`、`docs/zh/...` 路径必须能在两棵树里各自找到镜像（除 `docs/archive/` 下的内容，它不要求对等）。这条检查直接呼应 be-assembly-standard 反馈里"结构检查脚本自己也要用真实反例验证"那条教训。

## 6. 新内容的写作标准

`docs/{en,zh}/architecture/` 与 `docs/{en,zh}/patterns/` 下的新文档统一遵守：

- **每份文档只回答一个问题、服务一种场景**（借用 be-assembly-standard `01-documentation-standard.md` §2.8 的"一份文档一个职责"检验法）。
- **禁止裸的"见上文"引用**——AI 常常只读到文档的一个片段。引用别处必须带具体章节/锚点。
- **每条禁令都带"为什么"和"违反后的症状"**——只写"不许做 X"对 AI 自查没有用。
- **用 mermaid 图 + 真实代码示例，不用纯文字描述机制**——这是用户本轮明确提的要求，区别于旧 `design/` 偏论证性的写法。示例代码优先取自 `tests/components/` 里真实跑过的组件，不虚构片段。
- `docs/zh/` 与 `docs/en/` 同一份文档内容对等（结论、示例、代码一致），但不要求逐句直译——允许中文版用更符合中文表达习惯的行文，只要传达的信息和结论完全一致。

`docs/guide/` 延续现有"试用指南"每篇必须真跑过的原则（不新增设计约束，沿用现有 `make check-guides` 一类门禁的精神）。

## 7. 落地阶段划分（供实现计划参考）

体量太大，不可能一轮做完，建议至少分两个阶段：

**阶段一：骨架与入口**（本次实现计划的范围）
- 建 `docs/en/`、`docs/zh/`、`docs/archive/` 目录结构
- 用 `git mv` 把 `design/`、`试用指南/`、`开发进度/`、`开发计划.md`、四份方法论文档搬进 `docs/archive/` 对应子目录（保留 git 历史）
- 重写 `README.md`（英文，用户向）
- `AI-CONTEXT.md` → `AGENTS.md`，内容更新（新路径、语言路由规则）；新增 `CLAUDE.md`
- 重新生成 `llms.txt`（新结构 + 中英文分节）
- 新增 §5.5 的结构校验门禁

**阶段二起：内容分批填充**（后续多轮实现计划）
- `docs/{en,zh}/architecture/` 按主题重新切分旧 14 本设计书的核心内容
- `docs/{en,zh}/guide/` 重新设计教程剧本
- `docs/{en,zh}/patterns/` 优先写测试分层与种子/测试数据方法论（be-assembly-standard 验证过、价值最高、brickKit 目前完全空白）

为了在阶段一就能演示新结构真的立得住，阶段一的实现计划里额外包含**一篇示范性内容**（架构或方法论各一篇，双语,带 mermaid + 真实代码），而不是只搭空壳目录。
