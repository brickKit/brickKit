# 部署形态选择

这一篇只回答一个问题：**一个有 N 个组件的项目，到底该跑成什么样。** 它不教你怎么造外壳（见 [外壳开发指南](../04-shell/05-shell-development.md)），
也不讲把一个组件放进外壳的具体步骤（见 [成员管理](../04-shell/04-members-management.md)）。还没决定项目整体长什么样时，先读这一篇。

## 简短的回答

| 你要 | 就这样跑 |
| --- | --- |
| 在一台机器上长期运行：一次交付、一个小规模的生产 | 容器，用**无根 Podman**；Docker 同等支持，给已经在跑 Docker 的机器、或只认 Docker 的周边工具 |
| 长期运行，还要自愈、跨机器扩容，或者已经有集群 | 容器，用 Kubernetes |
| 改一两个组件，对着真实的其余部分 | 容器，这几个组件以本机进程运行（`mode: debug` / `mode: local`） |
| 在一台没有容器引擎的机器上演示或试用 | 每个组件都 `mode: local`——只用于演示、试用，不用于交付 |

不管哪一种，拓扑都另外决定：先让每个组件独立，组件的内存或 CPU 真的算不过来时再把组件收进外壳，最后多半是混搭。一个项目的实测里，外壳让组件的内存少约三分之一、
CPU 少 14–28%，整套的内存却几乎不动——运行时越重的组件省得越多（[实测](#实测每种形态花多少)）。

**容器是主线。** 容器崩了由引擎拉起，开机时由引擎再启动，镜像钉住了组件测试时用的运行时。**本机进程是图省事的另类**：不用容器引擎、不用镜像，
但只活在启动它的那次 `up` 里，用的是这台机器上装着的工具链。部署越来越多由脚本与 AI 助手完成，装一个容器引擎对它们不是负担；所以留给本机进程的只有开发、演示与试用。

## 三个决定

1. **容器在哪跑**——部署文件里的 `target: podman`、`docker` 或 `k8s`。
2. **拓扑**——组件最终收拢成几个容器：全部独立、全部进外壳，还是混搭。
3. **这一次要不要让几个组件以本机进程运行**——开发时的叠加手段；所有组件都这样时，就是不用容器的演示。放在最后讲：[主线之外](#主线之外本机进程)。

前两个是互相独立的两根轴：任何拓扑都能跑在任何目标上，换哪一个都只是换一份部署文件，`config/` 一个字都不用改。[矩阵](#矩阵拓扑--在哪跑)列出它们的六格。
每种选择要花多少 CPU 与内存，下一节给出实测。

## 实测：每种形态花多少

下面的数来自一个项目，它在一台机器上把每种形态都跑了一遍。这些数用来看差别有多大，不是对你的项目的预测：定机器规格之前，量你自己的这一套。

**测的是什么**

| | |
| --- | --- |
| 机器 | Intel i5-12450H（12 线程）、14 GiB、NVMe，Linux 7.0，performance 电源模式 |
| 组件 | 12 个：11 个 Go、1 个 Python（打印）；一条从报价到出账、打印的业务链 |
| 拓扑 | **全部独立**：12 个进程。**全部进外壳**：3 个外壳——安全与主数据（7 个成员）、交易（4 个）、打印（1 个）。**混搭**：只用第一个外壳（7 个成员），其余 5 个独立 |
| 基础资源 | PostgreSQL 16、NATS JetStream、对象存储、身份产品——每一行都在同一台机器的 Docker 里 |
| 数据与负载 | 2 个法人、2 000 个产品、500 个客户、2 万张历史订单；开环混合负载每秒 7 次（列表、报价、确认、交货、出账），预热 5 分钟后测 15 分钟 |
| 版本 | Podman 5.7.0（无根）、Docker 29.9.2、minikube v1.38.1（Kubernetes v1.35.1，单节点）、BrickKit v1.10 |

**怎样读这些数**

- **组件**只算组件的进程（或外壳）；**整套**再加上基础资源与平台（容器引擎、集群，或本机进程的启动器）。Podman、Kubernetes、本机进程三行的整套还算上了给基础资源服务的那个 Docker。
- 内存是负载时不含页缓存的工作集；CPU 是每千次请求的 CPU 秒（越少越好）——每秒 7 次请求时，每千次 100 CPU 秒就是 0.7 核。
- 每格测一遍。比较只在同一批测量里做：不同批之间整体可能差约 8%，所以横着比一行，不要竖着比一列。差别在 10% 以内算看不出差别。

### 全部独立、全部进外壳、混搭：组件本身

| 在哪跑 | 内存：独立 → 外壳 / 混搭 | 每千次请求的 CPU：独立 → 外壳 / 混搭 |
| --- | --- | --- |
| Docker | 383 → 243 MiB（−37%）/ 290 MiB（−24%） | 36.5 → 28.3 秒（−22%）/ 32.3 秒（−12%） |
| 无根 Podman | 377 → 244 MiB（−35%）/ 288 MiB（−24%） | 35.4 → 25.5 秒（−28%）/ 29.8 秒（−16%） |
| Kubernetes，单节点 | 354 → 245 MiB（−31%）/ 291 MiB（−18%） | 34.3 → 29.4 秒（−14%）/ 31.5 秒（−8%，看不出差别） |
| 本机进程（`mode: local`） | 370 → 234 MiB（−37%）/ 281 MiB（−24%） | 31.2 → 26.4 秒（−15%）/ 29.2 秒（−6%，看不出差别） |

每种形态上，全部进外壳都让组件的内存少约三分之一、CPU 少 14–28%；混搭省下其中约三分之二的内存、一半的 CPU。延迟没有变：每一格的 p95 都在 49.6–54.2 毫秒。

### 全部独立、全部进外壳、混搭：整套

| 在哪跑 | 内存：独立 / 外壳 / 混搭 | 每千次请求的 CPU：独立 / 外壳 / 混搭 |
| --- | --- | --- |
| Docker | 1.97 / 2.04 / 1.88 GiB | 101.2 / 88.2（−13%）/ 94.0 秒（−7%） |
| 无根 Podman | 1.37 / 1.36 / 1.29 GiB | 106.8 / 94.2（−12%）/ 96.5 秒（−10%） |
| Kubernetes，单节点 | 2.38 / 2.46 / 2.36 GiB | 109.3 / 103.2（−6%）/ 105.4 秒（−4%） |
| 本机进程 | 1.43 / 1.43 / 1.32 GiB | 101.9 / 97.8（−4%）/ 101.6 秒（0%） |

整套的内存几乎不随拓扑变（在 −8% 到 +4% 之间），CPU 最多少 13%。每一行是自己的一批，这里不要行与行比——引擎之间的比较在[后面](#引擎之间平台自己的开销)。

### 为什么组件省了，整套不一定省

- **一个进程自己要多少。** 空闲时一个 Go 组件 29 MiB、0.012 核，一个 Python 组件 101 MiB、0.017 核；外壳每多承载一个成员只多 1–2 MiB、约 0.01 核（它的后台轮询）。
  合并每少一个进程，就省一份运行时——所以运行时重的组件（这里的 Python；JVM 一般几百 MB，没有量）每合并一个省得比 Go 多得多。
- **基础资源是最大的一块。** 四个基础资源不含页缓存就占 0.64–1.15 GiB，比全部组件加起来还多；拓扑不改变它们。
- **外壳的数据库连接更大。** 外壳的一条连接为几个成员服务，为每个成员各留一份缓存：每条连接的私有内存 10.1 MiB，独立时 4.2 MiB。连接从 102 条降到 63 条，
  PostgreSQL 反而多了约 210 MiB——抵掉了组件省下的约 130 MiB（Docker 那一批）。外壳的连接池上限、连接的最长寿命还可以调，没有量。

所以外壳稳定地省 CPU 与进程数——连带启动时间、要盯的日志、要重启的对象。省不省内存取决于运行时与数据库：以 Go 为主、共用一个数据库时，一进一出差不多抵消。要为内存合并之前，先量你自己的。

### 引擎之间：平台自己的开销

全部独立，同一批（Kubernetes 在第二批里以 Docker 为参照重测）：

| | 组件 | 平台自己的内存 | 平台每千次请求的 CPU | 整套 CPU 对 Docker |
| --- | --- | --- | --- | --- |
| Docker | 378 MiB、35.6 秒 | 548 MiB（dockerd、containerd、shim、端口代理） | 14.7 秒 | — |
| 无根 Podman | 377 MiB、35.4 秒 | 135 MiB（每个容器一个 `conmon`、`pasta`）；3 个外壳时 55 MiB | 16.0 秒 | +6%（看不出差别） |
| Kubernetes，单节点 | 354 MiB、34.3 秒 | 约 2 GiB（控制面与 kubelet；不含页缓存 0.75 GiB），另有约 0.25 GiB 的发布端口代理 | 14.8 秒 | +8%（看不出差别） |
| 本机进程 | 370 MiB、31.2 秒 | 435 MiB（每个进程旁边的 `go run`）；3 个外壳时 116 MiB | 0.5 秒 | +1%（看不出差别） |

- 组件在每种引擎上花的一样；差别在平台的内存。全部用无根 Podman 而不用 Docker，每台机器省下这个差——这里约 0.4 GiB（另一批里 Docker 守护进程在构建了一天镜像之后涨到约 0.7 GiB）。
- 无根 Podman 的用户态网络要花 CPU：Podman 自己每千次请求无根 13.1 CPU 秒、有根 2.9；有根 Podman 整套的 CPU 少 9–10%（另一批），代价是引擎以 root 运行。
- 本机进程经 Docker 发布的端口连基础资源，Docker 的端口代理多转发一份这些流量：每千次请求 20.5 CPU 秒，是那一行最大的平台开销。
- **几个本机进程、其余在容器里**（后来的一批，组件的一处改动让每一格都少了约 17%）：与同一批全在容器里相比看不出差别（Docker +2%、Podman +4%）；外壳在那里省得一样——组件 CPU −20%、内存 −35–36%，整套 −8% 到 −10%。

**定规格。** 负载加倍（每秒 7 → 14 次）时，组件与数据库的核数只多 50–56%，延迟不升；数据加倍只让数据库多 10–15%。整套容器放进 4 GiB、6 GiB 的内存上限都照常跑完——让出去的只是页缓存。
没有量的：负载上限、更多组件同机、多台机器、高可用、多节点 Kubernetes、别的运行时的组件。

## 决定一：容器在哪跑

这几乎完全是基础设施问题，不是性能问题：你有没有 Kubernetes 集群、需不需要跨机器调度和自愈？没有的话，一台机器用 `podman compose` 或 `docker compose`
驱动一切，运维最简单。有的话，`k8s` 生成 Deployment / Service / Ingress。

### 一台机器：无根 Podman，或 Docker

`target: podman` 与 `target: docker` 生成的是同一份 `compose.yaml`——唯一的不同是重启策略（见[重启机器之后](#重启机器之后)）——每个 `brickkit` 命令在两者上用法也一样。
不同的是主机上的引擎：

| 引擎 | 主机上跑着什么 | 好处 | 代价 | 适合 |
| --- | --- | --- | --- | --- |
| **无根 Podman**（推荐） | 没有守护进程：每个容器一个小的看护进程（`conmon`）；容器的网络由用户态的辅助进程（`pasta`）转发 | 引擎从不以 root 运行；常驻内存最少 | 用户态转发网络要花 CPU；主机要做几项设置（[见下](#为无根-podman-准备主机)）；1024 以下的端口不能直接发布 | 单机交付；内存小的机器；不允许常驻 root 守护进程的主机 |
| **Docker** | Docker 守护进程（`dockerd`、`containerd`），以 root 运行 | 最普及，周边工具最多；装上就能用 | 守护进程的常驻内存 | 已经在跑 Docker 的机器；只认 Docker 的周边工具 |
| **有根 Podman** | Podman 以 root 运行；网络由内核转发 | 没有用户态转发 | 引擎以 root 运行；与 Docker 在同一台机器上时，放行 Podman 的网桥之前容器之间互相不通（见[排障一节](../10-troubleshooting/01-up-down-issues.md#podman-上全部-healthy容器之间的调用却超时)） | 在意网络转发的 CPU、又接受 root 时 |

**实测说明了什么**（[引擎之间](#引擎之间平台自己的开销)）：组件在每种引擎上花的一样，整套的 CPU 也看不出差别；不同的是平台自己的内存，每台机器付一次——
无根 Podman 约 0.14 GiB，Docker 守护进程约 0.55 GiB，单节点集群约 2 GiB。机器越小越显眼。有根 Podman 省掉用户态网络的 CPU（整套的 9–10%）。

### 为无根 Podman 准备主机

用将来拥有这套部署的那个用户：

1. 装 Podman 与 Docker 的 Compose V2（`docker-compose`）。`podman compose` 自己没有 compose 实现，只是把调用转给这个程序，由它连 Podman；
   不需要装 Docker Engine 本身。`podman compose version` 应当打印 `Executing external compose provider ".../docker-compose"`；另一个项目 `podman-compose` 没有在 BrickKit 上验证过。
2. `systemctl --user enable --now podman.socket`——`brickkit up`、`down`、`status` 经它连 Podman。
3. `sudo loginctl enable-linger <用户>`——这个用户的服务在退出登录后继续运行，开机时不用有人登录也会启动。
4. `systemctl --user enable podman-restart.service`——开机时把容器再启动起来。
5. 1024 以下的端口（比如 `exposePort: 443`）无根的引擎不能直接发布：发布一个 1024 及以上的端口，由前面的网关接 443；或者在主机上调低 `net.ipv4.ip_unprivileged_port_start`。
6. 跑一遍[环境检查](../10-troubleshooting/01-up-down-issues.md#podman先跑一遍环境检查)，它实测容器之间能不能互通、能不能干净地删掉。

在 BrickKit 上验证过的是"无根 Podman，同一台机器上也装着 Docker"；只装 Podman 与 Compose 二进制的机器没有端到端验证过。

### Kubernetes

给已经有集群的，或者需要自愈、跨机器扩容的。它的代价：

- **集群自己的资源。** 单节点时控制面与 kubelet 是固定开销（[实测](#引擎之间平台自己的开销)约 2 GiB）：给一个小项目起一个单节点集群，买到的主要就是这份开销。
- **运维。** 需要真正的集群管理能力；执行 `up` 的机器要有 `kubectl` 与能连上集群的 context（`k8s.context`）。
- **崩溃时。** Pod 被重启，几秒内重新就绪；这几秒里发给它的请求会等待或失败。

本机进程不能与 `k8s` 组合：部署文件里 `mode: debug` / `mode: local` 碰上 `target: k8s`，装载阶段就被拒绝，报错指出是哪个条目（`components[N].mode`）——集群里的 Pod 到不了你的机器。

### 重启机器之后

容器是能长期运行的那种形态：容器崩了由引擎拉起，开机时由引擎再启动。每种引擎要具备的条件：

| 引擎 | 崩溃之后 | 开机时 |
| --- | --- | --- |
| Docker | 生成 `restart: unless-stopped` | Docker 服务设为开机启动（多数安装包已经设好；`systemctl is-enabled docker` 查） |
| 无根 Podman | 生成 `restart: always` | 给这个用户开 linger，并启用用户单元 `podman-restart.service`（[第 3、4 步](#为无根-podman-准备主机)） |
| 有根 Podman | 生成 `restart: always` | 启用系统单元：`sudo systemctl enable podman-restart.service` |
| Kubernetes | kubelet | 集群 |

- Podman 用 `always`，是因为它的开机单元只启动策略为 `always` 的容器；除此之外两种策略在 Podman 里行为相同。Docker 上用 `unless-stopped`，手动停掉的容器保持停止。
- 回来的是上一次 `up` 建出来的那些容器。`down` 会删掉容器，所以 `down` 之后重启机器什么都不会回来。
- 开机时由引擎自己启动容器：不按 `up` 等待的那个顺序（`depends_on`），迁移也不再跑——上一次 `up` 时已经跑过。一个组件比它的依赖先起来时，要一直重试，不能放弃；
  依赖重启时它本来也需要这样。
- 本机进程永远不会回来：没有谁重启它们，也没有谁开机启动它们。

## 决定二：拓扑——组件最终收拢成几个容器？

- **全部独立**：每个组件各自一个容器（或 Pod）。什么都不多写就是这个形态。
- **全部进外壳**：能合并的组件尽量编进少数几个外壳，一个外壳一个容器。
- **混搭**：一部分进外壳，一部分独立。这通常是常态，不是妥协：有些组件**结构上**就进不了外壳——一个由 nginx 提供服务的纯前端没有可以编进去的后端进程；
  一个无状态的网关常常故意保持独立，好按自己的负载单独扩缩容。

外壳自己是一个普通组件（`brickkit.yaml` 里标着 `kind: shell`），它能承载哪些成员写在它的 `component.yaml` 的 `shell.members` 里；
**这一次承载哪些**写在部署文件里——成员条目嵌在外壳条目的 `members` 下面。所以拓扑是**按部署文件**决定的：
开发机的 `deploy.yaml` 可以全部独立，生产的 `deploy.prod.yaml` 可以把几个成员收进外壳，`config/` 一个字都不用改。

**什么时候合并。** 每个进程的内存底线几乎完全由语言运行时决定——Go / Rust 8–20MB，Python / Node 40–90MB，JVM 200–450MB（各语言运行时的一般量级，你的组件以实测为准）。
20 个空闲的 Go 组件加起来不到半个 G；20 个空闲的 Spring Boot 组件，一件事都没做就已经 4–9G。保持全部独立，直到这笔账在你要部署的机器上真的算不过来；
合并之前先试更便宜的办法：给贵的组件换更轻的运行时（JVM 组件编成 GraalVM 原生镜像，内存底线从几百 MB 掉到几十 MB，部署形态不变）；确认拉高数字的组件是不是这次本来就可以 `mode: disable`。

**合并省多少**（[实测](#全部独立全部进外壳混搭组件本身)）：组件的内存约三分之一、CPU 14–28%，延迟看不出差别；整套的内存几乎不动，因为基础资源是最大的一块，
外壳的数据库连接又更大（[为什么](#为什么组件省了整套不一定省)）。合并稳定地省 CPU 与进程数；省内存，运行时越重越划算。

### 1. 全部独立 × 一台机器

**是什么**：每个组件一个 Compose 服务，`brickkit up` 端到端驱动：地址注入、健康检查、按依赖顺序启动、迁移。

**什么时候用**：组件数量单机装得下时的默认形态（见[什么时候合并](#决定二拓扑组件最终收拢成几个容器)）。

**好处**：每个组件能单独启停，出事只影响它自己；一个组件对应一个容器、一份日志、一个健康状态，排查最简单。

**代价**：每个组件各付一份运行时内存底线——这正是外壳存在的原因；单机形态，没有跨机器调度。

**值得知道**：觉得"装不下"之前先量（`podman stats`、`docker stats`），别照着表拍数字——50 个组件的项目可能只跑几个，因为大部分这次 `mode: disable` 了，或者没有谁需要它们。

### 2. 全部独立 × Kubernetes

**是什么**：每个组件一个 Deployment + Service，地址由集群原生的 Service DNS 解析。

**什么时候用**：集群资源宽裕，不需要用合并去换更低的内存底线。每个组件保留自己的 `replicas`、自己的 `resources`。

**好处**：真正独立的水平扩缩容；跨机器调度与故障恢复按组件生效。

**代价**：运维复杂度最高；组件多就意味着 Deployment / Service 对象多。

**值得知道**：K8s 下 `expose: true` 必须配 `hostname`（Ingress 按域名路由），`exposePort` 不起作用；漏配 `hostname`，`up --dry-run` 就会拦下。
`config/` 里假设了单机容器网络的地址，换到 K8s 要自己改——用部署文件的 `vars:` 按环境给不同的值最省事。

### 3. 全部进外壳 × 一台机器

**是什么**：尽量多的组件编进少数几个外壳；每个外壳一个 Compose 服务，成员不生成自己的服务容器。
调用方拿到的成员 `*_ENDPOINT` 就是成员自己的地址：`http://<成员的服务名>:<它自己的端口>`，和它单独运行时一样；这个名字解析到外壳——
是外壳容器的网络别名（K8s 上是选中外壳 Pod 的 Service）。调用方代码不用改，成员并进或拆出外壳时地址也不变。

**什么时候用**：第 1 格那笔内存账真的算不过来时——不要提前用。

**好处**：一个外壳只背一份运行时底线、一份连接池，而不是 N 份；容器少，启动快，要盯的日志和重启对象也少。

**代价**：共用一个外壳的成员共享故障域（一个成员崩溃，整个外壳重启，除非外壳造得足够小心），也共享扩缩容单位（没法单独给某个成员加副本）；升级一个成员要重建外壳。

**值得知道**：
- 成员的迁移**仍由平台跑**：用成员自己的镜像、自己的配置，外壳等它成功才启动（见 [与外壳的交互](../05-migration/04-shell-interaction.md)）。所以每个成员都必须有自己的镜像——外壳在本机运行时，从本地仓库编进去的成员除外：它从源码迁移（`local.migrationCommand`）。
- 本机构建的外壳镜像，`brickkit build` 会在标签里记下编进了哪些成员版本，`up` 拿它对照外壳 `component.yaml` 的 `shell.members`：
  对不上就停下（`IMAGE_STALE`），而不是让一个少编了成员的外壳悄悄跑起来。没有这个标签的镜像（手工构建的）只警告（`IMAGE_UNVERIFIED`）；
  拉取的镜像不查——发布出去的版本，镜像与 `component.yaml` 天然一致。
- 成员条目上描述"自己容器怎么部署"的字段（`replicas`、`resources` 等）在外壳里不生效；它们留着是为了成员回落成独立组件时生效。`expose` 例外：外壳替成员开放它的端口（一台机器上映射在外壳容器上，K8s 上是指向成员 Service 的 Ingress）。
- 放进外壳之后可能出现启动等待环，`up` 会拦下并给出三条出路（见 [成员管理](../04-shell/04-members-management.md#合并造成的启动环与-skipwaitfor)）。

### 4. 全部进外壳 × Kubernetes

**是什么**：同样的合并，对接集群：每个外壳一个 Deployment；每个成员一个 Service，`selector` 选中外壳的 Pod、端口用成员自己声明的端口；成员不生成自己的 Deployment。

**什么时候用**：集群资源真的紧张，把总开销压到最低比单独扩缩容某个成员更重要。

**好处**：同时拿到"合并省内存"和"K8s 自愈、跨机器调度"两边的好处。开了网络策略时，成员的调用方和依赖方会自动算进外壳的规则。

**代价**：第 3 格的每条代价原样成立；第 2 格的每条 K8s 代价也原样成立——合并不会降低 K8s 本身的要求。

**值得知道**：K8s 下 Pod 之间没有启动顺序，所以合并造成的等待环在这里不拦，`skipWaitFor` 写了也只警告、不生效；成员的迁移照样是它自己的 Job。

### 5. 混搭 × 一台机器

**是什么**：一部分独立容器，一部分在外壳里，`brickkit up` 一次驱动整套。谁在哪，完全由部署文件里条目的位置决定（顶层，还是某个外壳的 `members` 下）。

**什么时候用**：一个成熟项目通常的归宿，而且通常是**结构性**的，不是资源折中——前端、网关这类组件本来就不该进外壳。一个组件要单独扩容、单独升级或隔离故障时，
也是这样从外壳里拆出来。拿不准一次本地化交付该选哪一格时，这通常是答案。

**好处**：需要独立的地方独立，其余地方省内存；两种条目并排写在同一份部署文件里，不需要特殊处理。

**代价**：排查时要同时带着两套心智模型；合并那一半的代价和独立那一半的代价各自原样成立，混搭不会把它们平均掉。

**值得知道**：同一个组件的老版本独立运行、新版本在外壳里，可以零协调共存（见[文末](#多版本共存不用额外操心)）。

### 6. 混搭 × Kubernetes

**是什么**：第 5 格的混合拓扑对接集群：独立组件各自 Deployment + Service，成员的 Service 指向外壳 Pod。

**什么时候用**：资源不紧也不宽裕：大部分组件留在外壳里压住总开销，把真正需要独立副本数或资源配额的几个挑出来单独部署。
和第 5 格不同，这里的混搭常常是**资源调优**决定——一个结构上完全可以合并的组件，因为要单独扩缩容而被主动拆出来。

**好处**：资源分配最灵活；地址解析、网络策略原生支持混搭，不需要额外配置。

**代价**：同时背上完整的 K8s 运维代价和完整的合并代价；出问题时要查的地方最多：K8s 本身、外壳内部编排、普通容器。

## 主线之外：本机进程

有三种方式让组件以本机进程运行，不进容器。三种都用于开发、演示与试用，没有一种是交付。

| 方式 | 谁启动进程 | 适合 |
| --- | --- | --- |
| [容器加几个本机进程](#容器加几个本机进程)：部分条目写 `mode: debug` / `mode: local` | 你在 IDE 里（`debug`），或 `up`（`local`） | 改一两个组件，对着真实的其余部分 |
| [每个组件都是本机进程](#每个组件都是本机进程)：每个条目都写 `mode: local` | `up` | 在没有容器引擎的机器上演示或试用 |
| [平台之外，手动跑起来](#平台之外手动跑起来) | 你，不经过 `brickkit up` | 单个组件最快的开发循环；单独测外壳自己的编排 |

和容器相比，它们有几点相同：

- **不能长期运行。** `mode: local` 的进程只活在启动它的那次 `up` 会话里：`Ctrl+C` 或关掉终端就停，一个崩溃整个会话收尾。没有谁重启它，也没有谁开机启动它——
  BrickKit 没有常驻进程（见 [`mode`](../01-three-layers/03-deploy-yaml.md#mode跑不跑怎么跑)）。
- **运行时是这台机器的。** 进程用这里装着的工具链跑，不是镜像钉住的那个，所以两台机器可能用同一种语言的两个版本跑同一个组件。它的源码要在这台机器上。
- **它们的开销**（[实测](#引擎之间平台自己的开销)）：CPU 与容器一样。Go 组件的启动命令是 `go run`，它在自己编出来的程序旁边一直常驻；与容器混合时，
  本机进程经宿主机端口连容器，引擎的端口转发多转发一份这部分流量。

### 容器加几个本机进程

**是什么**：除了你标成 `mode: debug` 或 `mode: local` 的组件，其余都是真实容器。

- `mode: debug`：进程由你在 IDE 里启动，平台只负责让别人找到它。只能写在个人的 `deploy.local.yaml` 里。
- `mode: local`：平台从组件源码识别启动命令、启动这个进程（组件写了 `local.migrationCommand` 时先从源码跑迁移），在那次 `up` 运行期间看管它。

平台让其他容器把这个组件的版本化服务名解析到你的机器（`extra_hosts` 指向 `host-gateway`）；调用方拿到的服务名不变——`extra_hosts` 只改变它解析到哪里；
端口换成你的 `localPort`，缺省就是组件声明的端口，所以地址常常一个字都不变。

**什么时候用**：既要"其余部分是真实的"，又要"改这一个组件不想重新构建镜像"。它只是开发期的叠加手段，不决定生产拓扑。一台机器上的每种拓扑都能用：

- **其余全部独立**：最简单；本机进程依赖的一切拿到的都是平台算好的真实地址。
- **其余在外壳里**：本机进程依赖某个成员时，拿到的是真实的 `http://localhost:<端口>`——映射开在**外壳**的 Compose 服务上（成员没有自己的服务），端口是成员自己声明的、
  外壳本来就必须监听的那个。成员本身也能被拉出来：在 `deploy.local.yaml` 里给外壳条目 `members` 下的那个成员写 `mode: debug` 和 `localPort`，外壳这次就不承载它——
  外壳对 `BRICKKIT_SERVED_MEMBERS` 里少了一项的处理要正确。
- **其余是混搭**：不碰生产，却最接近"对着生产调试"，因为其余部分就是项目的真实形状；代价是要同时理解外壳合并、本机进程的地址和普通容器。

**好处**：组件代码零改动；可以同时拉出好几个组件，各用各的 `localPort`；不需要知道某个成员具体在哪个外壳里。

**代价**：连不上时要先问"这个名字解析到了我的机器还是某个容器"，而不是泛泛地查网络；`config/` 里手写的容器网络地址不会被改写。

**值得知道**：`mode: debug` 的组件有一份 `local-debug.<服务名>.env` 供 IDE 加载，多行值、含特殊字符的值都已按 shell 规则转义。
它的**数据库迁移不会替你跑**——迁移步骤跟着它的容器一起没了，你用组件在 `local.migrationCommand` 里写的命令从源码跑（见[不跑迁移容器的情况](../05-migration/01-migration-service.md#不跑迁移容器的情况)）。

### 每个组件都是本机进程

**是什么**：每个条目都写 `mode: local`。`up` 根本不启动容器引擎：它从源码跑每个组件的迁移，启动这些进程，在前台看管它们。组件要用的基础资源（比如数据库）要从这台机器连得上。

**什么时候用**：有人想看这个项目跑一次、或者试用一下，又不想在这台机器上安装、配置容器引擎：一次 `up` 起来，`Ctrl+C` 关掉。

**好处**：不要引擎、不要镜像、不用构建；CPU 与容器一样。

**代价**：上面每一条局限，对整个项目成立：会话结束就停，每个组件的语言工具链都要装好，重启机器之后什么都不剩。要长期运行时换成容器——部署文件去掉 `mode: local` 那几行，`config/` 不变。

### 平台之外，手动跑起来

没有任何东西阻止你把每个组件当成普通进程启动（`go run`、`uvicorn`，或者你的语言对应的命令），完全不经过 `brickkit up`。

**先说清边界：这不是平台管理的形态，平台甚至不知道它存在。** 依赖解析、环境变量注入、健康检查、迁移顺序、服务发现统统不会发生，因为你没调用它。
每个进程听哪个端口、真实部署会注入的每一个变量、启动顺序，全部要你自己还原。这是"CLI 跑完就退出、没有常驻服务"的直接结果：平台只在命令运行的那一刻存在。

它仍然完全正当、非常常见——通常是最快的开发循环（不用构建镜像，断点直接挂上去）。按拓扑有三种样子：

- **全部独立**：单组件开发最常见的起点，尤其项目里还没有外壳时。进程和它连的地址之间没有容器层，出问题只有两个变量要查。
- **单独一个外壳**：外壳自己的程序直接在你机器上启动，脱离容器层测它的多模块编排——启动顺序、健康检查、模块之间的故障隔离；几乎只有造外壳的人需要。
  `BRICKKIT_SERVED_MEMBERS` / `BRICKKIT_SERVED_MEMBERS_CONFIG` 要你自己拼（精确形状见 [JSON 注入](../04-shell/02-json-injection.md)），所以它只能证明外壳在你自己拼的数据下表现正确。
  外壳里的模块注册表要按**完整的组件 ID 加版本**做键，才能在真实部署里同时承载一个组件的两个版本——这个坑只有真的喂两个版本进去才会暴露，值得在这里故意练一遍。
- **混搭**：生产拓扑用上外壳之后，按真实的形态只起你要改的那几个——独立组件单独起，外壳照上一条。按真实形态还原，能在本地就撞上形态相关的 bug；
  没有任何东西检查你手工搭的"谁在哪"是不是和部署文件对得上。

**一个值得知道的技巧：让 CLI 替你算出环境变量。** 在 `deploy.local.yaml` 里临时把要手动跑的组件标成 `mode: debug`，跑一次 `brickkit up --dry-run`，
读生成的 `.brickkit/generated/local-debug.<版本化服务名>.env`——那正是一次真实部署会喂给它的完整变量。比如 `shop/order` 依赖外壳里的成员 `shop/stock`：

```text
COMPONENT_ID=shop/order
COMPONENT_VERSION=0.1.0
PORT=8083
SHOP_STOCK_ENDPOINT=http://localhost:18082
```

抄下需要的部分，再把那一行删掉（或 `brickkit local off`）。`deploy.local.yaml` 本来就不提交，不会影响任何人。
这个技巧覆盖不到一件事：你在 `config/` 里手写的、指向别的容器服务名的地址——平台不解析配置值的内容，不会替你改写，
这一点和 `mode: debug` 本身一样。只有 `host.docker.internal` 例外：在本机跑的进程拿到的是 `localhost`，除非本机把这个名字解析到回环地址。

## 多版本共存不用额外操心

这一页的哪种形态都不改变同一组件多个版本共存的行为。版本化服务名让共存与拓扑、与部署目标都无关：老调用方和新调用方、独立运行的版本和外壳里的版本，
都能在同一次部署里共存。平台不检查新老版本之间能不能正确协作——守住契约兼容是组件作者的责任（见 [多版本共存](../03-component-guide/09-multi-version-coexistence.md)）。

## 对比两个环境

每个环境一份完整的部署文件，所以对比两个环境用不着专门的命令，两次普通的 `diff` 就够：

1. `diff -u deploy.yaml deploy.prod.yaml` 看**你写了什么不同**。
2. 两次 `up --dry-run` 的输出做 `diff`，看**这些不同带来的后果**——哪些组件因此不启动、为什么。

下面是真实输出：`demo/caller` 强依赖 `demo/hello`、弱依赖 `demo/bus`；生产文件换成了 `k8s`，并关掉了 `demo/hello`：

```text
$ diff -u deploy.yaml deploy.prod.yaml
--- deploy.yaml
+++ deploy.prod.yaml
@@ -1,10 +1,8 @@
-# deploy.yaml —— 这个项目怎么部署：部署目标，以及哪些组件运行、怎么运行。
-# 团队文件：请提交它。个人的那份是 deploy.local.yaml（brickkit local on）。
-target: docker # docker | podman | k8s
-
+target: k8s
 components:
   - id: demo/hello
+    mode: disable
   - id: demo/bus
   - id: demo/caller
     expose: true
-    exposePort: 18080
+    hostname: shop.example.com
```

```text
$ diff <(brickkit up --dry-run 2>&1 | grep -v '^{') \
       <(brickkit up --dry-run -f deploy.prod.yaml 2>&1 | grep -v '^{')
1c1,2
< 🚀 启动项目 my-shop（target: docker）
---
> 使用 deploy.prod.yaml（--file）
> 🚀 启动项目 my-shop（target: k8s）
3,5c4,6
<    ✅ demo/hello@1.0.0   启动（demo/caller 需要）
<    ✅ demo/bus@1.0.0     启动（demo/caller 需要）
<    ✅ demo/caller@1.0.0  启动（顶层）
---
>    ⬜ demo/hello@1.0.0   显式禁用（mode: disable）
>    ⬜ demo/bus@1.0.0     不启动（上层都不启动）
>    ⬜ demo/caller@1.0.0  不启动（强依赖 demo/hello 不启动）
```

（第二段 `diff` 后面还有启动顺序与生成文件的差异，这里截掉了。）

第二段直接给出后果：不只 `demo/hello` 不启动，`demo/caller` 也跟着不启动（它强依赖 `demo/hello`），`demo/bus` 没有上层需要它，也不启动。
只看第一段的 `mode: disable` 那一行，推不出这些。

- `grep -v '^{'` 滤掉 CLI 写在 stderr 上的 JSON 日志行，否则它们混进人读的输出，`diff` 出一堆噪音。
- 这里比的是**启动决策**，不是生成的部署文件本身：一边是 `compose.yaml`，一边是一组 Kubernetes 清单，本来就没法逐行比。
