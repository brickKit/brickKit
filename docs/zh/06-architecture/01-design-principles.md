# 设计原则与取舍

[架构总览](00-overview.md)讲的是平台**做了什么**。这一篇讲它**为什么长成这个样子**：把整个设计串起来的那一个想法；BrickKit 用到（以及刻意没用）的那些工程想法，每个都从"它是什么"讲起，不假设你听过，并说清它对应 AI 开发的什么痛点、BrickKit 怎么做、BrickKit 不做什么、AI 怎么应对；以及每个设计提议都要拿来对照的十二条原则。

[AGENTS.zh.md](../../../AGENTS.zh.md) 里有同样的十二条原则，压缩成一行一条，写给 AI 助手拿去判断某个提议合不合适。这一篇是那些行背后的论证：每条原则是什么意思、换来了什么、付出了什么、拒绝了什么。下面十二个小节的标题，去掉前面的编号后，与 AGENTS.zh.md §4 逐字一致；两边一旦分叉、或编号错位，`make lint` 会失败。

## 贯穿一切的那一个想法：声明一张图，其余全部派生

你写两种声明。每个组件的 `component.yaml` 说它是什么、依赖什么；项目的 `brickkit.yaml` 说你要哪些版本、启用什么、暴露什么、数据库在哪。两者合起来，描述的是一张图。平台产出的其余一切，都是每次运行时从这张图**派生**出来的，每一条规则都能用一句话说清：

| 派生出的东西 | 从什么派生 | 规则 |
| --- | --- | --- |
| 哪些组件运行 | `enabled` 加依赖图 | 顶层组件默认运行；下层组件只要上面有需要它的在跑，它就跑；显式写了 `enabled` 则以所写为准。实现上算的是"谁不跑"的最小不动点，所以环不需要任何特殊处理 |
| 启动顺序 | 依赖图 | 拓扑排序。强依赖缺失在解析期就是错误，不是运行期的意外 |
| 服务名与地址 | 组件 ID + 精确版本 | `/` 和 `.` 变成 `-`，全小写，再拼成 `http://<服务名>:<端口>`——Docker 和 K8s 上是同一个字符串 |
| `*_ENDPOINT` 变量名 | 组件 ID | `/` 和 `-` 变成 `_`，全大写，末尾加 `_ENDPOINT` |
| 资源连接变量 | 资源的 `kind` 与它的绑定 | 以 `kind` 名作前缀：`DATABASE_*`、`REDIS_*` …… |
| `docker-compose.yaml` 或 K8s 清单 | Manifest 与 `deploy.target` | 每次运行重新生成；组件自己从不携带 |
| 网络策略 | 依赖图 | 需主动开启（`deploy.networkPolicy`）：流量沿着你声明过的依赖边放行 |
| 哪些源码目录处于活动状态 | 级联判定的结果 | `brickkit sync` 把不启动的归档、把要跑的还原 |

用"派生"代替"配置"，换来三样东西：

- **派生出的值不可能和它的来源不一致。** 变量名永远对得上组件 ID，地址永远对得上版本，网络策略永远对得上依赖关系，不存在"忘了同步的第二份"。对比一份手写的网关配置：里面烧进了版本化服务名，组件一升版本它就悄悄过期，还不会有任何提示。
- **派生可以双向推。** 从 `people/basic` 能算出 `PEOPLE_BASIC_ENDPOINT`；看到 `PEOPLE_BASIC_ENDPOINT`，也能确切知道它指向哪个组件。这就是依赖别名被拒绝的原因：别名只保住了这条双向关系的一半。
- **CLI 可以保持无状态。** 每个产物都是声明的纯函数，所以 CLI 读入声明、生成、交给 Docker 或 K8s、然后退出。两次运行之间没有任何需要记住的东西，也就不需要常驻进程。

**派生不是猜。** 派生值是你所声明内容的纯函数。平台从不推断你的意图：它不会替你选版本（`^1.0.0` 直接报错）、不会替你打开你没暴露的端口、不会自作主张认定某个缺失的弱依赖该降级成什么、也不会因为觉得你"大概想跑它"就把一个组件拉起来。算不出来的值，就由你声明。这就是这个想法与"精确优于隐式"这条原则的衔接方式——后者负责把前者拦在"猜"的门槛之外。

代价是：算不出来的东西必须写下来，而且逃生口刻意开得很窄——`labels` 与 `deploy.ingressAnnotations` 原样透传给底层引擎，平台不做任何解释。

## 认识这些想法

BrickKit 用到的、以及刻意没用的，都是软件工程里早就有的想法。你不需要事先认识其中任何一个：下面每个想法，都从"它是什么"讲起，再讲它的好处和代价、用 AI 写代码时它对应什么痛点、BrickKit 怎么做、BrickKit **不**做什么，最后讲 AI 该怎么应对。

**"BrickKit 不做的部分"** 指的是：平台故意不管、把决定留给组件作者（和 AI）的那部分。这是有意的取舍，不是"还没做"——每一条都有理由。

**怎么读：** 先看下面五张总表（按主题分组）。点第一列的名字，跳到对应编号的详细介绍。

### 1. 限界上下文 (DDD)

**它是什么：** 一个大系统里，同一个词在不同业务里往往不是同一件事——订单系统里的"客户"是下单的人，客服系统里的"客户"是等着被回复的人。DDD（领域驱动设计）的做法是按业务划出几块边界，每一块（一个"限界上下文"）有自己的词汇、规则和数据，块与块之间只通过明确的接口交换信息。比如一家网店，订单、库存、客服就可以各是一个上下文。

- **好处：**
  - 每块可以由不同的人独立理解、独立修改、独立发布，改一块不会牵动别的块。
  - 词汇不会互相污染：同一个词在不同的上下文里，各有各的精确含义。
  - 出了问题，容易判断是哪一块的事。
- **代价：**
  - 边界划错了很难补救——太细，块与块之间要不停地沟通；太粗，又回到一团乱。
  - 划边界得先真正弄懂业务，这本身要花时间。
  - 跨块的一致性更难保证：一件事要同时改两块时，没有一个事务能罩住两边。
- **AI 开发的痛点：** 系统一大，AI 一次读不完，改一处也不知道会牵动谁，只能连蒙带猜。
- **BrickKit 怎么做：**
  - 一个组件就是一块业务边界，有自己的仓库、Manifest（`component.yaml`）、版本和接口契约，是独立的发布单位、版本单位和权限单位。
  - 边界写在 `component.yaml` 里：它依赖哪些组件、提供哪些端口、需要哪些配置和资源。AI 只要读当前组件的 `component.yaml`，加上它依赖的组件的契约，就能开工，不用理解整个系统。
  - 组件小：项目自带的 10 个真实组件在 200 到 3500 行之间，AI 一次读得完。
  - 一个组件不该横跨两个上下文；一个上下文可以由一个或几个组件组成。必须同时成立的数据（比如"余额永远不为负"同时约束账户和流水）要放进**同一个组件**，因为组件之间没有跨组件事务。
  - 拆不拆，可以问三个问题（推荐的判据，不是平台的规则）：这两块数据之间有没有一条任何时刻都必须同时成立的不变量？它们要不要各自独立发版、归不同的人？拆开之后，调用方只靠契约能不能写出调用代码？
- **BrickKit 不做什么：**
  - 不管组件内部怎么建模（聚合、实体怎么划）。这是组件自治：平台只管边界，边界之内归作者。
  - 不强制隔离：几个组件是否共用一个数据库（比如用 schema 分组或主键前缀隔离）、是否合并进同一个进程（`servedBy` 外壳），由你按业务决定。共用数据库时要自己留意：迁移状态表的主键必须包含组件标识，否则各组件的迁移会互相覆盖。
  - 原因：平台一旦开始规定内部，就从编排器变成了框架，而框架只能产出一种形状的组件。
- **AI 怎么应对：**
  - 边界该画在哪，AI 替代不了：一个功能该拆成几个组件、哪些操作需要事务，是领域判断，要由你（和领域专家）来定。
  - AI 在划好的边界内工作，一次只写一个组件，写完跑通再写下一个。
  - 让 AI 读依赖方的契约，别读它的源码（见 [8. 契约先行](#8-契约先行)）。
  - DDD 术语与 BrickKit 机制的逐条对照，见[组件设计准则](../07-patterns/00-component-design.md#如果你的团队习惯用-ddd-的语言)。

### 2. 微服务与服务网格

**它是什么：** 微服务是把一个大程序拆成许多小服务，各自开发、各自部署，通过网络互相调用。服务网格是专门管"这些服务之间怎么通信"的一层基础设施：帮它们找到对方、分流、限流、失败重试、熔断（对方一直出错时先停止调用）。像把一家大餐馆拆成一条街上的许多小店。

- **好处：**
  - 各家小店可以独立开张、独立装修，用不同的技术，由不同的团队负责。
  - 一家出了问题，不至于整条街停业。
- **代价：**
  - 店多了，得有人管路牌（注册中心：谁在哪儿）、管入口（网关：外面的请求先到哪）、管排队限流（网格）——运维复杂度陡增。
  - 调用变成了跨网络：网络抖动、超时、对方只成功了一半，都成了要处理的情况。
  - 出了问题还得跨好几家店去查。
- **AI 开发的痛点：** 服务发现、配置中心、注册 SDK……这些概念都得 AI 去处理；组件之间调用失败时怎么办，AI 又常常只写了正常路径。
- **BrickKit 怎么做：**
  - 组件独立构建、独立部署、独立调用；每个组件都是一个容器（前端也是）。
  - 地址靠 DNS 加环境变量：调用方读一个变量（如 `PEOPLE_BASIC_ENDPOINT`，值是 `http://people-basic-1-0-0:8080`），不用理解服务发现。组件里不需要任何注册 SDK，零侵入。
  - 该有的能力，交给底层引擎原生提供：负载均衡是 Kubernetes Service 自带的；健康检查和重启是 Compose 的 `healthcheck` 和 Kubernetes 的 Probes；需要网关时，用 `labels` 把标签原样透传给 Traefik 这类工具，平台不理解标签的含义，只负责传。
- **BrickKit 不做什么：**
  - **注册中心：** Docker Compose 和 Kubernetes 自带的 DNS 已经免费提供了服务发现。自建一个还得保证它高可用；组件一旦接入自制的服务发现 SDK，就不再是"零侵入"。
  - **网关、网格、负载均衡：** 路由规则因业务而异，平台强行统一只会削足适履。如果你绕开 `labels` 透传，自己手写一份包含版本化服务名的路由配置，组件一升版本它就悄悄过期，平台不会提醒你。
  - **熔断、限流、重试：** 阈值和退避策略因业务而异，平台给一个默认值，既很难对所有场景都合适，也会限制某个组件真正需要的灵活度。等平台替你重试，什么都不会发生——一次瞬时的网络抖动会直接以未处理异常的形式冒出来。
  - **配置中心、热更新：** 那是长连接、推送、版本比对的一整套机制，而多数基础配置本来就必须重启才能安全生效。
  - **健康检查轮询：** Compose 和 Kubernetes 已经原生解决；平台自己做，要么得有个后台进程，要么得让每个组件都嵌入一份客户端库。
  - 共同的原因：每一样都意味着一个要长期运行、要有人运维的东西，而 BrickKit 的 CLI 是用完即走的。详见[平台刻意不做的事，以及为什么](00-overview.md#平台刻意不做的事以及为什么)。
- **AI 怎么应对：**
  - 重试、超时、降级、限流都是组件自己的代码，要明确要求 AI 写——它的错误处理常只覆盖正常情况。
  - `/healthz` 只让它检查进程自己，别顺手去探数据库或别的依赖：否则一个依赖一抖，所有上游会一起被判成不健康、一起重启。
  - 需要网关，用 `labels` 透传，别手写含版本号的路由配置。
  - 调别的组件，读环境变量里的地址，别让 AI 自己去做服务发现。

### 3. 六边形与分层架构

**它是什么：** 都是"程序内部怎么组织"的办法。分层是把程序切成上下几层（接收请求的、处理业务的、存取数据的），上层只调用下层。六边形架构更进一步：业务逻辑放在中心，数据库、网页接口、消息队列这些外部的东西，都通过事先约定的接口接上来。像厨房和外卖平台、收银机、供货商之间隔一层标准接口，换个供货商不用改菜谱。

- **好处：**
  - 业务逻辑不依赖具体的框架或数据库，更容易单独测试（比如用一个假的数据库替身）。
  - 更容易换掉某个外部系统。
  - 关注点分开，读代码时知道去哪一层找。
- **代价：**
  - 要多写不少接口和转换代码。
  - 间接层多了，读一条请求的完整路径要多跳几步。
  - 在小程序里，像给自行车装变速箱。
- **AI 开发的痛点：** AI 容易给简单功能堆出很多层抽象（过度设计），需要你主动要求简化。
- **BrickKit 怎么做：**
  - 不强制任何内部结构。平台只规定组件在**边界上**呈现的样子：一份 Manifest、一个健康检查、以及读环境变量（见原则「[组件自治](#2-组件自治)」）。
  - 有一份真实的分层参考：[用 Go 写一个 BrickKit 组件](../04-go-component-template.md)。它是一个依赖 PostgreSQL、带迁移的真实组件，`server.go` / `service.go` / `store.go` 分别是 HTTP 层、业务层、数据访问层，另有 `config.go`（只从环境变量读配置）和 `migrate.go`。
- **BrickKit 不做什么：**
  - 不规定内部怎么分层，也不要求用不用六边形。`brickkit new` 只生成一份能通过校验的 `component.yaml`，不生成任何代码结构，也不替你选语言。
  - 原因：平台一旦管到内部，就从编排器变成了框架，而框架只能产出一种形状的组件。
- **AI 怎么应对：**
  - 你要主动写明"够用就好"：比如"HTTP、业务、存取数据三层就够，不要为只有一个实现的东西加接口"。
  - 想要分层，就拿 Go 模板给它当样子，比只用文字描述可靠。
  - 想用六边形，得在给 AI 的要求里写明，平台不会替你选。

### 4. 声明式与 GitOps

**它是什么：** 让工具做事有两种说法。命令式是一步步告诉它"先做这个、再做那个"，像教厨师做菜；声明式是只写"我最终要什么"，怎么做由工具去算，像在菜单上点菜。GitOps 是把这份声明放进 Git，当作系统的唯一事实来源，再由一个一直运行的程序持续把真实状态拉向声明——真实状态和声明对不上，叫"漂移"，这个程序的工作就是发现漂移并纠正它。

- **好处：**
  - 声明本身就是文档：打开文件就知道系统该是什么样。
  - 放进 Git 之后，每次改动都能审查、能回滚。
  - 重复应用同一份声明，结果不变。
- **代价：**
  - 声明语言表达不了的事，就做不了。
  - 出了问题，你得理解"声明是怎么变成实际动作的"。
  - "持续拉回"那一半，还要有个常驻的程序一直盯着。
- **AI 开发的痛点：** 让 AI 写部署脚本：步骤多、有先后顺序、每个环境还要各写一份，改动又难评审。
- **BrickKit 怎么做：**
  - 你写两种声明：每个组件的 `component.yaml` 说它是什么、依赖什么；项目的 `brickkit.yaml` 说你要哪些版本、启用什么、暴露什么。两者合起来是一张图，其余的一切都由 CLI 从这张图**派生**（见本页开头的[贯穿一切的那一个想法](#贯穿一切的那一个想法声明一张图其余全部派生)）：哪些组件运行、启动顺序、服务地址、环境变量、`docker-compose.yaml` 或 Kubernetes 清单、网络策略。
  - 每个环境一份完整、自包含的文件，用 `brickkit up --config brickkit.prod.yaml` 选择。
  - `brickkit up --dry-run` 不启动任何东西，先把计划打印出来，让你（和 AI）先看再动手。
  - 想缩小启动范围，唯一的办法是改 `enabled`，没有 `--only` 这类参数。
- **BrickKit 不做什么：**
  - **持续拉回：** `brickkit up` 是一次性下发，CLI 用完就退出，没有任何东西一直盯着。有人手动改了运行中的容器，不会有程序替你改回去，要等下一次 `up` 才对齐。持续拉回需要一个常驻、要有人运维的程序。想解决"没人记得跑 `up`"而自建一个守护进程，你就重新造出了 BrickKit 刻意躲开的那个单点故障和攻击面（见原则「[平台极简](#1-平台极简)」）。
  - **多环境 overlay（基础层 + 覆盖层）：** overlay 要求你先在脑子里拼出"基础层、覆盖层、合并规则"才看得懂最终配置，Git diff 也看不出改动会不会波及别的环境。BrickKit 选的是每个环境一份完整文件：所见即所得，代价是文件之间会有重复。
  - **"你确定吗"的确认：** `brickkit.yaml` 就是声明，写了就执行。
- **AI 怎么应对：**
  - 让 AI 只改 `brickkit.yaml`，改完先 `brickkit up --dry-run` 看计划，再 `up`。
  - 不要手改运行中的容器：它们不会被自动改回去，下次 `up` 才会对齐。
  - 多个环境，让 AI 分别改各自完整的文件，别指望有继承。

**例：** `brickkit up --dry-run` 打印的计划（节选，来自[教程第 2 篇](../03-guide/02-what-runs.md)）——每个组件为什么启动、按什么顺序启动，一目了然：

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0   启动（demo/caller 需要）
   ✅ demo/caller@1.0.0  启动（顶层）
...
📋 启动顺序（拓扑排序）：
   1. demo-hello-1-0-0   无依赖
   2. demo-caller-1-0-0  ← 依赖 1
```

### 5. 约定优于配置

**它是什么：** 工具先替你定好一套规矩（叫什么名字、放在哪儿、默认怎么做），你照着来，就几乎不用写配置。Rails 是最有名的例子：一个叫 `User` 的模型默认对应数据库里的 `users` 表，照做就不用再写一行映射。

- **好处：**
  - 要写、要读的配置少。
  - 换个人接手，一眼就知道东西在哪儿。
- **代价：**
  - 规矩不合你的情况时，没有商量的余地。
  - 更麻烦的是"靠猜"的约定：规矩没讲清楚，工具悄悄替你做了决定，出错时你不知道它猜了什么。
- **AI 开发的痛点：** AI 要猜变量名、端口、服务地址；猜错了，变量只是悄悄不存在，往往没有任何报错。
- **BrickKit 怎么做：** 固定命名，全部由规则算出，不用猜也不用配：

  | 东西 | 规则 | 例子 |
  | --- | --- | --- |
  | 服务名 | 组件 ID + 精确版本，`/` 和 `.` 变成 `-`，全小写 | `people/basic` 1.0.0 → `people-basic-1-0-0` |
  | 服务地址 | `http://<服务名>:<端口>`，Docker 和 Kubernetes 上一样 | `http://people-basic-1-0-0:8080` |
  | 依赖地址变量 | 组件 ID 的 `/` 和 `-` 变成 `_`，全大写，加 `_ENDPOINT` | `PEOPLE_BASIC_ENDPOINT` |
  | 额外端口的变量 | 再加上端口名 | `PEOPLE_BASIC_GRPC_ENDPOINT` |
  | 组件自己的配置 | `configSchema` 的驼峰键变成大写下划线 | `defaultPageSize` → `DEFAULT_PAGE_SIZE` |
  | 资源连接变量 | 以资源的 `kind` 为前缀 | `DATABASE_*`、`REDIS_*` …… |

  这条规则是**双向**的：看到 `people/basic` 能算出变量名，看到 `PEOPLE_BASIC_ENDPOINT` 也确切知道它指向哪个组件。默认值也是约定：不写 `expose` 就不对外，不写 `enabled` 就跟着上层走。
- **BrickKit 不做什么：**
  - **不替你做决定：** 用哪个版本、暴露哪个端口、要不要启用某个组件，平台从不猜，必须你写明（见原则「[精确优于隐式](#5-精确优于隐式)」）。所以 BrickKit 自己的说法是"派生优于配置"：能从你写的内容**算出来**的才派生，算不出来的，你来写。
  - **不提供依赖别名：** 曾有人提议给依赖起个别名（`as: iam`）。别名只保住了双向关系的一半——`IAM_ENDPOINT` 没法追溯到它指向哪个组件，而排查"地址指错了"恰恰从这里开始。
  - 代价也是真实的：组件 ID 会原样变成每个调用方代码里的变量名，所以取名要用领域自己的词，别用实现细节的词。
- **AI 怎么应对：**
  - 变量名照规则推算，别让 AI 凭印象起。先让它读 `component.yaml` 里的 `dependencies`，再推变量名。
  - 版本、是否对外暴露、是否启用这类决定，要求它明确写下来。
  - 给组件取 ID 时，用业务的词。

### 6. 十二要素配置

**它是什么：** "十二要素"是一份写云上应用的经验清单，其中三条和配置有关：配置存在环境里（要素 III）、数据库和缓存这类后端服务当作可以随时换的"附加资源"（IV）、开发环境和生产环境尽量一样（X）。最常被引用的是第一条：配置（数据库地址、密码、别的服务在哪）不写死在代码里，而是在程序启动时从环境变量里读。

- **好处：**
  - 同一个镜像放到测试环境、生产环境都能跑，环境之间的差别只在"启动时给了哪些环境变量"。
  - 密码不进代码仓库。
  - 环境变量所有语言都能读，不依赖任何库。
- **代价：**
  - 环境变量只是一串扁平的文字，复杂的配置得自己编码解码。
  - 变量一多就难管；漏了，往往到程序真正用到它的那一刻才发现。
  - 改了配置还得重启才生效。
- **AI 开发的痛点：** AI 要处理不同环境的配置差异，一不小心就把地址、密码写进代码。
- **BrickKit 怎么做：**
  - 组件需要知道的一切，都以环境变量交给它：依赖地址（`*_ENDPOINT`）、平台通用变量（`COMPONENT_ID`、`COMPONENT_VERSION`）、数据库等资源的连接信息（`DATABASE_*`、`REDIS_*` 等）、组件自己的配置（`configSchema` 的键转成大写下划线）。
  - Docker 和 Kubernetes 上的地址格式完全相同，换环境只改一个字段（`deploy.target`），组件代码零改动。
  - `up` 时就查："漏了才发现"的代价被提前到部署那一刻——写错的配置键会警告，并猜你想写哪个；必填、没有默认值、项目里又没填的配置项，会直接拦下 `up`；配置键名撞上平台保留的变量，会警告并跳过（平台注入的值优先）。
  - 全部变量的完整清单见[环境变量注入契约](04-environment-variables.md)。
- **BrickKit 不做什么：**
  - **配置中心、热更新：** 那是长连接、推送、版本比对的一整套重机制；而连接池大小、超时这类基础配置，本来就只有重启才能安全生效。改配置就改 `brickkit.yaml`，再 `brickkit up`。真要毫秒级热更新的业务开关，组件自己去轮询 Redis 就行。
  - **校验配置的值：** `configSchema` 只是说明书，见 [9. 契约式设计](#9-契约式设计)。
- **AI 怎么应对：**
  - 只用 `os.environ.get()`（Java 是 `System.getenv()`）读变量；先读 `configSchema` 知道有哪些键、默认值是什么。
  - 弱依赖的变量可能根本不存在，绝不能写 `os.environ["X"]`，否则缺失时启动即崩（见 [10. 大声失败](#10-大声失败)）。
  - **一个已经核实的坑：** 声明成 `array` 或 `object` 的配置项，到了容器里**不是 JSON**——`["cn-east", "cn-north"]` 会变成 `[cn-east cn-north]`，`json.loads` 解析不了。需要结构化配置时，声明成 `type: string`，值写成一段 JSON 字符串，在组件代码里自己解析。
  - 改了配置，要 `brickkit up` 重启才生效。

**例：** 组件读配置的样子——强依赖、弱依赖、自己的配置，三种读法：

```python
import os

people = os.environ.get("PEOPLE_BASIC_ENDPOINT")             # 强依赖：一定存在
bus = os.environ.get("INFRA_REDIS_EVENT_BUS_ENDPOINT")       # 弱依赖：没在跑时根本不存在
page_size = int(os.environ.get("DEFAULT_PAGE_SIZE", "20"))   # 自己的配置：有默认值兜底

if not bus:
    ...  # 降级：怎么降级是组件自己的业务逻辑
```

### 7. 精确版本与锁文件

**它是什么：** 依赖别人的软件时，版本可以写成"范围"（如 `^1.0.0`，意思是"1.x 里最新的都行"），也可以写死一个具体版本（`1.0.0`，格式是 `主版本.次版本.补丁`）。锁文件（如 npm 的 `package-lock.json`）则是把第一次装出来的具体版本记下来，以后照着装。

- **好处：**
  - 今天装出来的和三个月后装出来的是同一份，不会因为别人发了个新版本，你的生产环境半夜悄悄变了。
  - 出问题时，确切知道跑的是哪一版，回滚也有明确的目标。
- **代价：**
  - 补丁和安全修复不会自己到来，升级得你动手改一行。
  - 长期不升级，会落后很多。
- **AI 开发的痛点：** AI 做"破坏性修改"（新版本和旧版本不兼容），会连累所有依赖它的组件；它也可能顺手写出 `^1.0.0` 或 `latest`。
- **BrickKit 怎么做：**
  - 只认精确版本：`^1.0.0`、`~1.0.0`、`latest` 都会在解析阶段直接报错，不拖到运行时。
  - `brickkit add people/basic` 不写版本时，CLI 会在那一刻查一次最新的可安装版本，把它作为**精确版本**写进配置——相当于自动生成锁文件。和"配置里写范围"的区别在于解析发生的时间：只解析一次，而不是每次都解析。
  - 版本号进入服务名：`people-basic-1-0-0` 和 `people-basic-2-0-0` 是两个不同的 DNS 名字，可以并排运行、互不冲突。
  - 变量名不带版本，变量**值**带版本：`DEPARTMENT_TREE_ENDPOINT=http://department-tree-1-0-0:8080`。调用方永远知道自己在跟哪一版说话，不存在隐式升级。
  - 见[核心概念](../01-concepts.md)。
- **BrickKit 不做什么：**
  - **版本范围解析：** 范围是"我机器上能跑、生产上炸"的常见原因。
  - **一个组件里并排写两个版本：** 同一份 `component.yaml` 的 `dependencies` 里，同一个组件 ID 只能出现一次——变量名不带版本，写两个版本会撞上同一个 `*_ENDPOINT`，后写的悄悄覆盖先写的。所以"并排共存"是**项目级**的能力，不是组件级的：`brickkit.yaml` 可以列两条版本，让不同的调用方各用各的。
  - **并排版本之间的数据兼容：** 平台只提供一块物理上的缓冲，破坏性变更是组织之间的协调问题，数据层是否兼容是你自己的责任。
  - 也不会问"你确定吗"：`brickkit.yaml` 里列了两个版本，就是你的意图。
- **AI 怎么应对：**
  - 让 AI 写 v2 时，新增一个版本条目，和 v1 并排跑，再慢慢把调用方迁过去；别覆盖 v1。
  - 让它永远写精确版本，不接受 `^` 或 `latest`。
  - 两个版本共用一个数据库时，迁移是否向下兼容要你和 AI 自己保证；迁移状态表的主键要包含组件标识。

**例：** 两个版本并排运行，只需在 `brickkit.yaml` 里各列一条（完整演示见[教程第 5 篇](../03-guide/05-upgrades-and-versions.md)）：

```yaml
components:
  - id: demo/hello
    version: 2.0.0
  - id: demo/hello
    version: 1.0.0
```

### 8. 契约先行

**它是什么：** 两个团队要对接，先把"接口长什么样"写成一份文件（HTTP 接口常用 OpenAPI，gRPC 常用 protobuf），双方各自照着实现，而不是写完一边、再让另一边去猜。像先约好插头的形状。

- **好处：**
  - 双方可以并行开发。
  - 不读实现代码，就知道组件对外承诺了什么。
- **代价：**
  - 契约文件要有人维护。
  - 契约与实现对不上的时候，比没有契约更糟——读的人信了一份过期的说明。
- **AI 开发的痛点：** AI 想调用另一个组件，只能去翻它的源码，靠猜。而源码里的内部实现并不是对外的承诺，依赖方一重构，AI 写的调用就坏了。
- **BrickKit 怎么做：**
  - 组件用 `artifacts` 把契约文件随 Manifest 一起发布，`brickkit add` 和 `brickkit fetch` 会把它们下载下来。`fetch` 只下载产物，不改 `brickkit.yaml`、不部署——用于调用另一个项目里的服务。
  - 市场要求闭源、且对外提供 API 的组件必须带上 `api-contract` 产物：代码可以闭源，契约不能。
  - 平台唯一的职责是确保 `files` 里的东西真的能送到要它的人手里。
- **BrickKit 不做什么：**
  - 不规定用哪种格式：`type` 和 `format` 是 CLI 从不解析的自由字符串（OpenAPI、protobuf、你自己的什么都行）。要解析格式，平台就得先理解 OpenAPI 和 protobuf。
  - 不检查实现是否真的符合契约。契约与实现是否一致，是组件自己的事。
- **AI 怎么应对：**
  - 让 AI 读依赖方的契约文件，别读它的源码——这样依赖方怎么重构都波及不到它。
  - 先写契约，再写实现；契约与实现是否一致，靠你自己写的契约测试（[分层测试](../07-patterns/01-testing.md)里的 L1）来验证。
  - 见 [AI 辅助开发指南](../05-ai-development.md)。

**例：** 一条产物声明（来自 `demo/hello`，详见[教程第 7 篇](../03-guide/07-consuming-artifacts.md)）：

```yaml
artifacts:
  - type: api-docs
    format: openapi
    description: HTTP API 文档
    files:
      - openapi.json
```

### 9. 契约式设计

**它是什么：** 每个函数或模块写明"我要求输入满足什么条件、我保证输出满足什么条件"，违反就立刻报错。像电器铭牌上写着"输入 220V、输出 12V"，接错了就跳闸。英文名 Design by Contract。

- **好处：**
  - 错误在离原因最近的地方被抓住。
  - 这些规则本身就是最精确的说明书。
- **代价：**
  - 规则写得太严，合法但没想到的用法也会被挡在门外；写得太松，等于没写。
  - 每次运行都检查，有开销。
  - 规则本身也要维护。
- **AI 开发的痛点：** AI 不知道一个组件接受哪些配置、什么取值范围，只能凭印象。
- **BrickKit 怎么做：** 只借"写下来"这一半。BrickKit 里最接近它的是 `configSchema`——严格说只是近亲，因为它只描述、不强制。
  - 组件用它写明自己有哪些配置项、什么类型、默认值、允许什么取值范围（`enum`、`minimum`、`maximum`、`pattern`），人和 AI 都读得到。
  - CLI 检查项目里写的配置键**名字**是否存在于 `configSchema`：写错会警告，并猜你想写哪个。组件根本没声明 `configSchema`、项目却写了 `config` 时，整块配置都不会生效，同样会警告。
  - 必填（`required`）、没有默认值、项目里又没填的配置项，会直接拦下 `up`，并点名是哪个组件的哪一项。
- **BrickKit 不做什么：**
  - **不检查配置的值。** 例如声明成 `type: integer` 的项被填成了字符串，CLI 不会拦；组件拿到字符串去 `int()` 才崩溃——发现的时间点是运行时，而不是 `brickkit up` 那一刻。
  - 分界线在于有没有运行时的安全网：值写错了，组件自己会崩，你一定会发现；名字写错了，变量只是悄悄不存在，组件走默认分支照常运行，没有任何东西提醒你。所以名字要查，值不查。
  - 而且一旦开始校验值就停不下来——枚举？范围？正则？`required`？JSON Schema 的能力很大，CLI 会越长越胖。值写错了怎么办（报错、降级、用默认值），也该由组件自己决定。
  - 详见原则「[configSchema 是说明书，不是安检机](#10-configschema-是说明书不是安检机)」。
- **AI 怎么应对：**
  - 让 AI 先读 `configSchema` 再写读取配置的代码，键名和默认值以它为准。
  - 配置值的校验（范围、枚举），让它写在组件启动时，失败就立刻退出，并给出清楚的报错。
  - 别让它把 `configSchema` 里的 `minimum` / `maximum` 当成平台会强制执行的东西。

**例：** 一段 `configSchema`，以及项目里把键名写错时 CLI 的真实警告（来自[分层测试](../07-patterns/01-testing.md)里的演示，把 `greeting` 写成了 `greetting`）：

```yaml
configSchema:
  type: object
  properties:
    defaultPageSize:
      type: integer
      default: 20
      minimum: 1
      maximum: 100
      description: 列表接口默认每页条数
```

```
⚠️ config 里有配置项不会生效：组件 demo/hello 的 greetting
   配置项：greetting
   原因：组件的 configSchema 里没有这一项，是不是想写 greeting？
   影响：这一项不会被注入任何环境变量；组件会使用它自己的默认值
```

### 10. 大声失败

**它是什么：** 程序发现自己不对劲时，立刻、明显地停下来报错，而不是假装没事继续往下跑。英文叫 fail fast。

- **好处：**
  - 错误暴露在最早、离原因最近的时候。
  - 最坏的 bug 不是崩溃，而是"悄悄给出一个看起来正常的错误答案"：崩溃你一定会注意到，错误答案不一定。
- **代价：**
  - 更严格意味着更多"拒绝"：一个多写了未知字段的文件、一个没做防御的组件，本来也许能凑合跑，现在直接起不来。
- **AI 开发的痛点：** AI 的错误处理常只覆盖正常情况，弱依赖缺失、迁移失败这类边界情况容易被漏掉。
- **BrickKit 怎么做：** 把错误尽量提前到 `up` 的那一刻，并且说清是哪里、为什么：
  - Manifest 里出现不认识的字段，直接拒绝，而不是悄悄忽略（Manifest 没有扩展字段的机制）。
  - 依赖里写了版本范围，解析阶段就报错。
  - 强依赖缺失，`up` 拒绝生成任何东西；写错的配置键会警告；必填、没有默认值、项目里又没填的配置项，会拦下 `up`。
  - 迁移失败，主服务不会启动；端口冲突，直接报错。
  - **最典型的是弱依赖：** 一个缺失的弱依赖**什么变量都不注入**，而不是注入一个空字符串。
- **BrickKit 不做什么：**
  - **不替组件决定怎么降级。** Redis 挂了，有的组件改查数据库，有的返回空列表，有的写本地文件稍后重试——这是纯业务判断，平台没法统一定义"降级"。平台唯一的动作，就是不注入对应的变量。
  - 代价也是真实的：组件读这个变量时若直接写 `os.environ["X"]`，变量缺失就启动即崩。这是刻意的：宁可启动时大声崩，也不要运行时悄悄错。
- **AI 怎么应对：**
  - 明确要求它处理"弱依赖缺失"和"迁移失败"这两个最容易漏的边界。
  - 弱依赖的变量用 `.get()` 读，并写明缺失时怎么办。
  - 入口对不认识的参数立刻报错退出。迁移容器和主服务用的是同一个镜像，只靠命令行参数区分；如果入口对未知参数"照常启动服务"，写错的迁移命令就会让迁移容器变成第二个服务，永远不退出，整个部署卡在 `Created`，而它自己的日志还说一切就绪。

**例：** 为什么缺失时不能注入空字符串（AGENTS.zh.md §9.13）。开发者忘了检查空值，写了 `requests.get(f"{ENDPOINT}/healthz")`：如果注入的是空字符串，拼出来就是 `/healthz`，请求会打到容器**自己**的端口，而它自己的 `/healthz` 返回 200——开发者于是误以为那个弱依赖是健康的。这类 bug 极难查。所以平台选择让变量根本不存在，让组件在启动时就大声崩。

### 11. 最小权限

**它是什么：** 每个程序、每个组件只拿到完成工作所需的最少访问权限，其余一律默认不通。像宾馆的房卡，只能开你自己那间房。在网络安全里它常和"零信任"一起被提起。

- **好处：**
  - 某个组件被攻破，或者只是出了 bug，它能碰到的东西有限，损失被限制在小范围里。
- **代价：**
  - 每一条允许的访问都要明确写出来。
  - 漏放一条，就是一次"莫名其妙连不上"的排查。
- **AI 开发的痛点：** 出了 bug 或被攻破，组件能碰到的东西越多，损失越大。
- **BrickKit 怎么做：**
  - **默认不可达：** 没有端口映射，就不能从外部访问；不写 `expose`，就没有对外入口（Kubernetes 上则不生成 Ingress）。
  - **网络策略：** 在 Kubernetes 上，`deploy.networkPolicy.enabled: true` 会从依赖图直接算出网络策略——流量只沿着你声明过的依赖方向放行，不需要另外手工维护一份访问控制列表。依赖图之外的访问者（比如 Ingress 控制器、另一个团队的命名空间），用 `allowFrom` 手写放行。还可以打开出站方向的策略（`egress`），并在 `allowTo` 里说明资源在哪。
  - **ServiceAccount：** `serviceAccount: { enabled: true }` 会给每个组件一个单独的 ServiceAccount，且不挂载令牌。
  - CLI 本身从不挂载 Docker socket。
  - 见[网络策略与最小权限](../03-guide/11-network-policy.md)。
- **BrickKit 不做什么：**
  - **不默认开启**网络策略、ServiceAccount 隔离和 `podSecurity: restricted`：每一项都可能让一个本来能跑的组件起不来，这是真实的、因项目而异的代价，平台没法替你权衡。
  - **验证不了网络策略是否生效：** 很多集群接受这些对象却完全不执行——`kubectl apply` 成功、`kubectl get networkpolicy` 看得见，流量却照样畅通无阻，而且没有任何报错。minikube 和 kind 的默认网络插件（CNI）就属于这一类。Kubernetes 没有提供查询这件事的 API，平台测不出来，所以 `brickkit up` 每次都会警告你自己验一次。
- **AI 怎么应对：**
  - 让 AI 只声明真正需要的依赖：依赖越少，放行的路越少。
  - 只有需要对外提供服务时，才写 `expose`。
  - 要不要开启网络策略和 ServiceAccount 隔离，由人来判断；开启之后，按教程里的办法验证"授权的路径照常能用、未授权的路径真的被挡住"，别只看生成的 YAML 说得通。

**例：** 给 `demo/hello` 自动生成的网络策略——`demo/caller` 是它唯一的调用方，所以放行的来源只有它，端口只有 `demo/hello` 自己监听的那个：

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
spec:
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: demo-caller-1-0-0
      ports:
        - port: 8080
          protocol: TCP
  podSelector:
    matchLabels:
      app: demo-hello-1-0-0
  policyTypes:
    - Ingress
```

### 12. 供应链安全

**它是什么：** 你安装的第三方组件，是不是真的出自它声称的作者？有没有在半路被人调包？像快递上的封条加发件人签名。

- **好处：**
  - 能防止冒名顶替。
  - 能防止传输途中被篡改。
- **代价：**
  - 签名只能证明"这是谁发的、没被改过"，不能证明"发的东西没有恶意"。
  - 你还得自己管理"信任哪些公钥"，发布者也要保管好私钥。
- **AI 开发的痛点：** 让 AI 引入第三方组件时，来源难以核实。
- **BrickKit 怎么做：**
  - **发布：** 发布者用 cosign 签名（`brickkit publish --sign --key ...`）。真正被签名的是一份"规范化载荷"——Manifest 解析后按固定规则重新编码——所以注释、缩进、键的顺序改了，都不会让签名失效；带重复键的 Manifest 会被直接拒绝，免得不同解析器读出两种含义。
  - **镜像摘要：** `brickkit publish` 默认先把可变的镜像 tag 解析成摘要再签名，这样签名覆盖的是一个事后没法被悄悄改指的引用；要跳过得显式加 `--no-pin-digest`，并且会打印一条点名风险的警告。
  - **安装：** 安装方只用 Go 标准库验签，不需要装 cosign。信任的公钥配在你自己项目的 `installer.publicKeys` 里，`requireSignature` 默认为 `true`。
  - **状态与可见性：** 组件版本有 `draft` / `stable` / `deprecated` / `blocked` 四种状态，可见性有 `public` / `private`。
  - 见[签名与信任模型](06-signing-and-trust.md)。
- **BrickKit 不做什么：**
  - **不做事前审查：** 不扫描、不沙箱、不做静态分析。安装即信任，和 npm、VS Code 插件市场、GitHub 是同一套模型。事前审查要么误报太多（拦下正常组件），要么漏报太多（放过精心伪装的恶意代码），成本高、可靠性低。事后发现恶意组件，唯一的手段是把它标成 `blocked`，阻止新的安装。
  - **不从市场取公钥：** 否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉，验证照样通过，等于市场给自己发证书。
  - **注意：** 一把公钥都没配，签名验证就是**完全关闭**的，`requireSignature: true` 也不起作用（CLI 会警告一次）。
- **AI 怎么应对：**
  - 引入新组件、往 `publicKeys` 里加信任的公钥，都由人来确认，别交给 AI。
  - 别让 AI 为了"让安装通过"而关掉 `requireSignature`，或删掉 `publicKeys`。

### 13. 类型驱动开发

**它是什么：** 用编程语言的类型系统把规则"写进代码的形状里"，让错误的写法根本编译不过。比如订单金额不用随便一个数字，而用一个专门的"金额"类型，这样就不会误把"数量"当"金额"传进去。

- **好处：**
  - 一大类错误在编译时就被挡住了，不用等到运行才发现。
  - 类型本身就是一份不会过期的文档。
- **代价：**
  - 依赖语言：不是所有语言的类型系统都足够强（动态语言可以靠类型注解加检查器，比如 Python 的类型注解加 mypy，拿到一部分好处）。
  - 类型设计本身也要花功夫，设计得不好会变成负担。
- **AI 开发的痛点：** AI 写的代码读起来通顺，但对不对，光看代码看不出来，得有机器去查。
- **BrickKit 怎么做：** 没有，也不需要。BrickKit 的 CLI 自己是用 Go 写的，受益于类型检查，但并不要求组件也这样。
- **BrickKit 不做什么：**
  - **不限制语言，而且是最彻底的一种不限制：** 任何能构建出容器镜像的语言都行。仓库自带的夹具就有三种：`people/basic` 是 Python，`auth/password-login` 是 Go，`portal/user-frontend` 是 nginx 托管的纯 HTML。语言无关是这个平台的核心价值之一。
  - **不提供 SDK：** 平台在组件代码里唯一的痕迹，是读环境变量。因此平台交给组件的一切都是**字符串**（数字、布尔值也是），转成类型是组件自己的事。
- **AI 怎么应对：**
  - 选一门带类型检查的语言让 AI 写，让编译器（或类型检查器）当第一道关：写完先过编译，再谈别的。
  - 在组件启动时，把环境变量一次性读成一个有类型的配置结构，缺了必需项就立刻启动失败，别悄悄退化成默认值。[用 Go 写一个 BrickKit 组件](../04-go-component-template.md)里的 `config.go` 就是这样做的：缺了 `DATABASE_HOST` 这类必需项，启动即失败并一次列出缺了哪几个，绝不退化到 `localhost`（见 [10. 大声失败](#10-大声失败)）。
  - 见[从零开发自己的第一个组件](../03-guide/10-build-your-own.md)。

**例：** 类型怎么让错误的写法编译不过（Go）：

```go
type Cents int64   // 金额，单位：分
type Quantity int  // 数量

func charge(amount Cents) { /* ... */ }

var qty Quantity = 3
charge(qty) // 编译不过：Quantity 不能当 Cents 用
```

### 14. TDD 与 BDD

**它是什么：** TDD（测试驱动开发）是先写测试，再写让测试通过的代码：先让测试变红，再写实现让它变绿。BDD（行为驱动开发）是先用接近日常语言的"给定……当……则……"描述期望的行为，再把它变成测试。像先写好验收标准，再开始做菜。

- **好处：**
  - 测试成了对"代码该做什么"的约束，而不是对"代码已经做了什么"的复述。
  - 需求变得可以检验。
- **代价：**
  - 前期要投入时间。
  - 如果验收标准本身写错了，你会非常认真地把错的东西做出来。
- **AI 开发的痛点：** 让 AI 先写实现、再补测试，测试就成了对实现的复述——测的只是"代码做了它做的事"。而且 AI 生成的测试常只测正常场景，边界场景容易漏。
- **BrickKit 怎么做：** 不强制，但给了建议：
  - [分层测试](../07-patterns/01-testing.md)讲怎么给组件分层测试：L1 契约测试（接口的形状）、L2 业务规则测试（不变量、幂等、合法的状态迁移）、L3 单元测试（这一版实现的分支）、L4 集成测试（接真实依赖跑端到端）。区分 L2 和 L3 只需要一条判据：把实现整个删掉、换一种语言重写，这条测试还应该成立吗？成立就是 L2。
  - 还给了一个"先立规格、再写实现"的推荐顺序（见下表）。BrickKit 的组件恰好有三份不依赖实现的规格，都写在 `component.yaml` 里：`configSchema`、`dependencies`、契约文件。
  - BrickKit 独有的一点是 `brickkit up --dry-run`：它不起任何容器，就能检查 `component.yaml` 与 `brickkit.yaml` 是否对得上（比如配置项名写错）。
- **BrickKit 不做什么：**
  - 不要求也不检查怎么测试：测试策略从来不在平台的管辖范围内，这是组件自治的一部分。
  - `--dry-run` 查的是**装配对不对**，不是**组件代码对不对**。
  - 顺便说清楚证据：分层测试这套方法来自一个真实生产部署（14 个组件）的复盘；"先立规格、再写实现"这个顺序是推荐做法，还没有同样的实战背书，用不用由你判断。
- **AI 怎么应对：**
  - 按顺序来：先规格，再测试、看着它们变红，最后才让 AI 写实现。红得要有理由：如果测试第一次运行就是绿的，说明它什么都没测到。
  - 把业务规则先写成一句"给定……当……则……"，再翻成测试。比如"给定一个还没处理过的幂等键；当两个带着同一个幂等键的请求同时到达；则只有一个真正执行，另一个拿到同一份结果"——这句话本身就是给 AI 最精确的提示。
  - AI 常只测正常场景，边界场景要你自己补，或者明确要求。
  - L4 要打真实依赖跑一遍，别只信替身（mock）。

**例：** 推荐的顺序，每一步都有真实的反馈：

| 步 | 做什么 | 怎么知道这一步对了 |
| --- | --- | --- |
| 1 | 把 `component.yaml` 写完整：`dependencies`、`configSchema`、契约文件 | `brickkit up --dry-run`（不起容器） |
| 2 | 照契约文件写 L1 契约测试 | 此时必须全红，而且红得有理由 |
| 3 | 把 L2 的每条业务规则先写成一句话，再翻成测试 | 同样必须先红 |
| 4 | 让 AI 写实现，直到 L1、L2 全绿 | 测试就是验收，不需要人逐行读实现 |
| 5 | 补 L3：当前这版实现的各条分支 | 分支都走到 |
| 6 | 跑 L4：`brickkit up` 起真实依赖，走一遍真实链路 | 端到端跑通 |

---

### 15. 属性测试

**它是什么：** 普通测试是你手写几个例子：输入 A 应该得到 B。属性测试换一种思路：你描述"无论输入是什么，结果都应该满足的性质"（比如"排序之后的列表一定是有序的，而且长度不变"），再让工具随机生成成千上万组输入，去找出违反这条性质的反例。

- **好处：**
  - 能撞出你自己想不到的边界情况。
  - 找到反例后，工具通常会把它缩小到最小的能复现的样子。
- **代价：**
  - 想清楚"性质"本身不容易。
  - 随机测试的失败要能复现，所以得记录随机种子。
  - 对大量依赖外部系统的代码不太好用。
- **AI 开发的痛点：** AI 生成的测试常只覆盖它自己想到的那些正常场景。
- **BrickKit 怎么做：** 平台自己在用。CLI 里规则最密的三处，都有用随机输入去验证的测试：
  - **启停判定（`cascade`）：** 用数千个随机小图（最多 6 个组件，涵盖三态的 `enabled`、强弱依赖、弱依赖成环、多个上层共享），去对拍一份独立写的暴力参照答案。这份参照物不复刻平台的传播算法，而是枚举全部候选集合，取满足文档逐条规则的最大集合——两边只共享规则、不共享算法。
  - **启动顺序（`resolver`）：** 验证"依赖先于依赖方""每个组件恰好一次""删掉全部弱依赖边，顺序不变""打乱输入顺序，结果相同"这些性质。
  - **资源配额合并（`inject`）：** 验证逐字段的优先级、`limits` 没有默认层、把结果再合并一次不变。
  - 全部固定随机种子，失败信息带种子，可以原样复现；不依赖任何新库。验证这些测试是否真的有效时，曾往三处实现里各植入两个 bug，六个全被抓到；三处实现也都对得上文档里的规则。
  - 对组件，只是在[数据构造指南](../07-patterns/02-data-construction.md)里提到过：属性测试适合"核心不变量"（比如余额永远不为负、状态机不会走到非法的迁移），它需要大量数据，但理由和种子数据不同——是为了尽可能让随机输入撞上边界，而不是为了体验完整。
- **BrickKit 不做什么：**
  - 不要求、也不推荐给组件：适用面比较窄，主要适合核心不变量；对多数业务代码，普通的例子测试就够了。
  - 不提供属性测试的框架或库：平台自己用的是标准库的随机数。
- **AI 怎么应对：**
  - 有核心不变量时，先用一句话把它写下来（"账户余额永远不为负"），再让 AI 据此写属性测试。
  - 其余情况不必：别为了用而用。

## 十二条原则

### 1. 平台极简

CLI 能不做的事就不做。每多一个功能就是永远多一份维护成本，而平台的全部工作只是：把组件连起来，把它们的声明翻译给 Docker 或 K8s。

**为什么。** 底层引擎本来就做得好的事——DNS、健康探针、重启策略、负载均衡——由它们来做，比平台自己造一份副本更好。一个长出运行时的平台，会变成你还得多养活的一样东西。

**代价。** 人们最先想到的那些东西这里没有：没有网关、没有配置中心、没有注册中心。[拒绝清单](00-overview.md#平台刻意不做的事以及为什么)写明了每一项该怎么替代，以及你要是硬造一个会看到什么。

**拒绝了什么。** 常驻控制面、注册中心、健康检查轮询、配置中心、服务网格。

---

### 2. 组件自治

语言、框架、API 风格、事务、日志格式，都归组件自己。平台只要求三样：一份 Manifest、一个健康检查、以及组件去读它的环境变量。

**边界在哪。** 影响组件**之间**怎么协作的，平台管：怎么声明、怎么寻址、怎么配置、怎么依赖。影响组件**内部**怎么写的，平台不强制：用什么架构、怎么建模、怎么分层、怎么测试（[patterns/](../07-patterns/README.md) 里有建议，但没有任何东西检查）。这不等于平台对容器没有要求——它规定的是容器在**边界上**呈现的样子：入口对不认识的参数必须立刻报错退出（迁移容器与主服务用的是同一个镜像）、弱依赖的环境变量要用 `.get()` 读（缺失时平台根本不注入）、`/healthz` 只查进程自己、冷启动超过 30 秒要设 `startPeriodSeconds`。这些都是边界上的契约，不是对内部代码结构的干涉。平台一旦开始管边界之内，它就从"编排器"变成了"框架"——而框架只能产出一种形状的组件。

**为什么。** 这才让"任何能构建 Docker 镜像的语言"这句话成立。也因此前端组件只是另一个监听端口的容器：没有"静态"组件这个类型，CLI 里也就不会蔓延出到处是 `if type == static` 的分支（AGENTS.zh.md §9.10）。

**代价。** 边界之内的事平台帮不上忙——没有共享 SDK，不校验业务配置，对你怎么组织代码不表态。

**拒绝了什么。** SDK、sidecar、agent；特殊的组件类型；由平台定义的降级行为。

---

### 3. 渐进式

不需要先把整个系统设计完。加一个组件，跑起来；再加一个，再跑；随时可以停，随时可以继续。

**为什么。** `brickkit add` 一条命令拉下一个组件的整棵依赖子树；`enabled` 跟着上层走，没人需要的就不在跑；`brickkit sync` 让源码目录只剩你正在看的那几个。这也是为什么五十个组件并不意味着五十样东西要装在脑子里：你只需要知道直接依赖的契约（通常一到三个），五十个组件的项目在本地可能只跑四个容器，传递依赖是 CLI 的事（AGENTS.zh.md §9.15）。

**代价。** 平台限定的是你**每个组件**需要知道的东西，而不是整体能长到多大。没有任何东西拦着你长出一个一次装不进脑子的系统。

**拒绝了什么。** 一个必须先完整、然后才能跑起任何东西的设计阶段。

---

### 4. 环境无关

组件代码永远不知道自己跑在 Docker 还是 K8s 上。它读到的地址在两边都是 `http://<版本化服务名>:<端口>`，一个字节都不差。

**为什么。** 一份 Manifest，两种环境。组件描述的是"我是什么、我需要什么"，从不描述"我跑在哪"，所以它不带 `docker-compose.yaml`，也不带任何 K8s 清单（AGENTS.zh.md §9.4）。切换环境只改一个字段：`deploy.target`。

**代价。** 平台必须为两种引擎都生成正确的文件，而只有某一种引擎才能做到的事，从组件这一侧表达不出来。针对引擎的提示走 `labels` 透传，平台不解释它。

**拒绝了什么。** 按环境区分的组件文件；Manifest 里出现针对某个引擎的字段。

---

### 5. 精确优于隐式

精确版本、显式暴露、显式启用。凡是平台不得不猜的，就让你自己说。

**为什么。** 范围版本是"我机器上能跑，生产上炸"的经典来源（AGENTS.zh.md §9.2）。钉版本仍然只发生一次，在 `add` 的时候，和锁文件的做法一样：不写版本，CLI 就向安装源问最新的可安装版本，把确切的结果写到磁盘上。暴露是主动开启的，因为对它的一次猜测，就是悄悄做出的一个安全决定。

**代价。** 要多写一些。就连没写 `enabled` 也是刻意的：它的意思是"跟着上层走"，不是"没设置"。

**拒绝了什么。** 范围版本（是错误，不是警告）、隐式暴露、依赖别名、一切"自动探测"。

---

### 6. 安全默认

你不说，就什么都不可达。不映射端口，外部就访问不到；不声明 `expose`，就没有 Ingress；`private` 表示未经授权不可见。

**为什么。** 什么都不写时得到的，应当就是安全的那个状态。CLI 用完即走、没有监听端口，也从不挂载 Docker socket，所以平台自己不增加任何攻击面。

**它止步于哪里。** 这条原则管的是**可达性**，并不延伸到 K8s 的每一个默认值。`serviceAccount.enabled` 与 `podSecurity: restricted` 都是需主动开启的，因为它们任何一个都可能让一个已经能跑的组件起不来，而这是取决于具体项目的代价，平台没法替你权衡。不写 `serviceAccount: { enabled: true }`，每个 Pod 就用命名空间的 `default` ServiceAccount 运行，它的 token 照常挂载。

**拒绝了什么。** 任何默认就打开一条通路的做法。

---

### 7. 开源优先

CLI 与市场都开源。闭源组件通过市场受控分发。

**为什么。** 你把部署交给它的平台，应该是你读得懂的。闭源是一个商业事实，不该被禁止，所以市场用 Manifest 与镜像引用取代 Git 仓库来存放它。它唯一不允许一直闭着的是契约：提供 API 的闭源组件必须声明 `api-contract` 产物（[市场指南](../03-guide/08-marketplace.md)里能看到这条拒绝）。

**代价。** 让闭源组件保持闭源，是发布者自己的工作，而且拉下镜像就等于交出了它要运行的每一个字节——见[闭源组件的镜像安全规范](../07-patterns/04-closed-source-image-hardening.md)。

**拒绝了什么。** 私有的 CLI 或市场。

---

### 8. 平台提供工具，不替人做决定

只给机制，不定策略。多版本默认共存；降级逻辑归组件；破坏性变更是组织协调问题，版本共存只是它的一个物理缓冲。

**为什么。** `people-basic-1-0-0` 和 `people-basic-2-0-0` 是两个不同的 DNS 名字，所以共存对平台来说没有成本，也就没什么需要它去问"你确定吗"——`brickkit.yaml` 里把两个都列出来，**本身**就是意图（AGENTS.zh.md §9.3）。Redis 挂了以后组件怎么办——查数据库、返回空列表、写文件稍后重试——是业务逻辑，不同组件的正确答案不一样（AGENTS.zh.md §9.7）。

**代价。** v1 与 v2 之间的数据层不兼容，或者缺了降级，平台救不了你。这两样都是你的。

**拒绝了什么。** 弱依赖降级、通信治理（熔断、限流、重试）、多租户。

---

### 9. 安装即信任

和 npm、VS Code 插件市场、GitHub 是同一套模型：安装一个组件，就是信任它。平台不做前置审查——不扫描、不沙箱、不做静态分析——只在事后出手：确认为恶意的组件会被标为 `blocked`，阻止新的安装。

**为什么。** 前置审查要么误报太多，拦下正常的组件；要么漏报太多，放过精心伪装的恶意代码。`blocked` 作为最后一道防线，成本低而且足够有效（AGENTS.zh.md §9.11）。市场是"集市"，不是"保险库"。

**它确实提供的。** 签名。发布者用 cosign 签名；安装方只用 Go 标准库验证。公钥必须放在**你自己**的项目里（`installer.publicKeys`），而不能从市场取——否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉，验证照样通过。一个公钥都没配时，验证整体关闭，CLI 会告警一次。细节见[签名与信任模型](06-signing-and-trust.md)。

**代价。** 你自己要对"从谁那里安装"负责。

**拒绝了什么。** 由平台提供的第三方安全审查。

---

### 10. configSchema 是说明书，不是安检机

`configSchema` 记录的是组件自己的配置：类型、默认值，以及 `enum`、`minimum`、`maximum`、`pattern`（会被解析并保存，但从不强制执行）。CLI 不校验你填进 `config` 的**值**。但它会查**键名**：写了 `properties` 里没有的键，会警告，并猜你想写的是哪一个。

**界线为什么划在这里。** 划线的依据是：有没有运行期的安全网。**类型**写错，会大声失败——组件拿到 `"abc"`，对它调 `int()`，崩溃，你一定会注意到。**键名**写错，则是悄无声息地失败：那个变量压根不会出现，组件落进它的默认分支，运行得完全正常，只是不是你配置的那个样子。所以平台去抓那个否则看不见的失败，放过看得见的那个。它还只是一次存在性检查，没有后续的追问；而值校验一旦开了这扇门，就得一路回答要不要校验 `enum`、`minimum`、`pattern`，最后把整个 JSON Schema 都装进 CLI（AGENTS.zh.md §9.12）。

**一个很窄的例外。** 列在 `required` 里、又没有 `default` 的键，会让 `up` 直接失败。道理是同一个：缺失的项否则会悄悄地不存在，组件会看起来健康地跑着，只是有一条调用路径永远走不通。

**代价。** 这些声明不是保证。用户完全可以给一个 `minimum: 1` 的键填 `0`，`up` 时没有任何东西拦他。写下它们换来的是：人和 AI **看得见**预期的范围；报错、截断还是回退到默认值，由组件自己决定。

**拒绝了什么。** 任何形式的值校验。

---

### 11. 一个组件一个仓库

不支持 monorepo 里拆子目录当组件。组件是独立的发布单元（它有自己的版本——monorepo 你要怎么打 tag？）、独立的移动单元（`brickkit sync` 搬的是整个目录，连 `.git` 一起），也是独立的权限单元（有自己的可见性和发布者）。

**为什么。** 两个组件一旦共用一个仓库，这三个单元都会坏（AGENTS.zh.md §9.16）。

**代价。** 通常情况下没有：同一块业务的几个部分——proto、后端代码、迁移脚本——属于**同一个**组件，不需要拆开。这条规则说的是组件，不是文件。

**拒绝了什么。** 子目录形式的组件。

---

### 12. brickkit.yaml 就是声明

配置即意图。写了就执行，CLI 不反问"你确定吗"。

**为什么。** 期望状态在这份文件里，实际状态在 Docker 或 K8s 里；CLI 在两者之间不持有任何东西。每个环境一份完整、自包含的文件（`brickkit.prod.yaml`，用 `--config` 选择），没有 overlay、继承或合并规则。打开一个文件就能看到全貌，Git diff 一眼能读懂，对基础层的改动也永远不会悄悄影响到生产（AGENTS.zh.md §9.9）。

**代价。** 各环境文件之间会重复几行。而且你写了什么，跑的就是什么：用 `enabled: false` 收窄范围，下一次 `up` 就生效；想放宽回来，`git checkout brickkit.yaml`。

**拒绝了什么。** Overlay 与继承；确认提示。
