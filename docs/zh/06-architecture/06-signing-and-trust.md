# 签名与信任模型

AGENTS.zh.md §5.9 用一句话概括了信任模型：发布者用 cosign 签名，安装者用 Go 标准库验签，平台唯一的事后防线是把组件标成 `blocked`。这篇文档讲的是这句话背后的实际机制——真正被签名的到底是什么、签名和验签为什么用了两套完全不同的工具、公钥为什么绝对不能来自市场本身，以及一个真实验证过的例子，展示保留变量防护是怎么防止组件自己的配置悄悄覆盖平台注入的值的。

## 被签名的是规范化载荷，不是 Manifest 的原始字节

一份 Manifest 从发布者到安装者的路上要经过好几种不同的表示形态：`component.yaml`（YAML）→ 转成 JSON 上传 → 市场存成 JSON → CLI 取回 → 再解析回 Manifest 结构。每一步的字节序列都不一样。对任何一步的原始字节签名，只要另一步的序列化器做出了不同（但语义等价）的选择——一条注释、一种缩进风格、键的顺序——签名就会失效，而且失效得**毫无规律**，取决于当天路径上恰好是哪个市场版本、哪个反向代理。

所以真正被签名的对象是一份**规范化载荷**：把 Manifest 解析成数据结构，再用一条固定规则重新编码（JSON，键按字典序排列）。两份含义相同的文档，不管原本各自怎么写的，规范化之后的输出都逐字节相同——这也意味着注释、引号风格的改动、YAML 键顺序的调整，永远不会被当成篡改，因为它们根本不会改变规范化之后的样子。

规范化本身要先堵上一个攻击面才能被信任：**重复的键会被直接拒绝，而不是取舍着挑一个。** 如果双方各自计算"同一份"文档的规范形式，就必须确保这份文档不会被两边解析成两种不同的结构——而重复键恰好是不同解析器会给出不同答案的地方（有的取第一次出现的，有的取最后一次的）。与其挑一个约定、然后祈祷所有实现都跟它保持一致，不如直接把带重复键的 Manifest 判为无效。

这也正是[闭源组件的镜像安全规范](../07-patterns/04-closed-source-image-hardening.md)里"钉住摘要"这条建议真正补上缺口的地方：签名签的是 Manifest，而 `deployment.image` 只是它里面的一个字符串字段——只签 Manifest，保证的只是这个字符串没被改，不保证这个字符串现在还指向签名那一刻的那些字节。`brickkit publish` 默认会在做规范化和签名之前，先把一个可变的 tag 解析成它当时的摘要，这样签名真正覆盖的那个字符串，就是一个 registry 事后没法悄悄重新指向的引用。要跳过这一步得显式加 `--no-pin-digest` 参数，加了会打印一条点名这个风险的大大的警告，而不是悄悄跳过。

```mermaid

    subgraph 发布方（需要 cosign）
        M["Manifest"] -->|规范化| Canon["规范载荷<br/>JSON，键按字典序"]
        Canon -->|cosign sign-blob| Sig["签名"]
    end
    subgraph 市场
        Sig -->|只存，不验| Store[("签名值")]
    end
    subgraph 安装方（零依赖）
        Store -->|"公钥来自 installer.publicKeys"| Verify["Go 标准库验签"]
    end
```

## 为什么签名需要装 cosign，验签却完全不需要

这种不对称是刻意设计的，不是不一致：**每一个安装者都要验签，但只有发布者——通常是一条 CI 流水线——才会去签名。** cosign 的 `sign-blob` 产出的是标准的 ECDSA P-256 over SHA-256 签名（ASN.1 DER，再 base64 编码），对应的是标准的 PKIX PEM 公钥——这两样东西 Go 标准库都能原生校验，所以验签不需要引入任何额外依赖。真正用得上 cosign 自身能力的是签名这一侧：口令保护的私钥、KMS 托管的密钥、硬件密钥、绑定 OIDC 身份的 keyless 签名——密钥管理的花样这么多，本来就该是 cosign 去解决的问题，不值得为了在发布这一侧少装一个依赖就重新造一遍轮子。

这个不对称带来的结果，正是让 `installer.requireSignature: true` 能在生产环境里当默认值的原因：如果验签也要装 cosign，那"生产环境强制签名"就意味着每一台跑 `brickkit add` 的机器、每一个 CI runner 都得装 cosign——大多数团队面对这种成本，多半会直接把校验关掉，而不是把这个依赖背到每个地方。让昂贵的工具只出现在少见的操作（发布）上，让常见的路径（安装）保持零依赖，才是这条校验能被真正坚持下去的原因。

## 为什么公钥必须放在你自己的项目里，绝不能从市场取

一条签名的元数据里带着一个 `publicKeyRef`——一个**名字**，不是密钥材料本身（AGENTS.zh.md §7）。总得有个地方把这个名字解析成真正的公钥，而这件事在哪里发生，直接决定了整套机制到底有没有意义：

| 公钥从哪儿来 | 市场一旦被攻破，你会付出什么代价 |
| --- | --- |
| 从市场本身取 | 等于市场在给自己签发证书。一旦市场被攻破，攻击者可以把组件和公钥一起换掉——验签照样通过，而签名什么都没防住 |
| 配置在项目里（`installer.publicKeys`，跟 `brickkit.yaml` 一起进 Git） | 信任锚点握在安装者自己手里，市场被攻破也不受影响，而且会跟着项目自己的 Git 历史接受日常的代码评审 |

只有第二种方式被真正实现了——一个在项目自己的 `installer.publicKeys` 里找不到的 `publicKeyRef`，就是验签失败，没有任何"那就从组件来源那边取一个"的兜底。AGENTS.zh.md §7 早就点出了这个设计最锋利的后果：**`publicKeys` 是唯一真正让验签生效的字段**——一个公钥都没配的话，`requireSignature: true` 什么都不会做，因为根本没有信任锚点可以拿来对照签名，而 CLI 只能事后警告一次，没法在你真把这份配置发出去之前拦住你。

## 保留变量：一道发布时的拒绝，一道注入时的警告——只有一道能在不起市场的情况下真实验证

AGENTS.zh.md §5.2 描述了两层防线，防止组件自己的配置跟平台注入的变量撞车：市场在发布阶段拒绝撞车的 `configSchema` 键，CLI 在注入阶段警告并跳过撞车的那一项。第二层是真实验证过的输出——声明一个叫 `backendEndpoint` 的 `configSchema` 属性（大写之后是 `BACKEND_ENDPOINT`，跟保留的 `*_ENDPOINT` 后缀模式撞车），跑一次 `brickkit up`：

```
⚠️ 配置冲突：组件 demo/hello 的配置项已被忽略
   组件：demo/hello
   配置项：backendEndpoint
   环境变量名：BACKEND_ENDPOINT
   冲突的保留模式：*_ENDPOINT
   处理：该配置项已被忽略，平台注入的值优先
   建议：
   1. 修改 configSchema 中的配置项名称，避开平台保留变量
   2. 例如改为 backendBaseUrl
```

组件照样会启动——这是警告，不是拦下部署——但 `backendEndpoint` 声明的默认值会悄悄从容器的环境里消失，跟平台承诺的完全一致：平台注入的值（如果真有别的组件依赖了 `demo/hello`、并因此拿到一个真实的 `*_ENDPOINT` 注入到这同一个变量名下）永远赢；CLI 甚至直接给出了一个具体的改名建议，而不只是指出问题。
