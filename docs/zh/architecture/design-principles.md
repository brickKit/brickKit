# 设计原则与取舍

[架构总览](overview.md)讲的是平台**做了什么**。这一篇讲它**为什么长成这个样子**：把整个设计串起来的那一个想法；BrickKit 借用了（以及刻意没借用）的那些工程想法，每一个都从"它是什么"讲起，不假设你听过；以及每个设计提议都要拿来对照的十二条原则。

[AGENTS.zh.md](../../../AGENTS.zh.md) 里有同样的十二条原则，压缩成一行一条，写给 AI 助手拿去判断某个提议合不合适。这一篇是那些行背后的论证：每条原则是什么意思、换来了什么、付出了什么、拒绝了什么。下面十二个小节的标题与 AGENTS.zh.md §4 逐字一致，一旦两边分叉，`make lint` 会失败。

## 贯穿一切的那一个想法：声明一张图，其余全部派生

你写两种声明。每个组件的 `component.yaml` 说它是什么、依赖什么；项目的 `brickkit.yaml` 说你要哪些版本、启用什么、暴露什么、数据库在哪。两者合起来，描述的是一张图。平台产出的其余一切，都是每次运行时从这张图**派生**出来的，每一条规则都能用一句话说清：

| 派生出的东西 | 从什么派生 | 规则 |
| --- | --- | --- |
| 哪些组件运行 | `enabled` 加依赖图 | 顶层组件默认运行；下层组件只要上面有需要它的在跑，它就跑；显式写了 `enabled` 则以所写为准。实现上算的是"谁不跑"的最小不动点，所以环不需要任何特殊处理 |
| 启动顺序 | 依赖图 | 拓扑排序。强依赖缺失在解析期就是错误，不是运行期的意外 |
| 服务名与地址 | 组件 ID + 精确版本 | `/` 和 `.` 变成 `-`，全小写，再拼成 `http://<服务名>:<端口>`——Docker 和 K8s 上是同一个字符串 |
| `*_ENDPOINT` 变量名 | 组件 ID | `/` 和 `-` 变成 `_`，全大写，末尾加 `_ENDPOINT` |
| 资源连接变量 | 资源的 `kind` 与它的绑定 | 以 `kind` 名作前缀：`DATABASE_*`、`REDIS_*` …… |
| `docker-compose.yaml` 或 K8s 清单 | Manifest 与 `deploy.target` | 每次运行重新生成；组件自己从不携带 |
| 网络策略 | 依赖图 | 需主动开启（`deploy.networkPolicy`）：流量沿着你声明过的依赖边放行 |
| 哪些源码目录处于活动状态 | 级联判定的结果 | `brickkit sync` 把不启动的归档、把要跑的还原 |

用"派生"代替"配置"，换来三样东西：

- **派生出的值不可能和它的来源不一致。** 变量名永远对得上组件 ID，地址永远对得上版本，网络策略永远对得上依赖关系，不存在"忘了同步的第二份"。对比一份手写的网关配置：里面烧进了版本化服务名，组件一升版本它就悄悄过期，还不会有任何提示。
- **派生可以双向推。** 从 `people/basic` 能算出 `PEOPLE_BASIC_ENDPOINT`；看到 `PEOPLE_BASIC_ENDPOINT`，也能确切知道它指向哪个组件。这就是依赖别名被拒绝的原因：别名只保住了这条双向关系的一半。
- **CLI 可以保持无状态。** 每个产物都是声明的纯函数，所以 CLI 读入声明、生成、交给 Docker 或 K8s、然后退出。两次运行之间没有任何需要记住的东西，也就不需要常驻进程。

**派生不是猜。** 派生值是你所声明内容的纯函数。平台从不推断你的意图：它不会替你选版本（`^1.0.0` 直接报错）、不会替你打开你没暴露的端口、不会自作主张认定某个缺失的弱依赖该降级成什么、也不会因为觉得你"大概想跑它"就把一个组件拉起来。算不出来的值，就由你声明。这就是这个想法与"精确优于隐式"这条原则的衔接方式——后者负责把前者拦在"猜"的门槛之外。

代价是：算不出来的东西必须写下来，而且逃生口刻意开得很窄——`labels` 与 `deploy.ingressAnnotations` 原样透传给底层引擎，平台不做任何解释。

## 认识这些想法

BrickKit 没有发明新范式，用到的都是软件工程里早就有的想法。你可能全都听过，也可能一个都没听过——这一节按后一种情况写：每个想法先用一两句话讲清它是什么，再讲它的好处和代价，最后讲 BrickKit 怎么对待它：用了什么、没用什么、为什么没用。

BrickKit 对这些想法的态度分三种：

- **采用**：平台自己实现了它。
- **只借一半**：借了其中一部分，另一部分刻意不做。
- **不干预**：那是组件内部的事，平台不管。

先看全景，下面再逐个展开，顺序与这张表一致。

| 想法 | 一句话 | BrickKit 的态度 |
| --- | --- | --- |
| 限界上下文（DDD） | 按业务领域给系统划边界，每块自己管自己 | 采用 |
| 声明式与 GitOps | 只写"要什么"，不写"怎么做"，声明放进 Git | 采用，但不做持续纠偏 |
| 十二要素配置 | 配置不写进代码，启动时用环境变量传进去 | 采用 |
| 约定优于配置 | 工具先定好规矩，照做就不用配 | 只借一半 |
| 精确版本与锁文件 | 依赖写死具体版本，不写"1.x 都行" | 采用 |
| 契约先行 | 先把接口写成文件，再各自实现 | 只借一半 |
| 契约式设计 | 写明"要求什么、保证什么"，违反就报错 | 只借一半 |
| 大声失败 | 出错就立刻明显地失败，不悄悄带着错继续 | 采用 |
| 最小权限 | 只给完成工作所需的最少访问，其余默认不通 | 采用（部分需主动开启） |
| 供应链安全 | 确认第三方代码出自谁、没被改过 | 只借一半 |
| 微服务与服务网格 | 拆成许多小服务，网格统一管它们之间的通信 | 只借一半 |
| 六边形与分层架构 | 把业务核心和外部系统隔开 | 不干预 |
| 类型驱动开发 | 用类型让错误的写法编译不过 | 不干预 |
| TDD 与 BDD | 先写测试或行为描述，再写实现 | 不强制，有建议 |
| 属性测试 | 描述"任何输入都成立的性质"，让工具随机找反例 | 不强制，平台自己用 |

### 限界上下文（DDD）

**它是什么。** DDD 是"领域驱动设计"的缩写。它的一个核心想法是：一个大系统里，同一个词在不同的业务里往往不是同一件事——订单系统里的"客户"是下单的人，客服系统里的"客户"是等着被回复的人。与其硬造一个包打天下的"客户"，不如按业务划出几块边界，每一块（一个"限界上下文"）有自己的词汇、规则和数据。

**好处。** 每块可以由不同的人独立理解、独立修改，改一块不会牵动别的块；出了问题，也容易判断"是哪一块的事"。

**代价。** 边界划错了很难补救：划得太细，块与块之间要不停地沟通；划得太粗，又回到一团乱。而且划边界得先真正弄懂业务，这本身要花时间。

**BrickKit 怎么对待它。** 采用：组件天然对应限界上下文的工程边界——自己的仓库、Manifest、版本和接口契约，边界就是 `component.yaml`。一个组件不该横跨两个上下文，一个上下文则可以由一个或几个组件组成。不管：组件内部怎么建模，以及几个上下文是否共用一个数据库、是否合并进同一个进程（`servedBy`）——由你按业务决定。术语的逐条对照见[组件设计准则](../patterns/component-design.md#如果你的团队习惯用-ddd-的语言)。

### 声明式与 GitOps

**它是什么。** 让工具做事有两种说法。命令式是一步步告诉它"先做这个、再做那个"，像教厨师做菜；声明式是只写"我最终要什么"，怎么做由工具去算，像在菜单上点菜。GitOps 则是把这份"要什么"的声明放进 Git，让它成为系统的唯一事实来源，再由一个一直在运行的程序持续把真实状态拉向声明。

**好处。** 声明本身就是文档：打开文件就知道系统该是什么样。放进 Git 之后，每次改动都能审查、能回滚。

**代价。** 声明语言表达不了的事，就做不了；出了问题，你得理解"声明是怎么变成实际动作的"。GitOps 里"持续纠偏"那一部分，还要有一个常驻的程序一直盯着。

**BrickKit 怎么对待它。** 采用声明式：`brickkit.yaml` 是唯一输入，放在 Git 里，每个环境一份完整、自包含的文件——diff 就是评审。不做"持续纠偏"：`brickkit up` 是一次性下发，CLI 用完就退出，没有任何东西一直盯着。有人手动改了运行中的容器，不会有程序替你改回去，要等下一次 `up` 才会对齐。原因是持续纠偏需要一个常驻、要有人运维的程序，与"CLI 用完即走"直接冲突（见[平台极简](#平台极简)）。

### 十二要素配置

**它是什么。** "十二要素"是一份写云上应用的经验清单，其中一条最常被引用：配置（数据库地址、密码、别的服务在哪）不要写死在代码里，而是在程序启动时从环境变量里读。

**好处。** 同一个镜像放到测试环境、生产环境都能跑，环境之间的差别只在"启动时给了它哪些环境变量"。密码不会进代码仓库，代码也不需要知道自己跑在哪儿。

**代价。** 环境变量只是一串扁平的文字，复杂的配置得自己编码解码；变量一多就难管；变量漏了，往往要到程序真正用到它的那一刻才发现。改了配置还得重启才生效。

**BrickKit 怎么对待它。** 采用：依赖的地址、数据库等资源的连接信息、组件自己的配置，全部以环境变量交给组件；Docker 和 Kubernetes 上的地址格式完全相同，所以换环境不用改组件代码。针对"漏了才发现"这个代价，平台在 `up` 时就查：写错的配置项名会警告，必填、没有默认值、项目里又没填的配置项会直接阻止 `up`。不做：配置中心和热更新——改配置就改 `brickkit.yaml` 再 `brickkit up` 重启，因为多数配置本来就必须重启才能安全生效。详见[环境变量注入契约](environment-variables.md)。

### 约定优于配置

**它是什么。** 工具先替你定好一套规矩（叫什么名字、放在哪儿、默认怎么做），你只要照着来，就几乎不用写配置。Rails 是最有名的例子。

**好处。** 要写、要读的配置少；换个人接手，一眼就知道东西在哪儿。

**代价。** 规矩不合你的情况时，没有商量的余地。更麻烦的是"靠猜"的约定：规矩没讲清楚，工具悄悄替你做了决定，出错时你根本不知道它猜了什么。

**BrickKit 怎么对待它。** 只借一半。借的是"固定命名"：服务名、环境变量名、地址格式都由固定规则算出来——`people/basic` 1.0.0 的服务名一定是 `people-basic-1-0-0`，变量名一定是 `PEOPLE_BASIC_ENDPOINT`——所以你不用去配。不借的是"替你做决定"：用哪个版本、暴露哪个端口、要不要启用某个组件，平台从不替你猜，必须你写明（见[精确优于隐式](#精确优于隐式)）。所以 BrickKit 自己用的说法是"派生优于配置"：能从你写下的内容**算出来**的才派生，算不出来的，就要你写。

### 精确版本与锁文件

**它是什么。** 依赖别人的软件时，版本可以写成"范围"（比如 `^1.0.0`，意思是"1.x 里最新的都行"），也可以写死一个具体版本（`1.0.0`）。锁文件（比如 npm 的 `package-lock.json`）则是把第一次装出来的具体版本记下来，以后照着装。

**好处。** 今天装出来的和三个月后装出来的是同一份，不会因为别人发了个新版本，你的生产环境半夜悄悄变了。出问题时，也能确切知道跑的是哪一版。

**代价。** 补丁和安全修复不会自己到来，升级得你动手改一行；长期不升级，会落后很多。

**BrickKit 怎么对待它。** 采用，而且比 npm 更严：配置里只认精确版本，写 `^1.0.0` 会直接报错。`brickkit add people/basic` 不写版本时，CLI 会在那一刻查一次最新版本，把它作为精确版本写进配置——相当于自动生成锁文件：只解析一次，而不是每次都解析。版本号还会进入服务名（`people-basic-1-0-0`），所以两个版本是两个不同的 DNS 名字，可以并排运行、互不冲突。不管：并排运行的两个版本之间，数据是否兼容——那是你的事。见[核心概念](../concepts.md)。

### 契约先行

**它是什么。** 两个团队要对接，先把"接口长什么样"写成一份文件（比如 OpenAPI 或 protobuf 文件），双方各自照着实现，而不是先写完一边、再让另一边去猜。像先约好插头的形状，两边就能各造各的。

**好处。** 双方可以并行开发；不读实现代码，就能知道一个组件对外承诺了什么。

**代价。** 契约文件要有人维护。契约与实现对不上的时候，比没有契约更糟——读的人信了一份过期的说明。

**BrickKit 怎么对待它。** 只借一半。借的是"随身携带"：组件通过 `artifacts` 把契约文件随 Manifest 一起发布，`add`/`fetch` 会把它们下载下来；市场还要求闭源且对外提供 API 的组件必须带上 `api-contract` 产物——代码可以闭源，契约不能。不做的是"管理契约本身"：不规定用哪种格式（`type`、`format` 是 CLI 从不解析的自由字符串），也不检查实现是否真的符合契约。见 [AI 辅助开发指南](../ai-development.md)。

### 契约式设计

**它是什么。** 每个函数或模块写明"我要求输入满足什么条件、我保证输出满足什么条件"，一旦违反，立刻报错。像电器铭牌上写着"输入 220V、输出 12V"，接错了就跳闸。它的英文名是 Design by Contract。

**好处。** 错误在离原因最近的地方被抓住；这些规则本身就是最精确的说明书。

**代价。** 规则写得太严，合法但没想到的用法也会被挡在门外；写得太松，等于没写。每次运行都检查，有开销，规则本身也要维护。

**BrickKit 怎么对待它。** 只借"写下来"这一半。BrickKit 里最接近它的是 `configSchema`——严格说只是近亲，因为它只描述、不强制：组件用它写明自己有哪些配置项、什么类型、允许什么取值范围（`enum`、`minimum`、`maximum`、`pattern`），让人和 AI 都能读到。不借"强制"这一半：CLI 只检查配置项的**名字**是否存在（写错会警告），从不检查**值**。分界线在于有没有运行时的安全网：值写错了，组件自己会崩，你一定会发现；名字写错了，变量只是悄悄不存在，组件走默认分支照常运行，没有任何东西提醒你。而且一旦开始校验值，就停不下来——枚举？范围？正则？CLI 会越长越胖。见 [configSchema 是说明书，不是安检机](#configschema-是说明书不是安检机)。

### 大声失败

**它是什么。** 程序发现自己不对劲时，立刻、明显地停下来报错，而不是假装没事继续往下跑。英文叫 fail fast。

**好处。** 错误暴露在离原因最近、最早的时候。最坏的 bug 不是崩溃，而是"悄悄给出一个看起来正常的错误答案"——崩溃你一定会注意到，错误答案不一定。

**代价。** 更严格意味着更多"拒绝"：一个多写了未知字段的文件、一个没做防御的组件，本来也许能凑合跑，现在直接起不来。

**BrickKit 怎么对待它。** 采用，而且是有意的。Manifest 里出现不认识的字段，直接拒绝，而不是悄悄忽略；写错的配置项名会警告；必填、没有默认值、项目里又没填的配置项，会阻止 `up`。最典型的是弱依赖：一个缺失的弱依赖**什么变量都不注入**，而不是注入一个空字符串——空字符串拼进地址，请求会悄悄打到组件自己身上，还会拿到一个看似健康的 200，这种 bug 极难查（AGENTS.zh.md §9.13）。代价也是真实的：组件读这个变量时若直接写 `os.environ["X"]`，变量缺失就启动即崩，所以作者必须用 `.get()` 防御性地读。

### 最小权限

**它是什么。** 每个程序、每个组件，只拿到完成工作所需的最少访问权限，其余一律默认不通。像宾馆的房卡，只能开你自己那间房。在网络安全里它常和"零信任"一起被提起。

**好处。** 万一某个组件被攻破，或者只是出了 bug，它能碰到的东西有限，损失被限制在小范围里。

**代价。** 每一条允许的访问都要明确写出来。漏放一条，就是一次"莫名其妙连不上"的排查。

**BrickKit 怎么对待它。** 采用：不映射端口就不能从外部访问，不写 `expose` 就没有对外入口；在 Kubernetes 上可以让 CLI 按依赖图生成网络策略——只放行你声明过的依赖方向；CLI 本身也从不挂载 Docker socket。要注意两点。第一，网络策略和 ServiceAccount 隔离都要**主动开启**，平台不替你默认打开，因为打开它们可能让一个本来能跑的组件起不来，这个代价该由你按项目判断。第二，网络策略是否真的生效，取决于集群的网络插件（CNI）是否执行它——不执行的话它就是一张空文，CLI 会为此告警。见[网络策略与最小权限](../guide/11-network-policy.md)。

### 供应链安全

**它是什么。** 你安装的第三方组件，是不是真的出自它声称的作者？有没有在半路被人调包？像快递上的封条加发件人签名。

**好处。** 能防止冒名顶替，也能防止传输途中被篡改。

**代价。** 签名只能证明"这是谁发的、没被改过"，不能证明"发的东西没有恶意"。你还得自己管理"信任哪些公钥"。

**BrickKit 怎么对待它。** 只借一半。借的是验签：发布者用 cosign 签名，安装方只用 Go 标准库验证，不需要装 cosign。信任的公钥配在你自己项目的 `installer.publicKeys` 里，而不是从市场上取——否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉，验证照样通过。注意：一把公钥都没配，签名验证就是**完全关闭**的（CLI 会警告一次）。不做的是事前审查：不扫描、不沙箱、不做静态分析，安装即信任，和 npm、VS Code 插件市场是同一套模型；事后发现恶意组件，市场把它标成 `blocked`，阻止新的安装。原因是事前审查要么误伤大量正常组件，要么放过精心伪装的恶意代码，成本高、可靠性低。见[签名与信任模型](signing-and-trust.md)。

### 微服务与服务网格

**它是什么。** 微服务是把一个大程序拆成许多小服务，各自开发、各自部署，通过网络互相调用。服务网格则是专门管"这些服务之间怎么通信"的一层基础设施：帮它们找到对方、分流、限流、失败重试、熔断（对方一直出错时先停止调用）。像把一家大餐馆拆成一条街上的许多小店。

**好处。** 各家小店可以独立开张、独立装修；一家出了问题，不至于整条街停业。

**代价。** 店多了，就得有人管路牌（注册中心）、管入口（网关）、管排队和限流（网格）——运维复杂度陡增，出了问题还得跨好几家店去查。

**BrickKit 怎么对待它。** 只借一半。借的是"拆"：组件独立构建、独立部署、独立调用。不做的是整套治理：没有注册中心（Docker Compose 和 Kubernetes 自带的 DNS 就是服务发现，也就是用名字找到对方）、没有网关、没有服务网格、没有熔断和限流（那是组件自己的代码，因为阈值和退避策略因业务而异，平台一刀切不可能对）、没有配置中心。每一样都意味着一个要长期运行、要有人运维的东西，而 BrickKit 的 CLI 是用完即走的。如果你确实需要网关（比如 Traefik），可以通过 `labels` 把标签原样透传给它——平台不理解标签的含义，只负责传。详见[平台刻意不做的事，以及为什么](overview.md#平台刻意不做的事以及为什么)。

### 六边形与分层架构

**它是什么。** 这两种都是"程序内部怎么组织"的办法。分层是把程序切成上下几层（比如接收请求的、处理业务的、存取数据的），上层只调用下层。六边形架构更进一步：把真正的业务逻辑放在中心，数据库、网页接口、消息队列这些外部的东西，都通过事先约定好的接口接到它上面。像厨房和外卖平台、收银机、供货商之间隔一层标准接口，换个供货商不用改菜谱。

**好处。** 业务逻辑不依赖具体的框架或数据库，更容易单独测试，也更容易换掉某个外部系统。

**代价。** 要多写不少接口和转换代码；在小程序里，像给自行车装变速箱。

**BrickKit 怎么对待它。** 不干预。一个组件内部怎么分层、怎么组织，由组件作者自己定。原因是 BrickKit 只规定组件在**边界上**呈现的样子（见[组件自治](#组件自治)），一旦开始规定内部结构，平台就从编排器变成了框架。想看一个真实的分层组件长什么样，[用 Go 写一个 BrickKit 组件](../go-component-template.md)带读了一个：HTTP 层、业务层、数据访问层。

### 类型驱动开发

**它是什么。** 用编程语言的类型系统把规则"写进代码的形状里"，让错误的写法根本编译不过。比如订单金额不用随便一个数字，而用一个专门的"金额"类型，这样就不会误把"数量"当"金额"传进去。

**好处。** 一大类错误在编译时就被挡住了，不用等到运行才发现。

**代价。** 依赖语言：不是所有语言的类型系统都足够强。类型设计本身也要花功夫，设计得不好会变成负担。

**BrickKit 怎么对待它。** 不干预，而且是最彻底的一种不干预：平台不限制组件用什么语言，任何能构建出容器镜像的语言都行。BrickKit 的 CLI 自己是用 Go 写的，受益于类型检查，但并不要求组件也这样。见[从零开发自己的第一个组件](../guide/10-build-your-own.md)。

### TDD 与 BDD

**它是什么。** TDD（测试驱动开发）是先写测试，再写让测试通过的代码；BDD（行为驱动开发）是先用接近日常语言的"给定……当……则……"描述期望的行为，再把它变成测试。像先写好验收标准，再开始做菜。

**好处。** 测试成了对"代码该做什么"的约束，而不是对"代码已经做了什么"的复述；需求也变得可以检验。

**代价。** 前期要投入时间。而且如果验收标准本身写错了，你会非常认真地把错的东西做出来。

**BrickKit 怎么对待它。** 不强制：怎么测试是组件自己的事，平台不检查。但给了建议：[分层测试指南](../patterns/testing.md)讲了怎么给组件分层测试，还给了一个"让 AI 写组件时先立规格、再写实现"的推荐顺序。BrickKit 独有的一点是 `brickkit up --dry-run`：它不启动任何东西，就能检查 `component.yaml` 与 `brickkit.yaml` 是否对得上（比如配置项名写错）。请注意它查的是**装配对不对**，不是**组件代码对不对**。

### 属性测试

**它是什么。** 普通测试是你手写几个例子：输入 A 应该得到 B。属性测试换一种思路：你描述"无论输入是什么，结果都应该满足的性质"（比如"排序之后的列表一定是有序的"），再让工具随机生成成千上万组输入，去找出违反这条性质的反例。

**好处。** 能撞出你自己想不到的边界情况。

**代价。** 想清楚"性质"本身不容易；找到反例之后往往要先把它缩小才看得懂；对大量依赖外部系统的代码不太好用。

**BrickKit 怎么对待它。** 不要求、也不推荐给组件：适用面比较窄，主要适合"核心不变量"（比如余额永远不为负），[数据构造指南](../patterns/data-construction.md)里提到过这一点。但平台自己用了：CLI 里规则最密的三处——启停判定、启动顺序、资源配额合并——都有用几千组随机输入去验证的测试。

## 十二条原则

### 平台极简

CLI 能不做的事就不做。每多一个功能就是永远多一份维护成本，而平台的全部工作只是：把组件连起来，把它们的声明翻译给 Docker 或 K8s。

**为什么。** 底层引擎本来就做得好的事——DNS、健康探针、重启策略、负载均衡——由它们来做，比平台自己造一份副本更好。一个长出运行时的平台，会变成你还得多养活的一样东西。

**代价。** 人们最先想到的那些东西这里没有：没有网关、没有配置中心、没有注册中心。[拒绝清单](overview.md#平台刻意不做的事以及为什么)写明了每一项该怎么替代，以及你要是硬造一个会看到什么。

**拒绝了什么。** 常驻控制面、注册中心、健康检查轮询、配置中心、服务网格。

### 组件自治

语言、框架、API 风格、事务、日志格式，都归组件自己。平台只要求三样：一份 Manifest、一个健康检查、以及组件去读它的环境变量。

**边界在哪。** 影响组件**之间**怎么协作的，平台管：怎么声明、怎么寻址、怎么配置、怎么依赖。影响组件**内部**怎么写的，平台不强制：用什么架构、怎么建模、怎么分层、怎么测试（[patterns/](../patterns/README.md) 里有建议，但没有任何东西检查）。这不等于平台对容器没有要求——它规定的是容器在**边界上**呈现的样子：入口对不认识的参数必须立刻报错退出（迁移容器与主服务用的是同一个镜像）、弱依赖的环境变量要用 `.get()` 读（缺失时平台根本不注入）、`/healthz` 只查进程自己、冷启动超过 30 秒要设 `startPeriodSeconds`。这些都是边界上的契约，不是对内部代码结构的干涉。平台一旦开始管边界之内，它就从"编排器"变成了"框架"——而框架只能产出一种形状的组件。

**为什么。** 这才让"任何能构建 Docker 镜像的语言"这句话成立。也因此前端组件只是另一个监听端口的容器：没有"静态"组件这个类型，CLI 里也就不会蔓延出到处是 `if type == static` 的分支（AGENTS.zh.md §9.10）。

**代价。** 边界之内的事平台帮不上忙——没有共享 SDK，不校验业务配置，对你怎么组织代码不表态。

**拒绝了什么。** SDK、sidecar、agent；特殊的组件类型；由平台定义的降级行为。

### 渐进式

不需要先把整个系统设计完。加一个组件，跑起来；再加一个，再跑；随时可以停，随时可以继续。

**为什么。** `brickkit add` 一条命令拉下一个组件的整棵依赖子树；`enabled` 跟着上层走，没人需要的就不在跑；`brickkit sync` 让源码目录只剩你正在看的那几个。这也是为什么五十个组件并不意味着五十样东西要装在脑子里：你只需要知道直接依赖的契约（通常一到三个），五十个组件的项目在本地可能只跑四个容器，传递依赖是 CLI 的事（AGENTS.zh.md §9.15）。

**代价。** 平台限定的是你**每个组件**需要知道的东西，而不是整体能长到多大。没有任何东西拦着你长出一个一次装不进脑子的系统。

**拒绝了什么。** 一个必须先完整、然后才能跑起任何东西的设计阶段。

### 环境无关

组件代码永远不知道自己跑在 Docker 还是 K8s 上。它读到的地址在两边都是 `http://<版本化服务名>:<端口>`，一个字节都不差。

**为什么。** 一份 Manifest，两种环境。组件描述的是"我是什么、我需要什么"，从不描述"我跑在哪"，所以它不带 `docker-compose.yaml`，也不带任何 K8s 清单（AGENTS.zh.md §9.4）。切换环境只改一个字段：`deploy.target`。

**代价。** 平台必须为两种引擎都生成正确的文件，而只有某一种引擎才能做到的事，从组件这一侧表达不出来。针对引擎的提示走 `labels` 透传，平台不解释它。

**拒绝了什么。** 按环境区分的组件文件；Manifest 里出现针对某个引擎的字段。

### 精确优于隐式

精确版本、显式暴露、显式启用。凡是平台不得不猜的，就让你自己说。

**为什么。** 范围版本是"我机器上能跑，生产上炸"的经典来源（AGENTS.zh.md §9.2）。钉版本仍然只发生一次，在 `add` 的时候，和锁文件的做法一样：不写版本，CLI 就向安装源问最新的可安装版本，把确切的结果写到磁盘上。暴露是主动开启的，因为对它的一次猜测，就是悄悄做出的一个安全决定。

**代价。** 要多写一些。就连没写 `enabled` 也是刻意的：它的意思是"跟着上层走"，不是"没设置"。

**拒绝了什么。** 范围版本（是错误，不是警告）、隐式暴露、依赖别名、一切"自动探测"。

### 安全默认

你不说，就什么都不可达。不映射端口，外部就访问不到；不声明 `expose`，就没有 Ingress；`private` 表示未经授权不可见。

**为什么。** 什么都不写时得到的，应当就是安全的那个状态。CLI 用完即走、没有监听端口，也从不挂载 Docker socket，所以平台自己不增加任何攻击面。

**它止步于哪里。** 这条原则管的是**可达性**，并不延伸到 K8s 的每一个默认值。`serviceAccount.enabled` 与 `podSecurity: restricted` 都是需主动开启的，因为它们任何一个都可能让一个已经能跑的组件起不来，而这是取决于具体项目的代价，平台没法替你权衡。不写 `serviceAccount: { enabled: true }`，每个 Pod 就用命名空间的 `default` ServiceAccount 运行，它的 token 照常挂载。

**拒绝了什么。** 任何默认就打开一条通路的做法。

### 开源优先

CLI 与市场都开源。闭源组件通过市场受控分发。

**为什么。** 你把部署交给它的平台，应该是你读得懂的。闭源是一个商业事实，不该被禁止，所以市场用 Manifest 与镜像引用取代 Git 仓库来存放它。它唯一不允许一直闭着的是契约：提供 API 的闭源组件必须声明 `api-contract` 产物（[市场指南](../guide/08-marketplace.md)里能看到这条拒绝）。

**代价。** 让闭源组件保持闭源，是发布者自己的工作，而且拉下镜像就等于交出了它要运行的每一个字节——见[闭源组件的镜像安全规范](../patterns/closed-source-image-hardening.md)。

**拒绝了什么。** 私有的 CLI 或市场。

### 平台提供工具，不替人做决定

只给机制，不定策略。多版本默认共存；降级逻辑归组件；破坏性变更是组织协调问题，版本共存只是它的一个物理缓冲。

**为什么。** `people-basic-1-0-0` 和 `people-basic-2-0-0` 是两个不同的 DNS 名字，所以共存对平台来说没有成本，也就没什么需要它去问"你确定吗"——`brickkit.yaml` 里把两个都列出来，**本身**就是意图（AGENTS.zh.md §9.3）。Redis 挂了以后组件怎么办——查数据库、返回空列表、写文件稍后重试——是业务逻辑，不同组件的正确答案不一样（AGENTS.zh.md §9.7）。

**代价。** v1 与 v2 之间的数据层不兼容，或者缺了降级，平台救不了你。这两样都是你的。

**拒绝了什么。** 弱依赖降级、通信治理（熔断、限流、重试）、多租户。

### 安装即信任

和 npm、VS Code 插件市场、GitHub 是同一套模型：安装一个组件，就是信任它。平台不做前置审查——不扫描、不沙箱、不做静态分析——只在事后出手：确认为恶意的组件会被标为 `blocked`，阻止新的安装。

**为什么。** 前置审查要么误报太多，拦下正常的组件；要么漏报太多，放过精心伪装的恶意代码。`blocked` 作为最后一道防线，成本低而且足够有效（AGENTS.zh.md §9.11）。市场是"集市"，不是"保险库"。

**它确实提供的。** 签名。发布者用 cosign 签名；安装方只用 Go 标准库验证。公钥必须放在**你自己**的项目里（`installer.publicKeys`），而不能从市场取——否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉，验证照样通过。一个公钥都没配时，验证整体关闭，CLI 会告警一次。细节见[签名与信任模型](signing-and-trust.md)。

**代价。** 你自己要对"从谁那里安装"负责。

**拒绝了什么。** 由平台提供的第三方安全审查。

### configSchema 是说明书，不是安检机

`configSchema` 记录的是组件自己的配置：类型、默认值，以及 `enum`、`minimum`、`maximum`、`pattern`（会被解析并保存，但从不强制执行）。CLI 不校验你填进 `config` 的**值**。但它会查**键名**：写了 `properties` 里没有的键，会警告，并猜你想写的是哪一个。

**界线为什么划在这里。** 划线的依据是：有没有运行期的安全网。**类型**写错，会大声失败——组件拿到 `"abc"`，对它调 `int()`，崩溃，你一定会注意到。**键名**写错，则是悄无声息地失败：那个变量压根不会出现，组件落进它的默认分支，运行得完全正常，只是不是你配置的那个样子。所以平台去抓那个否则看不见的失败，放过看得见的那个。它还只是一次存在性检查，没有后续的追问；而值校验一旦开了这扇门，就得一路回答要不要校验 `enum`、`minimum`、`pattern`，最后把整个 JSON Schema 都装进 CLI（AGENTS.zh.md §9.12）。

**一个很窄的例外。** 列在 `required` 里、又没有 `default` 的键，会让 `up` 直接失败。道理是同一个：缺失的项否则会悄悄地不存在，组件会看起来健康地跑着，只是有一条调用路径永远走不通。

**代价。** 这些声明不是保证。用户完全可以给一个 `minimum: 1` 的键填 `0`，`up` 时没有任何东西拦他。写下它们换来的是：人和 AI **看得见**预期的范围；报错、截断还是回退到默认值，由组件自己决定。

**拒绝了什么。** 任何形式的值校验。

### 一个组件一个仓库

不支持 monorepo 里拆子目录当组件。组件是独立的发布单元（它有自己的版本——monorepo 你要怎么打 tag？）、独立的移动单元（`brickkit sync` 搬的是整个目录，连 `.git` 一起），也是独立的权限单元（有自己的可见性和发布者）。

**为什么。** 两个组件一旦共用一个仓库，这三个单元都会坏（AGENTS.zh.md §9.16）。

**代价。** 通常情况下没有：同一块业务的几个部分——proto、后端代码、迁移脚本——属于**同一个**组件，不需要拆开。这条规则说的是组件，不是文件。

**拒绝了什么。** 子目录形式的组件。

### brickkit.yaml 就是声明

配置即意图。写了就执行，CLI 不反问"你确定吗"。

**为什么。** 期望状态在这份文件里，实际状态在 Docker 或 K8s 里；CLI 在两者之间不持有任何东西。每个环境一份完整、自包含的文件（`brickkit.prod.yaml`，用 `--config` 选择），没有 overlay、继承或合并规则。打开一个文件就能看到全貌，Git diff 一眼能读懂，对基础层的改动也永远不会悄悄影响到生产（AGENTS.zh.md §9.9）。

**代价。** 各环境文件之间会重复几行。而且你写了什么，跑的就是什么：用 `enabled: false` 收窄范围，下一次 `up` 就生效；想放宽回来，`git checkout brickkit.yaml`。

**拒绝了什么。** Overlay 与继承；确认提示。
