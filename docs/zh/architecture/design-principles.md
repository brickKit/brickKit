# 设计原则与取舍

[架构总览](overview.md)讲的是平台**做了什么**。这一篇讲它**为什么长成这个样子**：把整个设计串起来的那一个想法；BrickKit 用到（以及刻意没用）的那些工程想法，每个都从"它是什么"讲起，不假设你听过，并说清它对应 AI 开发的什么痛点、BrickKit 怎么具备、为什么刻意留白；以及每个设计提议都要拿来对照的十二条原则。

[AGENTS.zh.md](../../../AGENTS.zh.md) 里有同样的十二条原则，压缩成一行一条，写给 AI 助手拿去判断某个提议合不合适。这一篇是那些行背后的论证：每条原则是什么意思、换来了什么、付出了什么、拒绝了什么。下面十二个小节的标题与 AGENTS.zh.md §4 逐字一致，一旦两边分叉，`make lint` 会失败。

## 贯穿一切的那一个想法：声明一张图，其余全部派生

你写两种声明。每个组件的 `component.yaml` 说它是什么、依赖什么；项目的 `brickkit.yaml` 说你要哪些版本、启用什么、暴露什么、数据库在哪。两者合起来，描述的是一张图。平台产出的其余一切，都是每次运行时从这张图**派生**出来的，每一条规则都能用一句话说清：

| 派生出的东西 | 从什么派生 | 规则 |
| --- | --- | --- |
| 哪些组件运行 | `enabled` 加依赖图 | 顶层组件默认运行；下层组件只要上面有需要它的在跑，它就跑；显式写了 `enabled` 则以所写为准。实现上算的是"谁不跑"的最小不动点，所以环不需要任何特殊处理 |
| 启动顺序 | 依赖图 | 拓扑排序。强依赖缺失在解析期就是错误，不是运行期的意外 |
| 服务名与地址 | 组件 ID + 精确版本 | `/` 和 `.` 变成 `-`，全小写，再拼成 `http://<服务名>:<端口>`——Docker 和 K8s 上是同一个字符串 |
| `*_ENDPOINT` 变量名 | 组件 ID | `/` 和 `-` 变成 `_`，全大写，末尾加 `_ENDPOINT` |
| 资源连接变量 | 资源的 `kind` 与它的绑定 | 以 `kind` 名作前缀：`DATABASE_*`、`REDIS_*` …… |
| `docker-compose.yaml` 或 K8s 清单 | Manifest 与 `deploy.target` | 每次运行重新生成；组件自己从不携带 |
| 网络策略 | 依赖图 | 需主动开启（`deploy.networkPolicy`）：流量沿着你声明过的依赖边放行 |
| 哪些源码目录处于活动状态 | 级联判定的结果 | `brickkit sync` 把不启动的归档、把要跑的还原 |

用"派生"代替"配置"，换来三样东西：

- **派生出的值不可能和它的来源不一致。** 变量名永远对得上组件 ID，地址永远对得上版本，网络策略永远对得上依赖关系，不存在"忘了同步的第二份"。对比一份手写的网关配置：里面烧进了版本化服务名，组件一升版本它就悄悄过期，还不会有任何提示。
- **派生可以双向推。** 从 `people/basic` 能算出 `PEOPLE_BASIC_ENDPOINT`；看到 `PEOPLE_BASIC_ENDPOINT`，也能确切知道它指向哪个组件。这就是依赖别名被拒绝的原因：别名只保住了这条双向关系的一半。
- **CLI 可以保持无状态。** 每个产物都是声明的纯函数，所以 CLI 读入声明、生成、交给 Docker 或 K8s、然后退出。两次运行之间没有任何需要记住的东西，也就不需要常驻进程。

**派生不是猜。** 派生值是你所声明内容的纯函数。平台从不推断你的意图：它不会替你选版本（`^1.0.0` 直接报错）、不会替你打开你没暴露的端口、不会自作主张认定某个缺失的弱依赖该降级成什么、也不会因为觉得你"大概想跑它"就把一个组件拉起来。算不出来的值，就由你声明。这就是这个想法与"精确优于隐式"这条原则的衔接方式——后者负责把前者拦在"猜"的门槛之外。

代价是：算不出来的东西必须写下来，而且逃生口刻意开得很窄——`labels` 与 `deploy.ingressAnnotations` 原样透传给底层引擎，平台不做任何解释。

## 认识这些想法

BrickKit 用到的、以及刻意没用的，都是软件工程里早就有的想法。你不需要事先认识其中任何一个：下面每个想法，都从"它是什么"讲起，再讲它对应用 AI 写代码时的什么痛点、BrickKit 怎么具备它、BrickKit 为什么**不**具备它，以及 AI 该怎么适应这块空缺。

**"留白"** 指的是：平台故意不做、把决定留给组件作者（和 AI）的那部分。

### 1. 限界上下文 (DDD)

**它是什么：** 一个大系统里，同一个词在不同业务里往往不是同一件事——订单系统里的"客户"是下单的人，客服系统里的"客户"是等着被回复的人。DDD（领域驱动设计）的做法是按业务划出几块边界，每一块（一个"限界上下文"）有自己的词汇、规则和数据。

- **好处：** 每块可以由不同的人独立理解、独立修改；出了问题，容易判断是哪一块的事。
- **代价：** 边界划错了很难补救——太细，块与块之间要不停地沟通；太粗，又回到一团乱。划边界得先真正弄懂业务，这本身要花时间。
- **AI 开发的痛点：** 系统一大，AI 一次读不完，只能连蒙带猜。
- **BrickKit 怎么具备：** 一个组件就是一块业务边界，有自己的仓库、Manifest、版本和接口契约。项目自带的 10 个真实组件在 200 到 3500 行之间，AI 一次读得完。一个组件不该横跨两个上下文；一个上下文可以由一个或几个组件组成。
- **BrickKit 为什么不具备：** 不管组件内部怎么建模，也不管几个组件是否共用一个数据库、是否合并进同一个进程（`servedBy`）。平台只管边界，边界之内归作者（见[组件自治](#组件自治)）。
- **AI 怎么适应：** 边界该画在哪，AI 替代不了，这是领域判断，要由你（和领域专家）来定。AI 在划好的边界内工作，一次只写一个组件。术语对照见[组件设计准则](../patterns/component-design.md#如果你的团队习惯用-ddd-的语言)。

### 2. 微服务与服务网格

**它是什么：** 微服务是把一个大程序拆成许多小服务，各自开发、各自部署，通过网络互相调用。服务网格是专门管"这些服务之间怎么通信"的一层基础设施：帮它们找到对方、分流、限流、失败重试、熔断（对方一直出错时先停止调用）。像把一家大餐馆拆成一条街上的许多小店。

- **好处：** 各家小店可以独立开张、独立装修；一家出了问题，不至于整条街停业。
- **代价：** 店多了，得有人管路牌（注册中心）、管入口（网关）、管排队限流（网格）——运维复杂度陡增，出了问题还得跨好几家店去查。
- **AI 开发的痛点：** 服务发现、配置中心、注册 SDK……这些概念都得 AI 去处理。
- **BrickKit 怎么具备：** 组件独立构建、独立部署、独立调用。地址靠 DNS 加环境变量，AI 只需读一个变量（如 `PEOPLE_BASIC_ENDPOINT`），不用理解服务发现。
- **BrickKit 为什么不具备：** 没有注册中心（Docker Compose 和 Kubernetes 自带的 DNS 就是服务发现）、网关、服务网格、熔断限流、配置中心。每一样都要常驻一个有人运维的东西，而 BrickKit 的 CLI 用完即走；熔断阈值、退避策略也因业务而异，平台一刀切不可能对。真要网关（如 Traefik），用 `labels` 原样透传。详见[平台刻意不做的事，以及为什么](overview.md#平台刻意不做的事以及为什么)。
- **AI 怎么适应：** 重试、超时、降级是组件自己的代码，要明确要求 AI 写——它的错误处理常只覆盖正常情况。

### 3. 六边形与分层架构

**它是什么：** 都是"程序内部怎么组织"的办法。分层是把程序切成上下几层（接收请求的、处理业务的、存取数据的），上层只调用下层。六边形架构更进一步：业务逻辑放在中心，数据库、网页接口、消息队列这些外部的东西，都通过事先约定的接口接上来。像厨房和外卖平台、收银机、供货商之间隔一层标准接口，换个供货商不用改菜谱。

- **好处：** 业务逻辑不依赖具体的框架或数据库，更容易单独测试，也更容易换掉某个外部系统。
- **代价：** 要多写不少接口和转换代码；在小程序里，像给自行车装变速箱。
- **AI 开发的痛点：** AI 容易给简单功能堆出很多层抽象（过度设计）。
- **BrickKit 怎么具备：** 不强制。有一份真实的分层参考：[用 Go 写一个 BrickKit 组件](../go-component-template.md)（HTTP 层、业务层、数据访问层）。
- **BrickKit 为什么不具备：** 组件内部怎么组织归作者。平台只规定组件在**边界上**呈现的样子（见[组件自治](#组件自治)），一旦管到内部，就从编排器变成了框架。
- **AI 怎么适应：** 要主动要求"够用就好，别加多余的抽象"；想要分层，就拿 Go 模板给它当样子。

### 4. 声明式与 GitOps

**它是什么：** 让工具做事有两种说法。命令式是一步步告诉它"先做这个、再做那个"，像教厨师做菜；声明式是只写"我最终要什么"，怎么做由工具去算，像在菜单上点菜。GitOps 是把这份声明放进 Git，当作系统的唯一事实来源，再由一个一直运行的程序持续把真实状态拉向声明。

- **好处：** 声明本身就是文档；放进 Git 之后，每次改动都能审查、能回滚。
- **代价：** 声明语言表达不了的事，就做不了；出了问题，要理解"声明是怎么变成实际动作的"。"持续拉回"那一半，还要有个常驻程序一直盯着。
- **AI 开发的痛点：** 让 AI 写部署脚本，步骤多，改动还难评审。
- **BrickKit 怎么具备：** `brickkit.yaml` 是唯一输入，放在 Git 里，每个环境一份完整文件。启动顺序、服务地址、环境变量、部署文件，都由 CLI 算出来——你评审的是 diff，不是一堆脚本。
- **BrickKit 为什么不具备：** 不做"持续拉回"。`brickkit up` 是一次性下发，CLI 用完就退出，没有任何东西盯着；有人手动改了运行中的容器，不会有程序替你改回去，要等下一次 `up` 才对齐。持续拉回需要一个常驻、要有人运维的程序，与"CLI 用完即走"冲突（见[平台极简](#平台极简)）。
- **AI 怎么适应：** 让 AI 只改 `brickkit.yaml`，先 `brickkit up --dry-run` 看计划、再 `up`；不要手改运行中的容器。

---

### 5. 约定优于配置

**它是什么：** 工具先替你定好一套规矩（叫什么名字、放在哪儿、默认怎么做），你照着来，就几乎不用写配置。Rails 是最有名的例子。

- **好处：** 要写、要读的配置少；换个人接手，一眼就知道东西在哪儿。
- **代价：** 规矩不合你的情况时，没有商量的余地。更麻烦的是"靠猜"的约定——工具悄悄替你做了决定，出错时你不知道它猜了什么。
- **AI 开发的痛点：** AI 要猜变量名、端口、服务地址；猜错了，往往没有任何报错。
- **BrickKit 怎么具备：** 固定命名：服务名、变量名、地址格式由固定规则算出——`people/basic` 1.0.0 的服务名一定是 `people-basic-1-0-0`，变量名一定是 `PEOPLE_BASIC_ENDPOINT`。不用猜，也不用配。
- **BrickKit 为什么不具备：** 不替你做决定。用哪个版本、暴露哪个端口、要不要启用某个组件，平台从不猜，必须你写明（见[精确优于隐式](#精确优于隐式)）。所以 BrickKit 自己的说法是"派生优于配置"：能从你写的内容**算出来**的才派生，算不出来的，你来写。
- **AI 怎么适应：** 变量名照规则推，别让 AI 自己起名字；版本、是否对外暴露这类决定，要求它明确写下来。

---

### 6. 十二要素配置

**它是什么：** "十二要素"是一份写云上应用的经验清单，其中一条最常被引用：配置（数据库地址、密码、别的服务在哪）不写死在代码里，而是在程序启动时从环境变量里读。

- **好处：** 同一个镜像放到测试环境、生产环境都能跑，环境之间的差别只在"启动时给了哪些环境变量"；密码不进代码仓库。
- **代价：** 环境变量只是一串扁平的文字，复杂配置得自己编码解码；变量一多就难管；漏了，往往到用到那一刻才发现；改配置还得重启。
- **AI 开发的痛点：** 要处理不同环境的配置差异。
- **BrickKit 怎么具备：** 依赖地址、数据库等资源的连接信息、组件自己的配置，全部以环境变量交给组件；Docker 和 Kubernetes 上的地址格式相同，换环境不用改代码。`up` 时就查：写错的配置键会警告，必填却没有值的会直接拦下。
- **BrickKit 为什么不具备：** 没有配置中心，也没有热更新——改配置就改 `brickkit.yaml`、再 `brickkit up` 重启，因为多数配置本来就必须重启才能安全生效。
- **AI 怎么适应：** 只用 `os.environ.get()` 读变量，并先读 `configSchema` 知道有哪些键；弱依赖的变量可能根本不存在，直接写 `os.environ["X"]` 会启动即崩。详见[环境变量注入契约](environment-variables.md)。

---

### 7. 精确版本与锁文件

**它是什么：** 依赖别人的软件时，版本可以写成"范围"（如 `^1.0.0`，意思是"1.x 里最新的都行"），也可以写死一个具体版本（`1.0.0`）。锁文件（如 npm 的 `package-lock.json`）则是把第一次装出来的具体版本记下来，以后照着装。

- **好处：** 今天装出来的和三个月后装出来的是同一份，不会因为别人发了个新版本，你的生产环境半夜悄悄变了；出问题时，也知道跑的是哪一版。
- **代价：** 补丁和安全修复不会自己到来，升级得你动手改一行；长期不升级，会落后很多。
- **AI 开发的痛点：** AI 做"破坏性修改"（新版本和旧版本不兼容），会连累依赖它的组件。
- **BrickKit 怎么具备：** 只认精确版本，写 `^1.0.0` 会直接报错；`brickkit add` 不写版本时，CLI 会查一次最新版本并写死（相当于自动生成锁文件）。版本号进入服务名，v1、v2 是两个不同的 DNS 名字，并排运行、互不冲突。见[核心概念](../concepts.md)。
- **BrickKit 为什么不具备：** 并排运行的两个版本之间，数据是否兼容，平台不管。
- **AI 怎么适应：** 让 AI 写 v2 时新增一个版本条目，别覆盖 v1；数据库迁移是否向下兼容，要你和 AI 自己保证。

---

### 8. 契约先行

**它是什么：** 两个团队要对接，先把"接口长什么样"写成一份文件（如 OpenAPI 或 protobuf 文件），双方各自照着实现，而不是写完一边、再让另一边去猜。像先约好插头的形状。

- **好处：** 双方可以并行开发；不读实现代码，就知道组件对外承诺了什么。
- **代价：** 契约文件要有人维护。契约与实现对不上的时候，比没有契约更糟——读的人信了一份过期的说明。
- **AI 开发的痛点：** AI 想调用另一个组件，只能去翻它的源码，靠猜。
- **BrickKit 怎么具备：** 组件用 `artifacts` 把契约文件随 Manifest 一起发布，`add`/`fetch` 会把它们下载下来；市场还要求闭源且对外提供 API 的组件必须带上 `api-contract`——代码可以闭源，契约不能。
- **BrickKit 为什么不具备：** 不规定用哪种格式（`type`、`format` 是 CLI 从不解析的自由字符串），也不检查实现是否真的符合契约。
- **AI 怎么适应：** 让 AI 读契约、别读依赖方的源码（这样依赖方怎么重构都波及不到它）；契约与实现是否一致，要靠你自己写的契约测试来验证。见 [AI 辅助开发指南](../ai-development.md)。

---

### 9. 契约式设计

**它是什么：** 每个函数或模块写明"我要求输入满足什么条件、我保证输出满足什么条件"，违反就立刻报错。像电器铭牌上写着"输入 220V、输出 12V"，接错了就跳闸。英文名 Design by Contract。

- **好处：** 错误在离原因最近的地方被抓住；这些规则本身就是最精确的说明书。
- **代价：** 规则写得太严，合法但没想到的用法也会被挡在门外；写得太松，等于没写。每次运行都检查有开销，规则本身也要维护。
- **AI 开发的痛点：** AI 不知道一个组件接受哪些配置、什么取值范围，只能凭印象。
- **BrickKit 怎么具备：** 只借"写下来"这一半：`configSchema` 写明有哪些配置项、什么类型、允许什么取值范围（`enum`、`minimum`、`maximum`、`pattern`），人和 AI 都读得到。CLI 检查项目里写的配置键**名字**是否存在，写错会警告。严格说它只是契约式设计的近亲，因为它只描述、不强制。
- **BrickKit 为什么不具备：** 不检查配置的**值**。分界线在于有没有运行时的安全网：值写错了，组件自己会崩，你一定会发现；名字写错了，变量悄悄不存在，组件走默认分支照常运行，没有任何东西提醒你。而且一旦开始校验值就停不下来——枚举？范围？正则？CLI 会越长越胖。见 [configSchema 是说明书，不是安检机](#configschema-是说明书不是安检机)。
- **AI 怎么适应：** 让 AI 先读 `configSchema` 再写代码；配置值的校验，让它写在组件启动时，并给出清楚的报错。

---

### 10. 大声失败

**它是什么：** 程序发现自己不对劲时，立刻、明显地停下来报错，而不是假装没事继续往下跑。英文叫 fail fast。

- **好处：** 错误暴露在最早、离原因最近的时候。最坏的 bug 不是崩溃，而是"悄悄给出一个看起来正常的错误答案"。
- **代价：** 更严格意味着更多"拒绝"：一个多写了未知字段的文件、一个没做防御的组件，本来也许能凑合跑，现在直接起不来。
- **AI 开发的痛点：** AI 的错误处理常只覆盖正常情况，弱依赖缺失、迁移失败这类边界情况容易被漏掉。
- **BrickKit 怎么具备：** Manifest 里不认识的字段直接拒绝；写错的配置键会警告；必填、没有默认值、项目里又没填的配置项，会拦下 `up`。最典型的是弱依赖：缺失时**什么变量都不注入**，而不是注入一个空字符串——空字符串拼进地址，请求会悄悄打到组件自己身上，还拿到一个看似健康的 200，这种 bug 极难查（AGENTS.zh.md §9.13）。
- **BrickKit 为什么不具备：** 出了错怎么降级，平台不定——降级是业务逻辑：Redis 挂了，有的组件改查数据库，有的返回空列表，有的写本地文件稍后重试。
- **AI 怎么适应：** 明确要求 AI 处理"弱依赖缺失"和"迁移失败"；读弱依赖变量用 `.get()` 并写明缺失时怎么办；入口对不认识的参数立刻报错退出。

---

### 11. 最小权限

**它是什么：** 每个程序、每个组件只拿到完成工作所需的最少访问权限，其余一律默认不通。像宾馆的房卡，只能开你自己那间房。在网络安全里它常和"零信任"一起被提起。

- **好处：** 某个组件被攻破，或者只是出了 bug，它能碰到的东西有限，损失被限制在小范围里。
- **代价：** 每一条允许的访问都要明确写出来。漏放一条，就是一次"莫名其妙连不上"的排查。
- **AI 开发的痛点：** 出了 bug 或被攻破，组件能碰到的东西越多，损失越大。
- **BrickKit 怎么具备：** 不映射端口就不能从外部访问，不写 `expose` 就没有对外入口；在 Kubernetes 上可以让 CLI 按依赖图生成网络策略——只放行你声明过的依赖方向；CLI 本身也从不挂载 Docker socket。
- **BrickKit 为什么不具备：** 网络策略和 ServiceAccount 隔离要**主动开启**，平台不替你默认打开——打开它们可能让一个本来能跑的组件起不来，这个代价该由你按项目判断。网络策略还要集群的网络插件（CNI）真的执行它才生效，否则形同空文（CLI 会警告）。见[网络策略与最小权限](../guide/11-network-policy.md)。
- **AI 怎么适应：** 让 AI 只声明真正需要的依赖（依赖越少，放行的路越少）；要不要开启网络策略，由人决定。

---

### 12. 供应链安全

**它是什么：** 你安装的第三方组件，是不是真的出自它声称的作者？有没有在半路被人调包？像快递上的封条加发件人签名。

- **好处：** 能防止冒名顶替，也能防止传输途中被篡改。
- **代价：** 签名只能证明"这是谁发的、没被改过"，不能证明"发的东西没有恶意"；你还得自己管理"信任哪些公钥"。
- **AI 开发的痛点：** 让 AI 引入第三方组件时，来源难以核实。
- **BrickKit 怎么具备：** 发布者用 cosign 签名，安装方只用 Go 标准库验证，不需要装 cosign。信任的公钥配在你自己项目的 `installer.publicKeys` 里，而不是从市场取——否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉。注意：一把公钥都没配，验签就是**完全关闭**的（CLI 会警告一次）。
- **BrickKit 为什么不具备：** 不做事前审查：不扫描、不沙箱、不做静态分析。安装即信任，和 npm、VS Code 插件市场是同一套模型；事后发现恶意组件，市场把它标成 `blocked`。事前审查要么误伤大量正常组件，要么放过精心伪装的恶意代码，成本高、可靠性低。
- **AI 怎么适应：** 引入新组件、往 `publicKeys` 里加信任的公钥，都由人来确认，别交给 AI。见[签名与信任模型](signing-and-trust.md)。

---

### 13. 类型驱动开发

**它是什么：** 用编程语言的类型系统把规则"写进代码的形状里"，让错误的写法根本编译不过。比如订单金额不用随便一个数字，而用一个专门的"金额"类型，这样就不会误把"数量"当"金额"传进去。

- **好处：** 一大类错误在编译时就被挡住了，不用等到运行才发现。
- **代价：** 依赖语言：不是所有语言的类型系统都足够强。类型设计本身也要花功夫，设计得不好会变成负担。
- **AI 开发的痛点：** AI 写的代码对不对，光看代码看不出来。
- **BrickKit 怎么具备：** 没有。BrickKit 的 CLI 自己是用 Go 写的，受益于类型检查，但并不要求组件也这样。
- **BrickKit 为什么不具备：** 不限制语言，而且是最彻底的一种不限制：任何能构建出容器镜像的语言都行。
- **AI 怎么适应：** 选一门带类型检查的语言让 AI 写，让编译器当第一道关。见[从零开发自己的第一个组件](../guide/10-build-your-own.md)。

---

### 14. TDD 与 BDD

**它是什么：** TDD（测试驱动开发）是先写测试，再写让测试通过的代码；BDD（行为驱动开发）是先用接近日常语言的"给定……当……则……"描述期望的行为，再把它变成测试。像先写好验收标准，再开始做菜。

- **好处：** 测试成了对"代码该做什么"的约束，而不是对"代码已经做了什么"的复述；需求也变得可以检验。
- **代价：** 前期要投入时间。而且如果验收标准本身写错了，你会非常认真地把错的东西做出来。
- **AI 开发的痛点：** 让 AI 先写实现、再补测试，测试就成了对实现的复述——测的只是"代码做了它做的事"。
- **BrickKit 怎么具备：** 不强制，但给了建议：[分层测试](../patterns/testing.md)讲怎么给组件分层测试，还给了"先立规格、再写实现"的推荐顺序。BrickKit 独有的一点是 `brickkit up --dry-run`：它不起任何容器，就能检查 `component.yaml` 与 `brickkit.yaml` 是否对得上（比如配置项名写错）。
- **BrickKit 为什么不具备：** 怎么测试是组件自己的事，平台不检查。`--dry-run` 查的是**装配对不对**，不是**组件代码对不对**。
- **AI 怎么适应：** 先让 AI 写 `component.yaml` 和测试、看着测试变红，再让它写实现；它常只测正常场景，边界场景要你自己补。

---

### 15. 属性测试

**它是什么：** 普通测试是你手写几个例子：输入 A 应该得到 B。属性测试换一种思路：你描述"无论输入是什么，结果都应该满足的性质"（比如"排序之后的列表一定是有序的"），再让工具随机生成成千上万组输入，去找出违反这条性质的反例。

- **好处：** 能撞出你自己想不到的边界情况。
- **代价：** 想清楚"性质"本身不容易；找到反例之后往往要先把它缩小才看得懂；对大量依赖外部系统的代码不太好用。
- **AI 开发的痛点：** AI 生成的测试常只覆盖它想到的正常场景。
- **BrickKit 怎么具备：** 平台自己用了：CLI 里规则最密的三处——启停判定、启动顺序、资源配额合并——都有用几千组随机输入去验证的测试。对组件，只是在[数据构造指南](../patterns/data-construction.md)里提到过。
- **BrickKit 为什么不具备：** 不要求、也不推荐给组件：适用面比较窄，主要适合"核心不变量"（比如余额永远不为负）。
- **AI 怎么适应：** 核心不变量可以让 AI 写属性测试，其余不必。

## 十二条原则

### 平台极简

CLI 能不做的事就不做。每多一个功能就是永远多一份维护成本，而平台的全部工作只是：把组件连起来，把它们的声明翻译给 Docker 或 K8s。

**为什么。** 底层引擎本来就做得好的事——DNS、健康探针、重启策略、负载均衡——由它们来做，比平台自己造一份副本更好。一个长出运行时的平台，会变成你还得多养活的一样东西。

**代价。** 人们最先想到的那些东西这里没有：没有网关、没有配置中心、没有注册中心。[拒绝清单](overview.md#平台刻意不做的事以及为什么)写明了每一项该怎么替代，以及你要是硬造一个会看到什么。

**拒绝了什么。** 常驻控制面、注册中心、健康检查轮询、配置中心、服务网格。

### 组件自治

语言、框架、API 风格、事务、日志格式，都归组件自己。平台只要求三样：一份 Manifest、一个健康检查、以及组件去读它的环境变量。

**边界在哪。** 影响组件**之间**怎么协作的，平台管：怎么声明、怎么寻址、怎么配置、怎么依赖。影响组件**内部**怎么写的，平台不强制：用什么架构、怎么建模、怎么分层、怎么测试（[patterns/](../patterns/README.md) 里有建议，但没有任何东西检查）。这不等于平台对容器没有要求——它规定的是容器在**边界上**呈现的样子：入口对不认识的参数必须立刻报错退出（迁移容器与主服务用的是同一个镜像）、弱依赖的环境变量要用 `.get()` 读（缺失时平台根本不注入）、`/healthz` 只查进程自己、冷启动超过 30 秒要设 `startPeriodSeconds`。这些都是边界上的契约，不是对内部代码结构的干涉。平台一旦开始管边界之内，它就从"编排器"变成了"框架"——而框架只能产出一种形状的组件。

**为什么。** 这才让"任何能构建 Docker 镜像的语言"这句话成立。也因此前端组件只是另一个监听端口的容器：没有"静态"组件这个类型，CLI 里也就不会蔓延出到处是 `if type == static` 的分支（AGENTS.zh.md §9.10）。

**代价。** 边界之内的事平台帮不上忙——没有共享 SDK，不校验业务配置，对你怎么组织代码不表态。

**拒绝了什么。** SDK、sidecar、agent；特殊的组件类型；由平台定义的降级行为。

### 渐进式

不需要先把整个系统设计完。加一个组件，跑起来；再加一个，再跑；随时可以停，随时可以继续。

**为什么。** `brickkit add` 一条命令拉下一个组件的整棵依赖子树；`enabled` 跟着上层走，没人需要的就不在跑；`brickkit sync` 让源码目录只剩你正在看的那几个。这也是为什么五十个组件并不意味着五十样东西要装在脑子里：你只需要知道直接依赖的契约（通常一到三个），五十个组件的项目在本地可能只跑四个容器，传递依赖是 CLI 的事（AGENTS.zh.md §9.15）。

**代价。** 平台限定的是你**每个组件**需要知道的东西，而不是整体能长到多大。没有任何东西拦着你长出一个一次装不进脑子的系统。

**拒绝了什么。** 一个必须先完整、然后才能跑起任何东西的设计阶段。

### 环境无关

组件代码永远不知道自己跑在 Docker 还是 K8s 上。它读到的地址在两边都是 `http://<版本化服务名>:<端口>`，一个字节都不差。

**为什么。** 一份 Manifest，两种环境。组件描述的是"我是什么、我需要什么"，从不描述"我跑在哪"，所以它不带 `docker-compose.yaml`，也不带任何 K8s 清单（AGENTS.zh.md §9.4）。切换环境只改一个字段：`deploy.target`。

**代价。** 平台必须为两种引擎都生成正确的文件，而只有某一种引擎才能做到的事，从组件这一侧表达不出来。针对引擎的提示走 `labels` 透传，平台不解释它。

**拒绝了什么。** 按环境区分的组件文件；Manifest 里出现针对某个引擎的字段。

### 精确优于隐式

精确版本、显式暴露、显式启用。凡是平台不得不猜的，就让你自己说。

**为什么。** 范围版本是"我机器上能跑，生产上炸"的经典来源（AGENTS.zh.md §9.2）。钉版本仍然只发生一次，在 `add` 的时候，和锁文件的做法一样：不写版本，CLI 就向安装源问最新的可安装版本，把确切的结果写到磁盘上。暴露是主动开启的，因为对它的一次猜测，就是悄悄做出的一个安全决定。

**代价。** 要多写一些。就连没写 `enabled` 也是刻意的：它的意思是"跟着上层走"，不是"没设置"。

**拒绝了什么。** 范围版本（是错误，不是警告）、隐式暴露、依赖别名、一切"自动探测"。

### 安全默认

你不说，就什么都不可达。不映射端口，外部就访问不到；不声明 `expose`，就没有 Ingress；`private` 表示未经授权不可见。

**为什么。** 什么都不写时得到的，应当就是安全的那个状态。CLI 用完即走、没有监听端口，也从不挂载 Docker socket，所以平台自己不增加任何攻击面。

**它止步于哪里。** 这条原则管的是**可达性**，并不延伸到 K8s 的每一个默认值。`serviceAccount.enabled` 与 `podSecurity: restricted` 都是需主动开启的，因为它们任何一个都可能让一个已经能跑的组件起不来，而这是取决于具体项目的代价，平台没法替你权衡。不写 `serviceAccount: { enabled: true }`，每个 Pod 就用命名空间的 `default` ServiceAccount 运行，它的 token 照常挂载。

**拒绝了什么。** 任何默认就打开一条通路的做法。

### 开源优先

CLI 与市场都开源。闭源组件通过市场受控分发。

**为什么。** 你把部署交给它的平台，应该是你读得懂的。闭源是一个商业事实，不该被禁止，所以市场用 Manifest 与镜像引用取代 Git 仓库来存放它。它唯一不允许一直闭着的是契约：提供 API 的闭源组件必须声明 `api-contract` 产物（[市场指南](../guide/08-marketplace.md)里能看到这条拒绝）。

**代价。** 让闭源组件保持闭源，是发布者自己的工作，而且拉下镜像就等于交出了它要运行的每一个字节——见[闭源组件的镜像安全规范](../patterns/closed-source-image-hardening.md)。

**拒绝了什么。** 私有的 CLI 或市场。

### 平台提供工具，不替人做决定

只给机制，不定策略。多版本默认共存；降级逻辑归组件；破坏性变更是组织协调问题，版本共存只是它的一个物理缓冲。

**为什么。** `people-basic-1-0-0` 和 `people-basic-2-0-0` 是两个不同的 DNS 名字，所以共存对平台来说没有成本，也就没什么需要它去问"你确定吗"——`brickkit.yaml` 里把两个都列出来，**本身**就是意图（AGENTS.zh.md §9.3）。Redis 挂了以后组件怎么办——查数据库、返回空列表、写文件稍后重试——是业务逻辑，不同组件的正确答案不一样（AGENTS.zh.md §9.7）。

**代价。** v1 与 v2 之间的数据层不兼容，或者缺了降级，平台救不了你。这两样都是你的。

**拒绝了什么。** 弱依赖降级、通信治理（熔断、限流、重试）、多租户。

### 安装即信任

和 npm、VS Code 插件市场、GitHub 是同一套模型：安装一个组件，就是信任它。平台不做前置审查——不扫描、不沙箱、不做静态分析——只在事后出手：确认为恶意的组件会被标为 `blocked`，阻止新的安装。

**为什么。** 前置审查要么误报太多，拦下正常的组件；要么漏报太多，放过精心伪装的恶意代码。`blocked` 作为最后一道防线，成本低而且足够有效（AGENTS.zh.md §9.11）。市场是"集市"，不是"保险库"。

**它确实提供的。** 签名。发布者用 cosign 签名；安装方只用 Go 标准库验证。公钥必须放在**你自己**的项目里（`installer.publicKeys`），而不能从市场取——否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉，验证照样通过。一个公钥都没配时，验证整体关闭，CLI 会告警一次。细节见[签名与信任模型](signing-and-trust.md)。

**代价。** 你自己要对"从谁那里安装"负责。

**拒绝了什么。** 由平台提供的第三方安全审查。

### configSchema 是说明书，不是安检机

`configSchema` 记录的是组件自己的配置：类型、默认值，以及 `enum`、`minimum`、`maximum`、`pattern`（会被解析并保存，但从不强制执行）。CLI 不校验你填进 `config` 的**值**。但它会查**键名**：写了 `properties` 里没有的键，会警告，并猜你想写的是哪一个。

**界线为什么划在这里。** 划线的依据是：有没有运行期的安全网。**类型**写错，会大声失败——组件拿到 `"abc"`，对它调 `int()`，崩溃，你一定会注意到。**键名**写错，则是悄无声息地失败：那个变量压根不会出现，组件落进它的默认分支，运行得完全正常，只是不是你配置的那个样子。所以平台去抓那个否则看不见的失败，放过看得见的那个。它还只是一次存在性检查，没有后续的追问；而值校验一旦开了这扇门，就得一路回答要不要校验 `enum`、`minimum`、`pattern`，最后把整个 JSON Schema 都装进 CLI（AGENTS.zh.md §9.12）。

**一个很窄的例外。** 列在 `required` 里、又没有 `default` 的键，会让 `up` 直接失败。道理是同一个：缺失的项否则会悄悄地不存在，组件会看起来健康地跑着，只是有一条调用路径永远走不通。

**代价。** 这些声明不是保证。用户完全可以给一个 `minimum: 1` 的键填 `0`，`up` 时没有任何东西拦他。写下它们换来的是：人和 AI **看得见**预期的范围；报错、截断还是回退到默认值，由组件自己决定。

**拒绝了什么。** 任何形式的值校验。

### 一个组件一个仓库

不支持 monorepo 里拆子目录当组件。组件是独立的发布单元（它有自己的版本——monorepo 你要怎么打 tag？）、独立的移动单元（`brickkit sync` 搬的是整个目录，连 `.git` 一起），也是独立的权限单元（有自己的可见性和发布者）。

**为什么。** 两个组件一旦共用一个仓库，这三个单元都会坏（AGENTS.zh.md §9.16）。

**代价。** 通常情况下没有：同一块业务的几个部分——proto、后端代码、迁移脚本——属于**同一个**组件，不需要拆开。这条规则说的是组件，不是文件。

**拒绝了什么。** 子目录形式的组件。

### brickkit.yaml 就是声明

配置即意图。写了就执行，CLI 不反问"你确定吗"。

**为什么。** 期望状态在这份文件里，实际状态在 Docker 或 K8s 里；CLI 在两者之间不持有任何东西。每个环境一份完整、自包含的文件（`brickkit.prod.yaml`，用 `--config` 选择），没有 overlay、继承或合并规则。打开一个文件就能看到全貌，Git diff 一眼能读懂，对基础层的改动也永远不会悄悄影响到生产（AGENTS.zh.md §9.9）。

**代价。** 各环境文件之间会重复几行。而且你写了什么，跑的就是什么：用 `enabled: false` 收窄范围，下一次 `up` 就生效；想放宽回来，`git checkout brickkit.yaml`。

**拒绝了什么。** Overlay 与继承；确认提示。
