# 怎么可靠地调用一个依赖的地址

AGENTS.zh.md §5.1 承诺依赖的地址是稳定的、基于 DNS 的：`http://<版本化服务名>:<端口>`，由底层引擎自己的 DNS 解析，从来不是 BrickKit 自己跑起来的什么东西。这条承诺讲的是**这个名字本身**——它没有回答另一个问题：你的进程已经通过这个名字建立好一条连接之后，名字背后的容器被换掉了（一次重新部署、一次崩溃重启、一次滚动更新），你的 HTTP 客户端接下来会怎么样。这篇文档就是在回答这个问题——真跑出来的结果，不是凭经验猜的：这个仓库自己的教程和模板用到的三种语言——Go、Python、Node.js——里,一个什么都没改过的默认 HTTP 客户端，能不能在一条已经建立好的连接背后,扛住依赖的容器被换掉这件事?

## 实验怎么做的

一个 `docker compose` 项目：一个后端服务（`traefik/whoami`，它只回显自己容器的 hostname——正好用来分辨"响应来自旧容器"还是"响应来自新容器"），每种语言一个客户端，各自每 500ms 对 `http://backend/` 发一次请求，用的就是这门语言默认的长连接/连接池 HTTP 客户端——Go 用 `net/http.Client`，Python 用 `requests.Session()`，Node.js 用 `http.Agent({keepAlive: true})`。等大约 25 次请求都已经成功打到第一个容器之后，把后端强制重建（删掉、重新起一个全新的容器，落在一个真正不同的 IP 上——用 `docker network inspect` 核实过，不是假设），而客户端还在按自己的节奏继续轮询，完全不知道背后发生了什么。这正是真实场景里一次依赖调用在任何一次重新部署期间的样子——不管是 `docker` 还是 `k8s`，调用方永远不会收到"对方即将被换掉"这条信号。

## 三种语言各自实际发生了什么

**Go——失败一次，很快，紧接着下一次请求就恢复了。** 恰好落在切换那一刻的那一次请求立刻就失败了，远远没到 500ms 的轮询间隔——不是卡住：

```
[ 25] t=21:31:55.147 status=200 took=632.03µs body="Hostname: 8bda437b989b"
[ 26] t=21:31:55.648 ERROR: Get "http://backend/": dial tcp: lookup backend on 127.0.0.11:53: server misbehaving
[ 27] t=21:31:56.150 status=200 took=1.173938ms body="Hostname: ce0eda814117"
```

`127.0.0.11` 是 Docker 自己内置的 DNS 服务器——这是一次真实的 DNS 解析失败，立刻以一个 Go 的 `error` 值形式冒出来，不是悄悄卡住。下一个 500ms 之后的那次请求，已经打到了新容器（`ce0eda814117`）。这个结果在两次独立的运行里完全一致地复现了。Go 默认的 `Transport` 会发现连接池里的连接已经死了，下次需要用时重新拨号——包括重新做一次 DNS 查询——这个基本行为不需要关掉长连接，也不需要自己写重试逻辑。

**Python（`requests.Session`）——完全不报错，但会悄悄卡住好几秒。** 这是本次实验里唯一真正危险的结果。整段运行里其它每一次请求都是个位数毫秒；恰好落在那条已经失效的连接上的那一次，花了 **2.506 秒**，而且照样返回了 `200`，从头到尾没有抛出任何异常：

```
[ 25] t=21:31:55 status=200 took=0.003s body='Hostname: 8bda437b989b'
[ 26] t=21:31:58 status=200 took=2.506s body='Hostname: ce0eda814117'
[ 27] t=21:31:58 status=200 took=0.001s body='Hostname: ce0eda814117'
```

这次调用没有任何一处报错、没有打印任何警告、也没有以任何方式宣告发生了什么不寻常的事——唯一的痕迹就是那个 `took=` 的计时，而默认情况下没有任何东西会去检查它。`requests.Session()` 底层的 `urllib3` 连接池尝试复用那个已经死掉的 socket，写操作进了一个对端已经彻底消失的连接（没有 FIN，没有 RST——那个容器的整个网络命名空间直接没了），这个延迟的量级符合"连接池最终放弃了这次尝试、悄悄开了一个新连接，包括重新做一次 DNS 查询"这个解释。这次测试里之所以停在约 2.5 秒，是因为写了 `timeout=2` 这个参数——不然 Linux 自己的 TCP 重传时间表会拖得远比 2 秒长得多。**一次没有带 `timeout=` 参数的 `requests.Session()` 调用，完全没有这样一个上限。**

**Node.js（`http.Agent({keepAlive: true})`）——那次卡住的请求会一直挂到你自己设的超时触发；没有任何东西会自己触发。** 日志里顺序是乱的，因为 Node 的请求是异步的，那次倒霉的请求没有最先完成：

```
[ 26] t=21:31:56 status=200 took=3ms body="Hostname: ce0eda814117"
[ 27] t=21:31:56 status=200 took=2ms body="Hostname: ce0eda814117"
[ 28] t=21:31:57 status=200 took=3ms body="Hostname: ce0eda814117"
[ 25] t=21:31:57 ERROR: timeout
[ 29] t=21:31:57 status=200 took=1ms body="Hostname: ce0eda814117"
```

`26`–`29` 这几次都是切换**之后**发出的请求，全部干净利落地立刻打到了新容器——`Agent` 的连接池毫无阻碍地为它们各自开了新连接。请求 `25` 是切换那一刻恰好挂在那条正在死去的连接上的那一次，它自己从来没有恢复过来；它之所以最终以一条错误现身，纯粹是因为这次测试的客户端代码显式给这次请求设了 2 秒的 `timeout`、并在触发时调用了 `req.destroy()`。**如果没有这个显式的超时，这次请求会无限期地挂在那里**——Node 的 `http` 模块对一次请求本身完全没有任何默认超时。

## 这对你写代码意味着什么

**每一种主流 HTTP 客户端都扛住了依赖的容器被换掉这件事——没有任何一个会永远卡死在一个已经不存在的地址上。** AGENTS.zh.md §5.1 那条稳定性承诺是站得住的：你不需要什么 DNS 缓存击穿技巧、不需要关掉连接池的开关，也不需要写任何 BrickKit 专属的客户端代码，就能让普通的服务间调用扛过一次重新部署。版本化服务名在测试的每一种语言里，下一次尝试就能重新正确解析。

**但"最终会恢复"和"你的调用方完全没感觉到出过问题"是两种不同的保证，而测试的三种语言里，只有 Go 的默认行为把这两者一起白送给你。** 从这次实验里能得出的、真正具体、按语言区分的建议：

- **在每一种语言、对依赖的每一次调用，都显式设一个请求级别的超时。** 这是这次实验真正验证过、而不是凭空断言的唯一一条建议：把一次开放式的卡死变成有边界的几秒钟的，是 Python 调用里那个 `timeout=2`、是 Node 调用里那个 `timeout: 2000`——跟平台无关，也不是那些库自带的默认值。Go 的 `http.Client{Timeout: ...}` 同样应该显式设置，哪怕这次实验碰巧的这种失败方式本身并不需要它才能恢复。
- **把一次对依赖的调用失败或变慢，当成普通的、可以重试的业务逻辑事件**，不是致命错误。一次带短退避的重试，就能吸收掉上面每种语言里都出现的那一次请求级别的小抖动。这是故意留给你自己代码的责任，不是 BrickKit 会替你做的事——AGENTS.zh.md §9.7 解释了为什么平台完全不插手熔断、重试、退避策略：什么样的重试策略算合理，是一个因调用而异的业务判断，平台级别的统一默认值对大多数场景都会是错的。
- **一次"慢但成功"的调用是真实的生产风险，不只是 Python 的一个怪癖。** 那 2.5 秒的卡顿零报错、零日志。如果你自己服务的调用方设的超时比你短，它看到的就是一次失败，而**你自己**的日志里却找不到任何解释。你对依赖设的超时，应该比你自己的调用方愿意为你等待的时间更短。

## Docker 和 Kubernetes：这次实验跑的是 Compose，这一点很重要

这次测试全程跑在 `deploy.target: docker` 下，Docker 自己内置的 DNS 服务器（`127.0.0.11`）在容器背后被换掉的那一刻，真的会把 `backend` 重新解析到一个新的 IP——这正是上面 Go 的 DNS 报错和其它语言连接卡顿的直接成因。

在 `deploy.target: k8s` 下，机制不一样，而且不一样的地方恰好抹掉了其中一种失败方式：Kubernetes `Service` 的 `ClusterIP` 在这个 Service 的整个生命周期里是稳定不变的——真正做流量转发的是 `kube-proxy` 的路由规则（iptables 或 IPVS），它工作在 DNS **之下**，把流量导向当前健康的那个 Pod。客户端已经解析出来的那个 IP（Service 的 ClusterIP，不是任何一个具体 Pod 自己的 IP）不会像这次实验里 Compose 的 IP 那样过期，所以 Go 客户端那一次 DNS 查询失败在 K8s 下根本不会有对应的情形。跟这次实验测出来的东西完全一样的是：旧 Pod 的进程一退出，**那条 TCP 连接本身**照样会死掉，跟这次实验里发生的一模一样——所以 Python 和 Node.js 那种连接池卡顿并不是 Docker 独有的现象，同样的建议（显式设超时、把失败当成可以重试的事）在 `k8s` 下原封不动地适用。
