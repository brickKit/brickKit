# 闭源组件的镜像安全规范

brickKit 上的闭源组件，能让你的 Git 仓库保持私有——市场只存 Manifest、镜像引用，以及（如果这个组件对外提供 API）它的契约文件（AGENTS.zh.md §5.9）。靠这条路径，团队之外的任何人都拿不到你的仓库。

但镜像引用是完全不同的另一回事。拉取它——或者用 `docker save` 导出它，这不需要任何超出"正常部署这个组件"之外的额外权限——就等于把容器将来会执行的每一个字节都交了出去：编译产物、解释型语言的源文件、打包进去的静态资源、配置文件，跨越镜像构建过程中出现过的每一层，全部都在里面。"闭源"描述的是你的**仓库**存在哪里，跟拿到**镜像**的客户能从里面复原出什么，完全是两个独立的问题。这份规范讲的是第二个问题——包括老实说清楚，一个纯软件平台到底能把这个口子堵到什么程度。

## 威胁模型：这份规范防的是什么，不防的是什么

这份规范要做到的，是把"从发布出去的镜像里提取业务逻辑"这件事的成本抬高到足以挡住随手尝试和中等投入的攻击——好奇心驱使的客户翻一翻、竞争对手扫一眼、被丢进一份解包出来的文件系统、要求"看看这东西怎么实现的"的 AI 编程助手。它挡不住、也没法挡住一个预算充足、技术过硬、有明确动机的攻击者。下面的每一种手段，操作的对象都是**已经交到攻击者手里的字节**——只要时间和技术足够，字节永远读得出来。真要把这最后一段路也堵上，需要的是硬件层面的方案（机密计算、可信执行环境），这完全超出了一个软件分发平台能提供的范围，也超出这份规范的讨论边界。

这种不对称是刻意的，不是缺陷：一个有预算、有能力破解下面全部手段的人，本身的技术成本也很高——花这份成本专门盯上你这一个组件，通常并不是他们对这份能力最划算的用法。这份规范的目标是把绝大多数人的门槛抬高，不是给所有人建一堵墙。

## 两个不同的问题，不要用同一套手段解决

**别人能不能从镜像里读出我的逻辑？**——这是这份规范要讲的：构建阶段的加固，以及从一开始就不让敏感内容进镜像的 Docker 卫生习惯。

**别人拿到镜像之后，能不能在没有授权的情况下把它跑起来？**——这是授权与机器指纹绑定要解决的：在组件真正开始对外服务之前，拿一份签名过的授权跟硬件或环境指纹做比对。这是一个真实、有用的控制手段，但解决的是不同的问题：它不藏任何东西，它管的是**能不能执行**。而且这完全是组件自己的业务逻辑，跟多租户、通信治理是同一种性质（AGENTS.zh.md §4.1 的拒绝清单）——brickKit 不提供、也不应该提供任何这方面的机制。真的需要的话，把它实现成组件自己启动逻辑里的一段普通代码就行，跟实现任何其他业务规则没有区别。

把这两件事混在一起想，很容易做出错误判断——比如误以为一个做了混淆的二进制"已经安全"了，只因为它同时也做了授权校验，而授权校验和代码混淆防的根本是两拨完全不同的人。

## Docker 镜像本身的卫生问题——跟语言无关，谁都得做

这几条不管用什么语言写的组件都适用，而且往往是最大的一块杠杆：一份用 `COPY . .` 写出来的单阶段镜像，会把整个源码树——README、内部设计笔记、测试夹具，以及（只要用了包管理器）全部开发依赖——原封不动地打进去，不管跑起来的进程有没有碰过这些东西。

- **用多阶段构建，只把运行时真正需要的产物拷进最后一个阶段。** 构建工具、源文件、包管理器缓存都该留在一个永远不会被推送出去的前置阶段里。如果你最终镜像的 `FROM` 拉的是一份完整的 SDK 镜像而不是精简的运行时基础镜像，值得想想为什么。
- **层是叠加的——后面某一层删掉的东西，不会从前面那一层消失。** 一层里 `COPY secrets.env .`，下一层再 `RUN rm secrets.env`，`secrets.env` 依然完完整整地存在于镜像里：`docker save`（或者任何直接遍历镜像层的工具）照样能从前面那一层读到它，跟后面有没有 `rm` 毫无关系。真正的修法不是"事后加一步清理"，而是从一开始就不要把敏感内容拷进任何一层会被发布出去的镜像。这是最常见、也最容易被忽视的一类失误——因为跑起来的容器里确实已经没有那个文件了，检查一个正在跑的容器完全看不出镜像层里还留着什么。
- **生产构建不要带 source map。** source map 能把压缩混淆过的 JavaScript 原样还原回接近原文、可读的源码。不管用哪个打包工具，都要确认生产环境的配置不会生成或者打包进 source map（webpack 的 `devtool: false`/不外泄 `hidden-source-map`，esbuild 生产构建关掉 `--sourcemap`，等等）。
- **最终镜像不要带编译器或者包管理器本体**，除非运行时进程真的需要它（比如一个 REPL，或者需要按需编译插件的加载系统）。如果它只是因为基础镜像凑巧带了才留在那儿，那纯粹是白白多出来的一个攻击面，什么好处都没换回来。
- **`.dockerignore` 要排除 `.git/`、README 和内部文档、测试夹具、CI 配置**——这些一个都不会被运行时用到，也就没有任何理由出现在镜像的任何一个字节里，`.git/` 尤其危险，它交出去的不只是当前这份代码，是整个提交历史。
- **发布的镜像引用要钉在内容摘要（`image@sha256:...`）上，而不是用可变的 tag。** 这条值得跟 brickKit 自己现有的签名机制对照着说清楚：市场的签名签的是 Manifest（AGENTS.zh.md §5.9），而镜像引用只是这份 Manifest 里的一个字符串——所以签名保证的是这个**字符串**没被改，不保证这个字符串现在指向的字节，跟你签名那一刻指向的字节还是不是同一份。一个可变 tag 完全可以在事后被重新指向另一个镜像，而已经签过名的那份 Manifest 一个字都不会变。换成摘要引用，这个缺口就自动补上了，不需要 brickKit 新增任何机制——这只是你本来就要往 `deployment.image` 里填的那个字符串该怎么写的问题。

## 按语言分类的加固手段——能做到什么程度由编译模型决定，不是靠使劲

这一部分没法一概而论，假装它能一概而论是最快把力气用错地方的做法。能做到什么程度几乎完全取决于你的语言把源码变成实际发布物的那道工序——选错了适合自己这一类的手段，得到的只是"看起来防住了"，实质上什么都没防住。

**原生编译语言（Go / Rust / C / C++ / Zig）。** 这一类天生就有一个不错的起点：编译成机器码之后，反编译工具能拿回控制流和逻辑，但拿不回原始的变量名、注释、源码结构——想复原出接近原文的源码是真的困难，不只是麻烦。去掉调试符号（`go build -ldflags="-s -w"`、C/C++ 用 `strip`、Rust 的 `strip = true` release 配置）能去掉反编译工具用来让输出变得可读的大部分线索，对大多数组件来说这一步基本就是能做到的大部分保护了。Go 具体来说，即使去过符号，剩下的元数据也比很多人以为的要多——包路径、部分字符串字面量、跟反射相关的类型信息在 `-ldflags="-s -w"` 之后依然存在——[`garble`](https://github.com/burrowers/garble) 这个工具就是专门为了补这个缺口存在的：它改写整个构建过程，混淆标识符、抹掉更多构建信息、混淆字面量。Rust/C++ 也有全程序混淆器（基于 LLVM pass 的工具，比如 `ollvm`），但它们相对"去符号后直接发布"带来的边际收益下降得很快，而维护和工具链兼容性的代价却在往上爬——只有在去符号之后的二进制真的还满足不了你的威胁模型时，才值得去碰它们。

**字节码虚拟机语言（Java / .NET/C#）。** 这一类是"不做加固"和"直接发布源码"距离最近的一类：JVM 字节码和 CIL 都被设计得保留了足够多的结构信息，反编译工具（CFR、Procyon、dnSpy、ILSpy）常规操作就能把输出还原到接近原文、读起来毫无障碍的程度，类名方法名全都在。对这两个生态来说，混淆器不是锦上添花，只要逻辑对你有价值，它基本是必需品：Java/Android 用 ProGuard 或 R8，更广泛的 Java 场景用 DashO 或 Zelix KlassMaster，.NET 用 ConfuserEx、Dotfuscator 或 Obfuscar。它们都会重命名标识符、去掉不必要的元数据，其中较强的那批还会做控制流混淆——真正能挡住一次直接反编译的，是这几件事叠加在一起，不是单靠某一项。

**解释型/脚本语言（Python / Ruby / PHP / 未打包的原生 Node.js/JavaScript）。** 最弱的一类，因为对这里的大多数语言来说，发布出去的产物本身**就是**源码，或者跟源码的差距小到几乎不重要：Python 的 `.pyc` 字节码，用成熟、免费可得的工具（`decompyle3` 及其后继者）就能还原成接近原文的 Python；未压缩的 JavaScript 就是……可以直接读。这一类要么真的需要一道编译工序，要么就得老实承认这里的保护本来就很弱：
- **Python**：[Cython](https://cython.org/) 把 Python 编译成原生的 C 扩展——这相当于把这个组件挪进了上面"原生编译"那一类，是实际可行的手段里最强的一个，代价是代码得跟 Cython 兼容，而且要多一道真实的构建工序。[PyArmor](https://pyarmor.readthedocs.io/) 不需要 Cython 那种改写，直接对字节码做加密和混淆，强度明显低于 Cython，但也绝不是零。
- **Node.js/TypeScript**：单靠打包和压缩（webpack、esbuild、terser）对一次认真的尝试来说基本没什么用——标识符被打乱了，但控制流和结构完全清晰可读。一个真正的 [JavaScript 混淆器](https://github.com/javascript-obfuscator/javascript-obfuscator)（控制流平坦化、字符串加密）能把你带到跟一个中等水平的字节码虚拟机混淆器差不多的档位。打包成单文件可执行程序（`pkg`、`nexe`，或者某些运行时自带的单可执行文件打包能力）嵌入的是 V8 字节码而不是源码文本，门槛明显比前两种都高，不过针对 V8 字节码的提取工具同样存在。
- **PHP**：`ionCube` 和 Zend Guard 在这里扮演的角色，跟 PyArmor 对 Python 是一样的——商业化的字节码加密器，brickKit 对这一类工具本身没有任何倾向性意见，只是指出这个类别确实需要这么一个东西。

这类工具生态会随时间变化——名单里的某个名字，等你真的读到这份文档时，可能已经没人维护，或者已经被别的工具取代。真正该留下来的是这个分类原则本身：原生编译起点就不错，基本靠去符号；字节码虚拟机不上真正的混淆器就约等于发布源码；解释型语言要么补一道真正的编译工序，要么就得清醒地承认发布出去的东西不管怎么处理都很接近源码。

## 这些手段一个都防不住的事

上面所有内容加固的都是**静态产物**——躺在镜像里的那些字节。它们一个都碰不到**正在运行的进程**：一个能挂调试器、能 dump 进程内存、能追踪系统调用去看一个正在跑的实例的攻击者，看到的是解密之后的字符串、反混淆之后的数据结构、明文的值——不管磁盘上那份二进制做过多少加固都一样。防这个需要控制运行环境本身（谁能 exec 进你的容器、谁能 attach 上去、宿主机层面的隔离）——这超出了上面任何一种手段能做到的范围，也超出了 brickKit 能提供的范围。一份只字不提这件事、只讲静态加固的安全规范，对读者是不诚实的，所以这里把话说明白：静态加固能防住一份镜像被随手拿走就白白交出逻辑；它防不住一个正在有意查看这个进程运行状态的、合法的操作者。

## brickKit 自己在这件事上做了什么

只有一件，而且已经现成存在：市场用 cosign 给 Manifest 签名，CLI 验签不依赖本机装没装 cosign（AGENTS.zh.md §5.9）。这份规范里除了"把镜像钉在摘要上，好让这份签名真的能担保字节，而不只是担保一个字符串"之外的所有内容，都是你自己构建流程的责任，不是 brickKit 的。这个分工不是疏漏——跟平台"拒绝清单"（AGENTS.zh.md §4.1）上每一条的道理完全一样：brickKit 负责连接和编排组件，不负责审查、扫描，或者替组件内部的内容做任何业务判断。一个"看看这像不像会泄露源码"的镜像内容扫描器，会撞上平台早就为第三方组件安全审查拒绝过的同一个两难（AGENTS.zh.md §9.11）——要么误报率高，要么漏报率高，一个通用工具在这两者之间找不到中间地带。加固自己的镜像，用上面这些跟你实际发布物匹配的工具，完全是你自己该做的判断。
