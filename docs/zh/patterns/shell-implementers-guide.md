# 外壳该怎么造才合格

> 前置阅读：先看[架构总览](overview.md)——本文假定你已经理解版本化服务名与环境变量注入这两个机制。

`servedBy`（见 AGENTS.md §5.7）让一个组件声明"我的代码跑在另一个组件的容器里，不是自己的"。这篇文档写给造那个"外壳"的人看，只做两件事：把平台到底会往外壳里塞什么、不塞什么说清楚；把任何一个真正上线过的合并进程都逃不掉的九条正确性要求列出来——跟语言、框架无关。

## servedBy 对平台的要求是什么、又不是什么

一个 servedBy 组件的代码跑在你外壳的那一个容器（或 Pod）里。平台负责把地址算对——按部署目标生成一个 Docker 网络别名或一个 K8s Service——并把该注入这个组件的那些 `*_ENDPOINT` 变量合并进外壳的环境，这样任何依赖了你收编的组件的调用方，地址照样能解析对。平台的合同到此为止：它不需要知道、这篇文档也不会要求你告诉它，你的外壳用什么语言写、开了几个进程或线程、用哪种并发原语、镜像基于什么。同一个平台上的两个外壳内部可以完全不像——一个用 Go 的 `errgroup` 编排 goroutine，另一个跑一个 `asyncio` 事件循环——两者同样合规，因为平台的边界只划到"哪个地址指向哪里"这一层，不再往下管。

## 平台会往外壳环境里放什么

- **每一个被收编组件如果独立部署本该拿到的 `*_ENDPOINT` 变量，一个不少。** 这些变量直接合并进外壳进程真实的操作系统环境——不是经过某个中间配置对象转手，由你自己的代码再去拼装。如果两个被收编组件对同一个变量名给出不同的值（比如同一个组件 ID 的两个不同精确版本各自需要不一样的地址），这是一个真实冲突，平台会当场拦下、拒绝生成，而不是悄悄选一个。
- **`BRICKKIT_SERVED_MEMBERS`**——当前这次部署实际收编的组件的版本化服务名列表，逗号分隔。一个外壳镜像里编译进去的模块数量，通常比任何一次具体部署实际要用到的多，这个变量就是告诉你，这一次启动，编译进去的这些模块里，到底该激活哪几个。这里有两个取值，意思正好相反：**空字符串**代表"当前零个成员被激活"——一个合格的外壳必须一个模块都不初始化；变量**整个不存在**代表这个容器压根不是由 brickKit 生成的部署在跑（比如你为了本地调试手动启动了这个二进制）——那种情况下你想怎么处理都行。千万别把这两种情况合并成一条回退逻辑。推荐做法：启动时，用平台同一套规则（组件 ID 里的 `/` 和 `.` 换成 `-`，全部小写，精确版本号里的 `.` 也换成 `-`）自己算出每个编译进来的模块对应的版本化服务名，不在这份名单上的模块——包括它的迁移、包括它要打开的资源连接——一律跳过初始化。

## 平台刻意不会往那里放什么

一个被收编组件自己的 `configSchema` 配置值，以及它的资源连接变量（`DATABASE_*` 之类），永远不会合并进外壳的环境——这不是遗漏，是一条硬边界。`*_ENDPOINT` 这类变量名是从组件 ID 算出来的，天然在整个系统里唯一；而 `pgSchema` 这样的配置键不是——两个各自独立开发的模块完全可能都用这个通用名字表示两个完全不同的值，合并进同一个共享的进程环境，只会悄悄让一个覆盖另一个。让你收编的每个模块拿到它自己那份隔离的配置视图、自己那份独立的资源连接，这是你的活，不是平台的——见下面第 5 条。同样的道理，平台也从不会为除外壳自己以外的任何东西写 `COMPONENT_ID` 或 `COMPONENT_VERSION`：这两个变量名是固定的，一旦你收编超过一个组件就必然撞车。

## 合并进程必须满足的九条性质

下面每一条都是真正把外壳发布上线的团队踩坑踩出来的。没有一条是绑定某种语言、数据库或框架的——只有举例是，举例都会标出来。

1. **健康检查只能反映合并单元本身，绝不能反映下游依赖。** 这跟平台对单个组件 `/healthz` 的要求是同一条规则——但合并之后赌注更大了：被收编的某一个模块的下游一抖，就能把这一整个进程里所有模块共用的健康信号一起拖垮，重启也是一锅端，不是只重启真正出问题的那一个。
2. **拿框架实际区别对待的每一种 HTTP 方法都去真的验一遍健康检查，不要相信文档说的行为在真实环境里也成立。** 一个真实案例：某个流行的 Python ASGI 框架的路由层，对一个只声明了 `GET` 的路由，并不会像它底层工具包的文档暗示的那样自动应答 `HEAD` 请求——用 `HEAD` 探活的健康检查器（`wget --spider` 就是这么干的）会对一个 `GET` 完全正常的路由拿到 404。这条教训不止对这一个框架成立：不管你的部署目标实际用哪种健康检查机制，拿你真正合并出来的那个二进制去实测一遍，不要靠读文档去推断。
3. **一个模块出了意料之外的错误，不能连累它的邻居。** 独立部署时每个组件的爆炸半径就是它自己；一个粗暴合并的进程很容易把这个半径悄悄放大成"整个外壳"。一个具体的坑：那些让一组独立任务共用同一个取消信号的编排原语（Go 的 `errgroup.WithContext` 就是一个例子——组内第一个返回非 nil 错误的 goroutine，会取消整组共享的 context，连累组里其它所有 goroutine）天生是为"这些东西该同生共死"设计的，这恰恰是模块之间本该保持独立故障隔离时最不该用的形状。不管你的语言里对应的原语是什么，先搞清楚它在单个失败发生时到底会做什么，再决定拿它来编排你的模块。
4. **任何跨模块共享的有状态资源——连接池、客户端——每次借出前都必须清掉上一次遗留的身份或作用域，否则下一个借用者会悄悄继承它。** 这是这份清单里最危险的一条，因为违反它不会崩溃、不会报错——只会安安静静地用错误的身份读到或写下错误的数据。具体怎么满足它完全看技术栈（PostgreSQL 里一个事务作用域的 `SET LOCAL ROLE`/`SET LOCAL search_path`，随提交或回滚自动重置，是一种真实可用的做法；换一个数据库或换一个连接池库需要换一种机制），但底层这条规则是通用的：永远不要在请求或事务边界之外，给一个共享资源池设置身份或作用域。
5. **进程级全局状态，整个进程只初始化一次，不是每收编一个模块就初始化一次。** 信号处理、tracer/logger/metrics 的注册、任何框架级的全局配置都属于这一条——按上面两节的道理，给每个模块一份自己的配置和自己的资源连接同样属于这一条，因为平台是刻意不替你做这层合并的。谁恰好最后初始化，谁往往就悄悄赢了，通常不会有任何提示告诉你发生了这件事。
6. **你独立部署时用来发现依赖地址的那套机制，合并之后必须照样能用。** 如果你的代码（或者你维护的一个共享 SDK）是直接从进程真实的环境变量里读依赖地址——正是本文档前面描述的那套机制——这条性质会自动成立，因为平台已经把这些变量原样写进了外壳容器真实的操作系统环境，跟独立部署一个组件时完全一样。唯一会踩坑的地方，是你自己技术栈里某一层把这个地址转手或者重新计算了一遍（比如外壳的启动器自己构造一个逐模块的配置对象，再分发给各个模块），而恰好就是这个转手的环节，没有人真的把真实环境变量接上去——这种 bug 会一直藏着，直到第一次有代码路径真的依赖它才会暴露。
7. **迁移和建表的先后顺序，完全变成你自己的责任，必须从你各模块真实的依赖关系推导出来。** 平台对 servedBy 组件完全不生成迁移容器（生成阶段就会警告你，就是为了不让你在运行时才被这件事惊到）——外壳自己的启动代码，必须按各模块之间真实存在的外键或引用关系去决定迁移的执行顺序，不能是随意的顺序，也不能假设它是幂等的。
8. **任何进程级、按名字全局唯一注册一次的机制，合并进同一个进程后都需要补一道重复注册检查。** 这条不局限于任何一种序列化格式。Go 里的经典坑是：两个模块各自 vendor 了同一个第三方组件生成的 gRPC/protobuf 客户端代码（为了避免互相直接 import 对方的仓库），编进同一个二进制之后，两份代码会各自尝试往 `google.golang.org/protobuf` 的进程级全局类型注册表里注册同一个 `.proto` 文件路径——第二次注册直接 panic，报错信息完全看不出真正的原因是一次合并部署。真正管用的修法，是对"组件之间从不互相 import"这条原则开一个刻意而窄的口子：一个只包含生成出来的消息类型和客户端桩代码——不含任何手写业务逻辑——的包，可以作为一个独立的共享模块发布出去，让所有需要这份契约的组件直接依赖它，而不是各自 vendor 一份。这样共享纯生成的契约代码，和共享真实业务逻辑不是一回事，不会破坏组件自治；而且它能保证不管这些模块最终怎么分组合并，一个契约的类型在合并进程里永远只有一份编译实例。如果你自己的技术栈里也有类似的全局按名字注册的模式（不是每种语言都有），同样的例外——以及同样的修法——大概率也适用。
9. **没有任何办法从外部验证一个外壳镜像声明的版本号，跟它里面实际编译进去的内容是不是真的对得上。** 镜像对平台来说是一个不透明的引用；守住这条承诺完全靠你自己团队的纪律（手工维护一份版本台账，是个不优雅但现实可行的答案）。这是把代码合并进一个制品之后一个诚实的、永久性的局限——不是未来哪个平台版本打算补上的缺口。

## 多版本共存、部署形态还能不一样

真实的迁移从来不是一刀切——总有一些调用方先升级、一些后升级，外壳自己收编的内容也会随时间变化。`servedBy` 并没有在这里额外引入一个新的复杂度维度：下面每一种场景，其实都是 BrickKit 原有的精确版本锁定与版本化服务命名规则（AGENTS.md §5.1/§9.2/§9.3）本来就该有的推论——`servedBy` 只是 `components:` 下某一条普通条目上多出来的一个字段而已。

**老调用方留在旧版本，新调用方切到新版本，一个版本合并部署、另一个版本独立部署——两者之间不需要任何协调。**

```yaml
components:
  - id: infra/shell-go-core
    version: 1.0.0
    image: brickenterprise/be-shell-go:1.0.0
    healthCheck: { path: /healthz }
    deployment: { port: 9000 }

  - id: mdm/customer
    version: 1.0.7                       # 还没迁移，仍然是自己独立的容器
    deployment: { port: 8080 }

  - id: mdm/customer
    version: 2.0.0                       # 已迁移，代码跑在外壳里
    servedBy: infra/shell-go-core@1.0.0
    deployment: { port: 8081 }
```

一个还在依赖 `mdm/customer@1.0.7` 的组件，拿到的是 `MDM_CUSTOMER_ENDPOINT=http://mdm-customer-1-0-7:8080`——这个版本自己独立的服务，跟这个功能存在之前完全一样。一个依赖 `mdm/customer@2.0.0` 的组件，拿到的是 `MDM_CUSTOMER_ENDPOINT=http://mdm-customer-2-0-0:8081`——注意这仍然是 `mdm/customer` 自己的版本化服务名、自己声明的端口，形状上跟一个独立部署的版本产出的东西完全一样。真正不一样的地方，在这一层完全看不见：平台让这个名字解析到外壳，而不是它自己的容器（要么是一个 Docker 网络别名，要么是一个专门选中外壳 Pod 的 K8s Service——见下文）。不管调用方自己声明的依赖，还是它算出来的地址，都完全不需要因为依赖实际部署在哪儿而改变——这种间接性正是平台地址注入机制存在的意义。

**同一个外壳可以同时收编同一个逻辑组件的两个版本**——这正是迁移过程中，一部分调用方停在旧版本、一部分已经切到新版本，而两个版本出于资源占用考虑又都已经合并部署的那种中间状态：

```yaml
  - id: mdm/customer
    version: 1.0.7
    servedBy: infra/shell-go-core@1.0.0
    deployment: { port: 8080 }
  - id: mdm/customer
    version: 2.0.0
    servedBy: infra/shell-go-core@1.0.0
    deployment: { port: 8081 }           # 必须跟 1.0.7 的端口不一样
```

给两个版本各自不同的端口，平台就会把它们当成同一个分组里两个完全独立的成员来处理——合并出来的端点变量、网络路由、`BRICKKIT_SERVED_MEMBERS`，全都不需要任何特殊处理，跟两个毫不相关的组件共享同一个外壳时的处理方式一模一样。唯一需要你自己保证正确的地方是：外壳自己的模块注册表，必须按完整的版本化服务名（`mdm-customer-1-0-7` 而不是 `mdm-customer-2-0-0`）来做键，不能只按裸组件 ID 做键——如果只按 ID 做键，第二个版本会在你的注册表里悄悄覆盖第一个，平台不会报错（它从不检查你的注册表内部结构），合并逻辑也不会报错（它只校验*地址*，不管你外壳内部怎么记账）。

**你不能做的事：让同一个精确版本同时拥有两种部署形态。**

```yaml
  - id: mdm/customer
    version: 1.0.7
    servedBy: infra/shell-go-core@1.0.0
  - id: mdm/customer
    version: 1.0.7                       # 拒绝：id+version 重复声明
```

这不是 servedBy 专属的限制——一份项目配置永远不能把同一个精确的 `(id, version)` 声明两遍，不管有没有 servedBy（这就是 AGENTS.md §5.1"同一个组件 ID 在依赖里只能出现一次"这条规则字面意义上的延伸：servedBy 只是这一条目上多出来的一个字段，不是一个能让重复条目分岔出去的新维度）。如果你真的需要"大多数调用方共用一个合并实例，但某一个调用方需要一个独立伸缩、代码逻辑上却是同一份东西的实例"，正确答案是把这份代码发布成第二个版本号——哪怕只是形式上的一次版本递增——让两个版本各自拥有自己的部署形态。一个版本号不能同时表示两件事；那正是这个平台"显式优于隐式"这条原则要杜绝的那种隐式、无法从配置本身猜出来的状态。

## 这份指南刻意从不要求你交代的事

这里的任何一条，都不要求你向平台透露外壳用的语言、开了多少进程、并发模型是什么、基础镜像是什么，平台自己的生成逻辑也没有任何一处会根据这些东西分支处理。这不是遗漏——这正是 servedBy 存在的全部意义：平台的职责到"哪个地址该指向哪里"这一层就结束了，再往后的一切，都由你按自己的技术栈去搭。
