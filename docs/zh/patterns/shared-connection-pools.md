# 在外壳里合并数据库连接池

这篇是[怎么声明 servedBy：部署方检查清单](servedby-deployment-checklist.md)
的一个具体延伸：几个组件因为内存原因被合并进同一个壳进程之后，它们的数据库
连接会变成一个独立的、壳本身省下的内存并不会自动帮你解决的资源问题——而且
如果不刻意设计，这件事可能会悄悄地、很危险地出错。这一篇专门针对
PostgreSQL 和 Oracle；用别的引擎请直接跳到[不适用的引擎](#不适用的引擎)。

## 合并进程不等于合并连接池

合并部署的动机通常是省 JVM 内存。但把 8 个 Spring Boot 组件收编进同一个进程
时，**8 个模块各自的连接池也会一起被带进来**，除非你专门处理这件事：

| | 每实例连接数 | 跑 2 副本 |
| --- | --- | --- |
| 8 个模块各自一个池（HikariCP 默认 `maximumPoolSize: 10`） | **80** | **160** |
| 合并成一个共享池（`maximumPoolSize: 20`） | **20** | **40** |

PostgreSQL 的 `max_connections` 默认是 **100**——光一个合并后的实例就快把
默认配置吃满了，两个副本直接爆表。PostgreSQL 的每一条连接都是一个完整的后
端进程，不是一个轻量 handle，所以 80 条和 20 条对数据库服务器造成的负载是
实打实的差距，不是舍入误差。你在壳这边省下的内存，代价落在了数据库那台机
器上。两边都要算，不能只算 `servedBy` 本来要帮你省的那一边。

## 池通常真的合不了——先查这一点，再往下规划

一条 PostgreSQL 连接在它整个生命周期里都绑死在一个数据库和一个认证角色
上。所以哪怕 8 个模块已经编进了同一个 JVM、同一个 ClassLoader、同一个进程，
只要它们指向 8 个不同的数据库，**这 8 个池物理上就没法合并**——一条连到
`people` 库的连接查不了 `department` 库。合并进程在这种情况下一分钱都省
不到。

**前提条件是从"一个组件一个数据库"切换成"一个组件一个 schema，共用同一
个数据库"**——只有这样，外壳才有真正可以合并的东西。

schema 分组是必要条件，不是充分条件，它做的事只是"把不可能变成可能"。真
正省下连接的动作是外壳去主动合并池子——如果每个被收编的模块仍然各自读自
己的 `DATABASE_*` 建自己的池，那还是 8 个池，schema 分组一分钱都没省下
来。**"共用一个 DataSource"必须是外壳的一个明确设计目标**，是外壳除了本
身该做对的那些事之外，额外要担的一件事。

## 两个条件，缺一不可

| 条件 | 怎么满足 |
| --- | --- |
| **同一个数据库** | schema 分组：8 个组件对应 8 个 schema，共用同一个数据库 |
| **同一个认证角色** | 连接也绑角色，8 个不同账号照样是 8 个池 |

第二个条件会撞上一个真实的矛盾：给每个组件配一个最小权限的独立数据库账
号，是平台自己推荐的默认做法（完整推理见
[docs/archive/design/006-基础资源规范.md](../../archive/design/006-基础资源规范.md)）。
在合并部署里，这个矛盾有一个真实可行、而且比挂一个 PgBouncer 之类的外部
连接池更好的解法——因为外壳本身完全控制连接什么时候被借出、什么时候被归
还：

```
借出连接 → BEGIN → SET LOCAL ROLE component_a → 跑该模块的查询 → COMMIT
                   ↑ SET LOCAL 在事务结束时自动还原，
                     连接干干净净地回到池里
```

用一个共享的登录角色连上库，借出连接期间切到该模块自己的角色，事务结束
自动还原。每个模块的权限边界保住了，池还是一个。`search_path` 同理，用
`SET LOCAL search_path`，或者 SQL 里全部使用限定名。

**绝对不能 `SET search_path`（不带 `LOCAL`）之后就把连接还回池子。** 下
一个借用者会原样继承它，于是 A 模块的查询开始读写 B 模块的表——不报错、
不崩溃，只是悄悄地在错误的身份下读写了数据。这是这套写法里最容易踩、事
后也最难发现的一个坑，因为从外面看什么都不像坏了。

## 这个决定有截止日期：必须在建库之前做

**一旦数据库已经按"一个组件一个库"建好、数据也进去了，再想改成一库多
schema，就不是改配置了，是一次数据迁移。** 所以如果你预见到将来有可能走
合并部署——值得留意的信号是"以 JVM 组件为主、正在走向资源受限的私有化交
付"——那么从一开始就采用 schema 分组，代价很小，哪怕你现在还完全没决定
要不要合并。这是这整篇文档里唯一一件"在决定要不要用 servedBy 之前就该考
虑"的事。

## 合并池子之后，你还是要付的代价

| 代价 | 为什么消不掉 |
| --- | --- |
| **共享池没有舱壁** | 一个模块连接泄漏，或者跑了个长事务，整组都会卡在同一个有限的池上等待。分开的池至少能各自独立失败 |
| **外壳要接管 DataSource** | 每个 Spring Boot 模块自己的 `DataSourceAutoConfiguration` 都要被外壳顶掉，这是实打实的集成工作，不是一个配置开关 |
| **迁移也要跟着重新分组** | 每个模块的迁移脚本要落到自己的 schema 里。这跟 AGENTS.zh.md 已经说过的规则是同一条——两个组件共用一个数据库时，迁移状态表的主键必须包含组件标识，否则迁移会互相覆盖——大多数迁移工具默认往 `public` 里写，不管实际数据分了多少个 schema，不配置这一点它们照样会挤在一起 |

第一行跟造壳指南里已经点名的"合并本身的故障隔离代价"是同一笔账——共享
连接池只是这笔代价又多冒出来的一个地方，不是额外新增的一笔。

## 不适用的引擎

PostgreSQL 和 Oracle 的连接在整个生命周期里都绑定在某个具体的数据库/PDB
上，这正是 schema 分组在这里有意义的全部原因。MySQL、MariaDB、SQL
Server、MongoDB 不是这样工作的——同一条连接可以自由跨库查询
（`people.employees JOIN department.nodes` 在 MySQL 里是一条普通查询）。
在这些引擎上，合并连接池完全不需要重新做 schema 分组；一库一组件本来就
可以直接共用一个池。

| 引擎 | 合并池子需不需要重新做 schema 分组 |
| --- | --- |
| PostgreSQL / Oracle | ✅ 需要——连接绑定在某个数据库/PDB 上 |
| MySQL / MariaDB / SQL Server / MongoDB | ❌ 不需要——连接本来就能自由跨库 |

不过认证角色这个维度跟引擎无关：共用一个池就意味着共用一个登录身份，
`SET LOCAL ROLE` 这类技巧（MySQL 自己的权限模型有对应的等价写法）仍然是
保住每个模块权限边界的正确做法。
