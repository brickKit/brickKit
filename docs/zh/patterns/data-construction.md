# 怎么规划种子数据与测试数据

这是**推荐实践**，不是 BrickKit 平台的硬性要求——跟
[基于 BrickKit 的组件该怎么分层测试](testing.md)是同一个级别的东西，也是
那篇的后续：那一篇讲怎么分层测试，这一篇讲那些测试（以及一个人手动探索
整套拼装出来的系统时）真正跑在什么数据上。之所以是推荐实践而不是强制要
求，理由跟那篇一样——BrickKit 的组件自治原则（AGENTS.zh.md §4）把"组件
怎么管理自己的数据"完全留给组件自己决定。下面这套方法论，来自验证过测
试分层的同一次真实生产部署（14 个组件，一条完整业务链路），把它在数据
这一侧的经验也一并验证过，再改写成跟 BrickKit 中性、不绑定任何具体项目
的推荐做法。

## 两条路径，物理隔离，永不共用

| | 种子/演示数据 | 测试现场构造的数据 |
| --- | --- | --- |
| **用途** | 一个人本地探索系统，或者做演示 | 各层自动化测试 |
| **怎么产生** | 固定标识符，认领式幂等——重跑种子脚本不会重建已经存在的东西 | 测试自己在每次运行时现场构造，用时间戳/随机数之类的唯一后缀互相区分 |
| **生命周期** | 持久化，可以整体清空 | 从不清理——数据行堆积没关系，反正下一次运行会拿到自己新的唯一后缀 |
| **能不能共用** | 组件之间可以互相查找、复用彼此的种子数据（见下文） | 绝对不行——任何自动化测试都不应该依赖"这一行是别的测试或别的运行留下来的" |

清空种子数据不该让任何一个测试变红，一次测试运行也不该污染一个人正在手
动探索的数据。这两条路径一旦混在一起，"这东西为什么突然坏了"就不再有单
一的排查方向——可能是有人清空了种子数据，也可能是别的测试并发跑了却没
清理，两种原因需要完全不同的排查路径。让两条路径物理隔离，而不只是逻辑
上约定隔离，能从根上消除这种歧义：测试指向一个跟人工探索**真正物理隔离**
的数据库，而不是共用同一个物理实例、只在逻辑上分了两个命名空间。一条真
实的集成测试往一行基线参考数据（一个默认仓库、一个默认成本中心）上写，
而这行数据恰好也是一个人做演示时会读到的——只要这两条路径共用物理存储，
这个风险就存在，不管当时有没有别的东西在并发跑。

BrickKit 本身就已经给了实现这件事所需要的机制，不需要另外发明：在
`brickkit.yaml` 里声明两个独立的 `resources:` 条目（AGENTS.zh.md §7）——
一个给探索用，一个专门给测试用——并给面向测试的那个配上自己的
`envPrefix`，这样组件的测试环境从一开始读到的就是一组独立的
`DATABASE_*` 变量。这只是平台已有机制的一次普通用法，不是这篇文档在
额外要求什么新东西。

如果你的数据库用到了轻量内嵌/内存替代品复现不了的特性（分区表、
`SET LOCAL ROLE` 这类会话级设置），为了图快换成一次性数据库，恰恰会牺牲
掉集成测试本来要证明的那件事——真实基础设施确实按预期工作。"重建数据慢、
不同测试互相污染"这个问题真正的解法不是换一个数据库，而是让数据本身变
得一次性——也就是上面那条"唯一后缀、从不清理"的模式。

## 同一条覆盖原则，用两种不同方式落地

两条路径共用一条底线：**任何组件都不该只有"一切正常"这一种数据。** 状态
机的每一条分支、每一条失败路径、每一个数据范围维度，都需要有真能触发它
的数据——不管这份数据来自种子脚本还是测试。但两条路径达到这条底线的方
式不一样：

- **种子数据追求"又多又全"。** 它同时还要服务"一个人能不能完整体验这套
  系统"这个目标，所以数量和多样性本身就是目标的一部分，不只是达到测试
  覆盖的手段。
- **测试数据追求"少而精准"。** 每个测试只需要恰好够验证它自己那条断言
  的数据——为了"看起来丰富"而堆量什么都换不来。唯一的例外是针对核心不
  变量的基于属性的测试（余额永远不为负、状态机永远不会跳到非法状态）：
  这类测试也需要数量，但理由不一样——是为了提高随机输入真正命中边界条
  件的概率，跟"体验完整性"完全是两码事。

这两者不是同一份数据的"丰富版"和"精简版"——它们服务不同的目的，本来就
该长得不一样。

## 怎样才算种子数据"够了"——这需要刻意设计，不是单纯堆数量

- **数据范围维度需要真正的多值存在。** 一个权限或归属边界（按部门、按
  owner、按仓库，或者你的业务领域里实际存在的任何范围维度），只有数据
  里真的存在多个值的时候，才能变成一件人能真正点开、验证的事情。种子
  数据如果全都挂在一个全能管理员账号底下，即便范围机制本身实现是对的，
  在实际体验里也等于不存在。
- **数量要真的能触发分页。** 如果一个列表接口做了游标分页，5 行数据永
  远只占一页——分页作为一个契约，在体验里没有真正存在过，除非数据量真
  的多到能撑出第二页。
- **时间要分散开**，不能全部是刚创建出来的，这样"最近 N 天"这类查询、
  趋势图、任何按时间分区的逻辑才有真实场景可以验证。
- **负面/边界数据要真实存在，而不只是想法。** 一条禁用记录、一笔零余
  额、一个逾期未结的账、一次被拒绝的申请——只存在于脑子里的失败路径没
  法点开验证。
- **数据要可被发现。** 数据量一大，就需要有个地方能查到"这个固定标识
  符到底代表什么概念"——否则新组件想复用现有种子数据时无处可查，还可
  能在不知情的情况下撞上已经被占用的标识符。用一份统一维护的清单（组
  件、数据、数量、归属方）来做这件事，比每个组件各自维护一份重复信息
  更划算。

## 组件之间数据重复是可以接受的——甚至是件好事

这些数据全是假的，不存在污染真实数据的顾虑。如果两个组件各自独立造了概
念上类似的东西（比如两个组件各自造了一个"示例客户"），费力去重不值得
付出这个协调成本——这里的重复成本几乎为零，而"看起来数据量很完整"本身
就是要达成的目标之一。当一个组件需要跟另一个组件类似的数据时，直接复用
现成的，比商量"这份数据该归谁维护"便宜得多。

## 归属原则：每个组件自己造自己的种子数据，先造依赖

把种子数据集中到拼装层，一旦有人只把某个组件连同它的依赖树单独跑起来
（这是 BrickKit 支持的、很常见的用法）就会立刻失效——一份集中脚本只有
在所有组件都已经一起跑起来的前提下才管用。所以：

- **每个组件自己拥有、自己维护自己的种子数据。**
- **造自己那部分之前，先把自己声明的每一个依赖的种子数据造好**——这里
  强依赖和弱依赖一视同仁，原因是这个场景本身的特殊性：开发或演示环境
  里，声明过的依赖通常本来就都在跑，不存在"只装了部分依赖"这种要去兼
  顾的场景；而一旦声明了某个依赖，就说明这个组件真的用得到它（强弱依
  赖的区分，服务的是真实部署时"这个可选模块要不要买"这个问题——对应
  AGENTS.zh.md 里弱依赖的语义——不是开发时种子数据该按什么顺序造这个
  问题）。如果某个声明的依赖在当前环境里确实连不上，跳过它、继续造自
  己那部分——依赖缺失应该让种子流程降级，而不是让它直接失败退出。
- **用组件自己的幂等机制来做交接，不要另外发明协议。** 下游组件如果需
  要一个依赖种子数据产生的 id，直接按一个双方约定好的固定标识符去查询
  那个依赖，拿到对应的行——不需要为了"一个脚本把 id 传给另一个脚本"这
  件事发明任何格式。

## 一旦被别人引用，固定的种子标识符就是一份轻量契约

一旦别的组件已经查过某个固定的种子标识符，这个标识符就不能再随便删掉
或者改指向别的含义——只能新增，不能修改已经被引用过的那个。把它当成已
发布 API 契约里的一个字段来对待：新增是可以的，破坏性变更需要跟真正的
契约变更同样的协调成本。

## 只增不减的数据要用整体重置，不能按行删除

如果一张表天生只增不减（一本流水账、一个已锁定的会计期间、一份审计日
志），它就不该有按行删除式的种子清理路径——只能整体重置。按行删除没法
把一张只增不减的表恢复到真正干净的状态（序列不会因为删了几行就回退），
硬这么做等于悄悄违反了这张表自己的设计。正确的工具是完整的迁移重置
（把全部迁移倒回去再重新跑一遍）——这样做的副作用是，迁移脚本自己灌进
去的基线数据也会跟着回来，因为它是被重建的 schema 的一部分，不是种子脚
本的职责。**经验法则：只增不减的表只有重置路径，没有按行删除的清理路
径**；可以安全按行删除的表两条路径都可以有，日常优先用更轻量、不动其
它数据的按行清理。

## 唯一一条不能破的底线：种子机制绝不能泄漏进生产环境

任何用来生成种子数据的机制，都绝不能有能力在真实客户的部署里种下一个
真实凭据。一旦一个测试账号或者一个共享密码，混进了某个"每次部署都会跑
一遍"的东西里（比如打进镜像的数据库初始化脚本），就等于在这个组件的每
一次安装里都永久埋了一道后门——跟"生产环境的认证应用不该留一个直接密
码登录的授权模式"是同一类风险。这条线没有例外：

- **每次部署都真正需要的通用基线数据**（一个默认仓库、一套基础会计科
  目、一组标准计量单位）应该走迁移，不是种子脚本——它不是测试数据，它
  是产品本身的一部分。BrickKit 已经给这件事准备好了归宿：组件的
  `migration.command`（AGENTS.zh.md §5.5）在主服务启动之前、每一次部
  署都会跑一遍，这正是这类数据需要的"到处都跑、不是可选项"的性质。
- **真实部署里"第一个管理员怎么进来"是一个配置驱动的引导问题，不是种
  子数据问题。** 第一个真实操作者的身份写进一个配置项，组件在启动时读
  到它、幂等地给自己授予管理员角色——没有人手写 SQL，也没有任何账号被
  硬编码在任何地方。这解决的是跟本地开发/演示需要的"拥有全部权限的超
  级测试角色"完全不同的问题，这两套机制不该互相替代。

## 测试数据除了唯一后缀这条规则之外，还需要什么

- **一个消费者/事件测试需要自己独立的私有 subject 或 topic**——测试自
  己发一个事件去触发被测代码时，如果跟同一台机器上可能正在跑的别的东
  西共用 subject，会有真实消费者跟测试抢消息的风险。
- **验证幂等消费逻辑（按唯一键去重）的测试，必须每次运行用不同的标识
  符，不能用固定字符串**——用固定字符串的话，第二次运行在去重逻辑看来
  跟第一次的合法重放毫无区别，会被悄悄吞掉，根本没有真正走到被测代码
  路径。
- **测试数据不需要种子数据那些专属维度**——分页量、时间分散、可发现
  性。一个测试只需要恰好匹配它自己那条断言的数据；为了"体验完整性"这
  种跟这一个测试毫无关系的目标去多造数据，纯属浪费。
