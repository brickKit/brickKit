# BrickKit vs 现有方案

这些工具大多解决的是**相邻但不同**的问题——下面每张表都尽量只比较真正重叠的那部分，而不是用 BrickKit 有的东西去衬托别的工具"没有"，因为很多时候它们本来就不打算做那件事。想知道 BrickKit 自己拒绝做什么、为什么，看 [README 的"设计哲学"一节](../../README.zh.md)或[架构文档](architecture/overview.md)。

## vs Docker Compose

| 维度 | Docker Compose | BrickKit |
| --- | --- | --- |
| 解决的问题 | 怎么用一份 YAML 编排一组容器 | 怎么管理一批**独立发布、独立版本**的业务组件的完整生命周期 |
| 组件来源 | 镜像仓库（不带元数据规范） | 组件市场（Manifest + API 契约 + 签名，可发现、可校验） |
| 依赖顺序 | 有 `depends_on` + `condition: service_healthy`，但要你手写、只管当前这份文件里的服务 | 从组件的 `dependencies` 递归展开整棵依赖树，区分强弱依赖，自动算出 `depends_on`（生成的 compose 文件里其实也是 `depends_on`，只是不用你手写、也不止一层） |
| 地址注入 | 手动写环境变量，自己保证前后一致 | 自动生成并注入版本化地址，变量名从组件 ID 推导，不会手滑写错 |
| 数据库迁移 | 无原生概念，得自己加一个跑一次性脚本的 service | 组件声明 `migration.command`，CLI 用一次性 service 跑，失败阻断主服务 |
| 多版本共存 | 得自己想办法给 service 改名 | 天然支持——服务名本身就带精确版本号，两个版本是两个不冲突的名字 |
| K8s 支持 | 没有；需要额外的转换工具（如 Kompose）且效果有限 | 改一个字段（`deploy.target`），同一份声明生成 K8s 清单 |

**什么时候用 Compose：** 快速原型、纯本地开发、服务之间没有"谁依赖谁的哪个版本"这种问题。
**什么时候用 BrickKit：** 组件会被独立发布和升级、需要多组件依赖解析、需要同一份声明覆盖本地和生产。

## vs Helm

| 维度 | Helm | BrickKit |
| --- | --- | --- |
| 解决的问题 | 怎么把 K8s 清单模板化、参数化 | 怎么让组件代码完全不用知道自己跑在 Docker 还是 K8s 上 |
| 目标平台 | 只面向 Kubernetes | Docker 和 Kubernetes 都能生成，同一份声明 |
| 组件来源 | Chart 仓库（可以是 OCI 或传统 index） | 组件市场（含 Manifest、API 契约、签名） |
| 多环境配置 | 一份 Chart + 多份 `values-<env>.yaml`，差异要自己维护 | 一份声明，改 `deploy.target` 这一个字段就切换目标平台 |
| 依赖解析 | Chart 依赖是"把子 Chart 一起装进来"，比较粗粒度 | 组件级依赖，区分强弱依赖，自动拓扑排序 |
| 服务命名 | K8s Service 本身就有 DNS，但没有内置的"版本进服务名"约定——多版本共存要 Chart 作者自己设计命名规则 | 服务名 = 组件 ID + 精确版本号，是平台的固定规则，不用每个 Chart 各自发明一套 |
| 本地调试 | 典型做法是 `kubectl port-forward` 或额外工具（如 Telepresence） | `local: true` + `extra_hosts`（仅 Docker 目标；K8s 下这条路径本来就不存在断点调试的需要，见部署选型指南） |

**什么时候用 Helm：** 已经在用 K8s、需要模板化部署复杂应用、Chart 生态本身就有你要的东西。
**什么时候用 BrickKit：** 组件需要独立演进、需要本地和生产用同一份声明、需要多版本共存不是靠手工命名约定撑着。

## vs Kustomize

| 维度 | Kustomize | BrickKit |
| --- | --- | --- |
| 解决的问题 | 怎么用 base + overlay 管理多环境的清单差异 | 怎么让每个环境都是一份完整、自包含、所见即所得的配置 |
| 配置模型 | 基础层 + 覆盖层，运行时合并 | 每个环境一份完整的 `brickkit.yaml`，没有继承链 |
| 心智负担 | 要理解继承关系和字段合并规则，`git diff` 经常看不出实际生效的值 | 打开一个文件就是全貌，`git diff` 直接对应实际变化 |
| 组件来源 | 没有这个概念，纯粹是清单层的工具 | 组件市场（含 Manifest、API 契约、签名） |
| 依赖解析 | 没有，只管清单怎么拼 | 递归展开依赖树，强弱依赖，拓扑排序 |

**什么时候用 Kustomize：** 已经在用 K8s、清单本身差异不大、团队已经熟悉 overlay 心智模型。
**什么时候用 BrickKit：** 觉得 overlay 的继承链不好推理、希望每个环境的配置能直接读懂。

## vs Tilt / Skaffold

| 维度 | Tilt / Skaffold | BrickKit |
| --- | --- | --- |
| 解决的问题 | 怎么加快本地开发循环（改代码 → 自动 build → 自动部署） | 怎么管理业务组件从开发到生产的完整生命周期 |
| 组件来源 | 本地源码，当前项目自己构建 | 组件市场，独立发布、独立版本 |
| 依赖顺序 | 可以手写资源依赖（如 Tilt 的 `resource_deps`），但要自己维护、不跨项目 | 从 Manifest 自动递归展开，不需要手写 |
| 使用场景 | 主要面向本地开发内循环 | 本地和生产用同一份声明 |
| 版本管理 | 没有"组件版本"这个概念，构建产物按开发迭代打标签 | 精确版本 + 多版本共存是平台原生能力 |

**什么时候用 Tilt/Skaffold：** 需要快速的本地开发内循环，改一行代码就要看到效果。
**什么时候用 BrickKit：** 组件需要独立演进、独立发布，本地和生产要能对得上号。

## vs Backstage（开发者门户 / IDP）

| 维度 | Backstage | BrickKit |
| --- | --- | --- |
| 解决的问题 | 怎么给开发者一个统一入口（服务目录、文档、插件生态） | 怎么让组件独立演进、依赖自动解析、部署文件自动生成 |
| 组件来源 | 服务目录（`catalog-info.yaml`，描述性元数据） | 组件市场（Manifest + API 契约 + 签名，可执行、可安装） |
| 依赖关系 | 目录里可以声明 `dependsOn` 用于展示和可视化，但不会拿它去驱动实际的部署顺序或地址注入 | 依赖关系直接驱动拓扑排序、启停级联和环境变量注入——不只是展示 |
| 部署 | 自己不部署，要接 ArgoCD / Helm 等 CD 工具 | 原生生成 Docker Compose / K8s 清单并调用底层引擎 |
| 部署复杂度 | 重——Backstage 本身就是一套要独立运维的应用（通常是 Node.js + Postgres） | 轻——CLI 是单二进制、用完即走，没有自己的后台服务 |

**什么时候用 Backstage：** 需要一个团队级的服务目录、开发者门户、插件生态，部署交给已有的 CD 体系。
**什么时候用 BrickKit：** 需要的是依赖解析和部署生成本身在跑，而不是一个展示层。两者其实不冲突——Backstage 的 `catalog-info.yaml` 完全可以指向一个 BrickKit 项目。

## vs monorepo（Turborepo / Nx / Lerna）

| 维度 | monorepo 工具 | BrickKit |
| --- | --- | --- |
| 解决的问题 | 怎么在一个仓库里管理多个模块、加速构建缓存 | 怎么让组件独立发布、独立版本、独立部署 |
| 组件来源 | 同一仓库下的不同目录 | 独立的 Git 仓库 |
| 版本管理 | 支持全局版本或独立版本（如 Lerna 的 independent 模式），但历史都在同一个仓库里 | 每个组件独立版本、独立仓库、独立的 Git 历史 |
| 依赖解析 | **构建时**依赖——代码级的 import 图，缓存和增量构建都基于它 | **运行时**依赖——API 级的契约，通过环境变量注入地址，不是代码 import |
| 发布权限 | 同一仓库通常共享同一套权限模型 | 每个组件独立仓库、独立可见性、独立签名 |

**什么时候用 monorepo：** 多个模块需要频繁协同修改、共享代码、经常一起发布。
**什么时候用 BrickKit：** 组件之间只通过 API 通信、需要独立的发布节奏和权限边界、不想因为改了 A 就被迫碰 B 的构建。
