# 检验 AI 找不找得到路

前面几页讲怎样给 AI 写项目的 `AGENTS.md`、路由和组件文档。这一页讲怎样知道写成了没有：一个对项目一无所知的 AI，是不是真的找到了对的文件、
照着它答对了。

自己读一遍看不出来。你已经了解这个项目，每个缺口都会被你脑子里的东西悄悄补上——而助手掉进去的恰恰是这些缺口。唯一的检验办法，是把文档交给一个
什么都不知道的助手，问它真实的请求者会问的话，看它往哪里走。

## 什么时候做

改了助手最先读、或者靠它找路的东西之后：项目的 `AGENTS.md`（尤其是"去哪找"那张表）、技能、组件的 `BRICKKIT.md` 或 `AGENTS.md`、`docs/` 的
布局。小改动问几道题就够；新项目或重新组织过的 `docs/` 值得一整套。

## 考生：只加载项目的新会话

考生是一个在项目目录里新开的会话，只加载项目自己提供的东西：它的 `AGENTS.md` 与 `CLAUDE.md`、`.claude/skills/`、缓存的 `.brickkit/manifests/`。
不带你自己的用户级设置，没有记忆，没有之前的对话——正是队友的助手第一次打开这个项目时的处境。

**子代理不算。** 从你的会话里开出来的子代理，带着你会话里的指令和上下文：你知道的它都知道，包括项目已经改掉的旧指令。有个项目测试时，一个当考生的子代理
自己报出它拿到了父会话里旧版的项目指令——它的答案量的是父会话的知识，不是文档。

怎样开出这样的会话看用什么工具。以 Claude Code 为例：在项目目录里运行 `claude -p "<题目>"`，让 `CLAUDE_CONFIG_DIR` 指向一个只放登录凭据的目录，
用户级的 `CLAUDE.md`、技能和记忆就都不会加载；再在它的权限里禁止读你的用户目录。

## 题目

- **用请求者的原话。** 问用户真的会敲出来的那句话——"退款之后订单页显示的还是原来的总额"——而不是已经点名了文件的问题（"`erp/order` 的
  `BRICKKIT.md` 对退款怎么说"）。要检验的正是找文件这一步。
- **参考要点在跑之前写好。** 每道题：应该找到哪个文件、哪一节，答对的答案包含哪几点。跑完再写，就会不自觉地往考生说的方向偏。
- **覆盖文档负责引路的几类事。** 某个东西在哪、怎么配、一个改动请求（归哪个组件、升哪一位版本号）、一次要排查的故障。
- **题目留在项目里**（比如 `dev/routing-tests/`），下次改动之后用同一套再跑，结果才能比。

## 跑与评分

1. 每道题**至少跑两次**：每次的回答会有出入，成功一次说明不了多少。
2. **至少加一档较弱的模型**。强模型会靠搜代码补上缺口，弱一些的会停在缺口上——要看的就是这个。
3. 记下考生**读了什么**，不只是答了什么：把整个源码树读一遍才答对，照样是路由失败。
4. **在另一个新会话里评分**，不在考生的会话里：把题目、参考要点和考生的答案交给评分的会话，让它逐条打 0 或 1。

## 能查出什么

一个项目实际跑出来的：入口文件超过助手一次读的长度，要紧的部分被截掉了；`AGENTS.md` 末尾一张过时的组件表把考生带到了错的组件（BrickKit 因此把组件表
挪进了单独的 `COMPONENTS.md`）；技能和项目自己的规则在该升哪一位版本号上说法不一，考生停下来问。每一条都是改文档；同一套题再跑一遍，确认改好了。

## BrickKit 在这里做什么、不做什么

BrickKit 没有为此提供命令。哪些题目要紧是项目自己的知识，跑模型、评分也不在一个部署 CLI 该做的范围里。它查的是机械的那一半——`brickkit lint`
报缺失的文件与小节、坏链接、代码地图里不存在的路径、哪里都走不到的文件。这一页的检验管 lint 管不到的：一个从零开始的助手，找不找得到、读不读得懂。
