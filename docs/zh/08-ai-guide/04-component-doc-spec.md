# 组件文档（AI 视角）

每个组件的 `BRICKKIT.md` 是写给使用者（人和 AI）的说明。格式与写法见 [组件文档 BRICKKIT.md](../03-component-guide/08-component-doc-spec.md)；这一篇讲 AI 怎么用它、怎么写它。

## 怎么读

**位置。** 项目根 `BRICKKIT.md` 的组件表里有每个组件文档的路径。一般是 `.brickkit/manifests/<scope>/<name>/<版本>/BRICKKIT.md`；
组件源码在本地源里、正好是这个版本时，是那个目录里的 `BRICKKIT.md`。

**五个区块各给你什么：**

| 区块 | 拿来做什么 |
| --- | --- |
| 组件定位 | 判断这个组件是不是你要找的 |
| 依赖说明 | 知道它缺了弱依赖时怎么表现，调用它时要不要考虑降级 |
| 配置指南 | 写 `config/<组件>.yaml` 时每一项该填什么——尤其默认值说不清的 |
| 契约索引 | 找到接口文件，照它写调用代码 |
| 外壳声明 | 它是不是外壳、编进了谁 |

`BRICKKIT.md` 与 `component.yaml` 不一致时，以 `component.yaml` 为准（CLI 只认它）；把不一致告诉用户。

## 没有 `BRICKKIT.md` 时

项目地图里文档路径是"—"，说明组件没带文档。退而求其次：

1. `component.yaml`：`metadata.description` 一句话定位；`dependencies`；`configSchema` 的 `description`、`default`、`required`。
2. 契约文件（`artifacts`）：接口。
3. 仍然不够时，告诉用户这个组件缺文档，而不是去读它的源码猜——猜出来的东西不是承诺。

## 为组件写 `BRICKKIT.md`

信息来源按可靠程度：

1. `component.yaml`：定位、依赖、配置项、是不是外壳——这些是事实，直接转述。
2. 契约文件：接口列表。
3. 组件代码：弱依赖缺失时代码里实际怎么做；某个配置项在代码里实际怎么用。
4. 用户：业务上"为什么"的部分——这个组件解决什么问题、某个配置怎么选。

写的时候：

- **不重复 `component.yaml` 已经写明的东西**（类型、默认值本身），写它说不出来的：取值怎么选、改了会怎样、缺了依赖会怎样。
- **与代码一起改。** 改了行为不改文档，下一个读它的 AI 就会照着错的说明写代码。
- **写给第一次见到这个组件的人。** 不要写内部实现细节——它们不是承诺。
