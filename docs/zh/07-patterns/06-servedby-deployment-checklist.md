# 怎么声明 servedBy：部署方检查清单

> 前置阅读：先看[架构总览](../06-architecture/00-overview.md)——本文假定你已经理解版本化服务名与环境变量注入这两个机制。还没决定整个项目该长什么样——哪些组件独立部署、哪些合并、`docker` 还是 `k8s`？先看[怎么选部署形态](05-deployment-selection-guide.md)；这一篇讲的是合并已经上了台面之后、按单个组件粒度怎么决定。

这篇跟[外壳该怎么造才合格](07-shell-implementers-guide.md)是两篇不同的文档。那一篇写给
**造壳的人**——负责建那个用来收编别的组件工作负载的容器。这一篇写给
**在自己 `brickkit.yaml` 里声明 `servedBy` 的人**——决定把某个组件路由进已有
的壳里，而不是让它自己起一个容器。如果这两件事都是你一个人做，两篇都该看；
分开写是因为在真实团队里这往往是两个人，各自需要知道的东西也不一样。

## 什么时候该用 servedBy，什么时候不该

`servedBy` 解决的是一个内存底线问题，不是"容器越少越好"这种泛泛的诉求。每个
跑着的进程都有一个跟负载无关的底线成本，这个底线几乎完全由语言运行时决定
（AGENTS.zh.md §6）：Go/Rust 是 8–20MB，Python/Node 是 40–90MB，JVM 是
200–450MB。20 个空闲的 Spring Boot 组件光底线就是 4–9G，一个单位的活都还没
干——这在资源受限的私有化交付里是真实约束。换成 20 个空闲的 Go 组件，加起来
连半个 G 都不到，下面这些代价通常就不值得付了。

在考虑 `servedBy` 之前，先量一遍真实的占用——用 `docker stats` 看实际在跑
的东西，别照着谁发的表拍数字——然后大致按下面这个顺序看便宜的选项：

```mermaid
graph LR
    A["1. 换更轻的运行时<br/>先试这个"] --> B["2. 按需启停<br/>enabled: false"] --> C["3. servedBy<br/>最后手段"]
```

（scale-to-zero 和"内存超卖"根本不在这个阶梯上——它们下面是直接被否掉的，不是被跳过的步骤。）

| 选项 | 结论 |
| --- | --- |
| **换个更轻的运行时**（JVM 组件编成 GraalVM 原生镜像、调小堆） | **先试这条。** 内存底线从 200–450MB 掉到几十 MB，部署形态一点没变——还是一个组件一个容器一个进程，签名、健康检查、迁移、独立扩缩容全都照常工作。这是组件作者自己的事，跟 `servedBy` 和这份清单都没关系。如果动机是"JVM 太贵"，这条的性价比比合并高出一个数量级。 |
| **按需启用**（这次部署用不到的组件直接 `enabled: false`） | 一个 50 组件的项目本地开发可能只跑 4 个容器——先确认拉高内存数字的那些组件在这次部署里是不是真的需要跑，再假设它们都得跑。 |
| **Scale-to-zero**（KEDA、Knative 把副本缩到 0） | **在这个平台上走不通。** 组件之间是直连 DNS 调用——调用链路上没有任何东西能把一个缩到 0 的组件重新唤醒，请求会直接失败。要让它可行得在调用路径上插一个 activator 或代理，这正好是平台故意不做的 API 网关/服务网格那一类东西（AGENTS.zh.md §4.1）——而且一旦调用方和它的 `*_ENDPOINT` 之间插了东西，`servedBy` 能安全建立起来所依赖的那条前提（调用方永远不需要知道对面是什么）也就不成立了。 |
| **内存超卖**（`requests` 报低、`limits` 放大） | **不只是没用，是真的有害。** 内存不可压缩：`requests` 远小于 `limits` 会产生 Burstable QoS，节点一紧张，驱逐顺序按"实际用量超出自己 requests 多少"排序——这会让你用得最多、最重要的那个组件排在最先被杀的位置。AGENTS.zh.md §6 早就给出了相反的建议：内存 `requests == limits`（Guaranteed QoS，最后才被驱逐），CPU 只设 `requests`，不设上限。 |

只有上面这些便宜的选项都用不上，合并才有意义。

而且合并是有真实代价的，这个代价由外壳的作者承担，平台不替你承担：合并进同
一个壳的组件共享故障域（一个 panic 可能把其它组件也拖下水，除非壳造得足够
小心——见造壳指南的九条性质），共享伸缩单元（没法单独调整壳里某一个组件的
副本数），也失去了自己独立的迁移容器（迁移顺序要靠壳的启动代码手工编排）。
当内存经济账算下来，对**这一组具体的组件**来说值得为此付出代价，并且你已经
有（或者愿意造并验证）一个满足造壳指南要求的壳——这时候 `servedBy` 才是对
的选择。（如果要合并的这些组件连的是 PostgreSQL 或 Oracle，在真正下决定之
前还有一个内存之外的资源问题值得先看一下，见[在外壳里合并数据库连接池](08-shared-connection-pools.md)。）
把它当成整理项目的默认手段是错的，平台也没有往这个方向引导你：不写
`servedBy`，你得到的就是每个组件各起一个容器的普通路径。

## 写 `servedBy:` 之前，四件事必须已经成立

1. **壳本身是配置里一条正常的 `components:` 条目**，有自己的 `id`、
   `version`、镜像、`deployment.port`、`healthCheck`——`servedBy` 指向的是
   一个组件，不是用别的方式配出来的某个容器。壳还不是组件的话，先把它加上。
2. **壳真的已经拿[九条性质](07-shell-implementers-guide.md#合并进程必须满足的九条性质)
   核对过了**。平台没法验证任何一条——它只负责在这九条都成立的前提下把地址
   接对。拿一个悄悄违反了第 4 条（共享连接池上的身份没清干净）或第 8 条
   （重复注册导致 panic）的壳去声明 `servedBy`，不会在 `brickkit up` 阶段
   报错，而是留到生产环境里以一种完全看不出跟 `servedBy` 有关的方式炸掉。
3. **这个组件要用哪个端口已经定好了**，并且确认过不会跟壳自己的端口、或者
   已经路由进这同一个壳的其它成员撞车。平台会在生成阶段替你查这一条（见下
   文），查不过就直接拒绝生成——但提前定好能让你少走一次"跑了才发现不行"
   的弯路。
4. **壳在这次部署里真的会跑起来**——不是 `enabled: false`，也不是
   `local: true`。壳没在跑，这个组件的代码就没有任何地方可以执行，平台把
   这个当错误处理，不是警告。

## 字段怎么写、哪些写法会被直接拒绝

```yaml
components:
  - id: mdm/customer
    version: 2.0.0
    servedBy: infra/shell-go-core@1.0.0   # <组件ID>@<精确版本>
    deployment: { port: 8081 }
```

值必须是精确版本——跟平台上所有版本引用一样的 `major.minor.patch` 限制
（AGENTS.zh.md §9.2）；写 `^1.0.0` 或者光写 `infra/shell-go-core` 不带版本，
在解析阶段、根本不需要看依赖图之前就会被拒绝。还有四种写法也是在同一个阶段
就被拒绝，同样不需要依赖图：

- **指向自己。** `mdm/customer@2.0.0` 声明 `servedBy: mdm/customer@2.0.0`
  会被当场抓住。
- **链式嵌套。** 如果你指向的这个壳自己也声明了 `servedBy`（它自己也被收编
  进了另一个壳），平台会拒绝——壳不能嵌套在另一个壳里面。
- **跟 `local: true` 同时声明。** 这两个字段表达的是互相矛盾的意图：
  `local: true` 是"这段代码跑在我自己机器上调试"，`servedBy` 是"这段代码已
  经编进了那个外壳镜像"。平台拒绝在同一个组件条目上同时写这两个字段——反过
  来也一样：如果某个组件已经被别的条目 `servedBy` 指向，平台也拒绝把它标成
  `local: true`，理由相同：壳得能在集群或容器网络里被访问到，开发者自己的
  机器做不到这件事。

还有两条检查需要完整的依赖图，所以要到生成阶段（`brickkit up`）才会报出来，
而不是解析阶段：

- **指向的壳不存在**——当前项目的 `components:` 列表里没有这一条，通常是
  组件 ID 或版本号写错了。
- **指向的壳存在但没在跑**——最常见的原因是被 `enabled: false` 关掉了。这
  个组件的代码在这种状态下真的没有任何地方可以执行，直到这个问题被修好。

## 哪些字段要挪到壳自己那条条目上

`servedBy` 组件自己条目上的 `expose`、`exposePort`、`hostname`、
`replicas`、`resources`、`serviceAccountName`、`labels` 全部不生效——平台
会警告，而不是悄悄忽略或者直接报错，因为这些字段描述的都是"我自己这个
容器/Pod该怎么部署"，而一个 `servedBy` 组件根本没有属于自己的容器。真要
控制合并后的部署怎么暴露、怎么伸缩、给多少配额、打什么标签，这些字段要
写在**壳自己那条条目**上——只有它才真的有容器。这一点第一次踩很容易：把
一个原本独立部署的组件迁进壳里，忘了它原来那段 `resources:` 已经失效，
壳就悄悄地在你以为继承过来的配额之外跑起来了。

`labels` 曾经是这份名单里唯一的例外——真的会跟每个成员合并，规则跟下文
`*_ENDPOINT` 变量一样。直到真实的多组件迁移证明这条规则行不通：语义上
本该因组件而异的标签值（最常见的例子是 `prometheus.io/port`，值就是各自
的端口号）几乎在每一次真实合并里都会触发"同名不同值"冲突，而这根本不是
真正的失误。平台没有为这一个键单独开例外（或者开始维护一份"哪些键天生
就该因组件而异"的名单），因为那等于让平台去解释具体某个 label 键的含义
——这正是 `labels` 作为纯透传口本该避免的事。所以它被挪进了这一类"什么
都不会发生"的字段里：成员自己的 `labels` 会被忽略（并给出警告），只有壳
自己条目上的 `labels` 才会落到合并后的容器上。

## 声明之后，哪些事平台会自动帮你做好

下面这些事，除了 `servedBy` 这一个字段本身，不需要任何额外配置——它们是平
台自己合同的一部分，而且专门被加固过（以前一个 servedBy 成员的流量对下面
这两套机制来说都是不可见的），为的就是让 `servedBy` 能跟项目配置的其它部
分正常组合，而不是一个悄悄绕开它们的特例：

- **依赖这个组件的每一个调用方拿到的 `*_ENDPOINT`**，都会解析到壳的地址，
  用的是这个组件自己声明的端口——调用方的依赖声明、以及它算出来的地址，
  完全不需要因为依赖跑在哪儿而改变。
- **NetworkPolicy**（如果开了 `deploy.networkPolicy.enabled`）：壳生成的
  ingress 规则会自动包含每一个被收编成员自己的调用方，用的是那个成员自己
  的端口——不需要因为壳现在还多收编了一个组件，就单独给它写一条 `allowFrom`。
- **Egress**（如果开了 `deploy.networkPolicy.egress.enabled`）：调用方对
  一个 `servedBy` 依赖的出站规则，会自动指向壳，而不是一个根本没被生成出
  来的容器。
- **Docker 的 `depends_on`**：一个依赖了 `servedBy` 组件的 Compose 服务，
  会自动改成依赖壳的服务和它的就绪条件。
- **资源绑定校验**：一个成员自己 `component.yaml` 里 `dependencies.resources`
  声明的资源依赖，只要壳自己的 componentId 已经绑了同一个 `kind`+`engine`
  的资源，就算满足——不需要在这份资源的 `bindings` 里也为成员自己重复写
  一份（写了也不会产生任何真实作用）来满足 `brickkit up` 的校验。真正的
  连接环境变量只会落进壳的容器，不管绑定写在哪个 componentId 名下都一样。
- **`local: true` 组件对这个成员的出站连通性**：如果一个 `local: true`
  调试模式下的组件依赖了这个 `servedBy` 成员，它在
  `local-debug.<服务名>.env` 里的 `*_ENDPOINT` 变量会解析成一个真正宿主机
  可达的 `localhost:<端口>`——CLI 把这条映射开在**壳自己**的 compose
  service 上（成员没有自己的），用的是成员自己声明的端口，正是壳本来就
  必须监听的那个端口（`checkPortConflicts` 在生成阶段就校验过这一点；
  跟上面 K8s 寻址依赖的是同一个假设，这里只是复用，不是新引入的）。

## 哪些事平台不会自动帮你做

**迁移。** 平台不会为 `servedBy` 组件生成任何迁移容器或 Job——它会在生成
阶段发出一条警告（点名被跳过的那条迁移命令），就是为了不让这件事到运行时
才变成一个意外。真正跑这段迁移、并且相对于壳里其它成员自己的迁移排在正确
的顺序上，是壳自己启动代码的职责（造壳指南里的第 7 条性质）——完全不是部
署这一侧能配出来的东西。如果你正在把一个原本独立部署的组件迁进壳里，先确
认壳的启动流程真的已经扩展到覆盖它了，再在生产环境里依赖这一点。

**任何假设"一个组件对应一个容器"的东西。** 有些可观测性或调试工具默认按
这个假设写死——它们需要被明确告知：对于一个 `servedBy` 组件，日志、指标、
进容器排查都要去壳里面找。平台在这一点上没有任何机制可以帮你打圆场，因为
真的没有一个独立的容器可以指过去。

**外部工具/脚本直接连组件端口，需要自己算地址。** 本地开发脚本（比如种子
数据脚本）、运维工具如果要绕开组件自己的业务 API、直接打它的 gRPC/HTTP
端口，平台不会为此提供任何专门支持——但也不需要，公式跟独立部署时完全
一样：`http://<版本化服务名>:<该组件自己声明的端口>`，详见
[架构总览"外部工具直接连组件端口"一节](../06-architecture/00-overview.md#外部工具直接连组件端口)。
容易踩的坑是照搬迁移前的写法——按容器名前缀找容器（`servedBy` 组件没有
自己的容器），或者假设端口发布到了宿主机（`expose: true` 对 `servedBy`
成员完全不生效）。

## 平台会替你拦住的冲突

下面这三种情况都会让 `brickkit up` 直接失败在生成阶段，而不是生成出一个悄
悄跑错的东西：

- **端口冲突。** 壳自己和所有路由进它的成员共用同一个端口空间。两个人（壳
  自己和某个成员，或者两个成员之间）声明了同一个端口，生成会失败，并且报
  出两边各是谁。
- **端点变量冲突。** 两个被收编进同一个壳的成员，各自依赖同一个组件 ID 的
  不同精确版本。合并它们的环境意味着同一个变量名（`*_ENDPOINT`，由组件 ID
  推导、本身不带版本）要同时代表两个不同的地址——这是真实的冲突，平台没法
  悄悄替你选一个，所以直接拒绝生成。

成员的 `deployment.labels` 以前也走同一套合并+冲突检测——现在不会了。
见上文"哪些字段要挪到壳自己那条条目上"：成员自己的 `labels` 会被忽略
（并给出警告），完全不参与合并，也就不存在"冲突"这回事了。

## 多版本与混合部署形态

把一个组件迁进壳里几乎从来不是一次性、瞬间完成的切换——有些调用方还留在
旧的、独立部署的版本上，另一些已经切到了新的、跑在壳里的版本；甚至两个版
本可能会在一段时间里共用同一个壳。这些都不是 `servedBy` 专属的机制——全都
是平台已有的精确版本锁定规则，应用在多了一个字段的普通组件条目上而已。
造壳指南已经把具体场景、以及唯一一个真实存在的语言级坑（Go 的构建系统在
不采用语义化导入版本的前提下，没法把同一个模块路径的两个版本静态链接进同
一个二进制里，而大多数组件都没有采用这个约定）讲透了：
[多版本、混合部署形态](07-shell-implementers-guide.md#多版本共存部署形态还能不一样)。

## 一个完整的例子

```yaml
components:
  - id: infra/shell-go-core
    version: 1.0.0
    image: brickenterprise/be-shell-go:1.0.0
    deployment: { port: 9000 }
    healthCheck: { path: /healthz }
    resources:
      requests: { cpu: "500m", memory: "512Mi" }

  - id: mdm/customer
    version: 2.0.0
    servedBy: infra/shell-go-core@1.0.0
    deployment: { port: 8081 }        # 在这个壳 + 它的成员之间必须唯一

  - id: mdm/orders
    version: 1.3.0
    servedBy: infra/shell-go-core@1.0.0
    deployment: { port: 8082 }        # 在这个壳 + 它的成员之间必须唯一
```

`mdm/customer` 和 `mdm/orders` 各自的调用方都能拿到正确的 `*_ENDPOINT`，
两者都路由到 `infra/shell-go-core` 的地址，也都不会生成自己的容器、迁移
Job 或 NetworkPolicy 规则——这些都是壳的，只算一次、大家共用。真正决定这
次合并省了多少资源的那段 `resources`，写在壳的条目上，不写在任何一个被收
编组件上。
