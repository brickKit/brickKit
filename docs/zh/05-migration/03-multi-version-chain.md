# 多版本的迁移顺序

## 问题

同一个组件的两个版本同时运行时（见 [多版本共存](../03-component-guide/09-multi-version-coexistence.md)），它们通常连同一个库。
两个版本的迁移如果同时跑，就在同一批表上并发改结构——轻则一方报错，重则把 schema 改坏。

## 按版本串起来

平台把同一个组件的各个版本的迁移按**版本号**串成一条链：低版本的迁移先跑完，高版本的才开始。`shop/stock` 的 0.1.0 与 0.2.0 都声明了迁移时，生成的是：

```yaml
  shop-stock-0-2-0-migration:
    command:
      - migrate
    depends_on:
      shop-stock-0-1-0-migration:
        condition: service_completed_successfully
    entrypoint:
      - /app/stock
    image: shop-stock:0.2.0
```

两个迁移容器的日志，按先后：

```text
shop-stock-0-1-0-migration-1  | shop/stock: migrations applied
shop-stock-0-2-0-migration-1  | shop/stock: migrations applied
```

规则：

- 按版本号比，不是按名字比（`1.10.0` 排在 `1.9.0` 之后）。
- 没有声明迁移的版本跳过，链照样接上。
- **不同组件的迁移不串**：它们各自的链并行跑——两个组件就算共用一个库，也是各管各的表。
- **从源码运行的迁移（`local.migrationCommand`）不在链里**：它在容器之后才跑。同一次 `up` 里同一组件更新的版本在容器里迁移时，
  旧版本从源码的迁移排在它后面——这与以后每一次 `up` 没有两样（见下一节）。

低版本先跑的道理：在空库上，旧版本的迁移建立它需要的结构，新版本的迁移在此之上继续。这只决定第一次 `up` 时库是什么样子。

## 旧版本的迁移会面对新版本迁移过的库

每个版本的迁移在每次 `up` 时都会再跑一遍（所以迁移必须幂等，见[迁移失败](01-migration-service.md#迁移失败)）。于是从第二次 `up`
起，链上旧版本的迁移面对的是一个已经被新版本迁移过的库。第一次 `up` 也会遇到：旧版本加入一个库已被新版本迁移过的项目时（加了一个依赖旧版本的组件），
以及旧版本从源码迁移、排在新版本的容器之后时。什么顺序都避不开。

所以，**版本并存时，组件的迁移必须把"库已被同一组件更新的版本迁移过"当作已完成**：什么也不改，以 0 退出。否则 `up` 停在旧版本的迁移上
（`MIGRATION_FAILED`），链上排在它后面的迁移、以及等着它们的服务都不启动。

要做到这一点，取决于迁移怎样记录状态：

- **按步骤记录已执行的步骤，只执行自己的、还没记录的步骤**：新版本多出来的步骤只是它不看的几行记录，不用另外做什么。
- **只记一个当前版本**，不少迁移工具是这样：其中一些遇到库的版本没有对应文件就报错（golang-migrate：`no migration found for version N`）。
  迁移之前先比较库的版本与组件自带的最新版本；库的更新时，在日志里说一声，以 0 退出。

## 数据兼容是组件作者的事

平台只保证两个版本的迁移不会同时改结构。两个版本同时读写同一批表时是否兼容——新版本加的列旧版本认不认、旧版本写进去的数据新版本读不读得了——
平台无从知道，只能由组件作者设计：通常意味着迁移只做"加法"（加列、加表），不删不改旧版本还在用的结构，等旧版本退役后再清理。
