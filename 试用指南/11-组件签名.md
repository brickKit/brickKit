# 11 · 组件签名（cosign）

🎯 **这一节验证什么：** 用真 cosign 给组件签名发布，再以使用者身份验签安装；然后**亲手篡改数据库**，看 CLI 会不会拦住。

前置：走完 [09-组件市场.md](09-组件市场.md)（市场后端在跑、已经能 `login` / `publish`）。

---

## 先弄清楚 cosign 是什么

**一句话：给一坨字节盖一个防伪章，别人能验章、且验章不需要信任任何中间人。**

它是 Sigstore 项目的签名工具（Linux Foundation，Kubernetes 生态的事实标准）。三个动作就是全部：

```bash
cosign generate-key-pair                        # 生成一对钥匙
cosign sign-blob   --key cosign.key  文件        # 用私钥签 → 一串 base64
cosign verify-blob --key cosign.pub  ...         # 用公钥验
```

它解决的问题跟 HTTPS 不同：**HTTPS 保护的是传输过程，签名保护的是东西本身**。组件从市场下载下来、在你机器上躺三个月、再被 CI 拿去部署——签名在这整条链上都还有效，HTTPS 早就管不着了。

### 两件必须先知道的事

**① 只有发布者要装 cosign。** BrickKit 的验签是 Go 标准库做的（cosign 的签名就是标准 ECDSA P-256 over SHA-256），CLI 零依赖。

| 角色 | 动作 | 要装 cosign 吗 |
| --- | --- | --- |
| 组件发布者 | `brickkit publish --sign` | ✅ 要（一次性，通常在 CI 里） |
| 组件使用者 | `brickkit add` 自动验签 | ❌ 不用 |

**② 公钥必须由你自己配。** 签名里只有 `publicKeyRef` 这个**名字**，真正的公钥来自你的 `brickkit.yaml`。如果公钥能跟着签名从市场取，那就是市场自己给自己发证——市场被攻破时，攻击者把组件和公钥一起换掉，验签照样通过。

## 11.1 发布者：生成密钥对

### ▶️ 操作

```bash
cd 试用指南/playground
mkdir -p publisher/keys && cd publisher/keys

# COSIGN_PASSWORD 置空是为了非交互。生产环境的私钥要有口令，放进 CI 的密钥管理里
COSIGN_PASSWORD="" cosign generate-key-pair
mv cosign.key people-basic-release.key
mv cosign.pub people-basic-release.pub
ls
```

### ✅ 预期

```
people-basic-release.key    ← 私钥，绝不能提交 Git
people-basic-release.pub    ← 公钥，应该提交 Git，要发给使用者
```

> 没装 cosign：`go install github.com/sigstore/cosign/v2/cmd/cosign@latest`，然后确认 `~/go/bin` 在 `PATH` 里。

### ⏹️ 怎么停

没有后台进程。密钥对就是两个文件。

## 11.2 发布者：签名发布

### ▶️ 操作

在发布者项目里（brickkit.yaml 已配好市场安装源、已 `brickkit login`）：

```bash
cd 试用指南/playground/publisher

COSIGN_PASSWORD="" brickkit publish \
  --path ./people/basic \
  --source-type git --git-url https://github.com/example/people-basic.git \
  --sign --key keys/people-basic-release.key \
  --signed-by release-bot@example.com
```

### ✅ 预期

```
📤 发布 people/basic@1.2.0
   ✅ Manifest 校验通过
   ✅ 镜像引用有效：registry.example.com/people-basic:1.2.0
   ✅ 已签名（cosign，公钥 ref：keys/people-basic-release.pub）
   💡 使用者需要在 brickkit.yaml 的 installer.publicKeys 下声明：
        keys/people-basic-release.pub: <公钥文件路径>
   ✅ 上传成功
🎉 发布完成
```

**那句 💡 是要转告给使用者的。** `publicKeyRef` 是发布者与使用者之间的契约：使用者得照这个名字配同名条目，否则谁也验不了。

几件值得注意的事：

- **`--public-key-ref` 默认按 `.key` → `.pub` 推导**，所以 `--key keys/people-basic-release.key` 得到 `keys/people-basic-release.pub`。要用别的名字就显式指定。
- **签名发生在联网之前。** 密钥路径写错时，市场里不会留下任何痕迹——版本号一旦建出来就不可回收，不能因为一次手误烧掉一个有语义的版本号。
- **不会上传到公共透明日志。** cosign 默认会把签名条目传到 Sigstore 的公共 Rekor 日志（全世界可查），CLI 固定关掉了它——BrickKit 的组件大量是 private 的。

### 确认签名真的存进去了

```bash
docker exec <postgres 容器> psql -U postgres -d brickkit_market -t -c \
  "SELECT jsonb_pretty(signature_json) FROM component_versions
   WHERE component_id='people/basic' AND version='1.2.0';"
```

```json
{
    "value": "MEUCIQD7ObW7AZWkYN5Wk10yw7uXosnLaXtTFlC6SpsQXYPbOAIg...",
    "signedAt": "2026-08-15T13:30:38.883605092Z",
    "signedBy": "release-bot@example.com",
    "algorithm": "cosign",
    "publicKeyRef": "keys/people-basic-release.pub"
}
```

### ⏹️ 怎么停

`publish` 跑完就退出。要撤回这个版本：市场侧把版本状态改成 `blocked`（版本号本身不可回收）。

## 11.3 使用者：配好公钥，装组件

### ▶️ 操作

```bash
cd 试用指南/playground
mkdir -p consumer/keys && cd consumer

# 把发布者给的公钥放进项目（公钥不是密钥，应该提交 Git）
cp ../publisher/keys/people-basic-release.pub keys/
```

在 `brickkit.yaml` 里加上 `installer` 段：

```yaml
installer:
  requireSignature: true
  publicKeys:
    # 签名里的 publicKeyRef  →  公钥文件路径（相对项目根目录）
    keys/people-basic-release.pub: keys/people-basic-release.pub
```

然后装：

```bash
brickkit add people/basic@1.2.0
```

### ✅ 预期

```
📦 添加 people/basic@1.2.0
   └── Manifest ✅
🔏 签名：✅ 已校验 people/basic@1.2.0（发布者 release-bot@example.com）
✅ 已写入 brickkit.yaml（1 个组件）
```

**只有真的验过才会出现这一行。** 没配公钥、发布者不认识时都会放行，但那是"没得验"，不是"验过了"——不会显示这一行。

### ⏹️ 怎么停

`add` 跑完就退出。要撤销：`brickkit remove people/basic@1.2.0`，或 `brickkit reset --last`。

## 11.4 篡改：亲手改数据库，看 CLI 拦不拦

这一步是整节的重点。前面都是"正常路径能跑通"，这里才是**签名到底有没有用**。

### ▶️ 操作

直接改市场数据库里的 Manifest，把镜像换成攻击者自己的：

```bash
docker exec <postgres 容器> psql -U postgres -d brickkit_market -c \
  "UPDATE component_versions
   SET manifest_json = jsonb_set(manifest_json, '{deployment,image}',
                                 '\"evil.example.com/people-basic:1.2.0\"')
   WHERE component_id='people/basic' AND version='1.2.0';"
```

签名没动过——攻击者改得了内容，改不出对应的签名。现在强制重新拉取：

```bash
cd 试用指南/playground/consumer
brickkit add people/basic@1.2.0 --refresh --yes
echo "退出码：$?"
```

### ✅ 预期

```
❌ 错误：签名校验不通过
   组件：people/basic@1.2.0
   公钥：keys/people-basic-release.pub
   原因：内容与签名不匹配，可能已被篡改，或签名不是该公钥所签
   建议：
   1. 联系组件发布者重新签名
   2. 确认 installer.publicKeys 中该 ref 指向的确实是发布者的公钥
退出码：1
```

再确认被篡改的内容**没有污染缓存**（先验后存）：

```bash
grep image .brickkit/manifests/people-basic-1.2.0.yaml
#     image: registry.example.com/people-basic:1.2.0   ← 还是原来的
```

### 把数据库改回去

```bash
docker exec <postgres 容器> psql -U postgres -d brickkit_market -c \
  "UPDATE component_versions
   SET manifest_json = jsonb_set(manifest_json, '{deployment,image}',
                                 '\"registry.example.com/people-basic:1.2.0\"')
   WHERE component_id='people/basic' AND version='1.2.0';"
```

## 11.5 requireSignature 的开与关

### ▶️ 操作

发布一个**没签名**的组件，然后在 `requireSignature: true` 的项目里装它：

```bash
cd 试用指南/playground/publisher
brickkit publish --path ./people/unsigned --source-type git --git-url https://example.com/x.git

cd ../consumer
brickkit add people/unsigned@1.2.0
```

### ✅ 预期（阻断）

```
❌ 错误：组件未签名，安装被阻断
   组件：people/unsigned@1.2.0
   原因：项目要求强制签名校验（installer.requireSignature 默认为 true）
   建议：
   1. 联系组件发布者用 brickkit publish --sign 重新发布
   2. 本地开发可在 brickkit.yaml 设置 installer.requireSignature: false 关闭校验
```

把 `requireSignature` 改成 `false` 再试一次，就装得上了。

### ⚠️ 但关掉它**不会**让被篡改的内容通过

这是最容易想当然弄反的一条。把 `requireSignature` 设成 `false`，再去装 11.4 里那个被篡改的组件：

```bash
brickkit add people/basic@1.2.0 --refresh --yes    # requireSignature: false
```

照样报 `签名校验不通过`，退出码 1。

原因：**`requireSignature` 管的是"没有签名允不允许"，不是"坏签名允不允许"。** 一个验不过的签名意味着内容被改过、或来源根本不对——那在任何模式下都不该放行。若关掉强制校验就连坏签名一起放过，本地开发环境会成为投毒的入口，而开发机上的组件照样连着真实的数据库。

## 11.6 签名保护的到底是什么：digest 钉住

签名覆盖的是**整个 Manifest**，而 `deployment.image` 就在里面。
所以"该拉哪个镜像"已经被签名保护了——改一个字签名就对不上。

但还剩一个缺口：

> 签名保证了镜像**字符串**没被改，保证不了那个字符串**还指向同样的字节**。

`repo:1.0.0` 这种 tag 是**可变**的。发布者签名时它指向 A，
攻击者拿到 registry 权限后用同一个 tag 重新 push 一个 B——
**签名依然有效，跑起来的却是 B**。

所以 `brickkit publish` **默认**把 tag 换成 digest 再签名。

### ▶️ 操作

照常发布就行，这是默认行为：

```bash
brickkit publish --path ./components/people/basic --sign
```

### ✅ 预期

```
📤 发布 people/basic@1.2.0
   ✅ Manifest 校验通过
   ✅ 镜像引用有效：registry.example.com/people-basic:1.2.0
   ✅ 镜像已钉 digest：sha256:d9e853e87e55526f6b2917df91a2115c…
```

上传的 Manifest 里镜像变成了 `registry.example.com/people-basic@sha256:d9e8…`。
digest 按定义不可变，**签名从此锁住的是确切的字节**。

### ⚠️ 这会让 publish 需要访问 registry

因为 digest 要向 registry 查。所以发布前**镜像必须已经推上去**：

```bash
docker push registry.example.com/people-basic:1.2.0   # ← 先推
brickkit publish --path ... --sign                    # ← 再发
```

没推的话会被拦下来：

```
❌ 错误：无法确定镜像的 digest，发布已中止
   为什么要拦住：发布出去的版本号不可回收（007 §6.4）。取不到 digest
        通常意味着这个镜像消费方也拉不到——与其在市场里留下一个装不上的
        版本，不如现在停下
   建议：
   1. 确认镜像已经**推送**到 registry：docker push ...
```

**这是有意的**：版本号一旦建出来就不可回收，与其留下一个谁都装不上的版本，
不如在本地就停下。

### 确实没法解析时

气隙环境、私有 registry 权限受限……用 `--no-pin-digest` 跳过：

```bash
brickkit publish --path ... --sign --no-pin-digest
```

```
   ⚠️ 跳过 digest 钉住（--no-pin-digest）
      签名只锁住了镜像**字符串**：registry 上换掉同名 tag 的话，
      签名照样有效，而跑起来的是另一个镜像
```

CLI 会明确告诉你放弃了什么。

### 📎 为什么不给镜像本身也签个名

那是另一件事：它解决的是**绕开 BrickKit 直接部署**时谁来保证镜像来源，
由集群的准入控制器（Kyverno / Sigstore policy-controller）校验——
镜像是 kubelet 拉的，CLI 根本不在那条链路上。

而钉 digest 用**现有签名**就把字节锁住了，不需要任何新机制。

## 完整判定表

| 情形 | `requireSignature: true` | `requireSignature: false` |
| --- | --- | --- |
| **没配 `publicKeys`** | 放行 + 警告 | 放行（静默） |
| 配了公钥，组件没有签名 | ❌ 阻断 | ✅ 放行 |
| 配了公钥，签名 ref 不认识 | ❌ 阻断 | ✅ 放行 + 警告 |
| 配了公钥，签名验不过 | ❌ 阻断 | ❌ 阻断 |

第一行值得单说：**没有可信公钥就没有"强制"可言**。此时就算组件带了签名，我们也没有公钥去验它；因此不阻断，但会警告——你以为自己开着强制校验，实际一次也没校验过。

还有一条边界：**只有市场安装源受签名约束**。本地源指向的是你自己硬盘上、正被你编辑的目录，git 源指向的是你自己在 `brickkit.yaml` 里写下的仓库——那里根本没有"发布者"这个角色。若一并强制，打开 `requireSignature` 会让所有用本地源开发的项目当场瘫痪。

## 还没实现

| 能力 | 状态 |
| --- | --- |
| 市场侧的密码学校验 | ⬜ **想清楚之后决定不做**。任何形态都需要"发布凭据不能管理密钥"这条权限分离，而市场的 Token 目前没有 scope——没有它，偷到 Token 的人也能换掉登记的公钥，"市场验过签"比不验更糟。真正的保护在使用者这边的 `installer.publicKeys`，信任锚点在你自己手里。详见 [008 §8.2](../design/008-安全与治理.md) |
| **镜像本身**的签名（cosign 签镜像） | ⬜ 属集群准入控制器的职责，见上面 11.6 的说明 |
