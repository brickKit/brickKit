# 07 · K8s 部署（minikube）

🎯 **这一节验证什么：** 同一份 `brickkit.yaml`，只改一个字（`target: k8s`），就部署到真集群上。

前置：`minikube` 已安装并启动；`00-准备.sh` 已把 `kubectl` 链到 `试用指南/bin/`。

## 7.1 建一个 K8s 项目

K8s 与 Docker 有两处**根本**不同，配置得跟着变：

| | Docker | K8s |
| --- | --- | --- |
| 基础资源 | `host: pg` → CLI 起一个容器 | **由运维部署**，CLI 一行不碰。`host` 要写集群内能解析的地址 |
| `local: true` | 支持 | **不支持**，会直接报错（集群里的 Pod 连不到你的笔记本） |

### ▶️ 操作

先在集群里准备一个 PostgreSQL（模拟"运维已部署"）：

```bash
kubectl create namespace infra

kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: {name: postgres, namespace: infra}
spec:
  replicas: 1
  selector: {matchLabels: {app: postgres}}
  template:
    metadata: {labels: {app: postgres}}
    spec:
      containers:
        - name: postgres
          image: postgres:15
          env:
            - {name: POSTGRES_USER, value: brickkit}
            - {name: POSTGRES_PASSWORD, value: trialpass}
          ports: [{containerPort: 5432}]
---
apiVersion: v1
kind: Service
metadata: {name: postgres, namespace: infra}
spec:
  selector: {app: postgres}
  ports: [{port: 5432, targetPort: 5432}]
EOF

kubectl -n infra rollout status deployment/postgres
kubectl -n infra exec deploy/postgres -- psql -U brickkit -d postgres -c 'CREATE DATABASE "department"'
```

把组件镜像塞进集群（minikube 用的是自己的镜像库，看不到你本机的）：

```bash
minikube image load brickkit-demo/department-tree:1.0.0
```

新建一个 K8s 项目目录：

```bash
cd 试用指南/playground
mkdir -p k8s-demo && cd k8s-demo
mkdir -p components/department && cp -r ../components/department/tree components/department/

cat > brickkit.yaml <<'EOF'
project: k8s-trial
deploy:
  target: k8s
sources:
  - id: local-dev
    type: local
    path: ./components
components:
  - id: department/tree
    version: 1.0.0
resources:
  - kind: database
    engine: postgresql
    id: pg-main
    host: postgres.infra          # ← 集群内 DNS 名（<service>.<namespace>）
    port: 5432
    username: brickkit
    password: ${TRIAL_PG_PASSWORD}
    bindings:
      - componentId: department/tree
        database: department
EOF

echo "TRIAL_PG_PASSWORD=trialpass" > .env
```

## 7.2 先看看会生成什么

### ▶️ 操作

```bash
brickkit up --dry-run
find .brickkit/generated/k8s -type f | sort
```

### ✅ 预期

```
📄 已生成 5 份清单：.brickkit/generated/k8s/
   命名空间：brickkit-k8s-trial

📌 以下数据库需要预先创建（平台不代建，见 006 §9.5）：
   department  （postgres.infra:5432，供 department/tree 使用）
      CREATE DATABASE "department";
```

```
.brickkit/generated/k8s/deployments/department-tree-1-0-0.yaml
.brickkit/generated/k8s/migrations/department-tree-1-0-0-migration.yaml
.brickkit/generated/k8s/namespace.yaml
.brickkit/generated/k8s/secrets/resource-secrets.yaml
.brickkit/generated/k8s/services/department-tree-1-0-0.yaml
```

### 值得亲自看一眼的三份

```bash
cat .brickkit/generated/k8s/deployments/department-tree-1-0-0.yaml
cat .brickkit/generated/k8s/secrets/resource-secrets.yaml
cat .brickkit/generated/k8s/migrations/department-tree-1-0-0-migration.yaml
```

| 看什么 | 为什么 |
| --- | --- |
| Deployment 里 `DATABASE_PASSWORD` 是 `secretKeyRef` | **密码不出现在 Deployment 里**——那份 YAML 会被人打开看、进 git |
| Secret 里 `password:` 是**真值**，文件权限 `0600` | kubectl 不做变量替换，`${VAR}` 必须在生成时求值。留占位符的话 Pod 会拿字面量去连库 |
| Job 的 `app` 标签是 `...-migration`，**和组件不一样** | 一样的话迁移 Pod 会被登记成组件 Service 的后端，迁移期间部分请求会打到一个不监听端口的 Pod 上 |
| `livenessProbe` / `readinessProbe` 是 `httpGet` | K8s 由 kubelet 从容器**外**探，不要求镜像里有 wget/curl（Docker 那边的 healthcheck 跑在容器**内**，所以必须凑一条镜像里真有的命令） |

### 试一下漏配变量

```bash
mv .env .env.bak && brickkit up --dry-run ; mv .env.bak .env
```

会**阻断**并列出缺哪个变量——绝不写出一份"看着对、跑起来错"的清单。

## 7.3 真部署

### ▶️ 操作

```bash
brickkit up
```

### ✅ 预期

```
☸️  正在部署到 Kubernetes（命名空间 brickkit-k8s-trial）...
   先执行数据库迁移，完成后才启动主服务
   department-tree-1-0-0        running（healthy）
✅ 全部组件已启动（1 个）

💡 查看状态：brickkit status
   查看日志：kubectl logs deployment/<服务名> -n brickkit-k8s-trial
   查看 Pod：kubectl get pods -n brickkit-k8s-trial
```

CLI 在背后按顺序做了这些（K8s 没有 compose 的 `depends_on`，串行控制只能由 CLI 来）：

```
namespace → secrets → delete 旧 Job → apply 迁移 Job → wait 迁移完成
          → deployments → services → ingress → rollout status
```

### 自己确认一遍

```bash
kubectl -n brickkit-k8s-trial get all
kubectl -n brickkit-k8s-trial logs job/department-tree-1-0-0-migration
kubectl -n brickkit-k8s-trial get endpoints department-tree-1-0-0
```

```
pod/department-tree-1-0-0-xxxxx             1/1   Running
pod/department-tree-1-0-0-migration-xxxxx   0/1   Completed     ← 迁移跑完退出了
job.batch/department-tree-1-0-0-migration   Complete   1/1
```

`endpoints` 只有**一个**地址——迁移 Pod 没被算进去，这就是上面那条标签规则的作用。

## 7.4 幂等：再来一次

### ▶️ 操作

```bash
brickkit up
```

### ✅ 预期

照常成功。Job 的 spec 是**不可变**的，同名 Job 还在时直接 apply 会报 `field is immutable`——所以 CLI 每次都先 `kubectl delete job/... --ignore-not-found` 再 apply。改完迁移脚本重跑，不需要你手工清理任何东西。

## 7.5 查状态

```bash
brickkit status
```

```
📦 资源状态
 ┌─────────┬──────────┬───────────────────────────────────────────────┐
 │ pg-main │ database │ postgres.infra:5432（集群内地址，本机不探测） │
 └─────────┴──────────┴───────────────────────────────────────────────┘

   资源在集群内访问，本机不做探测；组件跑起来了就说明它连得上
```

**K8s 下 CLI 不拨号探测资源** —— `postgres.infra` 是集群内的 DNS 名，你的笔记本解析不了它。照 Docker 那套探一次，会对一个完全健康的部署报"不可达"。

想从集群内验证：

```bash
kubectl run -n brickkit-k8s-trial --rm -it netcheck --image=busybox -- nc -zv postgres.infra 5432
```

## 7.6 对外暴露（Ingress）

```yaml
  - id: department/tree
    version: 1.0.0
    expose: true
    hostname: tree.example.com     # K8s 下必填
```

`brickkit up` 之后会多一份 `ingress/department-tree-1-0-0.yaml`。minikube 上要真访问还需要 `minikube addons enable ingress`，并把 `tree.example.com` 指到 `minikube ip`。

不写 `hostname` 会直接报错——一条没有 host 的 Ingress 会匹配**所有**进入集群的域名，一个内部组件可能就这样顶掉门户站点。

## 7.7 真实集群（不是 minikube）还要配什么

minikube 只有一个集群、权限全开、默认不开 Pod Security Admission，所以下面这些在本地永远试不出来。真集群上按需加进 `brickkit.yaml`：

```yaml
deploy:
  target: k8s
  context: prod-cluster          # 钉住集群：与当前 kubectl context 不一致就阻断
  namespace: team-a-prod         # 用运维分配的命名空间（默认 brickkit-<项目名>）
  createNamespace: false         # 命名空间已存在，不由 CLI 创建
  podSecurity: restricted        # 命名空间打了 enforce: restricted 时必须写
  imagePullSecrets: [regcred]    # 私有 registry
  ingressClass: nginx            # 集群没有默认 class 时必须写
  ingressAnnotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod

components:
  - id: portal/user-frontend
    version: 1.0.0
    expose: true
    hostname: portal.example.com
    tlsSecret: portal-tls
```

| 不写会怎样 | 现象 |
| --- | --- |
| `context` | 部到当前 context 指的集群。切走了忘记切回来 → **部错集群，而且成功** |
| `createNamespace` | 只有命名空间级权限时，建命名空间 Forbidden，`up` 在第一条命令就挂 |
| `podSecurity` | Pod 被 API Server 拒收。迁移 Job 更隐蔽：`apply` **成功**，但 Pod 建不出来，`wait` 静默挂到超时，**一条日志都没有**——原因只在 `kubectl describe job/...` 的 events 里 |
| `imagePullSecrets` | ImagePullBackOff |
| `ingressClass` | 集群没有默认 class 时，`apply` 成功但域名打不开 |

⚠️ **`podSecurity: restricted` 下绑不了 1024 以下的端口**（drop 掉了 `NET_BIND_SERVICE`）。CLI 在生成阶段就会警告。对外端口由 Service / Ingress 映射，组件自己监听 8080 就好。

### 本地想试一下 restricted

```bash
kubectl create namespace psa-test
kubectl label namespace psa-test pod-security.kubernetes.io/enforce=restricted
# brickkit.yaml 里 namespace: psa-test + createNamespace: false，先不加 podSecurity
brickkit up      # 迁移 Job 会卡住；另开终端 kubectl describe job/... 看 events
# 加上 podSecurity: restricted 再来一次，就通了
kubectl delete namespace psa-test
```

## ⏹️ 怎么停

```bash
brickkit down            # 删掉本项目在集群里的一切（连命名空间）
```

```
🛑 停止项目 k8s-trial
✅ 已停止全部组件

💡 基础资源（数据库等）由运维部署，不受 brickkit down 影响
```

清理这一节额外建的东西：

```bash
kubectl delete namespace infra      # 试验用的 postgres
```

关掉集群：

```bash
minikube stop        # 停掉，下次 minikube start 还在
minikube delete      # 彻底删掉（镜像、数据全没）
```
