## Docker 与 K8s 的四处真实差别

先看清楚，后面每一步都在处理其中一条：

| | Docker | Kubernetes |
| --- | --- | --- |
| **基础资源** | CLI 自己起 postgres / redis 容器 | **CLI 一行不碰**，由运维部署 |
| **暴露方式** | `exposePort` → 宿主机端口 | `hostname` → Ingress |
| **`${VAR}`** | compose 运行时展开 | **生成清单时就必须求值** |
| **迁移** | compose 的一次性容器 | Kubernetes Job |

第三条最容易踩：`kubectl` 不做变量替换，占位符会被原样当成密码部署上去。

## 16.1 基础资源要自己部署

K8s 环境下 CLI **不托管**任何资源（006 §10.4）—— 生产集群里数据库该由运维用
Operator 或云托管服务部署，CLI 凭空建一个 StatefulSet 只会碍事。

### ▶️ 操作

```bash
kubectl create namespace erp-demo

kubectl apply -n erp-demo -f - <<'YAML'
apiVersion: v1
kind: Secret
metadata: {name: infra-secret}
stringData: {POSTGRES_PASSWORD: q}
---
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: postgres}
spec:
  serviceName: postgres
  replicas: 1
  selector: {matchLabels: {app: postgres}}
  template:
    metadata: {labels: {app: postgres}}
    spec:
      containers:
        - name: postgres
          image: postgres:15
          env:
            - {name: POSTGRES_USER, value: postgres}
            - {name: POSTGRES_PASSWORD, valueFrom: {secretKeyRef: {name: infra-secret, key: POSTGRES_PASSWORD}}}
            - {name: PGDATA, value: /var/lib/postgresql/data/pgdata}
          ports: [{containerPort: 5432}]
          volumeMounts: [{name: data, mountPath: /var/lib/postgresql/data}]
      volumes: [{name: data, emptyDir: {}}]     # 试用而已；生产用 PVC
---
apiVersion: v1
kind: Service
metadata: {name: postgres}
spec:
  selector: {app: postgres}
  ports: [{port: 5432}]
---
apiVersion: apps/v1
kind: Deployment
metadata: {name: redis}
spec:
  replicas: 1
  selector: {matchLabels: {app: redis}}
  template:
    metadata: {labels: {app: redis}}
    spec:
      containers: [{name: redis, image: redis:7-alpine, ports: [{containerPort: 6379}]}]
---
apiVersion: v1
kind: Service
metadata: {name: redis}
spec:
  selector: {app: redis}
  ports: [{port: 6379}]
YAML

kubectl -n erp-demo wait --for=condition=ready pod -l app=postgres --timeout=120s
```

建库（平台照样不代建）：

```bash
for db in erp_department erp_people erp_auth erp_rbac; do
  kubectl -n erp-demo exec postgres-0 -- psql -U postgres -c "CREATE DATABASE \"$db\";"
done
```

### ⏹️ 怎么停

```bash
kubectl delete namespace erp-demo      # 这一节的所有东西都在这个 namespace 里
```

## 16.2 把镜像装进 minikube

集群拉不到你本机 docker 里的镜像。

### ▶️ 操作

```bash
for img in department-tree people-basic auth-password-login authorization-rbac \
           erp-backend portal-user-frontend infra-redis-event-bus infra-api-docs; do
  minikube image load "brickkit-demo/$img:1.0.0"
done
```

### ⚠️ 改了镜像之后它不会更新

**这一条真踩了半小时。** 改完组件重新 `docker build`、再 `minikube image load`，
集群里跑的还是旧的 —— 因为 minikube 从**自己的缓存**
（`~/.minikube/cache/images/`）加载，而那份缓存没更新。

可靠的办法是绕开缓存，走 tar：

```bash
docker build -t brickkit-demo/portal-user-frontend:1.0.0 tests/components/portal-user-frontend
docker save brickkit-demo/portal-user-frontend:1.0.0 -o /tmp/portal.tar
minikube image load /tmp/portal.tar
kubectl -n erp-demo delete pod -l app=portal-user-frontend-1-0-0    # 让它重建
```

怎么确认换成功了：

```bash
docker images --no-trunc -q brickkit-demo/portal-user-frontend:1.0.0
docker exec minikube crictl images --no-trunc | grep portal
```

两个 ID 一致才算换上了。**ID 不看就下结论，会白查很久** —— 症状是
"我明明改了代码，行为还是老样子"。

## 16.3 改一个字段

### ▶️ 操作

把 12 节的 `brickkit.yaml` 复制过来，改这几处：

```yaml
deploy:
  target: k8s                    # ← 就这一个字段决定生成什么
  namespace: erp-demo
  createNamespace: false         # 上一步已经建过了

components:
  - id: portal/user-frontend
    version: 1.0.0
    expose: true
    hostname: erp.local          # ← K8s 用 hostname，不是 exposePort
  - id: infra/api-docs
    version: 1.0.0
    enabled: true
    expose: true
    hostname: docs.local

resources:
  - id: pg
    host: postgres.erp-demo.svc.cluster.local    # ← 集群内的 Service DNS
    # ...
  - id: redis
    host: redis.erp-demo.svc.cluster.local
    # ...
```

```bash
brickkit up --dry-run
```

### ✅ 预期：先报错

```
❌ 错误：brickkit.yaml 里引用的环境变量没有定义
   缺少的变量：JWT_SECRET
   原因：生成 K8s 清单时必须求值——kubectl 不做变量替换
```

**这是 Docker 与 K8s 最实质的差别之一。** compose 会在运行时展开 `${VAR}`，
而 `kubectl` 不会 —— 占位符会被原样当成密码部署上去，Pod 以认证失败反复重启，
而 YAML 看着完全正常。所以 CLI 在生成阶段就硬性拦下。

把 12 节那份 `.env` 带过来即可：

```bash
cp ../erp-demo/.env .
brickkit up --dry-run
```

### 看看生成了什么

```bash
find .brickkit/generated/k8s -type f | sort
```

```
deployments/  8 个
ingress/      2 个   ← 只有 expose: true 的那两个
migrations/   4 个   ← 只有声明了 migration 的那四个
secrets/      1 个
services/     8 个
```

确认占位符真的被求值了：

```bash
grep -r '${' .brickkit/generated/k8s/ && echo "❌ 有未替换的占位符" || echo "✅ 干净"
```

### ▶️ 操作

```bash

```

```
☸️  正在部署到 Kubernetes（命名空间 erp-demo）...
   先执行数据库迁移，完成后才启动主服务
   department-tree-1-0-0        running（healthy）
   ...
✅ 全部组件已启动（8 个）
```

```bash
kubectl -n erp-demo get pods
```

```
auth-password-login-1-0-0-xxx            1/1   Running
auth-password-login-1-0-0-migration-xxx  0/1   Completed   ← 迁移 Job

```

```bash

```

## 16.5 通过 Ingress 访问

### ▶️ 操作

```bash
minikube addons enable ingress
kubectl -n ingress-nginx wait --for=condition=ready pod \
  -l app.kubernetes.io/component=controller --timeout=180s

IP=$(minikube ip)
```

`erp.local` 不是真域名，用 `--resolve` 告诉 curl 去哪儿找它（或写进 `/etc/hosts`）：

```bash
TOKEN=$(curl -s --resolve "erp.local:80:$IP" -X POST -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"demo-password"}' \
  http://erp.local/api/v1/login | python3 -c "import json,sys;print(json.load(sys.stdin)['token'])")

curl -s --resolve "erp.local:80:$IP" -H "Authorization: Bearer $TOKEN" \
  http://erp.local/api/v1/orders
```

### ✅ 预期

```
o-1  服务器采购  张三/技术中心
o-2  差旅报销    张三/技术中心
o-3  培训费用    赵六/后端组
```

审批一单，看弱依赖：

```bash
curl -s --resolve "erp.local:80:$IP" -X POST -H "Authorization: Bearer $TOKEN" \
  http://erp.local/api/v1/orders/o-1/approve
```

```json
{"approvedBy":"p-001","eventPublished":true,"orderId":"o-1","status":"approved"}
```

文档中心也有自己的 Ingress：

```bash
curl -s --resolve "docs.local:80:$IP" http://docs.local/api/v1/sources
```

**同一套组件、同一套业务逻辑，换了个部署形态而已。**

## 16.6 一个 nginx 特有的坑：K8s 里裸服务名解析不了

第一次部署时门户返回 **502**，而后端 Pod 好好的。日志里是：

```
erp-backend-1-0-0 could not be resolved (2: Server failure)
```

### 为什么

nginx 的 `resolver` 指令**不使用 `/etc/resolv.conf` 的 `search` 域** ——
它只拿 nameserver 的地址。而 K8s 正是靠 search 域让裸服务名可解析：

```
nameserver 10.96.0.10
search erp-demo.svc.cluster.local svc.cluster.local cluster.local
```

于是平台注入的 `http://erp-backend-1-0-0:8080` 在**别的组件里都好好的**
（Go / Python 的 DNS 解析会走 search 域），到 nginx 这里就解析不了。

### 怎么修的

修在**组件里**，不是平台里：裸服务名对其余所有组件都是对的，
只有 nginx 的 resolver 绕开了 search —— 那是 nginx 特有的行为，
该由用 nginx 的组件自己处理。

`portal/user-frontend` 加了一个入口钩子
（[15-cluster-fqdn.envsh](../tests/components/portal-user-frontend/docker-entrypoint.d/15-cluster-fqdn.envsh)）：
从 `/etc/resolv.conf` 里找带 `.svc.` 的 search 域，找到就把后端地址补成 FQDN。

```
portal/user-frontend: 检测到 Kubernetes（search erp-demo.svc.cluster.local），
后端地址补成 http://erp-backend-1-0-0.erp-demo.svc.cluster.local:8080
```

只在看到 `.svc.` 时才动手：Docker 环境下容器也可能有 search 域（网络名），
拼上去反而解析不了。

> **这个坑值得记住的地方不是 nginx，而是"同一份配置在两种编排下行为不同"。**
> Docker 上跑得好好的东西，到 K8s 可能因为一个基础设施层的细微差别就不工作 ——
> 而症状（502）跟原因（DNS search 域）看起来毫无关系。

## 16.7 K8s 特有的检查

### 迁移失败会怎样

```bash
kubectl -n erp-demo get jobs
kubectl -n erp-demo logs job/<组件名>-migration
```

迁移 Job 失败时，**主服务不会启动** —— 这是有意的（002 §8）：
表结构没准备好就启动，只会在第一个请求时以更难查的方式炸掉。

### Pod 一直 Pending 或 ImagePullBackOff

```bash
kubectl -n erp-demo describe pod <pod 名> | tail -20
```

十有八九是 16.2 那个镜像问题。

### 迁移 Job 卡着不动、日志是空的

先看**事件**，不是日志：

```bash
kubectl -n erp-demo get events --sort-by=.lastTimestamp | tail -20
```

Job 建出来了但 Pod 一直没创建，通常是被**准入控制**挡了（如 Pod Security
Standards 的 restricted 策略）。这种情况日志永远是空的，因为容器根本没跑起来。
