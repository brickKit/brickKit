# 19 · 多副本与优雅排空

> **这一篇解决什么：** 一个组件跑几份、以及"运维升级集群时会不会把你的服务一次干掉"。
>
> **前置：** 一个能用的 K8s 集群（[00-准备](00-准备.md) 里的 minikube 就行）。
> 本篇全程 `deploy.target: k8s`——**副本数是 K8s 概念**，Docker 目标下写了不生效（见 19.5）。

---

## 先说清楚这一篇在防什么

单副本时，运维执行 `kubectl drain`（换机器、升级集群、缩容，都会做这件事）
会把你那唯一的 Pod 赶走，**服务瞬间归零**。

多副本能让服务活着，但光有多副本还不够：K8s 允许**同时**赶走一个组件的
全部副本——三个都在同一台机器上时，那台机器一 drain，你还是归零。

PodDisruptionBudget（PDB）就是拦这件事的：**任何时刻最多允许一个副本不可用**。

---

## 19.1 把副本数改成 3

```yaml
# brickkit.yaml
project: replica-trial
deploy:
  target: k8s
components:
  - id: demo/hello
    version: 1.0.0
    replicas: 3          # ← 就这一行
```

```bash
brickkit up
```

### ✅ 预期

```
   ✅ demo/hello@1.0.0  根组件（没有其他组件依赖它）
✅ 全部组件已启动（1 个）
```

"1 个"指的是**组件**数，不是 Pod 数。看生成物：

```bash
ls .brickkit/generated/k8s/
```

```
deployments
namespace.yaml
poddisruptionbudgets     ← 多副本时自动出现
services
```

**`poddisruptionbudgets/` 是你没要求、平台自己加的。** 下一节说为什么。

---

## 19.2 平台替你生成了什么

```bash
cat .brickkit/generated/k8s/poddisruptionbudgets/demo-hello-1-0-0.yaml
```

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  labels:
    app: demo-hello-1-0-0
    brickkit.io/component: demo-hello
    brickkit.io/component-version: 1.0.0
    brickkit.io/project: replica-trial
  name: demo-hello-1-0-0
  namespace: brickkit-replica-trial
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: demo-hello-1-0-0
```

集群里：

```bash
kubectl get deploy,pdb -n brickkit-replica-trial
```

```
NAME                               READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/demo-hello-1-0-0   3/3     3            3           18s

NAME                                          MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
poddisruptionbudget.policy/demo-hello-1-0-0   N/A             1                 1                     18s
```

**`ALLOWED DISRUPTIONS: 1`** —— 记住这个数，19.4 会看到它变成 0 的样子。

### 为什么是 `maxUnavailable` 而不是 `minAvailable`

副本数固定时两者等价（3 副本时 `minAvailable: 2` == `maxUnavailable: 1`），
但 `maxUnavailable` **随副本数自动成立**：你把 3 改成 5，PDB 不用动。

写死 `minAvailable: 2` 的话，改成 5 副本之后容错度就从"允许挂 1 个"
悄悄变成"允许挂 3 个"——而没有任何提示。

## 19.3 验证它真的在拦

drain 的核心动作是**驱逐 Pod**。直接调驱逐接口，比 drain 整台机器更快看到结果。

```bash
NS=brickkit-replica-trial
ev() {
  kubectl create -n $NS --raw "/api/v1/namespaces/$NS/pods/$1/eviction" \
    -f <(printf '{"apiVersion":"policy/v1","kind":"Eviction","metadata":{"name":"%s","namespace":"'$NS'"}}' "$1")
}

PODS=$(kubectl get pod -n $NS -l app=demo-hello-1-0-0 -o jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}')
ev $(echo "$PODS" | sed -n 1p)     # 第一个
ev $(echo "$PODS" | sed -n 2p)     # 紧接着第二个
```

### ✅ 预期

```
{"kind":"Status","apiVersion":"v1","metadata":{},"status":"Success","code":201}
Error from server (TooManyRequests): Cannot evict pod as it would violate the pod's disruption budget.
```

**放行一个、拦住第二个。** 这正是 PDB 该做的事：
运维可以逐个换机器，但永远不会一次带走两个。

> ⚠️ **必须连着驱逐，中间不能等。** 第一个 Pod 被换掉之后副本会补齐，
> `ALLOWED DISRUPTIONS` 回到 1，那时第二次驱逐也会成功——
> 只验到"能驱逐"等于没验到 PDB 在工作。

## 19.4 反过来看：单副本时 PDB 是有害的

这是平台**单副本时坚决不生成 PDB** 的原因。想亲眼看的话，
[17.7](17-网络策略与最小权限.md) 有完整的实验：手动给一个单副本组件加 PDB，
`ALLOWED DISRUPTIONS` 立刻是 **0**，`kubectl drain` 一直重试到超时——
**排空永远不可能成功**。

要命的是代价落在谁身上：打开开关的是开发者，撞上的是几个月后升级集群的运维，
而现场只有一台排不空的机器，跟 `brickkit.yaml` 里某一行联系不起来。

### 改回单副本时，PDB 会被自动清掉

```bash
# 把 replicas 改回 1
brickkit up
```

```
🧹 已清理旧版本残留（1 项）：
✅ 全部组件已启动（1 个）
```

```bash
kubectl get pdb -n brickkit-replica-trial
```

```
No resources found in brickkit-replica-trial namespace.
```

**这一步比看起来重要。** `kubectl apply` 只创建和更新、**不会删**你没再生成的东西。
少了这层清理，那份 `maxUnavailable: 1` 的 PDB 会永远留在一个单副本组件上，
让那台机器从此排不空——正是上面说的那个坑，只是入口更隐蔽。

## 19.5 三条会被拦下的写法

| 写法 | 结果 |
| --- | --- |
| `replicas: 0` | ❌ 报错，并指向 `enabled: false` |
| `replicas` + `local: true` | ❌ 报错 |
| `replicas` + `external:` | ❌ 报错 |

试一下第一条：

```yaml
components:
  - id: demo/hello
    version: 1.0.0
    replicas: 0
```

```
❌ 错误：brickkit.yaml 校验失败
   文件：brickkit.yaml
   components[0].replicas：必须 >= 1（当前是 0）。要关掉这个组件请用
   enabled: false——它会走级联计算并提醒依赖方，而 replicas: 0 绕过这一切：
   依赖方照常启动、照常拿到地址，然后连一个不存在的后端
```

**为什么不许用 `replicas: 0` 关组件：** `enabled: false` 会走级联计算
（[04-组件开启模式](04-组件开启模式.md)），依赖它的组件会被一起关掉或收到提醒；
而 `replicas: 0` 绕过这一切——依赖方照常启动、照常拿到地址，然后连一个
**不存在的后端**。表现是 503，而 `brickkit status` 里那个组件显示"正常"。

后两条同理：`local: true` 是"这个组件在你的 IDE 里跑"（那里只有一个进程），
`external:` 是"它由别的项目部署"（副本数是那边的决定，见
[18-多项目与共享](18-多项目与共享.md)）。

### Docker 目标下写了会怎样

不报错，但会提醒：

```
⚠️ 配置里有只对 K8s 生效的字段
   字段：components[demo/hello].replicas
   当前目标：deploy.target: docker
   说明：这些字段只在 deploy.target: k8s 下生效，本次被忽略
   建议：要部署到 K8s 请把 deploy.target 改成 k8s
```

不提醒的话，你会看到 `up` 一切正常、`docker ps` 里只有一个容器，
然后怀疑是不是字段名写错了——**字段名是对的**。

## ⏹️ 怎么停

```bash
brickkit down
```

## 一句话总结

```
replicas: 3   →  三个副本 + 一份 maxUnavailable: 1 的 PDB（平台自动加）
replicas: 1   →  单副本，且那份 PDB 会被清掉（留着会让机器排不空）
```

多副本本身只是"跑几份"，PDB 才是那个**让运维能安全换机器**的东西。
而它是平台顺手加的——你只写了一个数字。
