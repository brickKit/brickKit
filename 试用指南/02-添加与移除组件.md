# 02 · 添加与移除组件

🎯 **这一节验证什么：** 安装源怎么配、`add` 会递归拉什么、产物落在哪、`remove` 清得干不干净。

前置：01 做完（项目已初始化）。**不需要 Docker**——本节只到「写进配置、拉下产物」，不启动任何容器。

---

## 2.1 安装源

`brickkit init` 生成的骨架**已经配好了一个本地源**，指向它自己创建的 `components/` 目录：

```yaml
sources:
  - id: local-dev
    type: local
    path: ./components      # brickkit init 已经建好这个目录
  # 组件市场按需取消注释并填上地址：
  # - id: brickkit-market
  #   type: market
  #   url: https://market.example.com/api/v1
```

所以本节全程**不用改一行配置**。市场源之所以留成注释，是因为 CLI 猜不到你的市场地址
——要用市场就取消注释并填上（见 [10-组件市场.md](10-组件市场.md)）。

### ▶️ 操作

确认一下就好：

```bash
sed -n '/^sources:/,/^components:/p' brickkit.yaml
```

### 三种安装源

| type | 字段 | 用途 |
| --- | --- | --- |
| `local` | `path` | 本地目录，**本指南全程用它**。目录布局必须是 `<path>/<组件ID>/component.yaml`，即 `components/demo/hello/component.yaml` |
| `market` | `url`、`authToken`（可选） | 组件市场，见 [10-组件市场.md](10-组件市场.md) |
| `git` | `url` | 直接从 Git 仓库拉（当前固定 `--depth 1` 拉默认分支） |

多个源按**声明顺序**依次尝试，前一个找不到就试下一个。加 `enabled: false` 可临时停用某个源而不删掉它。

> **本地源不吃缓存。** 改了 `components/` 下的 `component.yaml`，下次命令立刻生效——本地源本来就是"边改边试"的场景，缓存只会让人对着改了没反应的文件发懵。市场与 Git 源才走缓存（要强制刷新用 `brickkit add --refresh`）。

## 2.2 添加组件

### ▶️ 操作

```bash
brickkit add demo/caller@1.0.0
```

版本号可以不写——`brickkit add demo/caller` 会装安装源上最新的可安装版本，
并把解析出的**精确版本**写进 `brickkit.yaml`（配置里永远不会出现 `^1.0.0` 这类范围约束）：

```
🔎 未指定版本，解析到 demo/caller@1.0.0（来自安装源 local-dev，类型 local）
```

同一个组件已经装了别的版本时，CLI 会先问一句再共存——共存会真的多起一个容器。

### ✅ 预期

```
📦 添加 demo/caller@1.0.0
   ├── Manifest ✅
   ├── 依赖 demo/hello@1.0.0 ✅ 已拉取（artifacts 1 个文件）
   └── artifacts ✅（1 个文件）
⚠️ 警告：弱依赖缺失：demo/bus@1.0.0
   影响组件：demo/caller@1.0.0
   原因：该组件在所有安装源中均未找到
   影响：该组件的环境变量 DEMO_BUS_ENDPOINT 不会被注入
   💡 弱依赖降级由组件自行处理（002 §3.4）
✅ 已写入 brickkit.yaml（2 个组件）
📁 已下载 artifacts 到 .brickkit/artifacts/（2 个文件）
```

三件事同时发生了：

1. **递归拉依赖** —— 你只写了 `demo/caller`，它的强依赖 `demo/hello` 被自动拉进来并写入配置。
2. **弱依赖缺失只警告** —— `demo/bus` 根本不存在，但那是**弱**依赖：警告一句，继续。这个组件会以"没有 bus"的方式降级运行。
3. **产物下载** —— proto / openapi.json 落到 `.brickkit/artifacts/<版本化服务名>/`。

### 看看写进去了什么

```bash
cat brickkit.yaml
find .brickkit -type f | sort
```

```yaml
components:
  - id: demo/hello        # ← 自动加进来的依赖
    version: 1.0.0
  - id: demo/caller       # ← 你要的那个
    version: 1.0.0
```

```
.brickkit/artifacts/demo-caller-1-0-0/api-docs/openapi.json
.brickkit/artifacts/demo-hello-1-0-0/api-docs/openapi.json
.brickkit/backup/brickkit.yaml.initial
.brickkit/backup/brickkit.yaml.last      ← add 之前自动备份的
.brickkit/manifests/demo-caller-1.0.0.yaml
.brickkit/manifests/demo-hello-1.0.0.yaml
```

注意 `demo-caller-1-0-0` 这个名字：**版本化服务名**（组件 ID 的 `/` 和版本里的 `.` 都换成 `-`）。它同时是容器名、K8s Service 名、产物目录名、环境变量里的地址——全平台一个名字。

### 常用参数

| 参数 | 作用 |
| --- | --- |
| `-y` / `--yes` | 不问确认，CI 里用 |
| `--refresh` | 忽略缓存重新拉（本地源本来就不吃缓存） |
| `--repo` | 额外把该组件的 Git 仓库 clone 到 `components/`（仅开源组件） |
| `--repo-all` | 把所有递归依赖中的开源组件都 clone 下来 |

## 2.3 移除组件

### ▶️ 操作

```bash
brickkit add people/basic@1.0.0 -y     # 先多加一个
brickkit remove people/basic@1.0.0
find .brickkit -type f | sort
```

### ✅ 预期

`remove` 会一并清掉这个组件的 Manifest 缓存与 artifacts 目录，**但不会动它的依赖**——`department/tree` 是被 `people/basic` 拉进来的，移除时留在配置里（可能别人也在用）。要一起清掉就再 `remove` 一次。

源码目录也一起删干净：`components/<scope>/<name>/`，以及被 [`brickkit sync`](#24-整理源码工作区brickkit-sync) 归档到 `components/.archived/` 的那一份。`components/` 下不会留下任何一个"已经移除但还占着位子"的目录。（同一组件 ID 还有别的版本在用时例外——那份源码目录是共用的，会保留。）

### 试一个会被拦下来的操作

```bash
brickkit remove demo/hello@1.0.0
```

`demo/caller` 强依赖它，CLI 会明确报错并打印依赖链，而不是让你把项目改成一个起不来的状态。

## 2.4 整理源码工作区（`brickkit sync`）

`components/` 下每个组件都是一个**独立的 Git 仓库**。项目大了以后，那些当前根本不启动的组件源码还堆在那儿，IDE 索引、全局搜索、`git status` 全都被它们拖着。

`brickkit sync` 按级联计算结果把它们**双向**整理：不启动的移进 `components/.archived/`，重新启用的再移回来。

### ▶️ 操作

先给两个组件建源码目录（真实场景是 `brickkit add --repo` clone 下来的）：

```bash
mkdir -p components/demo
cp -r <仓库根目录>/tests/components/demo-hello  components/demo/hello
cp -r <仓库根目录>/tests/components/demo-caller components/demo/caller
(cd components/demo/hello  && git init -q && git add . && git commit -qm 初始提交)
(cd components/demo/caller && git init -q && git add . && git commit -qm 初始提交)

brickkit sync
```

```
📂 工作区整理：
   ✅ components/demo/caller/              活跃
   ✅ components/demo/hello/               活跃
✅ 工作区整理完成（2 个活跃，0 个归档，0 个激活）
```

现在把 `demo/hello` 关掉（`enabled: false`），再来一次：

```
📂 工作区整理：
   📦 components/demo/caller/              → components/.archived/demo/caller
      原因：级联跳过（强依赖 demo/hello 不启动）
   📦 components/demo/hello/               → components/.archived/demo/hello
      原因：显式禁用（enabled: false）
✅ 工作区整理完成（0 个活跃，2 个归档，0 个激活）
```

**`demo/caller` 也被归档了** —— 它强依赖 `demo/hello`，本来就不会启动。判断依据和 `brickkit up` 是同一套级联计算。

删掉 `enabled: false` 再 `sync`，两个都会移回来（原因写着"恢复启用"）。

归档之后如果直接 `brickkit remove` 掉这个组件，归档目录里的那份源码会被一起删掉——sync 只整理 `brickkit.yaml` 里还在的组件，留着就再没人回收了。

### 四条要记住的规则

| 规则 | 说明 |
| --- | --- |
| **不影响运行中的容器** | sync 只动目录。容器还在跑的时候 sync，容器一个都不会动——要停请用 `brickkit down` |
| **不集成在 `up` 里** | 纯独立命令，什么时候整理由你决定 |
| **只动 brickkit.yaml 里声明过的组件** | `components/` 下你正在开发、还没 `add` 进来的组件**不受影响** |
| **没有 `--dry-run`** | 搞错了再执行一次就回来了 |

`.git` 是整个目录一起搬走的，归档之后 `git status`、`git log`、提交推送全都照常。

⏹️ **怎么撤销：** 把配置改回去再 `brickkit sync` 一次。

## 2.5 一次装全，再把不要的关掉

这一节是个**独立演示**，走完会把试验场重置掉——所以放心大胆地试，不用担心
把后面几篇的状态搞乱。

演示两件事：`--local` 一次装全，以及**用 `enabled: false` 把不需要的关掉，而不是删掉**。

### ▶️ 操作

先把本地源里的组件**全部**加进来：

```bash
brickkit add --local
```

```
🔍 从本地安装源 local-dev 扫到 10 个组件
⏭️ demo/caller@1.0.0 已在 brickkit.yaml 中
⏭️ demo/hello@1.0.0 已在 brickkit.yaml 中
📦 添加 auth/password-login@1.0.0
   ├── Manifest ✅
   ├── 依赖 department/tree@1.0.0 ✅ 已拉取（artifacts 2 个文件）
   ├── 弱依赖 infra/redis-event-bus@1.0.0 ✅ 已拉取（artifacts 1 个文件）
   ├── 依赖 people/basic@1.0.0 ✅ 已拉取（artifacts 2 个文件）
   └── artifacts ✅（1 个文件）
   （中间省略若干个）
✅ 已写入 brickkit.yaml（10 个组件）
```

`准备.sh` 往 `components/` 拷了十个组件，所以这一条会把十个全装上——
已经在配置里的静静跳过（`⏭️`），**再跑一次不会重复写**。

十个里有六个要到 [13-完整装配](13-完整装配.md) 才用得上。**不用删——关掉就行。**
把 `brickkit.yaml` 的整个 `components:` 段替换成下面这份：

```yaml
components:
  # ↓ 这四个是 03–08 要用的，留着
  - id: demo/hello
    version: 1.0.0
  - id: demo/caller
    version: 1.0.0
  - id: department/tree
    version: 1.0.0
    enabled: true
  - id: people/basic
    version: 1.0.0
    enabled: true

  # ↓ 其余六个 13 才用得上，先关掉
  - id: auth/password-login
    version: 1.0.0
    enabled: false
  - id: authorization/rbac
    version: 1.0.0
    enabled: false
  - id: erp/backend
    version: 1.0.0
    enabled: false
  - id: portal/user-frontend
    version: 1.0.0
    enabled: false
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: false
  - id: infra/api-docs
    version: 1.0.0
    enabled: false
```

### ✅ 预期

```bash
brickkit order
```

四个 `✅`、六个 `⬜`：

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             被 demo/caller 依赖
   ✅ demo/caller@1.0.0            根组件（没有其他组件依赖它）
   ✅ department/tree@1.0.0        显式启用（钉住）
   ⬜ infra/redis-event-bus@1.0.0  显式禁用（enabled: false）
   ✅ people/basic@1.0.0           显式启用（钉住）
   ⬜ auth/password-login@1.0.0    显式禁用（enabled: false）
   ⬜ authorization/rbac@1.0.0     显式禁用（enabled: false）
   ⬜ erp/backend@1.0.0            显式禁用（enabled: false）
   ⬜ portal/user-frontend@1.0.0   显式禁用（enabled: false）
   ⬜ infra/api-docs@1.0.0         显式禁用（enabled: false）
```

### 为什么 `department/tree` 和 `people/basic` 要写 `enabled: true`

这是**唯一一处**你现在需要知道的例外，剩下的留给 [04](04-组件开启模式.md)。

`enabled` 有三种状态，不写 ≠ `true`：

| 写法 | 含义 |
| --- | --- |
| **不写** | "我不反对它跑"。真跑不跑由级联算——**没有任何启用中的组件依赖它，它就不跑** |
| `enabled: true` | "钉住，一定跑"，级联管不着 |
| `enabled: false` | "别跑"，并且依赖它的组件跟着被级联跳过 |

`people/basic` 被 `erp/backend` 依赖，而 `erp/backend` 刚被你关掉了。于是对级联来说，
`people/basic` 变成了"没有启用中的组件依赖它"——**不写 `enabled` 的话它不会跑**，
输出会是 `⬜ people/basic@1.0.0  级联跳过（没有启用中的组件依赖它）`，
`department/tree` 又被它带着一起跳过。写 `enabled: true` 就是把这两个钉住。

不信可以把那两行 `enabled: true` 删掉再 `brickkit order` 一次，然后加回来。
**这个"想当然"正是 [04](04-组件开启模式.md) 整篇要讲的东西。**
