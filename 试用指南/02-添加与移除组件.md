# 02 · 添加与移除组件

🎯 **这一节验证什么：** 安装源怎么配、`add` 会递归拉什么、产物落在哪、`sync` 怎么整理源码、`remove` 清得干不干净。

前置：项目已初始化——[01](01-初始化项目.md) 做完即可。想直接从这里开始：

```bash
./试用指南/准备.sh --reset
cd 试用指南/playground && brickkit init demo-shop
```

**不需要 Docker**——本节只到「写进配置、拉下产物、搬源码目录」，不启动任何容器。

---

## 2.1 安装源

`brickkit init` 生成的骨架**已经配好了一个本地源**，指向它自己创建的 `components/` 目录：

```yaml
sources:
  - id: local-dev
    type: local
    path: ./components      # brickkit init 已经建好这个目录
  # 组件市场按需取消注释并填上地址：
  # - id: brickkit-market
  #   type: market
  #   url: https://market.example.com/api/v1
```

所以本节全程**不用改一行配置**。市场源之所以留成注释，是因为 CLI 猜不到你的市场地址
——要用市场就取消注释并填上（见 [10-组件市场.md](10-组件市场.md)）。

### ▶️ 操作

确认一下就好：

```bash
sed -n '/^sources:/,/^components:/p' brickkit.yaml
```

### 三种安装源

| type | 字段 | 用途 |
| --- | --- | --- |
| `local` | `path` | 本地目录，**本指南全程用它**。目录布局必须是 `<path>/<组件ID>/component.yaml`，即 `components/demo/hello/component.yaml` |
| `market` | `url`、`authToken`（可选） | 组件市场，见 [10-组件市场.md](10-组件市场.md) |
| `git` | `url`、`ref`（可选） | 直接从 Git 仓库拉（不写 `ref` 时取默认分支） |

多个源按**声明顺序**依次尝试，前一个找不到就试下一个。加 `enabled: false` 可临时停用某个源而不删掉它。

> **本地源不吃缓存。** 改了 `components/` 下的 `component.yaml`，下次命令立刻生效——本地源本来就是"边改边试"的场景，缓存只会让人对着改了没反应的文件发懵。市场与 Git 源才走缓存（要强制刷新，就对同一个版本再 `brickkit add` 一次，它会问你要不要刷新）。

## 2.2 添加一个组件

### ▶️ 操作

```bash
brickkit add demo/caller@1.0.0
```

版本号可以不写——`brickkit add demo/caller` 会装安装源上最新的可安装版本，
并把解析出的**精确版本**写进 `brickkit.yaml`（配置里永远不会出现 `^1.0.0` 这类范围约束）：

```
🔎 未指定版本，解析到 demo/caller@1.0.0（来自安装源 local-dev，类型 local）
```

同一个组件已经装了别的版本时，CLI 会先问一句再共存——共存会真的多起一个容器。

### ✅ 预期

```
📦 添加 demo/caller@1.0.0
   ├── Manifest ✅
   ├── 依赖 demo/hello@1.0.0 ✅ 已拉取（artifacts 1 个文件）
   └── artifacts ✅（1 个文件）
⚠️ 警告：弱依赖缺失：demo/bus@1.0.0
   影响组件：demo/caller@1.0.0
   原因：该组件在所有安装源中均未找到
   影响：该组件的环境变量 DEMO_BUS_ENDPOINT 不会被注入
   💡 弱依赖降级由组件自行处理（002 §3.4）；如需启用，请确认该组件已发布并可从安装源获取
✅ 已写入 brickkit.yaml（2 个组件）
📁 已下载 artifacts 到 .brickkit/artifacts/（2 个文件）
```

三件事同时发生了：

1. **递归拉依赖** —— 你只写了 `demo/caller`，它的强依赖 `demo/hello` 被自动拉进来并写入配置。
2. **弱依赖缺失只警告** —— `demo/bus` 根本不存在，但那是**弱**依赖：警告一句，继续。这个组件会以"没有 bus"的方式降级运行。
3. **产物下载** —— proto / openapi.json 落到 `.brickkit/artifacts/<版本化服务名>/`。

### 看看写进去了什么

```bash
cat brickkit.yaml
find .brickkit -type f | sort
```

```yaml
components:
  - id: demo/hello        # ← 自动加进来的依赖
    version: 1.0.0
  - id: demo/caller       # ← 你要的那个
    version: 1.0.0
```

```
.brickkit/artifacts/demo-caller-1-0-0/api-docs/openapi.json
.brickkit/artifacts/demo-hello-1-0-0/api-docs/openapi.json
.brickkit/manifests/demo-caller-1.0.0.yaml
.brickkit/manifests/demo-hello-1.0.0.yaml
```

`.brickkit/` 下**只有缓存**，没有备份——要退回这次 `add` 之前，用
[01 §1.3](01-初始化项目.md) 里的 `git checkout brickkit.yaml`。

注意 `demo-caller-1-0-0` 这个名字：**版本化服务名**（组件 ID 的 `/` 和版本里的 `.` 都换成 `-`）。它同时是容器名、K8s Service 名、产物目录名、环境变量里的地址——全平台一个名字。

### 常用参数

| 参数 | 作用 |
| --- | --- |
| `-y` / `--yes` | 不问确认，CI 里用 |
| `--repo` | 额外把该组件的 Git 仓库 clone 到 `components/`（仅开源组件） |
| `--repo-all` | 把所有递归依赖中的开源组件都 clone 下来 |
| `--local` | 把本地源里的组件一次全部添加（见下一节） |

## 2.3 一次把本地源里的组件全装上

本地开发时 `components/` 下往往躺着一批组件，一个个 `add` 很烦。

### ▶️ 操作

```bash
brickkit add --local
```

### ✅ 预期

```
🔍 从本地安装源 local-dev 扫到 10 个组件
⏭️ demo/caller@1.0.0 已在 brickkit.yaml 中
⏭️ demo/hello@1.0.0 已在 brickkit.yaml 中
📦 添加 auth/password-login@1.0.0
   ├── Manifest ✅
   ├── 依赖 department/tree@1.0.0 ✅ 已拉取（artifacts 2 个文件）
   ├── 弱依赖 infra/redis-event-bus@1.0.0 ✅ 已拉取（artifacts 1 个文件）
   ├── 依赖 people/basic@1.0.0 ✅ 已拉取（artifacts 2 个文件）
   └── artifacts ✅（1 个文件）
   （中间省略若干个）
✅ 已写入 brickkit.yaml（8 个组件）
```

2.2 里已经装过的两个静静跳过（`⏭️`），所以**新增的是 8 个**，配置里一共十个。
再跑一次会看到十行 `⏭️`，末尾是 `✅ brickkit.yaml 未变更（本地组件都已在配置中）`——
**这条命令是幂等的**，重复执行不会多出任何东西。

`component.yaml` 写坏了的目录会被**点名**跳过，不会从"扫到几个"里悄悄少掉一个
——否则你只会去翻安装源配置，而问题在自己刚写的那份文件里：

```
⚠️ demo/broken 跳过：metadata.version 不是精确版本：latest
   来自安装源 local-dev；修好它再执行一次 brickkit add --local
```

**任一组件解析失败会整体中止，`brickkit.yaml` 一个字节不动**——半份配置比没有配置更难收拾。

## 2.4 不要的关掉，而不是删掉

十个里有六个要到 [13-完整装配](13-完整装配.md) 才用得上。**先别删——关掉就行。**
把 `brickkit.yaml` 的整个 `components:` 段替换成下面这份：

```yaml
components:
  # ↓ 这四个是 03–08 要用的，留着
  - id: demo/hello
    version: 1.0.0
  - id: demo/caller
    version: 1.0.0
  - id: department/tree
    version: 1.0.0
  - id: people/basic
    version: 1.0.0
    enabled: true

  # ↓ 其余六个 13 才用得上，先关掉
  - id: auth/password-login
    version: 1.0.0
    enabled: false
  - id: authorization/rbac
    version: 1.0.0
    enabled: false
  - id: erp/backend
    version: 1.0.0
    enabled: false
  - id: portal/user-frontend
    version: 1.0.0
    enabled: false
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: false
  - id: infra/api-docs
    version: 1.0.0
    enabled: false
```

### ✅ 预期

```bash
brickkit up --dry-run
```

四个 `✅`、六个 `⬜`：

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             启动（demo/caller 需要）
   ✅ demo/caller@1.0.0            启动（顶层）
   ✅ department/tree@1.0.0        启动（people/basic 需要）
   ⬜ infra/redis-event-bus@1.0.0  显式禁用（enabled: false）
   ✅ people/basic@1.0.0           启动（enabled: true）
   ⬜ auth/password-login@1.0.0    显式禁用（enabled: false）
   ⬜ authorization/rbac@1.0.0     显式禁用（enabled: false）
   ⬜ erp/backend@1.0.0            显式禁用（enabled: false）
   ⬜ portal/user-frontend@1.0.0   显式禁用（enabled: false）
   ⬜ infra/api-docs@1.0.0         显式禁用（enabled: false）
```

### 为什么只有 `people/basic` 要写 `enabled: true`

这是**唯一一处**你现在需要知道的例外，剩下的留给 [04](04-组件开启模式.md)。

判定规则一句话：**跟着上层走**——顶层默认跑，下层只要还有一个上层在跑就跑。

| 写法 | 含义 |
| --- | --- |
| **不写** | 跟着上层走。上层全不跑，它也不跑 |
| `enabled: true` | 一定跑，不看上层 |
| `enabled: false` | 一定不跑，依赖它的组件跟着不跑 |

`people/basic` 不是顶层——依赖它的是 `erp/backend` 那几个，而它们刚被你关掉了。
上层全不跑，它就跟着不跑，输出会是 `⬜ people/basic@1.0.0  不启动（上层都不启动）`。
写 `enabled: true` 就是把它单独留下来。

**`department/tree` 不用写。** 它被 `people/basic` 依赖，上一行留下来了，
它就跟着回来——所以它那行的理由写的是 `启动（people/basic 需要）`。
你不需要把整条链一个个钉住，钉最上面那个就够了。

不信可以把那行 `enabled: true` 删掉再 `brickkit up --dry-run` 一次，然后加回来。
**这个"想当然"正是 [04](04-组件开启模式.md) 整篇要讲的东西。**

## 2.5 整理源码工作区（`brickkit sync`）

`components/` 下每个组件都是一个**独立的 Git 仓库**。项目大了以后，那些当前根本不启动的组件源码还堆在那儿，IDE 索引、全局搜索、`grep -r`、以及替你读代码的 AI 都得连它们一起扫（`git status` 不受影响——`components/` 在 `.gitignore` 里）。

`brickkit sync` 按 `brickkit up` **同一套判定**把它们**双向**整理：这次不启动的移进 `components/.archived/`，重新启用的再移回来。

### ▶️ 操作

刚才关掉了六个，正好可以看它怎么动：

```bash
brickkit sync
```

### ✅ 预期

```
📂 工作区整理：
   📦 components/auth/password-login/      → components/.archived/auth/password-login
      原因：显式禁用（enabled: false）
   📦 components/authorization/rbac/       → components/.archived/authorization/rbac
      原因：显式禁用（enabled: false）
   ✅ components/demo/caller/              活跃
   ✅ components/demo/hello/               活跃
   ✅ components/department/tree/          活跃
   📦 components/erp/backend/              → components/.archived/erp/backend
      原因：显式禁用（enabled: false）
   📦 components/infra/api-docs/           → components/.archived/infra/api-docs
      原因：显式禁用（enabled: false）
   📦 components/infra/redis-event-bus/    → components/.archived/infra/redis-event-bus
      原因：显式禁用（enabled: false）
   ✅ components/people/basic/             活跃
   📦 components/portal/user-frontend/     → components/.archived/portal/user-frontend
      原因：显式禁用（enabled: false）
✅ 工作区整理完成（4 个活跃，6 个归档，0 个激活）
```

`components/` 下现在只剩四个目录：

```bash
find components -maxdepth 2 -mindepth 2 -type d | sort
```

```
components/.archived/auth
components/.archived/authorization
components/.archived/erp
components/.archived/infra
components/.archived/portal
components/demo/caller
components/demo/hello
components/department/tree
components/people/basic
```

**这就是"50 个组件不会失控"的那一半答案**：配置里有十个，你的 IDE 里只有四个。
`.archived` 以 `.` 开头，文件管理器与多数编辑器默认不显示它。

### 反过来：改回去再 sync 一次

把 `infra/redis-event-bus` 的 `enabled: false` 改成 `true`，再 `brickkit sync`：

```
📂 工作区整理：
   ✅ components/demo/caller/              活跃
   ✅ components/demo/hello/               活跃
   ✅ components/department/tree/          活跃
   📂 components/.archived/infra/redis-event-bus → components/infra/redis-event-bus/
      原因：恢复启用
   ✅ components/people/basic/             活跃
✅ 工作区整理完成（4 个活跃，0 个归档，1 个激活）
```

**它是双向的**，不是单向的归档工具。判断依据和 `brickkit up` 是同一套启停判定。

### 四条要记住的规则

| 规则 | 说明 |
| --- | --- |
| **不影响运行中的容器** | sync 只动目录。容器还在跑的时候 sync，容器一个都不会动——要停请用 `brickkit down` |
| **不集成在 `up` 里** | 纯独立命令，什么时候整理由你决定 |
| **只动 brickkit.yaml 里声明过的组件** | `components/` 下你正在开发、还没 `add` 进来的组件**不受影响** |
| **没有 `--dry-run`** | 搞错了再执行一次就回来了 |

`.git` 是整个目录一起搬走的，归档之后 `git status`、`git log`、提交推送全都照常。

⏹️ **怎么撤销：** 把配置改回去再 `brickkit sync` 一次。

> 💡 **`sync` 没有任何参数。** 留哪些、归档哪些完全由 `brickkit.yaml` 的 `enabled` 决定，
> 与 `brickkit up` 是同一套判定——不会出现"目录里看不到的组件正在跑"。
> 想收窄范围就改 `enabled`（关顶层最省事），`sync` 跟着走。见 [04](04-组件开启模式.md)。

## 2.6 移除组件

`remove` 的语义是"**彻底**移除"：配置、Manifest 缓存、artifacts、源码目录，一起清掉。

### ▶️ 先试一个会被拦下来的

```bash
brickkit remove people/basic@1.0.0
```

```
❌ 无法移除 people/basic
   版本：1.0.0
   以下组件强依赖它：auth/password-login@1.0.0、authorization/rbac@1.0.0、erp/backend@1.0.0
   建议：请先移除依赖方
```

**注意那三个依赖方现在都是 `enabled: false`。** 关掉不等于不存在——它们还在
`brickkit.yaml` 里，配置一改回来就要用到 `people/basic`。`remove` 看的是**声明**，
不是"这次跑不跑"，所以照样拦。

### ▶️ 再移除一个没人依赖的

`infra/api-docs` 弱依赖别人，没有人依赖它：

```bash
brickkit remove infra/api-docs@1.0.0
```

```
✅ 已移除 infra/api-docs@1.0.0
   🗑️ 已删除归档源码目录 components/.archived/infra/api-docs
   🗑️ 已清理 Manifest 缓存
```

**它删的是 `.archived/` 里那一份** —— 上一步 sync 刚把它归档进去。这一条很要紧：
`sync` 只整理 `brickkit.yaml` 里还在的组件，组件一旦被 `remove`，sync 就再也不认识它了。
归档目录里那份源码不在这里清掉，就成了永远没人回收的孤儿——而 `.archived` 是隐藏目录，
比普通的僵尸目录更难被发现。

### 两条容易踩的

| 情况 | 行为 |
| --- | --- |
| 多版本共存时不指定版本 | 报错，要求你写明 `<id>@<版本>` |
| 移除后它的依赖怎么办 | **留在配置里**（可能别人也在用）。要一起清掉就再 `remove` 一次 |

## ⏹️ 怎么停

这一节只读写文件，没有任何进程与容器。

| 想做的 | 命令 |
| --- | --- |
| 撤销刚才那一步 `add` / `remove` | `git checkout brickkit.yaml` |
| 只撤销其中一处改动 | `git checkout -p brickkit.yaml` |
| 连试验场一起重来 | `./试用指南/准备.sh --reset` |
| 直接跳到 03 的起点 | `./试用指南/准备.sh --baseline` |

前两条只动 `brickkit.yaml`，不碰缓存与源码目录；后两条重建整个试验场。
