# 13 · 完整装配（八个组件）

🎯 **这一节验证什么：** 用一条 `brickkit add` 拉出整棵依赖树，一条 `brickkit up`
把八个组件全起来，然后在浏览器里走完 登录 → 查订单 → 审批。

前置：`./试用指南/准备.sh --images`（[00](00-准备.md)）——试验场里要有十个组件的源码，
镜像也构建好；本篇第一步会把源码 `cp` 进一个新建的 `erp-demo` 项目；
Docker 可用，并且**基础资源已经跑着**（[05 §5.1](05-Docker启动全流程.md)：
`docker compose -f deploy/dev-resources/docker-compose.yaml up -d`）。
这一节不需要 minikube，也不需要市场。

> 前面 01–11 讲的是**单个能力**（怎么 add、怎么 up、怎么调试）。
> 这一节是把它们放在一起看：一个真实项目长什么样。

---

## 这八个组件是什么关系

```
portal/user-frontend (nginx)          ← 浏览器只认识它
      ↓ 强依赖
erp/backend (连接组件)
      ├── ↓ 强依赖 → people/basic (Python)
      │        └── ↓ 强依赖 → department/tree (Go)
      ├── ↓ 强依赖 → auth/password-login
      ├── ↓ 强依赖 → authorization/rbac  ←── Redis（当**加速器**）
      └── ↓ 弱依赖 → infra/redis-event-bus ←── Redis（当**数据源**）

infra/api-docs                        ← 谁也不依赖它，它弱依赖所有人
```

值得先记住的三件事，后面每一步都会用到：

| | |
| --- | --- |
| **强依赖** | 取不到就不启动。`erp/backend` 少了 `auth` 就干不了活 |
| **弱依赖** | 有就用、没有就降级。事件总线不在，审批照样成功 |
| **同一个 Redis，两种角色** | `rbac` 拿它当缓存（挂了回源查库），`event-bus` 拿它当存储（挂了就 503） |

## 13.1 建项目

### ▶️ 操作

```bash
export PATH="<仓库>/试用指南/bin:$PATH"     # 00-准备.md 里那一行
cd 试用指南/playground

mkdir -p ../erp-demo && cd ../erp-demo
cp -r ../playground/components .           # 八个组件的源码
brickkit init erp-demo                     # 骨架自带指向 ./components 的本地源
```

`init` 已经把 `project` / `deploy` / `sources` / 空的 `components` 都写好了，
`components` 留空是对的——下一步让 CLI 自己填。你只要把骨架末尾那行
`resources: []` **替换成**下面这段：

```yaml
# 注意：brickkit.yaml **没有** apiVersion 字段（003 §2）。
# apiVersion 是组件 Manifest（component.yaml）才有的东西——
# 写进来的话，CLI 会当成未知字段直接报错
resources:
  - id: pg
    kind: database
    engine: postgresql
    host: host.docker.internal   # ⚠️ 资源跑在本机时就写这个，见下面的坑
    port: 5432
    username: postgres        # ⚠️ 是 username 不是 user，见下面的坑
    password: q
    bindings: []              # ← 下一步再填

  - id: redis
    kind: cache
    engine: redis
    host: host.docker.internal
    port: 6379
    bindings: []
```

### ⚠️ 两个真踩过的坑

**① `host` 要写 `host.docker.internal`，不是裸服务名。** 平台**不部署基础资源**
（006 §10.1），所以 `host: postgres` 不会换来一个叫 `postgres` 的容器——
容器里解析不了这个名字，表现是启动之后才出现的 `no such host`。CLI 会在生成阶段
先警告一句，但改对了才不会撞上。

资源跑在本机时写 `host.docker.internal`：平台会为绑定它的容器（含迁移容器）
自动补上 `extra_hosts`，`local: true` 的组件在 env 文件里则换成 `localhost`。

**② 字段是 `username`，不是 `user`。** 写错的话 CLI 会当场拦下并猜出你想写的：

```
❌ 错误：brickkit.yaml 校验失败
   文件：brickkit.yaml
   resources[0].user：未知字段（第 51 行），是不是想写 username？
```

> 这条检查是**这一节写出来的时候补的**。在那之前 CLI 会静默忽略拼错的字段，
> 等组件启动才报"缺少 DATABASE_USER（这些变量由平台按资源绑定注入）"——
> 一句把**配置笔误**指向**平台**的错误。使用者会去查注入引擎、查资源绑定、
> 查组件代码，唯独不会想到自己少打了三个字母。

### ⏹️ 怎么停

还没起任何东西，直接删目录即可。

### ▶️ 操作

```bash
brickkit add portal/user-frontend@1.0.0
```

### ✅ 预期

```
📦 添加 portal/user-frontend@1.0.0
   ├── Manifest ✅
   ├── 依赖 department/tree@1.0.0 ✅ 已拉取（artifacts 2 个文件）
   ├── 弱依赖 infra/redis-event-bus@1.0.0 ✅ 已拉取（artifacts 1 个文件）
   ├── 依赖 people/basic@1.0.0 ✅ 已拉取（artifacts 2 个文件）
   ├── 依赖 auth/password-login@1.0.0 ✅ 已拉取（artifacts 1 个文件）
   ├── 依赖 authorization/rbac@1.0.0 ✅ 已拉取（artifacts 2 个文件）
   └── 依赖 erp/backend@1.0.0 ✅ 已拉取（artifacts 1 个文件）
✅ 已写入 brickkit.yaml（7 个组件）
📁 已下载 artifacts 到 .brickkit/artifacts/（9 个文件）
```

**你只说了一个组件，CLI 把 7 个都写进了 brickkit.yaml。** 弱依赖也标出来了 ——
它被写进配置，但下一步你会看到它**不会自动启动**。

顺便看看拿到了什么：

```bash
find .brickkit/artifacts -type f | sed 's|^|  |'
```

那些 `.proto` 与 `openapi.json` 就是"契约即产物"（002 §7）：
调用方靠它们生成客户端代码，不需要读对方的源码。

### ⏹️ 怎么停

`brickkit remove portal/user-frontend@1.0.0`，或 `git checkout brickkit.yaml` 撤销这次改动。

## 13.3 补上资源绑定与密钥

`add` 只管依赖，**不会替你决定哪个组件用哪个库** —— 那是你的部署决策。

### ▶️ 操作

编辑 `brickkit.yaml`：

```yaml
components:
  # ... add 写进来的 7 个 ...
  - id: auth/password-login
    version: 1.0.0
    config:
      jwtSecret: ${JWT_SECRET}      # ← 从 .env 引用，不写进 Git

  - id: portal/user-frontend
    version: 1.0.0
    expose: true                    # ← 唯一需要被浏览器访问的
    exposePort: 18080

resources:
  - id: pg
    # ...
    bindings:
      - componentId: department/tree
        database: erp_department
      - componentId: people/basic
        database: erp_people
      - componentId: auth/password-login
        database: erp_auth
      - componentId: authorization/rbac
        database: erp_rbac

  - id: redis
    # ...
    bindings:
      # 同一个 Redis，两个组件，两种角色
      - componentId: authorization/rbac
      - componentId: infra/redis-event-bus
```

建 `.env`（**不进 Git**）：

```bash
echo 'JWT_SECRET=this-is-a-demo-secret-at-least-32b' > .env
```

### 为什么密钥要这么绕一圈

`auth/password-login` 需要一个签名密钥。BrickKit **没有**组件级的 `env` 或
`secrets` 字段 —— 唯一能给组件传值的通道是 `config`（映射组件的 `configSchema`）。

所以组件在 `configSchema` 里声明了 `jwtSecret`，而且**故意没有默认值**：
有默认值就意味着所有装了这个组件的人共用同一把钥匙，任何人都能给任何一处部署
签出管理员令牌，而且看起来一切正常。

`${JWT_SECRET}` 从 `.env` 取值（006 §3：密钥必须通过环境变量引用）。

## 13.4 起来

### ▶️ 操作

```bash
brickkit up
```

第一次会失败，而且**是故意的**：

```
📌 以下基础资源需要先跑起来（平台不代为部署，见 006 §9.1）：
   pg      postgresql   host.docker.internal:5432  供 auth/password-login、... 使用
      需要库 erp_auth（供 auth/password-login 使用）：CREATE DATABASE "erp_auth";
      ...
```

建库要 `CREATEDB` 权限，且必须先连到另一个库；云数据库上应用账号通常没这个权限 ——
**代建会造成"开发能跑、生产必炸"**。所以库由人建，库名由平台注入。

照它说的建（用你自己的库就换成自己的连法）：

```bash
for db in erp_department erp_people erp_auth erp_rbac; do
  docker exec brickkit-dev-resources-postgres-1 \
    psql -U postgres -c "CREATE DATABASE \"$db\";"
done

brickkit up
```

### ✅ 预期

```
🔧 启动前会执行的数据库迁移（失败则该组件不会启动）：
   department/tree@1.0.0  /app/department-tree migrate
   people/basic@1.0.0  python -m app.main migrate
   auth/password-login@1.0.0  /app/auth-password-login migrate
   authorization/rbac@1.0.0  /app/authorization-rbac migrate

🐳 正在启动（docker）...
   department-tree-1-0-0        running（healthy）
   infra-redis-event-bus-1-0-0  running（healthy）
   people-basic-1-0-0           running（healthy）
   auth-password-login-1-0-0    running（healthy）
   authorization-rbac-1-0-0     running（healthy）
   erp-backend-1-0-0            running（healthy）
   portal-user-frontend-1-0-0   running（healthy）
✅ 全部组件已启动（7 个）
```

**7 个，一个不少。** 你在 brickkit.yaml 里写了 7 个组件，7 个都跑起来了 ——
包括那个只被弱依赖指着的 `infra/redis-event-bus`，下一节说它。

### ⏹️ 怎么停

```bash
brickkit down    # 停容器；数据卷保留
```

只想停其中几个：给它们写 `enabled: false` 再 `brickkit up`（[04](04-组件开启模式.md)）。

## 13.5 那个弱依赖也跑起来了

### ▶️ 操作

```bash
brickkit status
```

`infra/redis-event-bus` 在运行中的表里，和其余六个并列。

**这一点值得停一下：** 它只被 `people/basic` 和 `erp/backend` **弱**依赖，
没有任何组件强依赖它，它自己也不是顶层。它照样跑。

弱依赖管的是"**连不上怎么办**"，不是"**要不要装**"：

| | 强依赖 | 弱依赖 |
| --- | --- | --- |
| 上层在跑时，它跑吗 | 跑 | **一样跑** |
| 它没在跑时，上层怎么样 | 跟着不跑（钉住则报错） | 照常跑，只是拿不到 `*_ENDPOINT`，自己降级 |

你 `add erp/backend` 的时候它就被写进配置了（[02](02-添加与移除组件.md)）——
装了就该跑，否则一个装好的系统有一半功能是哑的，而没有任何一处告诉你为什么。

**嫌它多余就关掉：** 给它写一行 `enabled: false`。`up --dry-run` 的输出里
那一行 `只被弱依赖引用（关掉不影响别人：enabled: false）` 给的正是这份名单——
关掉它们不会连累任何人。关掉之后再看 `erp/backend`：它照常跑，只是发不出事件。

## 13.6 在浏览器里走一遍

### ▶️ 操作

打开 <http://localhost:18080>，或者用 curl：

```bash
# 登录：门户 → erp/backend → auth/password-login → people/basic
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"demo-password"}' \
  http://localhost:18080/api/v1/login
```

```bash
TOKEN=$(curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"demo-password"}' \
  http://localhost:18080/api/v1/login | python3 -c "import json,sys;print(json.load(sys.stdin)['token'])")

# 查订单：erp/backend 先问 rbac 有没有权限，再用 gRPC 向 people 补全姓名
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:18080/api/v1/orders
```

### ✅ 预期

```json
{"personId":"p-001","sessionTtlSeconds":3600,"token":"eyJhbGciOi...","username":"zhangsan"}
```

```
o-1  服务器采购  张三/技术中心  pending
o-2  差旅报销    张三/技术中心  pending
o-3  培训费用    赵六/后端组    pending
```

**一次查询串起了五个组件。** 姓名和部门不是 `erp/backend` 存的 ——
它只存 `ownerId`，姓名每次通过 gRPC（9090 端口，来自 `people/basic` 声明的
`extraPorts`）现取。这样人员改了名，这里不会留一份对不上的旧数据。

### 换个没权限的人试试

```bash
T4=$(curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"zhaoliu","password":"demo-password"}' \
  http://localhost:18080/api/v1/login | python3 -c "import json,sys;print(json.load(sys.stdin)['token'])")

curl -s -w "\nHTTP %{http_code}\n" -H "Authorization: Bearer $T4" http://localhost:18080/api/v1/orders
```

```
{"error":"没有权限：erp.order.read"}
HTTP 403
```

**403 不是 401。** 401 是"我不知道你是谁"，403 是"我知道你是谁，但你不能做这个" ——
混在一起会让人去反复重新登录，而登录一百次也不会有权限。

## 13.7 弱依赖降级：审批一次看看

### ▶️ 操作

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:18080/api/v1/orders/o-1/approve
```

### ✅ 预期

```json
{"approvedBy":"p-001","eventPublished":false,"orderId":"o-1","status":"approved"}
```

**审批成功了，但 `eventPublished: false`** —— 事件总线没启动（13.5），
所以事件没发出去。但业务照常完成，订单状态确实变成了 `approved`：

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:18080/api/v1/orders \
  | python3 -c "
import json,sys
for o in json.load(sys.stdin)['orders']: print(' ', o['id'], o['status'])"
```

这就是弱依赖降级的完整含义：**不是"接口返回 200 就行"，而是业务状态确实变了**。
若审批在发事件失败时回滚，弱依赖就成了事实上的强依赖。

同时它**如实告诉你事件没发出去**，没有假装发了。

## 13.8 把弱依赖打开

### ▶️ 操作

```yaml
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: true          # ← 只被弱依赖引用的组件，要它就得显式打开
```

```bash
brickkit up
```

再审批一单：

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:18080/api/v1/orders/o-2/approve
```

### ✅ 预期

```json
{"approvedBy":"p-001","eventPublished":true,"orderId":"o-2","status":"approved"}
```

事件真的落进了 Redis Stream：

```bash
docker exec brickkit-erp-demo-redis-1 redis-cli XLEN brickkit:events
# 1
docker exec brickkit-erp-demo-redis-1 redis-cli XREVRANGE brickkit:events + - COUNT 1
# ... type erp.order.approved  actor p-001  subject o-2 ...
```

**同一个 Redis 容器，两个组件在用它，角色完全不同：**

| 组件 | Redis 是什么 | Redis 挂了会怎样 |
| --- | --- | --- |
| `authorization/rbac` | **加速器** | 照常回源查库，只是慢一点 |
| `infra/redis-event-bus` | **唯一的数据源** | 503，绝不假装收下事件 |

13 节会让你亲手把它停掉验证这一点。

## 13.9 config 覆盖

### ▶️ 操作

`erp/backend` 的 `configSchema` 里 `sessionTtlSeconds` 默认是 3600。覆盖它：

```yaml
  - id: erp/backend
    version: 1.0.0
    config:
      sessionTtlSeconds: 7200
```

```bash
brickkit up
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"demo-password"}' \
  http://localhost:18080/api/v1/login | python3 -c "import json,sys;print(json.load(sys.stdin)['sessionTtlSeconds'])"
```

### ✅ 预期

```
7200
```

驼峰转成大写下划线注入：`sessionTtlSeconds` → `SESSION_TTL_SECONDS=7200`（003 §5.4）。
不覆盖的配置项用 `configSchema` 里的默认值；**既没默认值也没覆盖的项完全不注入** ——
注入空串会让组件以为"配置过了但值是空的"。

看看真的注进去了：

```bash
grep -A 20 "erp-backend-1-0-0:" .brickkit/generated/docker-compose.yaml | grep SESSION
```

## 13.10 全部停掉

### ▶️ 操作

```bash
brickkit down
```

### ✅ 预期

```
✅ 已停止 8 个组件
```

### ⚠️ `down` 不会删数据卷

这是**有意的**（`brickkit down --help` 里就写着）：数据库里的数据始终保留，
下次 `up` 还在。一条命令就把生产数据抹掉，代价太大。

要彻底清理得自己动手：

```bash
docker compose -p brickkit-erp-demo down -v
```

确认没有残留：

```bash
docker ps -a --filter name=brickkit-erp-demo
docker volume ls | grep brickkit-erp-demo
```
