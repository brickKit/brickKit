# 08 · 升级与多版本共存

🎯 **这一节验证什么：** 改一个版本号就是升级；同一个组件的两个版本可以同时跑。

前置：05 做完（Docker 跑得起来）。

---

## 8.1 升级 = 改版本号

BrickKit **没有 `upgrade` 命令**。`brickkit.yaml` 里的版本号就是声明，改了它再 `up` 就是升级。

### ▶️ 操作

本地源里 `demo/hello` 只有一份 `component.yaml`，先把它升到 2.0.0（镜像本机已经有了）：

```bash
sed -i 's/^  version: 1.0.0$/  version: 2.0.0/' components/demo/hello/component.yaml
sed -i 's|brickkit-demo/hello:1.0.0|brickkit-demo/hello:2.0.0|' components/demo/hello/component.yaml
```

再在 `brickkit.yaml` 里把 `demo/hello` 的版本改成 `2.0.0`：

```yaml
components:
  - id: demo/hello
    version: 2.0.0        # ← 1.0.0 改成 2.0.0
```

```bash
brickkit up --dry-run
```

### ✅ 预期

```
⬆️ 检测到版本变更（升级流程，004 §3.5.1）：
   demo/hello: 1.0.0 → 2.0.0
```

CLI 自动做了这些：拉新版本的 Manifest 与产物、跑兼容性检查（强依赖能不能满足、资源绑没绑、会不会成环）、**保留旧版本的产物**。

> **CLI 是无状态的**，它不记得"上次装的是哪个版本"。判据是"**这个版本在本地有没有**"——本地没有就说明是新的。

---

## 8.2 升级不会自动改调用方

### ✅ 预期（接着上一步）

```
📋 组件状态计算：
   ✅ demo/hello@2.0.0       根组件（没有其他组件依赖它）
   ✅ demo/hello@1.0.0       被 demo/caller 依赖
   ✅ demo/caller@1.0.0      根组件（没有其他组件依赖它）
```

**两个版本同时在。** 因为：

- 你在 `brickkit.yaml` 里要了 `demo/hello@2.0.0`
- `demo/caller@1.0.0` 的 `component.yaml` 里**写死**依赖 `demo/hello@1.0.0`

依赖是写死版本的，**升级一个组件不会悄悄把它的调用方切到新版本上**——那等于替调用方做了兼容性决定。1.0.0 从 Manifest 缓存里取（升级时旧版本产物刻意保留）。

真跑一下：

```bash
brickkit up
brickkit status
```

```
 │ demo/hello      │ 1.0.0 │ 运行中（healthy） │
 │ demo/caller     │ 1.0.0 │ 运行中（healthy） │
 │ demo/hello      │ 2.0.0 │ 运行中（healthy） │
```

两个 `demo/hello` 是**两个独立容器**：服务名带版本（`demo-hello-1-0-0` / `demo-hello-2-0-0`），天然不冲突。环境变量也各指各的。

### 要让调用方也升级怎么办

改 `demo/caller` 自己的 `component.yaml`，把依赖改成 `demo/hello@2.0.0`，然后给 caller 发一个新版本。**这是组件作者的决定，不是平台的。**

## 8.3 升级会被拦下来的情形

`brickkit up --dry-run` 在这些情况下会**在启动前**报错，而不是让你部署上去再炸：

| 情形 | 行为 |
| --- | --- |
| 新版本新增了一个装不到的强依赖 | ❌ 报错 |
| 新版本新增了资源依赖，但 `brickkit.yaml` 里没绑定 | ❌ 报错 |
| 新版本引入循环依赖 | ❌ 报错 |
| 新版本新增了弱依赖，装不到 | ⚠️ 警告，继续 |
| 新版本新增了配置项 | 用新的默认值 |
| 新版本删了配置项，但你的 `config:` 里还写着 | 静默忽略，不注入 |

自己造一个试试：给 `components/demo/hello/component.yaml` 加一条依赖 `demo/nothing@9.9.9`，然后 `brickkit up --dry-run`。

---

## 8.4 回滚

把版本号改回去，再 `brickkit up`。旧版本的产物一直在 `.brickkit/artifacts/` 里，不需要重新下载。

## 8.5 ⚠️ K8s 上升级会留下旧版本（已知缺陷）

**这一节前面的所有操作都是在 Docker 下做的。换成 `deploy.target: k8s`，
升级的行为不一样——而且不一样的地方是个缺陷。**

Docker 下 `brickkit up` 会把不在本次部署清单里的旧容器一并清掉
（compose 的 `--remove-orphans`）。K8s 下**没有这个机制**，
而 `kubectl apply` 默认不会删目录里没有的资源。

### 现象（已在 minikube 上实测）

把版本从 1.0.0 改成 2.0.0，再 `brickkit up`：

```
✅ 全部组件已启动（1 个）
```

```bash
kubectl get deployment -n <你的命名空间>
```

```
demo-hello-1-0-0   1/1   ← 旧版本还在跑，没人管了
demo-hello-2-0-0   1/1
```

更麻烦的两点：

| 现象 | 后果 |
| --- | --- |
| `brickkit status` 只报新版本 | **孤儿完全不可见**，只有 kubectl 才找得到 |
| `brickkit down` 报"已停止全部组件"而旧版本照样在跑 | 这是**永久泄漏**——BrickKit 再也不会碰它 |

### 在修好之前怎么办

升级之后手工确认一次，多出来的用 kubectl 删掉：

```bash
# 本项目在集群里实际有什么
kubectl get deployment,service -n <命名空间> -l brickkit.io/project=<项目名>

# 确认某个是旧版本残留后
kubectl delete deployment,service,networkpolicy,serviceaccount \
  -n <命名空间> -l app=demo-hello-1-0-0
```

注意 `-l app=<版本化服务名>`——**按版本化服务名删**，不要按组件名，
否则会把正在用的新版本一起删掉。

> 同样的泄漏也发生在**把组件从 `brickkit.yaml` 里删掉**的时候，不只是升级。
> 登记为 **P38**，修法是 `up` 之后按 `brickkit.io/project` 标签比对集群实际资源
> 与本次期望集合，删掉多余的。

## ⏹️ 怎么停

```bash
brickkit down
```

恢复这一节改动的组件：

```bash
cd <仓库根目录>
cp tests/components/demo-hello/component.yaml 试用指南/playground/components/demo/hello/component.yaml
```

再把 `brickkit.yaml` 里的版本号改回 `1.0.0`。或者干脆重来：

```bash
./试用指南/准备.sh --reset
```
