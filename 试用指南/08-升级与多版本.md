# 08 · 升级与多版本共存

🎯 **这一节验证什么：** 改一个版本号就是升级；同一个组件的两个版本可以同时跑。

前置：[05](05-Docker启动全流程.md) 做完（Docker 跑得起来）。
本篇要用 `brickkit-demo/hello:2.0.0` 镜像，它由 `./试用指南/准备.sh --images` 一并构建。

---

## 8.1 升级 = 改版本号

BrickKit **没有 `upgrade` 命令**。`brickkit.yaml` 里的版本号就是声明，改了它再 `up` 就是升级。

### ▶️ 操作

本地源里 `demo/hello` 只有一份 `component.yaml`，先把它升到 2.0.0（镜像本机已经有了）：

```bash
sed -i 's/^  version: 1.0.0$/  version: 2.0.0/' components/demo/hello/component.yaml
sed -i 's|brickkit-demo/hello:1.0.0|brickkit-demo/hello:2.0.0|' components/demo/hello/component.yaml
```

再在 `brickkit.yaml` 里把 `demo/hello` 的版本改成 `2.0.0`：

```yaml
components:
  - id: demo/hello
    version: 2.0.0        # ← 1.0.0 改成 2.0.0
```

```bash
brickkit up --dry-run
```

### ✅ 预期

```
⬆️ 检测到版本变更（004 §3.5.1）：
   demo/hello: 1.0.0 → 2.0.0
```

CLI 为此做的只有两件事：**拉新版本的 Manifest 与产物**，以及**保留旧版本的产物**（回滚要用）。

> **没有"升级路径"这回事。** 上面那行 `⬆️` 是一条**说明**，不是一道关卡——
> 它告诉你这次跑的 image 换了。改完版本号之后，CLI 看到的就是一份普通的
> `brickkit.yaml`，走的是和平时一模一样的解析：拉依赖图 → 算启动顺序 →
> 生成部署文件。新版本要是缺了强依赖、少了资源绑定、或者成了环，
> 会被**那套日常检查**拦下来（见 8.3），而不是被某个专门查升级的东西拦下来。
>
> 这不是省事，是**少一套要维护的逻辑**：专门的升级校验意味着"升级时"和
> "平时"两条路可能给出不同结论，而那两条路迟早会分叉。

> **CLI 是无状态的**，它不记得"上次装的是哪个版本"。判据是"**这个版本在本地有没有**"——本地没有就说明是新的。

## 8.2 升级不会自动改调用方

### ✅ 预期（接着上一步）

```
📋 组件状态计算：
   ✅ demo/hello@2.0.0             启动（顶层）
   ✅ demo/hello@1.0.0             启动（demo/caller 需要）
   ✅ demo/caller@1.0.0            启动（顶层）
   ✅ department/tree@1.0.0        启动（people/basic 需要）
   ✅ infra/redis-event-bus@1.0.0  启动（people/basic 需要）
   ✅ people/basic@1.0.0           启动（顶层）
```

**两个版本同时在。** 因为：

- 你在 `brickkit.yaml` 里要了 `demo/hello@2.0.0`
- `demo/caller@1.0.0` 的 `component.yaml` 里**写死**依赖 `demo/hello@1.0.0`

依赖是写死版本的，**升级一个组件不会悄悄把它的调用方切到新版本上**——那等于替调用方做了兼容性决定。1.0.0 从 Manifest 缓存里取（升级时旧版本产物刻意保留）。

真跑一下：

```bash
brickkit up
brickkit status
```

```
 │ demo/hello      │ 1.0.0 │ 运行中（healthy） │
 │ demo/caller     │ 1.0.0 │ 运行中（healthy） │
 │ demo/hello      │ 2.0.0 │ 运行中（healthy） │
```

两个 `demo/hello` 是**两个独立容器**：服务名带版本（`demo-hello-1-0-0` / `demo-hello-2-0-0`），天然不冲突。环境变量也各指各的。

### 要让调用方也升级怎么办

改 `demo/caller` 自己的 `component.yaml`，把依赖改成 `demo/hello@2.0.0`，然后给 caller 发一个新版本。**这是组件作者的决定，不是平台的。**

## 8.3 换了版本之后会被拦下来的情形

`brickkit up --dry-run` 在这些情况下会**在启动前**报错，而不是让你部署上去再炸。

注意这张表里没有一条是"升级专属"的——**换个版本号只是让新 Manifest 参与了
日常那套解析**，下面每一条对第一次 `add` 一个组件同样成立：

| 情形 | 行为 |
| --- | --- |
| 新版本新增了一个装不到的强依赖 | ❌ 报错 |
| 新版本新增了资源依赖，但 `brickkit.yaml` 里没绑定 | ❌ 报错 |
| 新版本引入循环依赖 | ❌ 报错 |
| 新版本新增了弱依赖，装不到 | ⚠️ 警告，继续 |
| 新版本新增了配置项 | 用新的默认值 |
| 新版本删了配置项，但你的 `config:` 里还写着 | ⚠️ 警告，不注入（那一行从此不起作用，可以清掉） |

自己造一个试试：给 `components/demo/hello/component.yaml` 加一条依赖 `demo/nothing@9.9.9`，然后 `brickkit up --dry-run`。

---

## 8.4 回滚

把版本号改回去，再 `brickkit up`。旧版本的产物一直在 `.brickkit/artifacts/` 里，不需要重新下载。

---

## 8.5 K8s 上旧版本会被自动清掉

Docker 下 `brickkit up` 会把不在本次部署里的旧容器一并清掉
（compose 的 `--remove-orphans`）。K8s 下 **CLI 自己做同一件事**——
因为 `kubectl apply` 只创建和更新，**不会删**目录里没有的资源。

### ▶️ 操作

`deploy.target: k8s` 的项目里，把版本从 1.0.0 改成 2.0.0，然后 `brickkit up`。

### ✅ 预期

```
🧹 已清理旧版本残留（2 项）：
   - deployment.apps/demo-hello-1-0-0
   - service/demo-hello-1-0-0
   它们带着本项目的标签，但不在本次部署范围内
   demo-hello-2-0-0             running（healthy）
✅ 全部组件已启动（1 个）
```

```bash
kubectl get deployment -n <命名空间>
```

只剩 `demo-hello-2-0-0`。

### 两件值得知道的事

| | 为什么 |
| --- | --- |
| **清理发生在新版本就绪之后** | 顺序反了的话，新版本还没起来就把旧的删了，中间有一段谁都服务不了——升级会从"无感知"变成"短暂 502" |
| **只清带本项目标签的东西** | 按 `brickkit.io/project=<项目名>` 收窄。同一个命名空间里别人的服务碰都不碰 |

删掉的东西**一定会打印出来**。如果你只是误删了 `brickkit.yaml` 里的一行、
本意并非下线那个组件，这几行输出是你唯一的线索。

> 同样的清理也适用于**把组件从 `brickkit.yaml` 里删掉**的情形，不只是升级。

## 8.6 先看清楚这次升级会改什么：`--dry-run`

改完版本号，别急着 `up`。先问一句"这次到底会变什么"：

```bash
brickkit up --dry-run
```

你手上这次升级（`demo/hello` 1.0.0 → 2.0.0）除了版本号什么都没改，所以六项全是"无"：

```
📋 版本变更摘要：
   demo/hello: 1.0.0 → 2.0.0
   ├── 依赖变更：无
   ├── 新增配置项：无
   ├── 删除配置项：无
   ├── 数据库迁移：无
   ├── artifacts 变更：无
   ├── 资源配额变更：无
   └── 旧版本产物：保留（调用方可能仍指向旧版本）
```

**换一个真的改了不少东西的升级，同样六项会长成这样**（下面这段是示意，不是你会看到的输出）：

```text
📋 版本变更摘要：
   demo/hello: 1.0.0 → 1.1.0
   ├── 依赖变更：无
   ├── 新增配置项：enableNotification（默认 true）
   ├── 删除配置项：无
   ├── 数据库迁移：/app/hello migrate
   ├── artifacts 变更：无
   ├── 资源配额变更：requests cpu 50m/内存 32Mi，limits cpu 200m/内存 128Mi
                    → requests cpu 50m/内存 32Mi，limits cpu 500m/内存 256Mi
   └── 旧版本产物：保留（调用方可能仍指向旧版本）
```

**六项固定都出，没变化的写"无"。** 藏起来的话，你分不清是"这一项没变"
还是"平台压根没检查这一项"——而这两件事该做的下一步完全不同。

### 每一行为什么值得看

| 行 | 看它是为了什么 |
| --- | --- |
| 依赖变更 | 新版本多依赖一个组件 = 这次升级会**多起一个容器** |
| 新增配置项 | 新增项走默认值，你要判断这个默认值对不对 |
| 删除配置项 | 你 `brickkit.yaml` 里对它的覆盖会被**静默忽略**——不提醒的话你会以为还生效 |
| 数据库迁移 | 会跑什么命令；失败会阻断主服务启动 |
| artifacts 变更 | 调用方可能要重新生成客户端代码 |
| 资源配额变更 | 少数几个"升级失败但和组件代码无关"的原因之一：节点资源不够 |

### 旧 Manifest 读不到时会说"未知"

缓存被清过、文件坏了的时候，这几行会显示 `未知（旧版本 Manifest 读不到）`
而不是"无"。

**这个区别是有意的。** 报"无变化"是一句看起来完全正常的假话——
你会据此认为可以放心升级。

## ⏹️ 怎么停

```bash
brickkit down
```

恢复这一节改动的组件：

```bash
cd <仓库根目录>
cp tests/components/demo-hello/component.yaml 试用指南/playground/components/demo/hello/component.yaml
```

再把 `brickkit.yaml` 里的版本号改回 `1.0.0`。或者干脆重来：

```bash
./试用指南/准备.sh --reset
```
