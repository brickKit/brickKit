# 17 · 网络策略与最小权限

🎯 **这一节验证什么：** 组件之间的调用关系已经在 `component.yaml` 里声明过一遍了。
能不能让集群**照着这份声明**放行——声明了的连得上，没声明的连不上？

前置：走完 [15-K8s完整装配.md](15-K8s完整装配.md)，并且**集群要能真的执行网络策略**（见 17.1）。

---

## 为什么这件事值得平台代劳

手写 NetworkPolicy 不难，难的是**让它一直是对的**：加一个依赖要记得去开口子，
删一个依赖没人记得收回。半年之后那份策略就成了谁也不敢动的摆设——
不敢收紧（怕挂），也不敢当它有用。

BrickKit 手里正好有这张图：

```
people/basic          →  department/tree     （强依赖，component.yaml 里写着）
infra/api-docs        →  department/tree     （弱依赖）
infra/redis-event-bus →  跟 department/tree 没关系
```

那 `department/tree` 该放行谁就是**算出来的**，不是人记的。

---

## 17.1 ⚠️ 先确认你的集群真的会执行策略

**这一步不能跳。** NetworkPolicy 是个"声明"，真正执行它的是 CNI 插件。
minikube 默认的 `bridge` CNI **根本不执行** —— 策略会 apply 成功、
`kubectl get networkpolicy` 也看得见，然后被静默忽略。

在那样的集群上做完这一节的所有实验，你会得到"全都通过"的结论，而那是假的。

### ▶️ 操作

```bash
kubectl get pods -n kube-system | grep -Ei 'calico|cilium|antrea|weave'
```

### ✅ 预期

看到 `calico-node` / `cilium` 之类的东西在跑。**什么都没有就说明不执行。**

minikube 上另起一个能执行策略的 profile（不影响你原来那个）：

```bash
minikube start -p netpol --cni=calico --memory=3500mb --cpus=4
minikube addons enable ingress -p netpol
```

之后所有命令都加 `--context netpol`，`brickkit.yaml` 里也写上：

```yaml
deploy:
  context: netpol       # CLI 会核对，切错了直接阻断
```

### 🔍 怎么自己确认它在执行

最直接的办法是等 17.3 做完那个"连不上"的实验 —— 如果**该被拦的居然通了**，
不是策略写错了，是根本没人执行。

### ⏹️ 怎么停

```bash
minikube stop -p netpol      # 保留状态
minikube delete -p netpol    # 彻底删掉
```

## 17.2 打开两个开关

### ▶️ 操作

在 `brickkit.yaml` 的 `deploy` 下加：

```yaml
deploy:
  target: k8s
  context: netpol
  namespace: p26-demo
  createNamespace: false

  networkPolicy:
    enabled: true
    ingressController:
      namespace: ingress-nginx                     # ← 必填（有 expose 组件时）
      podSelector:
        app.kubernetes.io/name: ingress-nginx      # ← 可选
  serviceAccount:
    enabled: true
```

```bash
brickkit up --dry-run
cat .brickkit/generated/k8s/networkpolicies/department-tree-1-0-0.yaml
```

### ✅ 预期

```yaml
spec:
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: infra-api-docs-1-0-0       # ← 弱依赖，也放行
        - podSelector:
            matchLabels:
              app: people-basic-1-0-0         # ← 强依赖
      ports:
        - port: 8080
          protocol: TCP
  podSelector:
    matchLabels:
      app: department-tree-1-0-0
  policyTypes:
    - Ingress
```

**这份文件没有一行是你写的**，全部来自 `component.yaml` 里的依赖声明。

### 三件事值得注意

| 看到的 | 为什么 |
| --- | --- |
| **弱依赖也在放行名单里** | 弱依赖是"有就用、没有就降级"，对方在的时候是**真会去连**的。漏掉的表现极其迷惑：组件装了、起来了、健康检查也过，只有那条"可选"链路永远超时——看起来像对方本来就没装 |
| **只有 `Ingress`，没有 `Egress`** | 出站方向平台生成不出正确规则，见下面的说明 |
| **只放行 8080** | 组件声明过的端口才放行。`people/basic` 的 gRPC 在 `extraPorts` 的 9090，它的策略里就会有两个端口 |

> **为什么不管出站。** 出站要放行 DNS（kube-dns 在哪个命名空间、什么标签，
> 各集群不一样）和数据库（K8s 下基础资源由运维部署，可能在别的命名空间，
> 也可能是集群外一个托管实例的 IP —— 配置里只有一个 host 字符串，
> 变不成 podSelector 也变不成 CIDR）。
>
> 生成一份"为了不误伤而放行 `0.0.0.0/0`"的出站策略**比不生成更糟**：
> 它会让人以为出站已经管住了。这条边界是有意画的。

### ⚠️ 一个已知缺口：监控抓不到指标

生成的策略只放行**依赖图里的组件** —— 而 Prometheus 不在这张图上。
组件就算在 `component.yaml` 里声明了 `observability.metrics: true`，
抓取也会被挡掉，**现象是指标悄悄停了**，服务本身完全正常。

这是缺口，不是有意的边界（登记为 P36）。在补上之前有两条路：

```bash
# 路一：不开 networkPolicy

# 路二：自己额外 apply 一条放行监控的策略。
# 多条策略之间是**并集**关系，加一条不会破坏生成的那份
kubectl -n p26-demo apply -f - <<'YAML'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-prometheus}
spec:
  podSelector: {}            # 本命名空间所有 Pod
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: monitoring}
YAML
```

### ⏹️ 怎么停

把 `networkPolicy.enabled` 改成 `false`，重新 `brickkit up`。

## 17.3 亲手验一次：谁进得来，谁进不来

这是整节的核心。光看生成的 YAML 说明不了任何问题 —— 要真的去连一下。

### ▶️ 操作

```bash
brickkit up

PROBE='import socket
s=socket.socket(); s.settimeout(5)
try:
    s.connect(("department-tree-1-0-0", 8080)); print("CONNECTED")
except Exception as e:
    print("BLOCKED:", type(e).__name__, e)'

# A. people/basic —— 强依赖 department/tree
kubectl --context netpol -n p26-demo exec \
  $(kubectl --context netpol -n p26-demo get pod -l app=people-basic-1-0-0 -o name) \
  -- python3 -c "$PROBE"

# B. infra/redis-event-bus —— 跟 department/tree 没关系
kubectl --context netpol -n p26-demo exec \
  $(kubectl --context netpol -n p26-demo get pod -l app=infra-redis-event-bus-1-0-0 -o name) \
  -- python3 -c "$PROBE"
```

### ✅ 预期

```
A: CONNECTED
B: BLOCKED: TimeoutError timed out
```

**B 如果也是 `CONNECTED`，回到 17.1** —— 你的集群没在执行策略。

### 弱依赖那条链路怎么验

`infra/api-docs` 是 Go 组件，镜像里没有 shell 工具。不过它自己就在探它的依赖，
直接问它就行：

```bash
curl -s --resolve "docs.local:80:$(minikube -p netpol ip)" \
  http://docs.local/api/v1/sources | python3 -m json.tool | head -20
```

`department/tree` 那一项是 `"status": "ok"`，说明**弱依赖穿过策略连上了**。

### ⏹️ 怎么停

```bash
brickkit down
```

## 17.4 亲手把它弄坏：删掉 ingress controller 那条规则

`expose: true` 的组件要额外放行 ingress controller。这一条**极容易被想当然地跳过**，
所以值得亲手看一次后果。

### ▶️ 操作

```bash
IP=$(minikube -p netpol ip)
curl -s -o /dev/null -w "改之前 HTTP %{http_code}\n" \
  --resolve "docs.local:80:$IP" http://docs.local/

# 手工把那条规则删掉
kubectl --context netpol -n p26-demo patch networkpolicy infra-api-docs-1-0-0 \
  --type=json -p '[{"op":"replace","path":"/spec/ingress","value":[]}]'
sleep 3

curl -s -o /dev/null -w "删掉之后 HTTP %{http_code}\n" --max-time 12 \
  --resolve "docs.local:80:$IP" http://docs.local/
```

### ✅ 预期

```
改之前 HTTP 200
删掉之后 HTTP 000
```

**`000` 是 curl 说"我压根没连上"** —— 不是 502，不是 503，是**连接超时**。

这就是为什么 CLI 要在生成阶段硬性拦下"开了策略 + 有 `expose` 组件 + 没写
`ingressController`"这个组合：放过去的话，`brickkit up` 会全部成功、
退出码 0、每个 Pod 都 healthy，**而网站直接打不开**。
现场看到的只有超时，跟"我刚在 brickkit.yaml 里打开的那个开关"联系不起来。

试试把配置里的 `ingressController` 整段删掉再 `brickkit up --dry-run`：

```
❌ 错误：开了 deploy.networkPolicy 又有 expose: true 的组件时，
   必须写 deploy.networkPolicy.ingressController.namespace
   对外组件：infra/api-docs@1.0.0（expose: true）
   原因：生成的策略默认拒绝一切入站；不说明 ingress controller 在哪，
        它也会被挡在门外——部署会全部成功，网站却打不开
   建议：
   1. 查一下 controller 在哪个命名空间：kubectl get pods -A | grep ingress
```

### 恢复

```bash
kubectl --context netpol -n p26-demo apply \
  -f .brickkit/generated/k8s/networkpolicies/infra-api-docs-1-0-0.yaml
```

> ⚠️ **`namespaceSelector` 和 `podSelector` 必须写在同一个 `from` 元素里。**
> 同一个元素里是 AND（那个命名空间里符合标签的 Pod），拆成两个元素就是 OR
> （那个命名空间的**所有** Pod，加上**所有**命名空间里符合标签的 Pod）。
> 这是 NetworkPolicy 最经典的坑：写错了照样 apply 成功、照样通，
> 只是放行范围比你以为的大得多，而且没有任何迹象。生成器不会写错。

## 17.5 ServiceAccount：把那张令牌拿掉

### ▶️ 操作

```bash
kubectl --context netpol -n p26-demo exec \
  $(kubectl --context netpol -n p26-demo get pod -l app=people-basic-1-0-0 -o name) \
  -- ls /var/run/secrets/kubernetes.io/serviceaccount/
```

### ✅ 预期

```
ls: cannot access '/var/run/secrets/kubernetes.io/serviceaccount/': No such file or directory
```

**默认情况下这个目录是有东西的** —— 每个 Pod 都会被塞进一张 `default` ServiceAccount
的令牌，拿着它就能跟 API Server 说话。而 BrickKit 的组件模型里
根本没有"访问 K8s API"这回事，所以关掉它是纯收益：
任何一个组件被拿下，攻击者也拿不到一张能问集群要东西的票。

```bash
kubectl --context netpol -n p26-demo get pods \
  -o custom-columns=NAME:.metadata.name,SA:.spec.serviceAccountName
```

每个组件一个专属 SA，不再共用 `default`。

### 用运维给你的那个 SA

云上常见：SA 上绑着 IRSA / Workload Identity 的注解，由运维创建并授权。
这时候写组件条目上的 `serviceAccountName`：

```yaml
components:
  - id: people/basic
    version: 1.0.0
    serviceAccountName: people-s3-reader     # ← 平台只引用，不生成
```

平台**不会**生成一份同名的 SA 去盖掉它 —— 那会把运维配好的授权安静地抹掉
（`kubectl apply` 还会成功）。也不会替它决定挂不挂令牌：
那个 SA 可能正是靠令牌去调 API 的。

### ⏹️ 怎么停

把 `serviceAccount.enabled` 改回 `false`，重新 `brickkit up`。

## 17.6 没有生成的：PodDisruptionBudget

有人会问：既然生成了策略和 SA，怎么不顺手生成 PDB？

**试一次就知道了。** 当前 `replicas` 固定是 1（多副本是后期能力，005 §5.8）：

```bash
kubectl --context netpol -n p26-demo apply -f - <<'YAML'
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: department-tree-1-0-0}
spec:
  minAvailable: 1
  selector: {matchLabels: {app: department-tree-1-0-0}}
YAML

kubectl --context netpol -n p26-demo get pdb
```

```
NAME                    MIN AVAILABLE   ALLOWED DISRUPTIONS   AGE
department-tree-1-0-0   1               0                     0s
```

**`ALLOWED DISRUPTIONS: 0`。** 现在模拟运维升级集群时天天做的事：

```bash
kubectl --context netpol drain netpol --pod-selector app=department-tree-1-0-0 \
  --ignore-daemonsets --delete-emptydir-data --timeout=45s
```

```
error when evicting pods/"department-tree-1-0-0-..." -n "p26-demo":
  global timeout reached: 45s
```

要留 1 个而总共就 1 个 —— 一个也不许赶走，**排空永远不可能成功**。
换成 `maxUnavailable: 1` 又等于没有这个 PDB。

要命的是代价落在谁身上：打开开关的是开发者，撞上的是几个月后升级集群的运维，
而现场只有一个排不空的节点，跟 `brickkit.yaml` 里某个开关联系不起来。

所以 PDB 等多副本落地之后再说。

```bash
kubectl --context netpol -n p26-demo delete pdb department-tree-1-0-0
kubectl --context netpol uncordon netpol
```

## 一句话总结

```
声明依赖 → 平台生成策略 → 集群照着执行
```

你已经为了让组件能跑起来而写过一遍依赖声明了。打开这个开关，
那份声明**顺便**变成了网络边界 —— 不用再写第二遍，也不会忘了同步。
