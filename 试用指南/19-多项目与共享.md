# 19 · 多个项目之间怎么共享

🎯 **这一节验证什么：** 两个团队、两个项目，需要"同一个东西"的时候怎么办。
以及一个更要紧的问题——**到底该不该共享**。

前置：走完 [05-Docker启动全流程.md](05-Docker启动全流程.md)（要的是"Docker 与组件镜像都就绪"，
本篇自己另建两个项目，不依赖 playground 里那份配置）。

---

## 先问一句：状态在哪

这是唯一要紧的问题，其余全部从它推出来。**先问这一句，问题往往就消失了。**

```
这个组件自己持有权威状态吗？
├─ 没有，也不依赖共享数据
│    → 各部各的。零成本，而且更好          → 19.1
├─ 组件自己无状态，状态在它连的资源里
│    → 各部各的组件 + 共享那个资源          → 19.2  ← 最常见
└─ 组件本身就是权威（单例副作用、成本高昂）
     → 当成别人的 API 来调                → 19.4
```

⚠️ **中间那一档最容易被跳过。** 组件规范（002）本来就把组件推向无状态——
配置来自环境变量、状态放资源里——所以"这个组件有权威状态"的情况**比直觉中少得多**。

举个会让人判断错的例子：`infra/redis-event-bus` 听上去像个必须共享的中枢。
但它**自己一行状态都不存**，事件全在 Redis Streams 里。
两个项目各跑一份、指向同一个 Redis，就是一条共享的事件流。

---

## 19.1 形态一：各部各的

不用做任何事。两个项目各自 `add`、各自 `up`，各得一份。

**这不是退而求其次，多数时候它更好：**

| 好处 | 说明 |
| --- | --- |
| 故障隔离 | 一边挂了完全不影响另一边 |
| 独立升级 | 各自的节奏，不用开会协调 |
| 版本自由 | A 用 1.0.0、B 用 2.0.0，互不干涉 |

只有当"两份副本看不见彼此的数据"会造成**业务问题**时，才需要往下看。

---

## 19.2 形态二：共享资源，不共享组件

组件各部一份，`resources` 指向同一个实例。

### ▶️ 操作

先起一个两个项目都能连到的 Redis：

```bash
docker run -d --name shared-redis -p 6399:6379 redis:7-alpine
```

建两个**完全独立**的项目：

```bash
cd 试用指南/playground
for proj in team-a team-b; do
  mkdir -p "$proj"
  port=$([ "$proj" = team-a ] && echo 18201 || echo 18202)
  cat > "$proj/brickkit.yaml" <<YAML
project: $proj
deploy:
  target: docker
sources:
  - id: local
    type: local
    path: ../components
components:
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: true
    expose: true
    exposePort: $port
resources:
  - kind: cache
    engine: redis
    id: redis
    host: host.docker.internal      # ← 关键：两个项目指向同一个 Redis
    port: 6399
    bindings:
      - componentId: infra/redis-event-bus
YAML
done

for p in team-a team-b; do
  (cd "$p" && echo y | ../../bin/brickkit add infra/redis-event-bus@1.0.0 >/dev/null 2>&1
   ../../bin/brickkit up 2>&1 | grep -E "✅ 全部" | sed "s/^/$p: /")
done
```

### ✅ 预期

```
team-a: ✅ 全部组件已启动（1 个）
team-b: ✅ 全部组件已启动（1 个）
```

### 验证：A 发的事件，B 读得到

```bash
curl -s -X POST http://localhost:18201/api/v1/events \
  -H 'Content-Type: application/json' \
  -d '{"type":"order.approved","actor":"alice","subject":"ORD-42"}'

curl -s "http://localhost:18202/api/v1/events?count=5" | python3 -m json.tool
```

```json
{
    "events": [
        {
            "type": "order.approved",
            "actor": "alice",
            "subject": "ORD-42",
            "id": "1786833372153-0"
        }
    ],
    "total": 1
}
```

**两个毫不相干的项目共享了同一条事件流**，而它们各跑各的组件、各自升级、
一边 `down` 完全不影响另一边。**没有用到任何新特性。**

### 为什么用 `host.docker.internal`

Docker 下每个 BrickKit 项目是一个独立的 compose 项目，**各有各的网络，默认互不可达**。
所以不能直接写对方的容器名。

`host.docker.internal` 指向**宿主机**——共享 Redis 的端口发布在宿主机上，
两个项目都从那里连。平台会自动为绑定了它的组件补 `extra_hosts`，你不用手工建网络。

换到别的部署目标时，**只有 `host` 这一个字段要改**：

| 目标 | `host` 写什么 |
| --- | --- |
| Docker / 本地调试 | `host.docker.internal`（+ 宿主机端口） |
| K8s | `redis.infra.svc.cluster.local`（命名空间之间默认可达） |

### ⏹️ 怎么停

```bash
cd 试用指南/playground
for p in team-a team-b; do (cd "$p" && ../../bin/brickkit down); done
docker rm -f shared-redis
rm -rf team-a team-b
```

## 19.3 反过来：一个字段就隔离

共享还是隔离，**往往只是一个配置**。组件的 `configSchema` 里通常有个划分数据边界的
字段——事件总线是 `streamName`。

### ▶️ 操作

给 team-b 换一个流名：

```yaml
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: true
    expose: true
    exposePort: 18202
    config:
      streamName: "team-b:events"      # ← 加这三行
```

```bash
cd team-b && ../../bin/brickkit up
curl -s "http://localhost:18202/api/v1/events?count=5" | python3 -m json.tool
```

### ✅ 预期

```json
{
    "events": [],
    "total": 0
}
```

team-b 再也看不到 team-a 的事件了，而 **team-a 自己的照常在**（`total = 1`）。

同一个 Redis、同一个组件，**共享与隔离的差别就是这一个字段**。
所以"要不要共享"不是一次性的架构决定，它是可以随时改的配置。

## 19.4 形态三：跨项目调用（当成别人的 API）

上面两种形态覆盖了绝大多数场景。剩下的情况是**组件本身就是权威**：

| 情形 | 例子 |
| --- | --- |
| 单例副作用 | 定时任务、通知发送——跑两份就是双倍邮件 |
| 成本高昂 | 大模型推理服务，复制一份不现实 |
| 归属独立 | 一个团队运维，别人只许调用 |

### 先想清楚这意味着什么

**跨项目 = 不同的维护人员。** 同一个人维护的东西，他不会特意拆成两个项目；
真拆了，他自己清楚里面的门道。所以一旦真的跨项目，前提一定是两边各有负责人、
商量好了要互通。

那么关系就和调**任何第三方 API** 一样：

- 你只需要知道**它在哪**；
- 它起没起来、什么时候升级、要不要扩容，是**对方负责人**的事；
- 它挂了，你的组件按自己的降级逻辑处理——跟市场 API 挂了没区别。

**你不会为了调一个 API 去帮对方启动服务。** 平台也不该替你去做这件事。

### 写法：一个必填配置项

**组件侧**声明"我需要一个地址，我猜不出来"：

```yaml
# component.yaml
configSchema:
  type: object
  properties:
    notifierBaseUrl:
      type: string
      description: 共用通知服务的地址，由部署它的那个项目提供
  required:
    - notifierBaseUrl        # 没有 default + required = 项目必须填
```

**项目侧**填上对方给的地址：

```yaml
# brickkit.yaml
components:
  - id: shop/order
    version: 1.0.0
    config:
      notifierBaseUrl: ${NOTIFIER_BASE_URL}   # 真值放 .env
```

组件代码读环境变量 `NOTIFIER_BASE_URL`——**本地、Docker、K8s 三处名字一模一样**，
和读任何别的配置项没有区别。

> **别把它命名成 `xxxEndpoint`。** `*_ENDPOINT` 是平台注入依赖地址的保留模式，
> 写了会被忽略并给出警告。用 `xxxBaseUrl` / `xxxAddr`。

### ▶️ 操作：验证"忘了填就起不来"

这是这套写法最要紧的一条。`demo/hello` 已经有 `configSchema` 了，
所以往里**加一项**、而不是再写一个 `configSchema`（重复的顶层键会被判成 YAML 错误）：

```bash
python3 - <<'EOF'
import pathlib
p = pathlib.Path("components/demo/hello/component.yaml")
p.write_text(p.read_text().replace(
    "configSchema:\n  type: object\n  properties:\n",
    "configSchema:\n  type: object\n  required:\n    - notifierBaseUrl\n  properties:\n"
    "    notifierBaseUrl:\n      type: string\n      description: 共用通知服务的地址\n"))
EOF
brickkit up --dry-run --only demo/hello
```

### ✅ 预期

```
❌ 错误：必填的组件配置没有值
   缺少配置：demo/hello@1.0.0 → notifierBaseUrl（注入为 NOTIFIER_BASE_URL）
   原因：组件在 configSchema.required 里声明了它，又没有给默认值——这一项平台推导不出来，只能由项目提供
   建议：
   1. 在 brickkit.yaml 里给它一个值：
    components:
      - id: demo/hello
        config:
          notifierBaseUrl: <值>
   2. 值里可以写 ${ENV_VAR}，真值放 .env（003 §4.6）
```

**这一拦是整套写法的地基。** 没有它，忘了填地址时那个环境变量根本不出现，
组件走进"未配置"分支——不崩、不报警，只是那一路调用永远走不通，
而你以为自己已经配好了。

### ▶️ 填上，再跑一次

在 `brickkit.yaml` 里给 `demo/hello` 加上 `config`：

```yaml
  - id: demo/hello
    version: 1.0.0
    config:
      notifierBaseUrl: http://host.docker.internal:18080
```

```bash
brickkit up --only demo/hello
docker exec brickkit-demo-shop-demo-hello-1-0-0-1 env | grep NOTIFIER
```

```
NOTIFIER_BASE_URL=http://host.docker.internal:18080
```

### 恢复

```bash
cd <仓库根目录>
cp tests/components/demo-hello/component.yaml 试用指南/playground/components/demo/hello/component.yaml
cd 试用指南/playground && git checkout brickkit.yaml 2>/dev/null || true
```

### 完整案例：两个团队、两个项目，各自做什么

场景：**平台组**维护一个通知服务（`infra/notifier`），**订单组**的订单系统要用它。
两个项目、两拨人。

#### 第 0 步：先谈一次（人对人，不是配置）

这一步没有命令，但它决定了后面所有事。两边要谈定三件：

| 谈定什么 | 谁给 | 为什么必须先谈 |
| --- | --- | --- |
| **接口契约** | 平台组给出 `.proto` / `openapi.json` | 订单组照它生成客户端。跨项目没有自动下载，是**平台组主动给一份** |
| **稳定入口** | 平台组给出一个各环境下都不变的地址 | 见下面「为什么必须是稳定入口」 |
| **变更怎么通知** | 双方约定 | 契约要改时订单组得提前知道——这跟用任何第三方 API 一样 |

> 你会发现这三件事和"接入一个外部支付网关"要谈的完全一样。**这就是重点**：
> 跨项目共享不是平台的一个功能，它就是一次普通的服务对接。

#### 第 1 步：平台组（服务提供方）

共享的东西自己就是一个**普通的 BrickKit 项目**：

```bash
mkdir platform && cd platform
brickkit init platform-shared
brickkit add infra/notifier@1.0.0
```

```yaml
# platform/brickkit.yaml —— 关键是 expose，它是对外的那个门
components:
  - id: infra/notifier
    version: 1.0.0
    expose: true
    hostname: notify.internal.corp     # K8s 下生成 Ingress；Docker 下发布宿主机端口
```

```bash
brickkit up
```

平台组从此对这个服务负全部责任：起停、升级、扩容、值班。
**它对订单组的唯一承诺是：`notify.internal.corp` 这个地址一直可用。**

#### 第 2 步：订单组（消费方）

组件侧声明"我需要一个地址"（这是**组件作者**写的，一次）：

```yaml
# shop/order 的 component.yaml
configSchema:
  properties:
    notifierBaseUrl:
      type: string
      description: 通知服务地址，由平台组提供
  required:
    - notifierBaseUrl
```

项目侧填上（这是**用这个组件的人**写的，每个项目一次）：

```yaml
# shop/brickkit.yaml
components:
  - id: shop/order
    version: 1.0.0
    config:
      notifierBaseUrl: https://notify.internal.corp
```

```bash
brickkit up      # 平台组的服务在不在，与这条命令无关
```

**订单组的 `brickkit.yaml` 里没有 `infra/notifier` 这一行。** 它不是本项目的组件，
就像支付网关不是你的组件一样。

#### 第 3 步：出事了找谁

| 现象 | 谁的事 | 怎么查 |
| --- | --- | --- |
| 订单系统起不来 | 订单组 | 与通知服务无关——`up` 从不检查它在不在 |
| 订单起来了，发通知报连接失败 | 先看地址填对没有；对了就是平台组的事 | `docker exec ... env \| grep NOTIFIER` 看注入的值 |
| 通知服务挂了 | 平台组 | 订单组按自己的降级逻辑处理（记日志、进重试队列） |
| 契约对不上（字段变了） | 平台组没按第 0 步通知 | 这是流程问题，不是平台问题 |

**注意第一行。** 这是把它当 API 的直接结果：平台组的服务挂着，
订单组照样能 `up`、能开发、能跑测试。反过来的设计（对方没起来我就起不来）
在 Docker 下真实存在过，见下一节。

#### 为什么必须是"稳定入口"，而不是内部服务名

订单组的三个环境（本机 / Docker / K8s 集群）如果都去猜通知服务的**内部**地址，
就会变成三个不同的写法，而且每次对方搬家都要跟着改。
稳定入口把这件事变成一个常量：

```yaml
config:
  notifierBaseUrl: https://notify.internal.corp     # 三个环境同一行
```

真要按环境连不同实例（比如测试环境连测试集群那一套），用多环境配置：

```bash
brickkit up --config brickkit.prod.yaml
```

**发布这个入口是平台组的职责，不是订单组去推导出来的。** 这条边界就是
`external` 当初弄反的地方。

### 为什么平台不替你做这件事

早先有过一个 `external: {project: X}` 字段：写上它，平台就去推导跨项目地址
（Docker 下把你接进对方的网络，K8s 下给地址拼上对方的命名空间后缀）。**已经删掉了。**

它看着方便，实际编码的是**相反的模型**——不是"调别人的 API"，是"共享别人的内部网络"：

| `external` 实际要求 | 而"调 API"只需要 |
| --- | --- |
| 对方的 `component.yaml` 得能从**你的**安装源解析出来 | 一个地址 |
| Docker 下对方没 `up`，**你起不来** | 他挂了是他的事，你照常跑 |
| K8s 下钻进对方 namespace，必须同集群，两边还要各配 NetworkPolicy | 一个地址 |
| `local: true` 时注入容器内部名，你 IDE 里的进程解析不了 | 本地也照样能连 |

后两条在删除前是真实存在的缺陷，而且都不报错：打开 `networkPolicy.egress` 之后，
到共享服务的调用会被策略静默丢弃；`local: true` 的组件拿到的是一个宿主机上
解析不了的名字。

**换掉它损失了什么：** 对方组件的 artifacts（`.proto` / `openapi.json`）不再自动下载，
要向对方要一份。一次性的动作。


## 一句话总结

```
先问：状态在哪？
  不在组件里  → 各部各的，或共享那个资源      ← 今天就能做
  在组件里    → 当成别人的 API 来调          ← 见 19.4，比你以为的少见
```
