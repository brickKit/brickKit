# 19 · 多个项目之间怎么共享

🎯 **这一节验证什么：** 两个团队、两个项目，需要"同一个东西"的时候怎么办。
以及一个更要紧的问题——**到底该不该共享**。

前置：走完 [05-Docker启动全流程.md](05-Docker启动全流程.md)。

---

## 先问一句：状态在哪

这是唯一要紧的问题，其余全部从它推出来。**先问这一句，问题往往就消失了。**

```
这个组件自己持有权威状态吗？
├─ 没有，也不依赖共享数据
│    → 各部各的。零成本，而且更好          → 19.1
├─ 组件自己无状态，状态在它连的资源里
│    → 各部各的组件 + 共享那个资源          → 19.2  ← 最常见
└─ 组件本身就是权威（单例副作用、成本高昂）
     → 外部依赖（external）              → 19.4
```

⚠️ **中间那一档最容易被跳过。** 组件规范（002）本来就把组件推向无状态——
配置来自环境变量、状态放资源里——所以"这个组件有权威状态"的情况**比直觉中少得多**。

举个会让人判断错的例子：`infra/redis-event-bus` 听上去像个必须共享的中枢。
但它**自己一行状态都不存**，事件全在 Redis Streams 里。
两个项目各跑一份、指向同一个 Redis，就是一条共享的事件流。

---

## 19.1 形态一：各部各的

不用做任何事。两个项目各自 `add`、各自 `up`，各得一份。

**这不是退而求其次，多数时候它更好：**

| 好处 | 说明 |
| --- | --- |
| 故障隔离 | 一边挂了完全不影响另一边 |
| 独立升级 | 各自的节奏，不用开会协调 |
| 版本自由 | A 用 1.0.0、B 用 2.0.0，互不干涉 |

只有当"两份副本看不见彼此的数据"会造成**业务问题**时，才需要往下看。

---

## 19.2 形态二：共享资源，不共享组件

组件各部一份，`resources` 指向同一个实例。

### ▶️ 操作

先起一个两个项目都能连到的 Redis：

```bash
docker run -d --name shared-redis -p 6399:6379 redis:7-alpine
```

建两个**完全独立**的项目：

```bash
cd 试用指南/playground
for proj in team-a team-b; do
  mkdir -p "$proj"
  port=$([ "$proj" = team-a ] && echo 18201 || echo 18202)
  cat > "$proj/brickkit.yaml" <<YAML
project: $proj
deploy:
  target: docker
sources:
  - id: local
    type: local
    path: ../components
components:
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: true
    expose: true
    exposePort: $port
resources:
  - kind: cache
    engine: redis
    id: redis
    host: host.docker.internal      # ← 关键：两个项目指向同一个 Redis
    port: 6399
    bindings:
      - componentId: infra/redis-event-bus
YAML
done

for p in team-a team-b; do
  (cd "$p" && echo y | ../../bin/brickkit add infra/redis-event-bus@1.0.0 >/dev/null 2>&1
   ../../bin/brickkit up 2>&1 | grep -E "✅ 全部" | sed "s/^/$p: /")
done
```

### ✅ 预期

```
team-a: ✅ 全部组件已启动（1 个）
team-b: ✅ 全部组件已启动（1 个）
```

### 验证：A 发的事件，B 读得到

```bash
curl -s -X POST http://localhost:18201/api/v1/events \
  -H 'Content-Type: application/json' \
  -d '{"type":"order.approved","actor":"alice","subject":"ORD-42"}'

curl -s "http://localhost:18202/api/v1/events?count=5" | python3 -m json.tool
```

```json
{
    "events": [
        {
            "type": "order.approved",
            "actor": "alice",
            "subject": "ORD-42",
            "id": "1786833372153-0"
        }
    ],
    "total": 1
}
```

**两个毫不相干的项目共享了同一条事件流**，而它们各跑各的组件、各自升级、
一边 `down` 完全不影响另一边。**没有用到任何新特性。**

### 为什么用 `host.docker.internal`

Docker 下每个 BrickKit 项目是一个独立的 compose 项目，**各有各的网络，默认互不可达**。
所以不能直接写对方的容器名。

`host.docker.internal` 指向**宿主机**——共享 Redis 的端口发布在宿主机上，
两个项目都从那里连。平台会自动为绑定了它的组件补 `extra_hosts`，你不用手工建网络。

换到别的部署目标时，**只有 `host` 这一个字段要改**：

| 目标 | `host` 写什么 |
| --- | --- |
| Docker / 本地调试 | `host.docker.internal`（+ 宿主机端口） |
| K8s | `redis.infra.svc.cluster.local`（命名空间之间默认可达） |

### ⏹️ 怎么停

```bash
cd 试用指南/playground
for p in team-a team-b; do (cd "$p" && ../../bin/brickkit down); done
docker rm -f shared-redis
rm -rf team-a team-b
```

## 19.3 反过来：一个字段就隔离

共享还是隔离，**往往只是一个配置**。组件的 `configSchema` 里通常有个划分数据边界的
字段——事件总线是 `streamName`。

### ▶️ 操作

给 team-b 换一个流名：

```yaml
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: true
    expose: true
    exposePort: 18202
    config:
      streamName: "team-b:events"      # ← 加这三行
```

```bash
cd team-b && ../../bin/brickkit up
curl -s "http://localhost:18202/api/v1/events?count=5" | python3 -m json.tool
```

### ✅ 预期

```json
{
    "events": [],
    "total": 0
}
```

team-b 再也看不到 team-a 的事件了，而 **team-a 自己的照常在**（`total = 1`）。

同一个 Redis、同一个组件，**共享与隔离的差别就是这一个字段**。
所以"要不要共享"不是一次性的架构决定，它是可以随时改的配置。

## 19.4 完全共享一个组件实例（`external`）

上面两种形态覆盖了绝大多数场景。剩下的情况是**组件本身就是权威**：

| 情形 | 例子 |
| --- | --- |
| 单例副作用 | 定时任务、通知发送——跑两份就是双倍邮件 |
| 成本高昂 | 大模型推理服务，复制一份不现实 |
| 归属独立 | 一个团队运维，别人只许调用 |

这时候要的是"**这个依赖已经有人部好了，我只连它**"。

### ▶️ 操作

共享的东西自己就是一个**普通的 BrickKit 项目**，用你已经会的命令建立：

```bash
# ① 平台项目：部署共享组件
mkdir platform && cd platform
brickkit init platform-shared
# 编辑 brickkit.yaml 加上 demo/hello@1.0.0
brickkit up
```

消费方项目只声明"我连它"：

```yaml
# consumer/brickkit.yaml
project: my-erp
components:
  - id: demo/caller
    version: 1.0.0
  - id: demo/hello
    version: 1.0.0
    external:
      project: platform-shared     # ← 就这一行
```

```bash
cd consumer && brickkit up
```

### ✅ 预期

`up` 会明确告诉你哪些依赖是外部的：

```
🔗 以下依赖由**别的项目**部署，本项目只连接、不启动也不停止：
   demo/hello@1.0.0  ← 项目 platform-shared
   对方没部署时，本项目会正常起来但调用它时连接失败

✅ 全部组件已启动（1 个）
```

注意是 **1 个**——`demo/hello` 没有被再起一份。

### 验证：真的连到了对方那一份

```bash
docker exec brickkit-my-erp-demo-caller-1-0-0-1 \
  wget -qO- http://localhost:8080/api/v1/call
```

```json
{"component":"demo/caller",
 "endpoint":"http://demo-hello-1-0-0:8080",
 "upstream":{"component":"demo/hello","version":"1.0.0","greeting":"你好"}}
```

### 验证：这才是 external 的全部理由

```bash
cd consumer && brickkit down
docker ps | grep hello        # 还在跑
```

**消费方停掉自己，对方毫发无伤。** 如果把共享组件写进消费方的
`brickkit.yaml` 由消费方部署，这一步就会把别的项目一起弄挂——
而那跟它部在哪个命名空间毫无关系。

### 平台替你处理的两处麻烦

| 目标 | 麻烦在哪 | 平台怎么做 |
| --- | --- | --- |
| Docker | 服务名**只在同一张网络**里解析 | 把依赖它的服务接进对方项目的网络（只引用不创建） |
| K8s | 裸服务名只在**本命名空间**解析 | 注入的地址自动带后缀：`demo-hello-1-0-0.brickkit-platform-shared` |

K8s 上还有一件不做比做更重要的事：**不生成同名 Service**。
生成了的话，本命名空间那个（背后零个 Pod）会**抢在**跨命名空间解析之前命中，
结果是稳定的 503，而你从依赖方看一切正常——地址对、DNS 通、Service 也在。

### ⏹️ 怎么停

```bash
cd consumer && brickkit down     # 只停自己
cd ../platform && brickkit down  # 平台方自己停自己
```

### 一件白送的好事

服务名带版本（`demo-hello-1-0-0`），所以声明 `@1.0.0` 时，
要么连上的正好是 1.0.0，**要么 DNS 解析不出来当场报错**——
不存在"连到了 2.0.0 却以为是 1.0.0"这种状态。

平台项目可以同时部署 1.0.0 和 2.0.0，让 A 和 B 各连各的，各自按节奏升级。

## 一句话总结

```
先问：状态在哪？
  不在组件里  → 各部各的，或共享那个资源      ← 今天就能做
  在组件里    → 才需要 external              ← 见 19.4，比你以为的少见
```
