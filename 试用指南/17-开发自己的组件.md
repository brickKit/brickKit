# 17 · 开发自己的组件

🎯 **这一节验证什么：** 从零写一个组件 → 被平台认出来 → 装进项目 → 跑起来 →
本地调试 → 发到市场。走完你就知道"写一个 BrickKit 组件"到底要做哪几件事。

前置：`./试用指南/准备.sh`（[00](00-准备.md)，CLI 已编译）；Docker 可用；发布那一段需要市场后端（[10](10-组件市场.md)）。
本篇从一个**空目录**开始写你自己的组件，不用 playground 里那份配置。

---

## 组件只有四条硬约束

先看清楚要求有多少 —— **只有四条**（002 §1.4）。其余全是你自己的自由：

| # | 约束 | 为什么 |
| --- | --- | --- |
| 1 | 配置**只从环境变量读** | 组件不知道也不该知道自己被部署在哪 |
| 2 | `/healthz` **只检查本进程** | 去查库/查依赖的话，依赖一抖就把这个本身正常的容器杀掉重启 |
| 3 | 日志是 **JSON 到 stdout**，带 `componentId` | 一个项目跑着十几个组件，没这个字段就没法在聚合日志里分开 |
| 4 | 容器**不以 root 运行** | — |

语言、框架、目录结构、用不用数据库 —— 平台一概不管。

## 17.1 写一个最小的组件

我们写 `notify/webhook`：收下消息、记在内存里、供查看。

### ▶️ 操作

```bash
mkdir -p ~/mycomp/notify && cp -r 试用指南/示例组件/notify/webhook ~/mycomp/notify/
cd ~/mycomp/notify/webhook
```

（想从空目录自己敲一遍也行，下面把要点都列出来了。）

> **目录必须是 `<scope>/<name>`**。本地安装源靠这个布局定位组件 ——
> 放成 `notify-webhook` 的话，`brickkit add notify/webhook` 会说找不到。

`main.go`（只摘要点，**完整可运行的版本**在
[试用指南/示例组件/notify/webhook/](示例组件/notify/webhook/)，
可以直接 `cp -r` 出来改）：

```go
func main() {
	// ① 配置只从环境变量读。componentId 由平台注入
	componentID := envOr("COMPONENT_ID", "notify/webhook")

	// configSchema 里声明的 keepMessages → 平台注入 KEEP_MESSAGES
	keep := 20
	if raw := os.Getenv("KEEP_MESSAGES"); raw != "" {
		if n, err := parseInt(raw); err == nil && n > 0 {
			keep = n
		} else {
			fail("KEEP_MESSAGES 必须是正整数，当前是 " + raw)   // 不静默用默认值
		}
	}

	// ③ 日志是 JSON，每条都带 componentId
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil)).With("componentId", componentID)

	// ② /healthz 只检查本进程存活——不查库、不调依赖
	mux.HandleFunc("/healthz", func(w http.ResponseWriter, _ *http.Request) {
		writeJSON(w, http.StatusOK, map[string]string{"status": "ok"})
	})
	...
}
```

### 三个容易做错的小地方

```go
// 空列表返回 []，不是 null——弱类型的调用方遍历 null 会直接崩
if items == nil {
	items = []message{}
}

// 配置值不合法时**启动失败**，不要静默用默认值：
// 悄悄用默认值会让人以为配置生效了
fail("KEEP_MESSAGES 必须是正整数，当前是 " + raw)

// 请求体要限大小，不然一个超大 body 就能把内存吃干净
http.MaxBytesReader(nil, r.Body, 64<<10)
```

### ⏹️ 怎么停

还没跑任何东西。

## 17.2 写 component.yaml

这是组件对平台的**承诺**：我叫什么、要什么、怎么检查我活着。

### ▶️ 操作

```yaml
apiVersion: brickkit/v1
kind: Component

metadata:
  id: notify/webhook        # 必须与目录布局一致
  name: 通知收集器
  version: 1.0.0
  description: 收下消息并记在内存里，供查看
  vendor: me
  license: MIT

configSchema:
  type: object
  properties:
    keepMessages:
      type: integer
      default: 20
      description: 最多保留多少条消息，注入为环境变量 KEEP_MESSAGES

deployment:
  type: container
  image: my/notify-webhook:1.0.0
  port: 8080

healthCheck:
  type: http
  path: /healthz
```

### 关于 configSchema

**驼峰会被转成大写下划线**：`keepMessages` → `KEEP_MESSAGES`（003 §5.4）。

三种情况：

| 情况 | 平台怎么做 |
| --- | --- |
| 有 `default`，使用者没覆盖 | 注入默认值 |
| 使用者在 `config:` 里覆盖了 | 注入覆盖值 |
| **既没 default 也没覆盖** | **完全不注入** —— 让组件走"未配置"分支 |

第三条是密钥的正确用法：声明一个**没有默认值**的配置项，
使用者用 `${JWT_SECRET}` 从 `.env` 引用（12.3 里 `auth/password-login` 就是这么做的）。

> ⚠️ `apiVersion` 是**组件 Manifest** 才有的字段。`brickkit.yaml` 里**没有**它 ——
> 写进去会被当成未知字段报错。

## 17.3 Dockerfile

### ▶️ 操作

```dockerfile
FROM golang:1.22-alpine AS build
WORKDIR /src
COPY go.mod ./
COPY *.go ./
RUN CGO_ENABLED=0 go build -trimpath -o /out/notify-webhook .

FROM alpine:3.20
RUN adduser -D -u 10001 brickkit
COPY --from=build /out/notify-webhook /app/notify-webhook

USER 10001          # ← 第 4 条硬约束
EXPOSE 8080
ENTRYPOINT ["/app/notify-webhook"]
```

```bash
docker build -t my/notify-webhook:1.0.0 .
```

### ⚠️ 用 python:slim 之类的基础镜像时

健康检查跑在**容器内部**，用的必须是镜像里真有的命令（002 §9.6）。
`python:slim` 既没有 `wget` 也没有 `curl` —— 不装的话，组件明明跑得好好的，
平台却判它 unhealthy，依赖方永远等不到它。**这是真踩过的**：

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

## 17.4 装进项目

### ▶️ 操作

```bash
mkdir -p ~/myproj && cd ~/myproj
brickkit init my-project
```

`init` 生成的骨架里，本地源默认指向项目自己的 `./components`。你的组件写在
`~/mycomp` 下，所以把那一行的 `path` 改掉：

```yaml
sources:
  - id: local-dev
    type: local
    path: ~/mycomp        # ← 从 ./components 改成这里；指向 <scope>/<name> 的**上一层**
```

> 组件源码在 `~/mycomp/notify/webhook/`，而 `path` 要写到**上一层** `~/mycomp`
> ——本地源用 `<path>/<组件ID>/component.yaml` 定位，多写一层就找不到了。

```bash
brickkit add notify/webhook@1.0.0
```

### ✅ 预期

```
📦 添加 notify/webhook@1.0.0
   └── Manifest ✅
✅ 已写入 brickkit.yaml（1 个组件）
```

**平台已经认识你的组件了。** 它读了 `component.yaml`、校验了格式、写进了配置。

### 起来看看

```yaml
components:
  - id: notify/webhook
    version: 1.0.0
    expose: true
    exposePort: 18099
    config:
      keepMessages: 3      # ← 覆盖 configSchema 的默认值 20
```

```bash
brickkit up

curl http://localhost:18099/healthz
for t in 一 二 三 四; do
  curl -s -X POST -H 'Content-Type: application/json' \
    -d "{\"text\":\"消息$t\"}" http://localhost:18099/api/v1/messages
done
curl -s http://localhost:18099/api/v1/messages
```

### ✅ 预期

```json
{"messages":[{"text":"消息二",...},{"text":"消息三",...},{"text":"消息四",...}],"total":3}
```

**只留了 3 条 —— `keepMessages: 3` 生效了。** 看看平台注入了什么：

```bash
grep -A 4 "environment:" .brickkit/generated/docker-compose.yaml
```

```
      - COMPONENT_ID=notify/webhook
      - COMPONENT_VERSION=1.0.0
      - KEEP_MESSAGES=3
```

### ⏹️ 怎么停

```bash
brickkit down
```

## 17.5 让它依赖别人

组件的价值在于**拼**。给它加一个依赖：

### ▶️ 操作

```yaml
# component.yaml
dependencies:
  components:
    - people/basic@1.0.0            # 强依赖：注入 PEOPLE_BASIC_ENDPOINT
    - id: infra/redis-event-bus@1.0.0
      optional: true                # 弱依赖：没装就完全不注入
  resources:
    - kind: database
      engine: postgresql            # 注入 DATABASE_HOST / PORT / NAME / USER / PASSWORD
```

代码里这样用：

```go
// 强依赖：缺了就启动失败，并说明这个变量由谁负责给
peopleEndpoint := os.Getenv("PEOPLE_BASIC_ENDPOINT")
if peopleEndpoint == "" {
	fail("缺少 PEOPLE_BASIC_ENDPOINT（由平台按 Manifest 的强依赖注入，见 003 §4.5）")
}

// 弱依赖：**空是正常状态**，不是错误
busEndpoint := os.Getenv("INFRA_REDIS_EVENT_BUS_ENDPOINT")
if busEndpoint == "" {
	logger.Warn("事件总线未启用，事件不会发出", "影响", "仅事件不发送，业务不受影响")
}
```

**弱依赖那一段是关键**：把它当必需项校验，就等于把弱依赖变成了强依赖 ——
一个从没装过事件总线的项目会永远启动不了你的组件。

`brickkit add` 之后 CLI 会递归把依赖也拉进来，`brickkit order` 能看到完整的图。

## 17.6 本地调试：在 IDE 里改代码

改一行就重新 build 镜像太慢。`local: true` 让组件跑在你的 IDE 里，
其余组件照常在容器里。

### ▶️ 操作

```yaml
components:
  - id: notify/webhook
    version: 1.0.0
    local: true          # ← 不生成容器
    localPort: 9099      # ← 你的进程监听这个端口
```

```bash
brickkit up
```

CLI 会：

- **不给它生成容器**
- 依赖方容器里，`NOTIFY_WEBHOOK_ENDPOINT` 指向宿主机（`extra_hosts` + `host-gateway`）
- 把它要用的依赖与资源**映射到宿主机端口**
- 生成 `.brickkit/generated/local-debug.notify-webhook-1-0-0.env`

那个 env 文件直接喂给 IDE（VS Code 的 `envFile`、IntelliJ 的 EnvFile 插件），
或者：

```bash
set -a && . .brickkit/generated/local-debug.notify-webhook-1-0-0.env && set +a
go run .
```

> **文件里的值是已经求好的**，不是 `${VAR}` —— IDE 的 envFile 不做变量替换，
> 留占位符等于把一串没用的字符串喂给程序。

细节见 [07-本地调试.md](07-本地调试.md)。

## 17.7 发布到市场

### ▶️ 操作

先把市场跑起来（[10-组件市场.md](10-组件市场.md)），登录，然后：

```bash
brickkit publish --path ~/mycomp/notify/webhook \
  --source-type git --git-url https://github.com/you/notify-webhook.git
```

### ✅ 预期

```
📤 发布 notify/webhook@1.0.0
   ✅ Manifest 校验通过
   ✅ 镜像引用有效：my/notify-webhook:1.0.0
   ✅ 上传成功
🎉 发布完成
```

### 想让别人生成客户端代码

在 `component.yaml` 里声明产物（002 §7 契约即产物）：

```yaml
artifacts:
  - type: api-contract
    format: protobuf
    files: [proto/notify/v1/notify.proto]
  - type: api-docs
    format: openapi
    files: [openapi.json]
```

发布时会一起上传，调用方 `add` 之后就在 `.brickkit/artifacts/` 里 ——
**不需要读你的源码，也不需要你的服务在跑**（见 [15-查看组件文档.md](15-查看组件文档.md)）。

闭源组件（`sourceType: registry`）**必须**提供 `api-contract`，
否则市场拒绝发布：代码可以闭源，API 契约不能（008 §1.5）。

### 顺手签个名

```bash
COSIGN_PASSWORD="" brickkit publish --path ~/mycomp/notify/webhook \
  --sign --key keys/my-release.key --signed-by me@example.com
```

细节见 [11-组件签名.md](11-组件签名.md)。

## 自查清单

写完一个组件，对着过一遍：

| # | 检查 | 怎么验 |
| --- | --- | --- |
| 1 | 配置全部来自环境变量，**没有硬编码地址** | `grep -rn "localhost\|127.0.0.1" *.go` |
| 2 | 缺必需配置时**启动失败**，不用默认值顶上 | 少给一个变量跑一次 |
| 3 | `/healthz` 不查库、不调依赖 | 把依赖停掉，healthz 仍应 200 |
| 4 | 日志是 JSON 且带 `componentId` | `docker logs <容器> \| head -1 \| python3 -m json.tool` |
| 5 | 口令不进日志 | `docker logs <容器> \| grep -i <你的口令>` |
| 6 | 容器非 root | `docker exec <容器> id` |
| 7 | 空列表返回 `[]` 不是 `null` | 查一个空结果 |
| 8 | 强依赖挂了报 **503**，不是 500、不是空列表 | 把依赖停掉试一次 |
| 9 | 弱依赖缺席时**业务照常完成** | 不注入那个变量试一次 |
| 10 | Manifest 声明的产物文件真的存在 | `brickkit publish` 会替你查 |
| 11 | 有迁移的话，**重复执行不出错** | 连跑两次 migrate |
| 12 | 健康检查用的命令镜像里真有 | `docker exec <容器> which curl` |

第 8、9 两条是最容易做错的 —— 前面几节里所有的"亲手弄坏它"实验，
验的都是别人的组件在这两条上做得对不对。

想找**范例**的话，按你的场景挑一个抄：

| --- | --- | --- |
