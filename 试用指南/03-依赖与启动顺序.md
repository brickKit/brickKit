## 3.1 看一眼启动顺序

`brickkit up --dry-run` **只算不启动**，是最安全的探路命令：它把 `up` 会做的计算
全做一遍、把部署文件生成出来，但一个容器都不起。

### ▶️ 操作

```bash
brickkit up --dry-run
```

### ✅ 预期

先是两条警告——**这里出现它们是对的**，下面「两条警告怎么读」会解释：

```
🚀 启动项目 demo-shop（deploy.target: docker）
⚠️ 警告：弱依赖缺失：demo/bus@1.0.0
   ...
⚠️ 警告：资源依赖未满足（--dry-run 不阻断）
   ...
```

然后是这一节真正要看的三段：

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             被 demo/caller 依赖
   ✅ demo/caller@1.0.0            根组件（没有其他组件依赖它）
   ✅ department/tree@1.0.0        被 people/basic 依赖
   ⬜ infra/redis-event-bus@1.0.0  级联跳过（只被弱依赖引用；需要它时请显式写 enabled: true）
   ✅ people/basic@1.0.0           根组件（没有其他组件依赖它）

📋 启动顺序（拓扑排序）：
   1. demo-hello-1-0-0       无依赖
   2. demo-caller-1-0-0      ← 依赖 1
   3. department-tree-1-0-0  无依赖
   4. people-basic-1-0-0     ← 依赖 3

可独立启动：demo-hello-1-0-0、department-tree-1-0-0（无依赖）
必须最后启动：people/basic（需等前 3 个组件就绪）

依赖图：
   people/basic@1.0.0 → department/tree@1.0.0
                      → infra/redis-event-bus@1.0.0（弱）
   demo/caller@1.0.0 → demo/hello@1.0.0
                     → demo/bus@1.0.0（弱，未安装）
```

最后一行是 `📄 已生成：.brickkit/generated/docker-compose.yaml`——
`--dry-run` 会真的写出那份文件（它在 `.gitignore` 里），只是不启动。

三段输出各自回答一个问题：

| 段 | 回答 |
| --- | --- |
| 组件状态计算 | **谁会启动、为什么** —— 五行，四个跑、一个不跑，每行都写着理由 |
| 启动顺序 | 按什么顺序起，谁等谁。**只排会启动的那四个** |
| 依赖图 | 依赖关系长什么样，弱依赖标出来 |

**两条警告怎么读：** 它们在这一篇里都是预期内的，不用去修。

- **弱依赖缺失 `demo/bus`**：基准配置里故意留了一个不存在的弱依赖，
  好让你在下面的依赖图里看到「弱，未安装」长什么样。
- **资源依赖未满足**：这三个组件都声明了要一个 postgresql 库，而基准配置还没有
  `resources`。`--dry-run` 只警告不阻断（不加 `--dry-run` 时这里会直接停下来），
  代价是生成的 compose 里没有 `DATABASE_*` 变量。资源怎么声明与绑定见
  [05 §5.2](05-Docker启动全流程.md)。

两个容易看漏的地方：

- **`infra/redis-event-bus` 装进来了，却不启动。** 它是 `people/basic` 的**弱**依赖，
  `add` 时被顺带拉了进来，但级联的规矩是"只被弱依赖引用的组件不自动启动"——
  弱依赖本来就是"有更好、没有也行"。要它跑就显式写 `enabled: true`（见 [04](04-组件开启模式.md)）。
  对照着看：`demo/bus` 是**真不存在**，所以依赖图里标的是「弱，未安装」，
  而 `infra/redis-event-bus` 只标「弱」。
- **不启动的组件不进启动顺序，但仍然出现在状态计算里。** 状态计算回答的是"谁会跑、为什么"，
  把不跑的连同理由一起列出来，才看得见级联的效果。

## 3.2 强依赖 vs 弱依赖

这是 BrickKit 里最需要先想清楚的一对概念。

| | 强依赖 | 弱依赖（`optional: true`） |
| --- | --- | --- |
| 声明在 | 组件的 `component.yaml` | 同左 |
| 找不到时 | ❌ **报错**，整个操作停下 | ⚠️ 警告一句，继续 |
| 环境变量 | 一定注入 `XXX_ENDPOINT` | **完全不注入**——不是注入空值 |
| 启动顺序 | 依赖方必须等它健康 | 不参与等待 |
| 被禁用时 | 依赖方跟着被级联跳过 | 依赖方照常启动 |

**"完全不注入"是关键。** 注入一个空的 `DEMO_BUS_ENDPOINT` 会让组件以为"配了但是空的"；不注入，组件用 `if os.Getenv(...) == ""` 就能干净地降级。

试验用的 `demo/caller` 与 `people/basic` 都故意声明了一个**不存在**的弱依赖，所以你每次命令都会看到那两条警告——那是**设计好的现象**，不是错误。

### ▶️ 看一眼组件是怎么声明的

```bash
grep -A 8 "^dependencies:" components/demo/caller/component.yaml
```

```yaml
dependencies:
  components:
    # 强依赖：地址注入为 DEMO_HELLO_ENDPOINT
    - demo/hello@1.0.0
    # 弱依赖：缺失时平台完全不注入 DEMO_BUS_ENDPOINT，组件自行降级
    - id: demo/bus@1.0.0
      optional: true
  resources:
    - kind: database
      engine: postgresql
```

## 3.3 循环依赖会被拦下来

### ▶️ 操作

临时给 `demo/hello` 加一条指回 `demo/caller` 的依赖：

```bash
cat >> components/demo/hello/component.yaml <<'EOF'
dependencies:
  components:
    - demo/caller@1.0.0
EOF
brickkit up --dry-run
```

### ✅ 预期

明确报出循环依赖并打印整条环，而不是无限递归或随便挑一个顺序。

### 恢复

```bash
cd <仓库根目录>
cp -r tests/components/demo-hello/component.yaml 试用指南/playground/components/demo/hello/component.yaml
```

## 3.4 多版本共存

同一个组件的两个版本可以同时写进配置，它们是**两个独立的容器**（服务名带版本，天然不冲突）：

```yaml
components:
  - id: demo/hello
    version: 1.0.0
  - id: demo/hello
    version: 2.0.0
```

`demo/caller@1.0.0` 依赖的是 `demo/hello@1.0.0`，它**不会**自动改指 2.0.0——依赖是写死版本的。详见 [08-升级与多版本.md](08-升级与多版本.md)。

## ⏹️ 怎么停

`up --dry-run` 不启动任何容器，只算一遍并写出 `.brickkit/generated/`
（那个目录在 `.gitignore` 里，删掉即可）。改坏了配置就 `git checkout brickkit.yaml`。
