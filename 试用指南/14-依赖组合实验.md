# 14 · 依赖组合实验（亲手弄坏它）

🎯 **这一节验证什么：** 把各个组件、资源一个个停掉，看**强依赖**、**弱依赖**、
**缓存**、**数据源**四种关系在故障时的表现有什么不同。

前置：走完 [13-完整装配.md](13-完整装配.md)，八个组件都在跑。

> 这一节没有"正常路径"。全都是故意弄坏 —— 因为组件之间的关系，
> 只有在坏掉的时候才看得出区别。

---

## 先记住这张表

后面每个实验都是在验证其中一行：

| 关系 | 挂了会怎样 | 谁是例子 |
| --- | --- | --- |
| **强依赖** | 调用方**如实报 503**，不假装 | `erp/backend` → `people/basic` |
| **弱依赖** | 调用方**照常完成业务**，只是少做一件事 | `erp/backend` → `infra/redis-event-bus` |
| **缓存资源** | 组件**回源**，只是慢一点 | `authorization/rbac` → Redis |
| **数据源资源** | 组件**503**，绝不假装收下 | `infra/redis-event-bus` → Redis |

最后两行用的是**同一个 Redis 容器**。这是这一节最值得看的地方。

---

## 14.1 停掉一个强依赖

`erp/backend` 强依赖 `people/basic`（订单上的姓名从那儿来）。

### ▶️ 操作

```bash
docker stop $(docker ps -qf name=people-basic)

TOKEN=$(curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"demo-password"}' \
  http://localhost:18080/api/v1/login | python3 -c "import json,sys;print(json.load(sys.stdin)['token'])")

curl -s -w "\nHTTP %{http_code}\n" -H "Authorization: Bearer $TOKEN" \
  http://localhost:18080/api/v1/orders
```

### ✅ 预期

```
{"error":"依赖的组件暂时不可用，请稍后重试"}
HTTP 503
```

**503 而不是 500，也不是空列表。** 三者的区别很要紧：

- 返回**空列表**等于说"你没有订单" —— 使用者会以为数据丢了
- 返回 **500** 等于说"我坏了" —— 运维会来查 `erp/backend`，而它好好的
- 返回 **503** 才是实话："我这边依赖的东西暂时不可用"

再看一眼门户本身：

```bash
curl -s -o /dev/null -w "门户静态页 HTTP %{http_code}\n" http://localhost:18080/
```

```
门户静态页 HTTP 200
```

**前端照常发页面。** nginx 的反向代理用的是"每次请求时解析地址"，
后端不可用只影响 `/api/`，不影响静态资源 —— 用户至少能看到一个说明页面，
而不是浏览器的连接错误。

### ⏹️ 恢复

```bash
docker start $(docker ps -aqf name=people-basic)
sleep 4
```

## 14.2 停掉一个弱依赖

`erp/backend` 弱依赖 `infra/redis-event-bus`（审批后发一条事件）。

### ▶️ 操作

```bash
docker stop $(docker ps -qf name=infra-redis-event-bus)

curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:18080/api/v1/orders/o-3/approve
```

### ✅ 预期

```json
{"approvedBy":"p-001","eventPublished":false,"orderId":"o-3","status":"approved"}
```

**审批成功了。** 这就是弱依赖：事件总线不在，业务照常完成。

但要验的不只是"返回了 200"，而是**状态确实变了**：

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:18080/api/v1/orders \
  | python3 -c "
import json,sys
for o in json.load(sys.stdin)['orders']:
    if o['id']=='o-3': print('o-3 →', o['status'])"
```

```
o-3 → approved
```

若审批在发事件失败时把状态回滚了，接口照样返回 200，但弱依赖已经被偷偷变成了
强依赖 —— **只测状态码看不出来**。

同时 `eventPublished: false` 如实说明事件没发出去，没有假装发了。

### ⏹️ 恢复

```bash
docker start $(docker ps -aqf name=infra-redis-event-bus)
```

## 14.3 同一个 Redis，两种角色

这是这一节的重点。`authorization/rbac` 和 `infra/redis-event-bus` 绑的是
**同一个 Redis 容器**，但它挂掉时两者的表现完全相反。

### ▶️ 操作

```bash
docker stop $(docker ps -qf name=erp-demo-redis)
sleep 1
```

**先看 `authorization/rbac`**（Redis 是它的**加速器**）：

```bash
curl -s -o /dev/null -w "查订单 HTTP %{http_code}\n" \
  -H "Authorization: Bearer $TOKEN" http://localhost:18080/api/v1/orders
```

```
查订单 HTTP 200
```

**照常工作。** 权限缓存没了就回源查数据库，只是慢一点。

**再看 `infra/redis-event-bus`**（Redis 是它的**唯一数据源**）：

```bash
NET=$(docker inspect $(docker ps -qf name=erp-backend) \
  --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}')

docker run --rm --network "$NET" curlimages/curl:latest -s -w "\nHTTP %{http_code}\n" \
  -X POST -H 'Content-Type: application/json' \
  -d '{"type":"erp.order.approved","actor":"p-001"}' \
  http://infra-redis-event-bus-1-0-0:8080/api/v1/events
```

```
{"error":"事件存储暂时不可用，请稍后重试"}
HTTP 503
```

**如实报错，绝不假装收下。** 假装成功等于把事件悄悄丢掉，而发布方会以为
它已经安全落地，再也不会重发 —— 那比直接报错糟得多。

> 为什么要用 `docker run --network` 绕一圈：事件总线**没有 `expose: true`**，
> 它不映射端口到宿主机（008 §5.2：默认不暴露）。要从外面访问它，
> 只能进到同一个容器网络里。

### 两者的健康检查都还是 200

```bash
docker inspect $(docker ps -qf name=authorization-rbac) --format '{{.State.Health.Status}}'
docker inspect $(docker ps -qf name=infra-redis-event-bus) --format '{{.State.Health.Status}}'
```

```
healthy
healthy
```

**健康检查只回答"本进程还活着吗"**（002 §9.4）。去探 Redis 的话，
Redis 一抖，编排系统就会把这两个**本身完全正常**的容器杀掉重启 ——
而重启并不会让 Redis 变好，只会让恢复之后还要多等一轮拉起。

### ⏹️ 恢复

```bash
docker start $(docker ps -aqf name=erp-demo-redis)
```

## 14.4 用 enabled 关掉一个组件

前面是"容器挂了"，这里是"配置里就没打算启动它"。

### ▶️ 操作

```yaml
  - id: erp/backend
    version: 1.0.0
    enabled: false          # ← 关掉中间那一层
```

```bash
brickkit up --dry-run
```

### ✅ 预期

**报错**——`portal/user-frontend` 强依赖 `erp/backend`：

```
❌ 错误：强依赖被显式关闭
   被关闭的组件：erp/backend@1.0.0（enabled: false）
   强依赖它的：portal/user-frontend@1.0.0
   ...
```

平台**不会**替你把门户也关掉。那是一次隐式决定，而门户没跑的线索只有输出里
一闪而过的一行——等你发现，线索已经断了。

### ▶️ 按报错的建议改：一起关掉

```yaml
  - id: erp/backend
    version: 1.0.0
    enabled: false
  - id: portal/user-frontend
    version: 1.0.0
    enabled: false          # ← 依赖方也关掉
    expose: true
```

```
📋 组件状态计算：
   ⬜ erp/backend@1.0.0           显式禁用（enabled: false）
   ⬜ portal/user-frontend@1.0.0  显式禁用（enabled: false）
   ✅ people/basic@1.0.0          启动
   ...
```

**`people/basic`、`auth`、`rbac` 照常启动**——它们只是暂时没人调，而"没人调"
不是关掉它们的理由。配置里写着什么，跑的就是什么。

### 想只留底层组件？

```bash
brickkit up --only people/basic
```

`--only` 会连它的依赖一起拉起（`department/tree` 与弱依赖 `infra/redis-event-bus`），
但不碰上层，而且**不动配置**。

### ⏹️ 恢复

把这两行 `enabled: false` 删掉。

---

## 14.5 为什么是报错，而不是替你收敛

`enabled: false` 只表达一件事：**这个组件不跑**。它不表达"顺便把依赖它的也停了"。

| 关掉的是 | 结果 |
| --- | --- |
| 有人**强**依赖它 | ❌ 报错，点名依赖方，两条出路都给出来 |
| 只有人**弱**依赖它 | ✅ 正常：调用方拿不到 `*_ENDPOINT`，按自己的降级逻辑处理 |
| 没人依赖它 | ✅ 正常 |

早先平台会"级联"：关掉 `erp/backend`，门户自动跟着跳过，输出里一行
"级联跳过"就过去了。删掉它的理由见 [012 §2.14](../design/012-架构设计原理与考量.md)——
一句话：那是平台替你做的隐式决定，而"我只想这次跑一个子集"有 `--only` 这条
更直接、还不动配置的路。

## 14.6 一次看清所有关系

### ▶️ 操作

```bash
brickkit up --dry-run
```

### ✅ 预期

```
📋 启动顺序（拓扑排序）：
   1. department-tree-1-0-0     无依赖
   2. infra-redis-event-bus-1-0-0  无依赖
   3. people-basic-1-0-0        ← 依赖 1
   ...

依赖图：
   portal/user-frontend@1.0.0 → erp/backend@1.0.0
   erp/backend@1.0.0 → people/basic@1.0.0
                     → auth/password-login@1.0.0
                     → authorization/rbac@1.0.0
                     → infra/redis-event-bus@1.0.0（弱）
   ...
```

标了 `（弱）` 的就是弱依赖。这张图是判断"停掉某个组件会波及谁"的依据。

## 实验清单（对照着做一遍）

| # | 做什么 | 该看到什么 |
| --- | --- | --- |
| 1 | 停 `people/basic` | `/api/v1/orders` → 503；门户静态页仍 200 |
| 2 | 停 `infra-redis-event-bus` | 审批仍成功，`eventPublished:false`，**状态确实变了** |
| 3 | 停 Redis | `rbac` 照常（回源）；`event-bus` 503（数据源）；两者健康检查都还是 healthy |
| 4 | `erp/backend` 设 `enabled: false` | **报错**：门户强依赖它 |
| 5 | 门户也设 `enabled: false` | 两个都不跑，其余组件照常 |
| 6 | 停 `department/tree` | `people/basic` 的人员接口 503，但 `/healthz` 仍 200 |

第 6 条留给你自己试 —— 它验证的是"强依赖故障不会顺着链条把健康检查也带塌"。
