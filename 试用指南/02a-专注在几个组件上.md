# 02a · 专注在几个组件上

🎯 **这一节验证什么：** 项目里躺着十个组件，今天只动其中一个——怎么把其余九个从眼前挪开，干完再一条命令收回来，而 `brickkit.yaml` 一个字节不动。

前置：组件已经装进项目——[02](02-添加与移除组件.md) 走到 §2.3（`add --local`）即可。想直接从这里开始：

```bash
./试用指南/准备.sh --reset
cd 试用指南/playground && brickkit init demo-shop && brickkit add --local --yes
```

**不需要 Docker**——本节只搬目录，不启动任何容器。

> **这一篇讲的是日常最常用的那个动作。** 真正的 `deploy` 一个项目一辈子做不了几次，
> 而"今天我只搞这几个组件"是每天都在发生的事。[02 §2.5](02-添加与移除组件.md) 讲的是
> sync 跟着 `enabled` 走的那一面（与 `brickkit up` 一致），这里讲的是**开发时**怎么用它。

---

## 2a.1 问题：十个组件，今天只动一个

`add --local` 之后，`components/` 下是这样：

```bash
find components -mindepth 2 -maxdepth 2 -type d | sort
```

```
components/auth/password-login
components/authorization/rbac
components/demo/caller
components/demo/hello
components/department/tree
components/erp/backend
components/infra/api-docs
components/infra/redis-event-bus
components/people/basic
components/portal/user-frontend
```

十个目录，每个都是独立的 Git 仓库。你今天要改的是 `people/basic`，但：

- IDE 的全局搜索每次都在十份代码里翻；
- 侧栏要滚三屏才找到你要的那个；
- 让 AI 帮你看代码时，它也得先把这十个都扫一遍才知道哪个相关。

## 2a.2 `sync --only`：只留今天要动的

### ▶️ 操作

```bash
brickkit sync --only people/basic
```

### ✅ 预期

```
🎯 --only：只保留 people/basic 及其强依赖（brickkit.yaml 未修改）
📂 工作区整理：
   📦 components/auth/password-login/      → components/.archived/auth/password-login
      原因：未被 --only 选中
   📦 components/authorization/rbac/       → components/.archived/authorization/rbac
      原因：未被 --only 选中
   📦 components/demo/caller/              → components/.archived/demo/caller
      原因：未被 --only 选中
   📦 components/demo/hello/               → components/.archived/demo/hello
      原因：未被 --only 选中
   ✅ components/department/tree/          活跃
   📦 components/erp/backend/              → components/.archived/erp/backend
      原因：未被 --only 选中
   📦 components/infra/api-docs/           → components/.archived/infra/api-docs
      原因：未被 --only 选中
   📦 components/infra/redis-event-bus/    → components/.archived/infra/redis-event-bus
      原因：未被 --only 选中
   ✅ components/people/basic/             活跃
   📦 components/portal/user-frontend/     → components/.archived/portal/user-frontend
      原因：未被 --only 选中
✅ 工作区整理完成（2 个活跃，8 个归档，0 个激活）
```

眼前只剩两个：

```bash
find components -mindepth 2 -maxdepth 2 -type d | sort
```

```
components/.archived/auth
components/.archived/authorization
components/.archived/demo
components/.archived/erp
components/.archived/infra
components/.archived/portal
components/department/tree
components/people/basic
```

**`department/tree` 为什么也留下了？** 它是 `people/basic` 的**强依赖**——改人员组件时多半要看一眼部门组件的接口。`--only` 留的永远是"点名的那些 + 它们的强依赖"，与 [`brickkit up --only`](04-组件开启模式.md) 是同一套语义。

想同时搞两个就都写上：

```bash
brickkit sync --only people/basic,demo/hello
```

## 2a.3 `brickkit.yaml` 一个字节没动

```bash
git diff --stat brickkit.yaml     # 项目已提交 Git 时
```

没有任何输出。**这是 `--only` 存在的全部理由。**

不用 `--only` 也能达到同样的效果，代价是去改配置：把不想要的根组件逐个写上 `enabled: false`，再把想要的写上 `enabled: true`（不写会被级联一起跳过——[02 §2.4](02-添加与移除组件.md) 演示这件事时，十个组件动了八行）。

问题不在于"八行很麻烦"，而在于**改的是哪个文件**：

| | `brickkit.yaml` | "我今天看哪几个组件" |
| --- | --- | --- |
| 归属 | 团队共享，提交进 Git（003 §10.2） | 个人的 |
| 时效 | 长期的部署声明 | 临时的，今天下班就没了 |
| 影响 | 决定**跑什么** | 决定**看什么** |

绑在一起只剩两个坏选项：把个人偏好提交上去（队友拉下来发现半个系统被关了），或者背一个永远脏着的 diff，每次 pull 都可能冲突。

`--only` 把它摘出来了：**只动目录，不动配置。**

## 2a.4 干完活：一条命令收回来

### ▶️ 操作

```bash
brickkit sync
```

### ✅ 预期

```
📂 工作区整理：
   📂 components/.archived/auth/password-login → components/auth/password-login/
      原因：恢复启用
   📂 components/.archived/authorization/rbac → components/authorization/rbac/
      原因：恢复启用
   📂 components/.archived/demo/caller     → components/demo/caller/
      原因：恢复启用
   📂 components/.archived/demo/hello      → components/demo/hello/
      原因：恢复启用
   ✅ components/department/tree/          活跃
   📂 components/.archived/erp/backend     → components/erp/backend/
      原因：恢复启用
   📂 components/.archived/infra/api-docs  → components/infra/api-docs/
      原因：恢复启用
   ✅ components/people/basic/             活跃
   📂 components/.archived/portal/user-frontend → components/portal/user-frontend/
      原因：恢复启用
✅ 工作区整理完成（2 个活跃，0 个归档，7 个激活）
```

**不带参数的 `sync` 就是"恢复"**：它回到与 `brickkit up` 一致的状态——会启动的留下，不启动的归档。

⚠️ 数一下：刚才归档了 8 个，这次只搬回来 7 个。少的那个是 `infra/redis-event-bus`——它**只被弱依赖引用**，级联本来就不会启动它（[03 §3.1](03-依赖与启动顺序.md)），所以"回到与 up 一致"就意味着它继续待在归档里。想让它出来，给它写 `enabled: true`。

## 2a.5 归档 ≠ 消失

这是用它之前唯一需要确认的事。归档目录里的组件：

| | 说明 |
| --- | --- |
| **平台照常算得出来** | `brickkit.yaml` 里那一行还在，`order` / `up` 的依赖图与级联计算一个都不少。本地安装源按组件 ID 查找时会回落到归档目录（004 §3.9） |
| **Git 仓库完好** | 整个目录连 `.git` 一起搬走，进去 `git status` / `git log` / 提交推送全都照常 |
| **位置固定** | 永远是 `components/.archived/<scope>/<name>/`。不打开就不用关心，真要看时一眼知道在哪 |
| **`add --local` 不会把它拽回来** | 批量添加只扫活跃目录——刚归档完又被一条命令拉回配置里，那就白整理了 |
| **`remove` 会连它一起删** | 组件一旦从 `brickkit.yaml` 移除，sync 就不再认识它，归档里那份不清掉就是永远没人回收的孤儿（[02 §2.6](02-添加与移除组件.md)） |

第一条可以直接验：把八个组件归档、再把 Manifest 缓存删掉，`order` 照样算得出完整依赖图。

```bash
brickkit sync --only people/basic
rm -rf .brickkit/manifests
brickkit order
```

十个组件一个不少地出现在「组件状态计算」里——归档只改变**看不看得见**，不改变**取不取得到**。

## 2a.6 两种用法怎么选

| 我想 | 用哪个 |
| --- | --- |
| 这两天只搞某几个组件 | `brickkit sync --only <组件>` |
| 干完了，恢复原状 | `brickkit sync` |
| 长期不跑某个组件（团队都不跑） | 给它写 `enabled: false`，再 `brickkit sync` |

前两个是**个人的、临时的**，不进 Git；第三个是**团队的、长期的**，该进 Git。这条线就是选择的依据。
