# 04 · 组件开启模式（重点）

🎯 **这一节验证什么：** 一个组件到底"开着"还是"关着"，一共有几种表达方式，它们互相怎么影响。

规则本身只有一句，但它有几处**反直觉的邻居**，值得一个个亲手试。全程用 `brickkit up --dry-run`（只算不启动），几秒钟一次。

前置：**五组件基准**（`./试用指南/准备.sh --baseline`，见 [00](00-准备.md)）；概念上接着 [03](03-依赖与启动顺序.md)。
**不需要 Docker**——`brickkit up --dry-run` 只做计算并生成部署文件，不碰引擎。

> 这一篇里 `--dry-run` 每次都会附带两条警告（弱依赖 `demo/bus` 缺失、资源依赖未满足）。
> 都是基准配置本来就有的，与 `enabled` 无关，看状态计算那一段就好——
> 来由见 [03 §3.1](03-依赖与启动顺序.md)。

---

## 一张总表

| 写法 | 含义 |
| --- | --- |
| 不写 `enabled` | ✅ 启动（`brickkit add` 写进来的就是这个样子） |
| `enabled: true` | ✅ 启动（**与不写完全等价**，写出来只是为了显眼） |
| `enabled: false` | ❌ 不启动 |
| `--only A,B` | 本次只启动 A、B 及其依赖，命令行临时收窄，不改配置 |
| `local: true` | 不生成容器，你在 IDE 里跑它（仍算"启动中"） |
| `expose: true` | 映射到宿主机 / 生成 Ingress（与开关无关） |

一句话：**配置里有它、又没写 `enabled: false`，就启动。**

强依赖与弱依赖在这件事上**一视同仁**——`optional: true` 管的是"取不到算不算错"，
不管"跑不跑"。

---

## 4.1 什么都不写

### ▶️ 操作

```bash
brickkit up --dry-run
```

### ✅ 预期

五个组件全是 `✅`——**一行都没写过 `enabled`**：

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             启动
   ✅ demo/caller@1.0.0            启动
   ✅ department/tree@1.0.0        启动
   ✅ infra/redis-event-bus@1.0.0  启动
   ✅ people/basic@1.0.0           启动
```

注意 `infra/redis-event-bus`：它**只被 `people/basic` 弱依赖**，没有任何人强依赖它，
但它照样启动。配置里写了它，那就是你的声明。

> 往下拉一点还能看到这一行：
>
> ```
> 只被弱依赖引用（关掉不影响别人：enabled: false）：infra/redis-event-bus
> ```
>
> 这是嫌容器太多时**可以下手的名单**：关掉它，调用方拿不到 `INFRA_REDIS_EVENT_BUS_ENDPOINT`，
> 按自己的降级逻辑处理，没有第三方受影响。

## 4.2 关掉一个没人强依赖的组件

### ▶️ 操作

给 `infra/redis-event-bus` 加一行 `enabled: false`：

```yaml
  - id: infra/redis-event-bus
    version: 1.0.0
    enabled: false          # ← 加这一行
```

```bash
brickkit up --dry-run
```

### ✅ 预期

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             启动
   ✅ demo/caller@1.0.0            启动
   ✅ department/tree@1.0.0        启动
   ⬜ infra/redis-event-bus@1.0.0  显式禁用（enabled: false）
   ✅ people/basic@1.0.0           启动
```

**只有它自己不跑，别人一个都没受影响。** `people/basic` 照常启动——它弱依赖那个组件，
拿不到地址就自己降级，这正是弱依赖存在的意义。

### 恢复

删掉那一行，继续下一步。

---

## 4.3 关掉一个被强依赖的组件 → 报错

### ▶️ 操作

改成给 `demo/hello` 加 `enabled: false`（`demo/caller` **强依赖**它）：

```yaml
  - id: demo/hello
    version: 1.0.0
    enabled: false          # ← 换成给它加
```

```bash
brickkit up --dry-run
```

### ✅ 预期

**报错**，而不是替你把 `demo/caller` 也关掉：

```
❌ 错误：强依赖被显式关闭
   被关闭的组件：demo/hello@1.0.0（enabled: false）
   强依赖它的：demo/caller@1.0.0
   原因：依赖方启动后必然连不上它；平台不会替你把依赖方一起关掉——那是一次隐式决定，而它们没跑的线索只有输出里一闪而过的一行
   建议：
   1. 要一起关掉就给依赖方也写 enabled: false
   2. 或者移除 demo/hello 的 enabled: false
   3. 只是这一次想跑一个子集的话，用 brickkit up --only <组件>，不必动配置
```

> **这里曾经不是这样。** 早先平台会"级联"：关掉 `demo/hello`，`demo/caller` 自动跟着跳过，
> 输出里一行"级联跳过"就过去了。那是平台替你做的一次**隐式**决定——
> 等你发现 `demo/caller` 没跑，线索已经断了。现在决定权交回给你，两条出路都摆在报错里。

### ▶️ 按建议 1 改：一起关掉

```yaml
  - id: demo/hello
    version: 1.0.0
    enabled: false
  - id: demo/caller
    version: 1.0.0
    enabled: false          # ← 依赖方也关掉
```

```
📋 组件状态计算：
   ⬜ demo/hello@1.0.0             显式禁用（enabled: false）
   ⬜ demo/caller@1.0.0            显式禁用（enabled: false）
   ✅ department/tree@1.0.0        启动
   ✅ infra/redis-event-bus@1.0.0  启动
   ✅ people/basic@1.0.0           启动
```

两行 `enabled: false` 换来的是：**配置里写着什么，跑的就是什么**，不需要在脑子里
再跑一遍推导。

### 恢复

把这两行 `enabled` 都删掉，再 `brickkit up --dry-run` 确认回到全 `✅`。

## 4.4 `--only`：本次只启动这些

改配置是持久的、要提交进 Git 的；`--only` 是**这一次**的，不动配置。

### ▶️ 操作

```bash
brickkit up --only people/basic --dry-run
```

### ✅ 预期

```
🎯 --only：只启动 people/basic 及其依赖
📋 组件状态计算：
   ⬜ demo/hello@1.0.0             未被 --only 选中
   ⬜ demo/caller@1.0.0            未被 --only 选中
   ✅ department/tree@1.0.0        启动
   ✅ infra/redis-event-bus@1.0.0  启动
   ✅ people/basic@1.0.0           启动
```

**它的依赖会被自动带上**：`department/tree`（强依赖）与 `infra/redis-event-bus`（弱依赖）。

> 弱依赖也带上，是因为"跑不跑"上强弱本来就一视同仁。只取强依赖的话，
> 你会得到一个**异步功能是哑的** `people/basic`——而你点它的名是想把它跑起来用。

写法：

```bash
brickkit up --only people/basic                    # 该组件的所有版本
brickkit up --only people/basic@1.0.0              # 只这个版本
brickkit up --only people/basic,demo/caller        # 多个，逗号分隔
brickkit down --only people/basic                  # down 也支持
```

`brickkit.yaml` **一个字都没改**——下次不带 `--only` 就恢复全量。

> 想让"只看这几个组件的源码"也跟着收窄，见 [02a](02a-专注在几个组件上.md) 的
> `brickkit sync --only`：同一套依赖闭包，只动目录，同样不改配置。

## 4.5 `local: true`：这个组件我在 IDE 里跑

```yaml
  - id: people/basic
    version: 1.0.0
    local: true
    localPort: 8080      # 可选，不写就用组件自己声明的 deployment.port
```

它仍然是"启动中"的组件（依赖方要能找到它），但**不生成容器**。完整玩法见 [07-本地调试.md](07-本地调试.md)。

⚠️ `local: true` **只能配 `deploy.target: docker`**。K8s 下集群里的 Pod 连不到你的笔记本，CLI 会直接报错而不是悄悄跳过。

---

## 4.6 `expose`：让外面能访问

```yaml
  - id: portal/user-frontend
    version: 1.0.0
    expose: true
    hostname: portal.example.com    # K8s 必须；Docker 可省略
    exposePort: 18080               # 仅 Docker：自定义宿主机端口
```

| | Docker | K8s |
| --- | --- | --- |
| 怎么暴露 | 端口映射到宿主机 | 生成 Ingress，按 `hostname` 域名路由 |
| 默认端口 | 组件的 `deployment.port` | — |
| 端口冲突 | 两个组件抢同一个宿主机端口会在**生成阶段**就报错，用 `exposePort` 错开 | 不存在——域名不同就不冲突，所以 K8s 下 `exposePort` 完全不参与生成 |
| `hostname` | 可省略 | **必填**，不写直接报错 |

> **不写 `expose` 就不暴露。** 组件之间在容器网络 / 集群内互相访问**不需要** `expose`——它们用服务名直连。只有"浏览器要打开它"才需要。

## 4.7 组合起来的优先级

同时用了好几种时，按这个顺序判断：

```
1. --only 没选中它            → 不启动（最先判，命令行说了算）
2. enabled: false             → 不启动
3. 其余                       → 启动
```

外加一条校验：**正在启动的组件，它的强依赖不能是 `enabled: false`**，否则报错。

`local: true` 与 `expose: true` **不参与**"启不启动"的判断，它们只影响"**怎么**启动"。

## ⏹️ 怎么停

这一节只用 `up --dry-run`，**没有启动任何容器**（只写了 `.brickkit/generated/`，那个目录在 `.gitignore` 里）。

`--dry-run` 会在 `.brickkit/generated/` 下留一份部署文件，删不删都行：

```bash
rm -rf .brickkit/generated
```

配置改乱了：

```bash
git checkout brickkit.yaml
```
