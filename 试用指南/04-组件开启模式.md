# 04 · 组件开启模式（重点）

🎯 **这一节验证什么：** 一个组件到底跑不跑，是怎么算出来的；你想少跑几个时该动哪一行。

这是整个平台最容易想当然的地方，值得一个个亲手试。全程用 `brickkit up --dry-run`（只算不启动），几秒钟一次。

前置：**五组件基准**（`./试用指南/准备.sh --baseline`，见 [00](00-准备.md)）；概念上接着 [03](03-依赖与启动顺序.md)。
**不需要 Docker**——`brickkit up --dry-run` 只做计算并生成部署文件，不碰引擎。

> 这一篇里 `--dry-run` 每次都会附带两条警告（弱依赖 `demo/bus` 缺失、资源依赖未满足）。
> 都是基准配置本来就有的，与 `enabled` 无关，看状态计算那一段就好——
> 来由见 [03 §3.1](03-依赖与启动顺序.md)。

> **先跑通 [05](05-Docker启动全流程.md) 再看这篇也完全可以。**
> 这一篇是整个平台**最容易想当然**的地方，而有过一次「东西真的跑起来」的经历之后，
> 这里的每条规则都能对上具体现象。

---

## 一句话规则：跟着上层走

> **顶层组件默认跑；下层组件只要还有一个上层在跑，它就跑；写了 `enabled` 就按写的来。**

"上层"＝依赖它的那些组件。"顶层"＝没有任何组件依赖它——它是你装这个项目的**目的**，
所以默认就该跑。

| 写法 | 含义 |
| --- | --- |
| 不写 `enabled` | **跟着上层走**（绝大多数组件都该是这个状态） |
| `enabled: true` | **一定跑**，不看上层 |
| `enabled: false` | **一定不跑** |

**强依赖和弱依赖一视同仁。** 上层弱依赖它，它照样跟着跑。`optional: true` 管的是
另外两件事：取不到时只警告不阻断、它没在跑时不注入 `*_ENDPOINT`（见 [03](03-依赖与启动顺序.md)）。

于是**你要做的决定只有一个：这个顶层我要不要。** 下面那一串跟着走，不用你算。

## 4.1 什么都不写：全跑

### ▶️ 操作

```bash
brickkit up --dry-run
```

### ✅ 预期

五个组件全 `✅`——**一行 `enabled` 都没写过**，全是算出来的：

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             启动（demo/caller 需要）
   ✅ demo/caller@1.0.0            启动（顶层）
   ✅ department/tree@1.0.0        启动（people/basic 需要）
   ✅ infra/redis-event-bus@1.0.0  启动（people/basic 需要）
   ✅ people/basic@1.0.0           启动（顶层）
```

**每一行都写着它为什么跑**，这是你唯一需要的抓手：

- `启动（顶层）`——没人依赖它。这个项目里有两个顶层：`demo/caller` 和 `people/basic`
- `启动（X 需要）`——它跟着 X 跑。想让它不跑，去关 X（或关 X 的上层）

`infra/redis-event-bus` 只被 `people/basic` **弱**依赖，它照样跑。
弱依赖的意思是"连不上也能降级"，不是"默认不装"——你 `add` 的时候它就进配置了
（[02](02-添加与移除组件.md)），装了就该跑。嫌它重再关掉不迟，见 §4.4。

## 4.2 关掉一个组件：它那条链跟着关

链会往两个方向传播，各试一次。先试**往上**：关掉一个被别人强依赖的组件。

### ▶️ 操作

给 `demo/hello` 加一行 `enabled: false`（它被 `demo/caller` 强依赖）：

```yaml
components:
  - id: demo/hello
    version: 1.0.0
    enabled: false          # ← 加这一行
```

```bash
brickkit up --dry-run
```

### ✅ 预期

```
📋 组件状态计算：
   ⬜ demo/hello@1.0.0             显式禁用（enabled: false）
   ⬜ demo/caller@1.0.0            不启动（强依赖 demo/hello 不启动）
   ✅ department/tree@1.0.0        启动（people/basic 需要）
   ✅ infra/redis-event-bus@1.0.0  启动（people/basic 需要）
   ✅ people/basic@1.0.0           启动（顶层）
```

**你只关了一个组件，`demo/caller` 自动跟着不启动了**——它**强**依赖 `demo/hello`，
硬起来只会在运行时报连接错误。这是往**上**传播的那一条：强依赖不跑，依赖方也不跑。

另外三个组件完全不受影响：它们不在这条链上。

### 反过来试：关掉一个顶层（往下传播）

把 `demo/hello` 那行改回去，改成关顶层 `people/basic`：

```yaml
  - id: people/basic
    version: 1.0.0
    enabled: false
```

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             启动（demo/caller 需要）
   ✅ demo/caller@1.0.0            启动（顶层）
   ⬜ department/tree@1.0.0        不启动（上层都不启动）
   ⬜ infra/redis-event-bus@1.0.0  不启动（上层都不启动）
   ⬜ people/basic@1.0.0           显式禁用（enabled: false）
```

**关一行，三个组件跟着不跑。** 这是往**下**传播的那一条：上层全不跑，下层也不跑。
`department/tree` 和 `infra/redis-event-bus` 只有 `people/basic` 这一个上层，它没了，
它们也就没有存在的理由了。

而 `demo/caller` 那一支一动不动——**关掉一条链不会误伤别的链**。

---

## 4.3 被两个上层共用的组件：只要还有一个在跑，它就跑

上一步里 `department/tree` 跟着 `people/basic` 一起不跑，是因为它**只有这一个上层**。
如果 `demo/caller` 也依赖它呢？那 `people/basic` 关掉之后它照样跑——
`demo/caller` 还需要它。

规则里的字是"**只要还有一个**上层在跑"，不是"所有上层都在跑"。
所以共享的底层组件（人员、部门、权限这类）不会被谁误伤：
只有当依赖它的**全部**组件都不跑了，它才跟着停。

这也是为什么你不需要在脑子里算依赖图——**关顶层就行，共享的自己会保住自己。**

## 4.4 我就想单独跑下面某一个：`enabled: true`

`enabled: true` 的意思是"**这个一定跑，不看上层**"。

### ▶️ 操作

在上一步的基础上（`people/basic` 仍是 `enabled: false`），给 `department/tree` 加 `enabled: true`：

```yaml
  - id: department/tree
    version: 1.0.0
    enabled: true           # ← 一定跑
```

### ✅ 预期

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             启动（demo/caller 需要）
   ✅ demo/caller@1.0.0            启动（顶层）
   ✅ department/tree@1.0.0        启动（enabled: true）
   ⬜ infra/redis-event-bus@1.0.0  不启动（上层都不启动）
   ⬜ people/basic@1.0.0           显式禁用（enabled: false）
```

`department/tree` 的唯一上层还关着，它照样跑——理由那一列直接写着 `enabled: true`。
`infra/redis-event-bus` 没跟着回来：它的上层仍然只有关着的 `people/basic`。

**什么时候真的需要它？** 只想单独调一个底层组件（起个 API 给 Postman 打）、
或者某个组件无论如何都得在（权限之类）。**日常几乎用不到**——
绝大多数时候关顶层就够了。

## 4.5 冲突：钉住的组件撞上被关掉的强依赖

### ▶️ 操作

回到基准配置，然后同时写两行：

```yaml
  - id: demo/hello
    version: 1.0.0
    enabled: false          # 它不许跑

  - id: demo/caller
    version: 1.0.0
    enabled: true           # 而它一定要跑
```

```bash
brickkit up --dry-run
```

### ✅ 预期

**报错**，而不是二选一：

```
❌ 错误：强依赖 demo/hello 被禁用
   组件：demo/caller@1.0.0（enabled: true，已钉住）
   依赖链：demo/caller → demo/hello
   被禁用的组件：demo/hello@1.0.0
   建议：
   1. 在 brickkit.yaml 中移除 demo/hello 的 enabled: false
   2. 或去掉 demo/caller 的 enabled: true，让它随上层一起不启动
```

你同时表达了两个直接冲突的意图（"caller 必须起" + "它的强依赖不许起"），平台不替你猜，
把两条出路都摆出来。

**对比 §4.2**：那时 `demo/caller` **没写** `enabled`，同样的配置是**静默跟着不跑**——
那正是"我关掉了一整条链"的正常操作。

| `demo/caller` 怎么写 | 强依赖被关掉时 |
| --- | --- |
| 不写 `enabled` | ⬜ 跟着不跑，不报错——你就是想关掉这条链 |
| `enabled: true` | ❌ 报错——你说过它必须跑，那这就是矛盾 |

**报不报错的分界只有一条：你有没有说过"这个必须跑"。**

只有**强**依赖会这样。弱依赖被关掉不报错——它本来就允许不在。

### 恢复

```bash
git checkout brickkit.yaml
```

## 4.6 两个组件互相依赖：都是顶层，都跑

如果 A 弱依赖 B、B 也弱依赖 A，那么谁都不是"没有人依赖它"——按字面读，
两个都不是顶层，岂不是两个都不跑？

**不是。环上没有更上层的东西，它们互为顶层，两个都跑。**

想通这一点最快的办法是反过来读规则：平台算的不是"谁跑"，而是"**谁不跑**"。
从显式关掉的那些出发往外传播，环上的两个互为上层，谁也没先倒下，于是都留着。

关掉其中一个，另一个跟着不跑（它唯一的上层没了）——这与 §4.2 是同一条规则。

> 强依赖成环是**报错**的：那样根本排不出启动顺序（[03](03-依赖与启动顺序.md)）。
> 只有弱依赖可以成环——弱依赖不参与启动顺序，谁先起来都行。

## 4.7 一个都不跑的时候

把两个顶层都关掉：

```
📋 组件状态计算：
   ⬜ demo/hello@1.0.0             不启动（上层都不启动）
   ⬜ demo/caller@1.0.0            显式禁用（enabled: false）
   ⬜ department/tree@1.0.0        不启动（上层都不启动）
   ⬜ infra/redis-event-bus@1.0.0  不启动（上层都不启动）
   ⬜ people/basic@1.0.0           显式禁用（enabled: false）

📋 本次没有组件会启动
   顶层组件（没有别的组件依赖它们）这次都不跑：
      demo/caller@1.0.0  显式禁用（enabled: false）
      people/basic@1.0.0  显式禁用（enabled: false）
   移除其中一个的 enabled: false，它下面那条链会跟着回来（003 §4.3）
💡 有 5 个组件本次不启动，brickkit sync 可以把它们的源码收进 components/.archived/
```

平台不会只丢一张空表让你自己想——它**把顶层逐个列出来，连同各自的理由**，
因为该改哪一行完全取决于顶层是怎么死的：

| 顶层那一行的理由 | 该改哪里 |
| --- | --- |
| `显式禁用（enabled: false）` | 就是它自己那一行，删掉即可 |
| `不启动（强依赖 X 不启动）` | **不是它**——顶层压根没写过 `enabled`，要放开的是 X |

第二种就是 §4.2 第一个例子的处境：你关的是 `demo/hello`，倒下的是 `demo/caller`。
那时这里会写"顶层自己都没被关掉"，省得你去 `demo/caller` 那两行里白找一遍。

最后那一行是 [02](02-添加与移除组件.md) 讲过的 `brickkit sync`：
**`up` 决定跑什么，`sync` 让源码目录跟上**。改完 `enabled` 顺手跑一次，
`components/` 下就只剩这次真正在跑的那几个。

## 4.8 日常怎么用

```bash
# 1. 看 up 的输出，找出标着"（顶层）"的那几个
brickkit up --dry-run

# 2. 给这几天不搞的顶层写 enabled: false，然后
brickkit up          # 只跑剩下的
brickkit sync        # 源码目录也跟着收拢

# 3. 上线前恢复全量
git checkout brickkit.yaml
brickkit sync
brickkit up
```

> 组件源码跟项目一起进 Git 的项目，第 3 步用 `brickkit restore` 一条命令更稳——
> 它只动 `enabled`，不会像 `git checkout` 那样把你刚 `add` 完还没提交的组件一起吃掉。
> 见 [§4.11](#411-组件源码要跟项目一起进-git-的话)。

**没有 `--only` 这类参数。** 收窄范围只有改 `enabled` 一条路——
命令行参数记不住，配置文件打开就看得见，而且两个命令用的是同一套判定，
不会出现"目录里看不到的组件正在跑"。

不想把 `enabled: false` 提交给队友？`git checkout brickkit.yaml` 就回来了，
和你平时丢弃任何本地改动是同一个动作。

## 4.9 `local: true`：这个组件我在 IDE 里跑

```yaml
  - id: people/basic
    version: 1.0.0
    local: true
    localPort: 8080      # 可选，不写就用组件自己声明的 deployment.port
```

它仍然是"启动中"的组件（依赖方要能找到它），但**不生成容器**。完整玩法见 [07-本地调试.md](07-本地调试.md)。

⚠️ `local: true` **只能配 `deploy.target: docker`**。K8s 下集群里的 Pod 连不到你的笔记本，CLI 会直接报错而不是悄悄跳过。

## 4.10 `expose`：让外面能访问

```yaml
  - id: portal/user-frontend
    version: 1.0.0
    expose: true
    hostname: portal.example.com    # K8s 必须；Docker 可省略
    exposePort: 18080               # 仅 Docker：自定义宿主机端口
```

| | Docker | K8s |
| --- | --- | --- |
| 怎么暴露 | 端口映射到宿主机 | 生成 Ingress，按 `hostname` 域名路由 |
| 默认端口 | 组件的 `deployment.port` | — |
| 端口冲突 | 两个组件抢同一个宿主机端口会在**生成阶段**就报错，用 `exposePort` 错开 | 不存在——域名不同就不冲突，所以 K8s 下 `exposePort` 完全不参与生成 |
| `hostname` | 可省略 | **必填**，不写直接报错 |

> **不写 `expose` 就不暴露。** 组件之间在容器网络 / 集群内互相访问**不需要** `expose`——它们用服务名直连。只有"浏览器要打开它"才需要。

`local` 和 `expose` **不参与**"跑不跑"的判断，它们只影响"**怎么**跑"。

## 4.11 组件源码要跟项目一起进 Git 的话

前面十节都建立在一个前提上：`components/` 在 `brickkit init` 生成的 `.gitignore` 里，
所以 `brickkit sync` 搬目录，项目的 `git status` 根本看不见。

**这个前提你可能会去掉。** 组件源码要跟项目一起进版本库、或者想在项目里留一份指针，
都是真实需求。去掉之后有一件事跟着变：**`sync` 的整目录移动会进项目的 diff**，
于是这个失误会反复发生——

> 本地为了聚焦，给几个顶层写了 `enabled: false`，跑 `sync` 归档；
> 干完活提交时**忘了还原结构**，把归档后的目录结构提交了出去。
> 队友 clone 下来，源码全在 `components/.archived/` 底下。

### 4.11.1 装上提交前的闸门

```bash
brickkit init --hooks
```

它往 `.git/hooks/pre-commit` 里写一个 hook。**`components/` 还在 `.gitignore` 里的项目装了也没有任何代价**——那种情形下它一次 git 调用就退出，不打印任何东西。

`brickkit init` 在「项目根就是仓库根」时会自动装上：

```
   🪝 .git/hooks/pre-commit提交前检查组件结构（004 §3.14）
```

项目嵌在别人的仓库子目录里时**不会**自动装（那等于往别人的 `.git/hooks` 里写东西），只提示你自己敲那条命令：

```
   💡 组件源码要跟项目一起进 Git 的话：brickkit init --hooks 装上提交前检查
```

### 4.11.2 案例一：忘了还原结构就提交

关掉 `shop/notify`、跑 `sync`，然后只暂存结构、忘了 yaml：

### ▶️ 操作

```bash
brickkit sync
git add -A components/     # 只暂存了结构
git commit -m "改完订单逻辑"
```

### ✅ 预期

```
❌ 提交被拦下：组件源码提交在归档目录里，但 brickkit.yaml 说它该启动
   shop/notify：即将提交的位置：components/.archived/shop/notify
   建议：
   1. 想保留这个归档结构 → git add brickkit.yaml（yaml 里的 enabled: false 进了提交，就是你的意图声明）
   2. 不想 → git reset components/ && brickkit restore，然后重新 git add
```

**判据只有一句话：即将提交的那份 `brickkit.yaml`，和即将提交的目录结构，说的是不是同一件事。**
它读的是**暂存区**——所以「改 yaml + 归档结构一起提交」这件事一次就能做成，
不需要先提交一轮。

按第 2 条走完整次序：

### ▶️ 操作

```bash
git reset components/
brickkit restore
```

### ✅ 预期

```
📄 brickkit.yaml：按最后一次提交还原 enabled（其余改动未动）
   shop/notify@1.0.0          enabled: false → 删除该字段（提交里没写）
📂 工作区整理：
   📂 components/.archived/shop/notify     → components/shop/notify/
      原因：恢复启用
   ✅ components/shop/orders/              活跃
✅ 工作区整理完成（1 个活跃，0 个归档，1 个激活）
```

`restore` **只动 `enabled` 这一个字段，逐条动**：

| 条目 | 它怎么做 |
| --- | --- |
| 工作区与最后一次提交都有的 | `enabled` 回到提交里的值（提交里没写就删掉这个字段） |
| 你刚 `add` 完还没提交的 | **一个字不动**——这就是它不用 `git checkout` 的理由 |
| 提交里有、工作区已经 `remove` 掉的 | 绝不加回来，它不是 `git revert` |

被覆盖的旧值**动手前**就印出来（上面那行 `enabled: false → 删除该字段`）：
`restore` 不可逆，如实汇报是它全部的缓解措施。

### 4.11.3 案例二：我确实想提交这个归档结构

有时归档就是你要的结果——比如这个分支就只留订单。那就把 yaml 一起提交，
**它本身就是意图声明**：

### ▶️ 操作

```bash
brickkit sync
git add -A components/ brickkit.yaml
git commit -m "只留订单：notify 暂时关掉"
```

提交通过，闸门一声不响。**`enabled: false` 进了提交，平台就没有立场替你改主意。**

### 4.11.4 已经装过 brickkit 的项目怎么拿到这道闸门

两步，缺一不可：

```bash
# 1. 升级 CLI（同一条安装命令，覆盖装到原来那个位置）
curl -fsSL https://raw.githubusercontent.com/brickKit/brickKit/main/install.sh | sh
brickkit version          # 确认版本变了

# 2. 进每个项目补装 hook（老项目 init 时还没有这个功能）
brickkit init --hooks
```

升级 CLI 之后**要重跑一次第 2 步**：hook 里写着当时那个可执行文件的绝对路径与版本戳，重跑会把两者刷新——

```
✅ pre-commit hook 已刷新到当前版本（v0.1.1）：.git/hooks/pre-commit
```

### 4.11.5 三件要先知道的事

- **`.git/hooks/` 不进版本库。** 团队每个人都得各自跑一次 `brickkit init --hooks`，
  没有办法替他们装上。
- **`git commit --no-verify` 绕得过。** git 的机制如此。
- **已经有别人的 `pre-commit`（husky、lefthook、或你自己写的）时，平台绝不覆盖它**，
  而是报错并把该插进去的那几行给你——那几行带着和自动生成的 hook 一样的保护：
  找不到 `brickkit` 就放行，绝不因为「没装 CLI」堵死任何人的提交。
