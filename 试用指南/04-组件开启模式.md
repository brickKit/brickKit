# 04 · 组件开启模式（重点）

🎯 **这一节验证什么：** 一个组件到底"开着"还是"关着"，一共有几种表达方式，它们互相怎么影响。

这是整个平台最容易想当然的地方，值得一个个亲手试。全程用 `brickkit order`（只算不启动），几秒钟一次。

前置：**五组件基准**（`./试用指南/准备.sh --baseline`，见 [00](00-准备.md)）；概念上接着 [03](03-依赖与启动顺序.md)。
**不需要 Docker**——`brickkit order` 只做计算，不碰引擎。

> **先跑通 [05](05-Docker启动全流程.md) 再看这篇也完全可以。**
> 这一篇是整个平台**最容易想当然**的地方，而有过一次「东西真的跑起来」的经历之后，
> 这里的每条规则都能对上具体现象。

---

## 一张总表

| 写法 | 名字 | 含义 | 会被级联关掉吗 |
| --- | --- | --- | --- |
| 不写 `enabled` | **默认开启** | 想启动 | ✅ 会 |
| `enabled: true` | **钉住** | 无论如何都要启动 | ❌ 不会（关不掉就报错） |
| `enabled: false` | **显式关闭** | 一定不启动 | — |
| `--only A,B` | **本次只要这些** | 命令行临时收窄，不改配置 | — |
| `local: true` | **本地调试** | 不生成容器，你在 IDE 里跑它 | ✅ 会（和普通组件一视同仁） |
| `expose: true` | **对外暴露** | 映射到宿主机 / 生成 Ingress | 与开关无关 |

前三种是 **`enabled` 三态**——注意"不写"和"写 `true`"**不是**一回事，差别只在"能不能被级联关掉"。

---

## 4.1 默认开启（不写 enabled）

### ▶️ 操作

```bash
brickkit order
```

### ✅ 预期

五个组件里四个 `✅`，一个 `⬜`——**一行都没写过 `enabled`**，全是算出来的：

```
📋 组件状态计算：
   ✅ demo/hello@1.0.0             被 demo/caller 依赖
   ✅ demo/caller@1.0.0            根组件（没有其他组件依赖它）
   ✅ department/tree@1.0.0        被 people/basic 依赖
   ⬜ infra/redis-event-bus@1.0.0  级联跳过（只被弱依赖引用；需要它时请显式写 enabled: true）
   ✅ people/basic@1.0.0           根组件（没有其他组件依赖它）
```

启动的两类理由：**根组件**＝没有任何组件依赖它，那它一定是你想要的入口；
**被依赖的**＝有人强依赖它，所以也得起来。

不启动的那一类同样重要：`infra/redis-event-bus` 只被**弱**依赖引用。
弱依赖的意思本来就是"有更好、没有也行"，所以它不会被自动带起来——
想要它跑，得自己写一行 `enabled: true`。这正是下面三态的第二种。

## 4.2 显式关闭 + 级联

### ▶️ 操作

给 `demo/hello` 加一行 `enabled: false`：

```yaml
components:
  - id: demo/hello
    version: 1.0.0
    enabled: false          # ← 加这一行
```

```bash
brickkit order
```

### ✅ 预期

```
📋 组件状态计算：
   ⬜ demo/hello@1.0.0             显式禁用（enabled: false）
   ⬜ demo/caller@1.0.0            级联跳过（强依赖 demo/hello 不启动）
   ✅ department/tree@1.0.0        被 people/basic 依赖
   ⬜ infra/redis-event-bus@1.0.0  级联跳过（只被弱依赖引用；需要它时请显式写 enabled: true）
   ✅ people/basic@1.0.0           根组件（没有其他组件依赖它）
```

**你只关了一个组件，`demo/caller` 自动跟着不启动了** —— 因为它强依赖 `demo/hello`，硬起来只会在运行时报连接错误。这就是**级联禁用**。

注意另外两个组件完全不受影响：级联只沿**强依赖**这条边传播。

---

## 4.3 钉住（enabled: true）

`enabled: true` 的意思是"**我不接受它被级联关掉**"。

### ▶️ 操作

在上一步的基础上（`demo/hello` 仍是 `enabled: false`），给 `demo/caller` 加 `enabled: true`：

```yaml
  - id: demo/caller
    version: 1.0.0
    enabled: true           # ← 钉住
```

```bash
brickkit order
```

### ✅ 预期

**报错**，而不是二选一：

```
❌ 错误：强依赖 demo/hello 被禁用
   组件：demo/caller@1.0.0（enabled: true，已钉住）
   依赖链：demo/caller → demo/hello
   被禁用的组件：demo/hello@1.0.0
   建议：
   1. 在 brickkit.yaml 中移除 demo/hello 的 enabled: false
   2. 或去掉 demo/caller 的 enabled: true，让它随依赖一起被级联跳过
```

你同时表达了两个直接冲突的意图（"caller 必须起" + "它的依赖不许起"），平台不替你猜，把两条出路都摆出来。

**对比一下**：如果 `demo/caller` **不写** `enabled`（4.2 的情形），同样的配置是**静默级联跳过**——那正是"我关掉了一整条链"的正常操作。

### 恢复

把这两行 `enabled` 都删掉，再 `brickkit order` 确认回到全 `✅`。

## 4.4 `--only`：本次只启动这些

改配置是持久的，`--only` 是**一次性**的。

### ▶️ 操作

```bash
brickkit up --only people/basic --dry-run
```

### ✅ 预期

```
🎯 --only：只启动 people/basic 及其强依赖
📋 组件状态计算：
   ⬜ demo/hello@1.0.0             未被 --only 选中
   ⬜ demo/caller@1.0.0            未被 --only 选中
   ✅ department/tree@1.0.0        被 people/basic 依赖
   ⬜ infra/redis-event-bus@1.0.0  级联跳过（只被弱依赖引用；需要它时请显式写 enabled: true）
   ✅ people/basic@1.0.0           根组件（没有其他组件依赖它）
```

**它的强依赖会被自动带上**（`department/tree`），因为少了它 `people/basic` 根本跑不起来。

写法：

```bash
brickkit up --only people/basic                    # 该组件的所有版本
brickkit up --only people/basic@1.0.0              # 只这个版本
brickkit up --only people/basic,demo/caller        # 多个，逗号分隔
brickkit down --only people/basic                  # down 也支持
```

`brickkit.yaml` **一个字都没改**——下次不带 `--only` 就恢复全量。

## 4.5 `local: true`：这个组件我在 IDE 里跑

```yaml
  - id: people/basic
    version: 1.0.0
    local: true
    localPort: 8080      # 可选，不写就用组件自己声明的 deployment.port
```

它仍然是"启动中"的组件（依赖方要能找到它），但**不生成容器**。完整玩法见 [07-本地调试.md](07-本地调试.md)。

⚠️ `local: true` **只能配 `deploy.target: docker`**。K8s 下集群里的 Pod 连不到你的笔记本，CLI 会直接报错而不是悄悄跳过。

---

## 4.6 `expose`：让外面能访问

```yaml
  - id: portal/user-frontend
    version: 1.0.0
    expose: true
    hostname: portal.example.com    # K8s 必须；Docker 可省略
    exposePort: 18080               # 仅 Docker：自定义宿主机端口
```

| | Docker | K8s |
| --- | --- | --- |
| 怎么暴露 | 端口映射到宿主机 | 生成 Ingress，按 `hostname` 域名路由 |
| 默认端口 | 组件的 `deployment.port` | — |
| 端口冲突 | 两个组件抢同一个宿主机端口会在**生成阶段**就报错，用 `exposePort` 错开 | 不存在——域名不同就不冲突，所以 K8s 下 `exposePort` 完全不参与生成 |
| `hostname` | 可省略 | **必填**，不写直接报错 |

> **不写 `expose` 就不暴露。** 组件之间在容器网络 / 集群内互相访问**不需要** `expose`——它们用服务名直连。只有"浏览器要打开它"才需要。

## 4.7 组合起来的优先级

同时用了好几种时，按这个顺序判断：

```
1. --only 没选中它            → 不启动（最先判，命令行说了算）
2. enabled: false             → 不启动
3. enabled: true（钉住）      → 一定启动；依赖被关就报错
4. 强依赖不启动               → 级联跳过
5. 其余                       → 启动
```

`local: true` 与 `expose: true` **不参与**"启不启动"的判断，它们只影响"**怎么**启动"。

## ⏹️ 怎么停

这一节只用 `order` 与 `up --dry-run`，**没有启动任何容器**。

`--dry-run` 会在 `.brickkit/generated/` 下留一份部署文件，删不删都行：

```bash
rm -rf .brickkit/generated
```

配置改乱了：

```bash
brickkit reset --last
```
