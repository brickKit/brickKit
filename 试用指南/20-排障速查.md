# 20 · 排障速查

出错了先看这里。左边是你**看到的现象**，不是错误码。

前置：无。这一篇是**查的**，不用按顺序跑。

---

## 启动类

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `service "xxx-migration" didn't complete successfully: exit 1` | 迁移失败，多半是**库还没建** | 看 `brickkit up` 输出里的 `CREATE DATABASE` 那几行，建完再来 |
| 组件卡在 `Created` 一直不启动 | 它的迁移容器没成功退出 | 看该组件的 `-migration` 容器日志 |
| postgres 容器反复重启，日志说 `Database is uninitialized and superuser password is not specified` | `.env` 没被读到，密码被替换成了空串 | `.env` 要放在**项目根目录**（`brickkit.yaml` 旁边）。CLI 会显式传 `--project-directory`，自己手敲 compose 命令时也要带上 |
| `brickkit up` 说启动成功，但组件明显不可用 | 组件的 `healthCheck` 写的是 `type: none` | 平台不会替你判断健康；给组件加健康检查 |
| 镜像拉取报"未授权" | 镜像不在本地也拉不到 | 本地开发的组件先 `docker build`；私有 registry 先 `docker login` |
| 端口冲突，第二个组件起不来 | 两个组件 `expose` 到了同一个宿主机端口 | 用 `exposePort` 错开。CLI 在**生成阶段**就会报这个错 |
| 组件反复重启，`docker inspect` 里 `OOMKilled: true` / K8s 里 `Reason: OOMKilled` | 它超过了**你写的**内存 `limits` | 平台不会替你猜上限（005 §2.5）——这个数字是你或组件作者写的。量一下真实用量再调；JVM 还要检查 `-Xmx` 是不是留了 30–40% 给堆外 |

## 依赖类

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `⚠️ 弱依赖缺失：xxx` | **正常现象**，试验组件故意声明了不存在的弱依赖 | 不用管。弱依赖缺失时平台**完全不注入**那个环境变量 |
| `❌ 强依赖 xxx 被禁用` | 你钉住了 A（`enabled: true`）又关掉了它依赖的 B | 二选一：放开 B，或去掉 A 的 `enabled: true` |
| 组件莫名其妙不启动了 | 它的强依赖没启动，或者它的上层全关了（[04](04-组件开启模式.md)） | `brickkit up --dry-run` 看"组件状态计算"那一段，每行都写着原因 |
| 改了组件的 `component.yaml` 没反应 | 用的是市场/Git 源，走了缓存 | 本地源不吃缓存；市场/Git 源再 `brickkit add` 同一版本一次，按提示刷新 |

## 配置类

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `⚠️ brickkit.yaml 中存在明文密码` | 你把密码直接写在配置里了 | 改成 `password: ${XXX}`，真值放 `.env` |
| `⚠️ brickkit.yaml 的 config 里可能写了明文密钥` | `config` 里有名字像密钥的项（apiToken、dbPassword…） | 改成 `${MY_TOKEN}`，真值放 `.env`。详见下方说明 |
| K8s：`❌ 错误：brickkit.yaml 里引用的环境变量没有定义` | `${VAR}` 求不出值 | kubectl **不做变量替换**，必须在生成时求值。补 `.env` 或 `export` |
| K8s：`❌ local: true 只能在 deploy.target: docker 下使用` | 集群里的 Pod 连不到你的笔记本 | 去掉 `local: true`，或把 target 改回 docker |
| K8s：`❌ expose: true 的组件必须写 hostname` | 没有 host 的 Ingress 会匹配所有域名 | 补 `hostname:` |
| 配置改坏了 | — | `git checkout brickkit.yaml`（整份退回上次提交）或 `git checkout -p`（挑着退） |
| 整个试验场乱了，想从头来 | 试了太多轮，已经说不清现在是什么状态 | `./试用指南/准备.sh --reset`，再按 [02 · 2.5 末尾](02-添加与移除组件.md#演示到此为止重置试验场)那四条命令回到基准状态 |

### 关于「config 里可能写了明文密钥」

完整输出长这样：

```
⚠️ brickkit.yaml 的 config 里可能写了明文密钥
   配置项：demo/hello@1.1.0 → apiToken
   为什么要紧：brickkit.yaml 是建议提交进 Git 的（003 §1.2），
        写在这里的密钥会跟着进版本库，而且历史里删不掉
   建议：
   1. 改成 ${MY_TOKEN} 这样的引用，把真实值放进 .env
   2. .env 必须在 .gitignore 中
   3. 确实不是密钥的话可以忽略这条——判据只看名字，不看值
```

**注意它没有把密钥值打出来。** 打印等于又抄了一遍到你的终端和 CI 日志里。

三件容易误会的事：

| | |
| --- | --- |
| **它只看名字，不看值** | `apiToken: "abc"` 会被点名，`sortKey: "xyz"` 不会。判据刻意收窄到 password / secret / token / apiKey 这类几乎没有别的含义的词——一个见谁都喊的告警，两天之内就会被所有人无视 |
| **写成 `${VAR}` 就不会再喊** | 判据看的是**你写的原文**，不是展开后的值。所以做对了不会被误报，而漏配变量也不会被这条告警掩盖 |
| **它是警告不是错误** | `config` 里放什么由你决定，平台不替你判断哪个值算密钥；但看着像密钥的东西必须说一声 |

**真正的泄漏路径不是生成物，是 `brickkit.yaml` 本身**——003 §1.2 明确建议
把它提交进 Git。密钥进了版本库，历史里删不掉。


## 命令类

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `docker compose ... logs` 什么都不输出 | 少了 `-p`。compose 拿目录名 `generated` 当项目名了 | 用 `brickkit up` 输出里给的完整命令 |
| compose 命令刷一串 `The "XXX" variable is not set` | 带了 `-f` 却没带 `--project-directory .`，compose 去部署文件旁边找 `.env` 没找着 | 看日志 / 停止根本不需要 `-f`：`docker compose -p brickkit-<项目名> logs <服务名>` |
| `❌ 错误：找不到 kubectl` | 没装 | 装 kubectl；或者本地开发把 target 改成 docker |

## 配额类（CPU / 内存）

完整规则与三个可直接抄的场景见 005 §2.5。

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 组件被 `OOMKilled`，而 JVM 日志里没有 `OutOfMemoryError` | 进程是被**内核**杀的，不是 JVM 自己抛的 | `-Xmx` 必须明显小于内存 limit：堆外（Metaspace / 线程栈 / 直接内存）通常还要 200–300 MB。留 30–40% 是常见起点 |
| 服务莫名其妙有 p99 毛刺，而节点整体很闲 | 设了 **CPU limit**，被 CFS quota 限流 | CPU 上限是"节点空闲也照样限流"的。删掉 CPU limit，只留 `requests`（005 §2.5） |
| 节点内存告急，被杀的偏偏是最忙的那个组件 | 内存 `requests` 报低了 | 驱逐顺序是「`BestEffort` → 超出 requests 最多的 `Burstable` → `Guaranteed`」。**报低不是省资源，是排在处刑队列前面**，而排最前的正是最忙的那个 |
| Pod 一直 `Pending`，事件写着 `Insufficient memory` | 某个节点装不下这个 Pod 的 `requests` | 这是**唯一**的硬约束：节点上所有 Pod 的 requests 之和 ≤ allocatable。`limits` 之和可以超卖，`requests` 不行 |
| 20 个组件觉得机器不够 | 多半是错觉 | 按默认 requests（100m/128Mi）合计才 2 核 / 2.5G。真正的成本是**每个进程的内存地板**，几乎完全由语言决定（Go 8–20MB vs JVM 200–450MB）——该换的是运行时，不是把组件合并回去 |

## K8s 专项

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| Pod 起不来，`ImagePullBackOff` | 集群看不到你本机的镜像 | `minikube image load <镜像>` |
| 资源状态显示"集群内地址，本机不探测" | **正常**。集群内 DNS 名你的机器解析不了 | 想验证就 `kubectl run --rm -it netcheck --image=busybox -- nc -zv <主机> <端口>` |
| Job 报 `field is immutable` | 同名旧 Job 还在 | CLI 每次 up 都会先删旧 Job；手工 apply 时自己 `kubectl delete job/xxx` |
| 手工 `kubectl delete -f k8s/` 没删干净 | 按目录删只能删掉目录里**还写着**的那些；改过配置就会有漏网的 | 用 `brickkit down`——它按 `brickkit.io/project` 标签删，不看目录 |

## 通用手法

**先看它算出了什么，再看它做了什么：**

```bash
brickkit up --dry-run              # 只算不做：谁会启动、为什么、什么顺序
brickkit up --dry-run       # 生成文件但不启动，然后自己看生成物
brickkit status             # 现在到底什么状态（现问引擎，CLI 不存状态）
```

**看生成物：**

```bash
cat .brickkit/generated/docker-compose.yaml         # Docker
find .brickkit/generated/k8s -type f | sort         # K8s
```

**日志级别：**

```bash
brickkit up --log-level debug     # 更啰嗦
brickkit up --log-level off       # 关掉 stderr 上的 JSON 日志
```

**退出码：** `0` 成功（含警告）、`1` 出错、`2` 命令用法不对。
