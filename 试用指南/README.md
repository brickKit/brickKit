# BrickKit 试用指南

按顺序走一遍，就能把**目前已实现的每一项能力**亲手试到。

**操作篇（01–19）**的结构都一样：

| 小节 | 内容 |
| --- | --- |
| 🎯 这一节验证什么 | 一句话 |
| ▶️ 操作 | 可直接复制的命令 |
| ✅ 预期 | 你应该看到什么 |
| ⏹️ 怎么停 | **每一节结束时怎么收尾**，不留后台进程 |
| 📁 代码在哪 | 这个能力由哪些文件实现，想深看时从这里进 |

三篇例外，它们不是"照着做"的篇：`00a`（路线图）、`00b`（环境清单）、`20`（排障速查）
都是**查的**，没有 `▶️ 操作`。另外 `09` 与 `12` 的命令散在正文里，也没有独立的 `▶️` 段。

## 顺序

> **只有两小时？** 走 [00a-两小时上手](00a-两小时上手.md) 那条主线，其余按需回来看。

先做 `00`（准备）。之后**按编号顺序读下去就是最好的理解顺序**——
每一组回答一个问题，后一组建立在前一组之上。

| 组 | 篇 | 这一组回答什么 |
| --- | --- | --- |
| **一、这东西是什么** | 01 – 02 | 一个项目长什么样，组件从哪来、依赖怎么跟着来、用不上的怎么收起来 |
| **二、平台怎么想** | 03 – 04 | 它怎么算出该启动谁、按什么顺序；开与关的三种表达 |
| **三、变成运行中的东西** | 05 – 07 | 同一份配置 → Docker / K8s；其中一个换成你 IDE 里的进程 |
| **四、系统会变** | 08 – 09 | 升级、多版本共存、多副本与安全排空 |
| **五、组件从哪来到哪去** | 10 – 12 | 市场、签名、权限与审计 |
| **六、真实系统长什么样** | 13 – 17 | 八组件的真实项目、故障时的差别、看别人的接口、搬到 K8s、写你自己的组件 |
| **七、用起来之后** | 18 – 19 | 网络策略、多项目共享 |
| **查阅** | 20 | 排障速查——出错了随时翻 |

**这个顺序是按"理解"排的，不是按"能跑什么"排的。** 早期版本把
`03`/`04`（平台怎么算）排在能看到容器之前，是因为当时还要靠它们证明模型成立；
现在每一篇都已真跑验证过，就没有必要为了"下一步能跑"而牺牲概念连贯。

> 想先看到东西动起来的话，仍然可以 `01 → 02 → 05` 再回头补 `03`/`04` ——
> 两条路都通，见 [00a](00a-两小时上手.md)。

### 每一篇的前置都是一条命令，不是"前面 N 篇做完"

**这不是一条流水线。** 想从哪一篇开始就从哪一篇开始，试花了就再跑一次——
**reset 是常规手段，不是应急措施**。

| 命令 | 得到什么 | 哪几篇用它 |
| --- | --- | --- |
| `./试用指南/准备.sh --images` | 十个组件镜像 + `hello:2.0.0` | 05 之后的每一篇（只需跑一次） |
| `./试用指南/准备.sh --reset` | 空试验场：只有十个组件的**源码**，没有项目 | 01 · 02 |
| `./试用指南/准备.sh --baseline` | **五组件基准**：`demo-shop` 项目 + 五个组件 | 03 · 04 · 05 · 07 · 08 |

09 只要一个 minikube；17 从空目录开始；19 自己另建两个项目。全都写在各篇的前置行里。

## 全局约定（先读这一段）

### 所有命令都是"跑完就退出"

BrickKit CLI **不是常驻服务**。`brickkit up` 会一直等到组件健康才返回，除此之外没有任何后台进程。所以：

- **想中断某条正在跑的命令：** `Ctrl-C`。
- **`brickkit up` 中途 Ctrl-C 了怎么办：** 容器可能已经起了一半。执行 `brickkit down` 收尾即可，不会有残留。

### 真正需要"关掉"的只有三样

| 东西 | 怎么停 | 怎么彻底删掉 |
| --- | --- | --- |
| 项目里的组件容器 | `brickkit down` | `docker compose -p brickkit-<项目名> down -v --remove-orphans`（`-v` 连数据卷一起删） |
| minikube 集群 | `minikube stop` | `minikube delete` |
| 市场后端 | `cd deploy/market && docker compose down` | `docker compose down -v` |

`brickkit down` **不会删数据卷**，数据库里的数据一直在——这是有意的（004 §3.6）。

### 每一节都可以独立重来

试验场在 `试用指南/playground/` 下，随时可以整个删掉重建：

```bash
cd <仓库根目录>
./试用指南/准备.sh --reset      # 空试验场（只有组件源码）
./试用指南/准备.sh --baseline   # 直接回到 03–08 用的五组件基准
```

**只想退配置、不想重建试验场**，用 Git——CLI 不自建备份，`brickkit.yaml`
本来就该提交（[01 §1.3](01-初始化项目.md)、003 §7.2）。

| 想撤销的范围 | 命令 |
| --- | --- |
| 刚才那一步 `add` / `remove` | `git checkout brickkit.yaml` |
| 只撤销其中一处改动 | `git checkout -p brickkit.yaml` |
| 整个试验场 | `./试用指南/准备.sh --reset` / `--baseline` |

## 还没实现的（试的时候别找）

### 还没实现的

| 能力 | 状态 |
| --- | --- |
| HPA 自动扩容 | ⬜ 按 CPU/内存自动调整副本数（005 §5.8）。**手动 `replicas` 已支持**，多副本时自动生成 PDB，见 [09](09-多副本与优雅排空.md) |
| **镜像本身**的签名 | ⬜ 属集群准入控制器（Kyverno / Sigstore）的职责，CLI 不在那条链路上。而镜像**字节**已由 digest 钉住保护，见 [11.6](11-组件签名.md) |
| 市场侧密码学校验 | ⬜ **想清楚之后决定不做**：任何形态都需要「发布凭据不能管理密钥」这条权限分离，而市场 Token 没有 scope。真正的保护在你自己的 `installer.publicKeys`（P30） |
| **Podman** | ❌ 写过、跑过，最后**移除了**。`up` / `status` / 业务请求都通，但 `down` 失败（`rootless netns: kill network process: permission denied`），而纯 `podman compose down` 不经过 BrickKit 也一样失败。**一个停不掉的项目比不支持更糟**——详见 [005 §7](../design/005-部署与运行规范.md) |

完整的进度与延后清单见 [开发进度/](../开发进度/README.md)——
其中 [延后实现清单](../开发进度/延后实现清单.md) 是 P 编号的权威出处。
