# BrickKit 是什么

## 一句话定位
- 声明式组件组装平台：声明组件和依赖，其余全部派生

## 核心理念（三段式）
- 声明组件 → CLI 派生一切（启动顺序、地址、环境变量、部署文件）
- 无注册中心、无配置中心、无网关、无守护进程
- 组件是独立的领域单元，边界是契约文件

## 三层架构极简示意
- brickkit.yaml（声明）→ deploy.yaml（部署）→ config/（配置）
- 一张图：从声明到运行容器的完整流水线

## 分形架构一句话引出
- 组件在开发时是项目，在消费时是黑盒
- 详细展开见 05-fractal-architecture.md

## AI 友好
- 组件足够小，AI 能一次读完
- 契约先行，AI 不需要猜边界
- 详细展开见 08-ai-guide/

## 与"你已知的工具"对照表
- 表格：BrickKit vs npm/helm/docker-compose/git clone
```

#### `04-comparison.md`

```
# 与现有方案对比

## 与 Docker Compose
- 重叠：都生成 compose 文件
- 不同：Compose 不解析依赖、不注入地址、不做拓扑排序

## 与 Helm / Kustomize
- 重叠：都生成 K8s Manifest
- 不同：BrickKit 是组件级声明，不是模板引擎

## 与 Tilt / Skaffold
- 重叠：都关注开发体验
- 不同：BrickKit 不自动构建、不做热重载

## 与 Backstage
- 重叠：组件目录概念
- 不同：BrickKit 不做门户、不做插件系统

## 与 Monorepo 工具（Turborepo / Nx / Lerna）
- 重叠：都管理多包/多组件
- 不同：BrickKit 管理的是运行时部署，不是构建管道
- 分形规范的区别：BrickKit 的组件有独立的生命周期和版本

## 总结：BrickKit 的独特定位
- 声明式 + 派生 + 无控制平面 + 分形
```

# 分形架构（套娃机制）

## 核心概念
- 物理不套娃，规范套娃
- 开发态 = 项目视角（有自己的三层文件）

- 主项目只读 component.yaml（契约）和 BRICKKIT.md（文档）

- 依赖树从 component.yaml 的 dependencies 字段解析

## CLI 身份识别
- 同时存在 component.yaml + brickkit.yaml 时的行为
- release 以 component.yaml 为准
- up/add 以项目视角操作

- 标准结构（五个区块）
- 三层分形放置（定义层 / 实例层 / 内容层）
- CLI 文档级联缓存（.brickkit/manifests/）

## AI 套娃读取路径
- 读主项目文件 → 读 .brickkit/manifests/ 下的组件文档
- 不翻源码、不读子项目的三层文件

## 图示
- 一张图展示三层分形放置关系

1. brickkit local on

4. 用 IDE 调试

- 恢复团队配置

## local refresh 与智能 Diff 提示
- 为什么需要 refresh：团队新增组件导致严格校验报错。
- refresh 的安全机制：物理备份为 `.bak`，生成全新文件（坚守完整替换原则）。
- **智能 Diff 摘要**：CLI 自动对比 `.bak` 与新文件，在终端列出你之前的 `debug`、`localPort` 或自定义 `vars` 覆盖。
- 最佳实践：只需照着终端的 Diff 列表，用文本编辑器将这几行抄回新文件，无需全量比对两个 YAML 文件。

- 前缀 / 后缀
- 阻断错误

## 外壳成员的地址重写（Address Rewriting）
- 底层机制：CLI 在解析阶段构建“成员 → 外壳”反向索引（O(N) 复杂度）
- 行为：当外部组件依赖被收编的成员时，注入的 `_ENDPOINT` 自动替换为外壳的物理地址

## 不做隐式覆盖

## 求值时机：CLI 提前求值 vs 引擎运行时透传
- 外壳 JSON 注入（`BRICKKIT_SERVED_MEMBERS_CONFIG`）：CLI 提前解析 `${}` 和 `file://`，JSON 安全编码后硬编码（防止多行密钥破坏 JSON）。

- `file://` 的特殊性：本地文件必须由 CLI 提前读取并硬编码。

# 配置冲突问题

## 重复 key
- IDE 标红
- 如何解决

## $var: 引用的变量不存在

## 环境变量被覆盖（不会发生）
- 所见即所得

## 使用 yq / IDE 格式化后，冲突标记消失，配置静默丢失
- 症状：执行 `yq` 或点击 IDE 的 "Format" 后，重复 Key 报错消失，但组件启动后读取到的是错误的默认值。
- 原因：YAML 规范对重复 Key 未定义，第三方格式化工具会静默丢弃重复项。
- 解决： brickkit restore 还原文件，然后**务必使用纯文本编辑器**（禁用 YAML 插件）手动删除多余行。
```

#### `06-shell-issues.md`

```
# 外壳问题

## JSON 解析失败
- 特殊字符

## 成员配置缺失

## _ENDPOINT 路由失败（外部调用外壳成员报 404 或超时）
- 症状：外部组件调用外壳内的成员时，网络连通但返回 404，或直接 Connection Refused。
- 原因：平台已自动将 `_ENDPOINT` 指向外壳，但外壳内部的路由器未正确配置 Path 分发规则，导致请求打到外壳后无处可去。
- 解决：检查外壳启动代码（如 `main.go`）中的路由分发逻辑，确保拦截了对应成员的 API 前缀并转发给内部模块。
```
