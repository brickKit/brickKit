# 组件设计准则

这是**推荐实践**，不是 BrickKit 平台的硬性要求——跟这个系列里的其它文档
（[测试](01-testing.md)、[种子数据与测试数据](02-data-construction.md)）是同一
个级别：BrickKit 的组件自治原则（AGENTS.zh.md §4）把"组件自己的领域模型
该怎么设计"完全留给造它的人决定。下面这套方法论，来自验证过测试分层和数
据构造这两份指南的同一次真实生产部署，在组件设计这一侧也一并验证过：怎
么在设计之前先做研究，以及研究过程中值得专门识别的一个信号——什么时候
一个特性不是一个配置开关，而是在提示你需要并排存在好几个独立的组件。

## 从参考实现出发，不要从一张白纸开始

业务逻辑的设计几乎总该先看一看成熟的现实软件是怎么解决同一个问题的。这
不是谦虚——一个经过多年真实部署打磨出来的领域模型，早就吸收了从零设计
几乎必然会漏掉的边界情况，而这些漏掉的边界情况通常要到客户已经上线三个
月之后才会冒出来，不会在设计评审阶段就被发现。

**顺序很重要，颠倒过来的结果比干脆不做这个研究还要糟：**

```mermaid
graph LR
    S1["1. 先画自己的设计草图"] --> S2["2. 只在解决不了的地方<br/>参考成熟实现"] --> S3["3. 回头对照自己项目的<br/>真实约束重新想一遍"]
```

| 步骤 | 做什么 | 为什么是这个顺序 |
| --- | --- | --- |
| **1. 先设计自己的版本** | 在打开任何参考实现之前，先按自己项目的真实约束画一版设计草图 | 带着自己的方案去看别人的实现，才能真正看出差异在哪儿。空着脑子去读，只会读出一份抄袭品 |
| **2. 只为自己想不通的那部分去查参考** | 领域模型怎么切分、状态机有哪些状态、哪些转换是合法的、哪些字段是必填的、边界情况实际上是怎么处理的 | 这一步是研究，不是抄作业——你已经知道自己在找什么 |
| **3. 回来自己想清楚，再动笔** | 把学到的东西对照自己项目真实的约束重新消化一遍 | 参考项目的技术栈和组件边界几乎不可能跟你的一样（语言不同、进程/数据库拓扑不同）。照抄既不可能，也不对——重点从来不是搬运代码，只是借用它背后的推理 |

**闭源产品也值得参考**，哪怕你读不到它的源码。你仍然可以观察一个成熟产
品在真实世界里是怎么被**使用**的：哪些功能客户天天用，哪些从来没人点，
哪些工作流被抱怨了很多年。这类信息在判断"某个能力是否值得拆成一个独立
可发布的组件"这件事上，往往比源码本身更有价值——而这个判断比任何实现
细节都更重要，因为它来得更早、也更难在事后纠正。

**关于许可证**，简单说一句：参考一个实现的推理方式，再独立地（哪怕换一
种语言）重新实现一遍，不构成衍生作品。真正要避免的是打开对方的源文件、
逐行照抄或者机械转录。按上面这三步走，天然就能远离这条线。如果真的需要
直接用到代码，只能限定在宽松许可证的项目上（Apache-2.0 / MIT / BSD），
并且保留原始的版权声明。

**把参考过什么记录下来**，作为组件设计笔记的一部分，在开始实现之前就写
好——这个记录当时写很便宜，日后有人问"这个字段为什么长这样"时再去重建
就很贵：

```markdown
## 参考过的实现

| 项目 | 版本/commit | 参考的模块 | 借鉴了什么 | 许可证（已核实） | 用法 |
|---|---|---|---|---|---|
| Odoo | 17.0 | `addons/product/models/product_uom.py` | 计量单位换算系数的表设计和它的取整策略 | LGPL-3 | 借鉴推理 |
| 某闭源产品 | — | — | 多单位换算在日常使用中的真实模式：哪些换算天天用到，哪些从来没被用过 | 闭源 | 借鉴真实使用模式 |

**明确没有参考过的**（写清楚，免得后面的读者以为是漏看了）：

**要刻意避免的做法**（点名在参考中发现的具体反模式，以及这个组件为什么不重蹈覆辙）：
```

"用法"这一列只有三种合法取值：**借鉴推理**（读了实现、理解了它为什么这
么设计，然后自己独立设计并实现——绝大多数行都该是这个值）、**借鉴真实
使用模式**（一个闭源产品，或者只看了文档/交互而没看源码）、**照抄代码**
（原样用了代码——只允许用在 Apache-2.0/MIT/BSD 项目上，必须保留原始版
权声明，并且这张表要写清楚具体是哪个文件、哪一段）。

## 对比参考实现时值得点名的一种失败模式

读几个同一领域的成熟实现，往往会发现它们共享同一批结构性弱点，通常是从
同一个架构传统的更早时期继承下来的。读的时候能识别出这一点，正是做这个
研究的意义所在——这是一次刻意不重蹈别人覆辙的机会：

| 成熟参考实现里常见的弱点 | 怎么设计规避 |
| --- | --- |
| 所有模块共享一个进程、一个数据库，跨模块表连接变成家常便饭，本该存在的模块边界变成一道随时被跨越的"软"边界 | 独立的组件、独立的 schema，用真实的访问控制而不是约定来强制边界——这正是 BrickKit 自己的组件模型已经免费给你的那条边界（AGENTS.zh.md §4 的组件自治原则） |
| 定制靠运行时打补丁或者往基础实现里挂钩子来实现，每次升级都可能打断每一处定制 | 一份独立版本管理的 fork 加一份锁定的契约，让升级变成一次显式、刻意的合并——绝不是一次悄悄跟打过补丁的代码互相影响的自动合并 |
| 一切都靠元数据驱动（动态字段、通用的"单据类型"抽象），没有任何静态类型能让 IDE 或类型检查器在运行前就抓到错误 | 一份真正的 schema/契约，再加上在语言支持的地方使用静态类型的实现 |
| 报表直接查询实时事务表，一条重的分析查询会拖垮事务路径 | 报表走汇总表或者一个专门的组件，绝不碰实时事务路径 |
| 表无节制地一直增长，系统迟早被自己的历史数据压垮 | 从第一天起就把每一张会持续增长的表设计成分区表，并配一条明确的归档策略 |

## 识别"槽位家族"信号

对比参考实现的过程中，会反复出现一种特定情况：**同一个特性在几个成熟系
统里有真正不同的实现，而且——这是关键的限定条件——每一种实现都是合理
的，只是适合不同的客户画像。**

这不是一个"要不要做成可配置"的问题。这是一个信号，说明这个特性需要的
是一整个可互换的组件家族，而不是把一个开关藏进单一实现里。

判断完全取决于那个限定条件：

- 如果对比几个实现后发现其中一个**明显更好**，其它都不如它 → 那就是你
  唯一该实现的版本，不需要家族。
- 如果几个实现**各自都站得住脚，服务的是真正不同的客户画像** → 说明这
  里存在真实的、互相独立的需求，值得做成一整个由独立组件构成、可以互
  换的家族。

| 特性 | 参考实现里发现的真实分歧 | 结论 |
| --- | --- | --- |
| 成本核算方法 | 移动加权平均 / 先进先出 / 带差异的标准成本 / 批次实际成本——四种方法，各自适合不同行业 | 需要做成家族 |
| 仓库拣货策略 | 先到期先出 / 先进先出 / 就近拣货 / 波次拣货 | 需要做成家族 |
| 审批路由 | 严格组织层级 / 按金额分级 / 矩阵式 / 规则引擎驱动 | 需要做成家族——但这是业务逻辑，不是基础设施，应该放进面向业务的组件里，不该指望一个通用的平台机制去表达它 |
| 单据编号方案 | 顺序号 / 按年月分段 / 按机构和类型分段 | **不是**家族——一个配置项就够了 |
| 核心主数据记录上到底有哪些字段 | 各家参考实现的差异只是"多几个字段、少几个字段" | **不是**家族——这是定制/fork 层面的事，不是架构层面的事 |

## 在 BrickKit 上，"一个家族"具体意味着什么

一旦识别出上面这个信号，它在这个平台上该长成什么样，直接可以从平台已经
具备的机制推出来——这不是 BrickKit 需要额外学一个新概念：

1. **每个家族成员各自发布成一个独立的组件**——自己的仓库、自己的
   Manifest、自己的版本历史（AGENTS.zh.md §9.16"一个组件、一个仓库"的
   原则在这里跟在任何别的地方一样适用）。`pricing/costing-fifo` 和
   `pricing/costing-standard-cost` 是两个组件，不是同一个组件的两种模
   式。
2. **每个家族成员对外暴露完全相同的契约面。** 针对某一个成员写的调用方
   代码，不用改就能对着家族里任何一个其它成员工作——这才是真正让这个
   家族可互换的东西，而不只是长得凑巧差不多。
3. **不能有任何东西对某一个具体的家族成员持有固定的依赖边**。这是让某
   个东西真正有资格成为家族成员的硬约束，在 BrickKit 里有非常具体的含
   义：一个组件自己的 `dependencies.components` 条目指向的是一个精确
   的组件 ID 加精确版本（AGENTS.zh.md §6）——这是在发布时就固化进那个
   组件 Manifest 里的东西，项目的 `brickkit.yaml` 事后没法把它重新指向
   别处（这正是依赖别名这个功能被拒绝作为平台特性的原因——AGENTS.zh.md
   §9.23）。所以一个要调用某个槽位的组件，**不应该**把
   `pricing/costing-fifo` 声明成一个普通依赖；它应该声明一个
   `configSchema` 地址字段（正是 AGENTS.zh.md §9.23 早就给出的那条出
   路——"需要一个地址、但不需要一条依赖边的服务"），由拼装这套系统的
   项目把它实际选择安装的那个家族成员的地址填进去。如果已经有什么东西
   对某个具体成员声明了固定依赖，那个成员就已经不再是可替换的了——正
   确的处理方式要么是"一个组件内部实现一个策略"（见下面"什么时候不该
   做成家族"那一条），要么是彻底做成一个独立维护的 fork。
4. **在写任何实现之前，先把这个家族注册下来**：起名字、定义清楚共享的
   契约面到底是什么、明确每个成员服务的是哪种客户画像，并决定——如果
   需要默认值的话——新项目默认该装哪一个。

**永远不要在单一组件内部写一个 `if costingMethod == "fifo"` 这样的分支
来敷衍一个真实的槽位家族信号。** 那样做等于把多个客户真正不同的需求塞
进同一份代码里，从此每个客户的需求都会牵制其它所有客户的构建——这正是
组件自治原则从一开始就要防止的"抽一根线、整体都跟着动"那种失败模式。
**唯一的例外**：分歧小到只需要两三个条件分支，而且看不到第三、第四种
变体的苗头——为一个大概率永远不会超过两个分支的差异专门拆出一整个组
件，本身就是另一种过度设计。

这套纪律恰好也是让客户能够从家族里最接近自己需求的那个成员出发、做闭源
定制的物理前提：一个家族的成员越贴近参考研究阶段发现的真实分歧，客户
fork 的起点就越接近他们真正想要的东西，事后要做的定制工作也就越少。

## 如果你的团队习惯用 DDD 的语言

这一节不要求你用 DDD。它只是一份对照表：团队本来就用限界上下文、聚合这套语言的话，下面是这些概念在 BrickKit 里对得上的地方。和上面几节不同，这一节没有某次真实部署的复盘作背书——它是把已有的平台机制翻译成 DDD 的说法，外加几条推荐的判据。

| DDD 里的概念 | 在 BrickKit 里对应什么 | 依据 |
| --- | --- | --- |
| 限界上下文 | 至少一个组件；一个组件不该同时横跨两个上下文 | 组件自治：一个组件有自己的模型、自己的 schema（AGENTS.zh.md §4） |
| 聚合（一致性边界） | 必须放进**同一个组件**：组件内部事务自洽，组件之间只有直接的请求/响应调用，平台不在调用路径上，也就没有任何跨组件的事务可以依赖 | AGENTS.zh.md §3（"单一组件"）、§2.2（没有常驻服务） |
| 统一语言 | 组件 ID 和 `configSchema` 的键名——组件 ID 会原样变成每一个调用方代码里的环境变量名（`people/basic` → `PEOPLE_BASIC_ENDPOINT`），取名时用领域自己的词，不用实现细节的词 | AGENTS.zh.md §5.2、§9.23 |
| 已发布语言 / 开放主机服务 | `artifacts` 里的契约文件 | [消费别人的组件](../03-guide/08-consuming-artifacts.md) |
| 客户—供应商 | 调用方在 `dependencies` 里钉死供应方的精确版本，没有隐式升级；升级是调用方自己写下的一次显式改动 | AGENTS.zh.md §9.2 |

**一处很容易搞反的用词。** DDD 里的"上游"是被依赖的供应方，"下游"是消费方。BrickKit 说"跟着上层走"（AGENTS.zh.md §5.4）时，"上层"是**依赖别人的那一方**——顶层就是没有任何组件依赖它的那些。也就是说，BrickKit 的"上层"对应 DDD 的下游，BrickKit 的"下层"对应 DDD 的上游。读到"某个下层组件跟着上层启动"时，别顺手按 DDD 的方向去理解。

**拆不拆，可以问三个问题**（推荐的判据，不是平台的规则）：

1. 这两块数据之间，有没有一条**任何时刻都必须同时成立**的不变量（比如"余额永远不能为负"同时约束账户和流水）？有 → 放进同一个组件，因为跨组件没有事务。
2. 它们要不要**各自独立发版、归不同的人或不同的客户**？要 → 拆开。一个组件就是一个发布单位、一个版本单位、一个权限单位（AGENTS.zh.md §9.16）。
3. 拆开之后，调用方只靠 `artifacts` 里的契约，能不能写出调用代码，而不必知道对方内部有哪些表？不能 → 边界划错了，回头看第 1 条。

这和上一节的"槽位家族"不冲突，回答的是另一个问题：这一节问的是"这两块东西该不该在同一个组件里"，上一节问的是"这一个特性该不该被做成一组可互换的组件"。
