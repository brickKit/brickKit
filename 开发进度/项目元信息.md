## 执行顺序调整 — 2026-08-12

**背景：** Step 10 之后复盘发现，`up` / 迁移 / 环境变量注入这些 Step 只能"自证"
（断言生成的文本），没法"他证"（真的把容器跑起来），因为**还没有一个能运行的组件镜像**；
同时市场端点契约（P11）也只被 Mock 验证过。

**调整后的顺序：**

```
插入 A（平台自测组件）→ Step 18（市场后端）→ Step 19（登录发布）→ Step 11（注入引擎）→
**Step 21/22（真实组件）→ Step 12 → 25/26 → 13/14/15** → …

> 2026-08-14 调整：先做两个真实组件再回 Step 12。理由是 CLI 的验证不能停在
> "生成的文件长得对"，得能"跑起来是对的"；而 Phase 5 绝大多数验证项不依赖剩余 CLI 工作，
> 现在就能做透。（Step 18/19 已完成，市场与发布链路可用，组件做完随时能发上去。）
```

| 决策 | 理由 |
| --- | --- |
| 先做自测组件，而不是先做市场 | 安装链路已经通了（local / git 两种安装源都实测过），市场只是第三种安装源；而**没有镜像就没法 up**，这是硬阻塞。开发计划 Step 4 的备注也写明"可并行启动 Step 21" |
| 自测组件不占用 Phase 5 的组件 ID | Phase 5（Step 21–28）是业务组件，服务于 E2E 验收；插入 A 是平台自己的测试夹具，长期供 Step 11–17、32、33、37 复用，两者不混淆 |
| 市场（18/19）提前到 Step 11 之前 | 你的要求：把两条路都先铺好，之后每个 Step 都能全量验证。客户端已有的 Mock 契约（D47/D48）正好翻译成服务端的验收测试，回填 P11 |
