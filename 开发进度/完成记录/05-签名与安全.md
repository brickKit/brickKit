### P30：市场侧密码学校验 —— 想清楚之后决定不做 — ✅ 2026-08-16

**结论先行：不做，并把理由写进设计书。** 这条不是延后，是有依据的否定。

**探索了两种形态。** 起点是 D285 的判断（市场手里没有可信公钥，让发布者
连公钥一起上传就是自己给自己发证）——那条仍然成立，但它排除得不够彻底，
因为存在两种不需要市场判断可信度的做法：

| | TOFU（首次自动钉） | 账号密钥登记（GitHub 模型） |
| --- | --- | --- |
| 密钥从哪来 | 首次发布时自动钉住 | 用户在账号里上传 |
| **轮换** | 要专门设计一套协议 | 加一把删一把，普通账号操作 |
| 心智模型 | 要解释什么叫“首次” | 大家都懂 |

**后者明显更好**，而轮换恰恰是 TOFU 最难的部分——GitHub 模型直接把它消解了。
TOFU 唯一的优势是“零操作就有保护”，但它只在发布者已经签名却没登记时
才多给保护，而且第一次发布若是攻击者，钉住的就是攻击者的密钥。
这条优势太窄，不值得换一整套轮换协议。

**但两者成立的唯一前提是权限分离。** GitHub 能这么做，靠的是 `repo` 权限的
token 改不了 SSH 密钥。BrickKit 的 `tokens` 表**只有 user_id 与过期时间，
没有 scope**——偷到发布 Token 的人同样能换掉登记的公钥，
“市场验过签”就成了一句空话，**比不验更糟**，因为它会让人以为验过了。

**所以不做。** 与其加一套认证层去支撑一个边际收益有限的机制，不如把校验
完整地留在 CLI 侧——那里的信任锚点是使用者自己的 `installer.publicKeys`，
不依赖市场是否被攻破。市场侧能多覆盖的只有“使用者没配公钥”这一种场景，
而那批人真正该做的是去配公钥。

**重新考虑的条件写进了设计书：Token 有了 scope 之后。**

**一个走到一半又删掉的实现。** 决定之前先做了跨 module 的验签地基
（market-server 是独立 module，引用不了 `internal/security`，只能各写一份）。
删掉了 `market-server/internal/signature/`——按项目自己的规矩，
不留半个用不上的机制。

**但保留了黄金样本，因为它的价值不依赖市场：** 签名是对**规范化载荷**做的，
那套规则一旦改变，此前发布的每一个签名都会一起失效——而且失效得很安静：
没有任何东西被篡改，但每个组件都验签失败。会触发它的改动看着都很无害
（换个 JSON 编码器、给 normalize 加个类型分支、改缩进参数）。
`testdata/signature-golden.json` + `internal/security/golden_test.go`
是唯一能在合并前发现它的地方。

守卫本身验过：把 `json.Marshal` 换成 `json.MarshalIndent`
（语义完全相同、只是缩进不同），三条测试立刻红。**一条不会红的守卫等于没有。**

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D427 | 市场**不做**密码学校验，并把理由与重新考虑的条件写进 008 §8.2 | 任何形态都需要权限分离才成立，而 Token 没有 scope。没有它，偷到发布 Token 的人也能换掉登记的公钥——“验过签”比不验更糟 |
| D428 | 真要做的话选**账号密钥登记**，不选 TOFU | 轮换是 TOFU 最难的部分，而账号模型直接消解了它。TOFU 唯一的优势（零操作就有保护）覆盖面太窄 |
| D429 | 保留黄金样本，删掉市场侧验签 | 前者防的是“改了规范化规则导致历史签名集体失效”'，与市场无关；后者已无用武之地，不留半个 |
| D430 | 市场存的 `manifest_json` **是关键内容**，不是“一些配置” | `deployment.image` 就在里面。改掉它就是改掉“该拉哪个镜像”——镜像字节没被动过完全不影响这次攻击。这也是签名唯一要保护的东西 |

### P29：镜像 digest 钉住 — ✅ 2026-08-16

**先把问题重新定义了一遍。** P29 原来记的是“镜像签名未实现”，
但查下来缺口比那小得多：`deployment.image` **就在 Manifest 里**，
而签名覆盖的是规范化后的整个 Manifest——所以“部署哪个镜像”已经被保护了。
真正的缺口只有一条：

> 签名保证了镜像**字符串**没被改，保证不了那个字符串**还指向同样的字节**。

tag 是可变的。攻击者拿到 registry 权限后用同一个 tag 重新 push，
签名依然有效、跑起来的却是另一个镜像。

**把 tag 换成 digest，缺口自己就关上了**——digest 按定义不可变，
而它已经在签名覆盖范围内。不需要任何新的密码学机制。

**实现：** `publish` 默认向 registry 解析 digest，改写 Manifest 与待上传文档，
**然后才签名**。顺序是这里唯一会静默出错的地方——先签后钉的话签的是旧内容，
消费方一律验签失败，而发布者这边一切正常。

**真跑抓到的关键差异：两条查询路径给的 digest 不一样。**

| 来源 | digest | MediaType |
| --- | --- | --- |
| `docker buildx imagetools inspect` | `sha256:d9e853e8…` | `image.index.v1+json`（多架构索引） |
| `docker manifest inspect -v` | `sha256:c64c687c…` | `image.manifest.v1+json`，`linux/amd64` |

钉住后者会把组件**锁死在 amd64**，而且往往是发布很久之后换机器才发现。
所以**只用 buildx、不做 fallback**——一个悄悄锁架构的 fallback 比直接报错糟得多。
查的也是 registry 而非本地 daemon：本地 `RepoDigests` 可能来自 `docker load`，
未必真在目标 registry 里存在。

**一个设计代价，是被测试暴露出来的。** 默认开启后 29 个既有 publish 测试全挂——
那不是测试问题，是“publish 从此需要 registry 访问”这件事显现出来了。
判断是默认仍该开启（取不到 digest 意味着消费方也拉不到，而版本号不可回收），
测试入口补一个“registry 里已有该镜像”的默认桩——那本来就是发布时的常态
（build → push → publish）。

**验证：** 12 条业务测试 + 真 registry 解析（`alpine:3.20` → 与 buildx 一致的索引 digest）。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D421 | 钉 digest，而不是给镜像再签一次 | `deployment.image` 已在签名覆盖范围内，缺口只有 tag 可变这一条。digest 不可变，等于用现有签名把字节也锁住了——零新机制 |
| D422 | 钉 digest **必须在签名之前** | 反过来的话签的是旧 Manifest、上传的是钉过的，消费方一律验签失败，而发布者这边一切正常，极难查 |
| D423 | 解析失败**阻断发布** | 取不到 digest 通常意味着镜像没推上去，那样消费方也拉不到；而版本号一旦建出来不可回收，与其留下一个装不上的版本不如现在停下 |
| D424 | **只用 buildx，不做 fallback** | `manifest inspect -v` 给的是单平台 digest，钉住会把组件锁死在 amd64，且往往很久之后才发现。悄悄锁架构比直接报错糟得多 |
| D425 | 查 registry，不查本地 daemon 的 `RepoDigests` | 本地那个可能来自 `docker load`，未必真在目标 registry 里存在——而消费方是从 registry 拉的 |
| D426 | cosign 签镜像本身仍不做 | 它解决的是绕开 BrickKit 直接部署的场景，由集群准入控制器负责。与 005 §5.13.0.1 对厂商 CRD 的判断同源：平台不该把自己塞进管不了的链路 |

**这一段抓到的三个真 bug：**

| # | 问题 | 怎么发现的 |
| --- | --- | --- |
| 1 | **判定顺序反了，打挂 11 个既有用例**：把"组件没有签名"判在"没有配公钥"之前，于是 `requireSignature` 默认 true + 现存项目都没配 `publicKeys` = **每个项目的 `add` 全部被阻断**，却换不来任何安全收益（没公钥本来也验不了）。这是 Step 20 最容易做错的地方 | 接线后跑全量测试，11 个用例同时红 |
| 2 | **PostgreSQL 会静默丢掉签名**：`signature_json` 这一列早就在建表脚本里预留了，但 SQL 语句里没写它。发布接口返回的是内存里那个结构体，看上去一切正常；等使用者 `add` 时才发现签名没了，而那时已无从判断是发布者没签、还是市场弄丢了。**内存实现天然不会犯这个错**，只有仓储契约测试抓得住 | 写了 `testVersionSignature` 契约测试，对**真 PostgreSQL** 跑 |
| 3 | **签名缓存文件被当成版本号**：`.brickkit/manifests/` 里多了 `people-basic-1.0.0.sig.json`，而扫描该目录找"已缓存版本"的代码只去掉一层扩展名，于是版本号成了 `1.0.0.sig`，一路显示到升级摘要：`people/basic: 1.0.0.sig → 1.1.0` | 加完签名缓存后跑全量测试 |

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D278 | **钥匙串是总开关**：没配 `publicKeys` 时 `requireSignature` 整体失效（放行 + 警告） | 没有信任锚点就没有"强制"可言。阻断换不来安全收益，只会让所有现存项目当场装不了东西——结果必然是大家把校验关掉。但要出声：使用者以为开着强制校验，实际一次没验过 |
| D279 | `requireSignature: false` **仍然拒绝验不过的签名** | 它管的是"没有签名允不允许"，不是"坏签名允不允许"。若关掉就连坏签名一起放过，本地开发环境成了投毒入口，而开发机上的组件照样连着真实数据库 |
| D280 | **只有市场安装源受签名约束** | 008 §8.4 原文是"从**市场**获取 Manifest 和签名"。本地源是使用者自己正在编辑的目录，git 源是他自己写下的仓库，那里没有"发布者"这个角色。一并强制会让所有本地开发项目瘫痪 |
| D281 | 校验放在 `internal/source`，不放在 `add` 命令里 | add / up / sync 都会取 Manifest。放命令层就要写三遍，漏一个就是一条不验签的通路。统一入口 `cli.newSourceClient` |
| D282 | **缓存也要校验**，并在旁边存 `<name>.sig.json` 信封 | 否则"先不校验 add 一次、再打开 requireSignature"就能让一份从未验过的 Manifest 一直用下去。信封里必须同时记**来源类型**：只存签名的话，"没有签名"分不清是市场给的未签名组件（该拦）还是 git 源给的（不该管） |
| D283 | 缓存校验不过时**退回重新拉取**，不直接报错 | 缓存可能只是旧了（公钥轮换、发布者重新签过），硬报错让人除了手删缓存无路可走；重新拉的那份同样要过校验，安全性没少 |
| D284 | **先验后存**：验不过的内容绝不写入缓存 | 否则下一次它就成了"本地已有的那份"。真环境篡改验证时确认了缓存里仍是原始镜像 |
| D285 | 市场**只做结构校验**，不做密码学校验 | 市场手里没有可信公钥。让发布者连公钥一起传就是自己给自己发证——攻击者拿到发布 Token 后用自己的密钥签、连公钥一起传，"校验"照样通过。**比没有更糟**，因为会让人以为验过了。这是对 008 §8.2 时序图的有意偏离，已回灌设计书；登记 **P30** |
| D286 | 市场**不强制**签名 | 强制与否是使用者的策略（008 §8.5）。同一个市场同时服务"本地开发随便装"和"生产必须验签"的项目，发布侧一刀切等于替所有人做决定 |
| D287 | 但市场**挡住结构非法的签名**（算法不认识 / 缺 ref / value 不是 base64） | 这三种一眼就是错的。放进库里只会让每个使用者在 add 时各自撞一次墙，那时已查不清是谁、什么时候传坏的 |
| D288 | `publish --sign` 在**联网之前**签名 | 版本号一旦建出来就不可回收（18.14，软删除也占位）。不能因为密钥路径写错就烧掉一个有语义的版本号。真环境验证时确认了：签名后市场因别的原因拒绝，库里没留下版本记录 |
| D289 | `publicKeyRef` 默认按 `--key` 的 `.key` → `.pub` 推导 | 恰好得到 008 §8.3 示例里的 `keys/people-basic-release.pub`，可预期也可解释。私钥名不是 `.key` 结尾时报错要求显式指定，不硬猜 |
| D290 | 签完在终端打印"使用者需要在 `installer.publicKeys` 下声明 xxx" | 签名的另一半在使用者手里。发布者不知道要转告什么，使用者就永远配不上公钥，签名等于白签 |
| D291 | 只渲染**验过的**组件（`🔏 签名：✅ 已校验`），不列"未校验" | 绝大多数项目还没用上签名，逐个列"未校验"会把正常状态渲染成一屏噪音。真正的落差（要求强制却没配公钥、发布者不认识）走警告 |
| D292 | 扫描 `.brickkit/manifests/` 时**只认 `.yaml`** | 这个目录以后还会放别的东西。筛"只认 .yaml"而不是"排掉 .sig.json"，下次加文件不会再踩一遍 |
| D293 | `remove` 一并删签名缓存 | 留下孤儿签名的话，重新 add 同一版本会先命中一份对不上的旧签名——虽有兜底会重新拉取，但那已经是在靠兜底救场 |

**回归影响：** `TestNotImplementedCommands` 的表已清空（命令树上不再有未实现入口），
`TestPublishSignFlagReportsNotImplemented` 按新行为重写为

### Step 20-A：签名核心（`internal/security`） — ✅ 2026-08-15

**产出文件：**

| 文件 | 说明 |
| --- | --- |
| `internal/security/security.go` | `Signature`（008 §8.3）、`Verify`、`VerifyManifest`。包注释说明"签的是 Manifest 不是镜像""验签零依赖" |
| `internal/security/canonical.go` | `CanonicalPayload` / `CanonicalDigest`：把 YAML/JSON 两种写法收敛成同一串待签字节 |
| `internal/security/keyring.go` | `KeyRing` / `LoadKeyRing`：信任锚点，只认 `installer.publicKeys` |
| `internal/security/sign.go` | `Sign`：调 cosign `sign-blob`，固定 `--tlog-upload=false` |
| `internal/config/config.go` | `Installer.PublicKeys` + `Config.PublicKeys()` |
| 测试 5 个文件 | 28 个测试（含子测试共 34 例），其中 6 个是**真 cosign** 跨工具测试 |

**先证明可行性，再动手写。** 动工前在草稿区做了两个真跑：

1. `cosign generate-key-pair` → `sign-blob` → `verify-blob`，并确认篡改后报错；
2. **只用 Go 标准库**（`x509.ParsePKIXPublicKey` + `ecdsa.VerifyASN1`）验同一个签名 → `true`，篡改 → `false`。

第 2 条决定了整个架构：**发布者要装 cosign，使用者不用**。若验签也要装 cosign，"生产环境强制签名"（008 §8.5）就意味着每台机器、每个 CI runner 都得装它——大多数团队会因此直接关掉校验，安全措施变成摆设。

第 1 条还撞出一个默认行为：cosign **默认把签名条目上传到 Sigstore 的公共 Rekor 透明日志**（输出 `tlog entry created with index: 2475377191`）。对开源组件是优点，对 private 组件等于公开"某公司某时刻发布了某个内部组件及其哈希"。因此 `signArgs` 固定带 `--tlog-upload=false`。

**设计书没写、但决定签名有没有意义的三件事**（已回灌 008 §8.3.1 / §8.4 / §8.4.1 / §8.4.2 与 003 §3.6）：

| 缺口 | 不补会怎样 |
| --- | --- |
| 公钥从哪来 | 008 §8.3 只有 `publicKeyRef` 这个名字。若跟着签名从市场取，就是市场自己给自己发证——市场被攻破时组件和公钥一起换掉，验签照样通过。而 §14.1 恰恰把"市场被攻破"的应对写成"签名校验" |
| 签的是哪串字节 | Manifest 一路 YAML→JSON→YAML 转换，字节序早变了。对原始字节签名必然失效，且失效方式随市场版本、反向代理而变 |
| 验完是否核对身份 | 签名只证明"是发布者签的"，不证明"是我要装的那个"。被攻破的市场可换成同一发布者签过的旧版本（含已知漏洞）——降级攻击 |

**跨工具验证（这组测试是全包最要紧的）：** 其余测试都用 Go 自己造的密钥和签名，只能证明逻辑自洽。`cosign_interop_test.go` 用真二进制**双向**验：cosign 签 → 标准库验通过；标准库的载荷 → `cosign verify-blob` 输出 `Verified OK`。反方向那条保证签名不是只有 BrickKit 认得的私有格式，运维和审计能拿标准 cosign 独立复核。没装 cosign 时跳过——使用者本来就不需要装。

**真跑出来的一个坑（单测发现不了）：** 第一版实现把 cosign 的失败原样透传。无终端环境（CI、测试进程）下私钥要口令时，cosign 报的是

```
reading key: inappropriate ioctl for device
```

跟签名、跟口令一个字都不沾边，只会让人往终端或权限方向白查。现已识别该输出并翻译成"需要私钥口令但没有终端可输入 + 用 `COSIGN_PASSWORD` 传入"，`TestSignReportsMissingPassword` 断言渲染结果里**不出现** `ioctl`。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D266 | 签的是 **Manifest**，不是镜像 | 开发计划 20.1/20.3 写"对镜像签名"，但 008 §8.4 / 007 §7.4 的流程是 CLI 在 `add` 时校验 **Manifest** 签名。镜像签名存在 registry 里、由集群准入控制器验，CLI 根本碰不到。按设计书做，镜像签名另立 **P29** |
| D267 | 验签只用 Go 标准库，不依赖 cosign 二进制 | cosign 的签名就是标准 ECDSA P-256 over SHA-256（ASN.1 DER + base64）。让每个使用者装 cosign 才能验签，等于劝人关掉校验 |
| D268 | 签名生成仍然调 **外部 cosign** | 私钥管理（口令、KMS、硬件密钥、keyless）全是 cosign 的地盘。自己实现只能覆盖"明文私钥文件"这一种最不安全的情形，还会把它变成唯一选择 |
| D269 | 签名对象是**规范化载荷**（键名字典序的 JSON），不是原始字节 | Manifest 一路被改写形态，对某一种写法的字节签名必然失效。顺带的好处：注释、缩进、引号风格的改动不算篡改——它们确实不改变行为 |
| D270 | 规范化时**重复键直接拒绝** | 不同解析器有取第一个的、有取最后一个的。这个分歧足以构造"发布者看到 A、CLI 校验 A、运行时用 B"的文档。规范化本身也是攻击面 |
| D271 | 公钥**只**来自 `installer.publicKeys`，找不到即失败 | 绝不回退到"那就从市场拿一个"。信任锚点必须在使用者手里，跟着 brickkit.yaml 进 Git、有评审记录 |
| D272 | `VerifyManifest` 额外核对 `metadata.id` / `version` | 挡降级攻击。ID 与版本本来就在签名覆盖的内容里，核对一下即可 |
| D273 | 签名固定 `--tlog-upload=false` | cosign 默认上传公共 Rekor 日志。private 组件（007 §5.1）绝不能这样。要透明日志的项目应自建 Rekor |
| D274 | `publicKeyRef` 必填，CLI 不代为编造默认值 | ref 是发布者与使用者之间的契约（使用者要照它配同名条目）。随手起一个默认值等于替双方定了一个谁都没约定过的名字 |
| D275 | 没配 `publicKeys` **不是**配置错误 | `requireSignature` 默认 true，若解析配置时就要求必须配公钥，所有还没用签名的现有项目连 `brickkit status` 都跑不起来。拦截放在安装时——那里才说得清是哪个组件、该怎么办 |
| D276 | `publicKeys` 相对路径以**项目根目录**为基准 | 否则在 `components/` 子目录里执行 brickkit 就找不到公钥：同一份配置在不同目录下行为不同，是最难查的一类问题 |
| D277 | 把 `cosign.key` 当公钥配进来时**点名说是私钥** | 私钥进了 Git 是要立刻轮换的事故，只报一句"格式不对"会让人当成小问题 |

**未做（20-B）：** `publish --sign` 接线、市场存储签名（20.6）、`add` 时按 `requireSignature` 校验（20.4 / 20.5）。目前 `--sign` 仍返回 `NotImplemented`，下载链路仍不验签（**P8** 未关闭）。
