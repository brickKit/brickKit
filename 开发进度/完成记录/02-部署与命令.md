### 移除 Podman 支持（P27 收尾） — ✅ 2026-08-16

**当初记的理由是错的。** 延后清单里写的是"podman 的 docker 兼容 API 对本机这个版本的
docker CLI 返回空镜像列表"，听起来像版本不兼容。查证下来：

```
podman 兼容 API:  ApiVersion 1.41 / MinAPIVersion 1.24
docker CLI:       想要 1.55 → 协商到 1.41，成功
```

协商是好的。真实原因是**本终端跑在 VS Code 的 snap 沙箱里**，
`XDG_DATA_HOME` 被改写成 `/home/zhijie/snap/code/254/.local/share`，
而 podman 服务用默认的 `~/.local/share`——CLI 与服务读的不是同一个存储。
跟 docker/podman 兼容性毫无关系。

**顺带查出一个真 bug（已修）：** 对齐存储后 `up` 走到了新的地方——
容器起来了、`podman ps` 显示 healthy，而 CLI 报"未创建"。根因是 `engine.run`
把 stdout 与 stderr 合并进同一个缓冲区，而 `podman compose` 每次往 stderr 打一行
`Executing external compose provider` 横幅，于是 `ps --format json` 的输出变成
"横幅 + JSON"，解析失败——**一次成功的部署被报成失败**。

这不是 Podman 特有的：**kubectl 的弃用警告会同样地毁掉 `status`
与 §5.9.1 的孤儿清理**。已改为成功只返回 stdout、失败才带上 stderr
（错误信息几乎总在那里）。3 条测试，其中一条用 `sh -c 'echo >&2; printf json'`
复现真实形状。

**修完后的实测：**

| 能力 | Podman |
| --- | --- |
| `up` | ✅ |
| `status` | ✅ 显示 healthy |
| 业务请求 | ✅ 返回真实数据 |
| 幂等重跑 | ✅ |
| **`down`** | ❌ `rootless netns: kill network process: permission denied` |

`down` 那条**不是我们的问题**：纯 `podman compose down`、甚至纯 `podman rm -f`
不经过 BrickKit 也一样失败。试了三个假设（跳出 snap 沙箱、重启 socket 服务、
对照纯 podman），都绕不过去。

**决定：移除 Podman 支持，留下解释。** 删掉 `NewPodman` / `NewPodmanCompose` /
`engine.Podman` / `BRICKKIT_ENGINE=podman` / `podmanEngine()` 及相关测试；
`Detect()` 在"只装了 Podman"时**单独报一条错**，说清卡在哪。
005 §7 从"Podman 支持"整节改写成"为什么暂时只支持 Docker"，
含实测结果表、为什么不留半个、CLI 的实际输出、以及回来的三个条件。

**顺带清掉一段死代码：** `hostGateway(engine string)` 的参数**完全没被使用**
（D 记录早已确认 Docker 与 Podman 用同一个 `host-gateway`）。
那条 engine 管线只为 Podman 存在，一并收敛。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D412 | 移除 Podman，而不是标成"实验性" | 坏的偏偏是 `down`。`up` 能跑通反而是陷阱——它让人以为整条路都通，直到卸不掉才发现。一个停不掉的项目会一直占着端口和数据卷，而 CLI 报的是成功 |
| D413 | "只装了 Podman"单独报一条错，不并进"没找到引擎" | 两者该做的下一步完全不同：后者装个 Docker 就好；前者说明问题不在他机器上，装了也未必有用 |
| D414 | 错误文案写出**具体卡在哪**，不只说"不支持" | 只说不支持会让人以为是没做。真实情况是做过、跑到一半、卡在一处绕不过去的地方——说出来，使用者才能自己判断他的环境会不会一样卡住 |
| D415 | `run` 成功只返回 stdout，失败才合并 stderr | 有些工具在成功路径上也往 stderr 写（podman 的横幅、kubectl 的弃用警告），混进来会毁掉 JSON 解析；而失败时错误信息几乎总在 stderr，丢了它就只剩一句没内容的"执行失败" |

| 文件 | 内容 |

**真跑验证：** 用**真的 Git 仓库**（`git init` + 一次提交）做源码目录，
跑完归档 → 激活 → 再归档，`.git` 完好、`git status` / `git log` 照常。
17.10 用**真容器**验证：两个组件跑着的时候执行 sync，源码被归档，
而 `docker ps` 里两个容器**一个都没动**。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D250 | 用 `os.Rename` 整目录搬家，不复制 | 每个组件是独立的 Git 仓库，整目录移动才能保住 `.git`（连同 index、hooks、文件权限）。归档目录就在 `components/` 底下，同一个文件系统，不会跨设备失败 |
| D251 | **只动 brickkit.yaml 里声明过的组件** | `components/` 下还可能有使用者正在开发、尚未 `add` 进来的源码。级联计算里没有它，不代表"它该被归档"，只代表"这不归我们管"——归档别人正在写的代码是不可接受的 |
| D252 | 目标目录已存在时**报错阻断**，绝不覆盖 | 两处都有源码时，平台不替使用者决定保留哪一份。移走一半更糟 |
| D253 | 归档原因优先取级联结果里的原话 | 级联算出来的是"强依赖 demo/hello 不启动"这种具体话；退回一句笼统的"级联跳过"等于把已经查明的原因丢掉 |
| D254 | 按**组件 ID** 归集，与版本无关 | 一个组件 ID 只有一份源码目录（`internal/workspace` 的既有约定）。多版本共存时，只要有任一版本会启动就保持活跃 |
| D255 | sync 不碰引擎、不写配置、不生成部署文件 | 004 §3.9 的职责对照表：sync 管源码目录，up 管容器。真容器验证过 |

**试用指南同步：** 02 章新增 §2.4「整理源码工作区」，README 的"还没实现"里删掉 sync。

**Phase 3（CLI 命令实现）就此完成。** 004 §2 的 11 个命令全部实现。

→ 确认失败 → 实现 → 真实验证。CLI 模块 **979 个测试**，`internal/cli` 覆盖率 **90.0%**。
**Step 15 至此三段全部完成。**

**产出文件：**

| 文件 | 说明 |
| --- | --- |
| `internal/cli/up_checks.go` | `--only` 收窄、升级处理、`--check-resources` 体检、明文密码告警<br>（后来拆成 `up_only.go` / `up_upgrade.go` / `up_checks.go` / `up_secrets.go` 四个文件） |

**测试验证结果：**

| # | 验证项 | 结果 |
| --- | --- | --- |
| 15.8 | `--only` 只启动指定组件 | **连同强依赖一起启动**——只起被点名的那个，它的依赖不在，容器起来也连不上 |
| 15.9 | `--only` 遇 `enabled: false` | 报错阻断：两个意图直接冲突 |
| 15.10 / 15.11 | `--only` 带 / 不带版本 | 带版本只启动那一个；不带版本启动该组件的所有版本（002 §3.6） |
| 15.12 | `--config` | 用指定配置文件；生成物仍写进默认的 `.brickkit/` |
| 15.7 | `--check-resources` 资源不可达 | 警告不阻断；**只探外部资源**（托管资源正要靠这次启动带起来，探它必然失败） |
| P22 | 宿主机端口被别的进程占着 | 启动前警告，并指出是哪个组件要用它；**排除本项目自己的容器** |
| P5 | 明文密码 | 每次 `up` 都查，警告不阻断，**警告里不打印密码本身** |
| P10 / P15 | 升级 | 版本号一改就走升级流程：兼容性检查（阻断项在启动前报错）→ 拉新版本 Manifest 与产物 |

**升级检测的判据：不是"版本号变过"，而是"这个版本的东西本地有没有"。**
004 §1.3 写明 CLI 不持有运行时状态，它记不住上一次跑的是哪个版本。
因此判据是"缓存里有这个组件的别的版本、却没有现在这个版本"：
首次安装（一个版本都没有）与缓存被清空都不算升级；
改回一个已经装过的版本也不再重复走流程（该拉的都在本地了），但照常按新配置启动。

**真实运行验证：**

```
up --only department/tree      → people/basic 标记"未被 --only 选中"，只起 department/tree
status                         → 确认只有一个组件在跑
外部进程占住 18092 后
  up --check-resources         → ⚠️ 宿主机端口已被占用（18092，people/basic 的 expose）
自家容器占着 18092 时再查      → 不报警（重复 up 的正常情形）
密码写成明文                   → ⚠️ 明文密码告警，且输出里没有密码本身
department/tree 1.0.0 → 1.1.0  → 检测到版本变更 → 新 Manifest 与产物落盘、旧版本保留
                               → 升级变更摘要（含新版本的迁移命令）
  up                           → 1.0.0 与 1.1.0 **同时在跑**（people/basic 强依赖 1.0.0）
```

最后一条同时验证了 002 §3.6 的多版本共存与开发计划 38.12。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D205 | `--only` 取**强依赖闭包**，不是字面上的那几个 | 只起被点名的组件，它的强依赖不在，容器起来也连不上——等于交付一个必然失败的启动 |
| D206 | 收窄启动集合的 `Restrict` 放在 cascade 包里 | running 索引与 Components 的一致性是那个包的不变量；在外面拼一个 Result 迟早会出现"说要启动、实际不在集合里" |
| D207 | 升级判据是"本地有没有这个版本的东西"，不是"版本号变没变过" | CLI 无状态（004 §1.3），记不住上次跑的版本。这条判据同时让"首次安装"与"缓存被清空"自然地不算升级 |
| D208 | 升级检查在**解析依赖图之前**做 | 不然新版本引入的依赖还没进图，就先报一句"缺依赖"，指向完全错误的方向 |
| D209 | 产物下载失败不阻断启动 | 产物是开发时的辅助（004 §10.1）；拿不到 openapi.json 不该拦住一次部署 |
| D210 | `--check-resources` 只探**外部**资源 | CLI 托管的资源正要靠这次启动带起来，探它必然失败——一条必然出现又毫无意义的警告只会让人以后忽略所有警告 |
| D211 | 端口体检要排除本项目自己的容器 | 否则第二次 `up` 会把上一次留下的自家容器报成"端口被占用" |
| D212 | 明文密码告警里不打印密码 | 那等于把它又抄了一遍到终端与 CI 日志里 |
| D213 | `--check-resources` 与 `--dry-run` 同用时照样体检，且不要求引擎可用 | `--dry-run` 的意思是"告诉我会发生什么"，不是"什么都别做"；那台机器上也许根本没装 docker |

**未做（明确记录）：** 15.20 Podman 只到单元测试（**P23**，Step 34）。

### Step 15-B：`brickkit down` 与 `brickkit status` — ✅ 2026-08-14

**开发方式：TDD。** 先写 22 个业务行为测试（覆盖 15.13–15.18、15.21）→ 确认失败
→ 实现 → **对着真容器验证**。CLI 模块 **949 个测试**。

**产出文件：**

| 文件 | 说明 |
| --- | --- |
| `internal/cli/lifecycle.go` | down / status 共用的"项目现状"读取：配置 + 级联 + 部署文件 + `--only` 解析 |
| `internal/cli/down.go` | 停止项目或部分组件，停止顺序与启动相反 |
| `internal/cli/status.go` | 运行中 / 未在运行 / 未启动及原因 / 本地调试 / 资源可达性 |
| `internal/cli/root.go` | `Options.Probe` 注入点（资源拨号，测试可替换） |
| `internal/compose/compose.go` | 导出 `IsManagedHost`：status 与生成器共用同一条"托管 / 外部"判据 |

**为什么 down 与 status 共用一份读取逻辑：** 它们在回答同一个问题的两个侧面
（"现在这个项目是什么样"）。各读各的迟早会出现 status 说在跑、down 却停不掉。
两者都**不重新生成部署文件**——它们面对的是已经跑起来的东西，
重新生成只会掩盖"配置改了但还没 up"这个事实。

**测试验证结果：**

| # | 验证项 | 结果 |
| --- | --- | --- |
| 15.13 | down 不删 volume | 引擎层用例锁定不带 `-v`；**真跑验证**：down 后卷仍在，重新 up 后数据完好 |
| 15.14 | `down --only` | 只停指定组件；支持 `@版本`，不带版本时停该组件的所有版本 |
| 15.21 | 停止顺序与启动相反 | `--only` 时由 CLI 倒序；整项目停时交给引擎（compose 本身按依赖倒序停） |
| 15.15 | 展示运行中的组件 | 组件 ID / 版本 / 状态 / 端口映射；**迁移容器与资源容器不混进组件列表** |
| 15.16 | 展示未启动的组件及原因 | 直接复用级联计算给出的理由（显式禁用 / 级联跳过） |
| 15.17 | 展示本地调试组件 | 单列一节；没写 localPort 时按 D178 显示组件声明的端口 |
| 15.18 | 展示资源状态 | 托管资源看容器状态、外部资源真拨号，见下 |

**一个必须分流的地方：资源可达性不能一律拨号。**
CLI 托管的资源（`host` 是服务名）跑在容器网络里，宿主机上 `dial postgres:5432`
连名字都解析不了——它的可达性只能看容器状态。只有外部资源（IP / 域名）才拨号，
而且判据必须与生成部署文件时**同一条**（因此把 `IsManagedHost` 导出，不各判一次）。

**真实运行验证：**

```
status（运行中）      → 两个组件 healthy + 端口映射 + postgres-main 可达
down --only people/basic → 只停它；再 status → people/basic 未创建，department/tree 照常
down                  → 全停；docker volume ls 里 brickkit-step15-demo_postgres-data 仍在
up                    → 数据完好（departments 4 条，张三仍能查到部门名）
status（local: true） → department/tree 单列在"本地调试"，端口按声明值 8080
```

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D197 | down / status 共用 `loadProject`，且都不重新生成部署文件 | 它们面对的是已经跑起来的东西；各读各的会出现"status 说在跑、down 停不掉" |
| D198 | 整项目 down 时不传 service 列表 | compose 自己就按依赖倒序停；CLI 再排一遍只会多一处可能出错的地方。`--only` 时才由 CLI 倒序 |
| D199 | `--only` 停部分组件用 `rm -sf` 而不是 `down` | `down` 会把网络一起拆掉，剩下还在跑的组件瞬间失去彼此 |
| D200 | 资源可达性按托管 / 外部分流，判据从 compose 包导出复用 | 托管资源在容器网络里，宿主机拨号解析不了它的名字；两处各判一次迟早分叉 |
| D201 | 资源不可达**不**让 status 失败 | status 的职责是报告现状，不是判定健康。资源连不上本身就是要报告的内容之一 |
| D202 | status 不画 ┌─┬─┐ 表格，沿用其余命令的缩进风格 | 004 §3.7 的样例是框线表，但表头是中文、内容是 ASCII，终端里对齐要算东亚字符宽度，脆且与 up / order 的风格不一致。信息一条不少 |
| D203 | 迁移容器与资源容器不出现在组件列表 | 使用者装的是组件，看到的也该是组件；资源单列一节，迁移是平台的实现细节 |
| D204 | 没有部署文件时，先说"为什么一个都不会跑"再说"尚未启动过" | 配置里全 `enabled: false` 时，一句"尚未启动过"等于什么都没回答 |

**未做（明确记录）：** `--only` / `--check-resources` / 升级路径（15-C，含 P5 / P10 / P15 / P22）。

**真跑起来抓到的三个真问题：**

**① compose 的项目名是 `generated`，多个 BrickKit 项目会互相顶掉。**
compose 默认拿部署文件所在目录名当项目名，而我们的文件固定在 `.brickkit/generated/` 下——
同一台机器上**所有** BrickKit 项目在引擎眼里都叫 `generated`：
`up` 会把别的项目的容器顶掉，`down` 会停错项目。修法是显式传 `-p brickkit-<项目名>`，
容器名因此也带上项目前缀（`brickkit-step15-demo-people-basic-1-0-0-1`）。

**② 引擎失败时只显示第一行输出，等于什么都没说。**
第一次真跑失败，CLI 报的是"输出：Network brickkit-xxx-net Creating"——
而真正的原因 `service "department-tree-1-0-0-migration" didn't complete successfully: exit 1`
在**最后一行**。compose 的输出是一长串进度行，原因永远在末尾。改成取末尾三行。

**③ 健康检查写死 `wget`，而 `python:3.12-slim` 里没有 wget（也没有 curl）。**
后果极其隐蔽：组件跑得好好的、日志写着"组件已就绪"，平台却判它 `unhealthy`，
依赖方卡在 `service_healthy` 上永远等不到。K8s 没有这个问题（`httpGet` 由 kubelet
从容器外发起），Docker 的健康检查却必须用镜像**内部**真有的命令。
修法：生成 `CMD-SHELL "wget … || curl … || exit 1"` 两者都试；
规则写进 **002 §9.3.1**（含各基础镜像的对照表）；people/basic 的镜像补装 curl。

**另外两处在解析真实输出时暴露的问题：**

| 问题 | 修法 |
| --- | --- |
| `compose ps --format json` 的 `Publishers` 是**对象数组**，按字符串映射直接解析失败 | 收原始 JSON，数组与字符串两种形状都认（不同 compose 版本不一样） |

**核对时发现的漏洞：迁移容器拿到了主容器的环境变量，却没有对应的 `extra_hosts`。**
002 §8.5 承诺"环境变量原封不动复制"，但项目里有 `local: true` 组件时，

已修（两者一起给），并把这条写进 002 §8.5。

**真跑起来抓到的两个真问题：**

**① 组件入口把未知参数当成"启动服务"，一个拼错的迁移命令就能卡死整个项目。**
构造 14.3 时，我把迁移命令改成 `migrate-does-not-exist`，预期是迁移容器失败退出。
实际是：`department/tree` 的 `run()` 只认 `args[0] == "migrate"`，**其余一律回落到 `serve()`**，
于是迁移容器把服务起了起来，永不退出，两个主服务永远卡在 `Created`——
而容器日志里写着"组件已就绪"，看上去一切正常。
这与 D167 的 entrypoint 参数错位是**同一种事故的两个来源**（一个来自平台生成，一个来自组件入口）。
`people/basic`（Python）有同样的写法，也一并修了。
两个组件都改成**先认参数、不认识就报错**，且校验发生在读环境变量、连数据库**之前**——
为了说一句"参数写错了"，不该先去连一个可能根本连不上的库。
规则写进 **002 §8.5.1**（硬性要求 + 正误对照）与 **009 §11.13**（组件开发者须知）。

**② 本地安装源的 Manifest 与产物被缓存，改了不生效且一声不吭。**
修好①之后重跑，迁移容器报的还是旧命令——`.brickkit/manifests/` 里是一份旧快照。
004 §7.5 原文就是"`up` 时优先使用缓存"，所以这不是实现走样，是**设计没区分本地源**。
缓存是为了省网络往返，本地源根本没有网络往返；它的语义恰恰是"这份源码正在被我改"。
后果是改了端口 / 迁移命令 / 配额之后 `brickkit up` 依旧按旧的生成，且没有任何提示。
已修：本地源不吃 Manifest 缓存，**产物（.proto / openapi.json）同理**——
缓存住会让调用方按旧契约生成客户端。远程源（market / git）的同一个版本内容不可变，缓存照旧。

**真实运行验证：**

```
迁移命令写错 → 迁移容器 exit 1，报"未知的参数：migrate-does-not-exist（可用：…）"

```

**① `localPort` 的默认值规则本身是坏的（设计书缺陷）。** 005 §4.6 原文是"用户未指定 →

| D175 | `localPort` / `exposePort` / 自动映射共用一张端口台账，使用者写死的先占位 | 它们抢的是同一台机器上的同一批端口。反过来会出现"自动分配抢走了使用者钦定的端口"这种莫名其妙的失败 |
| D176 | 外部资源（host 是 IP/域名）**不**改写成 localhost | 它本来就在容器网络之外，宿主机按原地址就能连上；改写反而会连到一个不存在的服务 |
| D177 | local 组件的额外端口不重新分配，保持声明值 | 宿主机上跑的是同一份代码，额外端口监听的还是声明值。两个 local 组件声明了同一个额外端口时它们会真的抢端口，因此在生成阶段报错 |
| D178 | `localPort` 默认取组件声明的 `deployment.port` | 见上文①：直接从 8081 起会得到一个没人监听的端口。8081 只是**退路** |
| D179 | local 组件的迁移不代跑，但必须警告 | 容器里那份代码不是开发者正在调试的代码，代跑没有意义；不说一声则会对着 `relation does not exist` 发懵 |
| D180 | `setVar` 只改已存在的变量，不补新的 | 变量不存在意味着注入引擎判定"这条不该注入"（如弱依赖没启动），本地调试没有理由把它凭空补回来 |
| D181 | 引擎检测放在命令层，`BRICKKIT_ENGINE` 可覆盖 | Step 13 只需要它决定 extra_hosts 的别名；"两个都没装"要到真启动（Step 15）才该报错。同时装了两个引擎的机器需要一个说得清的开关 |
| D182 | env 文件权限 0600 | 里面有资源连接信息；compose 文件是 0644，但那个文件本来就要交给 docker 读 |

**真跑起来抓到的一个真 bug（设计书样例同样有）：** 迁移容器没在做迁移，
而是**把服务启动起来了**——组件镜像带 `ENTRYPOINT`，而 compose 的 `command` 只覆盖 `CMD`，
于是实际执行的是 `/app/department-tree /app/department-tree migrate`，参数错位。
后果很隐蔽：迁移永远不"完成"，主服务卡在 `service_completed_successfully` 上，整个项目起不来。
修法是把 `migration.command` 拆成 `entrypoint`（第一段）+ `command`（其余）。
**设计书已全面修正**（不只是发现问题的那两处）：

| 位置 | 处理 |
| --- | --- |
| 002 §8.4 | 加入正确/错误写法对照、失败后果说明，并写明 **K8s 不需要拆**（`container.command` 本身整体替换 ENTRYPOINT） |
| 005 §5、§6.2；004 §5.x；006 §12.2；附录合集 | 4 处生成的 compose 迁移 service 全部改为 `entrypoint` + `command` |
| 005、004、附录合集的 K8s Job 样例 | **不改**，但加注释说明为什么这里整条命令写 `command` 就对——防止有人照着 compose 的写法去"修" |
| 009 §11.4 | 从组件开发者视角说明：`migration.command` 照常写完整命令，CLI 会自动拆；手写 compose 调试时才要注意 |
| 000 导航 | 故障速查加入"迁移容器一直不退出、主服务卡在 Created" |

`component.yaml` 里 `migration.command` 的写法**不变**（完整命令），
拆分是 CLI 生成 compose 时做的事——两种部署目标的差异只在这一处。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D166 | 不写 `version: "3.8"` | Compose V2 已废弃该字段，写了会产生警告。设计书样例成文于 V1 时代；测试直接断言 `docker compose config` 无警告 |
| D167 | 迁移 service 同时覆盖 `entrypoint` 与 `command` | 只写 command 在带 ENTRYPOINT 的镜像上参数错位，且失败方式极其隐蔽（迁移容器变成服务，项目卡死） |
| D168 | 弱依赖不进 `depends_on` | 它可能根本不启动，写进去 compose 会一直等，把"可选"变成"必须" |
| D169 | 依赖没有健康检查的组件时用 `service_started` | 等 `service_healthy` 会永远等下去 |
| D170 | environment 用 `KEY=value` 列表而非 map | 列表保序，生成文件可比对；map 在 YAML 里会被重排，每次 diff 都是噪音 |
| D171 | Step 12 只实现 `up --dry-run` | `--dry-run` 就是"只生成不启动"，正是 Step 12 的交付物；镜像权限检测、执行迁移、调引擎启动属 Step 15。`up` 不带 `--dry-run` 仍报"尚未实现（Step 15）"，并有用例锁定 |
| D172 | 生成时输出"需要预先创建哪些数据库" | 006 §9.5：CLI 不建库，但有责任说清楚。否则组件在迁移阶段抛 `database "xxx" does not exist`，使用者以为是组件的问题 |
