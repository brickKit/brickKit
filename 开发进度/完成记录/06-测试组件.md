### Step 29：多版本默认共存验证 — ✅ 2026-08-16 · **Phase 5 完成**

**这一步验的不是新能力，是一条贯穿全局的默认行为：**
多版本共存不是开关，而是 `brickkit.yaml` 的直接含义——**写了几个版本就启动几个容器**
（003 §4.8）。它成立的支点是服务名带版本（`demo-hello-1-0-0`），
那既是容器名，也是依赖方拿到的地址。

**生成侧补了 4 条业务测试**，其中最要紧的是 29.3：
两个调用方各依赖一个版本时，注入的地址必须**各指各的**。
写错的表现极隐蔽——两个调用方都能跑、都能连通，只是其中一个连到了错误的版本上，
而版本间的行为差异可能几周后才显形。

顺带锁住一条容易被"顺手改"的性质：**环境变量名不带版本**。
组件读的是 `DEMO_HELLO_ENDPOINT` 而不是 `DEMO_HELLO_1_0_0_ENDPOINT`——
否则调用方的代码会跟着被依赖方的版本一起改，而那正是版本化服务名要避免的：
版本差异只体现在**地址的值**里，不体现在**变量名**上。

**真容器验证（6 项全通过）：**

| # | 验证 | 结果 |
| --- | --- | --- |
| 29.1 | add 两个版本后 up | 3 个容器全部 healthy |
| 29.2 | 版本化服务名 | `demo-hello-1-0-0` / `demo-hello-2-0-0` 同时在跑 |
| 29.3 | 环境变量各指各的 | caller 的 `DEMO_HELLO_ENDPOINT` 指向它声明的那一版；两个 hello 各自的 `COMPONENT_VERSION` 正确 |
| 29.4 | remove 不指定版本 | 报错并列出全部版本 + 给出可直接执行的命令 |
| 29.5 | `--only demo/hello@2.0.0` | 只起 1 个容器 |
| 29.6 | `--only demo/hello`（不带版本） | 两个版本都起 |

**Phase 5 至此全部完成**（Step 21–29）。

**产出文件：** `tests/components/infra-api-docs/`

| 文件 | 说明 |
| --- | --- |

| `descriptor.go` | 用真描述符解析反射返回的 FileDescriptorProto，取方法名 |

| `config.go` / `main.go` | 环境变量配置、JSON 日志 |
| `component.yaml` / `Dockerfile` / `README.md` | Manifest、镜像、说明 |

**它在平台里的位置很特殊：全部依赖都是弱依赖**——这是唯一一个这样的组件。
六个目标装了几个就展示几个，一个都没装也照样起得来。这不是"容错做得好"，
而是这个组件的本来面目：文档入口不该因为某个业务组件没装就打不开，
而业务组件全挂时正是最需要看文档的时候。

**测试验证结果（真容器，故意只装 2/6 个目标组件）：**

| # | 验证项 | 结果 |
| --- | --- | --- |
| 28.1 | Swagger UI 正常展示 | `/`、`swagger-ui.css`、`swagger-ui-bundle.js` 均 200；代理出的 people/basic spec 含 3 个路径 |
| 28.2 | gRPC 文档正常展示 | Reflection 列出 `department.v1.DepartmentService` 的 `GetDepartment` / `GetSubtree` / `ListDepartments` |
| 28.3 | 弱依赖不可用时不崩溃 | 4 个未装标 `absent`、2 个已装正常；**再把已装的两个也停掉** → 页面仍 200，两者标 `unreachable` |

**四种状态各自对应不同处置**（这是本组件最要紧的设计）：

| 状态 | 含义 | 该做什么 |
| --- | --- | --- |
| `ok` | 拿到文档了 | — |
| `absent` | 平台没注入地址 = 组件**没装** | 装上它 |
| `unreachable` | 地址在，但连不上 | 去看那个组件 |
| `no-docs` | 组件在线，两条路径都没有 | 让它提供 `/openapi.json` 或开 Reflection |

混成一种的话，使用者只能对着空页面猜。`GET /api/v1/sources` 本身就是排障工具。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D357 | 四种状态严格分开，每种都给出"接下来该做什么" | 看到空页面时，使用者需要知道是没装、挂了、还是那个组件不提供文档——三者的处置完全不同 |
| D358 | Swagger UI 从 `swaggerapi/swagger-ui` 镜像拷，**不从 CDN 加载** | 008 §5 的默认不暴露意味着这个页面很可能跑在内网甚至气隙环境。指向公网 CDN 的 script 会让页面永远转圈，而症状看起来像"文档组件坏了" |
| D359 | OpenAPI 由本组件**代理**，不让浏览器直连组件 | 那些组件默认不暴露端口（008 §5.2），浏览器根本连不上；就算连得上也会撞跨域 |
| D360 | 聚合状态里**不含组件的内部地址** | 那等于把内网结构告诉任何能打开这个页面的人 |
| D361 | 探测**并发**且各自捕获错误 | 一个组件出问题最坏只是它自己显示"不可用"，不影响其余——这正是 28.3 的实质 |
| D362 | 探测结果缓存 30 秒，且会过期 | 每次刷新都探六个组件的话，一个卡住的上游会让页面很慢；不过期则新上线的组件永远看不到 |
| D363 | 用真 protobuf 描述符解析反射结果，不在字节里找字符串 | 后者看起来能跑，但方法名恰好出现在别的字段里就会多列一个不存在的方法——文档里多出一个调不通的方法比少一个更误导人 |
| D364 | 反射服务自身（`grpc.reflection.*`）不列出来 | 它不是业务 API，列出来只会干扰阅读 |
| D365 | **没有任何必需配置** | 依赖全是弱依赖，缺席是常态。列成必需就等于要求使用者把六个组件全装上才能看文档 |
| D366 | Go 组件不加 `/openapi.json`，如实显示 `no-docs` | 那是对四个已完成组件的改动，超出 Step 28 的范围。当前状态是真实的，页面也说清楚了组件该怎么做才能出现在这里。登记为 **P32** |

**顺带补齐：** `infra-api-docs` 已加入 `make test-components` 与 `make demo-images`。

| 27.2 | 健康检查正常 | 200 |
| 27.3 | 健康检查不检查 Redis | **停掉 Redis** 后 `/healthz` 仍 200，发布如实报 503 |

**P31 复验（关闭）：** 起完整七层链（department/tree → people/basic → auth + rbac
→ erp/backend → **真事件总线**），审批订单 → `eventPublished:true` →
事件总线读到 → `redis-cli XLEN` 确认真进了 Stream。25.2 从此是真组件验证的。

**契约测试：** 存储层用 fakeredis 与**真 Redis** 跑同一份用例（各 10 条）。
只测 fakeredis 的话，`XADD` 的 maxlen 写错、`xrevrange` 的顺序理解反了，
单测照样全绿——而事件总线出错的表现往往是"事件偶尔丢了"，最难查。

**这一段的一个方法论修正：**

**硬编码地址守卫的做法一直是错的。** 这已经是第三次撞上同一个问题了
（Step 25 的 `clients.go`、Step 26 的 nginx 模板、这里的 `config.py`）：
守卫在整份源码里 grep `localhost`，结果命中的都是**注释与文档字符串**里
必须写的说明（"绝不退化到 localhost"本身就是一句要写下来的话）。
前两次是改措辞绕过去，这次改用 `ast` 只检查**真正参与运行**的字符串字面量。
一个总在误报的守卫，最后只会被人删掉——于是真正的硬编码也就没人拦了。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D345 | 用 Redis **Streams** 而不是 Pub/Sub | Pub/Sub 发出去就没了：没有消费者在线时消息直接丢弃，也无法回看。Stream 能晚点来读、能从某个 ID 接着读，排障时还能翻最近发生了什么 |
| D346 | Redis 在这里是**唯一数据源**，缺了就启动失败 | 与 rbac 正好相反。一个连不上存储的事件总线，起来了也只会把每条事件都丢掉，而发布方以为它们都安全落地了 |
| D347 | 收不下的事件**如实报 503**，绝不假装收下 | 假装成功等于把事件悄悄丢掉，发布方再也不会重发。这比直接报错糟得多 |
| D348 | 启动时**不 ping Redis** | Redis 还没起来时本组件照样应该能启动，等真正收到事件时再报 503。启动就连不上直接退出的话，编排系统会把它反复重启，而它其实只是在等另一个容器就绪 |
| D349 | 健康检查也不 ping Redis | Redis 一抖就把所有副本杀掉重启，而**重启并不会让 Redis 变好**，只会让恢复之后还要多等一轮拉起 |
| D350 | 发布返回 **202** 而不是 200 | 事件已收下，但消费是异步的。用 200 会让发布方以为"已经被处理了" |
| D351 | 额外字段**原样存下** | 事件总线不理解事件的内容（平台不解析业务语义）。丢掉不认识的字段等于逼所有发布方都来改这个组件 |
| D352 | 缺时间戳时由本组件补上 | 宁可用"收到的时间"，也不要一条没有时间的事件——排障时时间往往是唯一能把几个组件的日志对起来的东西 |
| D353 | 发布方自己填的 `id` 被忽略 | 否则两条事件可能撞 ID，按 ID 去找会找出错的那条 |
| D354 | 流用 `maxlen` + approximate 裁剪 | 事件流会一直长，不裁剪迟早把 Redis 撑爆。approximate 按整节点裁剪快得多，代价只是实际长度略多于 maxlen |
| D355 | 契约由**调用方**先定下，本组件照着实现 | erp/backend 早在 Step 25 就在往 `POST /api/v1/events` 发事件了。不能反过来要求已经上线的调用方改 |
| D356 | 硬编码守卫改用 `ast` 只查代码里的字符串 | 见上面的方法论修正。这是这条守卫第三次在自己的文档里误报 |

**顺带补齐：** `infra-redis-event-bus` 已加入 `make test-components`（`PY_COMPONENTS`）、
`make test-components-integration`（真 Redis 契约）与 `make demo-images`。

| --- | --- | --- |

| 2 | **测试脚手架自己错了**：`/docker-entrypoint.sh true` 拿到的是镜像**自带**的 default.conf | 官方入口脚本只在 `$1` 为 `nginx` / `nginx-debug` 时才跑模板渲染。传别的命令进去，测试看起来在跑，其实什么也没验到 |

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D336 | `proxy_pass` 用**变量**而不是写死主机名 | nginx 对写死的主机名只在启动时解析一次：后端没起来时 nginx 直接以 `host not found in upstream` 退出，整个前端起不来——而它本该照常发页面。放进变量就变成每次请求时解析，启动顺序不再要紧 |
| D337 | 配套加 `resolver`，并带上 `$request_uri` | 这三样是一套：有 `set` 没 `resolver` 启动就语法错；用了变量之后 nginx 不再自动转发原始 URI |
| D338 | DNS 地址用官方的 `${NGINX_LOCAL_RESOLVERS}`，不写死也不自己实现 | Docker 内嵌 DNS 与 K8s CoreDNS 是两个完全不同的地址。官方脚本还处理了 IPv6 与多 nameserver，自己写只会少考虑几种情况 |
| D339 | nginx 监听 **8080** 而不是 80 | 容器非 root 运行（002 §1.4），1024 以下端口需要特权。`deployment.port` 也因此是 8080 |
| D340 | 健康检查用 `location = /healthz` 精确匹配 | 避免被 `location /api/` 之类的规则捞去代理到后端——那样后端一抖，前端容器就会被杀掉重启 |
| D341 | 页面里**只用相对路径** `/api/...` | 写死后端地址的话，换个部署环境这个页面就废了，浏览器直连后端还会撞跨域——症状看起来完全是另一回事 |
| D342 | 用真 nginx 跑 `nginx -t` 作为测试 | 配置写错时容器**启动失败**，平台看到的只是"容器起不来"，那句有用的报错还得进容器才看得到。没有 Docker 时跳过 |
| D343 | 占位符检查用正则 `\$\{[A-Z_][A-Z0-9_]*\}` 而不是找 `${` | 注释里写的 `${环境变量}` 是说明文字，不是变量。粗匹配会一直误报，最后只会被人删掉 |
| D344 | 不声明 `configSchema` | 这个组件没有任何需要使用者调的东西。为了"看起来完整"而加一个没人会改的配置项，只是增加噪音 |

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D309 | 权限 = 人的角色 ∪ **部门**的角色 | 这才让"强依赖 people/basic"成为真实需求而不是摆设。也贴合真实 RBAC：按部门授权是最常见的用法 |
| D310 | **Redis 挂了照常回源**，不报错 | 缓存是加速器不是数据源。若因此报错，一个可选的基础设施就变成单点——整个系统的每一次权限检查都会失败 |
| D311 | 没绑定 `cache` 资源时用**进程内缓存**，不报错 | 006 把 cache 定义为一种普通资源，绑不绑是使用者的决定。启动时打一条 warn 说明怎么绑 |
| D312 | **people/basic 挂了且缓存未命中 → 503，不做部分降级** | 那时只知道直接授权、不知道部门授权。返回残缺的权限集比返回错误更危险——调用方会当成完整的用，于是本该有权限的人被拒绝，或者一个"是否管理员"的判断走进别的分支 |
| D313 | 先查缓存**再**调 people/basic | 顺序反过来的话，缓存就挡不住 people/basic 的抖动。真容器验证时正是靠这一条让 p-001 在 people/basic 停机时仍能鉴权 |
| D314 | 缓存键带组件前缀 `authorization-rbac:` | 一个项目里多个组件可能绑同一个 cache 资源；不带前缀，两个组件撞了键名就互相覆盖，症状是"权限偶尔不对"（006 §7） |
| D315 | 缓存**必须有 TTL** | 授权变更时会主动失效，TTL 只是兜底。没有它，万一漏了一条失效，一份错的权限会永远留在缓存里 |
| D316 | 缓存内容损坏时**当作未命中**并删掉 | 报错的话，一条坏缓存会把这个人永久挡在门外 |
| D317 | 空权限集也要缓存 | 不缓存空结果的话，"什么权限都没有"的人每次都回源——而那恰恰是被攻击时最容易被反复探测的一类账号 |
| D318 | `check` 没有权限时返回 **200 + allowed:false**，不是 403 | 这个端点回答"他有没有这个权限"，调用方才决定放行。用 403 会让调用方分不清"我没权限查这个接口"和"我查到了、答案是否" |
| D319 | 权限与角色**排序去重**后返回 | 调用方常直接比对这个数组；顺序随 map 遍历变的话，同样的输入会得到不同输出，缓存里也会存下两份语义相同的值 |
| D320 | 授权指向不存在的角色时**跳过**而不报错 | 角色被删、授权还在，是运维过程中很正常的中间状态 |
| D321 | `GrantsFor` 一次查完"人 + 部门" | 授权判断是最高频的调用，少一次往返就是每个请求都少一次。SQL 里用 `$4 <> ''` 显式处理"没有部门"——那条 WHERE 写错会把**所有部门**的授权都查出来，是一次静默的全局越权（有专门的契约测试） |
| D322 | `reason` 只在"确实有权限"时才算 | 它要多查一次授权，高频路径上不做无谓的工作。算不出来时退回 `direct`——它是给人看的排障线索，不参与任何判定 |

| # | 决策 | 理由 |
| --- | --- | --- |
| D294 | 口令在本组件、身份在 people/basic | 主体的存废由人员系统说了算；也不会出现两份会漂移的身份数据。代价是 people/basic 挂掉时登录不可用——那正是"强依赖"的含义 |
| D295 | 强依赖故障报 **503**，人不在报 **401** | 把基础设施故障报成认证失败，会让使用者在自己的密码上白折腾半天，而真正的问题在另一个组件上。这是排障时最费时间的一类错误 |
| D296 | 用户不存在与口令错误返回**完全相同**的响应 | 任何差别（状态码、文案、字段）都能把一份用户名字典筛成"这些账号真实存在"。用户不存在时也走一遍哈希校验，抹平时间差 |
| D297 | JWT 用 `golang-jwt/jwt/v5`，不手搓 | 这个组件会被当成"BrickKit 组件怎么写"的范例来读。手搓 JWT 是经典安全脚坑（alg=none、签名剥离、定时攻击），范例里不该出现 |
| D298 | 校验时**只接受 HS256**，不看令牌自称的算法 | `alg=none` 与算法混淆攻击的入口就在这里（RFC 8725 §3.1）。有专门的用例锁这一条 |
| D299 | 弱密钥（< 32 字节）**拒绝启动** | HS256 的安全性完全等于密钥强度。一个用弱密钥跑着的认证组件表面上一切正常，只有被攻破时才会发现——宁可根本起不来 |
| D300 | 缺 `JWT_SECRET` 绝不回落到内置默认值 | 那意味着所有装了这个组件的人共用同一把钥匙，任何人都能给任何一处部署签出管理员令牌，而且看起来完全正常 |
| D301 | 口令哈希用 PBKDF2-SHA256 600000 轮 + 随机盐 | 口令哈希要**慢**；快的哈希意味着一张显卡一秒能试上百亿次。轮数取 OWASP 2023 建议值。哈希串带算法与参数前缀，将来换算法时旧哈希还认得出怎么验 |
| D302 | 比较用 `subtle.ConstantTimeCompare` | 普通的 `==` 在第一个不同的字节处返回，攻击者据此可逐字节把哈希试出来 |
| D303 | 损坏的哈希一律判为**失败** | 库里的一条脏数据不该变成一把万能钥匙 |
| D304 | 增加 `/api/v1/verify`（计划里没有） | 令牌用 HS256 签，密钥只有本组件有。没有这个端点，签出去的令牌对下游（erp/backend、authorization/rbac）就是一串不可用的字符串——Step 25 会用到 |
| D305 | 调用强依赖必须有超时（5s） | 没有超时的话，people/basic 卡住会把本组件的连接一个个耗尽，最后连 `/healthz` 都挤不进来：一个组件的慢拖垮两个组件 |
| D306 | 敏感字段名扩到含 `hash` / `credential` | 认证组件里出错时最想打印的就是"收到的请求体"，那里面正好是明文口令。在日志出口统一挡掉，哪怕有人顺手写了 `log("password", pw)` |
| D307 | 样例账号写进 seed 迁移，且可单独回退 | 装配起来要能真登录一次看看；但真实部署必须能一条命令清掉——`migrate down 1` 只回退数据那一版，保留表结构（有测试锁定） |
| D308 | `lib/pq` 钉在 v1.10.9 | `go mod tidy` 自己选了 v1.12.3，与仓库其他组件不一致。统一钉住，避免同一个仓库里两个组件用不同版本的驱动 |

**顺带补齐：** `auth-password-login` 已加入 `make test-components`、
`make test-components-integration`（新建 `brickkit_auth` 库）与 `make demo-images`。

| **强依赖（department/tree）停掉** | 业务接口 **503「部门信息暂时不可用」**，`/healthz` 仍 200，依赖恢复后自动好 |

**真容器踩出来的一个真问题：** 最初 `DepartmentClient` 里放了个永不过期的缓存。
结果把 department/tree 停掉之后，接口照样返回 200——**缓存把"强依赖已经挂了"盖住了**；
同时我自己写的 `test_department_rename_is_reflected_immediately` 也成了假测试
（测试替身没有缓存，真实现有）。改法：去掉跨请求缓存，
把 N+1 问题挪到服务层用**单次请求内的去重**解决，并补两个测试锁死这两条性质。

**CLI 端到端：** `brickkit add people/basic@1.0.0` 自动拉起强依赖 department/tree、
对缺失的弱依赖给出警告、下载 4 个产物文件，`brickkit order` 算出正确的启动顺序。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D149 | Python 组件的测试跑在容器里 | 宿主机没有 python3-venv，装它要 sudo。容器里版本固定、可复现，也和组件的实际运行环境一致 |
| D150 | 部门名**不在本组件存副本**，每次去问 department/tree | 002 §2.2 数据自治。存副本就得处理同步，而部门改名后本组件必须立刻跟着变 |
| D151 | 强依赖不可用 → 503，弱依赖不可用 → 静默降级 | 这是强弱依赖唯一有意义的区别。强依赖挂了还假装成功，会让调用方以为"这个人真的没有部门" |
| D152 | 去掉跨请求缓存，改为单次请求内去重 | 缓存会盖住依赖故障、也让"改名立刻生效"落空；请求内去重两头都占 |
| D153 | openapi.json 由 FastAPI 导出而非手写 | 手写的文档迟早和代码对不上，而它是要发布到市场的产物 |
| D154 | 把 department/tree 的 proto vendored 进本组件仓库 | 这正是使用方的真实工作流：`brickkit add` → 从 `.brickkit/artifacts/…/api-contract/` 取到 proto → 生成客户端 |

| D143 | 一份业务逻辑，HTTP 与 gRPC 都只是薄壳 | 两边各写一遍查询，迟早出现"HTTP 说有、gRPC 说没有"。测试里专门锁了两种协议结果一致 |
