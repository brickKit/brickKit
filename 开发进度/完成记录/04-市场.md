**同时发现一个真实缺陷（记为 P18）：** 把该版本标成 blocked 后再装，服务端返回的是
403 + `COMPONENT_BLOCKED` + "该版本已被市场下架"，但 CLI 只看状态码，
显示成"市场认证失败 → 执行 brickkit login"——把使用者引向完全错误的方向。
服务端是对的，问题在 CLI 没解析错误信封，回填到 Step 19。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D111 | 自己写路由器，不用 `http.ServeMux` | 组件 ID 自带一个 `/`（`scope/name`），且 ServeMux 未命中时写的是纯文本 404/405——CLI 只解析 JSON 信封，拿到纯文本会报"响应无法解析"，把真正的原因盖掉 |
| D112 | 错误码 → 状态码的映射是对外契约 | CLI 靠 404 判断"这个源没有该组件"从而继续试下一个安装源（D40），靠 401/403 提示登录。映射错了整条安装链都会跑偏。`COMPONENT_BLOCKED` 映射为 403（策略性拒绝），CLI 侧的文案问题记为 P18 |
| D113 | 上传端点是 `POST …/artifacts/{artifactId}/upload?file=` | 007 §9.3 写的是 `POST …/artifacts`，但一个产物可声明多个文件（多份 proto），不指明是哪个文件就落不到正确的对象键上；一次请求传一个文件，因此也不需要 multipart |
| D114 | 大小上限用自己的 `limitReader` 而非 `http.MaxBytesReader` | 后者的错误会穿过服务层被统一包成 INTERNAL（500），而"文件太大"是请求本身的问题、应该是 400。用标志位把这件事留在协议层 |
| D115 | `total` 下推到仓储层（新增 `CountComponents`） | 用 `len(items)` 冒充总数，翻页时前端永远算不出还有几页。`ListComponents` 与 `CountComponents` 共用同一份 WHERE 构造，防止两者过滤条件分叉 |
| D116 | 认证在 handler、鉴权在 service，中间件里一条权限规则都不写 | 匿名可以读 public 组件，"要不要认证"取决于被访问的资源，中间件没法一刀切；权限规则只有一份实现才不会分叉 |
| D117 | 令牌用不透明随机串存库，不用 JWT | 运维指南 §5.1 列了 `JWT_SECRET`，但存库的令牌可**即时吊销**（登出即失效），JWT 做不到。`JWT_EXPIRY_HOURS` 仍被采纳为有效期，`JWT_SECRET` 不再需要——**待 18-E 修订运维指南** |
| D118 | 管理员引导只补权限、不覆盖口令 | 运维可能已在市场里改过密码，每次重启按 `.env` 把它改回去会非常难排查 |
| D119 | 启动时自动建表、自动建桶 | 表结构全是 `CREATE TABLE IF NOT EXISTS`，重启幂等；省掉部署时"先跑迁移、再手工建桶"两步易漏的操作 |
| D120 | 配置缺失项一次全报，端口/有效期写错当场失败 | 让运维改一遍 `.env` 就能起来；默默退回默认端口会让人对着一个"起来了但访问不到"的服务查半天 |

### 修订：把建表 SQL 从代码里搬进真正的 migration 文件 — 2026-08-14

**起因：** 你问"migration 文件在哪、每个组件的库结构在哪生成"。答案暴露了一个我做错的地方：
我把建表 SQL 埋在了 Go 的 `ensureSchema()` 与 Python 的 `ensure_schema()` 里。
设计书（002 §8）确实只规定 `migration.command` 是一条命令、不规定形式，
但**把 DDL 藏在代码里，"这一版相对上一版改了什么"就看不见了** ——
而这正是 Step 38 升级测试要验证的东西。

**改法：两个组件都改成有版本的 SQL 文件 + 执行器。**

```
migrations/
├── 0001_init.sql              建表与索引
└── 0002_seed_*.sql            初始数据
```

| 组件 | 执行器 | 打包方式 |
| --- | --- | --- |
| department/tree（Go） | `migrate.go` | `go:embed migrations/*.sql`，直接进二进制 |
| people/basic（Python） | `app/migrate.py` | `COPY migrations ./migrations` 进镜像 |

执行器的三条不变量（两种语言各自实现，行为一致，各有 6 个对着真库跑的测试）：

| 不变量 | 为什么 |
| --- | --- |
| **幂等** | 容器每次重启都会再跑一遍迁移，第二次必须什么都不做 |
| **原子** | 迁移与它的版本记录在**同一个事务**里。先执行后记录会留下一个窗口，进程正好挂在那里就会重复执行 |
| **有序** | 按文件名递增执行，失败即中止；失败的迁移**不记录版本**——记了下次就跳过，数据库会永远停在半吊子状态 |

**真容器复验：** 两个组件各跑两次 `migrate`，第二次都是"无新增迁移"；
`schema_migrations` 表里两条记录、带执行时间；中途改过的数据不会被第二次迁移盖回去。

**顺带澄清的边界（你的原话）：**

| 事情 | 归属 |
| --- | --- |
| database 本身 | **由人建**（运维/你）。库名通过 `DATABASE_NAME` 注入，组件不猜 |
| 库里的表结构与初始数据 | **组件的 migrations**，平台按 `migration.command` 执行，语言无关 |

**追加（同日）：迁移记录按组件隔离 + 回退（undo）**

真容器又测出一个更严重的问题：把两个组件迁移到**同一个数据库**时，
`schema_migrations` 只按 `version` 去重，而两个组件的版本号都叫 `0001_init` ——
后跑的 people/basic 的 0001 被当成"已执行"跳过，然后 0002 往一张
根本没建出来的 people 表里插数据，**直接失败**。

| 改动 | 说明 |
| --- | --- |
| 主键改为 `(component_id, version)` | 版本号是**每个组件各自的**，不是全局的 |
| 共用库时打警告 | 不阻断（本地调试确实方便），但提示 002 §2.2 数据自治要求各用各的库 |
| 新增 `migrate down [n]` / `migrate reset` | 回退最近 n 个 / 全部回退，按版本**倒序**执行 |
| 迁移文件改为 `*.up.sql` + `*.down.sql` 成对 | 没有 down 脚本时回退**报错**，不假装成功 |
| 每个组件补 README | 写清预设库名与 `CREATE DATABASE` 命令，执行一次即可 |

真容器复验（两个组件各跑一遍 `migrate → down → reset → migrate`）：
数据 4 条 → 0 条（表还在）→ 表没了 → 重新回到 4 条。

**沉淀为设计书标准（2026-08-14）：** 这些规则原本只活在两个组件的 README 里，
下一个写组件的人无从知道。已写进设计书：

| 文档 | 新增内容 |
| --- | --- |
| **002 §8.10** | 迁移脚本组织：`NNNN_name.up.sql` / `.down.sql` 成对，版本在组件内唯一递增，**已执行的迁移不得修改** |
| **002 §8.11** | 迁移状态表：`schema_migrations` 的表结构，**主键必须含组件标识**（附共用库会怎么坏的说明） |
| **002 §8.12** | 迁移执行的三条不变量：幂等 / 原子 / 有序，以及各自不满足会怎样 |
| **002 §8.13** | 回退（down）的定位：开发测试用；生产用新的 up 迁移修；缺 down 脚本必须报错 |
| **006 §9.5** | 组件数据库的创建与命名：三层职责划分、为什么建库不交给组件 migration（权限/连接对象/归属）、一组件一库、命名约定、组件必须在文档里声明所需库 |
| **009 §11.10–11.12** | 组件开发者视角的"怎么做"：先建库、Go/Python 的脚本组织与打包、migrate/down/reset 子命令 |
| **011 §2.5** | 使用者视角：安装前为每个组件建库，附命令 |
| **000 导航** | 故障速查加两条（`database does not exist`、共用库迁移互顶）；概念索引加三条 |

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D165 | 这些规则写进设计书而不是只留在组件 README | README 只对这两个组件有效。下一个人写组件时会重新踩一遍共用库、缺 down 脚本、把建表埋进代码这些坑 |
| D160 | `schema_migrations` 主键是 `(component_id, version)` | 版本号是组件各自的。共用库时先跑的组件会把后跑的顶掉——真容器实测直接失败 |
| D161 | 共用数据库只警告不阻断 | 本地调试共用一个库确实方便；按组件隔离之后也不会再互相顶掉。但要提醒它违反数据自治 |
| D162 | down 脚本缺失时回退**报错** | 假装回退成功会让迁移记录与真实结构对不上，比报错危险得多 |
| D163 | `down` / `reset` 只面向开发与测试 | 生产环境的结构问题应当用一个新的 up 迁移去修（002 §8.9：不做破坏性操作） |
| D164 | 建库命令写进组件 README，并预设库名 | 006 §9.1 明确 CLI 不建库。既然是人来做，就必须在组件文档里说清楚要建哪个库、执行一次即可 |
| D155 | 建表 SQL 必须是独立的、有版本号的文件，不写在代码里 | 迁移文件是"结构变更"的可评审记录。埋在代码里的 `CREATE TABLE IF NOT EXISTS` 只能从无到有，表达不了加列、改索引 |
| D156 | 迁移与版本记录同事务 | 两者分开就存在"执行成功但没记上"的窗口，重启后会重复执行 |
| D157 | 失败的迁移不记录版本 | 记了下次跳过，数据库停在半吊子状态且再也不会被修复 |
| D158 | 内存实现不再参与迁移 | 迁移是 SQL，只能对着真库跑。内存实现是测试替身，直接给种子数据即可；两边数据漂移会被 PostgreSQL 那组契约测试抓到 |
| D159 | `CREATE DATABASE` 不进组件的 migration | 建库要 `CREATEDB` 权限、且必须先连到另一个库；云数据库上应用账号通常无权 —— 会造成"开发能跑、生产必炸"。库由人建，库名注入 |

### 结欠账（三）：P24 市场组织管理 — ✅ 2026-08-15

**做的时候发现这不是"补三个接口"，而是一个越权漏洞。**

007 §9.5 列的三个端点一直没实现，但**组织的授权链路是通的**：
`users.org_id` 有值、`canRead` 按 `TargetOrganization` 放行 private 组件。
唯一缺的是"怎么成为组织成员"——而当时的答案是**注册时自己填 `orgId`**：

```
POST /api/v1/auth/register  {"username":"outsider","password":"…","orgId":"org-acme"}
→ 该账号立刻能读走 org-acme 的全部 private 组件（详情、Manifest、产物）
```

也就是说：**私有组件的组织级授权形同虚设，任何人自报家门即可**。
缺的那三个端点，正是本该守在这里的门。

**交付：**

| 层 | 内容 |
| --- | --- |
| `model` | `Organization`（orgId / name / ownerId / createdAt）+ 两个审计动作 |
| `repo` | `CreateOrganization` / `GetOrganization` / `ListOrganizations` / `SetUserOrg`；内存与 PostgreSQL 两套实现 + schema 的 `organizations` 表 |
| `service` | `CreateOrganization` / `ListOrganizations` / `AddOrganizationMember`，**并把注册接口的 `orgId` 改为忽略** |
| `handler` | `GET/POST /organizations`、`POST /organizations/{id}/members` |

**验证：** 18 个服务层业务测试 + 8 个 HTTP 层测试；仓储契约新增「组织与成员」一组，
**在真 PostgreSQL 上跑过**（`MARKET_TEST_DATABASE_URL` 指向本机 PG，7 个子用例全过）。
market 模块 **375 个测试**。原有的 `TestPrivateComponentOrgAccess` 正是靠自报建组的，
已改成走 `AddOrganizationMember`——它现在测的是真实链路。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D266 | 注册接口的 `orgId` **忽略**，字段保留 | 直接删字段会让老客户端报 400；忽略它既堵了洞又不破坏兼容。字段注释里写明为什么 |
| D267 | 加成员只有**组织所有者与市场管理员**能做 | 成员关系就是授权本身。放开这道门等于回到"谁都能自称是成员" |
| D268 | 创建者自动入组并成为所有者 | 否则他建完组织自己还进不去，得再给自己加一次 |
| D269 | 一个用户至多属于一个组织；已在别处时报**冲突**，不悄悄挪 | `users.org_id` 是单值（007 §10 的数据模型）。悄悄挪走会让他原组织的私有组件突然读不到 |
| D270 | 重复添加同一个人**幂等** | 运维脚本要能放心重跑 |
| D271 | 普通用户的组织列表只含自己所属的 | 组织名与成员关系本身就是信息，内部平台不该让任何人把所有客户列一遍 |
| D272 | 成员关系记在 `users.org_id`，不另开成员表 | 跟着既有数据模型走。将来要多组织成员制再加join 表，那是一次明确的模型变更，不该顺手做 |

**设计书：** 007 §9.5 补上三个端点的权限说明与两条硬规则、新增 §10.4.1 组织表，→ 1.5.0。

### 结欠账（二）：P19 市场的 K8s 部署清单 — ✅ 2026-08-15

**交付：** `deploy/market/k8s/`，用 **kustomize**（`kubectl apply -k`），不用 Helm。

| 目录 | 内容 |
| --- | --- |
| `base/` | Namespace + Deployment + Service + Ingress + ConfigMap/Secret 生成器。**只有市场本身**，数据库与对象存储指向集群外 |
| `overlays/in-cluster-deps/` | 追加 PostgreSQL 与 RustFS 两个 StatefulSet（各带 PVC），并把地址覆盖成集群内的 Service |

**真集群验证（minikube）：** `kubectl apply -k overlays/in-cluster-deps` →
三个 Pod 全部 `1/1` → `port-forward` 打到 `/api/v1/health` 返回 ok →
**用 admin 登录拿到了 token**（说明建表、建管理员都跑通了）。
随后给命名空间打上 `pod-security.kubernetes.io/enforce=restricted` 并删掉全部 Pod 重建，
**三个 Pod 全部正常起来**——清单本身就是 restricted 兼容的。

**几处是这次真跑才定下来的：**

| 现象 | 处理 |
| --- | --- |
| 首次部署时 market-api 会 CrashLoopBackOff 一两次 | K8s 没有 `depends_on`，市场先于 PostgreSQL 就绪而启动、连不上、退出、被重启，直到 DNS 与端口都好。**这是正常的**，写进 README，否则谁看了都以为坏了 |
| compose 那边要一个 init 容器 chown 数据目录 | K8s 用 `fsGroup`，挂载时就把属主改好了，init 容器整个不需要 |
| 删了 `base/.env` 之后连 `kubectl delete -k` 都跑不了 | 任何 `-k` 操作都要先渲染 kustomization。README 里写明，并给出 `kubectl delete namespace` 的兜底 |

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D260 | 用 kustomize，不用 Helm | `apply -k` 是 kubectl 自带的，不需要额外装东西、不引入 release 状态。这份部署的读者是运维，不是要把市场当产品分发的人。分发场景才需要 Helm，登记为 **P28** |
| D261 | base 只部署市场本身，依赖在集群外 | 与 CLI 侧的规则一致（005 §5.1：基础资源由运维部署）。生产上 PostgreSQL 与对象存储通常是云托管的，备份/主从/升级这些事一个 StatefulSet 替不了 |
| D262 | 口令只放一份，在 `base/.env` | overlay 不再放第二份 `.env`。同一套口令放两处，迟早改漏一处 |
| D263 | ConfigMap / Secret 名字**带内容哈希** | 改了 `.env` 就是一个新名字，Deployment 引用被自动改写，Pod 因此**自动滚动重启**。不带哈希的话改完口令还得记得 `rollout restart`，很容易漏 |
| D264 | `market-api` 默认 1 个副本 | 建表在启动时幂等执行，多副本首次启动会并发建表。README 说明先起一个、建好表再 `scale` |
| D265 | 清单里**不写 `${VAR}`** | kubectl 不做变量替换（这条教训这个 session 已经踩过三次）。口令一律走 kustomize 的 `secretGenerator` |

**文档：** 新增 `deploy/market/k8s/README.md`；《市场部署与运维指南》新增 §2.4 指向它；
《部署模式》里 `k8s` 那行从 ⬜ 改为 ✅。
