### 试用指南 15 / 16：K8s 完整装配 + 开发自己的组件 — ✅ 2026-08-15

照旧是**先真跑、再写文档**。这次在 K8s 上又抓到一个只有换编排才暴露的 bug。

**15-K8s完整装配**：同一套八个组件搬到 minikube。改一个字段
（`deploy.target: k8s`），其余是**部署形态**的差异：基础资源改由运维部署、
`exposePort` 换成 `hostname` + Ingress、`${VAR}` 必须在生成时求值、
迁移变成 Job。真跑通了完整业务流（Ingress → 登录 → 查订单 → 审批 → 事件）。

**16-开发自己的组件**：从零写了一个 `notify/webhook`，真装进项目跑通，
`keepMessages: 3` 的 config 覆盖也真生效了。组件已放进
`试用指南/示例组件/notify/webhook/`，可以直接拷出来改。

**这一段抓到的两个问题：**

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **nginx 的 `resolver` 不走 DNS search 域，K8s 里裸服务名解析不了** | 门户返回 502 而后端好好的，日志是 `erp-backend-1-0-0 could not be resolved (2: Server failure)`。K8s 靠 search 域让裸服务名可解析，而 nginx 的 resolver 只拿 nameserver 地址。**别的组件都没事**（Go/Python 的 DNS 解析走 search 域），只有 nginx 特殊 |
| 2 | **`minikube image load` 不覆盖同名 tag** | 改完组件重新 build 再 load，集群里跑的还是旧的——它从 `~/.minikube/cache/images/` 加载，而那份缓存没更新。查了半小时，最后靠比对 image ID 才确认。可靠办法是走 tar：`docker save` → `minikube image load <tar>` |

问题 1 修在**组件里**而不是平台里：裸服务名对其余所有组件都是对的，
只有 nginx 的 resolver 绕开了 search——那是 nginx 特有的行为。
`portal/user-frontend` 加了个入口钩子，从 `/etc/resolv.conf` 找带 `.svc.` 的
search 域，找到就把后端地址补成 FQDN。只在看到 `.svc.` 时才动手：
Docker 环境下容器也可能有 search 域（网络名），拼上去反而解析不了。

配了 3 条测试，其中一条**直接 source 这个脚本**验三种输入
（K8s 补 FQDN / Docker 原样不动 / 已经是 FQDN 不动）——
光断言源码里有没有某个字符串是不够的，这条逻辑有分支，
而分支写反的表现是"Docker 好好的、K8s 502"，或者反过来。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D375 | nginx 的 FQDN 问题修在**组件**里，不修在平台注入侧 | 裸服务名对其余所有组件都是对的，它们的 DNS 解析都走 search 域。只有 nginx 的 resolver 绕开了 search，这是 nginx 特有的行为，该由用 nginx 的组件自己处理 |
| D376 | 只在 search 域里看到 `.svc.` 时才补 FQDN | Docker 环境下容器也可能有 search 域（网络名），无条件拼上去反而解析不了。`.svc.` 是 K8s 的通用标志（集群域可自定义，但这一段固定） |
| D377 | 钩子文件名必须以 `.envsh` 结尾 | 官方 nginx 入口对 `.envsh` 是 **source**、对 `.sh` 是执行。执行的话改过的变量留在子 shell 里，后面负责替换模板的脚本根本看不到——改了等于没改 |
| D378 | 示例组件放进仓库（`试用指南/示例组件/`） | 指南里只贴片段，读者照着敲容易漏东西。给一份能直接 `cp -r` 跑起来的，比十段代码片段有用 |

### 结欠账：P32 / P33 / P34 全部关闭 — ✅ 2026-08-15

首次真实装配抓到的三个问题，当场全修了，每条都配了测试。

**P33：未知字段被静默忽略 → 逐层比对 + 猜字段**

新增 `internal/config/unknown.go`：沿 YAML 节点与 Go 类型同时下行，
逐层比对键名。没有直接用 yaml 的 `KnownFields(true)`——它只会说
`field user not found in type config.Resource`：没有行号、没有中文、
更不会告诉你**想写的大概是哪个字段**。现在报的是：

```
resources[0].user：未知字段（第 51 行），是不是想写 username？
```

猜字段用两条规则，**前缀优先**：`user → username`（少打了后半截，最常见）、
`usrname → username`（打字打错）。前缀单列一条是因为编辑距离对它无能为力——
`user` 与 `username` 差 4 个字符，按距离早被筛掉，而它恰恰是真踩到的那一个。

`component.config` 底下不查：那里的键由**组件的 configSchema** 决定，
平台无从判断对错，在那儿报"未知字段"会把每一个正常的配置覆盖都拦下来。

**这条检查立刻发现了另一个问题：** 我在 12 节里给 brickkit.yaml 写了
`apiVersion: brickkit/v1`——而 003 §2 根本没有这个字段（它属于组件 Manifest），
`brickkit init` 也不生成。检查是对的，错的是我。已改。

**P34：宿主机上的资源 → 自动加 extra_hosts**

`host: host.docker.internal` 是完全合理的写法（"连宿主机上那个已经跑着的库"），
但它带点，不会被判成服务名，CLI 不托管它；而容器里默认解析不了这个名字，
迁移容器直接报 `dial tcp: lookup host.docker.internal ... no such host`——
症状与原因完全不搭。现在为**绑定了它的**组件（含迁移容器）自动加上映射。

只给绑定了的组件加，不无差别地全加：后者也能"跑通"，但会让生成的文件
说不清"这个容器到底要连宿主机上的什么"。

**P32：Go 组件在运行时暴露 `/openapi.json`**

四个 Go 组件各加一个端点，`go:embed` 把 `openapi.json` 打进二进制。
产物是**发布那一刻**的快照，而 `infra/api-docs` 要回答的是"**此刻跑着的**
服务长什么样"——组件升级之后，只有运行时这一份是准的。

真跑验证：文档中心从"2 个 openapi、2 个 grpc、2 个 no-docs"变成
**六个组件全部 `ok`**，其中 department/tree 与 authorization/rbac
同时提供 `openapi+grpc`。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D367 | 自己走一遍字段比对，不用 `KnownFields(true)` | 那个只给一句英文的类型错误。这个项目通篇的立场是"错误信息要能让人直接动手改"，一句 `field user not found in type config.Resource` 达不到 |
| D368 | 猜字段时**前缀优先**于编辑距离 | `user` 与 `username` 的编辑距离是 4，按距离早被筛掉——而"少打了后半截"恰恰是最常见的写法，也是真踩到的那一个 |
| D369 | 前缀猜测要求至少 3 个字符 | 一两个字母的前缀能命中一大片，挑出来的多半不是使用者想要的 |
| D370 | `component.config` 底下不查未知字段 | 那里的键由组件的 configSchema 决定，平台无从判断。在那儿报错会把每一个正常的配置覆盖都拦下来 |
| D371 | `extra_hosts` 只给**绑定了该资源**的组件加 | 无差别全加也能跑通，但会让生成的文件说不清"这个容器要连宿主机上的什么" |
| D372 | 迁移容器同样要加 `extra_hosts` | 迁移是**第一个**连库的东西。主容器有、迁移容器没有的话，迁移先失败，平台会把它当成"迁移失败"阻断整个启动 |
| D373 | 组件在运行时也暴露 `/openapi.json`，与市场产物并存 | 产物是发布那一刻的快照，运行时那一份才回答"此刻跑着的是什么"。两者用途不同，不是重复 |
| D374 | 用 `go:embed` 而不是 `COPY` 进镜像 | 编译期就绑定，不可能出现"镜像里漏了这个文件"。配了测试断言嵌进去的内容是合法 JSON |

**最终跑通的样子：** `brickkit add portal/user-frontend@1.0.0` 一条命令递归拉出

**抓到的三个问题：**

| # | 问题 | 性质 |
| --- | --- | --- |
| 1 | **`auth/password-login` 在真实项目里压根起不来**：它要 `JWT_SECRET`，但 brickkit.yaml **没有组件级的 env / secrets 机制**——唯一能给组件传值的通道是 `config`（映射 configSchema），而它没声明 `jwtSecret`。单元测试全绿，因为测试自己 set 环境变量 | **组件缺陷**，已修 |
| 2 | 我把资源字段写成 `user:`（正确是 `username:`），CLI **静默忽略**了这个未知字段。结果是每个组件启动时报"缺少 DATABASE_USER（由平台按资源绑定注入）"——把配置笔误指向了平台 | **平台可用性缺陷**，登记 **P33** |
| 3 | 资源 `host` 写成 `host.docker.internal` 时不会被 CLI 托管（只有服务名才托管，006 §10.4），而生成的 compose 也不加 `extra_hosts`，于是容器里解析不了这个名字 | 设计如此，但**文档没说清**，登记 **P34** |

有默认值就意味着所有装了这个组件的人共用同一把钥匙，任何人都能给任何一处部署
签出管理员令牌。没有默认值时平台不注入（003 §5.4），组件启动即失败并说明该配什么。
使用者用 `jwtSecret: ${JWT_SECRET}` 从 `.env` 引用（006 §3）。
已补 `TestComponentYamlDeclaresJWTSecret` 锁住这两点。

**顺带验证的几件事（都是真跑）：**

| 验证 | 结果 |
| --- | --- |
| 递归依赖解析 | `add` 一条命令拉出 7 个组件，弱依赖也标出来了 |

| 建库不代劳 | 平台如实列出四个要建的库并给出 SQL，不自己建（006 §9.5） |

### 结欠账（一）：P23 Podman 真机 + P12 git ref — ✅ 2026-08-15

**P23：Podman 真机验证 —— 抓到一个真 bug，而且是"设计书写错了"那种。**

本机已装 Podman 5.7.0（L1 的前提变了）。真跑之后发现 **13.14 这条验证项本身是错的**：

```
$ podman run --rm --add-host=x:host.containers.internal alpine getent hosts x
Error: invalid IP address in add-host: "host.containers.internal"

$ podman run --rm --add-host=x:host-gateway alpine getent hosts x
169.254.1.2       x                                              ✅
```

`host.containers.internal` 是 Podman **自动注入到容器 /etc/hosts 的主机名**
（确实在，地址就是 169.254.1.2），**不是** `--add-host` 能接受的值。
而 `host-gateway` 这个魔法值 Podman 同样支持。

也就是说：按设计书生成的 compose 文件，`local: true` + Podman 的容器
**根本创建不出来**——整条本地调试链路是断的，而单元测试全绿（它们只对比字符串）。
已改成两种引擎用**同一个值** `host-gateway`，并修正了 005 §4.2/§7.3/§7.5 与
**开发计划 13.14 那条验证项本身**。

**顺带修的第二个真问题：** 引擎检测只认独立的 `podman-compose` 程序，
而很多发行版（含本机）装了 Podman 却不装它。Podman 4.1+ 自带 `podman compose`
子命令——一台 Podman 与 compose 都能用的机器，会被 CLI 判成"没有可用的容器引擎"。
已加入检测顺序并新增 `engine.NewPodmanCompose()`。

**P12：git 安装源支持 `ref`（分支 / tag / commit）。**
设计书先行的前提已具备（003 §6.3 补上字段说明）。实现分两步：
先 `clone --depth 1 --branch <ref>`（分支与 tag 走这条，保持浅 clone），
失败再回落到完整 clone + `checkout`——因为 **`clone --branch` 不认 commit SHA**，
这是 ref 唯一真正的难点。5 个业务测试都用**真 Git 仓库**跑（造了 main/next/tag/SHA 四种情形）。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D256 | Docker 与 Podman 的 `extra_hosts` 用**同一个值** `host-gateway` | 真机实测：Podman 认 `host-gateway`，不认 `host.containers.internal`。设计书原文把"Podman 注入的主机名"和"add-host 能接受的值"搞混了 |
| D257 | 引擎检测加入 `podman compose` 子命令，排在 `podman-compose` 之后 | 独立的 podman-compose 更成熟、优先用；但没装它的机器不该被判成"没有容器引擎" |
| D258 | `ref` 先浅 clone 再回落完整 clone，不一上来就完整 clone | 绝大多数人写的是分支或 tag，让常见情况保持最快 |
| D259 | 生产环境建议 `ref` 钉 tag 或 commit（写进 003 §6.3） | 默认分支会动，同一份 brickkit.yaml 在不同时间装出不同组件，正是版本化要避免的事 |

**未做（明确记录）：** `podman compose` 的**端到端** up 在本机跑不通——
Podman 的 docker 兼容 API 对本机这个版本的 docker CLI（29.7.1 / compose v5.3.1）
返回**空镜像列表**，compose 于是每次都去 pull。这是环境不兼容，不是 CLI 的问题；
`extra_hosts` 这条（P23 的实质）已用 `podman run` 直接验过。剩下这一小块登记为 **P27**。

**③ 未登记的缺口：市场的组织管理端点（登记为 P24）。**

**④ 顺带落地：status 改回框线表（此前的 D202 反转）。**

之前判断"框线表在终端里对不齐"而改用缩进。这次做了：关键是**回避宽度不确定的字符**——
`●` `○` `◐` 在 Unicode 里是"东亚宽度：模糊"，同一字符在不同终端下可能占 1 格也可能占 2 格，
任何静态计算都对不齐。把它们移出表格（状态标记留在小节标题的 ✅/❌/⬜ 上）之后，
表格内容只剩"汉字 + 全角括号 + ASCII"，宽度确定，`internal/cli/table.go` 里
40 行的宽度函数就够用了。004 / 011 / 009 的样例按**实际输出**同步。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |

### 设计书复核：把真跑出来的结论回灌文档 — ✅ 2026-08-15

Step 13–15 有若干结论是**真跑才知道**的。这次通读设计书，把仍然与实际不符、
或会主动误导使用者的地方一并改掉。**其中一处是我自己 CLI 输出里的真 bug。**

**① `docker compose` 手写命令全都缺 `-p`（18 处，横跨 4 份文档）。**

compose 默认拿部署文件所在目录名当项目名，而部署文件固定在 `.brickkit/generated/` 下。
15-A 已经让 CLI 显式传 `-p brickkit-<项目名>`，但设计书里那 18 条手写命令没跟着改。
后果分两种，第二种尤其恶劣：

| 命令 | 不带 `-p` 的后果 |
| --- | --- |
| `up` / `down` | 所有 BrickKit 项目在引擎眼里都叫 `generated`，容器互相顶替 |
| **`logs`** | **静默返回空**——不报错、没有输出，让人以为组件根本没打日志 |

`logs` 那条是实测确认的：不带 `-p` 执行返回空，带上就正常。

**而 CLI 自己打印给使用者的命令也漏了 `-p`**（`up` 的"查看日志"、
`status` 与启动失败时的"看日志定位"共三处）——照抄执行同样是空的。
已修并加了三个用例盯住"CLI 打印出去的命令必须真能用"。

**② 健康检查样例与生成器不一致（12 处）。** 15-A 把生成的健康检查改成了
`CMD-SHELL "wget … || curl … || exit 1"`（002 §9.3.1），但 005 / 002 / 004 / 附录
里的样例还是单一 `wget`。照着旧样例手写 compose 的人会在 slim 镜像上翻车。

**③ `status` 输出样例是框线表，实现是缩进对齐（004 / 011 / 009 三处）。**
按实际输出重写，并写明为什么不画框线：表头中文、内容 ASCII，对齐要算东亚字符宽度，
在不同终端下很脆，也与 `up` / `order` 的风格不一致。

**④ `up` 输出样例把迁移写成"CLI 逐条执行并打勾"。** 实际是写成部署文件里的
一次性 service，主服务等它成功退出；CLI 只列"这次会执行哪些迁移"。已按实际重写，
并补写"迁移由谁执行"与"启动完成怎么判定（`--wait`）"两段。

**⑤ 升级判据的措辞。** 原文"版本号与本地缓存的 Manifest 版本不一致"读起来像
"版本号变过没有"，而 CLI 无状态、记不住上次跑的版本。改写为"本地还没有这个版本"，
并说明为什么首次安装与缓存清空自然地不算升级。

**⑥ 补上几条只有实现完才说得清的规则：** `down --only` 用 `rm -sf` 而不是 `down`
（后者会拆掉网络）；`--check-resources` 只探外部资源、排除自家容器、与 `--dry-run`
同用时照样体检；资源可达性按托管 / 外部分流的判据表。

**改动清单：**

| 文档 | 改动 |
| --- | --- |
