### 第二轮全审：静默跳过的三种形态 — ✅ 2026-08-23

上一轮查的是文档一致性与覆盖率数字，这一轮换角度查**逻辑本身与测试的有效性**。
六项，其中三项是自己前几轮引入的回归。

**六项里有四项是同一个病：静默跳过。** 这个仓库反复写过那句话——
"静默通过与真的通过长得一模一样"——而它自己在四个地方犯了。

#### 一、生产存储层 821 行、49 个函数，覆盖率 0%

`market-server/internal/repo/postgres.go` 每一条 SQL 都没被执行过，测试全走内存实现。

设计其实是对的：`repo_test.go` 是**行为契约测试**，同一份断言跑两个实现，
注释写着"两边语义必须完全一致——否则单测全绿、上了真库才出问题"。
问题是 PG 那半边要 `MARKET_TEST_DATABASE_URL` 才跑，而：

```
make test-market             不设那个变量
make test-market-integration 会设，但不在 test-all 里
go test ./internal/repo/     → ok（0.004s）   ← PG 那半边完全隐形
```

`t.Skipf` 不加 `-v` 什么都不打印。处置：`make test-market` 跑完**响亮报告**
PG 那半边跑没跑，并指出 postgres.go 一行都没被执行过、怎么跑真库。
两个分支都验过（设了变量走另一条）。

顺带量出 market-server 整体覆盖率 **75.4%**——这个数字以前从没被量过
（`cover-check` 只量 `internal/`）。

#### 二、"组件有问题"被降级成"组件不存在"（自己引入的）

实测：`components/` 下两个目录，一个 `version: latest`：

```
扫到 1 个组件          ← 坏的那个一声不响消失，连名字都没有
add demo/broken → ❌ 组件未找到，检查安装源配置…   ← 组件就躺在他指定的目录里
```

根因是把"解析不出来 / 版本非法"一律当 `errNotFound` 吞掉。改法：
目录型安装源新增 `manifestUnusable`——**组件在、但 component.yaml 用不了**，
与"这个源没有这个组件"分开；前者交给 `firstRealError` 浮上来，
后者继续找下一个源（坏的源不该挡住好的源，有用例守着）。
`listComponents` 也改成带回问题清单，`LocalComponents` 返回
`LocalScan{Components, Problems}`，`add --local` 逐条点名。

现在：`⚠️ demo/broken 跳过：metadata.version 不是精确版本：latest`。

#### 三、全是版本冲突时最后一句说反了（自己引入的）

⚠️ demo/hello 本地是 2.0.0，配置里是 1.0.0 —— 已跳过

#### 二、签名校验的两条分支从没被测试走到

### 给指南的预期输出加上看守（check-guide-output） — ✅ 2026-08-23

上一条查出"预期输出会悄悄漂移"，但只手工核了 8 个块（全指南有 **73 个**）。
手工核一轮解决不了问题——**没有看守，下次照样漂**。这一条把看守做出来，
并把上一条列出的其余三项一并做完。

#### 为什么已有的 check-guides 不够

它查的是**关键词出现没有**（"输出里必须包含 `弱依赖缺失`"），能证明"这一步跑得通"，
证明不了"指南上抄的那一屏就是它真会打印的那一屏"。💡 那行文案补了后半句
"；如需启用，请确认该组件已发布并可从安装源获取"，关键词检查全绿，指南里还是旧的半句。

#### 比对规则：指南可以少写，不能写得不一样

    指南块的每一行  →  必须与真实输出中的某一行逐字相等（右侧空白忽略）
    行与行之间      →  必须保持顺序
    省略标记        →  单独一行的 `...` 或含「省略」的行，可跳过任意多行

方向单向：真实输出可以比指南多（警告、后续步骤），但指南不能出现 CLI 从没打印过的行。
**截断会被这一条抓住**，而"子串包含"那种松规则抓不住——💡 那行正是被截断的。

只覆盖不需要 Docker / minikube / 市场的步骤（01/02/03/04/08 共 7 个块），
所以能进 `make lint` 天天跑。要环境的篇仍交给 `make check-guides` 分层冒烟。
一个跑不动就会被加 `|| true` 的检查等于没有检查。

### brickkit add --local：一次把本地源里的组件全加进来 — ✅ 2026-08-23

**起因：** 本地开发时 `components/` 下往往躺着一批自己写的、或 `--repo` clone 下来的
组件，一个个 `add` 很烦。

**只给 local 加枚举能力，不动 fetcher 接口。** 照 `signedFetcher`（只有 market 实现）
的先例做了个 `listableFetcher`，只有 local 实现：git 源可能是单组件仓库、也可能是按
`<scope>/<name>` 排布的大目录，形状不固定，枚举出来不可靠；market 有成千上万个组件，
"全都装上"没有意义。

**扫描要挡两道，缺一不可。** 默认约定里 local 源就指向 `./components`，而
`components/.archived/`（sync 的归档目录）和 `.git/` 都在那底下：

| 挡什么 | 怎么挡 |
| --- | --- |
| `.archived/`、`.git/` | 点开头的目录一律不当作 scope。归档的组件不该被 `--local` 拽回来 |
| `People/Basic` 这类目录名 | 用 `manifest.ComponentIDProblem` 兜——非法 ID 进不了 brickkit.yaml，扫出来只会在后面炸 |
| 只有目录没有 `component.yaml` | 那只是个普通目录，不是组件 |
| `metadata.id` 与目录对不上 | 跳过，不猜 |

**两个决定按"批量命令不替人做决定"来。** 同 ID 但版本不同 → 跳过并单独提示，不自动
共存（共存会真的多起一个容器，而批量命令没法逐个问）。任一组件解析失败 → 整体中止、
配置一个字节不动，并在错误最前面点名是哪个组件卡住——本地源里躺着十几个组件时，
光看"强依赖缺失"根本不知道该去改哪一个。

**两条互斥规则。** `--local` 不接组件 ID（说的是两件事）；`--local` 不能与
`--repo` / `--repo-all` 同用——本地组件的源码本来就在盘上，`--repo` 想 clone 到的正是
同一个位置，而 `workspace.Clone` 遇到已存在的目录会直接报错阻断。

**顺带修了两处输出。** 单个安装源时不再逐源报数（"local-dev（2 个）扫到 2 个组件"
是句废话）；解析失败的错误里去掉了底层重复附上的那条"组件：xxx@1.0.0"，
它和新加的"卡在组件"说的是同一件事。

**验证：** source 9 个新用例（枚举、点目录、非法 ID、无 manifest、id 对不上、多源优先级、
非 local 源不参与、空目录、路径不存在）、cli 10 个。真跑五条路径：扫描并添加（`.archived/`
与无 manifest 目录都正确跳过）、重复执行、两条互斥、一个组件坏掉时整体中止（`diff` 确认
配置一个字节没动）。`make lint` 全绿。

**文档：** 004 §3.3（参数表 + 新小节含扫描规则表）、011 §3.1、附录合集 CLI 表、
试用指南 02，以及 `add` 自己的帮助文本。

**决策记录：**

| 编号 | 决策 |
| --- | --- |
| D522 | 枚举能力做成只有 local 实现的可选接口 `listableFetcher`，不加进 fetcher 接口 |
| D523 | `--local` 扫描挡两道：点开头目录 + 合法组件 ID 校验。默认 local 源就指向 ./components，归档目录就在那底下 |

### brickkit add 不写版本时默认装最新版 — ✅ 2026-08-23

**起因：** `add` 原本强制 `<组件ID>@<精确版本>`，少写一个版本号就是 usage 错误。

**先确认这不是在破坏 012 §2.2。** 那条"只接受精确版本、拒绝 `^1.0.0`"约束的是
**配置里写什么**，不是**命令行必须写什么**。省略版本号是在 add 那一刻解析出一个
具体版本、再钉进 `brickkit.yaml`——落到配置里的依然是精确版本。区别在解析时机：
范围约束每次安装都重新解析（同一份配置在不同时间装出不同版本），省略版本号只解析
一次（配置一旦写下就固定）。`add people/basic@^1.0.0` 仍然报错。

**三种源的"最新版"不是一回事：**

| 源 | 怎么算 |
| --- | --- |
| local / git | `manifestBytes` 本来就忽略 version 参数——按 `<scope>/<name>` 找目录、读那份 `component.yaml`。目录里是哪个版本就是哪个版本，"最新"没有别的候选 |
| market | `GET /components/{id}/versions`，先按状态筛掉装不上的，再按版本号取最大 |

**两个坑：**

- **不能用服务端的 `latestVersion` 字段。** 服务端 `ListVersions` 只过滤了 `deleted`
  （以及非 owner 的 `draft`），**`blocked` 的版本还在列表里**，而 `Installable()` 说
  blocked 装不上。直接拿 `Versions[0]` 当默认版本，会稳定解析到一个装不上的版本。
  改成客户端自己按 `stable` / `deprecated` 筛完再比大小。
- **不能跨源比大小。** 按 003 §6.5，第一个有这个组件的源说了算。跨源比会让本地源里
  正在开发的 1.0.0 被市场上的 9.9.9 顶掉，而把本地源排在前面的人要的恰恰是相反的结果。

**同 ID 已装别的版本时先问一句。** 显式写版本号是"我知道我在搞多版本共存"，不写版本号
的人多半没这个预期，而共存会真的多起一个容器。`--yes` 时不问。解析结果恰好就是已装的
那个版本时，走原本的"已存在，是否刷新缓存"分支。

**顺带收敛了一处重复：** 选最新版要比较版本，而 `compareVersions`（按数字比，
避免 `10.0.0 < 2.0.0` 的字符串陷阱）原本是 resolver 的私有函数。提到 `manifest` 包
导出为 `CompareVersions`，与 `IsExactVersion` 放一起，只留一份。

**一处顺序调整：** client 原本建在备份之后，且 `Refresh` 取决于"该版本是否已在配置里"。
不写版本时要先靠 client 解析版本，才知道版本、才知道要不要刷新。把 client 提到备份之前，
并给它加了 `SetRefresh`——为查一次版本再建一个 client 不划算，git 源会重新 clone 整个仓库。

**验证：** source 8 个新用例（三种源各自的最新版、blocked/draft 被跳过、deprecated 保留、
源优先级、逐源回落、全都没有、没有安装源）、cli 8 个、manifest 1 个。另有 1 个锁旧行为的
用例（`TestAddRequiresExactVersion`）改写成锁新契约。真跑四条路径：不带版本装上、
重复 add、`^1.0.0` 仍拒绝、组件不存在的报错。`make lint` 全绿，覆盖率 92.9%。

**文档：** 004 §3.3、011 §3.1、012 §2.2、附录合集 CLI 表、试用指南 02，以及 `add` 命令
自己的帮助文本。

**决策记录：**

| 编号 | 决策 |
| --- | --- |
| D518 | `add` 允许省略版本号：在 add 那一刻解析成精确版本钉进配置。约束的是配置里写什么，不是命令行必须写什么 |
| D519 | 最新版由客户端按状态筛选后自行比较，不用服务端 `latestVersion` 字段——那个字段里还留着装不上的 blocked 版本 |

### 覆盖率"退化"是假的：-coverpkg 撞上测试结果缓存 — ✅ 2026-08-23

**症状：** 改完 remove 之后跑 `make cover-check`，报 90.1% < 92%。
`git stash` 掉全部改动再跑，90.3%——看起来"改之前就是红的"，
于是一度当成 08-19 之后某处掉下去的历史欠账报了出去。**这个判断是错的。**

**真相：** 干净树连跑 12 次（含 `-count=1`、含清 testcache）全部稳定 **93.0%**，
与 08-19 记录的数字分毫不差。**从来没退化过。**

**根因：** `-coverpkg=./internal/...` 让**每个**测试二进制都带上全部 internal/ 包的
插桩块。改了 `workspace.go` 之后，那些不依赖它、因而从**测试结果缓存**里回放的包，
交回来的仍是**按旧代码切分的块**。同一个文件于是在 profile 里出现两套块边界：

```
workspace.go:76.70,78.2     ← 新 RemoveSource（一条 return）
workspace.go:76.70,77.29    ← 旧 RemoveSource（if !Exists ...）
workspace.go:77.29,79.3     ↲
```

实测坏 profile 里 `workspace.go` 有 **69 组**块边界，正常只有 **40 组**。
`go tool cover` 合并不了两套，只能都算进分母——旧那套一律 0，
总数凭空掉 2~3 个百分点。

**为什么骗过了人：** 它不报错、不报警，只是给出一个略低的数字，
**长得和"覆盖率退化"一模一样**。识别特征是**单语句函数出现不可能的百分比**：
`RemoveSource` 函数体只有一条 `return`，却显示 38.5%。看见这种数就该知道量错了，
而不是去补测试。

**修法：** `COVERPKG` 加上 `-count=1`。量覆盖率不能用测试结果缓存。

**验证：** 造出"缓存=旧代码、磁盘=新代码"的状态，同一时刻两种量法各跑一次——
旧量法失败，新量法 93.0% 通过。`make lint` 全绿。

**决策记录：**

| 编号 | 决策 |
| --- | --- |
| D517 | 覆盖率测量强制 `-count=1`：`-coverpkg` 跨包插桩 + 测试结果缓存 = 同一文件两套块边界，量出来的数会偏低且看起来像退化 |

### remove 补漏：归档目录里的孤儿源码 — ✅ 2026-08-23

**问题：** `brickkit remove` 只删活跃源码目录，完全不碰 `components/.archived/`。
而 `brickkit sync` 的 `planSync` **只整理 `brickkit.yaml` 里还声明着的组件**。
两条规则一撞，就有了一个谁也回收不了的目录：

```
brickkit sync              → components/demo/hello/ 搬进 components/.archived/demo/hello/
brickkit remove demo/hello → 配置删了、缓存清了，活跃目录不存在 → 源码原封不动留着
brickkit sync              → 配置里已经没有 demo/hello，sync 不认识它，永远不再整理
```

设计书 004 §3.4 第 6 条只写了"删除 `components/<scope>/<name>/`"，
012 §2.20 讲了半天"避免僵尸目录"，却恰恰漏掉了**最难被发现的那种**——
归档目录以 `.` 开头，文件管理器默认隐藏，组件一多全是坟头。

**修法：** `workspace.RemoveArchived` 与 `RemoveSource` 对称，remove 两处都清
（同 ID 还有别的版本时两处都保留，与原有规则一致）。顺带把 `RemoveSource` 与
`Archive` / `Activate` 收敛到同一个 `srcLoc{root, path, display}`：
`pruneEmptyScope` 现在靠 `root` 判断"父目录就是根目录"，
不再靠 `strings.Cut(id, "/")` 猜——`move` 那条路径原先根本没有这道防护，
组件 ID 不含 scope 时会去 `os.Remove(components/)`。

**验证：** `internal/cli` 3 个新用例（只归档 / 活跃+归档并存 / 多版本保留）、
`internal/workspace` 4 个新用例（含 `RemoveArchived` 不碰活跃源码、
两个根目录都不会被 prune 掉）。`go build ./... && go vet ./... && go test ./...` 全绿。

#### 写这个脚本时，它自己抓出了两个自己的 bug

| bug | 症状 | 根因 |
| --- | --- | --- |
| `init` 那条验的不是 init | 报 `PROJECT_EXISTS` | 脚本先 init 建好项目，清单第一条又 init 一次——**它验的成了"重复 init 会报错"**，与自称验的东西不是一回事 |

### P40：产物下载并发 — ✅ 2026-08-18 · **延后清单清空**

**这一条最值得记的是：我当初"暂不做"的理由是错的。**

Step 36 发现 `downloadArtifacts` 串行时，我把它与刚修好的 `checkImages` 做了对比，
判成**带宽受限**——"并发只是把同一条管道切成几份，收益小得多"——据此登记为延后。

**那是没有量就下的判断。** P40 的第一步本该是量，而我直接给了结论。

#### 量完之后

| 量的是什么 | 实测 |
| --- | --- |
| 本项目 11 个产物文件的大小 | **443 B – 6.5 KB**（全部实测） |
| 一次远程往返的等待 | 30–350 ms |
| 6.5 KB 的传输时间 | ~0.3 ms（实测带宽 ~170 Mbit/s） |

**延迟主导 100–1000 倍**，和 `CheckImage` 完全同一形状。

错在哪很清楚：产物是 **proto、openapi.json 这类契约文件**，本来就该是小的——
组件规范里它们的用途是"让调用方生成客户端"，不是分发二进制。
是"下载"这个词让我先入为主想成了大文件传输。

#### 实现

并发在**组件**这一层，上限 8（与镜像预检同源：请求打到的多半是同一个市场，
无上限只会撞限流）。选组件层而不是文件层：一个组件通常只声明 1–2 个产物文件
（本项目 8 个组件全都是），而组件数会到几十——组件层拿到的是接近组件数的倍数。

结果按**依赖图顺序**汇总而不是完成顺序。并发的完成顺序每次都不一样，
直接按完成顺序追加的话，同一次 `add` 连跑两次会输出顺序不同的警告，
使用者会以为发生了不同的事情，而 diff 两次输出也看不出真正的差别。

#### 真跑

起真市场、发布 8 个各带一个 5.8 KB 产物的组件，再让一个根组件依赖其余 7 个，
这样**单次 `add` 就会拉全部 8 份产物**（否则每次 add 是独立进程，根本走不到并发路径）。

| | 8 个组件，各 5 次平均 |
| --- | --- |
| 串行 | 0.062 秒 |
| 并发 8 | **0.041 秒** |

1.5 倍，而这还是 RTT≈0.1ms 的**本机**市场。真实市场是远程的，收益随 RTT 增长。

#### 丢弃了一个自己搭的测量模型

为了模拟远程 RTT，我写了个延迟代理挡在市场前面。它给出的结论是**并发更慢**
（0.244 → 0.355 秒），与直连结果相反。

追查后发现它的数字**自相矛盾**：经一个"每请求 +150ms"的代理、走 16 次请求，
串行却只用 0.219 秒——算术上不可能。说明它没在量我以为的东西。

**没有报告这组数字，也没有拿它下任何结论。** 一个自己都解释不了的测量，
比没有测量更危险——它看起来是证据。最终结论只用了直连真市场那组
干净、可复现、5 次平均的 A/B。

（中途还撞到三次"快得可疑"：8 次 `add` 用 0.108 秒——每次 add 是独立进程，
根本没走并发路径；串行 0.012 秒——组件已在配置里，`add` 转成了交互式提示等输入；
发布 0/8 —— `sed` 正则没匹配上，产物类型压根没改。每一次都是靠"这个数字不合常理"
才回头查的。）

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D470 | 推翻 Step 36 的判断，产物下载并发化 | 产物是契约文件（443 B – 6.5 KB），延迟主导 100–1000 倍。当初判成"带宽受限"是没量就下的结论 |
| D471 | 并发在**组件**层而非文件层 | 一个组件通常只有 1–2 个产物文件，组件数却有几十；文件层只有 2 倍，还要为两层各设一个上限 |
| D472 | 结果按依赖图顺序汇总，不按完成顺序 | 并发的完成顺序每次都不一样，同一次 add 连跑两次不该给出顺序不同的警告 |
| D473 | 丢弃自建的延迟代理测量，不用它下结论 | 它的数字自相矛盾（16 次 +150ms 的请求只用 0.219 秒）。解释不了的测量比没有测量更危险，因为它看起来是证据 |

### P35：多副本与 PodDisruptionBudget — ✅ 2026-08-18

**P35 不能单做。** 它是"生成 PDB"，而单副本下 PDB 无论怎么写都是死路——
这是当初在 calico 集群上真跑确认、并写进测试注释的结论。所以实际范围是两半：
**先让 `replicas` 可配（005 §5.8），再据此生成 PDB**。那条旧测试自己就写着
「replicas 一旦可配，就该回头重新考虑 PDB」。

#### 前置：`replicas`

仅 K8s 生效，默认 1。默认必须是 1——加个字段不该让任何既有项目的副本数发生变化，
那是没人会在升级 CLI 时预期收到的改动。

| 校验 | 理由 |
| --- | --- |
| 必须 >= 1，写 0 时指向 `enabled: false` | 两者不是一回事：`enabled: false` 走级联、会提醒依赖方；`replicas: 0` 绕过这一切——依赖方照常启动、照常拿到地址，然后连一个不存在的后端，表现是 503 而状态表里那个组件显示"正常" |
| 与 `local` 互斥 | local 是"在你的 IDE 里跑"，那里只有一个进程 |
| 与 `external` 互斥 | 副本数由部署它的那个项目决定（P39 同款理由） |
| Docker 目标下警告 | 那里完全不生效，而 `up` 一切正常、`docker ps` 里只有一个容器，使用者会以为是自己写错了字段名——字段名是对的 |

#### 本体：PDB 只在多副本时生成

**用 `maxUnavailable: 1` 而不是 `minAvailable`。** 固定副本数下两者等价
（replicas=3 时 minAvailable:2 == maxUnavailable:1），但 maxUnavailable
**随副本数自动成立**：把 3 改成 5 时不用回来改 PDB。写死 minAvailable: N-1 的话，
改副本数就会悄悄改变容错度，且没有任何提示。

取 1 而不是百分比是**安全的那一边**：副本很多时排空会慢一些，
但慢从来不会变成故障，而一次多驱逐几个会。

#### 真跑：两个方向都验到了

minikube 上部署 3 副本：

```
NAME               MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS
demo-hello-1-0-0   N/A             1                 1
```

`ALLOWED DISRUPTIONS: 1` —— 正是当初单副本下恒为 0 的那一栏。

连续驱逐两个 Pod（不给补齐的时间）：

| | 结果 |
| --- | --- |
| 第一个 | `{"status":"Success","code":201}` |
| 第二个 | `TooManyRequests: Cannot evict pod as it would violate the pod's disruption budget` |

**放行一个、拦住第二个**，这才是 PDB 该有的行为。而单副本时那条报错会出现在
**第一个**上，让 drain 永远超时。

> 中间走过一次弯路：第一次只驱逐一个就下结论，第二次驱逐也成功了——
> 因为副本已经补齐、ALLOWED DISRUPTIONS 回到 1。**只验到"能驱逐"等于没验**，
> 必须连续驱逐才看得到"拦"那一半。

#### 真跑抓到一个此前一直潜伏的清理 bug

把 `poddisruptionbudget` 加进 `pruneKinds` 之后，minikube 上实测**它照样没被删**。

根因是孤儿判定**只比对名字、不看类型**：`kubectl get -o name` 返回
`poddisruptionbudget.policy/demo-hello-1-0-0` 与
`deployment.apps/demo-hello-1-0-0`，两者名字相同，而这个名字在"本次期望"集合里
（Deployment 要留），于是 PDB 也被当成该留的。

**在 PDB 之前这个近似一直是对的**：deployment / service / networkpolicy /
serviceaccount 每个跑着的组件都必然有一份，"名字还在期望集合里"就等于
"这份资源还该在"。**PDB 是第一个条件生成的资源**（只有多副本才有），
它把这个前提打破了。

漏掉的后果**单向不可逆**：一份 `maxUnavailable: 1` 的 PDB 永远留在单副本组件上，
让节点从此排不空——正是 P35 当初决定不生成 PDB 的那个理由，换了个更隐蔽的入口。

修法是让生成侧明确点名本次期望哪些 PDB（`UpRequest.DesiredPDBs`），
条件生成的类型按这份名单判，其余类型仍按名字判。真跑复验：

```
🧹 已清理旧版本残留（1 项）
PDB → No resources found
Deployment → 1/1 还在      ← 同名，修错方向就会把正在服务的它一起删掉
```

#### 顺带修正一段过期的说明

旧测试 `TestNoPodDisruptionBudgetGenerated` 的注释写着"PDB 要等多副本落地之后
再说"。前提已经变了，注释也跟着改了——**留着一段过期的理由比没有更误导人**。
那条测试保留下来守另一半：**副本数是 1 时坚决不生成**。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D465 | P35 连同多副本一起做，不单做 | 单副本下 PDB 必然有害，分开做只会得到一个确定错误的 PDB |
| D466 | `replicas` 默认 1，且仅 K8s 生效 | 默认值一变，升级 CLI 就会静默改变既有项目的副本数；Docker 下它不起作用，不提醒会让人以为自己写错了字段名 |
| D467 | `replicas: 0` 报错并指向 `enabled: false` | 用它关组件会绕过级联计算：依赖方照常启动并连一个不存在的后端 |
| D468 | PDB 用 `maxUnavailable: 1` 而非 `minAvailable` | 前者随副本数自动成立，后者改副本数就会悄悄改变容错度 |
| D469 | 孤儿判定对**条件生成**的类型按显式名单判 | PDB 与 Deployment 同名，只按名字判会让它永远留在集群里拦 drain——minikube 上真跑到过 |

### P39：引用别的项目部署的组件（`external:`） — ✅ 2026-08-16

**结论：做了，Docker 与 K8s 两侧都真跑验证。** 组件条目新增一个字段：

```yaml
components:
  - id: infra/notifier
    version: 1.0.0
    external:
      project: platform-shared
```

平台**照常做**：进依赖图、版本兼容检查、下载 artifacts、把地址注入给依赖方。
平台**不做**：生成它的部署对象、执行它的迁移、检查它的镜像、`down` 时碰它。

#### 两种目标的难点完全不同

到这一步为止，注入**从不区分部署目标**——因为同一个组件在两边服务名一模一样。
external 打破了这个巧合：被引用的组件在**另一个项目**里。

| 目标 | 难在哪 | 做法 |
| --- | --- | --- |
| K8s | 裸服务名只在**本命名空间**解析 | 地址加后缀 `<服务名>.<对方命名空间>` |
| Docker | 服务名只在**同一张网络**里解析 | 把**依赖它的**服务接进对方项目的网络 |

**K8s 侧真正危险的不是加后缀，而是不能生成同名 Service。** 本命名空间里的
同名 Service 会**抢在**跨命名空间解析之前命中，而它背后一个 Pod 都没有——
表现是稳定的 503，且从依赖方看一切正常：地址对、DNS 通、Service 也确实存在。

**Docker 侧只接依赖方，不是全部接进去。** 网络是可达性边界，
全接进去等于把"谁能访问共享服务"从**按依赖声明**变成**默认全通**——
那正是 NetworkPolicy 在 K8s 侧要防的东西，没理由在 Docker 侧自己先破坏掉。

#### 互斥校验拦下的都是"写了不报错也不生效"

这类组合最难查：改了配置、命令成功了、行为没变，于是开始怀疑平台。

| 字段 | 为什么不能同时写 |
| --- | --- |
| `local` | 含义相反：一个说在本机调试，一个说在别的项目里跑 |
| `expose` | 它的入口该由部署它的那个项目决定；硬生成会得到指向不存在 Service 的 Ingress |
| `config` | 它读的是**对方项目**那份配置，写在这里不生效——而看上去像生效了 |
| `resources` | 配额由部署它的那个项目决定 |
| `project` 指向本项目 | 等于说"我不部署它，但它由我部署" |

#### 真跑抓到一个单元测试全绿也发现不了的 bug

三层（config / compose / k8s / inject）单元测试全绿之后真跑两个项目，
消费方 `up` **当场失败**：

```
no such service: demo-hello-1-0-0
```

原因是**命令层另有一份"这次要启动哪些服务"的名单**，它按依赖图算、不看生成物，
于是把一个根本没生成的服务名传给了 docker。

教训不在于漏了一处，而在于**"不生成它"这件事分散在四层**：
生成层不写、命令层不点名、预检层不查镜像、引擎层不清理。
这次是当场报错（还算幸运），漏在别处可能是"启动成功但没连上"那种要几周才发现的。

| 新增配置项 | ❌ 没有 |
| 删除配置项 | ❌ 没有 |
| 数据库迁移 | ✅ 有 |
| artifacts 变更 | ❌ 没有 |
| 资源配额变更 | ❌ 没有 |

缺的偏偏是「升级到底会改变什么」这个问题本身。使用者按下 `--dry-run`
就是想在真动手之前知道这个；只告诉他"有迁移"，等于让他自己去 diff
两份 Manifest——**而他多半不知道旧的那份就在 `.brickkit/manifests/` 里**。

现在的真实输出：

```
📋 升级变更摘要：
   people/basic: 1.0.0 → 1.1.0
   ├── 依赖变更：新增 department/tree@1.0.0
   ├── 新增配置项：enableNotification（默认 true）
   ├── 删除配置项：legacyMode
   ├── 数据库迁移：python manage.py migrate
   ├── artifacts 变更：新增 client.ts
   ├── 资源配额变更：limits cpu 500m/内存 256Mi → limits cpu 2/内存 1Gi
   └── 旧版本产物：保留（调用方可能仍指向旧版本）
```

**几处刻意的取舍：**

| 取舍 | 理由 |
| --- | --- |
| 旧 Manifest 读不到时报**「未知」**，绝不报「无」 | 缓存可能被清过、文件可能坏了。报"无变化"是一句**看起来完全正常的假话**，使用者会据此认为可以放心升级 |
| 六项**固定都出**，没变化写"无" | 藏起来会让人分不清"没有变化"和"平台没检查这一方面" |
| 新增配置项**带默认值** | 新增项走的就是默认值（38.13）。使用者要判断这个值对不对，而不只是知道"多了一项" |
| 删除配置项要报 | 删掉的项若 brickkit.yaml 里还写着覆盖，那个覆盖会被**静默忽略**（38.14，有意如此）。不提醒的话使用者会以为自己的配置仍然生效 |
| 资源配额给出**新旧两个值** | 配额变了可能导致节点资源不够而起不来，是少数几个"升级失败但与组件代码无关"的原因。只说"变了"的话使用者还得自己翻 Manifest |
| 配置项名**排序**后输出 | map 遍历顺序随机，不排序的话同一次升级两次运行的输出会不一样 |
| 资源依赖也算进"依赖变更" | 新版本开始要一个数据库，影响不比多依赖一个组件小——他得去 brickkit.yaml 里绑定它 |

| 38.26 升级后 status 显示新版本 | 无 |

**立刻通过的测试证明不了它抓得住回归**，所以三条都做了变异检验：

### Step 37：回归测试 — ✅ 2026-08-16

**25 项全部早就有测试覆盖**——项目里有 1599 个测试函数，每条命令都有几十条
（`TestUp*` 103 个、`TestPublish*` 60 个、`TestAdd*` 49 个）。
所以这一步**不该是再写 25 条测试**，那只是把已有的东西抄一遍。

#### 清单缺的不是覆盖，是连接

计划里那 25 项是 **25 个要人手打勾的方框**，`tests/regression/` 里只有 `.gitkeep`，
25 项只勾了 1 项。方框和测试之间没有任何东西，于是有两个坏结果：

- 改完 `up.go`，不知道该重点看哪几条测试
- 某条测试被改名或删掉，**清单还挂着 ☑——清单变成谎话，而且没人会发现**

第二条才是要害。一份不会失效的清单和一份没有清单，危险程度是不一样的：
后者你知道自己没有保障，前者你以为有。

#### 做法：单一事实源 + 守卫 + 执行

| 件 | 作用 |
| --- | --- |
| `tests/regression/清单.tsv` | 唯一事实源：承诺 → 证明它的那个测试（含 module / 包 / 测试名） |
| `tests/regression/regression_test.go` | **守卫**：逐条确认那个测试今天仍然存在且能被跑到 |
| `make test-regression` | 先校验清单没失效，**再**逐条执行 |
| 开发计划.md 的表 | 由 tsv 生成的**投影**，25 项现在都指向具体测试 |

**存在性用 `go test -list` 判，不搜源码。** 搜 `func TestXxx(` 能确认名字在，
确认不了它**能被跑到**——构建标签、包编译不过、名字写在注释里，
这些情况下源码里有那串字符而 `go test` 一条也跑不到。`-list` 走真正的编译与注册。

**R18 在 `market-server/`——那是另一个 Go module**，根模块的 `go test ./...`
到不了它。runner 因此要按 module 切目录。这正是 Step 31 审计报出 4 个假缺口的
同一个坑（语料漏了一整个 module），这次一开始就查了。

#### 四种坏法都真的验过

不是"写完看着对"，是每一种都制造出来跑过一遍：

| 制造的坏法 | 结果 |
| --- | --- |
| 把 R7 指向的测试改个名 | ❌ **R7（brickkit up 基本功能，对应 Step 15）指向的测试…已经不存在了** |
| 从清单里删掉 R13 | ❌ 清单里 R13 出现了 0 次（应当正好 1 次） |
| 加一条计划外的 R26 | ❌ 清单里有计划之外的条目 R26 |
| 让清单里某个测试真的失败 | ❌ make 退出码 2，**成功横幅没有打印** |

守卫自己也有自检（`TestGuardDetectsMissingTest`）：拿一个故意不存在的名字去查，
必须查不到。**如果连它都"找到了"，说明匹配逻辑坏了，那条绿灯就不可信**——
和 check-docs、Step 33 审计脚本是同一个道理。

**过程中差点被自己骗了一次。** 验"真失败时不打印 ✅"时，我 grep 输出里的 ✅
得到 1 处，一度以为横幅照打。查下来那个 ✅ 来自**我自己写在 `t.Fatal` 文案里的
表情符号**。横幅确实没打。检查的关键词出现在被检查的内容里，是这类自查最常见的假阳性。

**未做（明确记录）：** 没有为这 25 项新写测试——它们已有覆盖，
重复写只会多出一批需要同步维护的副本。清单选的是每项最有代表性的
"基本功能"那条，不是边界用例。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D440 | 回归清单不新写测试，只做「承诺 → 已有测试」的映射 | 25 项全都已有覆盖（1599 个测试函数）。再写一遍等于制造需要同步维护的副本，而副本迟早和本体不一致 |

### Step 36：性能基准测试 — ✅ 2026-08-16

**这是 Phase 7 里唯一的真空白**：项目此前**一个 Benchmark 都没有**，
`tests/perf/` 只有一个 `.gitkeep`。性能从来没被测量过。

#### 先决定"怎么测才有意义"

计划里 10 项全是`"< 30 秒"、"< 5 秒"`这类阈值。那是**人跑一次时的验收标准**，
直接写成自动化断言会得到一个两头不讨好的东西：机器快时永远绿（测了等于没测），
CI 负载高时随机红（几次之后所有人开始无视它）。所以拆成两类：

| 类别 | 作用 |
| --- | --- |
| `Benchmark*` | 报告 ns/op、B/op、allocs/op，让**回归可见**，不判定对错 |
| `Test*` | 只守**灾难性回归**，阈值放到秒级——只有算法退化了量级才会触发 |

#### 纯计算层：离成为问题差 3–6 个数量级

| 验证项 | 计划阈值 | 实测 | 余量 |
| --- | --- | --- | --- |
| 36.2 10 层依赖解析 | < 5 秒 | **4 µs** | ~100 万倍 |
| 36.3 100 个依赖解析 | < 5 秒 | **42 µs** | ~12 万倍 |
| 36.5 解析 100 条目配置 | < 1 秒 | **755 µs** | ~1300 倍 |
| 36.6 生成 compose（50） | < 5 秒 | **2.4 ms** | ~2000 倍 |
| 36.7 拓扑排序（50） | < 1 秒 | **20 µs** | ~5 万倍 |

深度 10→100 时耗时 4µs→41µs，正好 10 倍——线性，没有隐藏的重复遍历。

#### 36.10 内存：一次"绿灯但什么也没证明"的测量

最直觉的写法是 GC 前后比 `HeapAlloc`。**测出来是 -0.03 MB，负数。**

原因不是写错了，而是 50 个组件的常驻状态（几百 KB）**比两次 GC 之间的噪声还小**。
那样的测试会永远绿着——它没有量到任何东西，只是恰好小于 100MB。
**量不到信号的测试比没有测试更糟：它让人以为测过了。**

改量 `TotalAlloc`：只增不减、不受 GC 时机影响（连跑三次都是 **2.67 MB**），
而且**累计分配是峰值驻留的上界**——就算一个字节都不回收也不会超过它。
于是"2.67 MB"这句话直接蕴含了"峰值远低于 100MB"，且不依赖 GC 什么时候跑。

#### 真正的发现：唯一不随组件数伸缩的地方

36.1 / 36.4 / 36.8 / 36.9 都是 I/O 主导的，在我这台机器上计时只能测出机器状态。
但**计时测不了不等于没东西可查**——真正决定伸缩性的是
「有没有按组件串行地调外部命令」，这个直接看代码就能判断：

| 路径 | 结构 | 结论 |
| --- | --- | --- |
| `Status` | 一次 `compose ps --format json` 拿回全部 | O(1)，安全 |
| **`checkImages`** | **每个镜像一次串行 registry 往返** | **O(N)，是问题** |
| `downloadArtifacts` | 逐个组件串行下载 | O(N)，但性质不同 → **P40** |

`checkImages` 的后果：本地没有镜像时每次都是一趟 registry 往返，
按健康网络 0.3–0.5 秒算，50 个组件光预检就是 15–25 秒，
而 36.1 给整个 `up` 的预算是 30 秒——**第一个容器还没开始启动**。

**真跑验证（8 个镜像，冷缓存）：**

| | 耗时 |
| --- | --- |
| 串行（原行为） | **50.5 秒**（且只成功 2/8，其余超时） |
| 并发 8（现行为） | **1.6 秒** |

**31 倍。** 按 50 个组件外推，串行约 5 分钟。

#### 测量过程中自己犯的两个错，都靠"数字不合理"抓回来

**① 把 12 秒当成了普遍事实。** 首批测出单次往返 12–15 秒，差点写进结论。
查下来那是 **TLS 握手超时**（CDN 那一段不通），而直连 registry 只要 0.34 秒——
所以 12 秒是这台机器当时的网络病，不能当成一般数字。

**② 批量测出 15 毫秒，差点当成"并发已经很快"。** 实际是
**zsh 默认不对未加引号的变量做分词**，`$IMGS` 被当成一个单词，
循环只跑了一次、拿整串当镜像名，瞬间失败。量的是那个失败。
改成字面列表后才有上面那组真数字。

两次都是"数字好得不合常理"暴露的。**性能测量里最危险的不是慢，是快得可疑。**

#### 实现上的三个取舍

| 取舍 | 理由 |
| --- | --- |
| 并发**有上限**（8） | 请求打到的是同一个 registry，几百个并发只会撞限流，那时不但不快，还会换来一堆 429 让人误以为是凭据出了问题 |
| **不在第一个失败时掐断** | 掐断会丢两样东西：**哪个**错误被报出来变得不确定（同一份配置连跑两次给出不同的错误，使用者会以为问题在飘），以及"还有几个也拉不到"。跑完就能一次说清要修几个 |
| 错误按**输入顺序**取第一个 | 并发天然让"谁先失败"每次都不一样。按下标存结果再按序取，输出才稳定 |

#### 验证

6 条并发测试 + race 检测全过。**RED 是真验过的**：把并发度临时改成 1，
`TestCheckImagesRunsConcurrently` 如实报出 `24 个镜像用了 964ms，串行也就是 960ms`
并指出峰值并发为 1——测试确实抓得住串行，不是编译不过而已。

`fakeEngine.CheckImage` 同时加了锁：预检并发之后，
不加锁真正在 race 的会是**夹具本身**，而不是被测代码。

**未做（明确记录）：** 36.4 产物下载并发 → **P40**（带宽受限，与延迟受限的
`checkImages` 不是一回事，不该照抄同样的修法）。
36.1 / 36.8 / 36.9 的端到端计时不做——耗时由镜像大小、网络、磁盘决定，
测出来的数字说明不了 BrickKit 的性能，只说明当时那台机器的状态；
它们的**结构**已按上表逐条查过。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D435 | 性能测试拆成"报数字的 Benchmark"与"守量级的 Test"，不把计划阈值写成断言 | 阈值当断言两头不讨好：机器快时永远绿，CI 忙时随机红。数字用来看趋势，断言只当保险丝 |
| D436 | 36.10 量 `TotalAlloc` 而不是 `HeapAlloc` 差值 | 差值实测为负——50 个组件的常驻状态比 GC 噪声还小。累计分配稳定可复现，且是峰值驻留的**上界**，宁可高估不会漏报 |
| D437 | `checkImages` 并发化，上限 8 | 整条 up 链路上唯一的 O(N) 网络操作。真跑 50.5 秒 → 1.6 秒。有上限是因为打的是同一个 registry，无上限只会撞限流 |
| D438 | 预检失败时跑完全部再报，且按输入顺序取第一个错误 | 早掐断会让报出的错误随机变化，使用者以为问题在飘；跑完还能一次说清要修几个 |
| D439 | 产物下载不跟着并发化（P40） | 延迟受限与带宽受限不是一回事。并发只是把同一条管道切成几份，收益小得多还会互相抢带宽。要做得先量清楚慢在等待还是慢在传输 |

### Step 34：兼容性测试（Docker） — ✅ 2026-08-16

`host.containers.internal` 是 Podman 自动注入到容器 `/etc/hosts` 的**主机名**，

Docker 与 Podman 都用 `host-gateway`（P23 真跑证实过）。
已在开发计划里改正并注明原因——**留着一句写错的规范比没有规范更危险**，
下一个照着它实现的人会直接生成一份跑不起来的文件。

**② Docker 侧 11 项都已有覆盖**，只有 34.11 是真空白。

**③ `Detect()` 一次都没被测过。** 而它决定了后面的一切——选错引擎的后果是
“文件生成了、命令也成功了，只是整个项目跑在了错误的编排器上”（Step 16 之前真撞到过）。
它现在有三个分支：有 Docker、只有 Podman、两个都没有。

补了 3 条测试。它直接调 `exec.LookPath`、没有注入点，所以**用 PATH 本身做夹具**：
临时目录里放几个假的可执行文件，想让它看见什么就放什么。
这比加一层注入更贴近真实——`LookPath` 的行为（可执行位、PATH 顺序）
也一并被覆盖到了。

其中最要紧的一条是“只有 Podman 时报的必须是「暂不支持 Podman」，
而不是笼统的「没有找到可用的容器引擎」”：两者该做的下一步完全不同，
后者装个 Docker 就好，前者说明问题不在他的机器上。

### 探讨：命名空间、共享组件与升级孤儿 — ⚠️ 2026-08-16

**性质：** 这条不是一个 Step，是一次设计探讨的产物。之所以要登记，
是因为**探讨过程中真跑出了一个缺陷**（P38），而且澄清了两条此前只活在代码里的假设。

**起因：** 讨论"不同命名空间能不能互通、能不能给每个组件指定命名空间"。

**结论一：命名空间不是网络边界。** 跨命名空间访问默认就通
（`http://svc.other-ns:8080`），不需要任何配置。命名空间隔离的是名字作用域、
RBAC、ResourceQuota / LimitRange、PodSecurity 准入标签与 DNS 默认搜索域——
**网络不在其中**，那正是 NetworkPolicy 存在的理由。

**结论二：不做"每个组件指定命名空间"。** 已写进 005 §5.2.1，连同要付的代价。
其中唯一的**硬约束**是 K8s 不支持跨命名空间引用 Secret，密钥要多存几份。
其余动机都有更便宜的解法：团队边界 → 那多半就是两个项目；安全分层 →
那正是 NetworkPolicy 该干的；配额 → 组件级 `resources.limits` 更精确；
**组件多到不好管 → 用标签过滤，别拿命名空间当文件夹**。

**结论三：共享组件不该属于任何一个项目。** 若 `infra/event-bus` 被 A 和 B 共用，
它就有自己的负责人与升级节奏。让它出现在 A 的 brickkit.yaml 里、由 A 负责部署，
本身就是错的——**A 执行一次 `down`，B 就挂了**。正解是共享的那些东西自己是一个
BrickKit 项目，消费方只声明"我连它"（登记为 **P39**）。
共享前先问一句：**它持有权威状态吗？** 不持有就复制两份，故障隔离反而更好。

**自我修正：** 我一度说"external 依赖的版本平台验不了"，这是错的。
服务名**带版本**（`event-bus-1-0-0`），注入的地址因此是版本专属的——
要么连上声明的那一版，要么 DNS 解析不出来当场报错，
**不存在静默连到错版本**这种状态。真正剩下的只是"对面部没部"的可达性问题，
比我原来说的轻得多，而且可以套用 `--check-resources` 现成的探测机制。
多版本共存也确认仍是默认行为（`internal/config/validate.go:139`）。

**真跑抓到的缺陷（P38）：** 顺着"CLI 能不能自己发现版本变了、把旧的删掉"这个问题
去验，在 minikube 上复现了 K8s 升级路径的孤儿泄漏：

| 步骤 | 结果 |
| --- | --- |
| 版本 1.0.0 → 2.0.0 再 `up` | CLI 报"✅ 全部组件已启动（1 个）" |
| `kubectl get deployment` | **两个版本都在跑**，`demo-hello-1-0-0` 没人管了 |
| `brickkit status` | 只报 1 个组件——**孤儿完全不可见** |
| `brickkit down` | 报"✅ 已停止全部组件"，而**旧版本照样在跑** |

根因是两条路不对称：Docker 那边有 `docker compose up --remove-orphans` 兜底
（`internal/engine/compose.go:56`），K8s 这边没有对应机制，
而 `kubectl apply` 默认不删目录里没有的资源。后果是**永久泄漏**——
`down` 也清不掉，只有 kubectl 才找得到。

修法：`up` 之后按 `brickkit.io/project` 标签列出集群实际资源，与本次生成的期望集合
求差，删掉多余的。它顺带解决"把组件从 brickkit.yaml 里删掉"的同一类泄漏。
**关键风险是 `--only`**：那时只部署子集，绝不能把不在本次范围里的组件当成孤儿删掉——
那会变成一条比原 bug 更危险的路。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D391 | 维持"一个项目 = 一个命名空间"，不做组件级命名空间 | 唯一硬约束是 K8s 不支持跨命名空间引用 Secret（密钥要多存几份、轮换要多改几处）；其余动机都有更便宜的解法。命名空间是权限与配额的边界，不是整理工具 |
| D392 | 组件多到不好管时用**标签**分组，不用命名空间 | 代价不在一个量级：标签不影响 Secret、不影响注入地址、不影响 NetworkPolicy、不影响 `down` 的删除判断 |
| D393 | 共享组件走"**外部依赖**"，不走"跨命名空间部署" | 共享的东西有自己的负责人与生命周期，不属于任何消费方项目。由消费方部署的话，消费方一 `down` 就把别人弄挂了 |
| D394 | 共享前先分"有没有权威状态" | 无状态的复制两份更好（故障隔离、独立升级、各自的版本自由）；只有持有权威状态的才**必须**共享，否则语义就错了 |

---

**续（同一次探讨，2026-08-16）：把"共享"想清楚，并真跑验证。**

第二轮把 D394 的二分法（无状态 / 有权威状态）**修正成三分**——原来漏了最常见的一档：

| 形态 | 判据 | 今天能不能做 |
| --- | --- | --- |
| 一：各部各的 | 组件无状态，也不依赖共享数据 | ✅ 默认行为 |
| **二：各部各的组件 + 共享资源** | 组件无状态，**状态在它连的资源里** | ✅ **无需任何新特性** |
| 三：外部依赖 | 组件**本身**就是权威（单例副作用、成本、归属） | ⬜ P39 |

**我举错过一次例子，值得记下来。** 我原先拿 `infra/redis-event-bus`
当"必须共享"的例子，错了——它**自己一行状态都不存**，事件全在 Redis Streams 里，
属于形态二。而 002 的组件规范本来就把组件推向无状态，
所以真正的形态三**比直觉中少得多**。这正是最容易判断错的地方。

**真跑验证（Docker，两个完全独立的项目）：**

| 验证 | 结果 |
| --- | --- |
| team-a / team-b 各跑一份事件总线，`host.docker.internal:6399` 指同一个 Redis | 两边都起来 |
| team-a `POST /api/v1/events` | `{"id":"1786833372153-0"}` |
| team-b `GET /api/v1/events` | **读到了 team-a 发的那条**，`total: 1` |
| team-b 加 `config.streamName: "team-b:events"` 后重来 | `total: 0`，而 team-a 自己的仍是 1 |

最后一行是重点：**共享与隔离的差别就是一个配置字段**。
所以"要不要共享"不是一次性的架构决定，是可以随时改的配置。

**跨目标的自动化问题**（"不同项目在不同命名空间/不同启动方式下怎么统一"）：
形态二**不需要新机制**——三种目标的差别全部落在 `resources[].host` 一个字段上
（Docker/local 走 `host.docker.internal` + 宿主机端口，平台自动补 `extra_hosts`；
K8s 走 `<svc>.<ns>.svc.cluster.local`，命名空间之间本来就可达）。
只有形态三需要新机制，方式是**声明"它是谁"（对方项目名）让平台按目标算"它在哪"**——
K8s 推导命名空间、Docker 推导 compose 网络名，与 `ingressController` 同一条线。

**文档产出：** 005 新增 §5A（多项目与共享，→ 1.15.0）、§5.2.1（一个项目 = 一个命名空间）；
003 §5 加跨项目共享的指路（→ 1.8.0）；试用指南新增
[18-多项目与共享](../../试用指南/19-多项目与共享.md)，全部内容基于上面那次真跑。

**决策记录（续）：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D395 | 共享分**三**种形态，不是两种 | 漏掉的"组件无状态但状态在资源里"恰恰是最常见的一档，而且今天就能做。把它并进"必须共享"会让人去用最贵的方案解决最便宜的问题 |

### 结欠账：P32 / P33 / P34 全部关闭 — ✅ 2026-08-15

首次真实装配抓到的三个问题，当场全修了，每条都配了测试。

**P33：未知字段被静默忽略 → 逐层比对 + 猜字段**

新增 `internal/config/unknown.go`：沿 YAML 节点与 Go 类型同时下行，
逐层比对键名。没有直接用 yaml 的 `KnownFields(true)`——它只会说
`field user not found in type config.Resource`：没有行号、没有中文、
更不会告诉你**想写的大概是哪个字段**。现在报的是：

```
resources[0].user：未知字段（第 51 行），是不是想写 username？
```

猜字段用两条规则，**前缀优先**：`user → username`（少打了后半截，最常见）、
`usrname → username`（打字打错）。前缀单列一条是因为编辑距离对它无能为力——
`user` 与 `username` 差 4 个字符，按距离早被筛掉，而它恰恰是真踩到的那一个。

`component.config` 底下不查：那里的键由**组件的 configSchema** 决定，
平台无从判断对错，在那儿报"未知字段"会把每一个正常的配置覆盖都拦下来。

**这条检查立刻发现了另一个问题：** 我在 12 节里给 brickkit.yaml 写了
`apiVersion: brickkit/v1`——而 003 §2 根本没有这个字段（它属于组件 Manifest），
`brickkit init` 也不生成。检查是对的，错的是我。已改。

**P34：宿主机上的资源 → 自动加 extra_hosts**

`host: host.docker.internal` 是完全合理的写法（"连宿主机上那个已经跑着的库"），
但它带点，不会被判成服务名，CLI 不托管它；而容器里默认解析不了这个名字，
迁移容器直接报 `dial tcp: lookup host.docker.internal ... no such host`——
症状与原因完全不搭。现在为**绑定了它的**组件（含迁移容器）自动加上映射。

只给绑定了的组件加，不无差别地全加：后者也能"跑通"，但会让生成的文件
说不清"这个容器到底要连宿主机上的什么"。

**P32：Go 组件在运行时暴露 `/openapi.json`**

四个 Go 组件各加一个端点，`go:embed` 把 `openapi.json` 打进二进制。
产物是**发布那一刻**的快照，而 `infra/api-docs` 要回答的是"**此刻跑着的**
服务长什么样"——组件升级之后，只有运行时这一份是准的。

真跑验证：文档中心从"2 个 openapi、2 个 grpc、2 个 no-docs"变成
**六个组件全部 `ok`**，其中 department/tree 与 authorization/rbac
同时提供 `openapi+grpc`。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D367 | 自己走一遍字段比对，不用 `KnownFields(true)` | 那个只给一句英文的类型错误。这个项目通篇的立场是"错误信息要能让人直接动手改"，一句 `field user not found in type config.Resource` 达不到 |
| D368 | 猜字段时**前缀优先**于编辑距离 | `user` 与 `username` 的编辑距离是 4，按距离早被筛掉——而"少打了后半截"恰恰是最常见的写法，也是真踩到的那一个 |
| D369 | 前缀猜测要求至少 3 个字符 | 一两个字母的前缀能命中一大片，挑出来的多半不是使用者想要的 |
| D370 | `component.config` 底下不查未知字段 | 那里的键由组件的 configSchema 决定，平台无从判断。在那儿报错会把每一个正常的配置覆盖都拦下来 |
| D371 | `extra_hosts` 只给**绑定了该资源**的组件加 | 无差别全加也能跑通，但会让生成的文件说不清"这个容器要连宿主机上的什么" |
| D372 | 迁移容器同样要加 `extra_hosts` | 迁移是**第一个**连库的东西。主容器有、迁移容器没有的话，迁移先失败，平台会把它当成"迁移失败"阻断整个启动 |
| D373 | 组件在运行时也暴露 `/openapi.json`，与市场产物并存 | 产物是发布那一刻的快照，运行时那一份才回答"此刻跑着的是什么"。两者用途不同，不是重复 |
| D374 | 用 `go:embed` 而不是 `COPY` 进镜像 | 编译期就绑定，不可能出现"镜像里漏了这个文件"。配了测试断言嵌进去的内容是合法 JSON |

### 结欠账（一）：P23 Podman 真机 + P12 git ref — ✅ 2026-08-15

**P23：Podman 真机验证 —— 抓到一个真 bug，而且是"设计书写错了"那种。**

本机已装 Podman 5.7.0（L1 的前提变了）。真跑之后发现 **13.14 这条验证项本身是错的**：

```
$ podman run --rm --add-host=x:host.containers.internal alpine getent hosts x
Error: invalid IP address in add-host: "host.containers.internal"

$ podman run --rm --add-host=x:host-gateway alpine getent hosts x

```

`host.containers.internal` 是 Podman **自动注入到容器 /etc/hosts 的主机名**
（确实在，地址就是 169.254.1.2），**不是** `--add-host` 能接受的值。
而 `host-gateway` 这个魔法值 Podman 同样支持。

也就是说：按设计书生成的 compose 文件，`local: true` + Podman 的容器
**根本创建不出来**——整条本地调试链路是断的，而单元测试全绿（它们只对比字符串）。
已改成两种引擎用**同一个值** `host-gateway`，并修正了 005 §4.2/§7.3/§7.5 与
**开发计划 13.14 那条验证项本身**。

**顺带修的第二个真问题：** 引擎检测只认独立的 `podman-compose` 程序，
而很多发行版（含本机）装了 Podman 却不装它。Podman 4.1+ 自带 `podman compose`
子命令——一台 Podman 与 compose 都能用的机器，会被 CLI 判成"没有可用的容器引擎"。
已加入检测顺序并新增 `engine.NewPodmanCompose()`。

**P12：git 安装源支持 `ref`（分支 / tag / commit）。**
设计书先行的前提已具备（003 §6.3 补上字段说明）。实现分两步：

**决策记录：**

### 第三轮全审：两个真 bug + 设计书逻辑理清 — 2026-08-23

**做法：** 14 本设计书通读，按每条承诺反查实现；试用指南 01–05 在真 Docker 上照着跑了一遍。
全部测试与 `make check-docs` / `check-cli-docs` / `check-guides` / `check-guide-output`
在审查开始时都是绿的——**问题全在这些检查覆盖不到的地方**。

#### 一、`brickkit up --only` 在 Docker 下把没点名的组件全删了（真 bug，实测复现）

`engine.Compose.Up` 无条件带 `--remove-orphans`。它删的是"compose 文件里没有的容器"，
而 `--only` 生成的部署文件**只含被点名的子集**——其余组件与 CLI 托管的资源容器
全部落进它的射程。实测：4 个组件 + pg 在跑，`up --only demo/hello` 之后
**只剩 demo/hello**，其余连同 postgres 容器被 `rm` 掉，而 `up` 报的是成功。

K8s 侧早在 P38 就为这件事设了防（`pruneSelectorFor`：`--only` 时返回空选择器），
当时那段注释写的是"Docker 那边由 compose 的 `--remove-orphans` 兜底"——
**那句话把"清理孤儿"与"删掉没点名的"当成了同一件事，而它们正好相反。**

修法：`PruneSelector` 从"K8s 专用字段"升格为**两种目标共用的判据**，
Docker 侧据它决定带不带 `--remove-orphans`。判据只有一份就不会再分叉。
全量 `up` 的孤儿清理照旧生效（实测：把组件改成 `enabled: false` 后容器如期消失）。

#### 二、资源绑定检查从来没在普通 `up` 上跑过（真 bug，实测复现）

`CheckResourceBindings` 实现得完全正确，但全仓库唯一的调用点在 `CheckUpgrade` 里——
**只有升级路径会检查**。于是"从来没升级过"的项目一次也没被检查过。

实测：组件声明了 `resources: database/postgresql`、绑定被删掉，`up` 一路绿灯，
生成的 service 里**一个 `DATABASE_*` 都没有**，迁移容器同理，要到运行时才炸成
"连不上库"——正是平台最反对的静默失败。而 006 §4.4、011 §5.2、§5.3 三处
都写着"`brickkit up` 时检查，未绑定则报错阻断"，011 §5.3 连报错文案都给了。

修法：新增 `CheckRunningResourceBindings`，在生成部署文件**之前**检查**本次会启动的**
组件，一次报全。只查会启动的那些——试用指南 02 §2.5 教的就是"用 `enabled: false`
把暂时不用的关掉而不是删掉"，拿那些组件卡住 `up` 等于逼人为一个不跑的容器编配置。
`external` 组件同样跳过（它连哪个库是对方项目的事）。

| D558 | 010 的签名章节以 `brickkit publish --sign` 为唯一入口，不教手工 cosign | 手工那条路产出的签名 CLI 不看、会漏钉 digest、还会把 private 组件的哈希传到公共透明日志。发布指南教错，比不教更糟 |

### 试用指南重构：从"前面 N 篇做完"改成"一条命令" — 2026-08-23

**动机来自上一节那次审查。** 照着指南真跑 01–05 时，01 和 02 都跑不通：

| 断在哪 | 为什么 |
| --- | --- |
| 01 §1.3 教 `brickkit reset --last` | 那时 `.last` 还不存在（它在第一次 `add` / `remove` 前才生成）。命令直接失败，配置**没有**被恢复，而指南写着"恢复原样"。它自己的注解还说"`.last` 就是 init 时的样子"——也是错的 |
| 02 §2.5 的 `brickkit add --local` | §2.3 的 `remove people/basic` 会**删掉组件的源码目录**（这是 remove 的正确行为），于是本地源里少一个组件，`--local` 扫到 9 个而不是 10 个，并因 `auth/password-login` 的强依赖缺失**整体中止** |
| 08 / 13–16 / 19 | 00-准备 手抄了四条 `docker build`，而试验场里有十个组件；`hello:2.0.0`（08 要用）没有任何一步会产生它 |

**为什么这些没被检查发现。** `check-guide-output.py` 的用例各自拼状态，
`add --local` 那条的前置只有 `init` + `add demo/caller`——**它跳过了 §2.3**。
校验器复现的顺序和指南叙述的顺序不是一回事，于是指南块是照着校验器的状态写的，
而不是照着读者的状态。**夹具不真实时，绿的检查比没有检查更危险。**

#### 改法：三个命名状态

`准备.sh` 从"只会铺场地"变成"能把试验场推到某个具名状态"：

```
./试用指南/准备.sh --images     十个组件镜像 + hello:2.0.0（= make demo-images）
./试用指南/准备.sh --reset      空试验场：只有组件源码，没有项目
./试用指南/准备.sh --baseline   五组件基准：demo-shop 项目 + 五个组件
```

于是每一篇的前置从"03 做完"变成一条命令。**想从哪一篇开始就从哪一篇开始。**
基准状态也从 02 §2.5 末尾那段正文里搬了出来——它此前藏在一篇的正文里，
而到达它要先走完前面几节。

`--images` 调的是 `make demo-images`，不再在指南里抄第二份镜像清单：
镜像名与标签的唯一事实源在 Makefile 里，抄一份早晚会对不上（`hello:2.0.0` 就是证据）。

#### 02 重排：把破坏性的一步挪到最后

新顺序是 `add` 一个 → `add --local` 装全 → 关掉六个 → `sync` → `remove` → 回基准。
`remove` 排到最后之后，它反而演示得更好了：

- 十个组件的依赖图里，`remove people/basic` 会被**三个** `enabled: false` 的组件挡住
  ——正好说明"关掉不等于不存在，`remove` 看的是声明"；
- `remove infra/api-docs` 删的是 `.archived/` 里那一份（上一步 sync 刚归档它）
  ——D2xx 那条"归档目录里的孤儿源码"终于有了自然的现场。

`sync` 那一节也从"手工 cp 两个目录再 git init"（而 `准备.sh` 早就把源码放好了，
那几条 `cp -r` 其实会在已存在的目录里套一层）改成直接用刚关掉的那六个，
一次看到"配置里十个、IDE 里四个"。

#### 校验器：按指南自己的叙述顺序连跑

`check-guide-output.py` 的 01/02 用例改成**一条链**，中间不重建状态，
把 `!corrupt`（写坏配置）与 `!enable`（改回 true）两个夹具动作补上。
看守的输出块从 16 个涨到 20 个。

顺带修了 `check-cli-docs.py` 一个潜伏的解析 bug：它把一行里的参数归给**该行任意**
一条命令，于是 01 §1.3 里那段 CLI 自己打印的建议

    1. 先执行一次 brickkit add / brickkit remove，之后即可用 brickkit reset --last 回退

的可靠边界。宽松归属只留给反向检查（那一侧宽松只会漏报，不会冤枉正确的句子）。

冒烟清单也补真了：它一直没声明 `resources`，而 `demo/caller` 声明了 database 依赖
——上一节修好绑定检查之后它被正确拦下，说明**在此之前那条冒烟每次都在启动一个
连接变量全缺的组件并报告成功**。

**决策记录：**

## 设计书与实现复核（一）：孤儿清理与 remove

对 14 份设计书与全部实现做逐条对账时抓到的两个真缺陷，各自当场修掉。

### `brickkit remove` 之后项目被自己锁死

`remove` 只删 `components` 条目、不动 `resources[].bindings`，而"binding 指向
未声明的组件"当时是校验**硬错误**。于是一条报成功的 `remove` 之后，
此后每一条命令都在解析阶段失败，报的还是资源配置的问题——与使用者刚做的事
完全对不上号。

两半一起改：remove 掉最后一个版本时解除绑定（多版本共存时保留，绑定按组件 ID 记）；
悬空绑定降级为 `up` 时的警告。降级不是妥协——那条绑定的唯一后果是自己不生效，
拿致命错误去挡一个无害状态代价不成比例，而且它顺带禁掉了"先声明资源与绑定、
再 add 组件"这条本来说得通的路。

### 孤儿清理漏掉全部条件生成的资源

判据原本只比**名字**。Ingress / NetworkPolicy / ServiceAccount / PDB 都与
Deployment **同名**且**条件生成**，而 Deployment 必然生成——于是"名字还在期望
集合里"永远成立，这四类一个都清不掉。最严重的是 Ingress：把 `expose` 改成
`false`、`up` 报成功，而**站点仍然对外可达**，且生成目录里已经没有那份 Ingress。

P35 撞到过同一个形状（PDB），当时的修法是一张"哪些类型是条件生成的"例外表。
那张表是与生成器并列的第二份真相，而它只填了 PDB 一个。这次判据整个换成
`<类型>/<名字>`，例外表、`desiredNames`、`DesiredPDBs` 一起删掉；期望集合由
`emitAll` 从**文档本身**（kind + metadata.name）记账，生成器多产出一类清单时
不需要任何人记得回来同步。

Secret 顺势纳入：从前排除它的理由（"按资源 ID 命名，与期望名字集合对不上"）
随判据一起消失，而留着的是明文密码。Namespace 仍是唯一例外，理由不同——
删错了代价无限大。

### 真集群跑出来的第三个缺陷：`serviceAccountName` 取消不掉

minikube 上跑完整开关矩阵时，关掉 `deploy.serviceAccount` 那一轮**部署失败**：

```
ReplicaFailure: FailedCreate
pods "..." is forbidden: error looking up service account ...:
serviceaccount "demo-portal-1-0-0" not found
```

根因是 `spec.serviceAccount` 是 `spec.serviceAccountName` 的**废弃别名**：
`kubectl apply` 把后者置空之后，API Server 又从别名字段同步了回来。生成物里
没有这个字段、`last-applied` 里也没有，而活着的 Deployment 里两个字段双双还是
旧值。（`automountServiceAccountToken` 没有这个毛病，同一次实测里被正确删掉了。）

**这是个先前就存在、被孤儿清理暴露出来的缺陷**：以前 SA 永远不删，那个陈旧的
引用一直指着一个存在的对象，看不出任何异常。改成开关关掉时显式写
`serviceAccountName: default`。

### 真集群验证（minikube v1.35.1）

| 方向 | 结果 |
| --- | --- |
| 全开 → 八类资源齐全 | ✅ deployment / service / ingress / networkpolicy / serviceaccount / job / pdb / secret |
| 修复**前**的二进制关掉全部开关 | ❌ 只清掉 PDB——**在真集群上复现了原缺陷** |
| 修复后关掉全部开关 | ✅ ingress / networkpolicy / serviceaccount / pdb 全部清掉，deployment / service / job 保留，服务 1/1 healthy |
| 删掉资源 | ✅ 装着明文密码的 Secret 被清掉；SA 引用收敛回 `default`（含别名字段），ReplicaFailure 消失 |
| 全部重新打开 | ✅ 八类全部回来，一条清理都没发生，3/3 ready，PDB `allowed=1` |
| 安全边界 | ✅ 同命名空间里无标签的 TLS Secret 与**另一个项目**的 Secret 都毫发无伤 |

单元层另做了两个方向的变异检验：让 `Desired` 漏报一类 → 生成侧 2 条用例失败；
把比对退回只看名字 → 引擎侧 4 条用例失败。前一个方向尤其要守——`Desired` 漏报
会让引擎删掉一个**正在服务**的资源，比留个孤儿严重得多。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D567 | `remove` 解除绑定，而不是报错要使用者先解绑 | 平台能自己收拾的烂摊子不该推给使用者，与 012 §2.20（remove 连归档源码都删）同一个立场 |
| D568 | 悬空绑定是**警告**不是错误 | 唯一后果是那条绑定不生效；阻断的后果是整个项目跑不了。顺带解开"先声明资源再 add"这条被误伤的路 |
| D569 | 孤儿清理的判据是 `<类型>/<名字>`，不再维护"条件生成类型"例外表 | 例外表是与生成器并列的第二份真相，漏填一类就再犯一次——而它确实只填了 PDB 一个 |
| D570 | 期望集合由 `emitAll` 从文档本身记账，不让调用点各报一遍 | 同上：调用点自己报就是第二份真相。而这一份漏报会让引擎删掉正在服务的资源 |
| D571 | Secret 纳入清理，Namespace 仍然排除 | 排除 Secret 的旧理由随判据消失，而留着的是明文密码；Namespace 的理由不同——它上面也有项目标签，算进去一次普通升级就会删掉整个命名空间 |
| D572 | 关掉 `serviceAccount` 时显式写 `serviceAccountName: default` | 省略不等于取消：废弃别名 `spec.serviceAccount` 会把旧值同步回来。真集群上表现为 FailedCreate + rollout 超时 |
| D573 | 这类改动必须在真集群上跑完整**开关矩阵**，不只跑"打开" | D572 只在"从开到关"这条边上出现，静态生成物与单元测试全绿。开关只验一个方向等于没验 |

D572 之后顺手把**同类字段扫了一遍**：平台会有条件写进一个已存在 Deployment 的
字段共四处，逐个在 minikube 上做了"先带上、再省略、看活着的对象"。
`imagePullSecrets` / `container.securityContext` / 两个探针**都被正确删掉**，
只有 `serviceAccountName` 留下。对照做得很干净——同一份清单、同一次 apply，
`automountServiceAccountToken` 删掉而 `serviceAccountName` 与 `serviceAccount`
双双留下，判据因此明确：**看这个字段有没有废弃别名**，不是"apply 靠不靠得住"。
结论记进 005 §5.13.3，省得下一个人重新怀疑一遍全部字段。

## 设计书与实现复核（二）：`--check-resources` 与 `host: localhost`

### 删掉 `--check-resources`

它做两件不相干的事，两半都删。

**资源可达性探测**：006 §8.3 自己就论证过它证明不了什么——组件用的是自己那套
凭据、从容器网络里连，CLI 从宿主机用另一套凭据连成功说明不了组件也能连成功。
更要命的是它给出的结论**两个方向都会错**：`host: localhost` 时说"可达"而容器里
连的是它自己，`host` 是容器网络里的服务名时说"不可达"而容器里跑得好好的。
错的时候还都很有说服力——绿灯最大的作用恰恰是让人不再往那个方向查。

**宿主机端口占用**：docker 会为它发布的每个端口报出清楚的
`port is already allocated`。这个检查唯一多覆盖的是 `local: true` 组件自己
监听的端口，而那一类的典型命中恰恰是**开发者自己刚启动的那个进程**
（先 up、启动 IDE 进程、再 up 一次）。它给的还是一句错话——"启动时会因为端口
冲突失败"，可那个端口根本没有容器会去 bind。

一个必须显式请求、只会警告、结论还不准的检查，不值得让所有人在文档里多读一段。
`up` 保留的是**声明**（每次列出"要先跑起来什么"与要建的库），不是**探测**。

### `host: localhost`：一条长期没人执行的规矩

006 §10.2 早就写着「不要写 `localhost`」，但它长期只是一句话——生成的部署文件
完全正常、`DATABASE_HOST=localhost` 老老实实注进去、容器起来就去连自己。
表现是启动之后才出现的 `connection refused`，而配置挑不出毛病。

**而规范书自己的示例长期写的就是它**：003 §2 / §5.1 / §8.1（6 处）、
006 §3.1 / §3.2 / §4.2 / §7.4（4 处）、011 §2.5 / §5.1（4 处）。
试用指南反倒是对的（一律 `host.docker.internal`）。一条照着规范抄就会中招的规矩，
光加警告是治标——两件事一起做了：示例全部改掉，生成阶段补一条警告。

判据落在**"有没有容器组件绑它"**，不是 host 的字面形状：绑它的组件全是
`local: true` 时 `localhost` 恰恰是对的（那些进程就在宿主机上，平台也只把这个
地址写进 `local-debug.*.env`）。按字面形状决定行为，正是 006 §10.5 刚废掉的
那种隐式判据。

顺带修掉 011 §2.5 一句与 006 §8.2/§8.3 正面冲突的话（说 `--check-resources`
会连到 database、库不存在时报出来——它只拨 TCP，探不出这个）。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D574 | 删掉 `--check-resources`，两半都删 | 资源探测的结论两个方向都会错且很有说服力；端口探测唯一多覆盖的那一类，典型命中是开发者自己的进程 |

## 设计书与实现复核（三）：external 在 status / down / order 里的三处漏网

P39 的完成记录里写着一句教训：

> "不生成它"这件事分散在**三层**：生成层不写、命令层不点名、引擎层不清理。
> 三处任意一处漏掉，表现都不一样。

那句话说对了形状，但**修的范围小了一层**。命令层其实有**两份**"要动哪些服务"
的名单：`up` 自己那份（`collectTargets`）当时修了；`down` / `status` / `order`
共用的另一份（`internal/cli/lifecycle.go` 的 `project`）没修——它只认识
`local: true`，不认识 `external`。同一个坑因此在三处原样重现：

| 命令 | 症状 |
| --- | --- |
| `status` | external 组件常驻报成「❌ 未在运行 / 未创建」——一条永远存在的假失败 |
| `down --only <external>` | `no such service`，**整条命令失败**（与 P39 在 up 上那次一字不差） |
| `order` | 启动顺序里列着它，看上去像本项目要启动它 |

顺手验出 `down --only <local: true 组件>` 也是同一个错——`local` 虽然被
`containerRefs` 认识，但那个方法只用在 `status`，`downTargets` 压根没经过它。

### 修法：把判据收进一处

`containerRefs` 改成"**本项目生不生成它的容器**"（同时排除 local 与 external），
`down` / `status` / `order` 全部走它。新增 `externalRefs`，status 与 order 各自
单列一节，措辞与 `up` 已有的 🔗 一致。

### 差点造出一个更严重的 bug

过滤掉停不了的组件之后，`--only` 有可能一个目标都不剩——而**空的服务名列表在引擎
眼里就是"停整个项目"**。一条 `brickkit down --only <某个 external 组件>` 会把本项目
所有东西都停掉，比原来那句 `no such service` 严重得多。所以显式加了一道
`nothingToStop` 守卫，并单写一条测试盯它。

两个方向都做了变异检验：拿掉守卫 → 2 条失败；`containerRefs` 退回只认识 local
→ 4 条失败。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D579 | "本项目生不生成它的容器"这条判据只留一份（`containerRefs`），三条命令共用 | 命令层原本有两份名单，P39 只修了 `up` 那份。两份名单必然分叉，而分叉的表现每处都不一样 |
| D580 | external 在 status / order 里**单列一节**，不混进组件表 | 混进去就是一条常驻的假失败；使用者会去 docker ps 里找它，找不到，然后怀疑平台 |
| D581 | status 只陈述"由哪个项目部署"，不核实对方部没部署 | 核实要读另一个项目的部署文件；而"平台替你探一下"这条路已在 006 §8 上论证过。`up` 的网络预检是**启动前的阻断**，与"报告现状"是两回事 |
| D582 | `--only` 过滤后一个都不剩时，什么都不做 | 空的服务名列表 = 停整个项目。过滤本身引入了这条新路径，不显式拦就是把一个报错换成一次误伤 |

## 设计书与实现复核（四）：`up --only` 点名了却不启动

004 §3.5 承诺"只启动指定组件及其依赖"，而实现是拿级联结果**做交集**
（`Result.Restrict`）。于是点名一个只被弱依赖引用的组件时什么都不启动——
它本来就不在级联结果里（003 §4.3：弱依赖不会被自动拉起）：

```
🎯 --only：只启动 infra/bus 及其强依赖
   ⬜ infra/bus@1.0.0  级联跳过（只被弱依赖引用…）
📋 本次没有组件会启动
```

### 交集是对"--only 是什么"的误解

级联回答的是"**你没说的时候**该跑什么"。你在命令行上点了名，那就是最明确的
意图，与 `enabled: true` 同级——012 §2.17 为 `sync --only` 做过的论证在这里
一字不差地成立：`enabled` 是团队共享、进 Git、带部署语义的声明，
"我这两天只跑这几个"是个人的、临时的。

所以 `--only` 应该**重新计算**而不是收窄：点名的组件当种子（等同钉住），
根组件不再自动启动（收窄掉它们正是 `--only` 的意思）。
`cascade.Focus` 与 `Compute` 共用可行性传播与强依赖闭包——分开写迟早会出现
"up 会启动它、up --only 点名它却不启动"这种自相矛盾。

`Result.Restrict` 一并删掉：它就是这个误解的载体。

### 白捡的一条正确行为

点名的组件的**强依赖被关掉**时现在会报错，与钉住的组件走同一条路：

```
❌ 错误：强依赖 demo/hello 被禁用
   组件：demo/caller@1.0.0（被 --only 点名）
   依赖链：demo/caller → demo/hello
```

从前这条路上它会**静默启动一个必然连不上依赖的组件**。这不是额外加的检查——
"点名等于钉住"自动带来的。

变异检验：把实现退回 `Compute` + 交集 → `--only` 的 8 条用例失败。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D583 | `--only` **重新计算**级联，不在结果上做交集 | 交集把 `--only` 理解成"在会启动的那些里再挑几个"，而它其实是"这一次我说了算"。只被弱依赖引用的组件因此点名也不启动，与 004 §3.5 的承诺相反 |
| D584 | 点名 = 钉住（`enabled: true` 同级），根组件不再自动启动 | 命令行上的点名是最明确的意图；收窄掉根组件正是 `--only` 存在的理由。副产物：强依赖被关掉时自动走钉住那条报错路径 |
| D585 | `Focus` 与 `Compute` 共用可行性传播与强依赖闭包，只有"种子从哪来"不同 | 两套算法迟早分叉成"up 会启动它、up --only 点名它却不启动" |
| D586 | 删掉 `Result.Restrict` | 它是这个误解的载体；留着就还会有人拿它去"收窄" |

## 设计书与实现复核（五）：component.yaml 没有拼写检查

P33 给 `brickkit.yaml` 做了一套很好的未知字段纠错（`user` → 是不是想写
`username`？）。`component.yaml` 这边**一直没有**——而它其实更危险。

### 为什么 component.yaml 更危险

`brickkit.yaml` 的必填字段写错了，语义校验会兜住（"project 缺失"）。
`component.yaml` 里真正会咬人的是**可选字段**，它们没有任何兜底：

| 拼错 | 后果 |
| --- | --- |
| `dependencies` → `dependencys` | 依赖**整个消失**，调用方一个 `*_ENDPOINT` 都拿不到 |
| `migration` → `migrations` | 迁移不跑，组件起来报 `relation does not exist` |
| `extraPorts` → `extraports` | 额外端口不生成 |
| `configSchema` → `configSchemas` | 配置项默认值一个都不注入 |

第二行与 002 §8.5.1 警告的是**同一种事故**——那里是迁移命令写错一个字母，
这里是字段名写错一个字母，后果一样：一路绿灯，运行时才炸，
现场没有任何线索指向那一行。

顺带实测确认 yaml.v3 是**精确比对 tag** 的：`healthcheck` 匹配不上
`healthCheck`，`HealthCheck` 也不行。所以大小写写错同样静默。

### 抽成共用包，而不是复制一份

walker 本来就是通用的（只有入口那个 `reflect.TypeOf(Config{})` 与 config 有关），
搬进新的 `internal/yamlcheck`，两边共用。复制一份的话，迟早只有一边跟着
结构体演进——事实上 component.yaml 这边**从来就没有过**，正是同一个道理的
另一种表现。

`configSchema.properties` 下的键不查：那里的名字由组件作者自己定。
与 config 侧 `components[].config` 的例外同源（walker 遇到 map 就不再下行）。

### 会拒绝旧文件，所以先验过

这是个**破坏性**变化：一份多写了字段的 `component.yaml` 从此装不上。
仓库里 20 份真实 Manifest（tests/components/ 与 试用指南/playground/）
逐个解析确认全过。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D587 | component.yaml 也做未知字段检查 | 可选字段拼错没有任何兜底；`dependencies` 写错一个字母，依赖整个消失而 up 一路绿灯 |
| D588 | walker 抽进 `internal/yamlcheck`，两边共用 | 复制一份迟早只有一边跟着结构体演进——component.yaml 这边从来没有过，正是这个道理 |
| D589 | Manifest **不提供**扩展字段机制（如 `x-` 前缀） | 002 §2.2 定义的就是完整结构；给自己的工具链存东西放在仓库里另一个文件。开了这个口子，"多出来的键"就再也不能一律判成拼写错误 |

## 设计书与实现复核（六）：两个从未被读取的 Manifest 字段

`observability` 与 `compatibility.minCliVersion` 解析进结构体之后，
**全项目没有任何一处读它们**——CLI 侧没有，市场侧的校验也没有。

两者的处境不一样：

| 字段 | 谁在用 | 有没有通往消费者的路 |
| --- | --- | --- |
| `compatibility.minCliVersion` | **零个组件** | 有（实现一次版本比较就行） |
| `observability` | **9/10 真实组件都声明了**（照着设计书示例抄的） | **没有** |

`observability` 那一行是关键：设计书说"未来由可观测性工具组件读取"，
而组件**根本读不到别的组件的 Manifest**——只有 CLI 有。所以它不是"还没接线"，
是**没有线可接**。真做可观测性时需要的多半也不是一个布尔，而是抓取路径与端口，
那已经能用 `extraPorts` 表达。

`minCliVersion` 比单纯的死字段更糟：它长得像一道安全闸。写了
`minCliVersion: 2.0.0` 的组件，在 0.1.0 的 CLI 上照装不误——与 `host: localhost`
那条"长期没人执行的规矩"是同一类。

### 为什么现在删，而不是实现

`minCliVersion` 值得实现的那一天是"**真的有了两个 CLI 版本、且 Manifest 语义
不同**"。今天只有一个版本（`0.0.0-dev`），而设计书示例里写的
`minCliVersion: 1.0.0` 一旦实现就会在 dev 构建上把示例本身卡住——
正是复核（二）刚批评过的"照着规范抄就中招"。

反方论点记下来，它是真的：组件用了新版本才有的**字段**时，老 CLI 现在会报
"未知字段 xxx，是不是想写 yyy？"——对这种情形是**误导**的（它不是拼写错误）。
那正是把 `minCliVersion` 加回来的信号之一。届时也该重新想清楚形状：
是"最低 CLI 版本"，还是"我用到了哪些能力"。

### 第 6 条刚把"删字段"的代价改了

未知字段检查落地之后，声明过这两个字段的 Manifest 从此**直接报错**。
所以现在是删它们成本最低的时刻——还没有外部组件。仓库里 20 份真实 Manifest
连同 2 份测试夹具一并清理，逐个重新解析确认全过。

签名不受影响：规范化载荷走的是通用 `map[string]any`，与结构体字段无关
（`testdata/signature-golden.json` 里本来也没有这两个字段）。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D590 | 删掉 `observability` | 从未被读取，而且**没有通往消费者的路**——组件读不到别的组件的 Manifest。不生效的"预留"，代价是每个读到它的人都要想一遍该不该填 |
| D591 | 删掉 `compatibility.minCliVersion`，而不是实现它 | 今天只有一个 CLI 版本，它守不住任何东西；而一个不生效的版本闸比没有更糟。回来的条件写在 002 §2.3 与代码注释里 |
| D592 | 删字段的时机跟着 D587（未知字段检查）走 | 那条检查一落地，删字段就从"静默忽略"变成"直接报错"。趁还没有外部组件时删，成本最低 |

## 设计书与实现复核（七）：文档与实现对账

复核清单里剩下的五条，四条纯文档、一条补实现。

### 补实现：`add` 装完不说"这个弱依赖默认不会启动"

004 §3.3 的输出样例里有这一行，实现里没有。`add` 会把整棵依赖树写进
`brickkit.yaml`，弱依赖也在里面；而级联不会把只被弱依赖引用的组件拉起来
（003 §4.3）。于是配置里明明有它、`up` 却不起它——003 §4.3 亲自认定这是
"最容易想当然"的一处，而使用者要到 `up` 之后数容器才发现。

```
✅ 已写入 brickkit.yaml（3 个组件）
ℹ️ 提示：infra/bus 是弱依赖，已写入配置但**默认不会启动**（003 §4.3）
   长期需要它就写 enabled: true；只是这一次要它，用 brickkit up --only infra/bus
```

第二条出路是复核（四）刚修好的——在那之前 `up --only` 点名它也不会启动，
这句话给不出来。

**判定规则没有在命令层重写一遍**：导出 `cascade.OnlyWeaklyNeededIn`。
命令层自己照着 Dependents / Requires 再写一次，迟早会与级联分叉——
那时 `add` 说"它不会启动"而 `up` 真的启动了它。

写的时候先犯了一次错，值得记下来：`add --local` 一次解析多个根、**每个根一张图**，
我最初逐图判断，结果两处判反——组件自己也是一个根时它那张图里没有依赖方
（看起来"没人要它"），以及 A 图弱依赖、B 图强依赖时结论应当是"会启动"。
判据因此是跨图的两件事：**有人弱依赖它**，且**没有人强依赖它**。
单张图是这条规则的退化情形，`classify` 走的也是它。

## 功能实用性复核：删 `add --refresh`

复核的问题是"开发者天天用 git、天天用 IDE，这个功能真的有人用吗"。
`--refresh` 是第一个答案为"不"的。

**它已经被 `add` 自己覆盖了。** 重复 `add` 同一个 `id@version` 时，命令本来就会问
"是否刷新 Manifest 与 artifacts 缓存？"，`--yes` 直接刷新（004 §3.3）。
而"第一次添加某个版本"根本不存在陈旧缓存可言——那正是缓存被写入的时刻。
所以 `--refresh` 唯一的作用，是把一条已有的交互路径换成一个要记住的参数名。

留下的是内部机器：`source.Options.Refresh` 与 `Client.SetRefresh` 都还在，
上面那条确认路径正是靠它们实现的。删掉的只是 CLI 表面。

顺带修掉两处指向它的提示（`remove` 的"无法确认依赖关系"、产物下载失败），
它们原本教人去敲一个即将不存在的参数。

**发现一处上一轮的漏网**：`AI-CONTEXT.md` 在删 `--check-resources` 时整个没被扫到，
里面同时留着 `--check-resources` 和 `--refresh` 两条示例。这说明当时的排查
只按 `design/` + `试用指南/` 找，仓库根目录的文档不在范围内。

**并给 check-cli-docs.py 补了"墓碑"豁免。** 它此前会把
"早先有个 `brickkit up --check-resources`，已删除"这类句子报成"文档写错了"。
这类句子的价值恰恰在于写出那个不存在的名字：报它，只会逼人把删除记录一起删掉，
而下一个人又会把功能加回来。豁免只认同一行内的删除措辞，范围窄到不会放过真笔误。

## 功能实用性复核：删 `reset` 与整套备份机制

删掉的东西：`brickkit reset [--last]`、`internal/backup/` 整个包、
`init` 写的 `.initial`、`add` / `remove` 前写的 `.last`、
`Layout` 上的三个备份路径方法、`clierr.CodeBackupMissing`、
`.gitignore` 里的 `.brickkit/backup/`。约 900 行。

**理由：`brickkit.yaml` 本来就该进 Git。** 003 §11 明确建议提交它，
而备份目录自己在 `.gitignore` 里。于是自建备份在每一项上都不如 Git——
`.last` 只有一格（连着两次 `add` 就丢了第一次）、看不了差异、退不了一部分、
换台机器就没有。

**而 `reset`（不带 `--last`）自己是不可逆的**：它把 `init` 之后的全部改动一次抹掉，
覆盖前的状态没有任何地方留着。一个专为"救回配置"存在的命令，
是整套流程里唯一一个救不回来的操作。删掉它顺带修掉了这个缺陷。

### 顺带抓到一个真 bug：I/O 错误被说成"命令用法不正确"

删掉 `SaveLast` 之后，`TestAddConfigWriteFailure` 从退出码 1 变成 2，
输出是"❌ 错误：命令用法不正确 / 建议：执行 brickkit --help 查看命令用法"——
而真实原因是 `brickkit.yaml` permission denied。

根因在 `clierr.As`：它会把裸 error **合成**成 `CodeInternal`，
于是"是不是结构化错误"从返回值上看不出来。两处调用点只好写成
`Code != CodeInternal` 来近似判断，把我们自己抛出的、货真价实的
`CodeInternal`（写文件失败、创建目录失败）一并当成了 cobra 的解析错误。

`up.go` 的注释里其实已经写着这个 bug——"不然它会被顶层当成'命令用法不正确'，
明明是 docker 挂了，却让使用者去查自己的命令怎么写"——但当时只在
`engineFailure` 局部绕过去了，顶层的 `translate` 没修，绕法本身也是同一个错的判据。

修法：新增 `clierr.Structured(err) (*Error, bool)`，只用 `errors.As` 判断、不合成，
两处调用点都换成它。此前会被误报成用法错误的还有：生成目录创建失败、
部署文件写入失败、`local-debug.env` 写入失败、K8s 清单写入失败、
凭据序列化失败——磁盘满了都会让人去查 `brickkit --help`。

`TestAddConfigWriteFailure` 改成断言"报的是写入配置失败、且**不含**命令用法不正确"，
并接手回归清单的 R14（原本指向已删除的 reset 测试）——
这一区域真正剩下的承诺是"CLI 写不进配置时报错、不留半改的文件"。
