### P40：产物下载并发 — ✅ 2026-08-18 · **延后清单清空**

**这一条最值得记的是：我当初"暂不做"的理由是错的。**

Step 36 发现 `downloadArtifacts` 串行时，我把它与刚修好的 `checkImages` 做了对比，
判成**带宽受限**——"并发只是把同一条管道切成几份，收益小得多"——据此登记为延后。

**那是没有量就下的判断。** P40 的第一步本该是量，而我直接给了结论。

#### 量完之后

| 量的是什么 | 实测 |
| --- | --- |
| 本项目 11 个产物文件的大小 | **443 B – 6.5 KB**（全部实测） |
| 一次远程往返的等待 | 30–350 ms |
| 6.5 KB 的传输时间 | ~0.3 ms（实测带宽 ~170 Mbit/s） |

**延迟主导 100–1000 倍**，和 `CheckImage` 完全同一形状。

错在哪很清楚：产物是 **proto、openapi.json 这类契约文件**，本来就该是小的——
组件规范里它们的用途是"让调用方生成客户端"，不是分发二进制。
是"下载"这个词让我先入为主想成了大文件传输。

#### 实现

并发在**组件**这一层，上限 8（与镜像预检同源：请求打到的多半是同一个市场，
无上限只会撞限流）。选组件层而不是文件层：一个组件通常只声明 1–2 个产物文件
（本项目 8 个组件全都是），而组件数会到几十——组件层拿到的是接近组件数的倍数。

结果按**依赖图顺序**汇总而不是完成顺序。并发的完成顺序每次都不一样，
直接按完成顺序追加的话，同一次 `add` 连跑两次会输出顺序不同的警告，
使用者会以为发生了不同的事情，而 diff 两次输出也看不出真正的差别。

#### 真跑

起真市场、发布 8 个各带一个 5.8 KB 产物的组件，再让一个根组件依赖其余 7 个，
这样**单次 `add` 就会拉全部 8 份产物**（否则每次 add 是独立进程，根本走不到并发路径）。

| | 8 个组件，各 5 次平均 |
| --- | --- |
| 串行 | 0.062 秒 |
| 并发 8 | **0.041 秒** |

1.5 倍，而这还是 RTT≈0.1ms 的**本机**市场。真实市场是远程的，收益随 RTT 增长。

#### 丢弃了一个自己搭的测量模型

为了模拟远程 RTT，我写了个延迟代理挡在市场前面。它给出的结论是**并发更慢**
（0.244 → 0.355 秒），与直连结果相反。

追查后发现它的数字**自相矛盾**：经一个"每请求 +150ms"的代理、走 16 次请求，
串行却只用 0.219 秒——算术上不可能。说明它没在量我以为的东西。

**没有报告这组数字，也没有拿它下任何结论。** 一个自己都解释不了的测量，
比没有测量更危险——它看起来是证据。最终结论只用了直连真市场那组
干净、可复现、5 次平均的 A/B。

（中途还撞到三次"快得可疑"：8 次 `add` 用 0.108 秒——每次 add 是独立进程，
根本没走并发路径；串行 0.012 秒——组件已在配置里，`add` 转成了交互式提示等输入；
发布 0/8 —— `sed` 正则没匹配上，产物类型压根没改。每一次都是靠"这个数字不合常理"
才回头查的。）

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D470 | 推翻 Step 36 的判断，产物下载并发化 | 产物是契约文件（443 B – 6.5 KB），延迟主导 100–1000 倍。当初判成"带宽受限"是没量就下的结论 |
| D471 | 并发在**组件**层而非文件层 | 一个组件通常只有 1–2 个产物文件，组件数却有几十；文件层只有 2 倍，还要为两层各设一个上限 |
| D472 | 结果按依赖图顺序汇总，不按完成顺序 | 并发的完成顺序每次都不一样，同一次 add 连跑两次不该给出顺序不同的警告 |
| D473 | 丢弃自建的延迟代理测量，不用它下结论 | 它的数字自相矛盾（16 次 +150ms 的请求只用 0.219 秒）。解释不了的测量比没有测量更危险，因为它看起来是证据 |

### P35：多副本与 PodDisruptionBudget — ✅ 2026-08-18

**P35 不能单做。** 它是"生成 PDB"，而单副本下 PDB 无论怎么写都是死路——
这是当初在 calico 集群上真跑确认、并写进测试注释的结论。所以实际范围是两半：
**先让 `replicas` 可配（005 §5.8），再据此生成 PDB**。那条旧测试自己就写着
「replicas 一旦可配，就该回头重新考虑 PDB」。

#### 前置：`replicas`

仅 K8s 生效，默认 1。默认必须是 1——加个字段不该让任何既有项目的副本数发生变化，
那是没人会在升级 CLI 时预期收到的改动。

| 校验 | 理由 |
| --- | --- |
| 必须 >= 1，写 0 时指向 `enabled: false` | 两者不是一回事：`enabled: false` 走级联、会提醒依赖方；`replicas: 0` 绕过这一切——依赖方照常启动、照常拿到地址，然后连一个不存在的后端，表现是 503 而状态表里那个组件显示"正常" |
| 与 `local` 互斥 | local 是"在你的 IDE 里跑"，那里只有一个进程 |
| 与 `external` 互斥 | 副本数由部署它的那个项目决定（P39 同款理由） |
| Docker 目标下警告 | 那里完全不生效，而 `up` 一切正常、`docker ps` 里只有一个容器，使用者会以为是自己写错了字段名——字段名是对的 |

#### 本体：PDB 只在多副本时生成

**用 `maxUnavailable: 1` 而不是 `minAvailable`。** 固定副本数下两者等价
（replicas=3 时 minAvailable:2 == maxUnavailable:1），但 maxUnavailable
**随副本数自动成立**：把 3 改成 5 时不用回来改 PDB。写死 minAvailable: N-1 的话，
改副本数就会悄悄改变容错度，且没有任何提示。

取 1 而不是百分比是**安全的那一边**：副本很多时排空会慢一些，
但慢从来不会变成故障，而一次多驱逐几个会。

#### 真跑：两个方向都验到了

minikube 上部署 3 副本：

```
NAME               MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS
demo-hello-1-0-0   N/A             1                 1
```

`ALLOWED DISRUPTIONS: 1` —— 正是当初单副本下恒为 0 的那一栏。

连续驱逐两个 Pod（不给补齐的时间）：

| | 结果 |
| --- | --- |
| 第一个 | `{"status":"Success","code":201}` |
| 第二个 | `TooManyRequests: Cannot evict pod as it would violate the pod's disruption budget` |

**放行一个、拦住第二个**，这才是 PDB 该有的行为。而单副本时那条报错会出现在
**第一个**上，让 drain 永远超时。

> 中间走过一次弯路：第一次只驱逐一个就下结论，第二次驱逐也成功了——
> 因为副本已经补齐、ALLOWED DISRUPTIONS 回到 1。**只验到"能驱逐"等于没验**，
> 必须连续驱逐才看得到"拦"那一半。

#### 真跑抓到一个此前一直潜伏的清理 bug

把 `poddisruptionbudget` 加进 `pruneKinds` 之后，minikube 上实测**它照样没被删**。

根因是孤儿判定**只比对名字、不看类型**：`kubectl get -o name` 返回
`poddisruptionbudget.policy/demo-hello-1-0-0` 与
`deployment.apps/demo-hello-1-0-0`，两者名字相同，而这个名字在"本次期望"集合里
（Deployment 要留），于是 PDB 也被当成该留的。

**在 PDB 之前这个近似一直是对的**：deployment / service / networkpolicy /
serviceaccount 每个跑着的组件都必然有一份，"名字还在期望集合里"就等于
"这份资源还该在"。**PDB 是第一个条件生成的资源**（只有多副本才有），
它把这个前提打破了。

漏掉的后果**单向不可逆**：一份 `maxUnavailable: 1` 的 PDB 永远留在单副本组件上，
让节点从此排不空——正是 P35 当初决定不生成 PDB 的那个理由，换了个更隐蔽的入口。

修法是让生成侧明确点名本次期望哪些 PDB（`UpRequest.DesiredPDBs`），
条件生成的类型按这份名单判，其余类型仍按名字判。真跑复验：

```
🧹 已清理旧版本残留（1 项）
PDB → No resources found
Deployment → 1/1 还在      ← 同名，修错方向就会把正在服务的它一起删掉
```

#### 顺带修正一段过期的说明

旧测试 `TestNoPodDisruptionBudgetGenerated` 的注释写着"PDB 要等多副本落地之后
再说"。前提已经变了，注释也跟着改了——**留着一段过期的理由比没有更误导人**。
那条测试保留下来守另一半：**副本数是 1 时坚决不生成**。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D465 | P35 连同多副本一起做，不单做 | 单副本下 PDB 必然有害，分开做只会得到一个确定错误的 PDB |
| D466 | `replicas` 默认 1，且仅 K8s 生效 | 默认值一变，升级 CLI 就会静默改变既有项目的副本数；Docker 下它不起作用，不提醒会让人以为自己写错了字段名 |
| D467 | `replicas: 0` 报错并指向 `enabled: false` | 用它关组件会绕过级联计算：依赖方照常启动并连一个不存在的后端 |
| D468 | PDB 用 `maxUnavailable: 1` 而非 `minAvailable` | 前者随副本数自动成立，后者改副本数就会悄悄改变容错度 |
| D469 | 孤儿判定对**条件生成**的类型按显式名单判 | PDB 与 Deployment 同名，只按名字判会让它永远留在集群里拦 drain——minikube 上真跑到过 |

### P39：引用别的项目部署的组件（`external:`） — ✅ 2026-08-16

**结论：做了，Docker 与 K8s 两侧都真跑验证。** 组件条目新增一个字段：

```yaml
components:
  - id: infra/notifier
    version: 1.0.0
    external:
      project: platform-shared
```

平台**照常做**：进依赖图、版本兼容检查、下载 artifacts、把地址注入给依赖方。
平台**不做**：生成它的部署对象、执行它的迁移、检查它的镜像、`down` 时碰它。

#### 两种目标的难点完全不同

到这一步为止，注入**从不区分部署目标**——因为同一个组件在两边服务名一模一样。
external 打破了这个巧合：被引用的组件在**另一个项目**里。

| 目标 | 难在哪 | 做法 |
| --- | --- | --- |
| K8s | 裸服务名只在**本命名空间**解析 | 地址加后缀 `<服务名>.<对方命名空间>` |
| Docker | 服务名只在**同一张网络**里解析 | 把**依赖它的**服务接进对方项目的网络 |

**K8s 侧真正危险的不是加后缀，而是不能生成同名 Service。** 本命名空间里的
同名 Service 会**抢在**跨命名空间解析之前命中，而它背后一个 Pod 都没有——
表现是稳定的 503，且从依赖方看一切正常：地址对、DNS 通、Service 也确实存在。

**Docker 侧只接依赖方，不是全部接进去。** 网络是可达性边界，
全接进去等于把"谁能访问共享服务"从**按依赖声明**变成**默认全通**——
那正是 NetworkPolicy 在 K8s 侧要防的东西，没理由在 Docker 侧自己先破坏掉。

#### 互斥校验拦下的都是"写了不报错也不生效"

这类组合最难查：改了配置、命令成功了、行为没变，于是开始怀疑平台。

| 字段 | 为什么不能同时写 |
| --- | --- |
| `local` | 含义相反：一个说在本机调试，一个说在别的项目里跑 |
| `expose` | 它的入口该由部署它的那个项目决定；硬生成会得到指向不存在 Service 的 Ingress |
| `config` | 它读的是**对方项目**那份配置，写在这里不生效——而看上去像生效了 |
| `resources` | 配额由部署它的那个项目决定 |
| `project` 指向本项目 | 等于说"我不部署它，但它由我部署" |

#### 真跑抓到一个单元测试全绿也发现不了的 bug

三层（config / compose / k8s / inject）单元测试全绿之后真跑两个项目，
消费方 `up` **当场失败**：

```
no such service: demo-hello-1-0-0
```

原因是**命令层另有一份"这次要启动哪些服务"的名单**，它按依赖图算、不看生成物，
于是把一个根本没生成的服务名传给了 docker。

教训不在于漏了一处，而在于**"不生成它"这件事分散在四层**：
生成层不写、命令层不点名、预检层不查镜像、引擎层不清理。
这次是当场报错（还算幸运），漏在别处可能是"启动成功但没连上"那种要几周才发现的。

#### 真跑验证

| | Docker | K8s |
| --- | --- | --- |
| 只起本项目的组件 | ✅ 1 个 | ✅ 1 个 |
| 跨项目业务调用 | ✅ 拿到 `demo/hello@1.0.0` 真实响应 | ✅ 同左 |
| 地址 | `http://demo-hello-1-0-0:8080` | `http://demo-hello-1-0-0.brickkit-platform-shared:8080` |
| 网络/命名空间 | caller 同时在两张网上 | 本命名空间**只有** caller 的 Service |
| **消费方 `down` 后对方还在** | ✅ `Up 3 minutes (healthy)` | ✅ `Running` |

最后一行是 **P39 存在的全部理由**：若把共享组件写进消费方的 brickkit.yaml
由消费方部署，那一步就会把别的项目一起弄挂。

003 新增 §4.9（字段语义、两种目标各做了什么、互斥表、唯一新增的失败模式）；
试用指南 18.4 从"还不能做"改写为完整可跑的操作 + 三处验证。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D459 | `external` 写**项目名**而不是命名空间或地址 | 共享的东西自己就是一个 BrickKit 项目，有自己的负责人与升级节奏。写项目名还白送版本安全：服务名带版本，要么连上声明的那一版、要么当场解析失败 |
| D460 | K8s 侧**不生成同名 Service** | 同名 Service 会抢在跨命名空间解析之前命中，而背后零个 Pod。表现是稳定 503 且依赖方看一切正常——比"没生成"难查一个数量级 |

### Step 40：文档验证 — ✅ 2026-08-16

`make check-docs` 一直在保证**引用**（小节号、链接）不悬空，但它查不到**内容**
是否与实现一致。而文档里最容易悄悄过期的恰恰是命令行：改一个 flag 名、
删一个参数，代码和测试都会跟着改，文档里那行 `brickkit up --old-flag` 却没人记得。

它不会让任何测试失败，也不会让构建报错——直到有人照着文档敲了一遍，

#### 新增 `make check-cli-docs`

问 CLI 要它自己的命令与参数，再拿去比对所有文档里的 `brickkit ...` 用法。
**965 处命令用法、190 处参数，零偏差。**

这个脚本身上装了三道防线，因为同类脚本在这个项目里已经坏过三次：

| 防线 | 挡什么 |
| --- | --- |
| 自检基线（含一个**故意不存在**的 flag） | 解析坏掉时直接退出，而不是跑出漂亮的 0 |

#### 真缺口一：升级摘要比设计书少了四行（38.18 / 38.19 / 38.21 / 38.22）

004 §3.5.1 把摘要定成**六项**，而实现只输出了其中两项：

| 设计书规定 | 实现前 |
| --- | --- |
| 依赖变更 | ❌ 没有 |
| 新增配置项 | ❌ 没有 |
| 删除配置项 | ❌ 没有 |
| 数据库迁移 | ✅ 有 |
| artifacts 变更 | ❌ 没有 |
| 资源配额变更 | ❌ 没有 |

缺的偏偏是「升级到底会改变什么」这个问题本身。使用者按下 `--dry-run`
就是想在真动手之前知道这个；只告诉他"有迁移"，等于让他自己去 diff
两份 Manifest——**而他多半不知道旧的那份就在 `.brickkit/manifests/` 里**。

现在的真实输出：

```
📋 升级变更摘要：
   people/basic: 1.0.0 → 1.1.0
   ├── 依赖变更：新增 department/tree@1.0.0
   ├── 新增配置项：enableNotification（默认 true）
   ├── 删除配置项：legacyMode
   ├── 数据库迁移：python manage.py migrate
   ├── artifacts 变更：新增 client.ts
   ├── 资源配额变更：limits cpu 500m/内存 256Mi → limits cpu 2/内存 1Gi
   └── 旧版本产物：保留（调用方可能仍指向旧版本）
```

**几处刻意的取舍：**

| 取舍 | 理由 |
| --- | --- |
| 旧 Manifest 读不到时报**「未知」**，绝不报「无」 | 缓存可能被清过、文件可能坏了。报"无变化"是一句**看起来完全正常的假话**，使用者会据此认为可以放心升级 |
| 六项**固定都出**，没变化写"无" | 藏起来会让人分不清"没有变化"和"平台没检查这一方面" |
| 新增配置项**带默认值** | 新增项走的就是默认值（38.13）。使用者要判断这个值对不对，而不只是知道"多了一项" |
| 删除配置项要报 | 删掉的项若 brickkit.yaml 里还写着覆盖，那个覆盖会被**静默忽略**（38.14，有意如此）。不提醒的话使用者会以为自己的配置仍然生效 |
| 资源配额给出**新旧两个值** | 配额变了可能导致节点资源不够而起不来，是少数几个"升级失败但与组件代码无关"的原因。只说"变了"的话使用者还得自己翻 Manifest |
| 配置项名**排序**后输出 | map 遍历顺序随机，不排序的话同一次升级两次运行的输出会不一样 |
| 资源依赖也算进"依赖变更" | 新版本开始要一个数据库，影响不比多依赖一个组件小——他得去 brickkit.yaml 里绑定它 |

### Step 37：回归测试 — ✅ 2026-08-16

**25 项全部早就有测试覆盖**——项目里有 1599 个测试函数，每条命令都有几十条
（`TestUp*` 103 个、`TestPublish*` 60 个、`TestAdd*` 49 个）。
所以这一步**不该是再写 25 条测试**，那只是把已有的东西抄一遍。

#### 清单缺的不是覆盖，是连接

计划里那 25 项是 **25 个要人手打勾的方框**，`tests/regression/` 里只有 `.gitkeep`，
25 项只勾了 1 项。方框和测试之间没有任何东西，于是有两个坏结果：

- 改完 `up.go`，不知道该重点看哪几条测试
- 某条测试被改名或删掉，**清单还挂着 ☑——清单变成谎话，而且没人会发现**

第二条才是要害。一份不会失效的清单和一份没有清单，危险程度是不一样的：
后者你知道自己没有保障，前者你以为有。

#### 做法：单一事实源 + 守卫 + 执行

| 件 | 作用 |
| --- | --- |
| `tests/regression/清单.tsv` | 唯一事实源：承诺 → 证明它的那个测试（含 module / 包 / 测试名） |
| `tests/regression/regression_test.go` | **守卫**：逐条确认那个测试今天仍然存在且能被跑到 |
| `make test-regression` | 先校验清单没失效，**再**逐条执行 |
| 开发计划.md 的表 | 由 tsv 生成的**投影**，25 项现在都指向具体测试 |

**存在性用 `go test -list` 判，不搜源码。** 搜 `func TestXxx(` 能确认名字在，
确认不了它**能被跑到**——构建标签、包编译不过、名字写在注释里，
这些情况下源码里有那串字符而 `go test` 一条也跑不到。`-list` 走真正的编译与注册。

**R18 在 `market-server/`——那是另一个 Go module**，根模块的 `go test ./...`
到不了它。runner 因此要按 module 切目录。这正是 Step 31 审计报出 4 个假缺口的
同一个坑（语料漏了一整个 module），这次一开始就查了。

#### 四种坏法都真的验过

不是"写完看着对"，是每一种都制造出来跑过一遍：

| 制造的坏法 | 结果 |
| --- | --- |
| 把 R7 指向的测试改个名 | ❌ **R7（brickkit up 基本功能，对应 Step 15）指向的测试…已经不存在了** |
| 从清单里删掉 R13 | ❌ 清单里 R13 出现了 0 次（应当正好 1 次） |
| 加一条计划外的 R26 | ❌ 清单里有计划之外的条目 R26 |
| 让清单里某个测试真的失败 | ❌ make 退出码 2，**成功横幅没有打印** |

守卫自己也有自检（`TestGuardDetectsMissingTest`）：拿一个故意不存在的名字去查，
必须查不到。**如果连它都"找到了"，说明匹配逻辑坏了，那条绿灯就不可信**——
和 check-docs、Step 33 审计脚本是同一个道理。

**过程中差点被自己骗了一次。** 验"真失败时不打印 ✅"时，我 grep 输出里的 ✅
得到 1 处，一度以为横幅照打。查下来那个 ✅ 来自**我自己写在 `t.Fatal` 文案里的
表情符号**。横幅确实没打。检查的关键词出现在被检查的内容里，是这类自查最常见的假阳性。

**未做（明确记录）：** 没有为这 25 项新写测试——它们已有覆盖，
重复写只会多出一批需要同步维护的副本。清单选的是每项最有代表性的
"基本功能"那条，不是边界用例。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D440 | 回归清单不新写测试，只做「承诺 → 已有测试」的映射 | 25 项全都已有覆盖（1599 个测试函数）。再写一遍等于制造需要同步维护的副本，而副本迟早和本体不一致 |

### Step 36：性能基准测试 — ✅ 2026-08-16

**这是 Phase 7 里唯一的真空白**：项目此前**一个 Benchmark 都没有**，
`tests/perf/` 只有一个 `.gitkeep`。性能从来没被测量过。

#### 先决定"怎么测才有意义"

计划里 10 项全是`"< 30 秒"、"< 5 秒"`这类阈值。那是**人跑一次时的验收标准**，
直接写成自动化断言会得到一个两头不讨好的东西：机器快时永远绿（测了等于没测），
CI 负载高时随机红（几次之后所有人开始无视它）。所以拆成两类：

| 类别 | 作用 |
| --- | --- |
| `Benchmark*` | 报告 ns/op、B/op、allocs/op，让**回归可见**，不判定对错 |
| `Test*` | 只守**灾难性回归**，阈值放到秒级——只有算法退化了量级才会触发 |

#### 纯计算层：离成为问题差 3–6 个数量级

| 验证项 | 计划阈值 | 实测 | 余量 |
| --- | --- | --- | --- |
| 36.2 10 层依赖解析 | < 5 秒 | **4 µs** | ~100 万倍 |
| 36.3 100 个依赖解析 | < 5 秒 | **42 µs** | ~12 万倍 |
| 36.5 解析 100 条目配置 | < 1 秒 | **755 µs** | ~1300 倍 |
| 36.6 生成 compose（50） | < 5 秒 | **2.4 ms** | ~2000 倍 |
| 36.7 拓扑排序（50） | < 1 秒 | **20 µs** | ~5 万倍 |

深度 10→100 时耗时 4µs→41µs，正好 10 倍——线性，没有隐藏的重复遍历。

#### 36.10 内存：一次"绿灯但什么也没证明"的测量

最直觉的写法是 GC 前后比 `HeapAlloc`。**测出来是 -0.03 MB，负数。**

原因不是写错了，而是 50 个组件的常驻状态（几百 KB）**比两次 GC 之间的噪声还小**。
那样的测试会永远绿着——它没有量到任何东西，只是恰好小于 100MB。
**量不到信号的测试比没有测试更糟：它让人以为测过了。**

改量 `TotalAlloc`：只增不减、不受 GC 时机影响（连跑三次都是 **2.67 MB**），
而且**累计分配是峰值驻留的上界**——就算一个字节都不回收也不会超过它。
于是"2.67 MB"这句话直接蕴含了"峰值远低于 100MB"，且不依赖 GC 什么时候跑。

#### 真正的发现：唯一不随组件数伸缩的地方

36.1 / 36.4 / 36.8 / 36.9 都是 I/O 主导的，在我这台机器上计时只能测出机器状态。
但**计时测不了不等于没东西可查**——真正决定伸缩性的是
「有没有按组件串行地调外部命令」，这个直接看代码就能判断：

| 路径 | 结构 | 结论 |
| --- | --- | --- |
| `Status` | 一次 `compose ps --format json` 拿回全部 | O(1)，安全 |
| **`checkImages`** | **每个镜像一次串行 registry 往返** | **O(N)，是问题** |
| `downloadArtifacts` | 逐个组件串行下载 | O(N)，但性质不同 → **P40** |

`checkImages` 的后果：本地没有镜像时每次都是一趟 registry 往返，
按健康网络 0.3–0.5 秒算，50 个组件光预检就是 15–25 秒，
而 36.1 给整个 `up` 的预算是 30 秒——**第一个容器还没开始启动**。

**真跑验证（8 个镜像，冷缓存）：**

| | 耗时 |
| --- | --- |
| 串行（原行为） | **50.5 秒**（且只成功 2/8，其余超时） |
| 并发 8（现行为） | **1.6 秒** |

**31 倍。** 按 50 个组件外推，串行约 5 分钟。

#### 测量过程中自己犯的两个错，都靠"数字不合理"抓回来

**① 把 12 秒当成了普遍事实。** 首批测出单次往返 12–15 秒，差点写进结论。
查下来那是 **TLS 握手超时**（CDN 那一段不通），而直连 registry 只要 0.34 秒——
所以 12 秒是这台机器当时的网络病，不能当成一般数字。

**② 批量测出 15 毫秒，差点当成"并发已经很快"。** 实际是
**zsh 默认不对未加引号的变量做分词**，`$IMGS` 被当成一个单词，
循环只跑了一次、拿整串当镜像名，瞬间失败。量的是那个失败。
改成字面列表后才有上面那组真数字。

两次都是"数字好得不合常理"暴露的。**性能测量里最危险的不是慢，是快得可疑。**

#### 实现上的三个取舍

| 取舍 | 理由 |
| --- | --- |
| 并发**有上限**（8） | 请求打到的是同一个 registry，几百个并发只会撞限流，那时不但不快，还会换来一堆 429 让人误以为是凭据出了问题 |
| **不在第一个失败时掐断** | 掐断会丢两样东西：**哪个**错误被报出来变得不确定（同一份配置连跑两次给出不同的错误，使用者会以为问题在飘），以及"还有几个也拉不到"。跑完就能一次说清要修几个 |
| 错误按**输入顺序**取第一个 | 并发天然让"谁先失败"每次都不一样。按下标存结果再按序取，输出才稳定 |

#### 验证

6 条并发测试 + race 检测全过。**RED 是真验过的**：把并发度临时改成 1，
`TestCheckImagesRunsConcurrently` 如实报出 `24 个镜像用了 964ms，串行也就是 960ms`
并指出峰值并发为 1——测试确实抓得住串行，不是编译不过而已。

`fakeEngine.CheckImage` 同时加了锁：预检并发之后，
不加锁真正在 race 的会是**夹具本身**，而不是被测代码。

**未做（明确记录）：** 36.4 产物下载并发 → **P40**（带宽受限，与延迟受限的
`checkImages` 不是一回事，不该照抄同样的修法）。
36.1 / 36.8 / 36.9 的端到端计时不做——耗时由镜像大小、网络、磁盘决定，
测出来的数字说明不了 BrickKit 的性能，只说明当时那台机器的状态；
它们的**结构**已按上表逐条查过。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D435 | 性能测试拆成"报数字的 Benchmark"与"守量级的 Test"，不把计划阈值写成断言 | 阈值当断言两头不讨好：机器快时永远绿，CI 忙时随机红。数字用来看趋势，断言只当保险丝 |
| D436 | 36.10 量 `TotalAlloc` 而不是 `HeapAlloc` 差值 | 差值实测为负——50 个组件的常驻状态比 GC 噪声还小。累计分配稳定可复现，且是峰值驻留的**上界**，宁可高估不会漏报 |
| D437 | `checkImages` 并发化，上限 8 | 整条 up 链路上唯一的 O(N) 网络操作。真跑 50.5 秒 → 1.6 秒。有上限是因为打的是同一个 registry，无上限只会撞限流 |
| D438 | 预检失败时跑完全部再报，且按输入顺序取第一个错误 | 早掐断会让报出的错误随机变化，使用者以为问题在飘；跑完还能一次说清要修几个 |
| D439 | 产物下载不跟着并发化（P40） | 延迟受限与带宽受限不是一回事。并发只是把同一条管道切成几份，收益小得多还会互相抢带宽。要做得先量清楚慢在等待还是慢在传输 |

### Step 34：兼容性测试（Docker） — ✅ 2026-08-16

它现在有三个分支：有 Docker、只有 Podman、两个都没有。

补了 3 条测试。它直接调 `exec.LookPath`、没有注入点，所以**用 PATH 本身做夹具**：
临时目录里放几个假的可执行文件，想让它看见什么就放什么。
这比加一层注入更贴近真实——`LookPath` 的行为（可执行位、PATH 顺序）

### 探讨：命名空间、共享组件与升级孤儿 — ⚠️ 2026-08-16

**性质：** 这条不是一个 Step，是一次设计探讨的产物。之所以要登记，
是因为**探讨过程中真跑出了一个缺陷**（P38），而且澄清了两条此前只活在代码里的假设。

**起因：** 讨论"不同命名空间能不能互通、能不能给每个组件指定命名空间"。

**结论一：命名空间不是网络边界。** 跨命名空间访问默认就通
（`http://svc.other-ns:8080`），不需要任何配置。命名空间隔离的是名字作用域、
RBAC、ResourceQuota / LimitRange、PodSecurity 准入标签与 DNS 默认搜索域——
**网络不在其中**，那正是 NetworkPolicy 存在的理由。

**结论二：不做"每个组件指定命名空间"。** 已写进 005 §5.2.1，连同要付的代价。
其中唯一的**硬约束**是 K8s 不支持跨命名空间引用 Secret，密钥要多存几份。
其余动机都有更便宜的解法：团队边界 → 那多半就是两个项目；安全分层 →
那正是 NetworkPolicy 该干的；配额 → 组件级 `resources.limits` 更精确；
**组件多到不好管 → 用标签过滤，别拿命名空间当文件夹**。

**结论三：共享组件不该属于任何一个项目。** 若 `infra/event-bus` 被 A 和 B 共用，
它就有自己的负责人与升级节奏。让它出现在 A 的 brickkit.yaml 里、由 A 负责部署，
本身就是错的——**A 执行一次 `down`，B 就挂了**。正解是共享的那些东西自己是一个
BrickKit 项目，消费方只声明"我连它"（登记为 **P39**）。
共享前先问一句：**它持有权威状态吗？** 不持有就复制两份，故障隔离反而更好。

**自我修正：** 我一度说"external 依赖的版本平台验不了"，这是错的。
服务名**带版本**（`event-bus-1-0-0`），注入的地址因此是版本专属的——
要么连上声明的那一版，要么 DNS 解析不出来当场报错，
**不存在静默连到错版本**这种状态。真正剩下的只是"对面部没部"的可达性问题，
比我原来说的轻得多，而且可以套用 `--check-resources` 现成的探测机制。
多版本共存也确认仍是默认行为（`internal/config/validate.go:139`）。

**真跑抓到的缺陷（P38）：** 顺着"CLI 能不能自己发现版本变了、把旧的删掉"这个问题
去验，在 minikube 上复现了 K8s 升级路径的孤儿泄漏：

| 步骤 | 结果 |
| --- | --- |
| 版本 1.0.0 → 2.0.0 再 `up` | CLI 报"✅ 全部组件已启动（1 个）" |
| `kubectl get deployment` | **两个版本都在跑**，`demo-hello-1-0-0` 没人管了 |
| `brickkit status` | 只报 1 个组件——**孤儿完全不可见** |
| `brickkit down` | 报"✅ 已停止全部组件"，而**旧版本照样在跑** |

根因是两条路不对称：Docker 那边有 `docker compose up --remove-orphans` 兜底
（`internal/engine/compose.go:56`），K8s 这边没有对应机制，
而 `kubectl apply` 默认不删目录里没有的资源。后果是**永久泄漏**——
`down` 也清不掉，只有 kubectl 才找得到。

修法：`up` 之后按 `brickkit.io/project` 标签列出集群实际资源，与本次生成的期望集合
求差，删掉多余的。它顺带解决"把组件从 brickkit.yaml 里删掉"的同一类泄漏。
**关键风险是 `--only`**：那时只部署子集，绝不能把不在本次范围里的组件当成孤儿删掉——
那会变成一条比原 bug 更危险的路。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D391 | 维持"一个项目 = 一个命名空间"，不做组件级命名空间 | 唯一硬约束是 K8s 不支持跨命名空间引用 Secret（密钥要多存几份、轮换要多改几处）；其余动机都有更便宜的解法。命名空间是权限与配额的边界，不是整理工具 |
| D392 | 组件多到不好管时用**标签**分组，不用命名空间 | 代价不在一个量级：标签不影响 Secret、不影响注入地址、不影响 NetworkPolicy、不影响 `down` 的删除判断 |
| D393 | 共享组件走"**外部依赖**"，不走"跨命名空间部署" | 共享的东西有自己的负责人与生命周期，不属于任何消费方项目。由消费方部署的话，消费方一 `down` 就把别人弄挂了 |
| D394 | 共享前先分"有没有权威状态" | 无状态的复制两份更好（故障隔离、独立升级、各自的版本自由）；只有持有权威状态的才**必须**共享，否则语义就错了 |

---

**续（同一次探讨，2026-08-16）：把"共享"想清楚，并真跑验证。**

第二轮把 D394 的二分法（无状态 / 有权威状态）**修正成三分**——原来漏了最常见的一档：

| 形态 | 判据 | 今天能不能做 |
| --- | --- | --- |
| 一：各部各的 | 组件无状态，也不依赖共享数据 | ✅ 默认行为 |
| **二：各部各的组件 + 共享资源** | 组件无状态，**状态在它连的资源里** | ✅ **无需任何新特性** |
| 三：外部依赖 | 组件**本身**就是权威（单例副作用、成本、归属） | ⬜ P39 |

**我举错过一次例子，值得记下来。** 我原先拿 `infra/redis-event-bus`
当"必须共享"的例子，错了——它**自己一行状态都不存**，事件全在 Redis Streams 里，
属于形态二。而 002 的组件规范本来就把组件推向无状态，
所以真正的形态三**比直觉中少得多**。这正是最容易判断错的地方。

**真跑验证（Docker，两个完全独立的项目）：**

| 验证 | 结果 |
| --- | --- |
| team-a / team-b 各跑一份事件总线，`host.docker.internal:6399` 指同一个 Redis | 两边都起来 |

| team-b 加 `config.streamName: "team-b:events"` 后重来 | `total: 0`，而 team-a 自己的仍是 1 |

最后一行是重点：**共享与隔离的差别就是一个配置字段**。
所以"要不要共享"不是一次性的架构决定，是可以随时改的配置。

**跨目标的自动化问题**（"不同项目在不同命名空间/不同启动方式下怎么统一"）：

K8s 走 `<svc>.<ns>.svc.cluster.local`，命名空间之间本来就可达）。

K8s 推导命名空间、Docker 推导 compose 网络名，与 `ingressController` 同一条线。

[18-多项目与共享](../../试用指南/18-多项目与共享.md)，全部内容基于上面那次真跑。

**决策记录（续）：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D395 | 共享分**三**种形态，不是两种 | 漏掉的"组件无状态但状态在资源里"恰恰是最常见的一档，而且今天就能做。把它并进"必须共享"会让人去用最贵的方案解决最便宜的问题 |

**这一段抓到的两个问题：**

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **nginx 的 `resolver` 不走 DNS search 域，K8s 里裸服务名解析不了** | 门户返回 502 而后端好好的，日志是 `erp-backend-1-0-0 could not be resolved (2: Server failure)`。K8s 靠 search 域让裸服务名可解析，而 nginx 的 resolver 只拿 nameserver 地址。**别的组件都没事**（Go/Python 的 DNS 解析走 search 域），只有 nginx 特殊 |

Docker 环境下容器也可能有 search 域（网络名），拼上去反而解析不了。

而分支写反的表现是"Docker 好好的、K8s 502"，或者反过来。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D375 | nginx 的 FQDN 问题修在**组件**里，不修在平台注入侧 | 裸服务名对其余所有组件都是对的，它们的 DNS 解析都走 search 域。只有 nginx 的 resolver 绕开了 search，这是 nginx 特有的行为，该由用 nginx 的组件自己处理 |
| D376 | 只在 search 域里看到 `.svc.` 时才补 FQDN | Docker 环境下容器也可能有 search 域（网络名），无条件拼上去反而解析不了。`.svc.` 是 K8s 的通用标志（集群域可自定义，但这一段固定） |

### 结欠账：P32 / P33 / P34 全部关闭 — ✅ 2026-08-15

首次真实装配抓到的三个问题，当场全修了，每条都配了测试。

**P33：未知字段被静默忽略 → 逐层比对 + 猜字段**

新增 `internal/config/unknown.go`：沿 YAML 节点与 Go 类型同时下行，
逐层比对键名。没有直接用 yaml 的 `KnownFields(true)`——它只会说
`field user not found in type config.Resource`：没有行号、没有中文、
更不会告诉你**想写的大概是哪个字段**。现在报的是：

```

```

猜字段用两条规则，**前缀优先**：`user → username`（少打了后半截，最常见）、
`usrname → username`（打字打错）。前缀单列一条是因为编辑距离对它无能为力——
`user` 与 `username` 差 4 个字符，按距离早被筛掉，而它恰恰是真踩到的那一个。

`component.config` 底下不查：那里的键由**组件的 configSchema** 决定，
平台无从判断对错，在那儿报"未知字段"会把每一个正常的配置覆盖都拦下来。

**这条检查立刻发现了另一个问题：** 我在 12 节里给 brickkit.yaml 写了
`apiVersion: brickkit/v1`——而 003 §2 根本没有这个字段（它属于组件 Manifest），
`brickkit init` 也不生成。检查是对的，错的是我。已改。

**P34：宿主机上的资源 → 自动加 extra_hosts**

`host: host.docker.internal` 是完全合理的写法（"连宿主机上那个已经跑着的库"），
但它带点，不会被判成服务名，CLI 不托管它；而容器里默认解析不了这个名字，
迁移容器直接报 `dial tcp: lookup host.docker.internal ... no such host`——
症状与原因完全不搭。现在为**绑定了它的**组件（含迁移容器）自动加上映射。

只给绑定了的组件加，不无差别地全加：后者也能"跑通"，但会让生成的文件
说不清"这个容器到底要连宿主机上的什么"。

**P32：Go 组件在运行时暴露 `/openapi.json`**

四个 Go 组件各加一个端点，`go:embed` 把 `openapi.json` 打进二进制。
产物是**发布那一刻**的快照，而 `infra/api-docs` 要回答的是"**此刻跑着的**
服务长什么样"——组件升级之后，只有运行时这一份是准的。

真跑验证：文档中心从"2 个 openapi、2 个 grpc、2 个 no-docs"变成

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D367 | 自己走一遍字段比对，不用 `KnownFields(true)` | 那个只给一句英文的类型错误。这个项目通篇的立场是"错误信息要能让人直接动手改"，一句 `field user not found in type config.Resource` 达不到 |
| D368 | 猜字段时**前缀优先**于编辑距离 | `user` 与 `username` 的编辑距离是 4，按距离早被筛掉——而"少打了后半截"恰恰是最常见的写法，也是真踩到的那一个 |
| D369 | 前缀猜测要求至少 3 个字符 | 一两个字母的前缀能命中一大片，挑出来的多半不是使用者想要的 |
| D370 | `component.config` 底下不查未知字段 | 那里的键由组件的 configSchema 决定，平台无从判断。在那儿报错会把每一个正常的配置覆盖都拦下来 |

| D373 | 组件在运行时也暴露 `/openapi.json`，与市场产物并存 | 产物是发布那一刻的快照，运行时那一份才回答"此刻跑着的是什么"。两者用途不同，不是重复 |

### 结欠账（一）：P23 Podman 真机 + P12 git ref — ✅ 2026-08-15

**P23：Podman 真机验证 —— 抓到一个真 bug，而且是"设计书写错了"那种。**

本机已装 Podman 5.7.0（L1 的前提变了）。真跑之后发现 **13.14 这条验证项本身是错的**：

```
$ podman run --rm --add-host=x:host.containers.internal alpine getent hosts x
Error: invalid IP address in add-host: "host.containers.internal"

$ podman run --rm --add-host=x:host-gateway alpine getent hosts x
169.254.1.2       x                                              ✅
```

`host.containers.internal` 是 Podman **自动注入到容器 /etc/hosts 的主机名**
（确实在，地址就是 169.254.1.2），**不是** `--add-host` 能接受的值。
而 `host-gateway` 这个魔法值 Podman 同样支持。

也就是说：按设计书生成的 compose 文件，`local: true` + Podman 的容器
**根本创建不出来**——整条本地调试链路是断的，而单元测试全绿（它们只对比字符串）。
已改成两种引擎用**同一个值** `host-gateway`，并修正了 005 §4.2/§7.3/§7.5 与
**开发计划 13.14 那条验证项本身**。

**顺带修的第二个真问题：** 引擎检测只认独立的 `podman-compose` 程序，
而很多发行版（含本机）装了 Podman 却不装它。Podman 4.1+ 自带 `podman compose`
子命令——一台 Podman 与 compose 都能用的机器，会被 CLI 判成"没有可用的容器引擎"。
已加入检测顺序并新增 `engine.NewPodmanCompose()`。

**P12：git 安装源支持 `ref`（分支 / tag / commit）。**
设计书先行的前提已具备（003 §6.3 补上字段说明）。实现分两步：
先 `clone --depth 1 --branch <ref>`（分支与 tag 走这条，保持浅 clone），
失败再回落到完整 clone + `checkout`——因为 **`clone --branch` 不认 commit SHA**，
这是 ref 唯一真正的难点。5 个业务测试都用**真 Git 仓库**跑（造了 main/next/tag/SHA 四种情形）。

**决策记录：**

| # | 决策 | 理由 |
| --- | --- | --- |
| D256 | Docker 与 Podman 的 `extra_hosts` 用**同一个值** `host-gateway` | 真机实测：Podman 认 `host-gateway`，不认 `host.containers.internal`。设计书原文把"Podman 注入的主机名"和"add-host 能接受的值"搞混了 |
| D257 | 引擎检测加入 `podman compose` 子命令，排在 `podman-compose` 之后 | 独立的 podman-compose 更成熟、优先用；但没装它的机器不该被判成"没有容器引擎" |
| D258 | `ref` 先浅 clone 再回落完整 clone，不一上来就完整 clone | 绝大多数人写的是分支或 tag，让常见情况保持最快 |
| D259 | 生产环境建议 `ref` 钉 tag 或 commit（写进 003 §6.3） | 默认分支会动，同一份 brickkit.yaml 在不同时间装出不同组件，正是版本化要避免的事 |

Podman 的 docker 兼容 API 对本机这个版本的 docker CLI（29.7.1 / compose v5.3.1）
返回**空镜像列表**，compose 于是每次都去 pull。这是环境不兼容，不是 CLI 的问题；
