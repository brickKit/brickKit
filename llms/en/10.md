# Choosing a deployment shape

This page answers one question only: **what should a project with N components actually run as?** It doesn't teach you
how to build a shell (see [Writing a shell](../../docs/en/04-shell/05-shell-development.md)), nor the steps to put a component into a
shell (see [Managing members](../../docs/en/04-shell/04-members-management.md)). Read this page first, before the project's overall
shape is decided.

## The short answer

| You want to | Run it as |
| --- | --- |
| Keep it running on one machine: a delivery, a small production | Containers on Podman as systemd units (`podman.units: quadlet`): **rootful** when the engine may run as root, **rootless** when it may not; Docker is equally supported, for a machine that already runs Docker or tools that only speak Docker |
| Keep it running with self-healing and scaling across machines, or on a cluster you already have | Containers on Kubernetes |
| Change one or two components against the real rest | Containers, with those components as processes on this machine (`mode: debug` / `mode: local`) |
| Show it or try it on a machine without a container engine | Every component `mode: local` — a demo or a trial, never a delivery |

Whichever of these, the topology is decided separately: start with every component standalone, move components into
shells when their memory or CPU really doesn't add up, and expect to end up mixed. In one measured project, shells cut
the components' memory by about a third and their CPU by 14–28%, while the whole stack's memory hardly moved — the
saving is largest for components on heavy runtimes ([measured](#measured-what-each-shape-costs)).

**Containers are the main line.** The engine restarts a crashed container and starts it again at boot, and the image
pins the runtime the component was tested with. **Processes on this machine are the convenient alternative**: they need
no container engine and no image, but they live only as long as the `up` that started them, and they run on whatever
toolchain the machine has. More and more deployments are run by scripts and AI assistants, for which installing a
container engine is no burden; so the cases left for processes are development, demos and trials.

## Three decisions

1. **Where the containers run** — `target: podman`, `docker` or `k8s` in the deploy file (on Podman also `podman.units`:
   systemd units or compose).
2. **The topology** — how many containers the components end up in: all standalone, all in shells, or mixed.
3. **Whether some components run as processes on this machine this time** — a development overlay, or, with every
   component that way, a demo without containers. It is described last, in
   [Off the main line](#off-the-main-line-processes-on-this-machine).

The first two are independent axes: any topology runs on any target, and switching either is switching one deploy
file, without a word of `config/` changing. [The matrix](#the-matrix-topology--where-it-runs) lists their six cells.
What each choice costs in CPU and memory is measured in the next section.

## Measured: what each shape costs

The numbers below come from one project that ran every shape on one machine. They are a reference for the size of
the differences, not a prediction for your project: measure your own before you size a machine.

**What was measured**

| | |
| --- | --- |
| Machine | Intel i5-12450H (12 threads), 14 GiB, NVMe, Linux 7.0, performance power mode |
| Components | 12: 11 in Go, 1 in Python (printing); one business chain from quotation to invoice and print |
| Topologies | **All standalone**: 12 processes. **All in shells**: 3 shells — security and master data (7 members), trading (4), printing (1). **Mixed**: only the first shell (7 members), the other 5 standalone |
| Infrastructure | PostgreSQL 16, NATS JetStream, an object store, an identity provider — on every row in Docker on the same machine |
| Data and load | 2 companies, 2,000 products, 500 customers, 20,000 historical orders; an open-loop mixed load of 7 requests a second (lists, quotations, confirmations, deliveries, invoices), 15 minutes after a 5-minute warm-up |
| Versions | Podman 5.7.0 (rootless), Docker 29.9.2, minikube v1.38.1 (Kubernetes v1.35.1, one node), BrickKit v1.10 |

**How to read the numbers**

- **Components** are the component processes (or shells) alone; **the whole stack** adds the infrastructure and the
  platform (the container engine, the cluster, or the launcher of processes on this machine). On the Podman,
  Kubernetes and processes rows it also counts the Docker that served the infrastructure.
- Memory is the working set without page cache, under the load; CPU is CPU seconds per 1,000 requests (lower is
  better) — 100 CPU seconds per 1,000 requests at 7 requests a second is 0.7 cores.
- Each cell was measured once. Comparisons are made only within one batch of measurements: different batches differed by
  up to about 8% overall, so compare across a row, not down a column. Differences under 10% count as no difference.

### All standalone, all in shells, mixed: the components

| Where it runs | Memory: standalone → shells / mixed | CPU per 1,000 requests: standalone → shells / mixed |
| --- | --- | --- |
| Docker | 383 → 243 MiB (−37%) / 290 MiB (−24%) | 36.5 → 28.3 s (−22%) / 32.3 s (−12%) |
| Rootless Podman | 377 → 244 MiB (−35%) / 288 MiB (−24%) | 35.4 → 25.5 s (−28%) / 29.8 s (−16%) |
| Kubernetes, one node | 354 → 245 MiB (−31%) / 291 MiB (−18%) | 34.3 → 29.4 s (−14%) / 31.5 s (−8%, no difference) |
| Processes on this machine (`mode: local`) | 370 → 234 MiB (−37%) / 281 MiB (−24%) | 31.2 → 26.4 s (−15%) / 29.2 s (−6%, no difference) |

On every shape, all in shells cut the components' memory by about a third and their CPU by 14–28%; mixed saved about
two thirds of that memory and half of that CPU. Latency didn't change: p95 was 49.6–54.2 ms in every cell.

### All standalone, all in shells, mixed: the whole stack

| Where it runs | Memory: standalone / shells / mixed | CPU per 1,000 requests: standalone / shells / mixed |
| --- | --- | --- |
| Docker | 1.97 / 2.04 / 1.88 GiB | 101.2 / 88.2 (−13%) / 94.0 s (−7%) |
| Rootless Podman | 1.37 / 1.36 / 1.29 GiB | 106.8 / 94.2 (−12%) / 96.5 s (−10%) |
| Kubernetes, one node | 2.38 / 2.46 / 2.36 GiB | 109.3 / 103.2 (−6%) / 105.4 s (−4%) |
| Processes on this machine | 1.43 / 1.43 / 1.32 GiB | 101.9 / 97.8 (−4%) / 101.6 s (0%) |

The whole stack's memory hardly moved with the topology (between −8% and +4%), and its CPU fell by at most 13%. Each
row is its own batch, so don't compare rows here — the engines are compared [further down](#the-engines-the-platforms-own-cost).

### Why the components save and the whole stack doesn't

- **What a process costs on its own.** Idle, a Go component took 29 MiB and 0.012 cores, a Python one 101 MiB and
  0.017 cores; each member a shell hosts adds only 1–2 MiB and about 0.01 cores (its background polling). Merging saves
  the runtime once per process removed — so components on a heavy runtime (Python here; JVM, typically hundreds of MB,
  wasn't measured) save far more per merge than Go ones.
- **The infrastructure is the largest part.** The four infrastructure services alone took 0.64–1.15 GiB without page
  cache, more than all the components; the topology doesn't change them.
- **A shell's database connections are bigger.** One connection of a shell serves several members and keeps caches for
  each of them: 10.1 MiB of private memory per connection against 4.2 MiB standalone. Connections went from 102 to 63,
  yet PostgreSQL grew by about 210 MiB — cancelling the about 130 MiB the components saved (Docker batch). The shells'
  pool limits and connection lifetimes could be tuned further; that wasn't measured.

So shells reliably save CPU and processes — and with them start-up time, logs and things to restart. Whether they save
memory depends on the runtime and the database: with mostly Go components on one database, it was a wash. Measure your
own before merging for memory.

### The engines: the platform's own cost

All standalone, one batch (Kubernetes re-measured in a second batch with Docker as its reference):

| | Components | The platform's own memory | The platform's CPU per 1,000 requests | Whole-stack CPU against Docker |
| --- | --- | --- | --- | --- |
| Docker | 378 MiB, 35.6 s | 548 MiB (dockerd, containerd, shims, port proxies) | 14.7 s | — |
| Rootless Podman | 377 MiB, 35.4 s | 135 MiB (`conmon` per container, `pasta`): 55 MiB with the 3 shells | 16.0 s | +6% (no difference) |
| Kubernetes, one node | 354 MiB, 34.3 s | about 2 GiB (control plane and kubelet; 0.75 GiB without page cache) and about 0.25 GiB of published-port proxies | 14.8 s | +8% (no difference) |
| Processes on this machine | 370 MiB, 31.2 s | 435 MiB (`go run` beside each process): 116 MiB with the 3 shells | 0.5 s | +1% (no difference) |

- The components cost the same on every engine; the difference is the platform's memory. Running everything on rootless
  Podman instead of Docker saves that difference once per machine — about 0.4 GiB here (Docker's daemon grew to about
  0.7 GiB in another batch, after a day of image builds).
- Rootless Podman's user-space networking costs CPU: Podman's own share was 13.1 CPU seconds per 1,000 requests rootless
  and 2.9 rootful; rootful Podman used 9–10% less CPU across the whole stack (another batch), at the price of a root
  engine.
- Processes on this machine reached the infrastructure through Docker's published ports, so Docker's port proxy carried
  that traffic once more: the Docker serving the infrastructure took 20.5 CPU seconds per 1,000 requests on that row,
  against 7.2 on the Podman row — about 13 seconds more, the largest platform cost of that row.
- **A few processes on this machine, the rest in containers** (a later batch, after a change in the components that cut
  every cell by about 17%): against all-in-containers in the same batch, no difference (+2% with Docker, +4% with
  Podman); shells saved the same there — components −20% CPU and −35–36% memory, the whole stack −8 to −10%.

**Sizing.** Doubling the load (7 → 14 requests a second) added 50–56% to the cores of the components and the database,
with no rise in latency; doubling the data added 10–15% to the database. The whole stack in containers ran unchanged
under a 4 GiB and a 6 GiB memory limit — only page cache gave way. Not measured: the load ceiling, more components on
one machine, several machines, high availability, multi-node Kubernetes, components on other runtimes.

## Decision one: where the containers run

This is almost entirely an infrastructure question, not a performance one: do you have a Kubernetes cluster, do you need
scheduling across machines and self-healing? If not, one machine runs everything on Podman or Docker, the simplest to
operate. If so, `k8s` generates Deployments / Services / Ingresses.

### One machine: Podman, rootful or rootless, or Docker

What differs is the engine on the host:

| Engine | What runs on the host | Upside | Cost | For |
| --- | --- | --- | --- | --- |
| **Rootful Podman** (recommended when the engine may run as root) | Podman as root, no daemon: each container has a small monitor process (`conmon`); the kernel carries the containers' network | Coming back at boot needs nothing beyond systemd; no user-space networking (9–10% less CPU across the whole stack than rootless); any port can be published | The engine runs as root, as Docker's does: a process that escapes its container is root on the host unless the image runs as a non-root user; next to Docker, Podman's bridges must be let through Docker's firewall chain ([below](#setting-up-a-host-for-rootful-podman)) | Single-machine delivery where root is acceptable |
| **Rootless Podman** (recommended when it may not) | Podman as the deploying user: each container has its `conmon`; a user-space helper (`pasta`) carries the containers' network | The engine never runs as root; the least resident memory | The user-space networking costs CPU; coming back at boot takes host settings, each of which fails silently until the next reboot ([below](#setting-up-a-host-for-rootless-podman)); ports below 1024 can't be published as they are | Hosts that don't allow a root engine |
| **Docker** | The Docker daemon (`dockerd`, `containerd`), as root | The most widespread, the most surrounding tooling; setting it up is installing it | The daemon's resident memory; root, as for rootful Podman | Machines that already run Docker; tools that only speak Docker |

**Choosing between them.** Ask first whether the engine may run as root on this host. If it may, rootful Podman: the
boot path is the system's own and the networking is the kernel's. If it may not, rootless Podman, with the host settings
below; the [environment check](../../docs/en/10-troubleshooting/01-up-down-issues.md#podman-run-the-environment-check-first) tells
you which of them is missing. Docker is the same choice as rootful Podman with a daemon: take it where Docker is already
there.

**What the measurement says** ([the engines](#the-engines-the-platforms-own-cost)): the components cost the same on every
engine, and the whole stack's CPU didn't differ between rootless Podman and Docker; what differs is the platform's own
memory, paid once per machine — about 0.14 GiB for rootless Podman against about 0.55 GiB for Docker's daemon, about
2 GiB for a one-node cluster. It weighs most on a small machine. Rootful Podman saves the user-space networking's CPU
(9–10% of the whole stack); its memory wasn't measured separately (the same `conmon` per container, no `pasta`).

**What a reboot showed** (the same machine — Ubuntu 26.04, Podman 5.7.0, Docker installed beside it, Wi-Fi by DHCP — and
the same 12 components, run with compose): rootful Podman came back on the first real reboot with only the system boot
unit and the firewall unit in place — all 12 healthy, none restarted, Podman's boot unit done 3.5 seconds after the network
was online. Rootless Podman took three reboots to find what it needs: the AppArmor profile (nothing came back), the boot
unit waiting for the network (the containers came back without a route to the host), and then it passed.

### How Podman runs them: Quadlet units, or compose

On Podman the deploy file chooses what BrickKit hands over, with `podman.units`:

```yaml
target: podman
podman:
  units: quadlet      # left out: compose
```

- **`quadlet`** (recommended for a delivery): `up` writes systemd units in Podman's Quadlet format — one `.container` per
  component and per migration, one `.network` — and systemd keeps the containers running and starts them at boot.
- **`compose`** (when `podman.units` is left out): `up` generates `compose.yaml` and runs it with `podman compose`, the
  same file as `target: docker`. This is the one for a development machine: only it can run some components as processes
  on this machine (`mode: local` / `mode: debug`, a focus run) next to the containers.

| | Quadlet units | compose |
| --- | --- | --- |
| At boot | Each unit starts by itself; nothing else to enable | Podman's boot unit `podman-restart.service`, enabled by hand |
| Waiting for the network at boot | Built in (rootless too) | Rootless: a drop-in by hand |
| Order at boot | Each component after the ones it needs are healthy | None: containers start all at once and retry |
| Migrations | At every `up` only | At every `up` only |
| A component turns unhealthy | Killed and restarted (only when it declares no separate `readinessCheck`) | Left running |
| Logs | journald: `journalctl [--user] -u 'brickkit-<project>_*'` | `podman compose logs` |
| A migration fails | `up` stops before installing any component's unit: they keep running their previous version, after a reboot too | The component waits for its migration and doesn't start |
| What the host needs | Podman 5.3 or later | Podman, Docker's Compose V2 (`docker-compose`), `podman.socket` |
| Processes on this machine, focus runs | Refused while loading | Supported |
| Runs `up` | Rootless: the deploying user. Rootful: root (`sudo brickkit up`) — it installs into `/etc/containers/systemd`. Run the other way, `up` refuses rather than deploy a second copy | The deploying user; rootful also through a socket group ([step 5](#setting-up-a-host-for-rootful-podman)) |

The units are what you see: `up` writes them into `.brickkit/generated/quadlet/` (`up --dry-run` stops there), then
copies them into a directory of their own, `~/.config/containers/systemd/brickkit-<project>/` (rootless) or
`/etc/containers/systemd/brickkit-<project>/` (rootful), and `down` removes that directory. Values that must not be
read in a file — secrets, `file://` contents, `${VAR}` templates, values spanning several lines — are evaluated at `up`
and handed over as Podman secrets; a unit only names them. `mount: file` values are the exception: the units mount them
from the project's `.brickkit/generated/secrets/`, so the project directory has to stay where it is. A project runs one way at a time: switching `podman.units`
(or to `target: docker`) and running `up` removes what the other way left (compose's containers, or the units) and says
so.

Verified with BrickKit: Quadlet units, rootless, on Podman 5.7.0 — `up`, a change restarting only that component, a failed
migration leaving the previous version running, replicas, switching to compose and back, `down`. Real reboots, rootful
and rootless (by a user on Ubuntu 26.04 with the database in Docker on the same machine): every component came back
healthy in dependency order without `podman-restart.service` or the network drop-in, and nothing came back after `down`.

### Setting up a host for rootful Podman

As root, or with `sudo`. Steps marked *compose* aren't needed with Quadlet units, and the other way round:

1. Install Podman, 5.3 or later for Quadlet units. *compose*: also Docker's Compose V2 (`docker-compose`), as in step 1
   [for rootless Podman](#setting-up-a-host-for-rootless-podman).
2. *compose*: `systemctl enable --now podman.socket` — `brickkit up`, `down` and `status` reach Podman through it
   (`/run/podman/podman.sock`).
3. *compose*: `systemctl enable podman-restart.service` — starts the containers again at boot. It is a system unit, so
   its `After=network-online.target` really waits for the network. Quadlet units start at boot by themselves.
4. **Docker on the same machine**: let Podman's bridges through Docker's firewall chain, and put the rules back at every
   boot, after Docker and before the containers start; without them containers can't reach each other
   ([the unit](../../docs/en/10-troubleshooting/01-up-down-issues.md#all-healthy-on-podman-yet-calls-between-containers-time-out)).
   Quadlet units are ordered after that unit by themselves.
5. Who runs `brickkit`: with Quadlet units, root (`sudo brickkit up`). *compose*: root as well, or a user in a group you
   let use root's socket. For the latter, `systemctl edit podman.socket` and add

   ```ini
   [Socket]
   SocketGroup=<group>
   SocketMode=0660
   ExecStartPost=/bin/chmod 0711 /run/podman
   ```

   then `systemctl restart podman.socket`, and give the user `export CONTAINER_HOST=unix:///run/podman/podman.sock`. The
   `chmod` is needed because the Podman package's own `tmpfiles.d` entry creates `/run/podman` as `0700` at every boot.
   Membership of that group is as good as root, the same as Docker's `docker` group.
6. Images run as a non-root user (`USER` with a non-zero uid in the `Dockerfile`): with a root engine, root in a
   container is root on the host ([why](../../docs/en/03-component-guide/02-component-yaml-reference.md#deployment-how-i-run)).
7. Podman's storage on a disk mounted with `nofail`: systemd doesn't then guarantee it is mounted before the containers
   start. *compose*: add `RequiresMountsFor=<that mount point>` under `[Unit]` with `systemctl edit podman-restart.service`.
   Quadlet units: one drop-in covers every unit whose name starts with `brickkit-`:

   ```bash
   mkdir -p /etc/systemd/system/brickkit-.service.d
   printf '[Unit]\nRequiresMountsFor=<that mount point>\n' > /etc/systemd/system/brickkit-.service.d/storage.conf
   systemctl daemon-reload
   ```

8. Run the [environment check](../../docs/en/10-troubleshooting/01-up-down-issues.md#podman-run-the-environment-check-first) as
   root once, with `--units quadlet` for Quadlet units: it tests that containers can reach each other and be removed
   cleanly, and warns about any of steps 1, 3, 4 and 7 that is missing.

Verified with BrickKit: rootful Podman with compose on a machine that also has Docker, steps 1–5 (with the group),
including a real reboot (all 12 components healthy without anyone logging in or running `up`). A machine with only Podman
hasn't been verified end to end; there, step 4 doesn't apply.

### Setting up a host for rootless Podman

As the user who will own the deployment. Steps marked *compose* aren't needed with Quadlet units:

1. Install Podman, 5.3 or later for Quadlet units. *compose*: also Docker's Compose V2 (`docker-compose`).
   `podman compose` has no compose implementation of its own: it forwards to that program, which talks to Podman; the
   Docker Engine itself isn't needed. `podman compose version` should print
   `Executing external compose provider ".../docker-compose"`; the separate `podman-compose` project hasn't been verified
   with BrickKit.
2. *compose*: `systemctl --user enable --now podman.socket` — `brickkit up`, `down` and `status` reach Podman through it.
3. `sudo loginctl enable-linger <user>` — the user's services keep running after logout, and start at boot without
   anyone logging in. Both ways need it: the units are the user's services too.
4. *compose*: `systemctl --user enable podman-restart.service` — starts the containers again at boot.
5. *compose*: make that unit wait for the network. It is written `After=network-online.target`, which means nothing in
   the user's systemd: when the network comes up late (Wi-Fi, a slow DHCP), Podman's network helper starts without an
   address and the containers never reach the host. Podman ships `podman-user-wait-network-online.service` for this; add
   it with a drop-in (Quadlet units depend on it by themselves):

   ```bash
   mkdir -p ~/.config/systemd/user/podman-restart.service.d
   printf '[Unit]\nWants=podman-user-wait-network-online.service\nAfter=podman-user-wait-network-online.service\n' \
     > ~/.config/systemd/user/podman-restart.service.d/wait-network.conf
   systemctl --user daemon-reload
   ```

6. Where AppArmor restricts unprivileged user namespaces (Ubuntu 23.10 and later:
   `sysctl kernel.apparmor_restrict_unprivileged_userns` prints `1`), Podman needs the AppArmor profile the apparmor
   package ships for it, `/etc/apparmor.d/podman`. Without it Podman fails at boot, over ssh and from a plain terminal
   with `failed to reexec: Permission denied`, while a terminal inside a snap may still work. Check from the user's
   systemd: `systemd-run --user --wait --pipe podman unshare cat /proc/self/attr/current` prints `podman (unconfined)`;
   if not, restore the profile
   ([how](../../docs/en/10-troubleshooting/01-up-down-issues.md#podman-fails-with-failed-to-reexec-permission-denied)).
7. Podman's storage on a disk mounted with `nofail`: systemd doesn't then guarantee it is mounted before the user's
   systemd starts. Add `RequiresMountsFor=<that mount point>` under `[Unit]` with `sudo systemctl edit user@<uid>.service`.
8. A port below 1024 (`exposePort: 443`, say) can't be published by a rootless engine as is: publish a port from 1024
   up and let the gateway in front take 443, or lower `net.ipv4.ip_unprivileged_port_start` on the host.
9. Run the [environment check](../../docs/en/10-troubleshooting/01-up-down-issues.md#podman-run-the-environment-check-first) once,
   with `--units quadlet` for Quadlet units: it tests that Podman can create its user namespace where systemd runs it, that
   containers can reach each other and be removed cleanly, and warns about any of steps 1, 3–5 and 7 that is missing.

Verified with BrickKit: rootless Podman with compose on a machine that also has Docker, including a real reboot with
steps 1–7 in place (Ubuntu 26.04, Podman 5.7.0, Wi-Fi by DHCP; all 12 components healthy without anyone logging in or
running `up`). A machine with only Podman hasn't been verified end to end.

### Kubernetes

For a cluster you already have, or when you need self-healing and scaling across machines. What it costs:

- **The cluster's own resources.** On one node, the control plane and kubelet are a fixed cost (about 2 GiB in
  [the measurement](#the-engines-the-platforms-own-cost)): a single-node cluster for a small project mostly buys that cost.
- **Operations.** It needs real cluster administration, and the machine running `up` needs `kubectl` and a context that
  reaches the cluster (`k8s.context`).
- **A crash.** The Pod is restarted and ready again within a few seconds; requests sent to it meanwhile wait or fail.

Processes on this machine don't combine with `k8s`: `mode: debug` / `mode: local` meeting `target: k8s` is refused while
loading, the error pointing at the offending entry (`components[N].mode`) — a Pod in the cluster can't reach your
machine. The same goes for `podman.units: quadlet`: the units outlive any `up`, a process on this machine doesn't.

### Coming back after a reboot

Containers are the shape that keeps running: the engine restarts a crashed container and starts them again at boot. What
has to be in place for each:

| Engine | After a crash | At boot |
| --- | --- | --- |
| Docker | `restart: unless-stopped`, generated | The Docker service enabled at boot (most packages do it; check with `systemctl is-enabled docker`) |
| Podman, Quadlet units, rootful | `Restart=always`, generated; unhealthy is killed and restarted | Nothing to enable; next to Docker, the unit that puts Podman's firewall rules back; its storage mounted in time ([steps 4, 7](#setting-up-a-host-for-rootful-podman)) |
| Podman, Quadlet units, rootless | `Restart=always`, generated; unhealthy is killed and restarted | Linger for the user, Podman able to create its user namespace, its storage mounted in time ([steps 3, 6, 7](#setting-up-a-host-for-rootless-podman)) |
| Podman, compose, rootful | `restart: always`, generated | The system unit `podman-restart.service` enabled; next to Docker, the unit that puts Podman's firewall rules back; its storage mounted in time ([steps 3, 4, 7](#setting-up-a-host-for-rootful-podman)) |
| Podman, compose, rootless | `restart: always`, generated | Linger for the user, the user unit `podman-restart.service` enabled and waiting for the network, Podman able to create its user namespace, its storage mounted in time ([steps 3–7](#setting-up-a-host-for-rootless-podman)) |
| Kubernetes | The kubelet | The cluster |

- With compose, Podman gets `always` because its boot unit starts only containers whose policy is `always`; otherwise the
  two policies behave the same in Podman. On Docker, `unless-stopped` keeps a container you stopped by hand stopped.
- What comes back is what the last `up` created. `down` removes the containers (and the units), so nothing comes back
  after it.
- With compose or Docker the engine starts the containers by itself at boot: not in the order `up` waits through
  (`depends_on`). Quadlet units keep the order: a component starts once the ones it needs are healthy. In neither case do
  the migrations run again — they ran at the last `up`, and a database that boots with the components is often not
  accepting connections yet. Either way a component that starts
  before its dependency is reachable must keep retrying rather than give up; it needs that anyway, for a dependency that
  restarts.
- Processes on this machine never come back: nothing restarts them or starts them at boot.

## Decision two: topology — how many containers do the components end up in?

- **All standalone**: each component its own container (or Pod). This is the shape you get by writing nothing extra.
- **All in shells**: as many components as can be merged are compiled into a few shells, one container per shell.
- **Mixed**: some in shells, some standalone. This is usually the norm, not a compromise: some components **structurally**
  can't go into a shell — a pure frontend served by nginx has no backend process to compile in; a stateless gateway is
  often kept standalone on purpose, so it can scale on its own load.

A shell is itself an ordinary component (marked `kind: shell` in `brickkit.yaml`); the members it can host are written in
`shell.members` of its `component.yaml`, and **which it hosts this time** is written in the deploy file — member entries
nested under the shell entry's `members`. So topology is decided **per deploy file**: the development machine's
`deploy.yaml` can be all standalone while production's `deploy.prod.yaml` gathers a few members into shells, without a word
of `config/` changing.

**When to merge.** Each process's memory floor is almost entirely set by its language runtime — Go / Rust 8–20 MB,
Python / Node 40–90 MB, JVM 200–450 MB (typical orders of magnitude; measure your own components). Twenty idle Go
components add up to under half a GB; twenty idle Spring Boot components already take 4–9 GB without doing anything. Stay
all standalone until that sum really doesn't work out on the machine you deploy to, and before merging try cheaper things
first: give the expensive components a lighter runtime (compiling JVM components into GraalVM native images drops the
memory floor from hundreds of MB to tens, with the deployment shape unchanged); check whether the components driving the
number up could be `mode: disable` this time anyway.

**What merging saves** ([measured](#all-standalone-all-in-shells-mixed-the-components)): about a third of the components'
memory and 14–28% of their CPU, with no difference in latency; the whole stack's memory hardly moved, because the
infrastructure is the largest part and a shell's database connections are bigger
([why](#why-the-components-save-and-the-whole-stack-doesnt)). Merging reliably saves CPU and processes; for memory,
it pays most with heavy runtimes.

## The matrix: topology × where it runs

|  | One machine (Podman / Docker) | Kubernetes |
| --- | --- | --- |
| **All standalone** | [1. The standard shape while one machine is enough](#1-all-standalone--one-machine) | [2. The most generous end](#2-all-standalone--kubernetes) |
| **All in shells** | [3. Squeezing memory when one machine isn't enough](#3-all-in-shells--one-machine) | [4. The tightest end](#4-all-in-shells--kubernetes) |
| **Mixed** | [5. Where most real projects end up](#5-mixed--one-machine) | [6. The middle ground on resources](#6-mixed--kubernetes) |

### 1. All standalone × one machine

**What it is**: one container per component — a Compose service, or a Quadlet unit with `podman.units: quadlet` — driven
end to end by `brickkit up`: address injection, health checks, starting in dependency order, migrations.

**When**: the default shape while one machine can hold the components (see [When to merge](#decision-two-topology--how-many-containers-do-the-components-end-up-in)).

**Upside**: every component can be started and stopped on its own, and trouble affects only itself; one component means
one container, one log, one health state — the simplest to troubleshoot.

**Cost**: every component pays its own runtime memory floor — the very reason shells exist; a single-machine shape, with no
scheduling across machines.

**Worth knowing**: measure before deciding "it doesn't fit" (`podman stats`, `docker stats`); don't take numbers off the
table — a 50-component project may run only a few, because most are `mode: disable` this time, or nothing needs them.

### 2. All standalone × Kubernetes

**What it is**: one Deployment + Service per component, with addresses resolved by the cluster's native Service DNS.

**When**: the cluster has resources to spare, and there's no need to trade merging for a lower memory floor. Every
component keeps its own `replicas` and its own `resources`.

**Upside**: truly independent horizontal scaling; scheduling across machines and failure recovery work per component.

**Cost**: the highest operational complexity; many components means many Deployment / Service objects.

**Worth knowing**: on K8s, `expose: true` needs `hostname` (Ingress routes by domain name), and `exposePort` does
nothing; a missing `hostname` is stopped by `up --dry-run`. Addresses in `config/` that assume a single-machine container
network have to be changed when moving to K8s — giving different values per environment with the deploy file's `vars:` is
the least work.

### 3. All in shells × one machine

**What it is**: as many components as possible compiled into a few shells; one container per shell, and members
get no container of their own. A caller's `*_ENDPOINT` for a member is the member's own address,
`http://<member's service name>:<its own port>` — the same as when it runs on its own — and that name reaches the shell:
a network alias of the shell's container (on K8s, a Service selecting the shell's Pod). Caller code doesn't change, and
neither does the address when a member moves into or out of a shell.

**When**: when the memory sum of cell 1 really doesn't work out — not before.

**Upside**: a shell carries one runtime floor and one connection pool, not N; fewer containers, faster start-up, fewer logs
to watch and fewer things to restart.

**Cost**: members sharing a shell share a failure domain (one crash restarts the whole shell, unless the shell is built
very carefully) and a unit of scaling (one member can't get extra replicas on its own); upgrading one member means
rebuilding the shell.

**Worth knowing**:
- Members' migrations **are still run by the platform**: with the member's own image and config, and the shell starts only
  once they succeeded (see [Migrations and shells](../../docs/en/05-migration/04-shell-interaction.md)). So every member must have an
  image of its own — except, with the shell running on this machine, a member compiled in from its local repository: it
  migrates from source (`local.migrationCommand`).
- For a shell image built on this machine, `brickkit build` records in a label which member versions it compiled in, and
  `up` compares that label with `shell.members` in the shell's `component.yaml`: a mismatch stops it (`IMAGE_STALE`),
  rather than a shell missing a member quietly starting. An image without the label (built by hand) only gets a warning
  (`IMAGE_UNVERIFIED`); pulled images aren't checked — a released version's image matches its `component.yaml` by
  construction.
- Fields on a member entry describing "how its own container is deployed" (`replicas`, `resources` and so on) do
  nothing inside a shell; they're kept for when the member falls back to a standalone component. `expose` is the
  exception: the shell opens the member's port (a mapping on the shell's container on one machine, an Ingress to the
  member's Service on Kubernetes).
- Merging can create a start wait cycle; `up` stops it and gives three ways out (see
  [Managing members](../../docs/en/04-shell/04-members-management.md#start-cycles-caused-by-merging-and-skipwaitfor)).

### 4. All in shells × Kubernetes

**What it is**: the same merging against a cluster: one Deployment per shell; one Service per member, whose `selector`
picks the shell's Pod and whose port is the member's own declared port; members generate no Deployment of their own.

**When**: the cluster's resources really are tight, and pushing the total cost down matters more than scaling a member on
its own.

**Upside**: both "merging saves memory" and "K8s self-healing and scheduling across machines". With network policies on, a
member's callers and dependencies are counted into the shell's rules automatically.

**Cost**: every cost of cell 3 holds unchanged; so does every K8s cost of cell 2 — merging doesn't lower K8s' own demands.

**Worth knowing**: Pods have no start order on K8s, so wait cycles caused by merging aren't stopped here, and `skipWaitFor`
only warns and does nothing; members' migrations are still their own Jobs.

### 5. Mixed × one machine

**What it is**: some standalone containers, some in shells, all driven by one `brickkit up`. Who is where is decided
entirely by where entries sit in the deploy file (at the top level, or under a shell's `members`).

**When**: where a mature project usually ends up, and usually **structurally**, not as a resource compromise — components
like frontends and gateways don't belong in shells to begin with. It is also how a component that needs to be scaled,
upgraded or isolated on its own leaves a shell. When you're unsure which cell an on-premises delivery should use, this is
usually the answer.

**Upside**: standalone where independence is needed, memory saved everywhere else; both kinds of entry sit side by side in
one deploy file, with no special handling.

**Cost**: troubleshooting means carrying two mental models at once; the costs of the merged half and of the standalone half
each hold unchanged — mixing doesn't average them out.

**Worth knowing**: an old version of a component running standalone while a new version runs in a shell can coexist with
zero coordination (see [the end of this page](#versions-side-by-side-need-no-extra-care)).

### 6. Mixed × Kubernetes

**What it is**: cell 5's mixed topology against a cluster: standalone components each with a Deployment + Service,
members' Services pointing at the shell Pods.

**When**: resources neither tight nor generous: most components stay in shells to keep the total cost down, and the few
that really need their own replica count or resource quota are picked out and deployed on their own. Unlike cell 5, mixing
here is often a **resource-tuning** decision — a component that could structurally be merged perfectly well is split out
deliberately, to scale on its own.

**Upside**: the most flexible resource allocation; address resolution and network policies support mixing natively, with
no extra configuration.

**Cost**: the full K8s operational cost and the full merging cost at once; the most places to look when something goes
wrong: K8s itself, a shell's internal orchestration, ordinary containers.

## Off the main line: processes on this machine

Three ways run components as processes on this machine instead of in containers. All three are for development, demos
and trials; none is a delivery.

| Way | Who starts the processes | For |
| --- | --- | --- |
| [Containers plus a few processes](#containers-plus-a-few-processes): `mode: debug` / `mode: local` on some entries | You in your IDE (`debug`), or `up` (`local`) | Changing one or two components against the real rest |
| [Every component as a process](#every-component-as-a-process): `mode: local` on every entry | `up` | A demo or a trial on a machine without a container engine |
| [By hand, outside the platform](#by-hand-outside-the-platform) | You, without `brickkit up` | The fastest loop for one component; testing a shell's own orchestration |

What they have in common, against containers:

- **They don't keep running.** A `mode: local` process lives as long as the `up` session that started it: `Ctrl+C` or
  closing the terminal stops it, and one crash ends the session. Nothing restarts it or starts it at boot — BrickKit has
  no long-running process (see [`mode`](../../docs/en/01-three-layers/03-deploy-yaml.md#mode-whether-it-runs-and-how)).
- **The runtime is the machine's.** The process runs on the toolchain installed here, not one pinned by an image, so two
  machines can run a component on two versions of its language. Its source has to be on the machine.
- **What they cost** ([measured](#the-engines-the-platforms-own-cost)): the same CPU as containers. For a Go component
  the start command is `go run`, which stays resident beside the program it built; mixed with containers, the
  processes reach the containers through host ports, so the engine's port forwarding carries that traffic once more.

### Containers plus a few processes

**What it is**: everything is a real container except the components you marked `mode: debug` or `mode: local`. On
Podman this needs compose (`podman.units` left out): Quadlet units refuse processes on this machine.

- `mode: debug`: you start the process in your IDE, and the platform only makes sure others can find it. It can only be
  written in the personal `deploy.local.yaml`.
- `mode: local`: the platform recognises the start command from the component's source, starts the process (after its
  migration from source, when the component declares `local.migrationCommand`) and supervises it for as long as that `up`
  runs.

The platform makes the other containers resolve that component's versioned service name to your machine (`extra_hosts`
pointing at `host-gateway`). Callers keep the same service name — `extra_hosts` only changes where it resolves — and the
port becomes your `localPort`, which by default is the component's declared port, so often nothing in the address changes.

**When**: you want "the rest is real" and also "no image rebuild for changing this one component". It's only a
development-time overlay; it doesn't decide the production topology. It works with every topology on one machine:

- **The rest standalone**: the simplest; everything the process depends on gets the real addresses the platform works out.
- **The rest in shells**: a process on this machine depending on a member gets a real `http://localhost:<port>` — the
  mapping is opened on the **shell's** Compose service (the member has no service of its own), on the port the member
  declares, which the shell must listen on anyway. A member itself can be pulled out: in `deploy.local.yaml`, write
  `mode: debug` and `localPort` on that member under the shell entry's `members`; the shell doesn't host it this time —
  the shell must handle one item fewer in `BRICKKIT_SERVED_MEMBERS` correctly.
- **The rest mixed**: the closest thing to "debugging against production" without touching production, because the rest
  is the project's real shape; it also means understanding shell merging, the addresses of processes on this machine
  and ordinary containers at once.

**Upside**: zero changes to component code; several components can be pulled out at once, each with its own `localPort`;
you don't need to know which shell a member is in.

**Cost**: when something can't connect, first ask "does this name resolve to my machine or to a container", rather than
checking the network in general; container-network addresses written by hand in `config/` aren't rewritten.

**Worth knowing**: a `mode: debug` component gets a `local-debug.<service name>.env` for the IDE to load, with multi-line
values and values holding special characters already escaped by shell rules. Its **database migration isn't run for you** —
the migration step went away together with its container; you run it from source, with the command the component
declares in `local.migrationCommand` (see [When no migration container runs](../../docs/en/05-migration/01-migration-service.md#when-no-migration-container-runs)).

### Every component as a process

**What it is**: every entry `mode: local`. `up` starts no container engine at all; it runs each component's migration
from source, starts the processes and watches them in the foreground. Infrastructure the components need (a database,
say) has to be reachable from this machine.

**When**: someone wants to see the project run once, or try it, on a machine where they don't want to install or set up a
container engine: one `up` to start it, `Ctrl+C` to stop it.

**Upside**: no engine, no images, no build step; the same CPU as containers.

**Cost**: every limit above, for the whole project: it stops with the session, the toolchain of every component's
language must be installed, and nothing about it survives a reboot. When it has to keep running, move it to containers —
the deploy file loses its `mode: local` lines and `config/` stays as it is.

### By hand, outside the platform

Nothing stops you from starting every component as an ordinary process (`go run`, `uvicorn`, or your language's
equivalent), without going through `brickkit up` at all.

**The boundary first: this isn't a shape the platform manages; the platform doesn't even know it exists.** Dependency
resolution, environment variable injection, health checks, migration order and service discovery all don't happen,
because you didn't call it. Which port each process listens on, every variable a real deployment would inject, the start
order — you reconstruct all of it yourself. That's a direct consequence of "the CLI exits when done, with no long-running
service": the platform exists only while a command runs.

It's still entirely legitimate and very common — usually the fastest development loop (no images to build, breakpoints
attach directly). It takes three forms, by topology:

- **All standalone**: the most common starting point for developing one component, especially while the project has no
  shells yet. No container layer between a process and the addresses it connects to, so a problem has only two variables
  to check.
- **A shell alone**: the shell's own program started straight on your machine, to test its multi-module orchestration —
  start order, health check, failure isolation between modules — without the container layer; needed almost only by
  whoever builds shells. `BRICKKIT_SERVED_MEMBERS` / `BRICKKIT_SERVED_MEMBERS_CONFIG` are yours to assemble (their exact
  shape is in [Config as JSON](../../docs/en/04-shell/02-json-injection.md)), so it proves only that the shell behaves right on data
  you assembled. The module registry inside a shell should be keyed by **the full component ID plus version**, so that a
  real deployment can host two versions of one component at once — a trap that only shows up when two versions really
  are fed in, worth practising on purpose here.
- **Mixed**: once the production topology uses shells, start the few components you're changing in their real shapes —
  standalone components alone, shells as above. Reconstructing the real shape lets you hit shape-related bugs locally;
  nothing checks that the "who is where" you set up by hand agrees with the deploy file.

**A trick worth knowing: have the CLI work out the environment variables for you.** In `deploy.local.yaml`, temporarily
mark the component you'll run by hand `mode: debug`, run `brickkit up --dry-run` once, and read the generated
`.brickkit/generated/local-debug.<versioned service name>.env` — exactly the full set of variables a real deployment would
give it. For instance, `shop/order` depending on the shell member `shop/stock`:

```text
COMPONENT_ID=shop/order
COMPONENT_VERSION=0.1.0
PORT=8083
SHOP_STOCK_ENDPOINT=http://localhost:18082
```

Copy what you need, then delete that line (or `brickkit local off`). `deploy.local.yaml` is never committed anyway, so it
affects no one. One thing the trick doesn't cover: addresses you wrote by hand in `config/` that name another container's
service — the platform doesn't parse config values and won't rewrite them for you, just as with `mode: debug` itself.
The one exception is `host.docker.internal`: a process on your machine receives `localhost` instead, unless your machine
resolves that name to a loopback address.

## Versions side by side need no extra care

No shape on this page changes how several versions of the same component coexist. Versioned service names make coexistence independent
of topology and of deploy target: old callers and new ones, a version running standalone and a version in a shell, can all
coexist in one deployment. The platform doesn't check whether old and new versions work together correctly — keeping
contracts compatible is the component author's responsibility (see
[Several versions side by side](../../docs/en/03-component-guide/09-multi-version-coexistence.md)).

## Comparing two environments

Each environment has one complete deploy file, so comparing two environments needs no dedicated command; two ordinary
`diff`s are enough:

1. `diff -u deploy.yaml deploy.prod.yaml` shows **what you wrote differently**.
2. A `diff` of two `up --dry-run` outputs shows **what those differences lead to** — which components don't start as a
   result, and why.

Real output below: `demo/caller` requires `demo/hello` and optionally depends on `demo/bus`; the production file switches
to `k8s` and turns `demo/hello` off:

```text
$ diff -u deploy.yaml deploy.prod.yaml
--- deploy.yaml
+++ deploy.prod.yaml
@@ -1,10 +1,8 @@
-# deploy.yaml — how this project is deployed: the target, and which components run and how.
-# The team file: commit it. Your personal copy is deploy.local.yaml (brickkit local on).
-target: docker # docker | podman | k8s
-
+target: k8s
 components:
   - id: demo/hello
+    mode: disable
   - id: demo/bus
   - id: demo/caller
     expose: true
-    exposePort: 18080
+    hostname: shop.example.com
```

```text
$ diff <(brickkit up --dry-run 2>&1 | grep -v '^{') \
       <(brickkit up --dry-run -f deploy.prod.yaml 2>&1 | grep -v '^{')
1c1,2
< 🚀 Starting project my-shop (target: docker)
---
> Using deploy.prod.yaml (--file)
> 🚀 Starting project my-shop (target: k8s)
3,5c4,6
<    ✅ demo/hello@1.0.0   starting (demo/caller needs it)
<    ✅ demo/bus@1.0.0     starting (demo/caller needs it)
<    ✅ demo/caller@1.0.0  starting (top-level)
---
>    ⬜ demo/hello@1.0.0   disabled explicitly (mode: disable)
>    ⬜ demo/bus@1.0.0     not starting (nothing above it is starting)
>    ⬜ demo/caller@1.0.0  not starting (required dependency demo/hello is not starting)
```

(The second `diff` goes on with differences in start order and generated files, cut here.)

The second one gives the consequences directly: not only does `demo/hello` not start, `demo/caller` doesn't either (it
requires `demo/hello`), and `demo/bus`, with nothing above needing it, doesn't start. The `mode: disable` line in the first
`diff` alone doesn't tell you any of that.

- `grep -v '^{'` filters out the JSON log lines the CLI writes on stderr; otherwise they mix into the human-readable output
  and the `diff` is full of noise.
- What's compared here is **the start decision**, not the generated deployment files themselves: one side is
  `compose.yaml`, the other a set of Kubernetes manifests, which can't be compared line by line anyway.

# up / down problems

`up` works in a fixed order: load and check the three layers → decide who starts this time → resolve dependencies →
generate the deployment files → check images → run migrations → call the engine. Which step an error appears in roughly
tells you which layer the problem is in. The whole flow is in [Starting and stopping](../../docs/en/02-project-guide/06-up-and-down.md).

## Images don't exist

**Symptom**

```text
❌ Error: these images are built locally and have not been built yet
   demo/hello@1.0.0: demo-hello:1.0.0
   demo/caller@1.0.0: demo-caller:1.0.0
```

Or `Error: image pull not authorized`, `Error: image not found`.

**Cause and fix**

`up` never builds images. For images built on this machine, run `brickkit build` first; for pulled ones, make sure you're
logged in to the image registry and the address and tag are right. More in [Build problems](../../docs/en/10-troubleshooting/05-build-issues.md).

## A required config item is missing

**Symptom**

```text
❌ Error: a required component config item has no value
   Missing config: demo/widget@0.1.0 → API_URL
   Reason: The component declares it in configSchema.required without a default — the platform can't derive this one, so the project has to supply it
   Suggestions:
   1. Give it a value in config/demo-widget.yaml:
    API_URL: <value>
   2. The value may be ${ENV_VAR} (real value in .env), $var:NAME (shared, from config/vars.yaml) or file://path
```

**Cause**

The component declares a required config item with no default — usually an address the platform can't work out (a
service deployed by another project) or a credential. With it missing, the component would still start and look healthy,
yet have a call path that never works; so the platform stops it before starting, instead of letting it slip through quietly.

**Fix**

Fill it in in `config/<component>.yaml`, as the suggestion says. For a component just `upgrade`d, required items the new
version added appear in the config file as `KEY: ""`, and need filling in too.

## Port conflicts

**Symptom one: two components want the same host port.**

```text
❌ Error: deploy.yaml failed validation
   File: deploy.yaml
   components[2].exposePort: conflicts with components[0].exposePort (host port 18080 is already taken)
   Suggestion: Full field reference: brickkit docs 11-reference/03-deploy-yaml-schema (online: https://github.com/brickKit/brickKit/blob/v1.1.0/docs/en/11-reference/03-deploy-yaml-schema.md)
```

**Fix**: give one of them another `exposePort` (or `localPort`).

**Symptom two: another program on this machine holds the port.** Validation passes, then `docker compose` fails to start
the container, with `port is already allocated` or `address already in use` in the engine's output.

**Fix**: find the program holding it (`ss -ltnp | grep <port>`) and stop it, or pick another `exposePort`.

For a `mode: local` process, `up` finds this out before starting any of them, and starts none:

```text
❌ Error: another program on this machine already holds a port a mode: local process needs
   Port 8083: demo-gamma-0-1-0: another program already answers on it
   Suggestions:
   1. Stop the program holding it, then run up again; none of the mode: local processes was started
   2. Or move the process to another port: write localPort on its entry in the deploy file (ports declared in component.yaml can't be moved)
```

The containers have started by then; only the local processes wait. A port in `extraPorts`, or one a shell listens on
for a member, is declared in `component.yaml`: free it on your machine.

**Symptom three: two components on a shell use the same port** — see
[Shell problems](../../docs/en/10-troubleshooting/06-shell-issues.md#two-components-on-a-shell-want-the-same-port).

**Symptom four: a component with several replicas needs a host port.**

```text
❌ Error: demo/hello@1.0.0 has 2 replicas, yet needs host ports — a host port maps to one container only
   Host ports: 18080:8080
   Suggestion: A process on this machine (mode: local / debug) reaches it through a host port: set replicas: 1 for it in the deploy file this run reads (deploy.local.yaml in local mode), or run that caller in a container too
```

On Docker / Podman a host port maps to one container only. The port comes either from the component's own `expose` or
from a process on this machine that reaches it; the suggestion matches the source.

**Fix**: do as the suggestion says. When it's only you debugging on your machine, write `replicas: 1` in
`deploy.local.yaml` and leave the team's `deploy.yaml` alone.

## A migration fails

**Symptom**

```text
❌ Error: database migration failed
   Component: shop/stock@0.2.0
   View logs: docker compose -p brickkit-shop logs shop-stock-0-2-0-migration
```

**Cause and fix**

The migration exited non-zero, so the main service won't start. Read the migration container's logs as the suggestion
says, fix it, and `up` again; the migration runs once more. More in [Migration problems](../../docs/en/10-troubleshooting/07-migration-issues.md).

With `podman.units: quadlet` the error names the migration's unit and its log (`journalctl [--user] -u <unit>`), and `up`
stopped before installing any component's unit: they keep running their previous version, after a reboot too.
`brickkit status` keeps saying that the last migration failed until one succeeds (or the machine restarts).

## The component's logs look fine, yet the platform says it's unhealthy

**Symptom**

`up` waits to the end and reports `Error: some components did not start properly`, or the components depending on it never
start. Meanwhile the component's own logs say it's ready and listening on its port.

**Cause**

On Docker and Podman (compose and Quadlet units alike), the health check runs **inside** the container, through the image's `/bin/sh`. For `type: http` it's:

```text
wget -q -O /dev/null http://127.0.0.1:8080/healthz || curl -fsS -o /dev/null http://127.0.0.1:8080/healthz || exit 1
```

and for `type: tcp` it's `nc -z 127.0.0.1 8080`. So `type: http` needs `/bin/sh` plus `wget` or `curl` in the image, and
`type: tcp` needs `/bin/sh` plus `nc`. When they're missing, the command always fails and the container is always judged
unhealthy — however healthy the component itself is. `scratch` and distroless images have no shell at all, so **neither
type** can pass there; images based on `busybox` or `alpine` have all of it. Another common cause: a wrong health check
path (`healthCheck.path` in `component.yaml` differs from what the component actually serves).

Both commands send `GET`, as a Kubernetes `httpGet` probe does, so the path only has to answer `GET`. The check
doesn't use `wget --spider` because that sends `HEAD` with GNU wget — the one Debian and Ubuntu images install — and
`GET` with BusyBox's, so a component with only a `GET` route would be healthy on Alpine and never on a Debian-based image.

The check goes to `127.0.0.1`, not `localhost`: inside a container `localhost` points at both `127.0.0.1` and `::1`,
Alpine's `wget` and `nc` pick `::1`, and a server listening only on `0.0.0.0` (the usual way in Python and Node) has
nothing answering on IPv6. So the component has to listen on `0.0.0.0` or `::` — one listening only on `localhost`
couldn't be reached from other containers anyway.

On Kubernetes this problem doesn't exist: the probes (`httpGet`, `tcpSocket`) are sent by the kubelet from outside the
container and need nothing in the image.

**Fix**

- Look at the container's health-check record: `docker inspect --format '{{json .State.Health}}' <container name>`; the
  output of the last few entries says `wget: not found`, `nc: not found` or that `/bin/sh` doesn't exist.
- Check what the image has: `docker run --rm --entrypoint sh <image> -c 'command -v wget curl nc'` (when even this fails,
  the image has no shell).
- Give the image the tools: build the final stage on `busybox` or `alpine` (a few MB; they carry `sh`, `wget` and `nc`).
  Switching from `http` to `tcp` only helps when the image has `nc` but neither `wget` nor `curl`.
- If the image must stay without a shell, `healthCheck.type: none` is the remaining choice: components depending on it
  then wait only for its container to start, not for it to be ready, and on Kubernetes it gets no probes either — so they
  have to retry on their own while it comes up.
- When the path doesn't match, change `healthCheck.path`.
- When the output is `Connection refused` and the component is running: look at the address it listens on
  (`docker exec <container name> netstat -ltn`). It has to be `0.0.0.0:<port>` or `:::<port>`, not `::1` or one specific
  address other than `127.0.0.1`, and the port has to be `deployment.port`: the platform passes it as `PORT`, so code that
  listens on `PORT` can't drift from the manifest the way a port hard-coded in the code or the image can.

## A component with a cold start over a minute is judged failed

**Symptom**

A slow-starting component (a heavy Spring Boot app, a Django project that preloads a lot, .NET's first JIT pass): on
Docker, `up` reports it unhealthy; on Kubernetes the Pod keeps restarting, stuck in `CrashLoopBackOff`. And the container's
own logs look perfectly normal throughout — it just hasn't finished starting yet.

**Cause**

The health check's rhythm is fixed by the platform: every 10 seconds, a 3-second timeout, 3 failures in a row means
unhealthy. The platform gives every component a 60-second start-up grace period, during which failures don't count. With a
cold start over 60 seconds, it isn't ready when the grace period ends and is declared dead; on Kubernetes it's killed and
restarted, starts over from scratch, and never comes up.

**Fix**

Raise the grace period in the component's `component.yaml`, with room to spare:

```yaml
healthCheck:
  type: http
  path: /healthz
  startPeriodSeconds: 180
```

The grace period only delays "declaring it dead", never "declaring it alive": a component ready in two seconds still turns
healthy in two seconds, so setting it generously costs nothing.

## `up` hangs, and the migration container keeps running

**Symptom**

`up` never returns. In `docker compose -p brickkit-<project> ps` the main service sits at `Created` while the migration
container is `running`; the migration container's logs say the service is ready and listening on its port.

**Cause**

The migration container and the main service run the same image, differing only in the command argument. When the
component's entry program meets an argument it doesn't know (`migration.command` misspelled), it doesn't exit with an
error — it **starts the service as usual**. The migration container becomes a second service that keeps running and never
finishes; the main service waits for it to "finish successfully" before starting, and waits forever.

**Fix**

- The entry program must fail and exit at once (with a non-zero exit code) on an argument it doesn't know; see
  [The migration container](../../docs/en/05-migration/01-migration-service.md). Check this **before** reading environment variables
  or connecting to the database, or a misspelled argument shows up as a misleading "can't connect to the database".
- Check the spelling of `migration.command`.
- `Ctrl+C` first, then `brickkit down` to clear the stuck containers.

## `docker compose logs` shows nothing

**Symptom**

The component is clearly running, yet `docker compose logs` prints nothing, or says it can't find the service.

**Cause**

`docker compose` finds containers by **project name**. The Compose project name BrickKit generates is
`brickkit-<project name>`, while running it directly in the project directory, Compose uses the directory's name and looks
at another (empty) project.

**Fix**

Add `-p`:

```bash
docker compose -p brickkit-my-shop logs -f demo-caller-1-0-0
```

The "View the logs" line `up` prints at the end is the right command. With `podman.units: quadlet` there is no Compose
project: the logs are in journald, `journalctl --user -u 'brickkit-<project name>_<service name>*'` (without `--user`
for rootful Podman), and `podman logs <container>` shows the same.

## Deployed to the wrong cluster (or nearly)

**Symptom**

```text
❌ Error: the cluster currently connected is not the one the configuration specifies
   Required by the deploy file (k8s.context): prod-cluster
   Current context: dev-cluster
   Suggestions:
   1. Switch to it: kubectl config use-context prod-cluster
   2. If dev-cluster is where you mean to deploy: use a deploy file whose k8s.context names it (brickkit up -f <file>)
   3. Don't continue until you are sure — deploying to the wrong cluster can't be undone
```

**Cause**

The deploy file's `k8s.context` names one cluster while `kubectl`'s current context is another. Deploying to the wrong
cluster can't be taken back, so `up` checks first and stops when they don't match.

**Fix**

`kubectl config use-context <the one in the deploy file>`, or use the deploy file naming the current cluster (`-f`).
There's no command-line flag to switch clusters for one run: one deploy file per cluster.

## Podman: run the environment check first

With the deploy target `podman`, the problems in the next few sections all come from the host's environment; none is a
BrickKit or Podman bug. When you hit any of them, or the first time you use Podman on a machine, run:

```bash
scripts/podman/check-environment.sh                  # podman.units left out: compose
scripts/podman/check-environment.sh --units quadlet  # podman.units: quadlet
```

**Run it as the user that runs `brickkit up`.**
Give the script's `--units` the deploy file's `podman.units`: compose needs `podman.socket` and a boot unit, Quadlet units
need Podman 5.3 or later and neither of those. Podman runs in two ways, and their environment problems differ:

- **Rootless** (run as a normal user): a helper process called `pasta` connects containers to the network in user space,
  without going through the host's firewall forwarding.
- **Rootful** (run as root): containers hang off a bridge on the host (netavark names them `podman0`, `podman1`, … by
  default), and traffic between containers goes through the host's forwarding chain.

Run as a normal user, it checks rootless Podman; run as root, rootful. It's essentially read-only; to get real answers it
starts a few throwaway test containers and one test network — you can't tell from configuration files alone, since what
gets blocked depends on the policy and firewall rules currently loaded in the kernel. It checks, in order: whether
`$XDG_DATA_HOME` is redirected by snap, whether rootless Podman can create its user namespace where the boot unit starts it
(see [below](#podman-fails-with-failed-to-reexec-permission-denied)), whether `podman.socket` is on, whether two
containers on one network can reach each other, and whether a container can be removed cleanly. Last, as warnings only,
what a deployment needs to [come back after a reboot](#the-containers-dont-come-back-after-a-reboot): linger, the boot unit
enabled and waiting for the network, Podman's storage mounted in time, and for rootful Podman next to Docker the unit that
puts the firewall rules back. Exit code `0` is fine, `1` means one of the known
problems below reproduced, `2` means the check itself couldn't run (Podman not installed, say).

**Two further prerequisites**

- **A terminal opened from a snap-packaged application** (VS Code installed as a snap, say) redirects `$XDG_DATA_HOME` to a
  versioned path, and after a Podman upgrade Podman reports `database configuration mismatch`. `check-environment.sh`
  flags it; the fix is setting `export XDG_DATA_HOME="$HOME/.local/share"` and `export XDG_CONFIG_HOME="$HOME/.config"` in
  your shell's start-up file.
- **`podman compose` should use Docker's own Compose V2 plugin.** `podman compose` has no compose implementation of its
  own; it only forwards to an external program it finds. Run `podman compose version`: `Executing external compose
  provider ".../docker-compose"` means that route; when it shows the separate `podman-compose` project, working with
  BrickKit hasn't been verified. What's verified is rootless and rootful Podman each on a machine that also has Docker,
  with it forwarding to Docker's Compose plugin; rootful Podman next to Docker needs Podman's bridges let through Docker's
  firewall chain, see [the section below](#all-healthy-on-podman-yet-calls-between-containers-time-out).

## `up` fails on Podman: `failed to connect to the docker API`

**Symptom**

The deploy target is `podman`, and `up` (or `down`, `status`) fails straight away, with one of these in the engine's
output (`up` gives the first, `down` and `status` the second):

```text
failed to connect to the docker API at unix:///run/user/1000/podman/podman.sock; check if the path is correct and if the daemon is running
Cannot connect to the Docker daemon at unix:///run/user/1000/podman/podman.sock. Is the docker daemon running?
```

Run as root, the path is `unix:///run/podman/podman.sock`.

**Cause**

`podman compose` hands the call to Docker's Compose plugin, which talks to Podman through Podman's API socket. That socket
isn't on by default. Rootless and rootful Podman each have their own: the rootless one lives under `/run/user/<uid>/` and is
a user-level systemd unit; the rootful one is `/run/podman/podman.sock`, a system-level unit. Turning on the wrong one
leaves the error unchanged.

**Fix**

BrickKit recognises this error and adds the matching command, picked by the path in the error, to its suggestions:

```bash
systemctl --user enable --now podman.socket        # rootless
sudo systemctl enable --now podman.socket          # rootful
```

## All healthy on Podman, yet calls between containers time out

**Symptom**

The deploy target is `podman`, run as root (rootful), and Docker is installed on the same machine. `up` succeeds, every
component is healthy, `status` is all green, yet every call between containers times out, and so do calls from a container
to a port mapped on the host; calls from a container to a process on the host (a `mode: local` component) work. Nothing
reports an error: a health check only looks at the component itself, not at whether it can reach anything else.

**Cause**

When Docker starts, it sets the default policy of the host firewall's `FORWARD` chain to `DROP` and lets through only the
traffic on its own bridges. Traffic between rootful Podman's containers goes through that same forwarding chain, so it's
dropped. netavark accepting it in its own rule table doesn't help: at the same forwarding step, a drop anywhere is final.

Rootless Podman isn't affected: `pasta` forwards its traffic in user space, never through the host's `FORWARD` chain.

Run as root, `check-environment.sh` actually tries two containers reaching each other; when that fails while the `FORWARD`
policy is `DROP` and Docker's `DOCKER-USER` chain exists, it recognises this problem.

**Fix** (any one)

1. **Let Podman's bridges through in Docker's `DOCKER-USER` chain.** Docker keeps that chain for exactly this, your own
   rules:

   ```bash
   sudo iptables -I DOCKER-USER -i podman+ -j ACCEPT
   sudo iptables -I DOCKER-USER -o podman+ -j ACCEPT
   ```

   The rules are lost on reboot, and Docker rebuilds its chains at every start, so they have to go back in after Docker
   starts and before Podman's boot unit starts the containers. A one-shot unit does that (BrickKit doesn't touch the
   host's firewall; this is one way, checked with a real reboot):

   ```bash
   sudo tee /etc/systemd/system/podman-docker-forward.service >/dev/null <<'UNIT'
   [Unit]
   Description=Let rootful Podman's bridges through Docker's DOCKER-USER chain
   After=docker.service
   Before=podman-restart.service

   [Service]
   Type=oneshot
   RemainAfterExit=yes
   ExecStart=/bin/sh -c 'for d in -i -o; do iptables -C DOCKER-USER $d podman+ -j ACCEPT 2>/dev/null || iptables -I DOCKER-USER $d podman+ -j ACCEPT; done'

   [Install]
   WantedBy=multi-user.target
   UNIT
   sudo systemctl daemon-reload
   sudo systemctl enable --now podman-docker-forward.service
   ```

   It adds each rule only when it's missing, so running it again changes nothing. At boot it runs right after Docker, and
   Podman's boot unit right after it; units generated with `podman.units: quadlet` are ordered after it by themselves. Where the host's firewall is managed by something else (firewalld, a saved
   `iptables` rule set), put the two rules there instead; the
   [environment check](#podman-run-the-environment-check-first) warns when this unit isn't enabled.
2. **Use rootless Podman**, running `brickkit up` as a normal user.
3. **Don't run rootful Podman and Docker on the same machine.**

## `down` fails on Podman: `permission denied`

**Symptom**

The deploy target is `podman`. `up`, `status` and ordinary requests all work, yet `down` (or `up` when it cleans up
leftover containers) fails, with this in the engine's output:

```text
Error: removing container ...: 1 error occurred:
	* rootless netns: kill network process: permission denied
```

BrickKit recognises this signature and adds a line to the error's suggestions:

```text
This is a known Ubuntu/Debian AppArmor gap blocking rootless Podman's network teardown (containers/podman#27372), not a BrickKit or Podman bug — the fix: brickkit docs 10-troubleshooting/01-up-down-issues (online: …)
```

On an affected machine it reproduces **every** time; it isn't intermittent. The container itself is usually already gone
(Podman falls back to `SIGKILL`), but network resources may not be released, and the command exits with a failure — easy to
mistake for "it didn't stop at all this time".

**Cause**

Rootless Podman connects containers on a bridge network through one shared `pasta` process. When the last of those
containers goes, Podman sends `pasta` a `SIGTERM` so it tears the network down. `pasta` runs under the AppArmor profile
the passt package ships (`/etc/apparmor.d/usr.bin.pasta`), and that profile doesn't allow receiving a signal from the
`podman` profile, so the kernel refuses it — in the kernel log:
`apparmor="DENIED" operation="signal" ... profile="pasta" ... signal=term peer="podman"`. It's a gap in how the
distribution packages its security policy; Podman upstream has exactly the same report
([containers/podman#27372](https://github.com/containers/podman/issues/27372)), and Debian has tracked the same error
([Debian #1100135](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1100135)).

**First, check whether you're affected**: run `scripts/podman/check-environment.sh` as a normal user (see
[above](#podman-run-the-environment-check-first)); it actually removes a test container. With no container running, it
reaches the network teardown; while a container holds the shared network — or a count left behind by an earlier failed
teardown says one does — it says it can't check, and how to clear that.

**The fix**

Add one rule to pasta's profile — receiving `SIGTERM` from `podman` — and load it:

```bash
sudo sed -i '/^profile pasta .*{$/a\  signal (receive) set=(term) peer=podman,' /etc/apparmor.d/usr.bin.pasta
sudo apparmor_parser -r /etc/apparmor.d/usr.bin.pasta
```

Verified on Ubuntu 26.04 (Podman 5.7.0, passt 0.0~git20260120), removing the last container on a bridge network: with the
profile as shipped, the teardown fails with the error above and the kernel logs the denied signal; with this rule, it
succeeds, and `pasta` stays enforced. The profile has no local include, so the rule goes into the packaged file: a later
passt upgrade asks whether to keep your version. Edit `usr.bin.pasta`, not `usr.bin.passt` — two binaries in one package
with near-identical names. Don't delete the `podman` AppArmor profile (`/etc/apparmor.d/podman`) for this: it doesn't take
part in the signal, and on Ubuntu 23.10 and later it is what lets Podman create its user namespace (see
[the next section](#podman-fails-with-failed-to-reexec-permission-denied)).

Putting `pasta` into complain mode (`aa-complain /usr/bin/pasta`) also makes the teardown succeed, but it stops enforcing
everything else in pasta's profile too; an earlier version of `fix-apparmor.sh` did that, and the current one switches it
back to enforce. The two commands above don't remove that flag. To start again from the profile as the package ships it,
delete the file and let apt put it back — `--force-confmiss` restores a missing configuration file, while a reinstall
alone (even with `--force-confnew`) leaves an edited one as it is — then add the rule:

```bash
sudo rm /etc/apparmor.d/usr.bin.pasta
sudo apt-get install --reinstall -o Dpkg::Options::=--force-confmiss passt
```

**When Podman needs more than this**, `scripts/podman/fix-apparmor.sh` does the same as part of a full reset. **Read it
before running it — it's destructive**: it deletes your existing Podman containers, images and volumes, reinstalls
`podman` with apt and regenerates the base configuration. It needs `sudo`, is verified only on Ubuntu / Debian, and
doesn't touch Docker. Besides the rule above, it restores the `podman` profile when it's missing, and handles three things
unrelated to this signal that likewise make `up` fail or hang: configuring default image registries in `registries.conf`
(otherwise pulling an image without a registry prefix, like `alpine:3`, fails, or pops up an interactive choice that
hangs a non-interactive `up`); setting `policy.json` (otherwise Podman refuses to pull any image); enabling the rootless
`podman.socket` (see [above](#up-fails-on-podman-failed-to-connect-to-the-docker-api)).

## Podman fails with `failed to reexec: Permission denied`

**Symptom**

The deploy target is `podman`, and every Podman call fails with this line — `brickkit up` (looking up images), `build`,
`podman-restart.service` at boot (in `journalctl --user -u podman-restart.service`), `podman info` from ssh or a plain
terminal:

```text
failed to reexec: Permission denied
```

The kernel log has the denial: `apparmor="DENIED" operation="exec" ... profile="unprivileged_userns" name="/proc/self/exe"`.
The same commands may still work in a terminal of an application installed as a snap (VS Code, say), and when a container
is already running. BrickKit recognises the line and adds a suggestion pointing here.

**Cause**

Ubuntu 23.10 and later restrict unprivileged user namespaces through AppArmor
(`sysctl kernel.apparmor_restrict_unprivileged_userns` prints `1`). Rootless Podman creates a user namespace and then
executes itself again; a process that has no AppArmor profile allowing `userns` is moved into the `unprivileged_userns`
profile when it creates one, and that profile refuses the second execution. The apparmor package ships such a profile
for Podman, `/etc/apparmor.d/podman` (`flags=(unconfined)` with `userns`); when it is missing or not loaded, Podman
fails wherever nothing else allows user namespaces. A snap's own profile allows them, and with a container running Podman
joins the existing namespace instead of creating one — which is why it can look fine from some terminals.

An earlier version of `scripts/podman/fix-apparmor.sh` deleted that profile, and a package upgrade doesn't bring back a
deleted configuration file.

**Fix**

Restore the profile the apparmor package ships (`--force-confmiss` restores missing configuration files,
`--force-confold` keeps the ones you edited), then load it:

```bash
sudo apt-get install --reinstall -o Dpkg::Options::=--force-confmiss -o Dpkg::Options::=--force-confold apparmor
sudo apparmor_parser -r /etc/apparmor.d/podman
```

Check from the user's systemd, where the boot unit runs Podman: `systemd-run --user --wait --pipe podman unshare cat
/proc/self/attr/current` should print `podman (unconfined)`. The environment check does the same. Turning the restriction
off for the whole machine (`kernel.apparmor_restrict_unprivileged_userns=0`) also works, but it lifts it for every
program, not just Podman.

## The containers don't come back after a reboot

**Symptom**

The deployment ran; after the machine restarted, `brickkit status` shows its components not running, or running but
failing their calls — and `brickkit up` brings them back.

**Cause**

BrickKit starts nothing at boot: the engine does, and only when it is set up to. Start with the boot unit's log —
`journalctl --user -b -u podman-restart.service` for rootless Podman (without `--user` for rootful Podman;
`journalctl -b -u docker` for Docker) — then find what you see below. With `podman.units: quadlet` there is no boot
unit: each unit starts by itself and waits for the network itself, so read the units' own log,
`journalctl --user -b -u 'brickkit-<project name>_*'` (without `--user` for rootful Podman). The rows about linger,
`failed to reexec` and the storage mount apply to it as well; the ones about the boot unit and the restart policy don't.

| What you see | Cause | Fix |
| --- | --- | --- |
| The boot unit has no entries at all (Docker: the daemon didn't start) | The engine isn't set to start at boot. Rootless Podman needs linger for the user (otherwise the user's services start only when someone logs in) and the user unit `podman-restart.service` enabled; rootful Podman the system unit; Docker the Docker service | `sudo loginctl enable-linger <user>` and `systemctl --user enable podman-restart.service`; rootful: `sudo systemctl enable podman-restart.service`; Docker: `sudo systemctl enable docker` |
| The boot unit failed with `failed to reexec: Permission denied` | AppArmor keeps Podman from creating its user namespace | [The section above](#podman-fails-with-failed-to-reexec-permission-denied) |
| The containers are up, but components keep restarting and can't reach anything on the host (`host.docker.internal`, ports published on the host) | Rootless Podman's network helper (`pasta`) started before the machine had an address, and it never picks one up later. The boot unit is written `After=network-online.target`, which means nothing in the user's systemd; Podman ships `podman-user-wait-network-online.service` for this, but the boot unit doesn't depend on it | Make the boot unit wait for the network (below); this time, stop and start the containers once — `systemctl --user restart podman-restart.service` does both, and the new `pasta` has the network |
| Rootful Podman next to Docker: all healthy, yet calls between containers time out — it worked before the reboot | The rules letting Podman's bridges through Docker's `DOCKER-USER` chain were lost: they live only in memory, and Docker rebuilds its chains at every start | The unit that puts them back after Docker: [All healthy on Podman, yet calls between containers time out](#all-healthy-on-podman-yet-calls-between-containers-time-out) |
| Podman reports no containers, or its storage missing | Podman's storage is on a disk mounted with `nofail`, which may mount after the boot unit starts (rootless: after the user's systemd starts) | Rootless: `sudo systemctl edit user@<uid>.service`; rootful: `sudo systemctl edit podman-restart.service`, or for Quadlet units the drop-in `/etc/systemd/system/brickkit-.service.d/storage.conf` ([step 7](../../docs/en/09-patterns/06-deployment-selection.md#setting-up-a-host-for-rootful-podman)); add `[Unit]` `RequiresMountsFor=<that mount point>` |
| A few components restart a couple of times right after boot, then turn healthy | At boot the engine starts the containers without the start order `up` waits through (`depends_on`); a component started before its dependency was reachable | Nothing — the restart policy keeps trying; a component should retry its connections rather than exit |
| Nothing came back, and `brickkit down` ran before the restart | `down` removes the containers; there is nothing to start | `brickkit up` |
| On Podman, the containers' restart policy is `unless-stopped` (`podman inspect -f '{{.HostConfig.RestartPolicy.Name}}' <container>`) | They were created by an older BrickKit; Podman's boot unit starts only containers whose policy is `always` | `brickkit up` once: it recreates containers whose restart policy changed |

The drop-in that makes the rootless boot unit wait for the network is step 5 of
[Setting up a host for rootless Podman](../../docs/en/09-patterns/06-deployment-selection.md#setting-up-a-host-for-rootless-podman).

`scripts/podman/check-environment.sh` reports each of the boot settings above as a warning when it's missing. The whole
setup, in order: [Setting up a host for rootful Podman](../../docs/en/09-patterns/06-deployment-selection.md#setting-up-a-host-for-rootful-podman),
[Setting up a host for rootless Podman](../../docs/en/09-patterns/06-deployment-selection.md#setting-up-a-host-for-rootless-podman).

## A Quadlet unit doesn't start

**Symptom**

The deploy file has `podman.units: quadlet`, and `up` fails with one of:

| What you see | Cause | Fix |
| --- | --- | --- |
| `these units did not start`, each with a `journalctl` command | The container started and exited, or never turned healthy within the unit's start limit | Read the unit's log with that command; `systemctl --user list-units --failed 'brickkit-<project name>_*'` lists every failed unit |
| `Podman <version> is too old for podman.units: quadlet` | The units use keys Podman 5.3 brought (`Notify=healthy`, templates, `NetworkAlias=`, the rootless wait for the network) | Upgrade Podman, or leave `podman.units` out on this machine and run with compose |
| `could not write the units into /etc/containers/systemd/…` | Rootful Podman: the units go into the system's systemd, which only root may write | `sudo brickkit up` |
| `Unit brickkit-….service not found` right after the reload | Podman's Quadlet generator rejected a unit file and generated nothing for it | `/usr/libexec/podman/quadlet -dryrun -user` (without `-user` for rootful Podman) prints why; the units are in `.brickkit/generated/quadlet/` |

**Worth knowing**

- `up` copies the units into `~/.config/containers/systemd/brickkit-<project name>/` (rootful:
  `/etc/containers/systemd/brickkit-<project name>/`). That directory is what is deployed; `down` removes it. An edit made
  there by hand is overwritten by the next `up`.
- Run `up`, `down` and `status` the way the project was deployed: rootful units are in `/etc/containers/systemd`,
  rootless ones in that user's home, and each systemd sees only its own. `up` run the other way refuses
  (`DEPLOYED_ELSEWHERE`) rather than deploy a second copy beside the first; `down` and `status` warn that the other copy
  is there.
- A value delivered as a Podman secret reaches the container when it is created. `podman exec <container> printenv`
  re-reads the secret and may show a newer value than the running process has; the process's own environment is
  `/proc/1/environ` inside the container. `up` restarts a component whenever one of its secrets changed.

## `down` can't stop a `mode: local` component

**Symptom**

After `brickkit down`, a `mode: local` component is still running; `down` only printed a session's process ID.

**Cause**

A `mode: local` process is supervised in the foreground by the terminal that ran `up`; it isn't a container. `down` only
looks after containers, and can't reach into another terminal's process tree.

**Fix**

`Ctrl+C` in that terminal. A normal stop prints no crash summary.

## Config changed, no difference after `up`

**Causes and fixes**

- The key name is wrong: `up`'s output has a warning saying it "is not declared in the component's configSchema, so it has
  no effect"; see [Config conflict problems](../../docs/en/10-troubleshooting/03-config-conflict-issues.md#config-written-but-not-taking-effect).
- The file changed isn't the one read this time: with local mode on, `deploy.local.yaml` is read, while you changed `vars:`
  in `deploy.yaml`. `brickkit local status` shows which one is read this time.
- What changed is code, not config: after changing code, `brickkit build --force`; see [Build problems](../../docs/en/10-troubleshooting/05-build-issues.md).
- On Kubernetes, what changed is the external Secret an `existingSecret` points at: the platform can't read its value, so
  it doesn't know it changed. A Pod reading it through an environment variable needs a restart to use the new value
  (`kubectl rollout restart deployment/<service name>`); a secret in the project's own `config/` rolls the Pod on `up`.
- What changed is a secret delivered as a file (the component declares `mount: file` in its `configSchema`): `up` only
  gives the file its new content and **does not restart the component**. A component that reads the file once at start
  needs a restart to use the new value (`brickkit down`, then `brickkit up`); on Kubernetes the file changes once the
  kubelet syncs, usually within a minute. See
  [Delivered as a file](../../docs/en/01-three-layers/07-sensitive-values.md#delivered-as-a-file-mount-file).
