# Design principles and trade-offs

[The pipeline](../../docs/en/06-architecture/01-pipeline-overview.md) covers **what** the platform does. This page covers **why it's shaped this way**:
the one idea that ties the whole design together; the engineering ideas BrickKit uses (and deliberately doesn't) — each
explained from "what it is", assuming you've never heard of it, together with the pain in AI development it answers, what
BrickKit does, what BrickKit doesn't do, and how an AI copes; and finally the ten principles every design proposal is
measured against.

[AGENTS.md](../../AGENTS.md) holds the same ten principles, compressed to one line each, for AI assistants to judge
whether a proposal fits. This page is the argument behind those lines: what each principle means, what it buys, what it
costs, what it refused. With their numbers removed, the ten subsection headings under "The ten principles" match
AGENTS.md §2 word for word; if the two drift apart, or the numbering slips, `make lint` fails.

## The one idea running through everything: declare a graph, derive the rest

You write three layers of declarations, plus one of each component's own:

| Declaration | Says |
| --- | --- |
| A component's `component.yaml` | What I am, whom I depend on, what config I need, how I'm deployed |
| `brickkit.yaml` | Which components this project uses, each at which exact version, and where to get them |
| The deploy file (`deploy.yaml` and others) | Where it's deployed, which components run, how they run |
| `config/` | The config values each component gets |

Together they describe a graph. Everything else the platform produces is **derived** from that graph on every run, and
every rule fits in one sentence:

| What's derived | Derived from | Rule |
| --- | --- | --- |
| Which components run | The deploy file's `mode` plus the dependency graph | Top-level components run by default; a lower one runs as long as something above it that needs it runs; an explicit `mode` takes precedence. The implementation computes the least fixed point of "who doesn't run", so cycles need no special handling |
| The start order | The dependency graph | A topological sort. A missing required dependency is an error at resolution time, not a surprise at run time |
| Service names and addresses | Component ID + exact version | `/` and `.` become `-`, all lowercase, then `http://<service name>:<port>` — the same string on Docker and on K8s |
| `*_ENDPOINT` variable names | The component ID | `/` and `-` become `_`, all uppercase, followed by `_ENDPOINT` |
| The config a component gets | `config/` and `configSchema` | What's written is used, `$var:` looks up a shared variable, what isn't written takes the default, and a required item with no value is stopped |
| `compose.yaml` or K8s manifests | The Manifests and the deploy file's `target` | Regenerated on every run; components never carry their own |
| Network policies | The dependency graph | Opt-in (the deploy file's `k8s.networkPolicy`): traffic is let through along the dependency edges you declared |
| Which source directories are active | The decision about who runs | `brickkit sync` archives what won't start and restores what will run |

"Derive" instead of "configure" buys three things:

- **A derived value can't disagree with its source.** Variable names always match component IDs, addresses always match
  versions, network policies always match dependencies — there's no "second copy someone forgot to update". Compare a
  hand-written gateway config: it has versioned service names baked in, goes stale quietly the moment a component raises
  its version, and nothing says a word.
- **Derivation works both ways.** From `people/basic` you compute `PEOPLE_BASIC_ENDPOINT`; seeing `PEOPLE_BASIC_ENDPOINT`,
  you know exactly which component it points at. That's why dependency aliases were refused: an alias keeps only half of
  this two-way relation.
- **The CLI can stay stateless.** Every output is a pure function of the declarations, so the CLI reads the declarations,
  generates, hands over to Docker or K8s, and exits. There's nothing to remember between two runs, so there's no need for
  a long-running process.

**Deriving isn't guessing.** A derived value is a pure function of what you declared. The platform never infers your
intent: it won't pick a version for you (`^1.0.0` is an error), won't open a port you didn't expose, won't decide on its
own what a missing optional dependency should degrade to, and won't start a component because it thinks you "probably
want it running". What can't be computed, you declare. That's how this idea meets the principle
"[Explicit over implicit](#7-explicit-over-implicit)" — the principle keeps the idea from crossing into guessing.

The cost: what can't be computed must be written down, and the escape hatch is deliberately narrow — `labels` and
`k8s.ingressAnnotations` are passed to the underlying engine verbatim, with no interpretation by the platform.

## Getting to know these ideas

What BrickKit uses, and what it deliberately doesn't, are ideas that have been in software engineering for a long time.
You don't need to know any of them beforehand: each idea below starts from "what it is", then its upside and cost, the pain
it corresponds to when AI writes code, what BrickKit does, what BrickKit **doesn't** do, and finally how an AI should cope.

**"What BrickKit doesn't do"** means the part the platform deliberately stays out of, leaving the decision to the
component's author (and the AI). It's a deliberate trade-off, not "not done yet" — each one has its reason.

**How to read it:** start with the five summary tables below (grouped by theme). Click a name in the first column to jump
to the numbered detail.

### 1. Bounded contexts (DDD)

**What it is:** in a large system, the same word often means different things in different parts of the business — a
"customer" in the order system is someone who places orders; in the support system, it's someone waiting for a reply. DDD
(domain-driven design) draws a few boundaries along the business, and each part (a "bounded context") has its own
vocabulary, rules and data; parts exchange information only through explicit interfaces. In an online shop, say, orders,
stock and customer support can each be a context.

- **Upside:**
  - Each part can be understood, changed and released independently by different people; changing one doesn't drag the
    others along.
  - Vocabularies don't pollute each other: the same word has its own precise meaning in each context.
  - When something goes wrong, it's easy to tell whose part it is.
- **Cost:**
  - A wrongly drawn boundary is hard to repair — too fine, and the parts talk to each other constantly; too coarse, and
    you're back to a tangle.
  - Drawing boundaries means really understanding the business first, which takes time in itself.
  - Consistency across parts is harder to guarantee: when one thing has to change two parts at once, no transaction
    covers both.
- **The pain in AI development:** once the system is big, an AI can't read it in one go, and doesn't know what a change
  in one place drags along, so it guesses.
- **What BrickKit does:**
  - A component is one business boundary, with its own repository, Manifest (`component.yaml`), version and interface
    contracts — an independent unit of release, of versioning and of permissions.
  - The boundary is written in `component.yaml`: which components it depends on, which ports it offers, which config it
    needs. An AI only has to read the current component's `component.yaml` plus the contracts of the components it depends
    on to start work, without understanding the whole system.
  - Components are small: the project's own 10 test components range from 200 to 3,500 lines, readable by an AI in one go.
  - One component shouldn't straddle two contexts; one context can be made of one or several components. Data that must
    hold together (say "a balance never goes negative", constraining both the account and its ledger) goes into **one
    component**, because there are no transactions across components.
  - Whether to split: ask three questions (a recommended test, not a platform rule). Is there an invariant between the two
    pieces of data that must hold at every moment? Do they need to be released separately, owned by different people?
    Once split, can callers write their calling code from the contract alone?
- **What BrickKit doesn't do:**
  - It doesn't care how a component models its inside (how aggregates and entities are drawn). That's component
    autonomy: the platform looks after the boundary; inside the boundary belongs to the author.
  - It doesn't enforce isolation: whether several components share one database, or are compiled into one process (a
    [shell](../../docs/en/04-shell/README.md)), is your decision by the business. When sharing a database, watch out yourself: the
    migration state table's primary key must include a component identifier, or components' migrations overwrite each
    other.
  - Why: once a platform starts prescribing the inside, it turns from an orchestrator into a framework, and a framework can
    only produce components of one shape.
- **How an AI copes:**
  - Where to draw the boundary is something an AI can't replace: how many components a feature should become, and which
    operations need a transaction, are domain judgments for you (and domain experts) to make.
  - The AI works inside the boundaries drawn, writing one component at a time, getting it running before the next.
  - Have the AI read the contracts of what it depends on, not their source (see [8. Contract first](#8-contract-first)).
  - How to draw component boundaries is discussed at length in [Component design](../../docs/en/09-patterns/01-component-design.md).

### 2. Microservices and service meshes

**What it is:** microservices split one big program into many small services, each developed and deployed on its own,
calling each other over the network. A service mesh is a layer of infrastructure dedicated to "how these services talk to
each other": helping them find each other, splitting traffic, rate limiting, retrying failures, circuit breaking (stop
calling a service that keeps failing). Like turning one big restaurant into many small shops along a street.

- **Upside:**
  - Each small shop can open and be refitted on its own, use different technology, and be run by a different team.
  - One shop in trouble doesn't close the whole street.
- **Cost:**
  - With many shops, someone has to look after the signposts (a registry: who is where), the entrance (a gateway: where
    outside requests go first), the queues and rate limits (a mesh) — operational complexity shoots up.
  - Calls go across the network: network hiccups, timeouts, the other side succeeding only halfway — all become cases to
    handle.
  - And when something goes wrong, you investigate across several shops.
- **The pain in AI development:** service discovery, config centres, registration SDKs… the AI has to handle all these
  concepts; and what to do when a call between components fails, the AI often writes only the happy path for.
- **What BrickKit does:**
  - Components are built, deployed and called independently; every component is a container (frontends too).
  - Addresses come from DNS plus environment variables: the caller reads one variable (like `PEOPLE_BASIC_ENDPOINT`, whose
    value is `http://people-basic-1-0-0:8080`) and needn't understand service discovery. Components need no registration
    SDK at all — zero intrusion.
  - The capabilities that are needed come natively from the underlying engine: load balancing is built into the
    Kubernetes Service; health checks and restarts are Compose's `healthcheck` and Kubernetes' Probes; when a gateway is
    needed, `labels` pass labels verbatim to tools like Traefik — the platform doesn't understand what labels mean, it
    only passes them on.
  - When memory is tight, several components can be compiled into one [shell](../../docs/en/04-shell/README.md) process — callers
    see the same addresses, and the platform points them at the shell.
- **What BrickKit doesn't do:**
  - **A registry:** the DNS built into Docker Compose and Kubernetes already provides service discovery for free. A home-made
    one would have to be kept highly available; and once components plug into a home-made service-discovery SDK, they're
    no longer "zero intrusion".
  - **Gateways, meshes, load balancing:** routing rules vary by business, and a platform forcing one shape on them only
    cuts the foot to fit the shoe. If you bypass the `labels` pass-through and hand-write a routing config containing
    versioned service names, it goes stale quietly the moment a component raises its version, and the platform won't
    remind you.
  - **Circuit breaking, rate limiting, retries:** thresholds and back-off strategies vary by business; a platform default
    would hardly fit every case, and would limit the flexibility a particular component really needs.
  - **Config centres, hot reload:** that's a whole machinery of long-lived connections, pushes and version comparisons,
    while most basic config has to be restarted to take effect safely anyway.
  - **Health-check polling:** Compose and Kubernetes already solve it natively; for the platform to do it, it would need
    either a background process or a client library embedded in every component.
  - The common reason: each of these means something long-running that someone has to operate, while BrickKit's CLI runs
    and leaves (see the principle "[Minimal platform](#2-minimal-platform)").
- **How an AI copes:**
  - Retries, timeouts, degradation and rate limiting are the component's own code; ask the AI explicitly to write them —
    its error handling often covers only the happy path.
  - Let `/healthz` check only the process itself, and don't let it probe the database or other dependencies on the side:
    otherwise one dependency's hiccup marks every upstream unhealthy and restarts them all at once.
  - When a gateway is needed, pass `labels` through; don't hand-write routing config with version numbers in it.
  - To call another component, read the address from the environment variable; don't let the AI do service discovery of
    its own.

### 3. Hexagonal and layered architecture

**What it is:** both are ways to organise "the inside of a program". Layering cuts the program into layers stacked on each
other (the one that receives requests, the one that handles the business, the one that stores and fetches data), and upper
layers only call lower ones. Hexagonal architecture goes further: the business logic sits in the centre, and outside
things like databases, web interfaces and message queues plug in through interfaces agreed beforehand. Like a kitchen with
a layer of standard interfaces between it and the delivery platforms, the till and the suppliers: changing a supplier
doesn't change the recipes.

- **Upside:**
  - The business logic doesn't depend on a particular framework or database, and is easier to test on its own (with a
    fake stand-in for the database, say).
  - It's easier to swap out an outside system.
  - Concerns are separated, so when reading code you know which layer to look in.
- **Cost:**
  - Quite a lot more interfaces and conversion code to write.
  - With more indirection, following one request's whole path takes more hops.
  - In a small program, it's like fitting a gearbox to a bicycle.
- **The pain in AI development:** AI tends to pile many layers of abstraction onto simple features (over-design), and you
  have to ask for simplification yourself.
- **What BrickKit does:** it enforces no internal structure. The platform only prescribes what a component presents **at
  its boundary**: a Manifest, a health check, and reading environment variables (see the principle
  "[Component autonomy](#4-component-autonomy)").
- **What BrickKit doesn't do:**
  - It doesn't prescribe how the inside is layered, or whether to use hexagonal architecture. `brickkit new` generates
    only a `component.yaml` that passes validation and a documentation skeleton — no code structure, and no language
    chosen for you.
  - Why: once a platform reaches inside, it turns from an orchestrator into a framework, and a framework can only produce
    components of one shape.
- **How an AI copes:**
  - Write "just enough" down yourself: for example, "three layers — HTTP, business, data access — are enough; don't add
    interfaces for things that have only one implementation".
  - If you want layers, giving it an existing component from your team as a model is more reliable than describing it in
    words.
  - If you want hexagonal architecture, say so in what you ask of the AI; the platform won't choose it for you.

### 4. Declarative and GitOps

**What it is:** there are two ways to tell a tool what to do. Imperative is telling it step by step, "do this, then that",
like teaching a cook a dish; declarative is writing only "what I want in the end" and letting the tool work out how, like
ordering from a menu. GitOps puts that declaration in Git as the system's single source of truth, and has an always-running
program keep pulling the real state towards the declaration — real state disagreeing with the declaration is called
"drift", and that program's job is finding and correcting drift.

- **Upside:**
  - The declaration is its own documentation: open the file and you know what the system should look like.
  - In Git, every change can be reviewed and rolled back.
  - Applying the same declaration again gives the same result.
- **Cost:**
  - What the declaration language can't express, you can't do.
  - When something goes wrong, you have to understand "how the declaration turns into actual actions".
  - The "keep pulling back" half also needs a long-running program watching all the time.
- **The pain in AI development:** having an AI write deployment scripts: many steps, a required order, one per
  environment, and changes that are hard to review.
- **What BrickKit does:**
  - You write the three layers of declarations (see
    [the one idea running through everything](#the-one-idea-running-through-everything-declare-a-graph-derive-the-rest) at
    the top of this page), and everything else is derived by the CLI: which components run, the start order, service
    addresses, environment variables, `compose.yaml` or Kubernetes manifests, network policies.
  - Each of the three layers owns one thing: `brickkit.yaml` owns "what's used", the deploy file "how it runs", `config/`
    "what it's configured to". Which layer a change lands in is plain in the Git diff.
  - One complete deploy file per environment, chosen with `brickkit up -f deploy.prod.yaml`.
  - `brickkit up --dry-run` starts nothing and prints the plan first, so you (and the AI) look before acting.
  - What starts is narrowed only through a file you can open: `mode` in the deploy file, or `focus:` in your own
    `deploy.local.yaml` (a [focus run](../../docs/en/02-project-guide/04-focus-run.md): `brickkit up --focus <id>`, or `brickkit up`
    in a component's directory, writes it, and `up --all` removes it). There's no `--only`-style flag that narrows one run
    and leaves nothing in a file: the narrowing stays written down, and `status` and `down` name the focus in effect.
- **What BrickKit doesn't do:**
  - **Pulling back continuously:** `brickkit up` applies once and the CLI exits; nothing keeps watching. If someone changes
    a running container by hand, no program changes it back; it's aligned at the next `up`. Pulling back continuously
    needs a long-running program someone operates — exactly the single point of failure and attack surface BrickKit
    deliberately avoids (see the principle "[Minimal platform](#2-minimal-platform)").
  - **Multi-environment overlays (a base layer + override layers):** an overlay makes you assemble "the base layer, the
    override layer, the merge rules" in your head before you can read the final config. BrickKit chooses one complete
    deploy file per environment: what you see is what runs, at the cost of repetition between files. Local mode's
    `deploy.local.yaml` likewise replaces the whole file; it isn't merged.
  - **"Are you sure?" prompts:** a declaration is intent; written, it's carried out.
- **How an AI copes:**
  - Have the AI change only the three layers, run `brickkit up --dry-run` to look at the plan after a change, then `up`.
  - Don't hand-edit running containers: they aren't changed back automatically, and only the next `up` aligns them.
  - For several environments, have the AI change each environment's complete deploy file; don't expect inheritance.

**Example:** the plan `brickkit up --dry-run` prints (an excerpt) — why each component starts, and in what order, at a
glance:

```text
📋 Component state calculation:
   ✅ demo/hello@1.0.0   starting (demo/caller needs it)
   ✅ demo/bus@1.0.0     starting (demo/caller needs it)
   ✅ demo/caller@1.0.0  starting (top-level)

📋 Start order (topological sort):
   1. demo-bus-1-0-0     no dependencies
   2. demo-hello-1-0-0   no dependencies
   3. demo-caller-1-0-0  ← depends on 2
```

### 5. Convention over configuration

**What it is:** the tool sets a set of rules for you in advance (what things are called, where they go, what happens by
default); follow them and you write almost no configuration. Rails is the best-known example: a model called `User` maps
to a `users` table in the database by default, and following that means not writing a single line of mapping.

- **Upside:**
  - Less configuration to write and read.
  - Someone new taking over knows at a glance where things are.
- **Cost:**
  - When the rules don't fit your case, there's no negotiating.
  - Worse are conventions that "guess": the rule wasn't spelled out, the tool quietly decided for you, and when it goes
    wrong you don't know what it guessed.
- **The pain in AI development:** the AI has to guess variable names, ports, service addresses; guess wrong, and the
  variable just quietly doesn't exist, often with no error at all.
- **What BrickKit does:** fixed naming, all computed by rules — nothing to guess, nothing to configure:

  | Thing | Rule | Example |
  | --- | --- | --- |
  | Service name | Component ID + exact version, `/` and `.` become `-`, all lowercase | `people/basic` 1.0.0 → `people-basic-1-0-0` |
  | Service address | `http://<service name>:<port>`, the same on Docker and Kubernetes | `http://people-basic-1-0-0:8080` |
  | Dependency address variable | The component ID with `/` and `-` turned into `_`, all uppercase, plus `_ENDPOINT` | `PEOPLE_BASIC_ENDPOINT` |
  | Extra port variable | Plus the port's name, by the same rule (`-` becomes `_`, all uppercase) | `PEOPLE_BASIC_GRPC_ENDPOINT`; port `admin-api` → `PEOPLE_BASIC_ADMIN_API_ENDPOINT` |
  | The component's own config | The keys of `configSchema` are the environment variable names, injected as they are | `DEFAULT_PAGE_SIZE` |
  | Config file name | The component ID with `/` turned into `-` | `config/people-basic.yaml` |

  The rule works **both ways**: from `people/basic` you compute the variable name, and seeing `PEOPLE_BASIC_ENDPOINT` you
  know exactly which component it points at. Defaults are conventions too: without `expose` it isn't exposed; without
  `mode` it follows the top.
- **What BrickKit doesn't do:**
  - **Decide for you:** which version to use, which port to expose, whether to enable a component — the platform never
    guesses; you must write it down (see the principle "[Explicit over implicit](#7-explicit-over-implicit)"). So
    BrickKit's own phrase is "derivation over configuration": what can be **computed** from what you wrote is derived;
    what can't, you write.
  - **Dependency aliases:** someone once proposed giving a dependency an alias (`as: iam`). An alias keeps only half of
    the two-way relation — `IAM_ENDPOINT` can't be traced back to the component it points at, and investigating "the
    address points at the wrong place" starts exactly there.
  - The cost is real too: the component ID turns, unchanged, into a variable name in every caller's code, so name
    components with the domain's own words, not with implementation details.
- **How an AI copes:**
  - Derive variable names by the rule; don't let the AI make them up from memory. Have it read `dependencies` in
    `component.yaml` first, then derive the variable names.
  - Ask it to write down decisions like versions, external exposure and enabling explicitly.
  - When naming a component ID, use the business's words.

### 6. Twelve-factor config

**What it is:** "the twelve factors" is a checklist of experience for writing cloud applications, three of which concern
config: config lives in the environment (factor III), backing services like databases and caches are treated as
"attached resources" that can be swapped at any time (IV), and development and production stay as alike as possible (X).
The most often quoted is the first: config (database addresses, passwords, where other services are) isn't hard-coded, but
read from environment variables when the program starts.

- **Upside:**
  - The same image runs in test and in production; the only difference between environments is "which environment
    variables were given at start-up".
  - Passwords stay out of the code repository.
  - Every language can read environment variables, without any library.
- **Cost:**
  - An environment variable is just a flat string; complex config has to be encoded and decoded by hand.
  - Many variables are hard to manage; a missing one is often found only the moment the program actually uses it.
  - Changed config takes a restart to take effect.
- **The pain in AI development:** the AI has to handle config differences between environments, and all too easily
  writes addresses and passwords into the code.
- **What BrickKit does:**
  - Everything a component needs to know reaches it as environment variables: dependency addresses (`*_ENDPOINT`),
    platform-wide variables (`COMPONENT_ID`, `COMPONENT_VERSION`), the component's own config (the keys of
    `configSchema`). Database addresses and passwords are just ordinary config items of the component.
  - The address format is exactly the same on Docker and Kubernetes; switching environments switches one deploy file, with
    zero changes to component code. Values that differ between environments reference shared variables with `$var:`,
    given by each environment's deploy file under `vars:`.
  - It's checked at `up`: the cost of "found only when missing" is moved up to the moment of deployment — a misspelled
    config key gets a warning with a guess at what you meant; a config item that is required, has no default and wasn't
    filled in by the project stops `up` outright; a config key colliding with a variable the platform reserves gets a
    warning and is skipped (the platform-injected value wins).
  - The complete list of every variable is [The environment variable contract](../../docs/en/06-architecture/03-env-injection-contract.md).
- **What BrickKit doesn't do:**
  - **Config centres, hot reload:** that's a whole heavy machinery of long-lived connections, pushes and version
    comparisons; and basic config like connection-pool sizes and timeouts can only take effect safely with a restart
    anyway. To change config, change `config/` and `brickkit up`. A business switch that truly needs millisecond-level hot
    updates can be polled by the component itself.
  - **Validating config values:** `configSchema` is only a spec sheet; see [9. Design by contract](#9-design-by-contract).
  - **Implicit environment overrides:** a variable of the same name that happens to be in the process environment never
    quietly overrides what's written in `config/`; the environment is read only where you explicitly wrote `${VAR}`.
- **How an AI copes:**
  - Read variables only with `os.environ.get()` (`System.getenv()` in Java); read `configSchema` first to know which keys
    exist and what their defaults are.
  - An optional dependency's variable may not exist at all: never write `os.environ["X"]`, or the component crashes on
    start-up when it's missing (see [10. Fail loudly](#10-fail-loudly)).
  - Config items declared as `array` or `object` arrive in the container as one line of JSON, which the component parses
    itself.
  - After changing config, `brickkit up` has to restart for it to take effect.

**Example:** what reading config looks like in a component — required dependency, optional dependency, own config, three
ways of reading:

```python
import os

people = os.environ.get("PEOPLE_BASIC_ENDPOINT")             # required dependency: always there
bus = os.environ.get("INFRA_REDIS_EVENT_BUS_ENDPOINT")       # optional dependency: absent when it isn't running
page_size = int(os.environ.get("DEFAULT_PAGE_SIZE", "20"))   # own config: a default to fall back on

if not bus:
    ...  # degrade: how is the component's own business logic
```

### 7. Exact versions and lock files

**What it is:** when you depend on someone else's software, the version can be written as a "range" (like `^1.0.0`,
meaning "the latest 1.x will do") or pinned to one specific version (`1.0.0`, in the form `major.minor.patch`). A lock file
(like npm's `package-lock.json`) records the specific versions installed the first time, and installs exactly those from
then on.

- **Upside:**
  - What's installed today is what's installed three months from now; your production doesn't quietly change at night
    because someone published a new version.
  - When something goes wrong, you know exactly which version is running, and a rollback has a clear target.
- **Cost:**
  - Patches and security fixes don't arrive by themselves; upgrading takes you acting.
  - Go long without upgrading and you fall far behind.
- **The pain in AI development:** an AI making a "breaking change" (a new version incompatible with the old) drags down
  every component depending on it; and it may write `^1.0.0` or `latest` along the way.
- **What BrickKit does:**
  - Only exact versions: `^1.0.0`, `~1.0.0` and `latest` are all errors at resolution time, not left for run time.
  - `brickkit.yaml` is itself the lock file: when `brickkit add people/basic` is given no version, the CLI looks up the
    latest installable version at that moment and writes it in as an **exact version**. The difference from "a range in
    the config" is when resolution happens: once, instead of every time. Upgrading is an explicit command
    (`brickkit upgrade`), which migrates the config at the same time.
  - The version goes into the service name: `people-basic-1-0-0` and `people-basic-2-0-0` are two different DNS names that
    can run side by side without clashing.
  - The variable name carries no version, the variable's **value** does:
    `DEPARTMENT_TREE_ENDPOINT=http://department-tree-1-0-0:8080`. A caller always knows which version it talks to; there's
    no implicit upgrade.
- **What BrickKit doesn't do:**
  - **Resolving version ranges:** ranges are the usual cause of "works on my machine, breaks in production".
  - **Two versions side by side in one component:** in one `component.yaml`'s `dependencies`, a component ID can appear
    only once — the variable name carries no version, so two versions would collide on the same `*_ENDPOINT`. So "side by
    side" is a **project-level** capability, not a component-level one: when different callers each depend on a different
    version, `brickkit.yaml` keeps both, with `requiredBy` saying whom each is kept for.
  - **Data compatibility between versions side by side:** the platform provides only a physical buffer; a breaking change
    is a coordination problem between teams, and whether the data layer stays compatible is your own responsibility.
- **How an AI copes:**
  - When having the AI write v2, run the new version side by side with v1 and move callers over gradually; don't
    overwrite v1.
  - Have it always write exact versions, never `^` or `latest`.
  - When two versions share one database, whether migrations stay backward compatible is for you and the AI to
    guarantee; the migration state table's primary key includes a component identifier.

**Example:** two versions side by side look like this in `brickkit.yaml` (more in
[Several versions side by side](../../docs/en/03-component-guide/09-multi-version-coexistence.md)):

```yaml
components:
  - id: demo/hello
    version: 1.1.0
  - id: demo/hello
    version: 1.0.0
    requiredBy: [demo/caller]
```

### 8. Contract first

**What it is:** when two teams connect their work, they first write "what the interface looks like" into a file (OpenAPI
for HTTP interfaces is common, protobuf for gRPC), and each side implements against it — rather than finishing one side and
leaving the other to guess. Like agreeing on the shape of the plug first.

- **Upside:**
  - Both sides can develop in parallel.
  - What a component promises to the outside is known without reading its implementation.
- **Cost:**
  - Someone has to maintain the contract file.
  - A contract that disagrees with the implementation is worse than none — the reader trusted an outdated description.
- **The pain in AI development:** to call another component, the AI can only dig through its source and guess. And the
  internal implementation in that source isn't a promise to the outside: once the other side refactors, the AI's calls
  break.
- **What BrickKit does:**
  - Components release their contract files with each version through `artifacts`, and `brickkit add` and
    `brickkit fetch` download them. `fetch` downloads only the artifacts, without changing `brickkit.yaml` or deploying —
    it's for calling a service in another project.
  - The platform's only job is making sure what's in `files` really reaches whoever wants it.
  - More in [Contracts and artifacts](../../docs/en/03-component-guide/06-artifacts-and-contracts.md).
- **What BrickKit doesn't do:**
  - It doesn't prescribe a format: `type` and `format` are free strings the CLI never parses (OpenAPI, protobuf, anything
    of your own). Parsing formats would require the platform to understand OpenAPI and protobuf first.
  - It doesn't check the implementation really matches the contract. Whether contract and implementation agree is the
    component's own business.
- **How an AI copes:**
  - Have the AI read the contract files of what it depends on, not their source — then however the other side refactors,
    it isn't affected.
  - Write the contract first, then the implementation; whether contract and implementation agree is verified by contract
    tests you write yourself (see the [testing strategy](../../docs/en/09-patterns/02-testing-strategy.md)).

**Example:** an artifact declaration:

```yaml
artifacts:
  - type: api-contract
    format: openapi
    description: The HTTP interface
    files:
      - api/openapi.yaml
```

### 9. Design by contract

**What it is:** every function or module states "what I require of my input, what I guarantee of my output", and fails
at once when that's violated. Like the rating plate on an appliance saying "input 220 V, output 12 V": connect it wrong and
the fuse blows.

- **Upside:**
  - Errors are caught as close as possible to their cause.
  - The rules themselves are the most precise documentation there is.
- **Cost:**
  - Rules written too strictly keep out legitimate uses nobody thought of; written too loosely, they may as well not be
    there.
  - Checking on every run has an overhead.
  - The rules themselves need maintaining.
- **The pain in AI development:** the AI doesn't know which config a component accepts, or which values are allowed, and
  goes by memory.
- **What BrickKit does:** it borrows only the "write it down" half. The closest thing in BrickKit is `configSchema` —
  strictly a close relative only, because it describes without enforcing.
  - A component uses it to state its config items, their types, defaults and allowed ranges (`enum`, `minimum`,
    `maximum`, `pattern`), readable by people and AI alike.
  - The CLI checks that the config key **names** written in `config/` exist in `configSchema`: a misspelled one gets a
    warning with a guess at what you meant. When a component declares no `configSchema` at all but `config/` holds config
    for it, none of it takes effect, and that gets a warning too.
  - A config item that is required (`required`), has no default and wasn't filled in by the project stops `up` outright,
    naming the component and the item.
- **What BrickKit doesn't do:**
  - **It doesn't check config values.** When an item declared `type: integer` is filled with a string, say, the CLI doesn't
    stop it; the component crashes when it calls `int()` on the string — found at run time, not the moment of
    `brickkit up`.
  - The line is whether there's a safety net at run time: a wrong value makes the component crash by itself, and you're
    sure to notice; a wrong name just means the variable quietly doesn't exist, the component takes its default branch and
    runs normally, and nothing reminds you. So names are checked, values aren't.
  - And once value checking starts, it doesn't stop — enums? ranges? regular expressions? JSON Schema can do a great deal,
    and the CLI would keep growing. What to do about a wrong value (fail, degrade, use a default) is also the component's
    own decision.
  - More in [Designing configSchema](../../docs/en/03-component-guide/03-config-schema-design.md).
- **How an AI copes:**
  - Have the AI read `configSchema` before writing the code that reads config; key names and defaults follow it.
  - Validating config values (ranges, enums) goes into the component's start-up, exiting at once on failure with a clear
    error.
  - Don't let it treat `minimum` / `maximum` in `configSchema` as something the platform enforces.

**Example:** a piece of `configSchema`, and the CLI's real warning when a key name in `config/` is misspelled:

```yaml
configSchema:
  type: object
  properties:
    QUOTE_PREFIX:
      type: string
      default: "Quote of the day: "
      description: The prefix put in front of the quotation
```

```text
⚠️ demo/quote@0.1.0: QUOTE_PREFX is not declared in the component's configSchema, so it has no effect
   File: config/demo-quote.yaml
   Declared keys: QUOTE_PREFIX
   Suggestion: Did you mean QUOTE_PREFIX?
```

### 10. Fail loudly

**What it is:** when a program finds something wrong with itself, it stops at once and visibly with an error, rather than
pretending nothing happened and carrying on. Also called fail fast.

- **Upside:**
  - Errors show up as early as possible, closest to their cause.
  - The worst bug isn't a crash, it's "quietly giving a wrong answer that looks normal": you're sure to notice a crash, not
    necessarily a wrong answer.
- **Cost:**
  - Stricter means more "refusals": a file with one unknown field too many, a component without defensive code, which
    might otherwise have limped along, now won't start at all.
- **The pain in AI development:** AI error handling often covers only the normal case; edge cases like a missing optional
  dependency or a failed migration slip through easily.
- **What BrickKit does:** it moves errors up to the moment of `up` as far as possible, and says where and why (this is also
  the first of the ten principles; see "[Fail loudly](#1-fail-loudly)"):
  - An unknown field in the three layers or a Manifest is refused outright, not quietly ignored.
  - A version range in dependencies is an error at resolution time.
  - With a required dependency missing, `up` refuses to generate anything; a required config item without a value, or a
    config conflict left by an upgrade, is stopped by `up`.
  - When a migration fails, the main service doesn't start, and the error names whose migration it was.
  - **The most typical is optional dependencies:** a missing optional dependency **injects no variable at all**, rather
    than an empty string.
- **What BrickKit doesn't do:**
  - **Decide for a component how to degrade.** When the cache is down, one component queries the database instead,
    another returns an empty list, another writes to a local file to retry later — pure business judgment, and the
    platform has no way to define "degrade" for everyone. The platform's only act is not injecting the variable.
  - The cost is real too: a component that reads the variable as `os.environ["X"]` crashes on start-up when it's missing.
    That's deliberate: better to crash loudly at start-up than go quietly wrong at run time.
- **How an AI copes:**
  - Ask it explicitly to handle the two most easily missed edges, "a missing optional dependency" and "a failed
    migration".
  - Read optional dependencies' variables with `.get()`, and say what happens when one is missing.
  - The entry program exits with an error at once on an argument it doesn't know. The migration container and the main
    service run the same image, told apart only by the command-line argument; if the entry program "starts the service as
    usual" on an unknown argument, a misspelled migration command turns the migration container into a second service
    that never exits, the whole deployment hangs, and its own logs say everything is ready.

**Example:** why an empty string can't be injected for a missing one. A developer forgets to check for empty and writes
`requests.get(f"{ENDPOINT}/healthz")`: with an empty string injected, that becomes `/healthz`, the request hits the
container's **own** port, and its own `/healthz` returns 200 — so the developer believes the optional dependency is
healthy. Bugs like this are extremely hard to track down. So the platform chooses to have the variable not exist at all,
and the component crashes loudly at start-up.

### 11. Least privilege

**What it is:** every program and every component gets only the least access it needs to do its work; everything else is
closed by default. Like a hotel key card that opens only your own room. In network security it's often mentioned together
with "zero trust".

- **Upside:**
  - When a component is broken into, or merely has a bug, what it can reach is limited, and the damage stays small.
- **Cost:**
  - Every allowed access has to be written out explicitly.
  - Miss one, and it's an investigation into "can't connect, no idea why".
- **The pain in AI development:** when there's a bug or a break-in, the more a component can reach, the bigger the
  damage.
- **What BrickKit does:**
  - **Unreachable by default:** without `expose` in the deploy file there's no external entry (no host port mapped on
    Docker, no Ingress generated on Kubernetes).
  - **Network policies:** on Kubernetes, writing `k8s.networkPolicy.enabled: true` in the deploy file computes network
    policies straight from the dependency graph — traffic is let through only along the dependency directions you declared,
    without maintaining a separate access-control list by hand. Callers outside the dependency graph (the Ingress
    controller, another team's namespace) are let through by hand with `allowFrom`.
  - **ServiceAccounts:** `k8s.serviceAccount.enabled: true` gives every component a ServiceAccount of its own, with no token
    mounted.
  - The CLI itself never mounts the Docker socket.
  - See [Security and signing](../../docs/en/06-architecture/08-security-and-signing.md).
- **What BrickKit doesn't do:**
  - **Turn on by default** network policies, ServiceAccount isolation or `podSecurity: restricted`: each can stop a
    component that ran fine from starting — a real, project-specific cost the platform can't weigh for you.
  - **Verify that network policies take effect:** many clusters accept these objects and don't enforce them at all —
    `kubectl apply` succeeds, `kubectl get networkpolicy` shows them, and traffic flows exactly as before, without any
    error. The default network plugins (CNI) of minikube and kind are of this kind. Kubernetes offers no API to ask, so the
    platform can't tell, and `brickkit up` reminds you every time to verify it yourself once.
- **How an AI copes:**
  - Have the AI declare only the dependencies it really needs: fewer dependencies, fewer paths let through.
  - Write `expose` only when a service must be offered to the outside.
  - Whether to turn on network policies and ServiceAccount isolation is a person's judgment; once on, verify that
    "authorised paths still work and unauthorised ones really are blocked", rather than trusting that the generated YAML
    looks right.

**Example:** the network policy generated for `demo/hello@1.0.0` — `demo/caller` is its only caller, so the only source
let through is it, on only the port `demo/hello` itself listens on:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
spec:
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: demo-caller-1-0-0
      ports:
        - port: 8080
          protocol: TCP
  podSelector:
    matchLabels:
      app: demo-hello-1-0-0
  policyTypes:
    - Ingress
```

### 12. Supply-chain security

**What it is:** does the third-party component you install really come from the author it claims? Was it swapped along
the way? Like the seal on a parcel plus the sender's signature.

- **Upside:**
  - It prevents impersonation.
  - It prevents tampering in transit.
- **Cost:**
  - A signature only proves "who sent it, and that it wasn't altered", not "what was sent isn't malicious".
  - You have to manage "which public keys to trust" yourself, and publishers have to keep their private keys safe.
- **The pain in AI development:** when an AI brings in a third-party component, its origin is hard to verify.
- **What BrickKit does:**
  - **Git sources:** which repository a component comes from is written by you in `brickkit.yaml`'s install sources; it's
    exactly as trustworthy as that repository and that hosting platform.
  - **Signatures on market components:** the publisher signs with cosign (`brickkit publish --sign --key ...`). What's
    actually signed is a "canonical payload" — the Manifest parsed and re-encoded by fixed rules — so changing comments,
    indentation or key order doesn't break the signature.
  - **Image digests:** by default `brickkit publish` first resolves the mutable image tag to a digest and then signs, so the
    signature covers a reference that can't be quietly re-pointed afterwards; skipping it takes an explicit
    `--no-pin-digest`.
  - **Installing:** the installer verifies with the Go standard library alone, with no need to install cosign. The public
    keys trusted are configured under `installer.publicKeys` in your own project's `brickkit.yaml`, and
    `requireSignature` defaults to `true`.
  - See [Security and signing](../../docs/en/06-architecture/08-security-and-signing.md).
- **What BrickKit doesn't do:**
  - **Review upfront:** no scanning, no sandboxing, no static analysis. Installing means trusting — the same model as npm,
    the VS Code extension marketplace and GitHub. When a component is found malicious afterwards, the one remedy is
    marking it `blocked` in the market, which stops new installs.
  - **Take public keys from the market:** otherwise, once the market is broken into, an attacker can swap both the
    component and the public key, verification still passes, and the market is issuing certificates to itself.
  - **Note:** with no public key configured at all, signature verification is **switched off entirely**, and
    `requireSignature: true` does nothing either (the CLI warns).
- **How an AI copes:**
  - A person confirms bringing in a new component or adding a trusted key to `publicKeys`; don't leave it to the AI.
  - Don't let the AI turn off `requireSignature`, or delete `publicKeys`, "to make the install pass".

### 13. Type-driven development

**What it is:** using a programming language's type system to "write the rules into the shape of the code", so wrong code
doesn't even compile. An order amount, for instance, isn't just any number but a dedicated "amount" type, so a "quantity"
can't be passed in as an "amount" by mistake.

- **Upside:**
  - A whole class of errors is stopped at compile time, instead of found at run time.
  - The types themselves are documentation that doesn't go stale.
- **Cost:**
  - It depends on the language: not every language's type system is strong enough (dynamic languages get part of the
    benefit from type annotations plus a checker, like Python's annotations with mypy).
  - Designing the types takes effort in itself, and badly designed types become a burden.
- **The pain in AI development:** AI-written code reads smoothly, but whether it's right can't be told by reading it; a
  machine has to check.
- **What BrickKit does:** nothing, and it needn't. BrickKit's CLI is itself written in Go and benefits from type
  checking, but components aren't required to be.
- **What BrickKit doesn't do:**
  - **Restrict languages — and in the most thorough way:** any language that builds into a container image will do. The
    repository's own test components come in several: Python, Go, plain HTML served by nginx. Being language-agnostic is
    one of the platform's core values.
  - **Provide an SDK:** the only trace the platform leaves in component code is reading environment variables. So
    everything the platform hands a component is a **string** (numbers and booleans too); converting to types is the
    component's own business.
- **How an AI copes:**
  - Pick a language with type checking for the AI to write in, and let the compiler (or type checker) be the first gate:
    it has to compile before anything else.
  - At start-up, read the environment variables once into a typed config structure, failing to start at once when
    required items are missing and listing all of them at once, rather than quietly falling back to defaults (see
    [10. Fail loudly](#10-fail-loudly)).

**Example:** how types keep wrong code from compiling (Go):

```go
type Cents int64   // an amount, in cents
type Quantity int  // a quantity

func charge(amount Cents) { /* ... */ }

var qty Quantity = 3
charge(qty) // doesn't compile: a Quantity can't be used as Cents
```

### 14. TDD and BDD

**What it is:** TDD (test-driven development) writes the test first, then the code that makes it pass: make the test go
red first, then write the implementation that turns it green. BDD (behaviour-driven development) first describes the
expected behaviour in near-everyday language as "given… when… then…", then turns that into a test. Like writing the
acceptance criteria before starting to cook.

- **Upside:**
  - Tests become a constraint on "what the code should do", not a restatement of "what the code already does".
  - Requirements become checkable.
- **Cost:**
  - It takes time up front.
  - If the acceptance criteria themselves are wrong, you'll build the wrong thing very diligently.
- **The pain in AI development:** have an AI write the implementation first and the tests after, and the tests become a
  restatement of the implementation — testing only that "the code does what it does". And AI-generated tests often test
  only the normal cases, missing the edges.
- **What BrickKit does:** nothing enforced, but advice:
  - The [testing strategy](../../docs/en/09-patterns/02-testing-strategy.md) covers how to test a component in layers: contract tests
    (the shape of the interface), business-rule tests (invariants, idempotency, legal state transitions), unit tests (this
    implementation's branches), integration tests (end to end against real dependencies). Telling business-rule tests from
    unit tests takes one question: delete the implementation entirely and rewrite it in another language — should this
    test still hold? If yes, it's a business-rule test.
  - There's also a recommended "spec first, then implementation" order (see the table below). BrickKit components happen
    to have three specifications that don't depend on the implementation, all written in `component.yaml`:
    `configSchema`, `dependencies`, and the contract files.
  - What's unique to BrickKit is `brickkit up --dry-run` and `brickkit lint`: without starting any container, they check
    that a component and the project's three layers agree (a misspelled config item name, a required item left empty).
- **What BrickKit doesn't do:**
  - It neither requires nor checks how you test: testing strategy was never within the platform's remit; that's part of
    component autonomy.
  - `--dry-run` checks **whether the assembly is right**, not **whether the component's code is right**.
- **How an AI copes:**
  - Go in order: spec first, then tests — watching them go red — and only then have the AI write the implementation. Red
    has to have a reason: a test green on its first run tests nothing.
  - Write a business rule as one sentence of "given… when… then…" first, then turn it into a test. For example, "given an
    idempotency key not yet processed; when two requests with the same key arrive at once; then only one really runs, and
    the other gets the same result" — that sentence is itself the most precise prompt you can give an AI.
  - AI often tests only the normal cases; add the edge cases yourself, or ask for them explicitly.
  - Integration tests run against real dependencies; don't trust only stand-ins (mocks).

**Example:** the recommended order, with real feedback at every step:

| Step | Do | How you know the step is right |
| --- | --- | --- |
| 1 | Complete `component.yaml`: `dependencies`, `configSchema`, contract files | `brickkit lint`, `brickkit up --dry-run` (no containers started) |
| 2 | Write contract tests from the contract files | They must all be red now, and red for a reason |
| 3 | Write each business rule as a sentence, then turn it into a test | Likewise red first |
| 4 | Have the AI write the implementation until the contract and business-rule tests are all green | The tests are the acceptance; no one needs to read the implementation line by line |
| 5 | Add unit tests: the branches of this implementation | Every branch is reached |
| 6 | Run integration tests: `brickkit up` starts real dependencies, and a real path is walked through | Works end to end |

### 15. Property-based testing

**What it is:** an ordinary test is a few examples you write by hand: input A should give B. Property-based testing
thinks differently: you describe "a property the result should have whatever the input" (say "a sorted list is always in
order, and has the same length"), and a tool generates thousands of random inputs looking for a counter-example that
breaks it.

- **Upside:**
  - It runs into edge cases you'd never think of.
  - Once it finds a counter-example, the tool usually shrinks it to the smallest form that still reproduces.
- **Cost:**
  - Thinking the "property" through isn't easy.
  - Failures of random tests must be reproducible, so the random seed has to be recorded.
  - It doesn't suit code that leans heavily on outside systems.
- **The pain in AI development:** AI-generated tests often cover only the normal cases the AI itself thought of.
- **What BrickKit does:** the platform uses it itself. The three places in the CLI densest with rules all have tests
  checking them with random input:
  - **Who runs:** thousands of small random graphs (covering every `mode` value, required and optional dependencies,
    optional cycles, several upstreams sharing one component) are checked against an independently written brute-force
    reference. The reference doesn't copy the platform's propagation algorithm; it enumerates every candidate set and takes
    the largest one satisfying the documented rules one by one — the two share the rules, not the algorithm.
  - **Start order:** properties like "dependencies before those that depend on them", "every component exactly once",
    "removing every optional edge leaves the order unchanged", "shuffling the input gives the same result".
  - **Resource quota merging:** field-by-field precedence, `limits` having no default layer, and merging the result again
    changing nothing.
  - Every random seed is fixed, failures carry the seed and can be reproduced exactly; no new library is involved.
  - For components it's mentioned only under [seed and test data](../../docs/en/09-patterns/03-seed-data.md): property-based tests
    suit "core invariants" (a balance never goes negative, a state machine never makes an illegal transition).
- **What BrickKit doesn't do:**
  - Require or recommend it for components: it fits a narrow range, mainly core invariants; for most business code
    ordinary example tests are enough.
  - Provide a property-testing framework or library: the platform itself uses the standard library's random numbers.
- **How an AI copes:**
  - When there's a core invariant, write it down as one sentence first ("an account balance never goes negative"), then
    have the AI write property tests from it.
  - Otherwise, don't: not for its own sake.

## The ten principles

Each principle is written in the same form: **what it is**, **what it buys**, **what it costs**, **what it refused**. To
judge whether a design proposal fits, hold it against them one by one.

### 1. Fail loudly

**What it is:** config conflicts, missing required values, duplicate keys and failed pushes are all reported the moment
the operation happens, not left to surface at run time. The error says which file, which item, why, and what to do next.

**What it buys:** the worst bug isn't a crash, it's a result that looks normal and is wrong — config that quietly didn't
take effect, a dependency address that's quietly empty. Moving failures up to the moment of `up` or `lint` puts the error
closest to its cause, where it's cheapest to fix.

**What it costs:** more "refusals". A file with one unknown field too many, a conflict left by an upgrade, a required item
not filled in, which might otherwise have limped along, now won't run at all — you have to deal with it first.

**What it refused:** quietly ignoring unknown fields; injecting an empty string for a missing optional dependency; "the
later one wins" on config conflicts; leaving behind a tag that exists only locally after a failed push.

### 2. Minimal platform

**What it is:** the platform does only mechanical work — parse, derive, generate, hand over to the engine — and never
guesses meaning: it doesn't guess that a config item was renamed, doesn't convert types, doesn't decide for a component how
to degrade.

**What it buys:** a small platform with few rules, each fitting in one sentence; a CLI that runs and leaves, with no
long-running process — so no single point of failure, no service to operate, no listening port.

**What it costs:** many things that "could be done along the way" aren't done by the platform, and components write them
themselves: retries, circuit breaking, degradation, validating config values. When an upgrade renames a config item, the
platform treats it as "one deleted, one added", and you move it over yourself.

**What it refused:** registries, config centres, API gateways, service meshes, health-check polling, multi-tenancy, type
validation of config values, guessing renames during upgrades.

### 3. What you see is what runs

**What it is:** no implicit overrides. The file you open is the configuration in effect.

**What it buys:** reading one file tells you the result, without merging several layers in your head. When `config/` says
`DB_HOST: pg.internal`, that's what the component gets — not quietly overridden by a same-named variable that happens to be
in the process environment; local mode reads the whole of `deploy.local.yaml`, not a merge of "the team's file plus a
personal patch".

**What it costs:** repetition. One complete deploy file per environment means repeated entries; when the team's file
changes, your `deploy.local.yaml` needs a `refresh`, after which you copy your local changes back.

**What it refused:** multi-environment inheritance and merging (overlays); environment variables implicitly overriding
config files; sparse personal override files; a "final view" command that merges the three layers into one.

### 4. Component autonomy

**What it is:** which config a component needs, how it degrades, what its logs look like, which language it uses, how it's
layered inside — all the component's own decisions. The platform asks only three things of a component: a Manifest, a
health check, and reading config from environment variables.

**What it buys:** anything that builds into a container image can be a component; there's no platform SDK in component
code, zero intrusion; move to another platform and not a line of the component changes.

**What it costs:** the platform can't help inside a component: wrong values, forgotten degradation, logs in a dozen
formats — the platform doesn't look after any of it. Quality rests on the component's author, not on a platform safety net.

**What it refused:** a platform SDK; prescribing components' internal structure; validating config values for
components; deciding for components what to do when an optional dependency is missing.

### 5. One job per file

**What it is:** each of the three layers owns one thing: `brickkit.yaml` owns "which components, which versions", the
deploy file "where it's deployed, how it runs", `config/` "which values it's configured with". Every fact is written in
one place only.

**What it buys:** which layer a change lands in is obvious; a fact has only one place to change, so two places can't
disagree. Several environments need only a few more deploy files, without copying the component list or the config.

**What it costs:** more files. Newcomers first have to learn which fact belongs to which layer.

**What it refused:** one big all-in-one file; writing the same fact in two places (listing a shell's members again in
`brickkit.yaml`, writing how it's deployed again on a component entry).

### 6. Atomic operations

**What it is:** `add`, `remove`, `upgrade` and `release` either succeed completely or put everything back as it was,
leaving nothing half-done.

**What it buys:** when a command fails, there's no mess to clean up. When `add` has changed the three layers and the
project then fails to load, all three files are restored; when `release` fails to push, the tag it just created locally is
deleted; `upgrade` with no component named upgrades everything, and either does all of it or changes none.

**What it costs:** the implementation has to finish the work in memory or on a copy and verify it before writing the real
files back; some operations are a little slower than "write as you go" because of it, and harder to write.

**What it refused:** files left changed halfway; "partly successful" batch operations; releases that exist only locally
and never reached the remote.

### 7. Explicit over implicit

**What it is:** exact versions, explicit `$var:` references, explicit port exposure, explicitly turning local mode on.
The platform refuses to "guess automatically".

**What it buys:** where every value comes from is written down, so when something goes wrong, following what was written
finds it; the same declarations give the same result on anyone's machine, at any time.

**What it costs:** more writing. Every shared variable needs its `$var:` written once, every external port its `expose`,
and every version number pinned one by one.

**What it refused:** version ranges (`^1.0.0`, `latest`); falling back to shared variables automatically by name; opening
ports to the outside by default; deciding by name which config items go through the secret channel (only `secret: true`
decides that).

### 8. One model at every size

**What it is:** a one-component project and a fifty-component project use the same three layers; a component being
developed on its own is itself a project of the same kind. There's no "single-file mode", no "simplified mode".

**What it buys:** learn it once and it lasts: a small project growing into a big one needn't migrate to another way of
writing; component authors and project maintainers speak the same language.

**What it costs:** even the smallest project has three layers (`init` generates them for you), which looks like a bit much
to someone who just wants to run one component.

**What it refused:** a simplified single-file form for small projects; special concepts that exist only at one size.

### 9. Build is separate from deploy

**What it is:** building an image is your explicit step (`brickkit build`); `brickkit up` never builds automatically.

**What it buys:** `up` is always predictable: it only runs images that already exist, and never bakes half-changed code
into an image and runs it when you didn't mean to. An image's tag follows the component's version
(`<scope>-<name>:<version>`, or `:<version>` added to an untagged `image`), so what's running is plain to see.

**What it costs:** one more command. Change the code, forget `build --force`, and the old image still runs — `up` can
only point out a missing image, not tell that an image is "old" (shell images are the exception: the member versions
compiled in carry a label that can be checked).

**What it refused:** `up` building an image on the side when it finds none; compiling code implicitly as part of
deploying.

### 10. Read on demand, don't merge everything

**What it is:** there's no command that merges the three layers into one view. To learn something, read the layer that
owns it — which version in `brickkit.yaml`, how it runs in the deploy file, what it's configured to in `config/`, who
depends on whom by asking `brickkit deps` or `brickkit graph`.

**What it buys:** every question has one source of answers, so a "merged view" can never disagree with the original
files; an AI assistant also reads only the layer that answers the current question, instead of swallowing a whole merged
result every time.

**What it costs:** seeing "everything about one component" at a glance takes two or three files (the deployment files
`up --dry-run` generates are the nearest thing to the whole picture).

**What it refused:** a "final config" view command merging the three layers; copying dependencies into `brickkit.yaml`
(they're already written in each component's `component.yaml`).

# The Git repository cache

## Why not `git clone` every time

On a Git install source, one component is one repository and one version is one tag. The most direct way for the CLI to
read a version's `component.yaml` and contract files would be to clone the repository every time — twenty components in a
project would be twenty full clones, on every `up`, in every project, in every component's own workbench.

BrickKit instead clones each component repository **once** on this machine, keeping it as a **bare repository** (Git's
data only, with no checked-out working tree), and afterwards only runs incremental `git fetch`es; to read a version's
files, it takes them straight from that tag in the bare repository (`git show <tag>:component.yaml`), with no checkout.

## Where it lives

In a user-level cache directory, organised by the full repository address:

```text
~/.cache/brickkit/repos/
└── git.example.com/
    └── components/
        ├── demo-hello.git
        └── demo-quote.git
```

(On macOS it's `~/Library/Caches/brickkit/repos/`.) It isn't in the project's `.brickkit/` because the same component
repository is shared by many projects, and by the component's own workbench — kept per project, the same repository would
be cloned N times. Named by the full address, same-named repositories in different organisations
(`github.com/a/erp-api` and `github.com/b/erp-api`) never collide.

## The four-level read order

To get a component version's `component.yaml`, the CLI tries these in order, stopping at the first that has it:

| Level | From | Network |
| --- | --- | --- |
| 1 | The project's permanent cache `.brickkit/manifests/<component>/<version>/` | Not needed |
| 2 | This tag in the cached bare repository (`git show`) | Not needed |
| 3 | `git fetch --tags`: the repository is there, but not this tag yet | Incremental |
| 4 | `git clone --bare`: this repository was never cloned | A full clone |

Components from a local install source don't take this path: a local source's `component.yaml` is read from the directory
afresh every time and never cached — change it, and the next command follows the new one.

## The whole flow of fetching a file

1. Check the project's Manifest cache. A hit ends it.
2. Work out the repository address: the install source's `baseUrl` plus `<scope>-<name>`, or `source.repo` when the
   component's entry has one. When the component sits in a repository subdirectory, the tag carries a namespace:
   `<scope>-<name>/<version>`.
3. Make sure the bare repository is in the cache, cloning it when it isn't. A clone lands in a temporary place under the
   cache directory first and is renamed when complete — failing or being interrupted halfway never leaves half a repository
   behind.
4. When the repository has the tag, read the files from the tag directly.
5. When it doesn't, `git fetch --tags` once for the increment (a repository is fetched at most once per run), then read.
   When a tag was force-moved, the remote wins; branches deleted on the remote are deleted in the cache too.
6. Write the `component.yaml` read into the project's permanent cache, together with every `BRICKKIT*.md` in the
   component's directory at that tag — `BRICKKIT.md` and each translation (`BRICKKIT.zh.md` …), when it carries them.

"The latest version" (`add` without a version, `upgrade`) needs the list of tags, and that step always fetches first, so
what it sees is the remote's tags as they are now.

## Offline

Once a version has been fetched, it's in the project's permanent cache, and `up`, `graph` and `deps` work without the
network from then on. When another project wants the same version, the bare repository is already in the user cache and
level 2 finds it, again without the network. Only a version never seen, or a repository never cloned, needs the network.

## Git submodules are never fetched

A component repository may register git submodules. BrickKit fetches none of them, on every path:

| Path | What you get |
| --- | --- |
| The bare-repository cache | Tags and their commits; a submodule is only a pointer in its tree |
| Reading `component.yaml`, `BRICKKIT*.md`, artifacts | Files read straight from the tag — never inside a submodule |
| `build` from a tag | An export of the tag: submodule directories are empty, and `build` warns about them |
| `add --repo` | A clone without `--recurse-submodules`; it names the submodules it left empty |

The reasons: a submodule points at another repository, with its own address and its own credentials; fetching it would
make installing one component quietly reach into repositories nobody declared. The contract of a component is its
`component.yaml`, its artifacts and its image — none of which should need a submodule. When the build does need one, the
component should publish an image; in a cloned repository you can always run `git submodule update --init` yourself.

## Authentication

The CLI calls your system's `git`, with the credentials you've already set up (SSH keys, a credential helper, a token CI
injects). It sets one environment variable, `GIT_TERMINAL_PROMPT=0`: without credentials `git` fails at once, rather
than stopping in CI to wait for a password that never comes. On failure, `git`'s own words appear in the error. See
[Distributing through Git](../../docs/en/03-component-guide/10-git-distribution.md#private-repositories-and-authentication).

## Cleaning up

Deleting the whole of `~/.cache/brickkit/repos/` is safe: it's only a cache, re-cloned the next time it's needed.
Temporary directories left by interrupted clones are cleared automatically by later runs once they're old enough.

# Cache design

## Two caches

| Where | Holds | Shared by |
| --- | --- | --- |
| The project's `.brickkit/` | The `component.yaml`, docs and contracts of the component versions this project uses; generated deployment files; this machine's state | This project only |
| The user-level `~/.cache/brickkit/repos/` | Bare repositories of component Git repositories | Every project on this machine, and components' own workbenches |

Bare repositories are covered in [The Git repository cache](../../docs/en/06-architecture/06-bare-repo-mechanism.md). This page is about the project's
`.brickkit/`.

## What's in `.brickkit/`

```text
.brickkit/
├── manifests/<scope>/<name>/<version>/
│   ├── component.yaml     this version's Manifest (a permanent cache)
│   ├── BRICKKIT.md        only when the component carries docs
│   ├── BRICKKIT.<lang>.md each translation it carries (BRICKKIT.zh.md …)
│   └── signature.json     where it came from, and signature information
├── artifacts/<versioned service name>/<type>/…   contract files the component declares (downloaded by add / fetch)
├── generated/
│   ├── compose.yaml       the deployment file for Docker / Podman
│   ├── env/               env files holding secrets (0600)
│   ├── k8s/               Kubernetes manifests
│   └── local-debug.<service name>.env   environment variables of a mode: debug component
├── last-run               the component versions of the last up; the baseline for version-change notices
├── local-mode             local mode is on while this exists
├── deploy.local.base.yaml the deploy.yaml that deploy.local.yaml was last copied from; refresh tells local changes by it
├── session.lock           a mode: local session is running
└── credentials            the component market login token (0600)
```

## Caching rules

**Manifests are cached permanently and never expire.** An exact version is immutable: whatever `demo/hello@1.0.0`'s
`component.yaml` is today, it always is — a released version doesn't change (`release` refuses to move an existing tag).
So there's no such thing as "the cache expired"; fetched once, it's used from then on.

**Local sources are never cached.** For components from a local install source (`components/`, `shell/`), the
`component.yaml` is read from the directory afresh every time: that's code under development, and a change should take
effect at once. When a local source directory at exactly this version exists, the doc path points at it too, rather than
at the snapshot in the cache.

**Generated files are rewritten every time.** Everything under `generated/` is output of `up`, regenerated every time;
hand edits are overwritten by the next `up`.

**Documentation is cached with the Manifest, from every kind of source.** `add` and `fetch` write `BRICKKIT.md` and
every `BRICKKIT.<lang>.md` next to `component.yaml` — from a local source, a Git tag or the market alike — and nothing
else: a component's `AGENTS.md` and `README.md` are for its own repository.

## `.brickkit/` stays out of Git

The `.gitignore` `init` generates leaves it out. What's inside either can be obtained again (Manifests, contracts,
generated files) or is the state of this machine and this person (the local-mode switch, the session lock, the login
token).

After a fresh `git clone` of a project, `.brickkit/` doesn't exist, and that's fine: on the first command, the CLI fetches
the Manifests and contracts it needs from the install sources again, by `brickkit.yaml`. It's the same reasoning as
`package.json` in Git and `node_modules` out of it: `brickkit.yaml` is the lock file, `.brickkit/` is what gets installed
from it.

## The AI assistant skills carry their own record

The skill files under `.claude/skills/` are committed with the project, and the CLI has to know, for each one, whether it
wrote it and whether someone has edited it since — an edited file is never overwritten. Earlier versions kept that record
in `.brickkit/skills.lock`. But `.brickkit/` stays out of Git: a teammate's fresh clone had no lock, and from then on the
skills there could never be refreshed.

Now each skill file carries its record on its last line:

```text
<!-- brickkit:skill version=<v> sum=sha256:<hex> -->
```

`version` is the CLI that wrote the file; `sum` is the fingerprint of the content above the line. When
`brickkit skills status` or `brickkit skills update` reads the file and the content still matches the fingerprint, it
is the CLI's own and can be refreshed; when it doesn't, someone edited it, and it is skipped. The record travels with the file, so every clone knows.

The skills' language isn't in the skill files either: it is the `lang=` recorded in the block at the end of the project's
`AGENTS.md`. An old `.brickkit/skills.lock` is read once, to recognise the files an earlier CLI wrote, and then deleted by
`brickkit skills update`.

## What can be deleted

| Delete | Consequence |
| --- | --- |
| All of `.brickkit/` | Safe. The next command fetches Manifests and contracts again and regenerates the deployment files; local mode turns off, and the market needs a new login |
| `manifests/`, `artifacts/` | Safe; fetched again as needed (from the user-level bare repositories, usually without the network) |
| `generated/` | Safe; the next `up` regenerates it |
| `~/.cache/brickkit/repos/` | Safe; re-cloned the next time it's needed |

Deleting caches is never the way to fix a problem — exact versions in the cache don't "go bad". When a change in a local
source doesn't take effect, first check the component really comes from the local source (the order of install sources in
`brickkit.yaml`).

# Security and signing

## The trust model: installing means trusting

BrickKit does no upfront review of third-party components — no scanning, no sandboxing, no static analysis. Installing a
component means trusting it, the same model as npm, the VS Code extension marketplace and GitHub. An upfront review either
has too many false positives (stopping legitimate components) or too many false negatives (letting carefully disguised
malicious code through); what the platform can do reliably is confirm "who a component comes from, and whether it was
altered".

| A component from | Is as trustworthy as |
| --- | --- |
| A local install source | You |
| A Git install source | That repository and that hosting platform, which you named in `brickkit.yaml`'s install sources |
| A component market | The publisher's signature (below) |

When a market component is confirmed to be a problem, the market marks it `blocked`, and it can't be installed from then
on.

## Signatures: signed on publishing, verified on installing

**The publisher** signs with cosign:

```bash
brickkit publish --path ./components/people/basic --sign --key cosign.key --signed-by release-bot@example.com
```

What's signed isn't the raw bytes of `component.yaml` but a **canonical payload**: the Manifest parsed and re-encoded by
fixed rules. So changing comments, indentation or key order doesn't break the signature; and a Manifest with duplicate keys
is refused outright — when the same file reads two ways to two different parsers, a signature means nothing.

By default `publish` first resolves the image's tag to an immutable digest, then signs: the signature covers a reference
that can't be quietly re-pointed afterwards. `--no-pin-digest` skips it, but then the signature stays valid when the
same-named tag is replaced in the image registry.

**The installer** verifies with the Go standard library alone, with no need to install cosign.

## Public keys live in your own project

```yaml
# brickkit.yaml
installer:
  requireSignature: true
  publicKeys:
    keys/vendor.pub: keys/vendor.pub
```

`publicKeys` are the publishers' public keys you trust: a name (the `publicKeyRef` written in the signature) → a public
key file in the project.

**Public keys aren't taken from the market.** Otherwise, once the market is broken into, an attacker can swap both the
component and the public key, and verification still passes — the market issuing certificates to itself. The root of
trust is in your own repository, through your own code review.

The cases:

| Situation | Result |
| --- | --- |
| The component is signed, the signer's key is in `publicKeys`, verification passes | Installed |
| `requireSignature: true`, and the component isn't signed | Installation blocked |
| The signature comes from a publisher not declared in `publicKeys` | A warning: not verified |
| No public key configured at all | Signature verification is **switched off entirely**, and `requireSignature: true` does nothing either; the CLI warns |

The last row is worth remembering: writing only `requireSignature: true` without configuring keys protects nothing.

## Least privilege

**Unreachable by default.** Components on the same network can call each other by service name; access from outside needs
`expose` written for it in the deploy file (Docker maps a host port, Kubernetes generates an Ingress).

**Network policies generated from the dependency graph.** On Kubernetes, write in the deploy file:

```yaml
k8s:
  networkPolicy:
    enabled: true
```

The platform generates one NetworkPolicy per component: it lets through only the component's real callers in the
dependency graph, and only on the ports it listens on itself. Callers outside the dependency graph (the Ingress
controller, another team's namespace) are let through by hand with `allowFrom`; the outbound direction can be covered too
(`egress`). You don't maintain a separate access-control list — it always agrees with the declared dependencies.

**ServiceAccounts.** `k8s.serviceAccount.enabled: true` gives every component a ServiceAccount of its own, without mounting
the token for the Kubernetes API.

**Pod security.** `k8s.podSecurity: restricted` generates a `securityContext` for every container following Pod Security's
restricted level: not running as root, no privilege escalation, every capability dropped, `seccompProfile:
RuntimeDefault`. A read-only root filesystem is deliberately not added — restricted doesn't require it, and it would kill
any component writing to `/tmp`. Dropping every capability also means ports below 1024 can't be bound: when a component
listens on such a port, `up` warns.

None of these three is **on by default**: each can stop a component that ran fine from starting (a component that needs to
run as root, or to call the Kubernetes API), a cost only you can weigh.

The CLI itself never mounts the Docker socket; it only calls the `docker compose` / `kubectl` command line.

## Network policies may not take effect at all

This is a limit you must know: **many clusters accept NetworkPolicy objects and don't enforce them at all.** `kubectl
apply` succeeds, `kubectl get networkpolicy` shows them, and traffic flows exactly as before, without any error. Whether
they're enforced depends on the cluster's network plugin (CNI); the default CNI of minikube and kind doesn't.

Kubernetes offers no API to ask "does this cluster enforce NetworkPolicy?", so the platform can't tell, and every time `up`
generates network policies it reminds you:

```text
🔒 Generated 3 NetworkPolicy manifests (k8s.networkPolicy.enabled: true)
   ⚠️ They only take effect when the cluster's CNI enforces them. When it doesn't: apply succeeds,
      kubectl get networkpolicy shows them, yet traffic is not restricted at all — with no error whatsoever.
      The default CNI of minikube / kind is exactly this kind.
   The platform can't detect this (K8s has no API for it), so you have to verify it yourself once:
      See docs/en/06-architecture/08-security-and-signing.md (swap en for zh for the Chinese version)
```

**Verify it yourself once:** after deploying, reach the same target from an **authorised** component and from an
**unauthorised** one.

```bash
# Authorised: demo/caller depends on demo/hello, so this should connect
kubectl exec -n brickkit-my-shop deploy/demo-caller-1-0-0 -- \
  wget -qO- -T 3 http://demo-hello-1-0-0:8080/healthz

# Unauthorised: demo/bus doesn't depend on demo/hello, so this should time out
kubectl exec -n brickkit-my-shop deploy/demo-bus-1-0-0 -- \
  wget -qO- -T 3 http://demo-hello-1-0-0:8080/healthz
```

The first succeeding and the second timing out means the network policies are in effect. Both succeeding means your
cluster doesn't enforce them — you need a CNI that does (Calico or Cilium, for instance), or to accept that "these
policies are declarations only". A generated YAML that looks right proves nothing.

## Secrets

Secrets don't go into `config/` (it's committed to Git): reference an environment variable or `.env` with `${VAR}`, a file
under `.secrets/` with `file://`, or, on Kubernetes, a Secret already in the cluster with `{ existingSecret, key }`. At
deployment, secrets take a separate channel and are never written into deployment files in plain text. More in
[Sensitive values](../../docs/en/01-three-layers/07-sensitive-values.md).
