# 设计原则与取舍

[架构总览](../../docs/zh/06-architecture/01-pipeline-overview.md)讲的是平台**做了什么**。这一篇讲它**为什么长成这个样子**：把整个设计串起来的那一个想法；BrickKit 用到（以及刻意没用）的那些工程想法——每个都从"它是什么"讲起，不假设你听过，并说清它对应 AI 开发的什么痛点、BrickKit 怎么做、BrickKit 不做什么、AI 怎么应对；最后是每个设计提议都要拿来对照的十条原则。

[AGENTS.zh.md](../../AGENTS.zh.md) 里有同样的十条原则，压缩成一行一条，写给 AI 助手拿去判断某个提议合不合适。这一篇是那些行背后的论证：每条原则是什么意思、换来了什么、付出了什么、拒绝了什么。「十条原则」一节的十个小节标题，去掉前面的编号后，与 AGENTS.zh.md §2 逐字一致；两边一旦分叉、或编号错位，`make lint` 会失败。

## 贯穿一切的那一个想法：声明一张图，其余全部派生

你写三层声明，外加每个组件自己的一份：

| 声明 | 说什么 |
| --- | --- |
| 组件的 `component.yaml` | 我是什么、依赖谁、要什么配置、怎么部署 |
| `brickkit.yaml` | 这个项目用哪些组件、各是哪个精确版本、从哪里取 |
| 部署文件（`deploy.yaml` 等） | 部署到哪里、哪些组件跑、怎么跑 |
| `config/` | 每个组件拿到的配置值 |

它们合起来描述一张图。平台产出的其余一切，都是每次运行时从这张图**派生**出来的，每一条规则都能用一句话说清：

| 派生出的东西 | 从什么派生 | 规则 |
| --- | --- | --- |
| 哪些组件运行 | 部署文件的 `mode` 加依赖图 | 顶层组件默认运行；下层组件只要上面有需要它的在跑，它就跑；显式写了 `mode` 则以所写为准。实现上算的是"谁不跑"的最小不动点，所以环不需要任何特殊处理 |
| 启动顺序 | 依赖图 | 拓扑排序。强依赖缺失在解析期就是错误，不是运行期的意外 |
| 服务名与地址 | 组件 ID + 精确版本 | `/` 和 `.` 变成 `-`，全小写，再拼成 `http://<服务名>:<端口>`——Docker 和 K8s 上是同一个字符串 |
| `*_ENDPOINT` 变量名 | 组件 ID | `/` 和 `-` 变成 `_`，全大写，末尾加 `_ENDPOINT` |
| 组件拿到的配置 | `config/` 与 `configSchema` | 写了用写的，`$var:` 查公共变量，没写用默认值，必填又没有值就拦下 |
| `compose.yaml` 或 K8s 清单 | Manifest 与部署文件的 `target` | 每次运行重新生成；组件自己从不携带 |
| 网络策略 | 依赖图 | 需主动开启（部署文件的 `k8s.networkPolicy`）：流量沿着你声明过的依赖边放行 |
| 哪些源码目录处于活动状态 | 启停判定的结果 | `brickkit sync` 把不启动的归档、把要跑的还原 |

用"派生"代替"配置"，换来三样东西：

- **派生出的值不可能和它的来源不一致。** 变量名永远对得上组件 ID，地址永远对得上版本，网络策略永远对得上依赖关系，不存在"忘了同步的第二份"。对比一份手写的网关配置：里面烧进了版本化服务名，组件一升版本它就悄悄过期，还不会有任何提示。
- **派生可以双向推。** 从 `people/basic` 能算出 `PEOPLE_BASIC_ENDPOINT`；看到 `PEOPLE_BASIC_ENDPOINT`，也能确切知道它指向哪个组件。这就是依赖别名被拒绝的原因：别名只保住了这条双向关系的一半。
- **CLI 可以保持无状态。** 每个产物都是声明的纯函数，所以 CLI 读入声明、生成、交给 Docker 或 K8s、然后退出。两次运行之间没有任何需要记住的东西，也就不需要常驻进程。

**派生不是猜。** 派生值是你所声明内容的纯函数。平台从不推断你的意图：它不会替你选版本（`^1.0.0` 直接报错）、不会替你打开你没暴露的端口、不会自作主张认定某个缺失的弱依赖该降级成什么、也不会因为觉得你"大概想跑它"就把一个组件拉起来。算不出来的值，就由你声明。这就是这个想法与原则「[显式优于隐式](#7-显式优于隐式)」的衔接方式——后者负责把前者拦在"猜"的门槛之外。

代价是：算不出来的东西必须写下来，而且逃生口刻意开得很窄——`labels` 与 `k8s.ingressAnnotations` 原样透传给底层引擎，平台不做任何解释。

## 认识这些想法

BrickKit 用到的、以及刻意没用的，都是软件工程里早就有的想法。你不需要事先认识其中任何一个：下面每个想法，都从"它是什么"讲起，再讲它的好处和代价、用 AI 写代码时它对应什么痛点、BrickKit 怎么做、BrickKit **不**做什么，最后讲 AI 该怎么应对。

**"BrickKit 不做的部分"** 指的是：平台故意不管、把决定留给组件作者（和 AI）的那部分。这是有意的取舍，不是"还没做"——每一条都有理由。

**怎么读：** 先看下面五张总表（按主题分组）。点第一列的名字，跳到对应编号的详细介绍。

### 1. 限界上下文 (DDD)

**它是什么：** 一个大系统里，同一个词在不同业务里往往不是同一件事——订单系统里的"客户"是下单的人，客服系统里的"客户"是等着被回复的人。DDD（领域驱动设计）的做法是按业务划出几块边界，每一块（一个"限界上下文"）有自己的词汇、规则和数据，块与块之间只通过明确的接口交换信息。比如一家网店，订单、库存、客服就可以各是一个上下文。

- **好处：**
  - 每块可以由不同的人独立理解、独立修改、独立发布，改一块不会牵动别的块。
  - 词汇不会互相污染：同一个词在不同的上下文里，各有各的精确含义。
  - 出了问题，容易判断是哪一块的事。
- **代价：**
  - 边界划错了很难补救——太细，块与块之间要不停地沟通；太粗，又回到一团乱。
  - 划边界得先真正弄懂业务，这本身要花时间。
  - 跨块的一致性更难保证：一件事要同时改两块时，没有一个事务能罩住两边。
- **AI 开发的痛点：** 系统一大，AI 一次读不完，改一处也不知道会牵动谁，只能连蒙带猜。
- **BrickKit 怎么做：**
  - 一个组件就是一块业务边界，有自己的仓库、Manifest（`component.yaml`）、版本和接口契约，是独立的发布单位、版本单位和权限单位。
  - 边界写在 `component.yaml` 里：它依赖哪些组件、提供哪些端口、需要哪些配置。AI 只要读当前组件的 `component.yaml`，加上它依赖的组件的契约，就能开工，不用理解整个系统。
  - 组件小：项目自带的 10 个测试组件在 200 到 3500 行之间，AI 一次读得完。
  - 一个组件不该横跨两个上下文；一个上下文可以由一个或几个组件组成。必须同时成立的数据（比如"余额永远不为负"同时约束账户和流水）要放进**同一个组件**，因为组件之间没有跨组件事务。
  - 拆不拆，可以问三个问题（推荐的判据，不是平台的规则）：这两块数据之间有没有一条任何时刻都必须同时成立的不变量？它们要不要各自独立发版、归不同的人？拆开之后，调用方只靠契约能不能写出调用代码？
- **BrickKit 不做什么：**
  - 不管组件内部怎么建模（聚合、实体怎么划）。这是组件自治：平台只管边界，边界之内归作者。
  - 不强制隔离：几个组件是否共用一个数据库、是否编进同一个进程（[外壳](../../docs/zh/04-shell/README.md)），由你按业务决定。共用数据库时要自己留意：迁移状态表的主键必须包含组件标识，否则各组件的迁移会互相覆盖。
  - 原因：平台一旦开始规定内部，就从编排器变成了框架，而框架只能产出一种形状的组件。
- **AI 怎么应对：**
  - 边界该画在哪，AI 替代不了：一个功能该拆成几个组件、哪些操作需要事务，是领域判断，要由你（和领域专家）来定。
  - AI 在划好的边界内工作，一次只写一个组件，写完跑通再写下一个。
  - 让 AI 读依赖方的契约，别读它的源码（见 [8. 契约先行](#8-契约先行)）。
  - 怎么划组件边界的详细讨论，见[组件设计](../../docs/zh/09-patterns/01-component-design.md)。

### 2. 微服务与服务网格

**它是什么：** 微服务是把一个大程序拆成许多小服务，各自开发、各自部署，通过网络互相调用。服务网格是专门管"这些服务之间怎么通信"的一层基础设施：帮它们找到对方、分流、限流、失败重试、熔断（对方一直出错时先停止调用）。像把一家大餐馆拆成一条街上的许多小店。

- **好处：**
  - 各家小店可以独立开张、独立装修，用不同的技术，由不同的团队负责。
  - 一家出了问题，不至于整条街停业。
- **代价：**
  - 店多了，得有人管路牌（注册中心：谁在哪儿）、管入口（网关：外面的请求先到哪）、管排队限流（网格）——运维复杂度陡增。
  - 调用变成了跨网络：网络抖动、超时、对方只成功了一半，都成了要处理的情况。
  - 出了问题还得跨好几家店去查。
- **AI 开发的痛点：** 服务发现、配置中心、注册 SDK……这些概念都得 AI 去处理；组件之间调用失败时怎么办，AI 又常常只写了正常路径。
- **BrickKit 怎么做：**
  - 组件独立构建、独立部署、独立调用；每个组件都是一个容器（前端也是）。
  - 地址靠 DNS 加环境变量：调用方读一个变量（如 `PEOPLE_BASIC_ENDPOINT`，值是 `http://people-basic-1-0-0:8080`），不用理解服务发现。组件里不需要任何注册 SDK，零侵入。
  - 该有的能力，交给底层引擎原生提供：负载均衡是 Kubernetes Service 自带的；健康检查和重启是 Compose 的 `healthcheck` 和 Kubernetes 的 Probes；需要网关时，用 `labels` 把标签原样透传给 Traefik 这类工具，平台不理解标签的含义，只负责传。
  - 内存吃紧时，可以把几个组件编进一个[外壳](../../docs/zh/04-shell/README.md)进程——调用方看到的地址照旧，平台把它指到外壳。
- **BrickKit 不做什么：**
  - **注册中心：** Docker Compose 和 Kubernetes 自带的 DNS 已经免费提供了服务发现。自建一个还得保证它高可用；组件一旦接入自制的服务发现 SDK，就不再是"零侵入"。
  - **网关、网格、负载均衡：** 路由规则因业务而异，平台强行统一只会削足适履。如果你绕开 `labels` 透传，自己手写一份包含版本化服务名的路由配置，组件一升版本它就悄悄过期，平台不会提醒你。
  - **熔断、限流、重试：** 阈值和退避策略因业务而异，平台给一个默认值，既很难对所有场景都合适，也会限制某个组件真正需要的灵活度。
  - **配置中心、热更新：** 那是长连接、推送、版本比对的一整套机制，而多数基础配置本来就必须重启才能安全生效。
  - **健康检查轮询：** Compose 和 Kubernetes 已经原生解决；平台自己做，要么得有个后台进程，要么得让每个组件都嵌入一份客户端库。
  - 共同的原因：每一样都意味着一个要长期运行、要有人运维的东西，而 BrickKit 的 CLI 是用完即走的（见原则「[平台极简](#2-平台极简)」）。
- **AI 怎么应对：**
  - 重试、超时、降级、限流都是组件自己的代码，要明确要求 AI 写——它的错误处理常只覆盖正常情况。
  - `/healthz` 只让它检查进程自己，别顺手去探数据库或别的依赖：否则一个依赖一抖，所有上游会一起被判成不健康、一起重启。
  - 需要网关，用 `labels` 透传，别手写含版本号的路由配置。
  - 调别的组件，读环境变量里的地址，别让 AI 自己去做服务发现。

### 3. 六边形与分层架构

**它是什么：** 都是"程序内部怎么组织"的办法。分层是把程序切成上下几层（接收请求的、处理业务的、存取数据的），上层只调用下层。六边形架构更进一步：业务逻辑放在中心，数据库、网页接口、消息队列这些外部的东西，都通过事先约定的接口接上来。像厨房和外卖平台、收银机、供货商之间隔一层标准接口，换个供货商不用改菜谱。

- **好处：**
  - 业务逻辑不依赖具体的框架或数据库，更容易单独测试（比如用一个假的数据库替身）。
  - 更容易换掉某个外部系统。
  - 关注点分开，读代码时知道去哪一层找。
- **代价：**
  - 要多写不少接口和转换代码。
  - 间接层多了，读一条请求的完整路径要多跳几步。
  - 在小程序里，像给自行车装变速箱。
- **AI 开发的痛点：** AI 容易给简单功能堆出很多层抽象（过度设计），需要你主动要求简化。
- **BrickKit 怎么做：** 不强制任何内部结构。平台只规定组件在**边界上**呈现的样子：一份 Manifest、一个健康检查、以及读环境变量（见原则「[组件自治](#4-组件自治)」）。
- **BrickKit 不做什么：**
  - 不规定内部怎么分层，也不要求用不用六边形。`brickkit new` 只生成一份能通过校验的 `component.yaml` 和一份文档骨架，不生成任何代码结构，也不替你选语言。
  - 原因：平台一旦管到内部，就从编排器变成了框架，而框架只能产出一种形状的组件。
- **AI 怎么应对：**
  - 你要主动写明"够用就好"：比如"HTTP、业务、存取数据三层就够，不要为只有一个实现的东西加接口"。
  - 想要分层，给它一个你们团队现成的组件当样子，比只用文字描述可靠。
  - 想用六边形，得在给 AI 的要求里写明，平台不会替你选。

### 4. 声明式与 GitOps

**它是什么：** 让工具做事有两种说法。命令式是一步步告诉它"先做这个、再做那个"，像教厨师做菜；声明式是只写"我最终要什么"，怎么做由工具去算，像在菜单上点菜。GitOps 是把这份声明放进 Git，当作系统的唯一事实来源，再由一个一直运行的程序持续把真实状态拉向声明——真实状态和声明对不上，叫"漂移"，这个程序的工作就是发现漂移并纠正它。

- **好处：**
  - 声明本身就是文档：打开文件就知道系统该是什么样。
  - 放进 Git 之后，每次改动都能审查、能回滚。
  - 重复应用同一份声明，结果不变。
- **代价：**
  - 声明语言表达不了的事，就做不了。
  - 出了问题，你得理解"声明是怎么变成实际动作的"。
  - "持续拉回"那一半，还要有个常驻的程序一直盯着。
- **AI 开发的痛点：** 让 AI 写部署脚本：步骤多、有先后顺序、每个环境还要各写一份，改动又难评审。
- **BrickKit 怎么做：**
  - 你写三层声明（见本页开头的[贯穿一切的那一个想法](#贯穿一切的那一个想法声明一张图其余全部派生)），其余一切都由 CLI 派生：哪些组件运行、启动顺序、服务地址、环境变量、`compose.yaml` 或 Kubernetes 清单、网络策略。
  - 三层各管一件事：`brickkit.yaml` 管"用什么"，部署文件管"怎么跑"，`config/` 管"配成什么"。一次改动落在哪一层，Git diff 一眼看得出。
  - 每个环境一份完整的部署文件，用 `brickkit up -f deploy.prod.yaml` 选择。
  - `brickkit up --dry-run` 不启动任何东西，先把计划打印出来，让你（和 AI）先看再动手。
  - 想缩小启动范围，只能通过一份打得开的文件：在部署文件里改 `mode`，或者在你自己的 `deploy.local.yaml` 里写 `focus:`（即[焦点运行](../../docs/zh/02-project-guide/04-focus-run.md)：`brickkit up --focus <ID>`、或在组件目录里执行 `brickkit up` 会替你写上，`up --all` 把它删掉）。没有 `--only` 这类"只缩小这一次、文件里什么都不留"的参数：缩小范围这件事一直写在文件里，`status`、`down` 也会说出当前的焦点。
- **BrickKit 不做什么：**
  - **持续拉回：** `brickkit up` 是一次性下发，CLI 用完就退出，没有任何东西一直盯着。有人手动改了运行中的容器，不会有程序替你改回去，要等下一次 `up` 才对齐。持续拉回需要一个常驻、要有人运维的程序——那正是 BrickKit 刻意躲开的单点故障和攻击面（见原则「[平台极简](#2-平台极简)」）。
  - **多环境 overlay（基础层 + 覆盖层）：** overlay 要求你先在脑子里拼出"基础层、覆盖层、合并规则"才看得懂最终配置。BrickKit 选的是每个环境一份完整的部署文件：所见即所得，代价是文件之间会有重复。本地模式的 `deploy.local.yaml` 也一样是整份替换，不是合并。
  - **"你确定吗"的确认：** 声明就是意图，写了就执行。
- **AI 怎么应对：**
  - 让 AI 只改三层文件，改完先 `brickkit up --dry-run` 看计划，再 `up`。
  - 不要手改运行中的容器：它们不会被自动改回去，下次 `up` 才会对齐。
  - 多个环境，让 AI 分别改各自完整的部署文件，别指望有继承。

**例：** `brickkit up --dry-run` 打印的计划（节选）——每个组件为什么启动、按什么顺序启动，一目了然：

```text
📋 组件状态计算：
   ✅ demo/hello@1.0.0   启动（demo/caller 需要）
   ✅ demo/caller@1.0.0  启动（顶层）

📋 启动顺序（拓扑排序）：
   1. demo-hello-1-0-0   无依赖
   2. demo-caller-1-0-0  ← 依赖 1
```

### 5. 约定优于配置

**它是什么：** 工具先替你定好一套规矩（叫什么名字、放在哪儿、默认怎么做），你照着来，就几乎不用写配置。Rails 是最有名的例子：一个叫 `User` 的模型默认对应数据库里的 `users` 表，照做就不用再写一行映射。

- **好处：**
  - 要写、要读的配置少。
  - 换个人接手，一眼就知道东西在哪儿。
- **代价：**
  - 规矩不合你的情况时，没有商量的余地。
  - 更麻烦的是"靠猜"的约定：规矩没讲清楚，工具悄悄替你做了决定，出错时你不知道它猜了什么。
- **AI 开发的痛点：** AI 要猜变量名、端口、服务地址；猜错了，变量只是悄悄不存在，往往没有任何报错。
- **BrickKit 怎么做：** 固定命名，全部由规则算出，不用猜也不用配：

  | 东西 | 规则 | 例子 |
  | --- | --- | --- |
  | 服务名 | 组件 ID + 精确版本，`/` 和 `.` 变成 `-`，全小写 | `people/basic` 1.0.0 → `people-basic-1-0-0` |
  | 服务地址 | `http://<服务名>:<端口>`，Docker 和 Kubernetes 上一样 | `http://people-basic-1-0-0:8080` |
  | 依赖地址变量 | 组件 ID 的 `/` 和 `-` 变成 `_`，全大写，加 `_ENDPOINT` | `PEOPLE_BASIC_ENDPOINT` |
  | 额外端口的变量 | 再加上端口名，规则相同（`-` 变成 `_`，全大写） | `PEOPLE_BASIC_GRPC_ENDPOINT`；端口 `admin-api` → `PEOPLE_BASIC_ADMIN_API_ENDPOINT` |
  | 组件自己的配置 | `configSchema` 的键就是环境变量名，原样注入 | `DEFAULT_PAGE_SIZE` |
  | 配置文件名 | 组件 ID 的 `/` 换成 `-` | `config/people-basic.yaml` |

  这条规则是**双向**的：看到 `people/basic` 能算出变量名，看到 `PEOPLE_BASIC_ENDPOINT` 也确切知道它指向哪个组件。默认值也是约定：不写 `expose` 就不对外，不写 `mode` 就跟着上层走。
- **BrickKit 不做什么：**
  - **不替你做决定：** 用哪个版本、暴露哪个端口、要不要启用某个组件，平台从不猜，必须你写明（见原则「[显式优于隐式](#7-显式优于隐式)」）。所以 BrickKit 自己的说法是"派生优于配置"：能从你写的内容**算出来**的才派生，算不出来的，你来写。
  - **不提供依赖别名：** 曾有人提议给依赖起个别名（`as: iam`）。别名只保住了双向关系的一半——`IAM_ENDPOINT` 没法追溯到它指向哪个组件，而排查"地址指错了"恰恰从这里开始。
    槽位家族要的"由项目决定指向谁"用 `$endpoint:` 表达：配置项名字仍由组件定，指向谁写在 `config/` 或 `vars.yaml` 里，打开就看得到（见 [另一个组件的地址](../../docs/zh/01-three-layers/06-vars-and-var-ref.md)）。
  - 代价也是真实的：组件 ID 会原样变成每个调用方代码里的变量名，所以取名要用领域自己的词，别用实现细节的词。
- **AI 怎么应对：**
  - 变量名照规则推算，别让 AI 凭印象起。先让它读 `component.yaml` 里的 `dependencies`，再推变量名。
  - 版本、是否对外暴露、是否启用这类决定，要求它明确写下来。
  - 给组件取 ID 时，用业务的词。

### 6. 十二要素配置

**它是什么：** "十二要素"是一份写云上应用的经验清单，其中三条和配置有关：配置存在环境里（要素 III）、数据库和缓存这类后端服务当作可以随时换的"附加资源"（IV）、开发环境和生产环境尽量一样（X）。最常被引用的是第一条：配置（数据库地址、密码、别的服务在哪）不写死在代码里，而是在程序启动时从环境变量里读。

- **好处：**
  - 同一个镜像放到测试环境、生产环境都能跑，环境之间的差别只在"启动时给了哪些环境变量"。
  - 密码不进代码仓库。
  - 环境变量所有语言都能读，不依赖任何库。
- **代价：**
  - 环境变量只是一串扁平的文字，复杂的配置得自己编码解码。
  - 变量一多就难管；漏了，往往到程序真正用到它的那一刻才发现。
  - 改了配置还得重启才生效。
- **AI 开发的痛点：** AI 要处理不同环境的配置差异，一不小心就把地址、密码写进代码。
- **BrickKit 怎么做：**
  - 组件需要知道的一切，都以环境变量交给它：依赖地址（`*_ENDPOINT`）、平台通用变量（`COMPONENT_ID`、`COMPONENT_VERSION`）、组件自己的配置（`configSchema` 的键）。数据库地址、口令也只是组件的普通配置项。
  - Docker 和 Kubernetes 上的地址格式完全相同，换环境只换一份部署文件，组件代码零改动。环境之间不同的值，用 `$var:` 引用公共变量，由各环境的部署文件在 `vars:` 里给出。
  - `up` 时就查："漏了才发现"的代价被提前到部署那一刻——写错的配置键会警告，并猜你想写哪个；必填、没有默认值、项目里又没填的配置项，会直接拦下 `up`；配置键名撞上平台保留的变量，会警告并跳过（平台注入的值优先）。
  - 全部变量的完整清单见[环境变量注入契约](../../docs/zh/06-architecture/03-env-injection-contract.md)。
- **BrickKit 不做什么：**
  - **配置中心、热更新：** 那是长连接、推送、版本比对的一整套重机制；而连接池大小、超时这类基础配置，本来就只有重启才能安全生效。改配置就改 `config/`，再 `brickkit up`。真要毫秒级热更新的业务开关，组件自己去轮询就行。
  - **校验配置的值：** `configSchema` 只是说明书，见 [9. 契约式设计](#9-契约式设计)。
  - **隐式的环境变量覆盖：** 进程环境里恰好有个同名变量，不会悄悄盖掉 `config/` 里写的值；只有你显式写了 `${VAR}` 的地方才读环境。
- **AI 怎么应对：**
  - 只用 `os.environ.get()`（Java 是 `System.getenv()`）读变量；先读 `configSchema` 知道有哪些键、默认值是什么。
  - 弱依赖的变量可能根本不存在，绝不能写 `os.environ["X"]`，否则缺失时启动即崩（见 [10. 大声失败](#10-大声失败)）。
  - 声明成 `array` 或 `object` 的配置项，注入到容器里是一行 JSON，组件自己解析。
  - 改了配置，要 `brickkit up` 重启才生效。

**例：** 组件读配置的样子——强依赖、弱依赖、自己的配置，三种读法：

```python
import os

people = os.environ.get("PEOPLE_BASIC_ENDPOINT")             # 强依赖：一定存在
bus = os.environ.get("INFRA_REDIS_EVENT_BUS_ENDPOINT")       # 弱依赖：没在跑时根本不存在
page_size = int(os.environ.get("DEFAULT_PAGE_SIZE", "20"))   # 自己的配置：有默认值兜底

if not bus:
    ...  # 降级：怎么降级是组件自己的业务逻辑
```

### 7. 精确版本与锁文件

**它是什么：** 依赖别人的软件时，版本可以写成"范围"（如 `^1.0.0`，意思是"1.x 里最新的都行"），也可以写死一个具体版本（`1.0.0`，格式是 `主版本.次版本.补丁`）。锁文件（如 npm 的 `package-lock.json`）则是把第一次装出来的具体版本记下来，以后照着装。

- **好处：**
  - 今天装出来的和三个月后装出来的是同一份，不会因为别人发了个新版本，你的生产环境半夜悄悄变了。
  - 出问题时，确切知道跑的是哪一版，回滚也有明确的目标。
- **代价：**
  - 补丁和安全修复不会自己到来，升级得你动手。
  - 长期不升级，会落后很多。
- **AI 开发的痛点：** AI 做"破坏性修改"（新版本和旧版本不兼容），会连累所有依赖它的组件；它也可能顺手写出 `^1.0.0` 或 `latest`。
- **BrickKit 怎么做：**
  - 只认精确版本：`^1.0.0`、`~1.0.0`、`latest` 都会在解析阶段直接报错，不拖到运行时。
  - `brickkit.yaml` 本身就是锁文件：`brickkit add people/basic` 不写版本时，CLI 在那一刻查一次最新的可安装版本，把它作为**精确版本**写进去。和"配置里写范围"的区别在于解析发生的时间：只解析一次，而不是每次都解析。升级是一条显式的命令（`brickkit upgrade`），它同时迁移配置。
  - 版本号进入服务名：`people-basic-1-0-0` 和 `people-basic-2-0-0` 是两个不同的 DNS 名字，可以并排运行、互不冲突。
  - 变量名不带版本，变量**值**带版本：`DEPARTMENT_TREE_ENDPOINT=http://department-tree-1-0-0:8080`。调用方永远知道自己在跟哪一版说话，不存在隐式升级。
- **BrickKit 不做什么：**
  - **版本范围解析：** 范围是"我机器上能跑、生产上炸"的常见原因。
  - **一个组件里并排写两个版本：** 同一份 `component.yaml` 的 `dependencies` 里，同一个组件 ID 只能出现一次——变量名不带版本，写两个版本会撞上同一个 `*_ENDPOINT`。所以"并排共存"是**项目级**的能力，不是组件级的：不同的调用方各自依赖不同的版本，`brickkit.yaml` 就把两个版本都留下，并用 `requiredBy` 写明为谁而留。
  - **并排版本之间的数据兼容：** 平台只提供一块物理上的缓冲，破坏性变更是组织之间的协调问题，数据层是否兼容是你自己的责任。
- **AI 怎么应对：**
  - 让 AI 写 v2 时，新版本和 v1 并排跑，再慢慢把调用方迁过去；别覆盖 v1。
  - 让它永远写精确版本，不接受 `^` 或 `latest`。
  - 两个版本共用一个数据库时，迁移是否向下兼容要你和 AI 自己保证；迁移状态表的主键要包含组件标识。

**例：** 两个版本并排，`brickkit.yaml` 里是这样（详见[多版本共存](../../docs/zh/03-component-guide/09-multi-version-coexistence.md)）：

```yaml
components:
  - id: demo/hello
    version: 1.1.0
  - id: demo/hello
    version: 1.0.0
    requiredBy: [demo/caller]
```

### 8. 契约先行

**它是什么：** 两个团队要对接，先把"接口长什么样"写成一份文件（HTTP 接口常用 OpenAPI，gRPC 常用 protobuf），双方各自照着实现，而不是写完一边、再让另一边去猜。像先约好插头的形状。

- **好处：**
  - 双方可以并行开发。
  - 不读实现代码，就知道组件对外承诺了什么。
- **代价：**
  - 契约文件要有人维护。
  - 契约与实现对不上的时候，比没有契约更糟——读的人信了一份过期的说明。
- **AI 开发的痛点：** AI 想调用另一个组件，只能去翻它的源码，靠猜。而源码里的内部实现并不是对外的承诺，依赖方一重构，AI 写的调用就坏了。
- **BrickKit 怎么做：**
  - 组件用 `artifacts` 把契约文件随版本一起发布，`brickkit add` 和 `brickkit fetch` 会把它们下载下来。`fetch` 只下载产物，不改 `brickkit.yaml`、不部署——用于调用另一个项目里的服务。
  - 平台唯一的职责是确保 `files` 里的东西真的能送到要它的人手里。
  - 详见[契约与产物](../../docs/zh/03-component-guide/06-artifacts-and-contracts.md)。
- **BrickKit 不做什么：**
  - 不规定用哪种格式：`type` 和 `format` 是 CLI 从不解析的自由字符串（OpenAPI、protobuf、你自己的什么都行）。要解析格式，平台就得先理解 OpenAPI 和 protobuf。
  - 不检查实现是否真的符合契约。契约与实现是否一致，是组件自己的事。
- **AI 怎么应对：**
  - 让 AI 读依赖方的契约文件，别读它的源码——这样依赖方怎么重构都波及不到它。
  - 先写契约，再写实现；契约与实现是否一致，靠你自己写的契约测试来验证（见[测试策略](../../docs/zh/09-patterns/02-testing-strategy.md)）。

**例：** 一条产物声明：

```yaml
artifacts:
  - type: api-contract
    format: openapi
    description: HTTP 接口
    files:
      - api/openapi.yaml
```

### 9. 契约式设计

**它是什么：** 每个函数或模块写明"我要求输入满足什么条件、我保证输出满足什么条件"，违反就立刻报错。像电器铭牌上写着"输入 220V、输出 12V"，接错了就跳闸。英文名 Design by Contract。

- **好处：**
  - 错误在离原因最近的地方被抓住。
  - 这些规则本身就是最精确的说明书。
- **代价：**
  - 规则写得太严，合法但没想到的用法也会被挡在门外；写得太松，等于没写。
  - 每次运行都检查，有开销。
  - 规则本身也要维护。
- **AI 开发的痛点：** AI 不知道一个组件接受哪些配置、什么取值范围，只能凭印象。
- **BrickKit 怎么做：** 只借"写下来"这一半。BrickKit 里最接近它的是 `configSchema`——严格说只是近亲，因为它只描述、不强制。
  - 组件用它写明自己有哪些配置项、什么类型、默认值、允许什么取值范围（`enum`、`minimum`、`maximum`、`pattern`），人和 AI 都读得到。
  - CLI 检查 `config/` 里写的配置键**名字**是否存在于 `configSchema`：写错会警告，并猜你想写哪个。组件根本没声明 `configSchema`、`config/` 里却写了配置时，整份配置都不会生效，同样会警告。
  - 必填（`required`）、没有默认值、项目里又没填的配置项，会直接拦下 `up`，并点名是哪个组件的哪一项。
- **BrickKit 不做什么：**
  - **不检查配置的值。** 例如声明成 `type: integer` 的项被填成了字符串，CLI 不会拦；组件拿到字符串去 `int()` 才崩溃——发现的时间点是运行时，而不是 `brickkit up` 那一刻。
  - 分界线在于有没有运行时的安全网：值写错了，组件自己会崩，你一定会发现；名字写错了，变量只是悄悄不存在，组件走默认分支照常运行，没有任何东西提醒你。所以名字要查，值不查。
  - 而且一旦开始校验值就停不下来——枚举？范围？正则？JSON Schema 的能力很大，CLI 会越长越胖。值写错了怎么办（报错、降级、用默认值），也该由组件自己决定。
  - 详见 [configSchema 设计准则](../../docs/zh/03-component-guide/03-config-schema-design.md)。
- **AI 怎么应对：**
  - 让 AI 先读 `configSchema` 再写读取配置的代码，键名和默认值以它为准。
  - 配置值的校验（范围、枚举），让它写在组件启动时，失败就立刻退出，并给出清楚的报错。
  - 别让它把 `configSchema` 里的 `minimum` / `maximum` 当成平台会强制执行的东西。

**例：** 一段 `configSchema`，以及 `config/` 里把键名写错时 CLI 的真实警告：

```yaml
configSchema:
  type: object
  properties:
    QUOTE_PREFIX:
      type: string
      default: "今日名言："
      description: 名言前面加的前缀
```

```text
⚠️ demo/quote@0.1.0：QUOTE_PREFX 不在组件的 configSchema 里，不会生效
   文件：config/demo-quote.yaml
   已声明的配置项：QUOTE_PREFIX
   建议：是不是想写 QUOTE_PREFIX？
```

### 10. 大声失败

**它是什么：** 程序发现自己不对劲时，立刻、明显地停下来报错，而不是假装没事继续往下跑。英文叫 fail fast。

- **好处：**
  - 错误暴露在最早、离原因最近的时候。
  - 最坏的 bug 不是崩溃，而是"悄悄给出一个看起来正常的错误答案"：崩溃你一定会注意到，错误答案不一定。
- **代价：**
  - 更严格意味着更多"拒绝"：一个多写了未知字段的文件、一个没做防御的组件，本来也许能凑合跑，现在直接起不来。
- **AI 开发的痛点：** AI 的错误处理常只覆盖正常情况，弱依赖缺失、迁移失败这类边界情况容易被漏掉。
- **BrickKit 怎么做：** 把错误尽量提前到 `up` 的那一刻，并且说清是哪里、为什么（这也是十条原则的第一条，见「[大声失败](#1-大声失败)」）：
  - 三层文件和 Manifest 里出现不认识的字段，直接拒绝，而不是悄悄忽略。
  - 依赖里写了版本范围，解析阶段就报错。
  - 强依赖缺失，`up` 拒绝生成任何东西；必填配置没有值、升级留下的配置冲突没解决，`up` 拦下。
  - 迁移失败，主服务不会启动，报错点名是哪个组件的迁移。
  - **最典型的是弱依赖：** 一个缺失的弱依赖**什么变量都不注入**，而不是注入一个空字符串。
- **BrickKit 不做什么：**
  - **不替组件决定怎么降级。** 缓存挂了，有的组件改查数据库，有的返回空列表，有的写本地文件稍后重试——这是纯业务判断，平台没法统一定义"降级"。平台唯一的动作，就是不注入对应的变量。
  - 代价也是真实的：组件读这个变量时若直接写 `os.environ["X"]`，变量缺失就启动即崩。这是刻意的：宁可启动时大声崩，也不要运行时悄悄错。
- **AI 怎么应对：**
  - 明确要求它处理"弱依赖缺失"和"迁移失败"这两个最容易漏的边界。
  - 弱依赖的变量用 `.get()` 读，并写明缺失时怎么办。
  - 入口对不认识的参数立刻报错退出。迁移容器和主服务用的是同一个镜像，只靠命令行参数区分；如果入口对未知参数"照常启动服务"，写错的迁移命令就会让迁移容器变成第二个服务，永远不退出，整个部署卡住，而它自己的日志还说一切就绪。

**例：** 为什么缺失时不能注入空字符串。开发者忘了检查空值，写了 `requests.get(f"{ENDPOINT}/healthz")`：如果注入的是空字符串，拼出来就是 `/healthz`，请求会打到容器**自己**的端口，而它自己的 `/healthz` 返回 200——开发者于是误以为那个弱依赖是健康的。这类 bug 极难查。所以平台选择让变量根本不存在，让组件在启动时就大声崩。

### 11. 最小权限

**它是什么：** 每个程序、每个组件只拿到完成工作所需的最少访问权限，其余一律默认不通。像宾馆的房卡，只能开你自己那间房。在网络安全里它常和"零信任"一起被提起。

- **好处：**
  - 某个组件被攻破，或者只是出了 bug，它能碰到的东西有限，损失被限制在小范围里。
- **代价：**
  - 每一条允许的访问都要明确写出来。
  - 漏放一条，就是一次"莫名其妙连不上"的排查。
- **AI 开发的痛点：** 出了 bug 或被攻破，组件能碰到的东西越多，损失越大。
- **BrickKit 怎么做：**
  - **默认不可达：** 部署文件里不写 `expose`，就没有对外入口（Docker 上不映射宿主机端口，Kubernetes 上不生成 Ingress）。
  - **网络策略：** 在 Kubernetes 上，部署文件写 `k8s.networkPolicy.enabled: true`，就会从依赖图直接算出网络策略——流量只沿着你声明过的依赖方向放行，不需要另外手工维护一份访问控制列表。依赖图之外的访问者（比如 Ingress 控制器、另一个团队的命名空间），用 `allowFrom` 手写放行。
  - **ServiceAccount：** `k8s.serviceAccount.enabled: true` 会给每个组件一个单独的 ServiceAccount，且不挂载令牌。
  - CLI 本身从不挂载 Docker socket。
  - 见[安全与签名](../../docs/zh/06-architecture/08-security-and-signing.md)。
- **BrickKit 不做什么：**
  - **不默认开启**网络策略、ServiceAccount 隔离和 `podSecurity: restricted`：每一项都可能让一个本来能跑的组件起不来，这是真实的、因项目而异的代价，平台没法替你权衡。
  - **验证不了网络策略是否生效：** 很多集群接受这些对象却完全不执行——`kubectl apply` 成功、`kubectl get networkpolicy` 看得见，流量却照样畅通无阻，而且没有任何报错。minikube 和 kind 的默认网络插件（CNI）就属于这一类。Kubernetes 没有提供查询这件事的 API，平台测不出来，所以 `brickkit up` 每次都会提醒你自己验一次。
- **AI 怎么应对：**
  - 让 AI 只声明真正需要的依赖：依赖越少，放行的路越少。
  - 只有需要对外提供服务时，才写 `expose`。
  - 要不要开启网络策略和 ServiceAccount 隔离，由人来判断；开启之后，验证"授权的路径照常能用、未授权的路径真的被挡住"，别只看生成的 YAML 说得通。

**例：** 给 `demo/hello@1.0.0` 自动生成的网络策略——`demo/caller` 是它唯一的调用方，所以放行的来源只有它，端口只有 `demo/hello` 自己监听的那个：

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
spec:
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: demo-caller-1-0-0
      ports:
        - port: 8080
          protocol: TCP
  podSelector:
    matchLabels:
      app: demo-hello-1-0-0
  policyTypes:
    - Ingress
```

### 12. 供应链安全

**它是什么：** 你安装的第三方组件，是不是真的出自它声称的作者？有没有在半路被人调包？像快递上的封条加发件人签名。

- **好处：**
  - 能防止冒名顶替。
  - 能防止传输途中被篡改。
- **代价：**
  - 签名只能证明"这是谁发的、没被改过"，不能证明"发的东西没有恶意"。
  - 你还得自己管理"信任哪些公钥"，发布者也要保管好私钥。
- **AI 开发的痛点：** 让 AI 引入第三方组件时，来源难以核实。
- **BrickKit 怎么做：**
  - **Git 源：** 组件来自哪个仓库，由你在 `brickkit.yaml` 的安装源里写明；它的可信程度就是那个仓库、那个托管平台的可信程度。
  - **市场组件的签名：** 发布者用 cosign 签名（`brickkit publish --sign --key ...`）。真正被签名的是一份"规范化载荷"——Manifest 解析后按固定规则重新编码——所以注释、缩进、键的顺序改了，都不会让签名失效。
  - **镜像摘要：** `brickkit publish` 默认先把可变的镜像 tag 解析成摘要再签名，这样签名覆盖的是一个事后没法被悄悄改指的引用；要跳过得显式加 `--no-pin-digest`。
  - **安装：** 安装方只用 Go 标准库验签，不需要装 cosign。信任的公钥配在你自己项目 `brickkit.yaml` 的 `installer.publicKeys` 里，`requireSignature` 默认为 `true`。
  - 见[安全与签名](../../docs/zh/06-architecture/08-security-and-signing.md)。
- **BrickKit 不做什么：**
  - **不做事前审查：** 不扫描、不沙箱、不做静态分析。安装即信任，和 npm、VS Code 插件市场、GitHub 是同一套模型。事后发现恶意组件，唯一的手段是在市场上把它标成 `blocked`，阻止新的安装。
  - **不从市场取公钥：** 否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉，验证照样通过，等于市场给自己发证书。
  - **注意：** 一把公钥都没配，签名验证就是**完全关闭**的，`requireSignature: true` 也不起作用（CLI 会警告）。
- **AI 怎么应对：**
  - 引入新组件、往 `publicKeys` 里加信任的公钥，都由人来确认，别交给 AI。
  - 别让 AI 为了"让安装通过"而关掉 `requireSignature`，或删掉 `publicKeys`。

### 13. 类型驱动开发

**它是什么：** 用编程语言的类型系统把规则"写进代码的形状里"，让错误的写法根本编译不过。比如订单金额不用随便一个数字，而用一个专门的"金额"类型，这样就不会误把"数量"当"金额"传进去。

- **好处：**
  - 一大类错误在编译时就被挡住了，不用等到运行才发现。
  - 类型本身就是一份不会过期的文档。
- **代价：**
  - 依赖语言：不是所有语言的类型系统都足够强（动态语言可以靠类型注解加检查器，比如 Python 的类型注解加 mypy，拿到一部分好处）。
  - 类型设计本身也要花功夫，设计得不好会变成负担。
- **AI 开发的痛点：** AI 写的代码读起来通顺，但对不对，光看代码看不出来，得有机器去查。
- **BrickKit 怎么做：** 没有，也不需要。BrickKit 的 CLI 自己是用 Go 写的，受益于类型检查，但并不要求组件也这样。
- **BrickKit 不做什么：**
  - **不限制语言，而且是最彻底的一种不限制：** 任何能构建出容器镜像的语言都行。仓库自带的测试组件就有好几种：Python、Go、nginx 托管的纯 HTML。语言无关是这个平台的核心价值之一。
  - **不提供 SDK：** 平台在组件代码里唯一的痕迹，是读环境变量。因此平台交给组件的一切都是**字符串**（数字、布尔值也是），转成类型是组件自己的事。
- **AI 怎么应对：**
  - 选一门带类型检查的语言让 AI 写，让编译器（或类型检查器）当第一道关：写完先过编译，再谈别的。
  - 在组件启动时，把环境变量一次性读成一个有类型的配置结构，缺了必需项就立刻启动失败，并一次列出缺了哪几个，别悄悄退化成默认值（见 [10. 大声失败](#10-大声失败)）。

**例：** 类型怎么让错误的写法编译不过（Go）：

```go
type Cents int64   // 金额，单位：分
type Quantity int  // 数量

func charge(amount Cents) { /* ... */ }

var qty Quantity = 3
charge(qty) // 编译不过：Quantity 不能当 Cents 用
```

### 14. TDD 与 BDD

**它是什么：** TDD（测试驱动开发）是先写测试，再写让测试通过的代码：先让测试变红，再写实现让它变绿。BDD（行为驱动开发）是先用接近日常语言的"给定……当……则……"描述期望的行为，再把它变成测试。像先写好验收标准，再开始做菜。

- **好处：**
  - 测试成了对"代码该做什么"的约束，而不是对"代码已经做了什么"的复述。
  - 需求变得可以检验。
- **代价：**
  - 前期要投入时间。
  - 如果验收标准本身写错了，你会非常认真地把错的东西做出来。
- **AI 开发的痛点：** 让 AI 先写实现、再补测试，测试就成了对实现的复述——测的只是"代码做了它做的事"。而且 AI 生成的测试常只测正常场景，边界场景容易漏。
- **BrickKit 怎么做：** 不强制，但给了建议：
  - [测试策略](../../docs/zh/09-patterns/02-testing-strategy.md)讲怎么给组件分层测试：契约测试（接口的形状）、业务规则测试（不变量、幂等、合法的状态迁移）、单元测试（这一版实现的分支）、集成测试（接真实依赖跑端到端）。区分业务规则测试和单元测试只需要一条判据：把实现整个删掉、换一种语言重写，这条测试还应该成立吗？成立就是业务规则测试。
  - 还给了一个"先立规格、再写实现"的推荐顺序（见下表）。BrickKit 的组件恰好有三份不依赖实现的规格，都写在 `component.yaml` 里：`configSchema`、`dependencies`、契约文件。
  - BrickKit 独有的一点是 `brickkit up --dry-run` 与 `brickkit lint`：不起任何容器，就能检查组件与项目的三层文件是否对得上（比如配置项名写错、必填项没填）。
- **BrickKit 不做什么：**
  - 不要求也不检查怎么测试：测试策略从来不在平台的管辖范围内，这是组件自治的一部分。
  - `--dry-run` 查的是**装配对不对**，不是**组件代码对不对**。
- **AI 怎么应对：**
  - 按顺序来：先规格，再测试、看着它们变红，最后才让 AI 写实现。红得要有理由：如果测试第一次运行就是绿的，说明它什么都没测到。
  - 把业务规则先写成一句"给定……当……则……"，再翻成测试。比如"给定一个还没处理过的幂等键；当两个带着同一个幂等键的请求同时到达；则只有一个真正执行，另一个拿到同一份结果"——这句话本身就是给 AI 最精确的提示。
  - AI 常只测正常场景，边界场景要你自己补，或者明确要求。
  - 集成测试要打真实依赖跑一遍，别只信替身（mock）。

**例：** 推荐的顺序，每一步都有真实的反馈：

| 步 | 做什么 | 怎么知道这一步对了 |
| --- | --- | --- |
| 1 | 把 `component.yaml` 写完整：`dependencies`、`configSchema`、契约文件 | `brickkit lint`、`brickkit up --dry-run`（不起容器） |
| 2 | 照契约文件写契约测试 | 此时必须全红，而且红得有理由 |
| 3 | 把每条业务规则先写成一句话，再翻成测试 | 同样必须先红 |
| 4 | 让 AI 写实现，直到契约测试、业务规则测试全绿 | 测试就是验收，不需要人逐行读实现 |
| 5 | 补单元测试：当前这版实现的各条分支 | 分支都走到 |
| 6 | 跑集成测试：`brickkit up` 起真实依赖，走一遍真实链路 | 端到端跑通 |

---

### 15. 属性测试

**它是什么：** 普通测试是你手写几个例子：输入 A 应该得到 B。属性测试换一种思路：你描述"无论输入是什么，结果都应该满足的性质"（比如"排序之后的列表一定是有序的，而且长度不变"），再让工具随机生成成千上万组输入，去找出违反这条性质的反例。

- **好处：**
  - 能撞出你自己想不到的边界情况。
  - 找到反例后，工具通常会把它缩小到最小的能复现的样子。
- **代价：**
  - 想清楚"性质"本身不容易。
  - 随机测试的失败要能复现，所以得记录随机种子。
  - 对大量依赖外部系统的代码不太好用。
- **AI 开发的痛点：** AI 生成的测试常只覆盖它自己想到的那些正常场景。
- **BrickKit 怎么做：** 平台自己在用。CLI 里规则最密的三处，都有用随机输入去验证的测试：
  - **启停判定：** 用数千个随机小图（涵盖 `mode` 的每种取值、强弱依赖、弱依赖成环、多个上层共享），去对拍一份独立写的暴力参照答案。这份参照物不复刻平台的传播算法，而是枚举全部候选集合，取满足文档逐条规则的最大集合——两边只共享规则、不共享算法。
  - **启动顺序：** 验证"依赖先于依赖方""每个组件恰好一次""删掉全部弱依赖边，顺序不变""打乱输入顺序，结果相同"这些性质。
  - **资源配额合并：** 验证逐字段的优先级、`limits` 没有默认层、把结果再合并一次不变。
  - 全部固定随机种子，失败信息带种子，可以原样复现；不依赖任何新库。
  - 对组件，只在[测试数据](../../docs/zh/09-patterns/03-seed-data.md)里提到过：属性测试适合"核心不变量"（比如余额永远不为负、状态机不会走到非法的迁移）。
- **BrickKit 不做什么：**
  - 不要求、也不推荐给组件：适用面比较窄，主要适合核心不变量；对多数业务代码，普通的例子测试就够了。
  - 不提供属性测试的框架或库：平台自己用的是标准库的随机数。
- **AI 怎么应对：**
  - 有核心不变量时，先用一句话把它写下来（"账户余额永远不为负"），再让 AI 据此写属性测试。
  - 其余情况不必：别为了用而用。

## 十条原则

每条原则按同一个格式写：**是什么**、**换来了什么**、**付出了什么**、**拒绝了什么**。判断一个设计提议合不合适，就拿它逐条对照。

### 1. 大声失败

**是什么：** 配置冲突、必填缺失、重复的键、推送失败，都在操作的那一刻报出来，不留到运行时才暴露。报错说清是哪个文件、哪一项、为什么，以及接下来怎么办。

**换来了什么：** 最坏的 bug 不是崩溃，而是一个看起来正常、其实错了的结果——配置悄悄没生效、依赖地址悄悄是空的。把失败提前到 `up`、`lint` 那一刻，错误离原因最近，修起来最便宜。

**付出了什么：** 更多"拒绝"。一个多写了未知字段的文件、一份升级留下的冲突、一个没填的必填项，本来也许能凑合跑，现在直接跑不起来——你必须先处理它。

**拒绝了什么：** 悄悄忽略未知字段；给缺失的弱依赖注入空字符串；配置冲突时"后写的覆盖先写的"；推送失败后留下一个只在本地的 tag。

### 2. 平台极简

**是什么：** 平台只做机械的事——解析、派生、生成、交给引擎——不猜语义：不猜配置项被改了名、不做类型转换、不替组件决定怎么降级。

**换来了什么：** 平台小，规则少，每一条都能用一句话说清；CLI 用完即走，没有常驻进程，也就没有单点故障、没有要运维的服务、没有监听端口。

**付出了什么：** 很多"顺手就能做"的事，平台不做，要组件自己写：重试、熔断、降级、配置值的校验。升级时配置项改了名，平台当成"删一个、加一个"，要你自己搬。

**拒绝了什么：** 注册中心、配置中心、API 网关、服务网格、健康检查轮询、多租户、配置值的类型校验、升级时猜测重命名。

### 3. 所见即所得

**是什么：** 没有隐式覆盖。你打开的那份文件，就是实际生效的配置。

**换来了什么：** 读一个文件就能知道结果，不用在脑子里合并好几层。`config/` 里写了 `DB_HOST: pg.internal`，组件拿到的就是它——不会被进程环境里恰好同名的变量悄悄盖掉；本地模式读的是整份 `deploy.local.yaml`，不是"团队文件 + 个人补丁"的合并结果。

**付出了什么：** 重复。每个环境一份完整的部署文件，条目会有重复；团队文件改了，你的 `deploy.local.yaml` 要 `refresh` 一次再把本地修改抄回去。

**拒绝了什么：** 多环境的继承与合并（overlay）；环境变量隐式覆盖配置文件；稀疏的个人覆盖文件；把三层合成一份的"最终视图"命令。

### 4. 组件自治

**是什么：** 组件需要什么配置、怎么降级、日志长什么样、用什么语言、内部怎么分层，都由组件自己决定。平台对组件只有三个要求：一份 Manifest、一个健康检查、从环境变量读配置。

**换来了什么：** 任何能构建成容器镜像的东西都能成为组件；组件代码里没有任何平台 SDK，零侵入；换一个平台，组件一行都不用改。

**付出了什么：** 平台帮不了组件内部：值写错了、降级写漏了、日志格式五花八门，平台都不管。质量靠组件作者，而不是靠平台兜底。

**拒绝了什么：** 平台 SDK；规定组件的内部结构；替组件校验配置的值；替组件决定弱依赖缺失时怎么办。

### 5. 职责单一

**是什么：** 三层文件各管一件事：`brickkit.yaml` 管"用哪些组件、哪个版本"，部署文件管"部署到哪、怎么跑"，`config/` 管"配成什么值"。同一个事实只写在一个地方。

**换来了什么：** 一次改动落在哪一层，一看就知道；一件事只有一处可改，就不会出现两处说法不一致。多环境只需要多几份部署文件，组件列表和配置不用复制。

**付出了什么：** 文件变多了。第一次接触的人要先弄懂哪件事归哪一层。

**拒绝了什么：** 一个大而全的单文件；在两处写同一件事（比如在 `brickkit.yaml` 里再列一遍外壳成员、在组件条目上再写一遍部署方式）。

### 6. 原子性操作

**是什么：** `add`、`remove`、`upgrade`、`release` 要么完全成功，要么回到原样，不留半成品。

**换来了什么：** 命令失败时你不用收拾残局。`add` 改了三层文件之后项目装载不了，三份文件全部还原；`release` 推送失败，本地刚打的 tag 被删掉；`upgrade` 不点名时升级所有组件，要么全做、要么一个都不改。

**付出了什么：** 实现要先在内存或副本里把事情做完、验证通过，才写回真正的文件；有的操作因此比"边做边写"慢一点，也更难写。

**拒绝了什么：** 改到一半停下的文件；"部分成功"的批量操作；只在本地存在、从没到过远端的发布。

### 7. 显式优于隐式

**是什么：** 精确版本、`$var:` 显式引用、显式暴露端口、显式开启本地模式。平台拒绝"自动猜"。

**换来了什么：** 每个值从哪来都写在纸面上，出了问题顺着写下的东西就能查到；同一份声明在谁的机器上、什么时候运行，结果都一样。

**付出了什么：** 要多写。每个公共变量都要写一次 `$var:`，每个对外端口都要写一次 `expose`，版本号要一个个写死。

**拒绝了什么：** 版本范围（`^1.0.0`、`latest`）；按名字自动去公共变量里兜底；默认对外开放端口；按名字决定哪个配置项走密钥通道（那只由 `secret: true` 决定）。

### 8. 概念一致性

**是什么：** 一个组件的项目和五十个组件的项目，用同一套三层文件；一个组件在独立开发时，它自己也是一个同样的项目。没有"单文件模式"、没有"简化模式"。

**换来了什么：** 学一次就够用到底：小项目长成大项目，不需要迁移到另一种写法；组件作者和项目管理者说同一种语言。

**付出了什么：** 最小的项目也要三层文件（`init` 会替你生成），对只想跑一个组件的人显得多了一点。

**拒绝了什么：** 为小项目准备的单文件简化写法；只在某种规模下才存在的特殊概念。

### 9. 构建与部署分离

**是什么：** 构建镜像是你的显式动作（`brickkit build`），`brickkit up` 绝不自动构建。

**换来了什么：** `up` 永远可预期：它只运行已经存在的镜像，不会在你没打算的时候把一份改到一半的代码打进镜像跑起来。镜像的 tag 跟着组件版本走（`<scope>-<name>:<版本>`，或者给没带 tag 的 `image` 补上 `:<版本>`），跑的是什么一目了然。

**付出了什么：** 多一步命令。改了代码忘了 `build --force`，跑的就还是旧镜像——`up` 只能提示镜像缺失，看不出镜像"旧了"（外壳镜像例外：编进的成员版本有标签可核对）。

**拒绝了什么：** `up` 发现镜像不存在就顺手构建；在部署流程里隐式地编译代码。

### 10. 按需检索优于全量合并

**是什么：** 不提供"把三层合成一份"的视图命令。要知道什么，就去读负责它的那一层——用哪个版本看 `brickkit.yaml`，怎么跑看部署文件，配成什么看 `config/`，谁依赖谁用 `brickkit deps` 或 `brickkit graph` 问。

**换来了什么：** 每个问题都有唯一的答案来源，不会出现"合并视图"和原文件说法不一致；AI 助手也只需读回答当前问题的那一层，而不是每次吞下一整份合并结果。

**付出了什么：** 想一眼看到"一个组件的全部情况"，要看两三个文件（`up --dry-run` 生成的部署文件是最接近的全貌）。

**拒绝了什么：** 合并三层的"最终配置"视图命令；把依赖关系抄进 `brickkit.yaml`（它们本来写在各组件的 `component.yaml` 里）。

# Git 仓库缓存

## 为什么不每次 `git clone`

Git 安装源上，一个组件一个仓库、一个版本一个 tag。CLI 要读某个版本的 `component.yaml`、契约文件，最直接的做法是每次克隆一遍仓库——
项目里二十个组件就是二十次完整克隆，每次 `up`、每个项目、每个组件的本地工作台都来一遍。

BrickKit 的做法是：每个组件仓库在本机只克隆**一次**，存成一个 **bare 仓库**（只有 Git 的数据，没有检出的工作区），之后只做增量的 `git fetch`；
要读某个版本的文件，直接从 bare 仓库里的那个 tag 取（`git show <tag>:component.yaml`），不需要检出。

## 放在哪

用户级的缓存目录，按完整的仓库地址分目录：

```text
~/.cache/brickkit/repos/
└── git.example.com/
    └── components/
        ├── demo-hello.git
        └── demo-quote.git
```

（macOS 上是 `~/Library/Caches/brickkit/repos/`。）不放在项目的 `.brickkit/` 里，是因为同一个组件仓库会被很多项目、以及组件自己的工作台共用——
放在每个项目里，同一个仓库就要克隆 N 次。按完整地址命名，不同组织下同名的仓库（`github.com/a/erp-api` 与 `github.com/b/erp-api`）不会撞在一起。

## 读取的四级优先级

要一个组件版本的 `component.yaml` 时，CLI 依次尝试，前一级有就不往下走：

| 级 | 从哪取 | 网络 |
| --- | --- | --- |
| 1 | 项目的 `.brickkit/manifests/<组件>/<版本>/` 永久缓存 | 不需要 |
| 2 | 缓存的 bare 仓库里的这个 tag（`git show`） | 不需要 |
| 3 | `git fetch --tags`：仓库在，但还没有这个 tag | 增量 |
| 4 | `git clone --bare`：这个仓库从没克隆过 | 完整克隆 |

来自本地安装源的组件不走这条路：本地源里的 `component.yaml` 每次都从目录里重新读，从不缓存——改了它，下一次命令就按新的来。

## 一次取文件的完整流程

1. 查项目的 Manifest 缓存。命中就结束。
2. 算出仓库地址：安装源的 `baseUrl` 加 `<scope>-<name>`；组件条目写了 `source.repo` 时用它。组件在仓库子目录里时，tag 带命名空间 `<scope>-<name>/<版本>`。
3. 确保 bare 仓库在缓存里：不在就克隆。克隆先落到缓存目录下的一个临时位置，完成后再改名——中途失败或被打断，不会留下半个仓库。
4. 仓库里有这个 tag，直接读 tag 里的文件。
5. 没有，就 `git fetch --tags` 取一次增量（一次运行里同一个仓库只取一次），再读。tag 被强制移动过时以远端为准；远端删掉的分支在缓存里也删掉。
6. 把读到的 `component.yaml` 写进项目的永久缓存，连同那个 tag 里组件目录下的每一份 `BRICKKIT*.md`——`BRICKKIT.md` 和每一份译本（`BRICKKIT.zh.md`……），组件带着才有。

"最新版本"（`add` 不写版本、`upgrade`）要列出 tag，这一步总是先 fetch 一次，保证看到的是远端现在的 tag。

## 离线

同一个版本只要取过一次，项目的永久缓存里就有它，之后不联网也能 `up`、`graph`、`deps`。换一个项目要用同一个版本时，bare 仓库已经在用户缓存里，
第 2 级就能取到，也不用联网。只有从没见过的版本、从没克隆过的仓库需要网络。

## 从不拉取 git submodule

组件仓库可能登记了 git submodule。BrickKit 在每一条路径上都一个也不拉：

| 路径 | 你得到的 |
| --- | --- |
| bare 仓库缓存 | tag 和它们的提交；submodule 在树里只是一个指针 |
| 读 `component.yaml`、`BRICKKIT*.md`、产物 | 直接从 tag 读文件——从不读 submodule 里面的 |
| 从 tag `build` | tag 的导出：submodule 目录是空的，`build` 会为此警告 |
| `add --repo` | 不带 `--recurse-submodules` 的克隆；它会点名留空了哪些 submodule |

原因：submodule 指向另一个仓库，有它自己的地址、自己的凭据；拉它，就意味着装一个组件会悄悄伸手到谁都没声明过的仓库里。
组件的契约是它的 `component.yaml`、产物和镜像——这些都不该需要 submodule。构建确实需要时，组件应当发布镜像；在克隆下来的仓库里，
你随时可以自己 `git submodule update --init`。

## 鉴权

CLI 调用系统的 `git`，用的就是你已经配置好的凭据（SSH key、credential helper、CI 注入的 token）。它只设一个环境变量 `GIT_TERMINAL_PROMPT=0`：
没有凭据时让 `git` 直接失败，而不是在 CI 里停下来等一个永远不会来的密码输入。失败时 `git` 的原话会出现在报错里。
见 [Git 分发](../../docs/zh/03-component-guide/10-git-distribution.md#私有仓库与鉴权)。

## 清理

`~/.cache/brickkit/repos/` 整个删掉是安全的：它只是缓存，下次用到时重新克隆。被中断的克隆留下的临时目录，放得够久的会在之后的运行里自动清掉。

# 缓存设计

## 两处缓存

| 在哪 | 放什么 | 谁共用 |
| --- | --- | --- |
| 项目的 `.brickkit/` | 这个项目用到的组件版本的 `component.yaml`、文档、契约；生成的部署文件；本机状态 | 只有这个项目 |
| 用户级 `~/.cache/brickkit/repos/` | 组件 Git 仓库的 bare 仓库 | 这台机器上所有项目，以及组件自己的工作台 |

bare 仓库见 [Git 仓库缓存](../../docs/zh/06-architecture/06-bare-repo-mechanism.md)。这一篇讲项目里的 `.brickkit/`。

## `.brickkit/` 里有什么

```text
.brickkit/
├── manifests/<scope>/<name>/<版本>/
│   ├── component.yaml     这个版本的 Manifest（永久缓存）
│   ├── BRICKKIT.md        组件带着文档时才有
│   ├── BRICKKIT.<语言>.md 它带的每一份译本（BRICKKIT.zh.md……）
│   └── signature.json     来源与签名信息
├── artifacts/<版本化服务名>/<type>/…   组件声明的契约文件（add / fetch 下载）
├── generated/
│   ├── compose.yaml       Docker / Podman 的部署文件
│   ├── env/               放密钥的 env 文件（0600）
│   ├── k8s/               Kubernetes 清单
│   └── local-debug.<服务名>.env   mode: debug 组件的环境变量
├── last-run               上一次 up 运行的组件版本，版本变更提示以它为基线
├── local-mode             存在即本地模式开着
├── deploy.local.base.yaml deploy.local.yaml 上次复制自的那份 deploy.yaml；refresh 靠它分辨本地修改
├── session.lock           mode: local 会话正在运行
└── credentials            组件市场的登录令牌（0600）
```

## 缓存规则

**Manifest 永久缓存，从不过期。** 精确版本是不可变的：`demo/hello@1.0.0` 的 `component.yaml` 今天是什么，永远就是什么——发布出去的版本不再改动
（`release` 拒绝移动一个已存在的 tag）。所以没有"缓存过期"这回事，取过一次就一直用。

**本地源从不缓存。** 来自本地安装源（`components/`、`shell/`）的组件，`component.yaml` 每次都从目录里重新读：那是正在开发的代码，改了就该立刻生效。
正好是这个版本的本地源目录存在时，文档路径也指向它，而不是缓存里的快照。

**生成物每次重写。** `generated/` 下的一切都是 `up` 的输出，每次重新生成；手改会被下一次 `up` 覆盖。

**文档跟着 Manifest 一起缓存，哪种安装源都一样。** `add` 与 `fetch` 把 `BRICKKIT.md` 和每一份 `BRICKKIT.<语言>.md`
写在 `component.yaml` 旁边——本地源、Git tag、市场都一样——别的都不取：组件的 `AGENTS.md` 和 `README.md` 是写给它自己仓库的。

## `.brickkit/` 不进 Git

`init` 生成的 `.gitignore` 把它排除在外。它里面的东西要么能重新得到（Manifest、契约、生成物），要么是这台机器、这个人的状态（本地模式开关、会话锁、登录令牌）。

第一次 `git clone` 一个项目之后，`.brickkit/` 不存在，没关系：第一次运行命令时，CLI 按 `brickkit.yaml` 从安装源重新取回需要的 Manifest 与契约。
这与 `package.json` 进 Git、`node_modules` 不进 Git 是同一个道理：`brickkit.yaml` 是锁文件，`.brickkit/` 是按它装出来的东西。

## AI 助手技能自己带着记录

`.claude/skills/` 下的技能文件跟着项目提交，CLI 要知道每一份是不是它写的、之后有没有人改过——改过的文件从不覆盖。
早先的版本把这份记录放在 `.brickkit/skills.lock` 里。可 `.brickkit/` 不进 Git：同事新克隆下来根本没有这份 lock，
那里的技能从此再也刷新不了。

现在每份技能文件在最后一行带着自己的记录：

```text
<!-- brickkit:skill version=<v> sum=sha256:<hex> -->
```

`version` 是写这份文件的 CLI 版本；`sum` 是这一行之上内容的指纹。`brickkit skills status` 或 `brickkit skills update`
读到文件时，内容与指纹对得上，就是 CLI 自己的、可以刷新；对不上，就是有人改过，跳过。记录跟着文件走，每一份克隆都知道。

技能的语言也不在技能文件里：它就是项目 `AGENTS.md` 末尾那一段记的 `lang=`。旧的 `.brickkit/skills.lock` 只读一次，
用来认出旧版 CLI 写的文件，然后由 `brickkit skills update` 删掉。

## 什么可以删

| 删掉 | 后果 |
| --- | --- |
| `.brickkit/` 整个 | 安全。下次命令重新取回 Manifest 与契约、重新生成部署文件；本地模式会变成关闭，市场需要重新登录 |
| `manifests/`、`artifacts/` | 安全，下次按需重新取回（从用户级 bare 仓库取，通常不用联网） |
| `generated/` | 安全，下次 `up` 重新生成 |
| `~/.cache/brickkit/repos/` | 安全，下次用到时重新克隆 |

删缓存从来不是修问题的办法——缓存里的精确版本不会"变坏"。本地源的改动没生效，先确认组件确实来自本地源（`brickkit.yaml` 里的安装源顺序）。

# 安全与签名

## 信任模型：安装即信任

BrickKit 不对第三方组件做事前审查——不扫描、不沙箱、不做静态分析。你安装一个组件，就是信任它，和 npm、VS Code 插件市场、GitHub 是同一套模型。
事前审查要么误报太多（拦下正常组件），要么漏报太多（放过精心伪装的恶意代码）；平台能可靠做到的，是确认"组件出自谁、有没有被改过"。

| 组件来自 | 可信程度取决于 |
| --- | --- |
| 本地安装源 | 你自己 |
| Git 安装源 | 那个仓库、那个托管平台；你在 `brickkit.yaml` 的安装源里写明了它 |
| 组件市场 | 发布者的签名（下文） |

市场上的组件被确认有问题时，市场把它标成 `blocked`，之后就不能再安装。

## 签名：发布时签，安装时验

**发布方**用 cosign 签名：

```bash
brickkit publish --path ./components/people/basic --sign --key cosign.key --signed-by release-bot@example.com
```

被签名的不是 `component.yaml` 的原始字节，而是一份**规范化载荷**：Manifest 解析之后按固定规则重新编码。所以改注释、缩进、键的顺序都不会让签名失效；
而带重复键的 Manifest 会被直接拒绝——同一份文件被不同的解析器读出两种意思，签名就没有意义了。

`publish` 默认先把镜像的 tag 解析成不可变的 digest，再签名：签名覆盖的是一个事后不能被悄悄改指的引用。加 `--no-pin-digest` 可以跳过，
但那样镜像仓库上同名 tag 被换掉时，签名照样有效。

**安装方**只用 Go 标准库验签，不需要装 cosign。

## 公钥放在你自己的项目里

```yaml
# brickkit.yaml
installer:
  requireSignature: true
  publicKeys:
    keys/vendor.pub: keys/vendor.pub
```

`publicKeys` 是你信任的发布者公钥：名字（签名里写的 `publicKeyRef`）→ 项目里的公钥文件。

**公钥不从市场取。** 否则市场一旦被攻破，攻击者可以把组件和公钥一起换掉，验证照样通过——等于市场给自己发证书。信任的根在你自己的仓库里，经过你自己的代码评审。

几种情况：

| 情况 | 结果 |
| --- | --- |
| 组件有签名，签名者的公钥在 `publicKeys` 里，验证通过 | 安装 |
| `requireSignature: true`，组件没签名 | 阻断安装 |
| 签名来自一个没在 `publicKeys` 里声明的发布者 | 警告：未做校验 |
| 一把公钥都没配 | 签名验证**完全关闭**，`requireSignature: true` 也不起作用；CLI 会警告 |

最后一行值得记住：只写 `requireSignature: true` 而不配公钥，什么都没有保护。

## 最小权限

**默认不可达。** 组件之间在同一个网络里可以按服务名互相调用；从外面访问，必须在部署文件里给它写 `expose`（Docker 映射宿主机端口，Kubernetes 生成 Ingress）。

**网络策略从依赖图生成。** Kubernetes 上，部署文件写：

```yaml
k8s:
  networkPolicy:
    enabled: true
```

平台为每个组件生成一条 NetworkPolicy：只放行它在依赖图里真正的调用方，端口只放行它自己监听的那些。依赖图之外的访问者（Ingress 控制器、
另一个团队的命名空间）用 `allowFrom` 手写放行；出站方向也可以打开（`egress`）。你不需要另外维护一份访问控制列表——它永远和依赖声明一致。

**ServiceAccount。** `k8s.serviceAccount.enabled: true` 给每个组件一个单独的 ServiceAccount，而且不挂载访问 Kubernetes API 的令牌。

**Pod 安全。** `k8s.podSecurity: restricted` 按 Pod Security 的 restricted 级别给每个容器生成 `securityContext`：不以 root 运行、禁止提权、
丢弃全部 capabilities、`seccompProfile: RuntimeDefault`。刻意不加只读根文件系统——restricted 并不要求它，而它会让任何往 `/tmp` 写东西的组件直接挂掉。
丢掉全部 capabilities 也意味着绑不了 1024 以下的端口：组件监听这样的端口时，`up` 会警告。

这三项都**不默认开启**：每一项都可能让一个本来能跑的组件起不来（比如组件需要以 root 运行、需要调用 Kubernetes API），这个代价只有你能权衡。

CLI 本身从不挂载 Docker socket，只调用 `docker compose` / `kubectl` 命令行。

## 网络策略可能根本没有生效

这是一个你必须知道的限制：**很多集群接受 NetworkPolicy 对象，却完全不执行它。** `kubectl apply` 成功、`kubectl get networkpolicy` 看得见，
流量却照样畅通无阻，而且没有任何报错。执行与否取决于集群的网络插件（CNI）；minikube 和 kind 的默认 CNI 就不执行。

Kubernetes 没有提供"这个集群执行 NetworkPolicy 吗"的 API，平台测不出来，所以 `up` 每次生成网络策略时都会提醒你：

```text
🔒 已生成 5 份 NetworkPolicy（k8s.networkPolicy.enabled: true）
   ⚠️ 它们只在集群的 CNI 支持执行时才有效。不支持时：apply 会成功、
      kubectl get networkpolicy 看得见、而流量完全不受限制——没有任何报错。
      minikube / kind 的默认 CNI 就属于这一类。
   平台测不出来（K8s 没有这个 API），只能你自己验一次：
      详见 brickkit docs 06-architecture/08-security-and-signing（网页版：https://github.com/brickKit/brickKit/blob/v1.1.0/docs/zh/06-architecture/08-security-and-signing.md）
```

**自己验一次：** 部署之后，分别从一个**被授权**的组件和一个**没被授权**的组件去访问同一个目标。

```bash
# 被授权：demo/caller 依赖 demo/hello，应当能连上
kubectl exec -n brickkit-my-shop deploy/demo-caller-1-0-0 -- \
  wget -qO- -T 3 http://demo-hello-1-0-0:8080/healthz

# 没被授权：demo/bus 不依赖 demo/hello，应当超时
kubectl exec -n brickkit-my-shop deploy/demo-bus-1-0-0 -- \
  wget -qO- -T 3 http://demo-hello-1-0-0:8080/healthz
```

第一条成功、第二条超时，网络策略在生效。两条都成功，说明你的集群不执行它——需要换一个执行 NetworkPolicy 的 CNI（例如 Calico、Cilium），
或者接受"这些策略只是声明"。只看生成的 YAML 说得通，证明不了任何事。

## 密钥

密钥不进 `config/`（它要提交进 Git）：用 `${VAR}` 引用环境变量或 `.env`、用 `file://` 引用 `.secrets/` 下的文件，或者在 Kubernetes 上用
`{ existingSecret, key }` 引用集群里已有的 Secret。部署时密钥走单独的通道，从不明文写进部署文件。详见 [敏感值](../../docs/zh/01-three-layers/07-sensitive-values.md)。
