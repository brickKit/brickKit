## 1. 本文档定位

本文档不是"架构决策流水账"（不记录我们曾经考虑过什么方案又放弃了什么方案），而是一份 **"架构辩护书"**。

对于最终的使用者和第三方开发者来说，他们不需要知道平台走过什么弯路，他们只需要知道 **"现在的架构为什么长这样"**。当你对 BrickKit 的某些"反直觉"设计产生疑问，或者想要反驳当前设计时，本文档提供了所有核心架构点的底层逻辑与辩护理由。

## 2. 核心架构辩护

### 2.1 为什么平台没有注册中心，也不做健康检查轮询？

**质疑：** 传统的微服务架构都有 Eureka、Consul 或 Nacos 作为注册中心，平台不轮询健康状态，怎么知道组件的死活和地址？

**决策：**
BrickKit 坚决不自建注册中心。服务发现完全依赖底层引擎的原生 DNS（Docker Compose 的 service name / K8s 的 Service name）。健康检查完全交由底层引擎的原生 Probe（K8s livenessProbe / Compose healthcheck）处理。

**理由：**

- **消除单点与运维负担：** 自建注册中心意味着平台必须是一个常驻的高可用集群，这极大地增加了运维复杂度。
- **底层能力已经足够：** Docker 和 K8s 原生就具备完美的 DNS 解析和基于 Probe 的重启机制。平台再去写一个定时器每 10 秒轮询一次 `/healthz`，纯属重复造轮子，且不如底层引擎响应迅速。
- **组件零侵入：** 组件不需要引入任何"注册 SDK"，启动后只要监听端口，底层引擎自然会发现它。

### 2.2 为什么强制使用"精确版本"，拒绝 `^1.0.0` 范围版本？

**质疑：** npm、Maven 等包管理器都支持 `^1.0.0`（自动升级兼容版本），BrickKit 为什么只允许写死 `1.0.0`？这太死板了。

**决策：**
Manifest 中的依赖声明和 `brickkit.yaml` 中的组件列表，只接受精确的语义化版本（`major.minor.patch`），拒绝任何范围约束符。

**理由：**

- **杜绝"隐式升级"带来的生产事故：** 范围版本是导致"在我的机器上能跑，在生产环境挂了"的罪魁祸首。精确版本确保了"所见即所得"，声明了什么版本，跑的就一定是那个版本。
- **天然支持多版本共存：** 因为使用了精确版本，CLI 可以将其直接拼接到服务名中（如 `people-basic-1-0-0` 和 `people-basic-2-0-0`）。这使得在同一个集群中同时运行一个组件的多个版本成为零成本的天然能力，为灰度发布和遗留系统迁移提供了极大的便利。

**那 `brickkit add people/basic` 不写版本号，算不算破例？**

不算。这条规矩约束的是**配置里写什么**，不是**命令行必须写什么**。省略版本号时，
CLI 在 add 那一刻去安装源问出一个具体版本，把它钉进 `brickkit.yaml`——落到配置里的
依然是 `version: 2.0.0` 这样的精确版本。区别在解析发生的时机：

| | 解析时机 | 后果 |
| --- | --- | --- |
| `^1.0.0` 范围约束（**拒绝**） | 每次安装/部署都重新解析 | 同一份配置在不同时间装出不同版本，"在我机器上能跑"从这里来 |
| 省略版本号（**接受**） | 只在 `brickkit add` 执行的那一刻解析一次 | 配置一旦写下就固定，之后无论装多少次都是同一个版本 |

第二种就是 npm `install` 之后锁进 lockfile 的做法：方便的是打字的人，不变的是配置。
`brickkit add people/basic@^1.0.0` 仍然报错——能省略的是版本号本身，不是"可以写个范围"。

### 2.3 为什么多版本默认共存？

**质疑：** 当组件 A 依赖 `X@1.0.0`，组件 B 依赖 `X@2.0.0` 时，npm 会自动嵌套安装两个版本。BrickKit 为什么也默认共存，而不是报错阻断？

**决策：**
多版本共存是默认行为。brickkit.yaml 中写了几个版本，CLI 就启动几个容器，无需任何额外参数。

**理由：**

- **版本化服务名天然支持共存：** `people-basic-1-0-0` 和 `people-basic-2-0-0` 是完全独立的容器，DNS 不冲突，环境变量各指各的。共存不需要任何额外机制，是精确版本 + 版本化服务名的天然能力。
- **brickkit.yaml 就是声明：** 用户在 brickkit.yaml 中写了两个版本条目，这就是他的意图。CLI 不需要再问一次"你确定吗？"。写了就启动，就这么简单。
- **与 migration 逻辑一致：** 如果新版本做了破坏性操作（删表），旧版本组件自然运行不了——这是数据层的事实，不需要 CLI 提前阻断。如果新版本只是加了字段，旧版本自然兼容，只是还没适配新字段而已。
- **破坏性变更是组织协同问题：** 平台不替人做决定。多版本共存只是物理缓冲，数据层兼容由使用者自行保证。详见 002 组件规范第 3.7 节"破坏性变更（Major）协同守则"。
- **极简原则：** 不需要 `--allow-multi-version` 参数，不需要"版本冲突检测"逻辑，不需要"阻断→确认→放行"的交互流程。写了就启动，就这么简单。

### 2.4 为什么组件不自带部署文件，非要 CLI 现生成？

**质疑：** Helm Chart 都是自带 K8s YAML 的，Docker 项目都自带 `docker-compose.yaml`。为什么 BrickKit 的组件仓库里只有 `component.yaml`，部署文件非要 CLI 运行时生成？

**决策：**
组件绝对不自带任何环境相关的部署文件。CLI 读取统一的 `component.yaml`，根据当前的 `deploy.target`（docker 或 k8s）动态生成对应的 YAML。

**理由：**

- **一套 Manifest，两种环境：** 组件开发者不需要同时维护 `docker-compose.yaml` 和 K8s `Deployment/Service/Ingress`。
- **环境解耦：** 组件代码和 Manifest 只描述"我是什么"、"我需要什么"，而不关心"我跑在哪里"。这确保了同一个组件可以无缝在本地开发（Docker）和生产环境（K8s）中流转，无需修改任何配置。

### 2.5 为什么 CLI 是个用完即走的本地工具，而不是常驻 Server？

**质疑：** 没有常驻的后台服务，怎么做全局状态管理？怎么做可视化的 Admin Console？

**决策：**
CLI 是纯粹的本地二进制工具，无状态，执行完命令即退出。项目的期望状态由 `brickkit.yaml` 持有，实际状态由底层引擎（Docker/K8s）持有。

**理由：**

- **极致的简单与安全：** 没有后台进程，就不存在单点故障，不占用系统资源，不监听任何端口（无攻击面）。
- **状态外置：** `brickkit.yaml` 就是唯一的"真相来源"（Source of Truth），可以完美接入 Git 进行版本控制和 Code Review。
- **Console 只是可选组件：** 如果未来团队确实需要一个可视化管理界面，它应该作为一个普通的"前端组件"和"后端 API 组件"发布到市场上，由用户按需安装，而不是硬编码在平台核心中。

### 2.6 为什么 K8s 环境下的数据库迁移要用 Job，而不是 InitContainer？

**质疑：** K8s 社区通常推荐使用 `InitContainer` 来执行数据库迁移等初始化操作，为什么 BrickKit CLI 要特意生成 K8s `Job`，并用 CLI 串行控制等待？

**决策：**
在 K8s 环境下，CLI 生成独立的 `Job` 执行迁移，`kubectl wait` 成功后再 apply 主业务的 `Deployment`。

**理由：** 屏蔽 InitContainer 的并发死锁坑。`InitContainer` 是 Pod 级别的。如果生产环境中业务组件配置了 `replicas: 3`，K8s 会同时创建 3 个 Pod，导致 3 个 `InitContainer` 并发执行同一个数据库迁移脚本。如果迁移工具没有实现完善的分布式锁，极易导致数据库死锁或表结构损坏。而 `Job` 是集群级别的，CLI 通过串行控制，绝对保证了迁移脚本在整个集群中只执行一次，且先于所有业务 Pod 启动。

**补充：K8s 环境自动清理旧 Job。** CLI 在执行迁移前，先执行 `kubectl delete job --ignore-not-found` 清理可能残留的旧 Job（如上一次迁移失败后残留的 Job），确保幂等性。用户修复迁移脚本后重新执行 `brickkit up`，CLI 会自动清理旧 Job 并重新执行迁移，无需手动干预。

### 2.7 为什么不做通信治理（熔断/限流）和弱依赖降级？

**质疑：** 作为一个微服务拼装平台，不提供 Service Mesh、熔断限流，甚至连弱依赖降级都不管，是不是太不负责任了？

**决策：**
平台完全不管通信治理和降级逻辑。组件间调用直连，降级逻辑由组件在自己的代码中用 `try...catch` 实现。弱依赖缺失时，CLI 完全不注入该环境变量（不注入空字符串），组件必须使用安全读取方式（如 `os.environ.get()`）。

**理由：**

- **业务复杂度千变万化：** 熔断的阈值、限流的算法、重试的退避策略，不同的业务场景差异巨大。平台如果做"一刀切"的治理，不仅做不好，还会限制业务的灵活性。
- **降级是纯粹的业务逻辑：** 当 Redis（弱依赖）挂掉时，组件 A 可能选择"直接查数据库"，组件 B 可能选择"返回默认空列表"，组件 C 可能选择"将请求写入本地文件稍后重发"。平台无法统一定义什么是"降级"，因此平台只负责"不注入该环境变量"，剩下的"丢车保帅"逻辑，必须由最懂业务的组件开发者自己写代码实现。
- **为什么不注入空字符串？** 详见 2.13 节。

### 2.8 为什么不做配置中心（动态热更新）？

**质疑：** 改个分页大小、改个日志级别也要重启组件吗？为什么不提供类似 Apollo/Nacos 的配置热更新能力？

**决策：**
配置通过环境变量注入。修改配置 = 修改 `brickkit.yaml` -> 执行 `brickkit up` -> 组件重启。

**理由：**

- **保持平台极简：** 引入配置中心意味着引入长连接、配置推送、版本比对等极其复杂的机制，这违背了 BrickKit "平台极简"的核心理念。
- **改配置就重启是常态：** 对于 90% 的基础配置（如数据库连接池大小、超时时间），重启是唯一安全的生效方式。
- **热更新是业务自己的事：** 如果某个组件确实需要"毫秒级热更新"的业务开关，它应该自己去连接 Redis 或数据库轮询，而不是逼迫底层平台去实现一套沉重的配置下发系统。

### 2.9 为什么多环境配置不引入 overlay（继承/覆盖）机制？

**质疑：** 如果有 dev、test、staging、prod 四个环境，就要维护 4 个完整的 `brickkit.yaml`，里面 90% 的组件列表是重复的，这不累吗？为什么不支持类似 Kustomize 的 overlay 继承？

**决策：**
维持现状，每个环境一个完整的、自包含的 `brickkit.yaml`，不引入任何继承或合并逻辑。

**理由：**

- **简单直接，拒绝心智负担：** 引入 overlay 意味着开发者需要理解"基础层"、"覆盖层"、"合并规则"、"数组合并策略"等复杂概念。打开一个文件看不到全貌，必须去脑补继承链。
- **完整的文件更安全：** 自包含的文件意味着"所见即所得"，在 Git 中 diff 时一目了然，不会因为底层基础配置的变更而意外"隐式"影响到生产环境。大多数团队通过 Git 的复制和 Code Review，完全能够管理好这种程度的重复。

### 2.10 为什么前端组件和后端组件在平台眼中没有区别？

**质疑：** 前端只是一堆 HTML/JS/CSS 静态文件，为什么非要打包成 Docker 镜像（如 nginx）当成后端容器来跑？为什么不给前端一个特殊的"无容器"类型？

**决策：**
BrickKit 中只有一种组件形态：`container`。前端组件就是一个运行着 Web Server（如 nginx/caddy）的普通容器。

**理由：** 统一心智模型与平台逻辑。

前端组件同样需要：
- 监听端口（如 nginx 的 80）
- 提供健康检查端点（如 `/`）
- 被 Ingress 暴露到外部网络
- 通过环境变量获取后端地址，在 nginx 中配置反向代理

如果为前端发明一种"无容器（static）"的特殊类型，CLI 就会充斥着 `if type == static` 的特殊分支（不生成容器、不生成 Service、特殊处理 CDN 等），这会导致架构出现裂痕，违背"平台极简"和"一视同仁"的原则。对平台而言，serve 静态资源的 nginx 容器和跑着 Go 代码的业务容器，在编排逻辑上没有任何本质区别。

### 2.11 为什么平台不做第三方组件的安全审查？

**质疑：** 组件市场允许第三方发布组件，如果有人在市场上传了一个恶意组件（比如偷数据、挖矿），平台不做安全审查，用户岂不是任人宰割？

**决策：**
BrickKit 对第三方组件采用 **"安装即信任"** 的信任模型。平台不做前置安全审查（不扫描代码、不沙箱运行、不静态分析），只做最后的"城管"：发现确凿的恶意组件时，市场管理员将其标记为 `blocked`，阻止新安装。

**理由：**

- **与成熟生态的模式一致：** VSCode 插件市场、npm、GitHub 开源项目都是这个模式——你用它说明你相信他，不相信他你就别用他。平台不为用户的组件选择兜底。
- **开源组件代码全透明：** 用户可以直接审查源码，安全性由用户自己负责。
- **闭源组件基于商业协议：** 既然用了闭源组件，说明用户和发布者达成了某种协议。出了问题走协议追责，而不是找平台索赔。
- **前置审查成本极高且效果有限：** 静态代码分析、沙箱运行、AI 审查等手段，要么误报率极高（阻断正常组件），要么漏报率极高（放过精心伪装的恶意代码）。在平台早期，投入产出比极低。
- **`blocked` 机制是最后的安全网：** 市场管理员可以在发现确凿的恶意行为后，将组件标记为 `blocked`，阻止新安装。已安装的组件会收到风险提示。这是"事后追责"而非"事前审查"，成本极低且足够有效。
- **未来可渐进增强：** 未来可能引入 AI 辅助代码审查、社区举报机制、组件安全评分等，但当前阶段安全责任由使用者自行承担。

**一句话总结：** 平台提供"集市"，不提供"保险箱"。你在集市上买了什么，是你自己的选择。

### 2.12 为什么 CLI 不校验 config 值的类型？

**质疑：** 组件 Manifest 中明明有 `configSchema`（JSON Schema），声明了每个配置项的类型（integer/string/boolean）。CLI 在注入环境变量时为什么不校验一下？用户把 `defaultPageSize` 写成 `"abc"`（字符串），CLI 也不报错，组件启动后直接崩溃，这不是坑人吗？

**决策：**
CLI 不校验 config 值的类型。CLI 只做"搬运工"：读 configSchema 默认值 → 用 config 覆盖 → 转大写下划线 → 注入环境变量。类型校验完全不做。

**理由：**

- **configSchema 是"配置说明书"，不是"安检机"：** 组件发布者通过 configSchema 向使用者提供"配置说明书"（类型、默认值、描述、枚举）。使用者参照说明书写 `brickkit.yaml` 的 `config` 字段。写错了类型（如把 integer 写成字符串），说明使用者没有认真看说明书，这是使用者自己的责任。
- **过度校验导致过度设计：** 如果 CLI 校验 `type`，那要不要也校验 `enum`？要不要校验 `minimum/maximum`？要不要校验 `pattern`（正则）？要不要校验 `required`？JSON Schema 的能力非常丰富，一旦开了校验的口子，就要不断追加校验逻辑，CLI 会变得越来越臃肿，违背"平台极简"原则。
- **市场已经校验了 configSchema 的格式：** 市场在组件发布时会校验 configSchema 本身的 JSON Schema 格式是否合法（结构校验）。这保证了"说明书"本身是正确的。至于使用者有没有按说明书填写，平台不管。
- **快速失败优于静默错误：** 如果 CLI 校验并报错，用户会在 `brickkit up` 时就发现问题。但如果不校验，用户会在组件运行时发现问题。两种方式都能让用户发现错误，但后者更符合"组件自治"原则——组件自己决定怎么处理错误的配置（报错、降级、使用默认值等），而不是由平台越俎代庖。

**一句话总结：** 说明书已经给你了，你不看或看错，平台不兜底。

### 2.13 为什么弱依赖缺失时完全不注入环境变量？

**质疑：** 弱依赖缺失时，CLI 为什么不注入一个空字符串（如 `INFRA_REDIS_EVENT_BUS_ENDPOINT=""`）？这样组件代码用 `os.environ["X"]` 也不会崩溃，对新手更友好。完全不注入变量，万一开发者用了方括号访问，组件直接就崩了，这不是故意制造障碍吗？

**决策：**
弱依赖缺失时，CLI 完全不注入该环境变量（不注入空字符串）。组件必须使用安全读取方式（如 `os.environ.get()`）。

**理由：**

我们对比了两个选项：

| 维度 | 选项 A：完全不注入 | 选项 B：注入空字符串 |
| --- | --- | --- |
| 语义 | "缺失即不存在"，最精确 | "存在但为空"，语义模糊 |
| 安全性 | 强制使用 `os.environ.get()`，代码更健壮 | `os.environ["X"]` 不崩溃，但可能拼出非法 URL |
| 调试 | `env` 搜不到变量 → "没配置" | `env` 看到空值 → "配置了但为空"（歧义） |
| 静默失败风险 | ✅ 低（方括号访问立刻崩溃，快速发现问题） | ❌ 高（空字符串拼接可能发出非法请求，且可能返回 200） |
| 跨语言一致性 | Python 抛异常、Go 返回 `""`、Java 返回 `null`（不一致） | 所有语言都拿到空字符串（一致） |
| 与"精确优于隐式"的契合度 | ✅ 完全契合 | ⚠️ 有张力（用隐式方式表达缺失） |

选择选项 A（完全不注入）的核心理由：

- **契合 BrickKit 的核心哲学："精确优于隐式"和"快速失败"。** 弱依赖缺失就是"不存在"，不制造任何歧义。如果开发者用了不安全的读取方式（`os.environ["X"]`），组件立刻崩溃，错误在第一时间暴露——这比"静默发出非法请求、三小时后才发现数据不对"要好一万倍。
- **避免"假存在"导致的静默失败：** 这是选项 B 最致命的缺点。如果注入空字符串，开发者忘记判空，直接写 `requests.get(f"{ENDPOINT}/healthz")`，空字符串会拼出 `/healthz`，请求打到容器自身的 8080 端口。这个请求可能返回 200（因为自己的 `/healthz` 就是 200），导致开发者误以为弱依赖是健康的。这种 bug 极难排查。
- **009 文档中的推荐代码已经用了 `os.environ.get()`：** 组件开发快速入门中的弱依赖代码模板天然适配"完全不注入"的行为。
- **Go 的 `os.Getenv` 在两种选项下行为一致：** 都返回 `""`，所以选项 A 对 Go 开发者没有额外负担。Python/Java 开发者只要遵循 `os.environ.get()` / `System.getenv()` 的安全读取方式，也完全没问题。

**一句话总结：** 宁可让组件在启动时"响亮地崩溃"，也不要让它在运行时"安静地出错"。

### 2.14 为什么 `enabled` 有三种状态，规则却要写成"跟着上层走"？

**质疑：** 三种状态（不写 / `true` / `false`）已经够绕了，为什么规则还要换个说法？结论又没变。

**决策：**
状态还是三种，判定结论一个字没改，但**表述**统一成自上而下的继承（003 §4.3）：

> 顶层组件默认跑；下层组件只要还有一个上层在跑，它就跑；写了 `enabled` 就按写的来。

**理由：**

**1. 两种说法结论一致，但只有一种读得懂。**

原来的写法是自下而上的倒推：

> 组件启动 ⟺ 钉住 ∨（根组件 ∧ 未关）∨（有正在启动的组件依赖它 ∧ 未关）

这是**实现视角**——读的人得在脑子里把依赖图反着推一遍，才知道自己关掉一个组件会发生什么。而使用者要做的决定其实只有一个：**这个顶层我要不要**。下面那一串跟着走，不需要他算。

逐种情况对过，两者一一对应：

| 情况 | 倒推说法 | 继承说法 |
| --- | --- | --- |
| 顶层没写 `enabled` | 根组件且未关 → 跑 | 默认跑 |
| 顶层写 `false` | 显式关 → 不跑 | 不跑 |
| 下层没写，某个上层在跑 | 有在跑的组件依赖它 → 跑 | 跟上层 → 跑 |
| 下层没写，上层全不跑 | 没有在跑的组件依赖它 → 不跑 | 跟上层 → 不跑 |
| 任意组件写 `true` | 钉住 → 跑 | 按你写的 → 跑 |

**2. 这不是措辞洁癖。**

原来那句话真的把人读岔过：照着它认真读完，会得出"这条规则错了、级联应该整个删掉"的结论——而规则本身一直是对的。**一份让认真读的人得出相反结论的规范，问题在规范，不在读的人。** 所以 003 §4.3 现在不再只给规则，而是把六个具体场景（关顶层、共享依赖、钉住下层、钉住撞上被关的强依赖、环）连输出一起摆出来。

**3. 配套改了一处实质规则：判定里的"依赖"从只算强依赖改成强弱一视同仁。**

早先只有强依赖能把下层带起来，于是只被弱依赖指着的组件默认不跑。那条规则与 §2.3"brickkit.yaml 就是声明"直接冲突——`brickkit add` 会把**整棵依赖树**（含弱依赖）写进配置，然后 `up` 不起它们。使用者装了组件却发现一半功能是哑的，而他得先知道这条规则，才想得到去翻配置。

两种失败方式比一比：默认全开、嫌重再关掉，最坏是多几个容器，`docker ps` 里看得见；默认不开，最坏是功能静悄悄地缺一半，没有任何一处告诉他为什么。选前者。完整论证见 003 §4.3 末尾。

`optional: true` 剩下的两件事没变：解析期取不到只警告不阻断；注入期它没在跑就不注入 `*_ENDPOINT`，让调用方自己降级（§2.13）。

**4. 实现上有一个后果值得记下来：算的是"谁不跑"。**

直觉的算法是"从顶层出发，沿依赖往下展开，走到谁谁就跑"。那样算不对**环**：两个组件互相依赖时谁都不是顶层，队列一开始就是空的，结论是两个都不跑——而正确答案是两个都跑（环上没有更上层的东西，它们互为顶层）。

所以实现反过来算：种子是显式关掉的那些，然后两条规则传播到稳定——

- 强依赖不跑的，跟着不跑（跑起来也必然连不上）
- 没写 `enabled`、有上层、而上层全不跑的，跟着不跑

顶层没有上层，第二条的前提永远不成立，于是除非显式关否则一定跑；环上的两个互为上层，谁也没先倒下，于是都跑。**不需要为环写任何特例**——这正是"算谁不跑"比"算谁跑"更对的地方。

**一句话总结：** 同一条规则，从"谁需要我"改成"我跟着谁"，使用者就不用再在脑子里跑一遍依赖图。

### 2.15 为什么 50 个组件不会失控——局部性与按需启用？

**质疑：** 如果市场里已经有 50 个组件，一个 ERP 系统依赖了 30 个，开发者不是要面对 30 个组件的复杂度吗？组件数量增长后，系统不会变得不可管理吗？

**决策：**
BrickKit 通过"局部性原则"和"按需启用"机制，确保任何开发者在任意时刻只需要面对 2~5 个组件的认知负担。50 个组件是系统的总量，但任何一个开发者在任何时刻面对的，永远只是自己那一小块积木和它紧挨着的两三块积木。

**理由：**

**1. 局部性原则：每个组件只关心"一跳邻居"**

组件 A 只需要知道自己直接依赖的组件 B、C、D 的 API 契约（通过环境变量注入的 ENDPOINT 地址）。B 后面连着什么、C 依赖了什么，是 B 和 C 的开发者需要管理的事情，与 A 无关。

```
A 的视角：我只调 B 和 C，其他我不关心
B 的视角：我只调 D 和 E，其他我不关心
C 的视角：我只调 F，其他我不关心
```

这意味着：无论系统总共有 50 个还是 500 个组件，**单个组件开发者的认知边界永远是"我的直接依赖"（通常 1~3 个）**。复杂度不会随系统规模线性增长到每个开发者头上。

**2. 按需启用：不相关的组件自动消失**

- 本地开发时，把这一轮不碰的那几个**顶层**写上 `enabled: false`，它们下面那一串跟着不跑（§2.14）
- `brickkit sync` 再把这些组件的源码一并收进 `components/.archived/`
- `brickkit status` 只展示当前活跃的组件

**一个 50 组件的项目，本地开发时可能只有 4 个容器在跑。** 其余 46 个组件对开发者来说"不存在"——不占资源、不产生日志、不需要理解。

**3. 业务组件是"可选扩展"，不是"必须存在"**

核心骨架（如人员、部门、权限）是稳定的少数组件。其余业务组件（审批流、报表、通知等）是按需添加的。开发新业务组件时，开发者只需要：
- 安装自己依赖的那 1~2 个底层组件
- 获取 API 契约
- 开发自己的业务逻辑
- 不需要理解系统中其他 48 个组件在做什么

**4. CLI 封装了传递依赖的复杂度**

`brickkit add erp/backend@1.0.0` 会自动递归拉取所有间接依赖。用户不需要手动管理"erp/backend 依赖 people/basic，people/basic 又依赖 department/tree"这条链。对用户来说，他执行了一条命令，系统就完整了。

**5. `brickkit sync` 让源码工作区也保持清爽**

通过 `--repo` clone 了多个组件源码后，`brickkit sync` 会把这次不启动的组件源码归档到 `components/.archived/`（判据与 `brickkit up` 完全一致）。开发者在文件管理器中只看到当前关注的 2~3 个组件的源码，其余全部隐藏。

**一句话总结：** 50 个组件是系统的总量，但任何一个开发者在任何时刻面对的，永远只是自己那一小块积木和它紧挨着的两三块积木。这就是"搭积木"的本质——你不需要同时看着所有积木。

### 2.16 为什么不支持 monorepo？

**质疑：** 很多大型项目使用 monorepo（如 Google、Meta），把多个模块放在一个 Git 仓库中管理。BrickKit 为什么要求每个组件必须是独立的 Git 仓库？这不是增加了仓库管理的负担吗？

**决策：**
BrickKit 中，一个组件 = 一个独立的 Git 仓库。不支持在一个 Git 仓库中放置多个组件（如 `repo/component-a/component.yaml` + `repo/component-b/component.yaml`）。

**理由：**

- **组件是独立的发布单元：** 每个组件有自己的版本号、自己的镜像、自己的迁移脚本。monorepo 中的多个组件无法独立发布。如果 component-a 发布了 1.1.0，component-b 还在 1.0.0，monorepo 的 Git tag 怎么打？
- **组件是独立的移动单元：** `brickkit sync` 归档功能移动的是完整的 Git 仓库目录（含 `.git`）。monorepo 中的子目录无法独立移动，因为 `.git` 在 monorepo 根目录。
- **组件是独立的权限单元：** 不同组件可能有不同的可见性（public/private）和不同的发布者。monorepo 无法实现这种隔离。
- **`--repo` clone 的语义清晰：** `brickkit add people/basic@1.0.0 --repo` clone 的是一个完整的 Git 仓库。如果是 monorepo，CLI 需要 clone 整个仓库然后只取子目录，这增加了复杂度且容易产生歧义。

**如果确实有多个组件需要协同开发怎么办？**

使用 Git 的分支和 PR 机制协同开发，但每个组件仍然是独立的仓库。或者使用 Git submodule / Git subtree 引用共享代码，但每个组件仓库仍然独立包含自己的 `component.yaml`。

**同一业务的多部分内容属于同一组件：** 如果一个业务功能需要多个文件（如 proto + 后端代码 + 迁移脚本），它们属于同一个组件仓库，一起移动、一起上传、一起发布。不需要拆分成多个组件。

**一句话总结：** 组件是 BrickKit 的最小独立单元。独立仓库保证了独立发布、独立移动、独立权限。monorepo 会打破这种独立性。

### 2.17 为什么 `brickkit sync` 是独立命令而非集成在 `brickkit up` 中？

**质疑：** 用户修改了 brickkit.yaml（比如把某个组件从 `enabled: false` 改回来），然后执行 `brickkit up`。此时被归档的组件源码还在归档目录里。为什么 `brickkit up` 不自动把它移回来？这样用户不需要记得执行 `brickkit sync`。

**决策：**
`brickkit sync` 是纯独立命令，不集成在 `brickkit up` 中。用户忘记执行就自己发现、自己处理。

**理由：**

- **职责分离：** `brickkit up` 的职责是"生成部署文件 + 启动容器"，`brickkit sync` 的职责是"整理源码目录"。两者是完全不同的操作。把源码目录管理塞进 `brickkit up` 会让 `brickkit up` 的职责变得模糊。
- **`brickkit up` 不依赖源码目录：** CLI 在 `brickkit up` 时从 `.brickkit/manifests/` 缓存读取 Manifest，不依赖源码目录位置。源码目录只是开发者在 IDE 中编辑代码时使用的，与运行时完全无关。
- **符合"平台提供工具，不替人做决定"原则：** 用户修改了配置但忘记执行 `brickkit sync`，这是用户自己的过失。CLI 不应该替用户操心"你的源码目录是不是该整理了"。
- **避免意外行为：** 如果 `brickkit up` 自动移动源码目录，用户可能会困惑"我的文件怎么突然 moved 了？"。独立命令让行为更可预测。
- **双向操作需要明确意图：** `brickkit sync` 是双向的（归档 + 激活）。如果集成在 `brickkit up` 中，每次启动都可能触发大量文件移动，这不是用户期望的行为。

**一句话总结：** `brickkit up` 管运行时，`brickkit sync` 管源码目录。两件事，两个命令，互不干扰。

#### 补充：为什么删掉了 `sync --only` / `up --only` / `down --only`？

**曾经的设计：** `--only <组件>` 只保留点名的组件与它们的强依赖，**不改 `brickkit.yaml`**。
当时的论证是"个人的、临时的偏好不该写进团队的、长期的声明里"：
`enabled` 是团队共享、要提交进 Git 的部署声明，而"我这两天只搞人员组件"是个人的、
今天下班就没了的事，不该为它去改一个带部署语义的文件。

**决策：三个 `--only` 全部删除。** 收窄范围只有一条路：改 `brickkit.yaml` 的 `enabled`。

**理由：**

**1. 它是第二套开关，回答的却是同一个问题。**

使用者面对"我只想跑这几个"时，有两条路可选，还得先知道有 `--only` 这个东西存在。
命令行参数记不住是常态——而 `enabled` 是他打开配置文件就看得见的。
一个平台能少一个概念就该少一个。

**2. "改配置太麻烦"这个前提，在"跟着上层走"之后不成立了。**

原来的论证说"十个组件的项目要动八行"。那是因为当时只有强依赖能把下层带起来，
不写 `enabled` 的组件会被跳过，所以想跑的还得逐个写 `enabled: true`。
现在下层跟着上层走，**只需要关顶层**——十个组件的项目通常只有两三个顶层，动两三行。
而且 `brickkit up` 的输出直接把顶层标出来了，不用自己看依赖图（003 §4.3）。

**3. `--only` 不改配置，会让 `up` 和 `sync` 的判据分叉。**

`sync --only people/basic` 把别的组件源码归档了，`up` 却仍然按 `enabled` 起它们的容器：
目录里看不到的组件正在跑。两套真相迟早对不上，而对不上的时候没有任何一处告诉使用者
是哪一套在生效。现在两个命令共用同一个判定函数，不可能分叉。

**4. "脏 diff"这个代价是真实的，但它的解法开发者天天在用。**

改完配置不想提交，`git checkout brickkit.yaml` 或 `git stash` 就回来了——
不需要 CLI 再发明一套机制。最终上线的流程也正是这个：
`git checkout` 恢复配置 → `brickkit sync` 把源码全移回来 → `brickkit up` 全量启动。

**保留了 `--dry-run`。** 它和 `--only` 不是一类东西：`--only` 是"换一套判据"，
`--dry-run` 是"用同一套判据但不动手"。前者制造第二份真相，后者只是先看一眼。

**一句话总结：** 收窄范围只有一条路——改 `enabled`。少一个概念，也少一份会跟配置分叉的真相。

### 2.18 为什么 `brickkit add --repo` 不自动 clone 所有组件源码？

**质疑：** 既然开源组件有 Git 仓库，为什么 `brickkit add` 不默认把完整仓库 clone 下来？这样用户随时可以修改源码，不需要额外执行 `--repo`。

**决策：**
`brickkit add` 默认不 clone 组件源码（只拉取 Manifest + artifacts）。当用户真正想修改某个组件的源码时，再执行 `brickkit add <组件>@<版本> --repo` 或 `--repo-all`。

**理由：**

- **大多数用户不需要源码：** 安装组件的用户通常只是想"使用"组件，不是想"修改"组件。自动 clone 所有依赖的源码会浪费磁盘空间和下载时间。
- **递归依赖可能很多：** `brickkit add erp/backend@1.0.0` 可能递归拉取 5~10 个依赖组件。如果每个都自动 clone，一条命令就要 clone 5~10 个 Git 仓库，速度很慢。
- **按需 clone 更精确：** 用户通常只需要修改 1~2 个组件的源码。`--repo` 只 clone 指定的组件，`--repo-all` clone 所有开源依赖。用户自己决定需要什么。
- **保持 `brickkit add` 的简单性：** 默认行为不变（只拉 Manifest + artifacts），`--repo` 是可选的增强。不改变现有用户的使用习惯。

**一句话总结：** 源码是"开发时"的需求，不是"安装时"的需求。按需获取，不强制下载。

### 2.19 为什么 clone 后的 Git 权限管理不由 CLI 负责？

**质疑：** 用户 clone 了官方开源组件的仓库后，通常没有 push 权限。为什么 CLI 不自动帮用户 fork 仓库、添加 remote？这样用户修改后可以直接 push，不需要手动操作。

**决策：**
CLI 不管 Git 权限。clone 后的 fork、remote 管理、push 操作完全由用户自己处理。CLI 在 clone 完成后输出一条提示，引导用户参考文档。

**理由：**

- **每个用户的 Git 平台不同：** 有人用 GitHub，有人用 GitLab，有人用 Gitee，有人用自建 Gitea。CLI 不可能适配所有平台的 fork API。
- **Git 操作是用户自己的事：** fork、remote 管理、分支策略、PR 流程，这些都是 Git 工作流的一部分，与 BrickKit 无关。CLI 不应该越界。
- **有 push 权限的用户不需要 fork：** 公司内部仓库通常有 push 权限，用户可以直接 push。如果 CLI 强制 fork，反而多此一举。
- **保持 CLI 的简单性：** 不引入额外的 API 调用和认证逻辑。CLI 只负责 `git clone`，其余的交给用户。
- **教程已经足够：** 011 组件安装与拼装指南中提供了完整的"修改开源组件源码后如何上传"教程，包括 fork + remote、删除原 remote + 添加自己的两种方式。

**一句话总结：** CLI 负责 clone，Git 权限负责权。两件事，两个主人。

### 2.20 为什么 `brickkit remove` 自动删除源码目录？

**质疑：** `brickkit remove` 移除组件后，为什么要自动删除 `components/` 下的源码目录？如果用户有未提交的修改怎么办？这不是太危险了吗？

**决策：**
`brickkit remove` 自动删除对应的源码目录（如果存在）。remove 就是彻底移除，不留痕迹。

**理由：**

- **remove 的语义就是"彻底移除"：** 用户执行 `brickkit remove`，意图是"我不要这个组件了"。如果源码目录还留着，会产生"垃圾"——一个不在 brickkit.yaml 中但源码还在的目录，容易造成困惑。
- **未提交的修改是用户自己的问题：** 如果用户有未提交的修改，应该在 remove 之前先 commit + push。CLI 不应该替用户检查"你有没有未提交的修改"。这符合"平台提供工具，不替人做决定"的原则。
- **与 `brickkit sync` 的归档逻辑一致：** `brickkit sync` 归档的是"不启动的组件"，`brickkit remove` 删除的是"不存在的组件"。两者语义不同，行为也不同。归档是"暂时不用"，删除是"彻底不要"。
- **避免"僵尸目录"：** 如果 remove 后不删除源码目录，用户可能会忘记这些目录的存在。随着时间推移，`components/` 下会积累越来越多的"僵尸目录"，增加管理负担。
- **归档目录也一样要删：** `brickkit sync` 的 `planSync` 只看 `brickkit.yaml` 里声明过的组件——组件一旦被 remove，sync 就再也不认识 `components/.archived/` 里那份源码了。remove 不顺手清掉，它就是一个连自动整理都够不着的僵尸目录，比 `components/` 下的僵尸目录更难被发现（归档目录以 `.` 开头，文件管理器默认隐藏）。

**一句话总结：** remove 就是彻底移除。如果你有未提交的修改，那是你的问题，不是 CLI 的问题。

#### 补充：这条论证覆盖不到手写的组件

上面第二条理由——"未提交的修改是用户自己的问题，应该在 remove 之前先 commit +
push"——**前提是有地方可 push**，也就是源码来自 `--repo` clone。

而 `init` 生成的骨架把本地安装源指向 `./components`，试用指南 17 教的正是在那儿
手写自己的组件。那种源码没有远端，"先 push"这条出路根本不存在。于是这条路完全
由默认约定自己铺出来：

```
照试用指南 17 在 components/demo/hello/ 写自己的组件
  → brickkit add --local 加进来
  → 觉得暂时不用了，brickkit remove demo/hello
  → 源码永久没了
```

没有确认、没有 `--yes`、一句提示都没有。真跑验证过：手写的 `main.go` 一并消失。

**而同一个仓库在别处的立场恰好相反。** `Clone` 遇到已存在的目录**坚决不覆盖**
（"活跃目录里多半是使用者自己的源码，平台不替他决定删不删"），`sync` 的 `move`
遇到已存在的目标同样拒绝。删除比覆盖更彻底，却是唯一不问的那个——这是一处
真正的自相矛盾，不是取舍。

**修法不是推翻这一节，是给它补上判据。** 判据从"你有没有做对"换成
**"这些字节在别的地方还有没有"**：

| 情形 | 行为 |
| --- | --- |
| 干净、且全部推到远端的 clone | ✅ 照常删——**本节写的正是这种情况，行为一点没变** |
| 不是 Git 仓库 / 有未提交的改动 / 有提交没推 | ❌ 拦下，`--force` 可覆盖 |

"避免僵尸目录"那条理由完全成立，所以拦下时给的三条出路里，第三条正是
`enabled: false` + `brickkit sync`——它把源码收进归档目录而不是删掉，
既不留僵尸，也不丢东西。

### 2.21 为什么平台不提供组件合并部署（多个组件跑成一个实例）？

**质疑：** 一个组件一个容器一个进程，20 个 Spring Boot 组件光是 JVM 地板就要 4–9 G（005 §2.5）。私有化交付时客户只给一台 8G 的机器。为什么平台不提供一个 `brickkit up --consolidated`，把同框架的组件合并成一个实例？

**决策：**
平台**不提供**任何合并部署的支持：没有命令、不生成外壳、不做校验、不出警告。同时**明确承认这条路是可行的**，并写一份文档说清它怎么走、代价是什么（仓库根《组件合并部署》）。

**理由：**

**1. 需求是真的，这条不否认。**

内存成本几乎完全由语言决定，Go 与 JVM 之间差 20 倍。以 JVM 为主、又要交付到低配硬件的项目，"合并"不是懒惰，是算过账的选择。所以这里的结论不是"这个需求不该有"，而是"这件事不该由平台做"。

**2. 平台其实已经把最难的一半做完了——而且是免费做完的。**

调用方只读 `*_ENDPOINT`，值是 `http://<版本化服务名>:<端口>`，服务名可推算，两个环境格式一样。**对端是 10 个容器、1 个容器还是 1 个 JVM 里的 10 个模块，调用方没有任何办法知道。**

这正是"DNS 就是注册中心"（§2.1）与"不做 API 代理 / 路由"（001 §5.2）的复利：调用链上没有中间层需要同步，所以只要 DNS 名指到别处，对端就可以被换成任何东西。**一个有注册中心、有代理的平台反而做不到这一点**——那些组件在中心里登记过，换形态要先说服中心。

于是剩下的活是：端口别撞、把 N 个服务名 alias 到外壳、接手健康检查与迁移。**这些全都在用户自己的 compose / Service / 框架里，一行平台代码也用不上。**

**3. 真做起来，平台要开始理解一个它不该理解的概念：外壳。**

`--consolidated` 意味着 CLI 得回答：哪些组件能合（同语言？同框架？同框架的哪个大版本？）、产物在镜像里的哪个路径（Manifest 没有这个字段，闭源镜像更无从猜）、外壳用哪个基础镜像、进程管理器是 supervisord 还是 s6、Spring 的多 connector 怎么起、Django 的多 app 怎么挂、N 个模块的迁移谁先谁后、一个容器一个 healthcheck 怎么代表 10 个模块的健康。

这是 §2.7（不做通信治理）与 002 的"框架层 vs 平台层"同一条线：**每多支持一个框架就多一份永远追不上生态的适配代码**，而它换来的东西用户自己两百行 compose 就能写出来。

**4. 更硬的一条：合并把平台的承诺一条条作废，而平台不能一边承诺一边帮你违约。**

| 平台的承诺 | 合并之后 |
| --- | --- |
| 故障隔离（一个组件挂不影响别人） | 一个模块拖死进程，整组重启 |
| 独立发布、独立回滚、独立扩缩容 | 合并那一组从此是一个发布单元 |
| 生产环境强制签名（008 §8.5） | 跑的是本地构建的外壳镜像，不在任何签名覆盖范围内 |
| 组件之间不共享代码（001 §2.1） | 合成一个多模块工程后，只靠纪律撑着 |
| 一个组件一个仓库（§2.16） | 外壳工程天然长成 monorepo 的形状 |

**如果平台出一条命令把这些一起拿掉，那平台就同时是"承诺方"和"违约工具的提供方"。** 用户自己动手时，这五条是他明确知道自己放弃的；平台给一个 `--consolidated`，它们会变成"平台支持的模式"里一串没人读的小字——将来必然有人拿故障隔离没了当 bug 报。

**5. 但"不做"不等于"不说"。**

不写文档的后果不是没人合并，是**每个人各自摸黑合并一遍**，各自在同一批坑里翻车：端口都写 8080、别名漏配、`enabled: false` 拿来当开关（把依赖方一起关掉了）、`local: true` 借用之后忘了迁移不再自动跑、开着 networkPolicy 把自己的外壳挡在外面。这些现象**没有任何一处报错指向"合并"**，排障方向会一路跑到组件代码上。

而且平台自己也有一处真实空缺要认：**K8s 下没有"这几个组件我自己接管、你别生成"的表达方式**（`local: true` 只能配 docker，`enabled: false` 会把依赖方一起拖下去）。这条空缺写在文档里，用户能提前知道 K8s 上 `brickkit up` 那一键不能直接用；不写，他会在 apply 之后才发现。

**一句话总结：** 平台把"对端是什么"隐藏得足够干净，所以合并这条路本来就是通的——不需要平台开门。而平台一旦开这道门，就得同时对故障隔离、独立发布、强制签名这些承诺的失效负责，那些代价只应由自己按下这个决定的人来付。

### 2.22 为什么默认仍推荐"一个组件一个数据库"，而不是"一个组件一个 schema"？

**质疑：** PostgreSQL 有 schema，MySQL 里的 database 本来就和它一个意思。既然一个组件一个 schema 也能划清数据边界，为什么 006 §7.3 还把"一个组件一个 database"排在前面？而且组件一多，一库一组件是不是白白多出一堆连接？

**决策：**
默认推荐**保持不变**：一个组件一个 database（006 §7.3）。同时把两件文档没说清的事补上——schema 与 database 在各引擎里分别是哪一档边界（006 §7.7），以及 schema 分组**不会**减少连接数（006 §7.8）。schema 分组仍然是被允许的方案（006 §7.2 表里的"✅ 可用"），只是不作为默认建议。

**理由：**

**1. "省连接"这条推论在默认部署形态下是错的。**

连接数由**进程数 × 池大小**决定，不由库的个数决定。平台的默认形态是一个组件一个容器一个进程（005 §2.5），30 个组件就是 30 个进程、30 个各自独立的连接池。把它们指向同一个库的 30 个 schema，这 30 个池仍然在 30 个进程里，**没有任何机制让它们合流**。

挂 PgBouncer 也不自动成立：**它的服务端池按 `(user, database)` 分**，schema 分组只合并了 `database` 那一维，而 006 §7.5 / §11.1、008 §15 要求每个组件一个独立账号——30 个账号 × 1 个库，还是 30 个服务端池。要真省下来，**代价是放弃每组件独立账号**，那是拿数据边界换连接数。

这条值得单独记下来，因为它反直觉：**"库变少了连接就变少"听起来天经地义，但它把两笔账记成了一笔。**

**2. 默认值要为"看不懂这件事的人"服务。**

schema 分组要做对，得同时管住三样东西：迁移工具默认往 `public` 里写、`search_path` 不能设完就把连接还回池子（会泄漏给下一个借用者）、跨 schema 的越界只有权限拦得住。三样里漏一样，**症状都是"不报错，只是悄悄读写了别人的数据"**——和 006 §7.2 要防的是同一件事，而且比它更难查。

一个 database 一个组件不需要理解这些：**连接绑在库上，越界这件事在 PG 上物理不可能。** 默认值应当是"想错了也不会烂"的那一个。

**3. 但收益是真的，只是记在别的账上。**

schema 分组省的是每库的服务端开销与运维面：每库一份系统目录与统计信息、扩展要装 N 遍、autovacuum 按库轮、备份与配额按库管。库的数量上百时这些会真的开始疼。所以文档的写法不是"别用 schema"，而是**把它省的和不省的分开说**（006 §7.7 末尾与 §7.8）。

**4. 唯一该主动选 schema 分组的场景，平台恰好不支持。**

合并部署（多个组件跑成一个进程）下，schema 分组是把 N 个池并成 1 个的**必要条件**——PG 的连接绑 database，一库一组件时那些池物理上合不了。而合并部署是明确的用户自理（§2.21）。

**一条给平台的默认值定性的规则：默认值服务于平台承诺的形态，不服务于平台明确不支持的形态。** 为一条自理路线去改默认推荐，等于让走默认路的多数人替少数人的选择付理解成本。所以这条建议写进《组件合并部署》第 7 章，而不是写进 006 的主推荐。

它还有时序性，这一点文档必须说：**库按 database 建好、数据进去之后再改成一库多 schema，就是一次数据迁移。** 预见到将来可能合并的项目（JVM 为主 + 私有化交付），一开始就选 schema 才是便宜的。**平台不推荐它，但必须让人在还来得及的时候知道有这个岔路口。**

**一句话总结：** 默认推荐不变，因为"省连接"在默认形态下不成立，而 schema 分组要做对需要理解三个静默失效点；但它在合并部署下是真正的必要条件，所以把它的收益与代价写清楚，放在会用到它的那份文档里。

## 3. 总结

BrickKit 的所有架构设计，都围绕着一个核心哲学：

**平台只做"连接器"和"翻译官"，绝不越界去做"业务逻辑"和"基础设施"已经做好的事情。**

- 我们用 **DNS** 替代了注册中心。
- 我们用 **底层引擎 Probe** 替代了健康检查轮询。
- 我们用 **精确版本** 替代了复杂的版本范围解析。
- 我们用 **多版本默认共存** 替代了版本冲突阻断。
- 我们用 **环境变量** 替代了沉重的配置中心。
- 我们用 **容器化** 统一了前端与后端的部署模型。
- 我们用 **信任模型** 替代了前置安全审查。
- 我们用 **"说明书"而非"安检机"** 定位 configSchema。
- 我们用 **"完全不注入"而非"注入空值"** 处理弱依赖缺失。
- 我们用 **三种 `enabled` 状态** 实现关联性组件管理。
- 我们用 **brickkit.yaml 就是声明** 的原则，让配置即意图。
- 我们用 **局部性原则与按需启用** 确保 50 个组件不会失控。
- 我们用 **一个组件一个仓库** 保证独立发布、独立移动、独立权限。
- 我们用 **独立命令 `brickkit sync`** 管理源码工作区，不侵入 `brickkit up`。
- 我们用 **按需 `--repo`** 替代自动 clone，源码是开发时需求不是安装时需求。
- 我们用 **CLI 不管 Git 权限** 保持简单，fork/remote/push 是用户自己的事。
- 我们用 **remove 自动删除源码** 保持干净，不留僵尸目录。
- 我们用 **不提供合并部署** 守住承诺：路是通的，账由按下决定的人自己付。

BrickKit 的克制，正是为了把最大的自由和灵活性，留给真正创造业务价值的组件开发者。
