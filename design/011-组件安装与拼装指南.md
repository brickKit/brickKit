## 1. 本文档目标

本文档教你如何安装组件、如何拼装多个组件形成完整系统、如何获取组件源码进行修改、以及如何整理源码工作区。

读完后你将知道：

- 怎么安装单个组件（`brickkit add` + `brickkit up`）
- 怎么安装带依赖的组件（自动拉取依赖）
- 怎么获取依赖组件的 API 契约（artifacts 自动下载）
- 怎么获取组件源码进行修改（`--repo` / `--repo-all`）
- 怎么整理源码工作区（`brickkit sync`）
- 怎么修改开源组件源码后上传（fork + remote）
- 怎么配置资源绑定（brickkit.yaml 中声明）
- 怎么覆盖组件配置（config 字段）
- 怎么拼装多个组件形成完整业务系统
- 怎么渐进式拼装（安装 → 获取契约 → 开发连接组件 → 发布 → 再安装）
- 怎么本地调试组件（IDE debugger + local-debug.env）
- 怎么更新组件
- 升级时 CLI 自动执行哪些检查
- 升级后调用方需要做什么
- 怎么处理破坏性变更（Major 版本）
- 怎么处理数据库迁移
- 怎么回滚组件
- 怎么卸载组件
- 怎么查看启动顺序
- 怎么排查安装问题

## 2. 安装前准备

### 2.1 确认 CLI 已安装

```bash
brickkit version
# BrickKit CLI v1.0.0
# 支持 Manifest 版本：brickkit/v1
# 支持部署目标：docker, k8s
```

### 2.2 确认 Docker 可用

```bash
# Docker
docker --version
docker compose version

```

### 2.3 初始化项目

```bash
mkdir my-project
cd my-project
brickkit init my-project
```

输出：

```
✅ 项目已初始化：my-project
   📁 brickkit.yaml        项目配置
   📁 components/          组件源码（已配为本地安装源 local-dev）
   📁 .brickkit/           CLI 工作目录

下一步：
  brickkit add --local               把 components/ 下的组件全加进来
  brickkit add people/basic@1.0.0    从安装源添加组件
  brickkit up                        一键启动
```

### 2.4 配置安装源

`brickkit init` 生成的骨架**已经自带一个本地安装源**（`local-dev` → `./components`，
正是 init 自己创建的那个目录），本地开发不用改任何配置。市场源在骨架里是注释掉的
——CLI 猜不到你的市场地址，要用就取消注释并填上。

完整写法：

```yaml
# brickkit.yaml
project: my-project

deploy:
  target: docker

sources:
  # 官方市场（默认）
  - id: brickkit-market
    type: market
    url: https://market.brickkit.io/api/v1
    authToken: ${MARKET_TOKEN}    # 可选，访问 private 组件时需要
    enabled: true

  # 本地开发目录（可选）
  - id: local-dev
    type: local
    path: ./components
    enabled: true
```

**Token 优先级：** 如果已执行 `brickkit login`，CLI 优先使用 `.brickkit/credentials` 中的登录态，忽略 `authToken` 字段。

### 2.5 确认基础资源（如果需要）

如果你的组件需要数据库等资源，需要做两件事：**声明资源** 与 **为每个组件创建 database**。

**① 为每个组件创建 database（每个组件执行一次）**

平台不会替你创建数据库（006 §9.1、§9.5）：库里的**表**由组件自己的 migration 建，
但 **database 本身**要你先建好。每个组件用**自己的**数据库——共用会让一个组件
读到另一个组件的表（002 §2.2 数据自治）。

组件的 README 里会写明它预设的库名，照着执行一次即可：

```bash
psql -U postgres -c "CREATE DATABASE brickkit_department"
psql -U postgres -c "CREATE DATABASE brickkit_people"

# 数据库跑在容器里时
docker exec -i my-postgres psql -U postgres -c "CREATE DATABASE brickkit_department"
```

> 忘了建也不会静默出错，但报错来的时机是**迁移容器**，不是 up 之前：
> `database "brickkit_department" does not exist`。平台这边把话说在前面——
> `brickkit up` **每次**都会把本次需要的库连同 `CREATE DATABASE` 语句列出来
> （006 §9.5）。两者配合：清单说"该建哪些"，迁移失败说"你还没建"。

**② 在 brickkit.yaml 中声明资源**

```yaml
resources:
  - kind: database
    engine: postgresql
    id: postgres-main
    host: host.docker.internal
    port: 5432
    username: dev
    password: ${POSTGRES_PASSWORD}
    bindings: []    # 后续安装组件时绑定

  - kind: cache
    engine: redis
    id: redis-main
    host: host.docker.internal
    port: 6379
    password: ${REDIS_PASSWORD}
    bindings: []
```

## 3. 安装单个组件

### 3.1 添加组件

```bash
brickkit add people/basic@1.0.0
brickkit add people/basic            # 不写版本：装安装源上最新的可安装版本
```

**不写版本时装哪个？** CLI 在 add 那一刻去安装源问出最新的**可安装**版本
（市场上 `draft` / `blocked` 的版本装不上，会被跳过；`deprecated` 能装，保留），
把它以精确版本写进 `brickkit.yaml`。按安装源优先级，**第一个有这个组件的源说了算**。
解析结果会打印出来，包括它来自哪个源：

```
$ brickkit add people/basic
🔎 未指定版本，解析到 people/basic@2.0.0（来自安装源 brickkit-market，类型 market）
```

省略版本号不等于可以写范围约束：`brickkit add people/basic@^1.0.0` 照旧报错。
配置里永远只有精确版本（012 §2.2）。

同 ID 已经装了别的版本时，CLI 会先问一句再共存——共存会真的多起一个容器，
而不写版本号的人多半没这个预期。`--yes` 时不问。

**本地开发：一次把本地源里的组件全加进来**

`components/` 下往往躺着一批自己写的、或 `--repo` clone 下来的组件，一个个 `add` 很烦：

```bash
brickkit add --local
```

它扫描所有 `type: local` 的安装源，把扫到的组件全部添加。已在配置中的跳过；
同 ID 但版本不同的也跳过并单独提示（批量命令不替你决定多起一个容器）；
任一组件解析失败则**整体中止，`brickkit.yaml` 一个字节不动**，并点名是哪个组件卡住了。

`components/.archived/`（`brickkit sync` 的归档目录）不会被扫进来——归档的组件
不该被 `--local` 拽回来。`--local` 不接组件 ID，也不能与 `--repo` / `--repo-all`
同用：本地组件的源码本来就在盘上，无须（也无从）再 clone 一份。

**`component.yaml` 有问题的目录会被点名跳过**，而不是从"扫到几个"里悄悄少掉一个：

```
⚠️ demo/broken 跳过：metadata.version 不是精确版本：latest
   来自安装源 local-dev；修好它再执行一次 brickkit add --local
```

CLI 行为：

1. 从安装源获取 `people/basic@1.0.0` 的 Manifest
2. 解析依赖（如果有）
3. 递归拉取依赖组件的 Manifest
4. 下载所有 artifacts（API 契约、SDK、文档等）到 `.brickkit/artifacts/`
5. 写入 brickkit.yaml（不写 `enabled` 字段）
6. 缓存 Manifest 到 `.brickkit/manifests/`

输出示例：

```
📦 添加 people/basic@1.0.0
   ├── 依赖 department/tree@1.0.0 ✅ 已拉取
   │   ├── Manifest ✅
   │   └── artifacts ✅（2 个文件：department.proto, openapi.json）
   └── 资源依赖 database/postgresql ✅ 已声明
✅ 已写入 brickkit.yaml（2 个组件）
📁 已下载 artifacts 到 .brickkit/artifacts/（3 个文件）
```

### 3.2 添加组件并 clone 源码

如果你需要修改组件的源码，使用 `--repo` 参数：

```bash
brickkit add people/basic@1.0.0 --repo
```

输出示例：

```
📦 添加 people/basic@1.0.0
   ├── Manifest ✅
   └── artifacts ✅（1 个文件：openapi.json）
📁 已 clone 源码到 components/people/basic/
✅ 已写入 brickkit.yaml（1 个组件）
💡 如需修改源码并上传，请参考文档"修改开源组件源码后如何上传"
```

`--repo` 参数说明：

- 只 clone 指定的组件的完整 Git 仓库到 `components/<scope>/<name>/`
- 仅对开源组件（`sourceType: git`）有效
- 闭源组件报错阻断（闭源组件没有 Git 仓库）
- 如果目标目录已存在，报错阻断

### 3.3 启动组件

```bash
brickkit up
```

CLI 行为：

1. 读取 brickkit.yaml
2. 读取所有组件 Manifest
3. 启停判定（enabled）
4. 检查强依赖是否满足
5. 拓扑排序得出启动顺序
6. 生成 docker-compose.yaml（或 K8s YAML）
7. 注入环境变量（依赖地址带版本号、资源连接、自身配置含 config 覆盖）
8. 生成 `local-debug.<版本化服务名>.env`（如有 `local: true` 组件）
9. 检测镜像拉取权限
10. 执行数据库迁移（如有 migration 字段）
11. 调用底层引擎启动

输出示例：

```
🚀 启动项目 my-project（deploy.target: docker）
 📋 组件状态计算：
    ✅ department/tree@1.0.0           启动（根组件）
    ✅ people/basic@1.0.0              启动
 📋 启动顺序：
    1. department-tree-1-0-0       无依赖
    2. people-basic-1-0-0          ← 依赖 1
 🔍 检测镜像拉取权限... ✅ 全部通过
 📄 已生成：.brickkit/generated/docker-compose.yaml
 🔧 执行数据库迁移：people-basic（python manage.py migrate）✅
 🐳 正在启动...
 ✅ 全部组件已启动
    department-tree-1-0-0    running
    people-basic-1-0-0       running
```

### 3.4 验证组件运行

```bash
brickkit status
```

输出：

```
📊 项目状态：my-project（deploy.target: docker）

✅ 运行中（2 个组件）
 ┌─────────────────┬───────┬───────────────────┬─────────────────────────┐
 │ 组件            │ 版本  │ 状态              │ 端口                    │
 ├─────────────────┼───────┼───────────────────┼─────────────────────────┤
 │ department/tree │ 1.0.0 │ 运行中（healthy） │ 8080/tcp                │
 │ people/basic    │ 1.0.0 │ 运行中（healthy） │ 0.0.0.0:18092->8080/tcp │
 └─────────────────┴───────┴───────────────────┴─────────────────────────┘

📦 资源状态
 ┌───────────────┬──────────┬──────────────────────────────┐
 │ 资源          │ 类型     │ 状态                         │
 ├───────────────┼──────────┼──────────────────────────────┤
 │ postgres-main │ database │ 可达（容器 postgres 运行中） │
 └───────────────┴──────────┴──────────────────────────────┘
```

### 3.5 调用组件

```bash
# 从 Docker Network 内调用
docker exec people-basic-1-0-0 wget -qO- http://people-basic-1-0-0:8080/api/v1/people

# 查看日志
docker compose -p brickkit-my-erp -f .brickkit/generated/docker-compose.yaml logs people-basic-1-0-0
```

### 3.6 停止组件

```bash
brickkit down
```

**重要：`brickkit down` 不删除数据库数据（volume）。** 等价于 `docker compose down`（不带 `-v` 参数）。如需彻底清理，请手动执行 `docker volume rm` 或 `docker compose down -v`。

## 4. 安装带依赖的组件

### 4.1 自动拉取依赖

当组件声明了依赖时，CLI 自动处理：

```yaml
# erp/backend 的 Manifest
dependencies:
  components:
    - people/basic@1.0.0          # 强依赖（精确版本）
    - department/tree@1.0.0       # 强依赖
    - authorization/rbac@1.0.0    # 强依赖
    - id: infra/redis-event-bus@1.0.0
      optional: true              # 弱依赖
  resources:
    - kind: database
      engine: postgresql
    - kind: cache
      engine: redis
```

安装 `erp/backend` 时：

```bash
brickkit add erp/backend@1.0.0
```

输出示例：

```
📦 添加 erp/backend@1.0.0
   ├── 依赖 people/basic@1.0.0 ✅ 已拉取
   │   ├── Manifest ✅
   │   ├── artifacts ✅（1 个文件：openapi.json）
   │   └── 依赖 department/tree@1.0.0 ✅ 已拉取
   │       ├── Manifest ✅
   │       └── artifacts ✅（2 个文件：department.proto, openapi.json）
   ├── 依赖 department/tree@1.0.0 ✅ 已拉取（去重）
   ├── 依赖 authorization/rbac@1.0.0 ✅ 已拉取
   │   ├── Manifest ✅
   │   └── artifacts ✅（2 个文件：rbac.proto, openapi.json）
   └── 弱依赖 infra/redis-event-bus@1.0.0 ✅ 已拉取
✅ 已写入 brickkit.yaml（5 个组件）
📁 已下载 artifacts 到 .brickkit/artifacts/（5 个文件）
ℹ️ 提示：infra/redis-event-bus 是弱依赖，已写入配置但**默认不会启动**（003 §4.3）
   需要它时给它写 enabled: true
```

### 4.2 添加组件并 clone 所有依赖源码

如果你需要修改多个组件的源码，使用 `--repo-all` 参数：

```bash
brickkit add erp/backend@1.0.0 --repo-all
```

输出示例：

```
📦 添加 erp/backend@1.0.0
   ✅ erp/backend         → clone 完成（components/erp/backend/）
   ✅ people/basic        → clone 完成（components/people/basic/）
   ✅ department/tree     → clone 完成（components/department/tree/）
   ⏭️ authorization/rbac  → 闭源组件，跳过 clone
   ✅ infra/redis-event-bus → clone 完成（components/infra/redis-event-bus/）
✅ 已写入 brickkit.yaml（5 个组件）
📁 已 clone 4 个开源组件仓库（跳过 1 个闭源组件）
```

`--repo-all` 参数说明：

- clone 所有递归依赖中开源组件的完整 Git 仓库到 `components/` 目录
- 闭源组件跳过并输出提示（闭源组件没有 Git 仓库）
- 如果目标目录已存在，报错阻断

### 4.3 依赖安装顺序

CLI 按依赖顺序启动（拓扑排序）：

```
1. department/tree（无依赖）
2. people/basic（依赖 1）
3. authorization/rbac（依赖 1）
4. erp/backend（依赖 1, 2, 3）
```

### 4.4 强依赖缺失

如果强依赖无法获取，CLI 报错阻断：

```
❌ 添加失败：强依赖缺失
   组件：erp/backend@1.0.0
   缺失依赖：authorization/rbac@1.0.0
   原因：该组件在所有安装源中均未找到
   建议：
   1. 检查安装源配置（brickkit.yaml → sources）
   2. 确认组件是否已发布到市场
   3. 确认版本号是否正确
```

### 4.5 弱依赖缺失

如果弱依赖无法获取，CLI 警告但继续：

```
⚠️ 弱依赖未获取：infra/redis-event-bus@1.0.0
   影响组件：erp/backend（异步事件功能不可用）
   该组件的环境变量 INFRA_REDIS_EVENT_BUS_ENDPOINT 不会被注入
   如需启用，请确认该组件已发布到市场
```

**弱依赖缺失时的降级处理完全是组件自己的责任。** CLI 的职责到"完全不注入该环境变量"（不注入空字符串）就结束了。组件必须使用安全读取方式（如 `os.environ.get()`）并在代码中自行处理弱依赖不可用的情况。

⚠️ **不要使用 `os.environ["INFRA_REDIS_EVENT_BUS_ENDPOINT"]`（方括号访问）。** 弱依赖缺失时该变量不存在，方括号访问会抛出 `KeyError`，导致组件崩溃。

### 4.6 多版本共存

由于使用精确版本和版本化服务名，多版本共存是天然支持的。

**默认行为：多版本共存。** 当 brickkit.yaml 中同一组件 ID 出现多个版本时，CLI 直接为每个版本生成独立的容器，无需任何额外参数。

```yaml
# brickkit.yaml 中的多版本共存
components:
  - id: people/basic
    version: 1.0.0    # 服务名：people-basic-1-0-0
  - id: people/basic
    version: 2.0.0    # 服务名：people-basic-2-0-0
```

调用方通过 Manifest 中的精确版本声明决定调哪个。

⚠️ **注意：** 多版本共存只是物理缓冲，不保证数据层兼容。涉及破坏性变更（删除字段等）时，必须遵循 002 组件规范第 3.7 节"破坏性变更（Major）协同守则"，由部门间协调同步升级。

## 5. 配置资源绑定

### 5.1 在 brickkit.yaml 中声明资源绑定

```yaml
# brickkit.yaml
resources:
  - kind: database
    engine: postgresql
    id: postgres-main
    host: host.docker.internal
    port: 5432
    username: dev
    password: ${POSTGRES_PASSWORD}
    bindings:
      - componentId: department/tree
        database: department
      - componentId: people/basic
        database: people
      - componentId: authorization/rbac
        database: authorization
      - componentId: erp/backend
        database: erp

  - kind: cache
    engine: redis
    id: redis-main
    host: host.docker.internal
    port: 6379
    password: ${REDIS_PASSWORD}
    bindings:
      - componentId: authorization/rbac
      - componentId: infra/redis-event-bus
```

### 5.2 绑定规则

| 规则 | 说明 |
| --- | --- |
| 资源必须已声明 | brickkit.yaml 中 resources 字段 |
| 一个资源可以绑定多个组件 | 如 postgres-main 绑定 4 个组件 |
| 每个组件使用不同的 database | 数据隔离 |
| 组件声明资源依赖（kind + engine） | Manifest 中声明 |
| 管理员在 brickkit.yaml 中绑定具体实例 | 静态声明 |
| CLI 校验资源是否已声明 | `brickkit up` 时检查 |
| CLI 注入资源连接配置 | 生成部署文件时注入环境变量 |

### 5.3 绑定检查

`brickkit up` 时，CLI 检查：

1. 组件声明了资源依赖（如 `kind: database, engine: postgresql`）
2. brickkit.yaml 中是否已声明对应类型的资源
3. 该资源是否已绑定给当前组件

如果资源未声明或未绑定，CLI 在**生成部署文件之前**报错阻断，一次报全：

```
❌ 错误：资源依赖未满足
   people/basic@1.0.0：需要 kind: database、engine: postgresql（brickkit.yaml 的 resources 中未声明）
   建议：
   1. 在 brickkit.yaml → resources 中声明该资源（kind + engine 必须与组件声明的一致）
   2. 在该资源的 bindings 中加入 componentId: <组件ID>
   3. 暂时不想跑这个组件的话，给它写 enabled: false
```

只查**本次会启动的**组件；`--dry-run` 时降级成警告。完整规则见 006 §4.4。

### 5.4 资源没跑起来会怎样

CLI **不替你探测资源**。`brickkit up` 每次都会列出"要先跑起来什么"
（含要预先建的库），但不会去连一下看看：

```
📌 以下基础资源需要先跑起来（平台不代为部署，见 006 §9.1）：
   pg-main      postgresql   host.docker.internal:5432  供 people/basic 使用
      需要库 people（供 people/basic 使用）：CREATE DATABASE "people";
```

资源没起来时，报错来自**组件自己**（或它的迁移容器）：

```
dial tcp 172.17.0.1:5432: connect: connection refused
```

**这条信息比平台的任何探测结论都准确**——它用的是组件自己那套凭据、
从容器网络里连，而 CLI 只能从宿主机、用另一套凭据试（006 §8.3、§12.3）。

> 早先有个 `brickkit up --check-resources` 做这件事，已经删掉。它必须显式请求、
> 只会警告，而给出的结论还不如不用它时准确——`host: host.docker.internal` 时它甚至
> 给的是**反的**答案（宿主机上通，容器里连的却是它自己）。

## 6. 覆盖组件配置

### 6.1 config 字段

组件在 Manifest 中通过 `configSchema` 声明自己接受的配置项。使用者可以通过 brickkit.yaml 的 `config` 字段覆盖默认值。

Manifest 中声明：

```yaml
configSchema:
  type: object
  properties:
    sessionTtlSeconds:
      type: integer
      default: 3600
    enableAudit:
      type: boolean
      default: true
```

brickkit.yaml 中覆盖：

```yaml
components:
  - id: erp/backend
    version: 1.0.0
    config:
      sessionTtlSeconds: 7200
      enableAudit: false
```

### 6.2 CLI 注入逻辑

CLI 读取 configSchema 默认值，用 config 字段覆盖，然后注入为环境变量：

```
SESSION_TTL_SECONDS=7200    # 被 config 覆盖
ENABLE_AUDIT=false           # 被 config 覆盖
```

未被覆盖的配置项使用 configSchema 中的默认值。

**重要：CLI 不校验 config 值的类型。** configSchema 是"配置说明书"，不是"安检机"。

### 6.3 config 与密钥的职责分离

| 配置类型 | 存放位置 | 示例 |
| --- | --- | --- |
| 业务配置 | brickkit.yaml → `config` 字段 | `sessionTtlSeconds: 7200` |
| 密钥/密码 | `.env` 文件（Docker）/ K8s Secret（生产） | `DATABASE_PASSWORD=xxx` |

## 7. 拼装多个组件

### 7.1 什么是拼装

拼装 = 添加多个组件 + 配置依赖关系 + 绑定资源 + 覆盖配置 + 让它们协同工作。

### 7.2 拼装示例：搭建一个 ERP 系统

```
portal/user-frontend（前端组件，nginx 容器）
      ↓ 强依赖
erp/backend（连接组件）
      ├── ↓ 强依赖 → people/basic
      │       └── ↓ 强依赖 → department/tree
      ├── ↓ 强依赖 → authorization/rbac
      └── ↓ 弱依赖 → infra/redis-event-bus
```

### 7.3 拼装步骤

**第1步：初始化项目**

```bash
mkdir my-erp
cd my-erp
brickkit init my-erp
```

**第2步：声明基础资源**

编辑 `brickkit.yaml`：

```yaml
resources:
  - kind: database
    engine: postgresql
    id: postgres-main
    host: postgres          # Docker Network 中的服务名
    port: 5432
    username: dev
    password: ${POSTGRES_PASSWORD}
    bindings:
      - componentId: department/tree
        database: department
      - componentId: people/basic
        database: people
      - componentId: authorization/rbac
        database: authorization
      - componentId: erp/backend
        database: erp

  - kind: cache
    engine: redis
    id: redis-main
    host: redis             # Docker Network 中的服务名
    port: 6379
    password: ${REDIS_PASSWORD}
    bindings:
      - componentId: authorization/rbac
      - componentId: infra/redis-event-bus
```

**第3步：安装连接组件（自动安装所有依赖）**

```bash
brickkit add erp/backend@1.0.0
```

CLI 会自动：

1. 拉取 `department/tree@1.0.0`（被 people/basic 依赖）
2. 拉取 `people/basic@1.0.0`
3. 拉取 `authorization/rbac@1.0.0`
4. 拉取 `infra/redis-event-bus@1.0.0`（弱依赖）
5. 下载所有 artifacts（proto / OpenAPI 等）
6. 写入 brickkit.yaml（不写 `enabled` 字段）

**第4步：安装前端组件**

```bash
brickkit add portal/user-frontend@1.0.0
```

前端组件是一个 nginx 容器，和其他组件一样是 container。

**第5步：（可选）配置外部暴露**

编辑 brickkit.yaml，为前端组件添加 expose：

```yaml
components:
  - id: portal/user-frontend
    version: 1.0.0
    expose: true
    hostname: portal.example.com    # K8s 必须，Docker 可省略
    exposePort: 8080                # Docker 环境：自定义宿主机映射端口（可选）
```

**第6步：（可选）覆盖组件配置**

```yaml
components:
  - id: erp/backend
    version: 1.0.0
    config:
      sessionTtlSeconds: 7200
      enableAudit: true
```

**第7步：一键启动**

```bash
brickkit up
```

**第8步：验证所有组件运行**

```bash
brickkit status
```

**第9步：测试组件间调用**

```bash
# 从 erp/backend 容器内调用 people/basic
docker exec erp-backend-1-0-0 wget -qO- http://people-basic-1-0-0:8080/api/v1/people

# 从 erp/backend 容器内调用 department/tree
docker exec erp-backend-1-0-0 wget -qO- http://department-tree-1-0-0:8080/api/v1/departments
```

**第10步：测试前端组件**

```bash
# Docker 环境（expose: true 时映射了端口）
curl http://localhost:8080/
```

### 7.4 渐进式拼装：从安装到开发到发布

BrickKit 支持"渐进式拼装"的开发模式：先安装底层组件，获取 API 契约，基于契约开发连接组件，发布后再安装连接组件，自动拼装完整系统。

完整流程：

```
第 1 步：安装底层组件（获取 API 契约）
      brickkit add department/tree@1.0.0
      → CLI 下载 Manifest + proto 文件到 .brickkit/artifacts/

 第 2 步：查看下载的契约文件
      ls .brickkit/artifacts/department-tree-1-0-0/api-contract/
      → proto/department/v1/department.proto

 第 3 步：基于契约开发连接组件
      → 读取 proto 文件，生成客户端代码
      → 开发连接组件业务逻辑
      → 在连接组件的 Manifest 中声明依赖 department/tree@1.0.0

 第 4 步：发布连接组件
      brickkit publish --path ./erp-backend --visibility public

 第 5 步：最终用户安装连接组件（自动拼装）
      brickkit add erp/backend@1.0.0
      → CLI 自动递归拉取所有依赖 + 下载所有 artifacts
      brickkit up
      → 一键启动完整系统
```

渐进式拼装的本质：

| 角色 | 做什么 | 使用什么 |
| --- | --- | --- |
| 底层组件开发者 | 开发并发布底层组件（如部门组件） | `brickkit publish` |
| 连接组件开发者 | 安装底层组件 → 获取契约 → 开发连接组件 → 发布 | `brickkit add` + IDE + `brickkit publish` |
| 最终用户 | 安装连接组件 → 自动拼装完整系统 | `brickkit add` + `brickkit up` |

## 8. 获取组件源码与工作区管理

### 8.1 为什么需要获取组件源码

默认情况下，`brickkit add` 只拉取 Manifest 和 artifacts，不 clone 组件的完整 Git 仓库。大多数用户只需要"安装并使用"组件，不需要修改源码。

但如果你需要修改某个开源组件的业务逻辑（如添加自定义字段、修改业务规则），就需要把组件的完整源码 clone 到本地。

### 8.2 获取单个组件源码

```bash
# 安装组件 + clone 源码
brickkit add people/basic@1.0.0 --repo
```

clone 下来的源码存放在 `components/<scope>/<name>/` 目录下，是一个完整的 Git 仓库（含 `.git` 目录）。

### 8.3 获取所有依赖组件源码

```bash
# 安装组件 + clone 所有递归依赖的源码
brickkit add erp/backend@1.0.0 --repo-all
```

闭源组件没有 Git 仓库，会被跳过并输出提示。

### 8.4 已安装的组件补充 clone 源码

如果组件已经在 brickkit.yaml 中了，可以再次 add 加 `--repo`：

```bash
# 组件已存在，只执行 clone（不重复写入 brickkit.yaml）
brickkit add people/basic@1.0.0 --repo
```

### 8.5 工作区整理（brickkit sync）

当项目中有很多组件源码时，你日常开发可能只关注其中 2~3 个组件。`brickkit sync` 可以把不活跃的组件源码归档到 `components/.archived/` 目录，让你的文件管理器保持清爽；`--only` 还能只留下你点名的那几个及其依赖。

```bash
brickkit sync
```

输出示例：

```
$ brickkit sync
📂 工作区整理：
   ✅ components/people/basic          → 活跃
   ✅ components/department/tree       → 活跃
   📦 components/erp/backend           → components/.archived/erp/backend
      原因：显式禁用（enabled: false）
   📦 components/portal/user-frontend  → components/.archived/portal/user-frontend
      原因：显式禁用（enabled: false）
   📂 components/.archived/authorization/rbac → components/authorization/rbac
      原因：恢复启用
✅ 工作区整理完成（3 个活跃，2 个归档，1 个激活）
```

核心规则：

| 规则 | 说明 |
| --- | --- |
| 判断依据 | 与 `brickkit up` 同一套判定：会启动的组件保留在活跃目录，不会启动的归档 |
| 双向操作 | 归档 + 激活。该归档的归档，该激活的移回来 |
| 不集成在 `brickkit up` 中 | 纯独立命令。用户忘记执行就自己发现、自己处理 |
| 不需要 `--dry-run` | 直接执行，一步到位。搞错了再执行一次就回来了 |
| `local: true` 组件一视同仁 | 不特殊处理。`local: true` 的组件不启动时同样会被归档 |
| 只操作有源码的组件 | 只操作 `components/` 目录下存在的组件源码。没有 clone 过源码的组件不受影响 |

归档判断逻辑：

| 启停判定结果 | `brickkit sync` 行为 |
| --- | --- |
| 会启动的组件 | 保留在 `components/`（如果在归档目录中，移回来） |
| 显式关闭（`enabled: false`） | 移到 `components/.archived/` |
| 未被 `--only` 选中 | 移到 `components/.archived/` |

`brickkit sync` 与 `brickkit up` 的关系：

| 维度 | brickkit up | brickkit sync |
| --- | --- | --- |
| 职责 | 生成部署文件 + 启动容器 | 整理源码目录 |
| 启停判定 | ✅ 使用 | ✅ 使用（同一套逻辑） |
| 影响运行时 | ✅ 启动/停止容器 | ❌ 不影响运行中的容器 |
| 影响源码目录 | ❌ 不移动源码 | ✅ 移动源码 |
| 集成关系 | 不自动执行 sync | 不自动执行 up |

### 8.6 工作区目录结构

```
components/
 ├── people/
 │   └── basic/              ← 活跃组件源码
 │       ├── .git/
 │       ├── component.yaml
 │       └── app.py
 ├── department/
 │   └── tree/               ← 活跃组件源码
 │       ├── .git/
 │       ├── component.yaml
 │       └── main.go
 └── .archived/              ← 归档目录（隐藏）
     ├── erp/
     │   └── backend/        ← 被归档的组件（完整 Git 仓库）
     └── portal/
         └── user-frontend/
```

关键规则：

- 每个组件是独立的 Git 仓库（有自己的 `.git` 目录）
- 一个组件 ID 在 `components/` 下只能有一个源码目录
- `components/` 目录不提交到项目 Git 仓库（见 `.gitignore` 建议）
- `brickkit sync` 是双向的：该归档的归档，该激活的移回来
- 归档目录以 `.` 开头，文件管理器默认隐藏

### 8.7 `brickkit remove` 与源码目录

执行 `brickkit remove` 时，CLI 会自动删除对应的源码目录（如果存在）：

```
$ brickkit remove people/basic@1.0.0
✅ 已移除 people/basic@1.0.0
   🗑️ 已删除源码目录 components/people/basic/
   🗑️ 已清理 Manifest 缓存
   🗑️ 已清理 artifacts 缓存
```

源码此前已被 `brickkit sync` 归档时，删的是归档目录里的那一份：

```
$ brickkit remove people/basic@1.0.0
✅ 已移除 people/basic@1.0.0
   🗑️ 已删除归档源码目录 components/.archived/people/basic
   🗑️ 已清理 Manifest 缓存
   🗑️ 已清理 artifacts 缓存
```

归档目录必须一起清：`brickkit sync` 只整理 `brickkit.yaml` 里还声明着的组件，
组件被 remove 之后它就再也不认识那份源码了，留着就是永远没人回收的孤儿。

**remove 就是彻底移除，不留痕迹。** 如果你有未提交的修改，应该在 remove 之前先 commit + push。

## 9. 修改开源组件源码后如何上传

当你通过 `--repo` clone 了组件源码并修改后，需要把修改推送回 Git 仓库。根据你的权限情况，有两种方式：

### 9.1 情况一：你有 push 权限（如公司内部仓库）

```bash
cd components/people/basic
git checkout -b feature/my-change
# 修改代码...
git add .
git commit -m "feat: 新增自定义字段"
git push origin feature/my-change
```

### 9.2 情况二：你没有 push 权限（如公共开源仓库）

先在 GitHub/GitLab 上 fork 仓库（浏览器操作），然后：

**方式 A：替换 remote（简单直接）**

适合"我就是要改这个组件，不关心上游了"的场景。

```bash
cd components/people/basic
# 删除原来的 remote
git remote remove origin
# 添加你的 fork 为新的 origin
git remote add origin https://github.com/yourname/people-basic.git
# 正常操作
git checkout -b feature/my-change
git add .
git commit -m "feat: 新增自定义字段"
git push origin feature/my-change
```

**方式 B：保留原 remote，添加新 remote（适合需要跟踪上游更新）**

适合"我想基于上游持续开发，定期同步上游更新"的场景。

```bash
cd components/people/basic
# 保留原 origin（用于拉取上游更新）
# 添加你的 fork 为新 remote
git remote add myfork https://github.com/yourname/people-basic.git
# 正常操作
git checkout -b feature/my-change
git add .
git commit -m "feat: 新增自定义字段"
git push myfork feature/my-change

# 如果需要同步上游更新
git fetch origin
git merge origin/main
```

### 9.3 修改后重新发布

如果你修改了组件源码并希望发布新版本：

1. 更新 `component.yaml` 中的版本号
2. 构建新镜像
3. 执行 `brickkit publish`

```bash
brickkit publish --path ./components/people/basic --visibility public
```

## 11. 本地调试模式

### 11.1 场景

你需要在 IDE 中用 Debugger 断点调试组件，但组件又需要被 Docker 网络中的其他组件访问。

### 11.2 配置 local: true

在 brickkit.yaml 中标记：

```yaml
components:
  - id: people/basic
    version: 1.0.0
    local: true       # 本地调试模式
    localPort: 8081   # 本地监听端口
  - id: erp/backend
    version: 1.0.0
    local: false      # 正常 Docker 模式
```

### 11.3 CLI 行为

- `local: true` 的组件不生成容器
- CLI 在其他容器的 `extra_hosts` 中将该组件的服务名映射到宿主机
- 环境变量中的端口改为 `localPort`
- CLI 为 local 组件的依赖组件自动映射端口到宿主机
- CLI 生成 `.brickkit/generated/local-debug.<版本化服务名>.env` 文件

### 11.4 调试流程

```bash
# 1. 启动 Docker 中的其他组件（不启动 people/basic）
brickkit up

# 2. 在 IDE 中启动 people/basic（源码模式，监听 8081）
#    加载 .brickkit/generated/local-debug.people-basic-1-0-0.env 中的环境变量
#    VS Code / IntelliJ / GoLand 等，debugger 直接 attach

# 3. erp/backend 容器访问 http://people-basic-1-0-0:8081
#    → 实际路由到宿主机 8081 端口
#    → IDE debugger 命中断点 ✅

# 4. people/basic 访问依赖组件（如 department-tree）
#    → 通过 localhost:18080（CLI 自动映射的端口）
#    → 访问 Docker 容器内的依赖组件 ✅
```

### 11.5 本地调试限制

| 限制 | 说明 |
| --- | --- |
| 闭源组件不支持 | 没有源码，无法在 IDE 中运行 |
| 需要 Docker 20.10+ | `host-gateway` 需要 Docker 20.10+ |

## 12. 更新组件

### 12.1 更新步骤

**方式1：手动修改 brickkit.yaml**

```yaml
# 修改前
components:
  - id: people/basic
    version: 1.0.0

# 修改后
components:
  - id: people/basic
    version: 1.1.0    # ← 改这里
```

```bash
brickkit up
```

**方式2：重新 add（默认共存）**

```bash
brickkit add people/basic@1.1.0
```

### 12.2 破坏性变更（Major）更新

当更新涉及 Major 版本（如 1.0.0 → 2.0.0）且包含破坏性变更时，必须遵循 002 组件规范第 3.7 节"破坏性变更（Major）协同守则"：

| # | 守则 | 责任方 |
| --- | --- | --- |
| 1 | Changelog 中必须强提示破坏性变更 | 组件发布者 |
| 2 | 调用方团队必须协调同步升级 | 调用方团队 |
| 3 | 无法按时更新的部门，多版本共存作为物理缓冲期 | 项目管理员 |
| 4 | 平台不保证多版本共存时的数据库结构兼容 | —（平台不介入） |

### 12.3 升级时 CLI 自动执行的检查

执行 `brickkit up` 时，CLI 自动检查以下内容：

| # | 检查项 | 失败时行为 |
| --- | --- | --- |
| 1 | 新版本 Manifest 可获取 | ❌ 报错阻断 |
| 2 | 新版本的强依赖可满足 | ❌ 报错阻断 |
| 3 | 新版本的资源依赖已绑定 | ❌ 报错阻断 |
| 4 | 新版本的弱依赖可获取 | ⚠️ 警告但继续 |
| 5 | 新版本无循环依赖 | ❌ 报错阻断 |

**CLI 不检查 API 兼容性、数据库结构兼容性、config 值类型。** 这些是组件开发者和使用者的责任。

### 12.4 升级后调用方需要做什么

**核心规则：升级被依赖组件后，调用方不会自动切换。**

| 场景 | 调用方需要做什么 |
| --- | --- |
| 被依赖组件发布了 Minor/Patch 更新（向后兼容） | 调用方无需修改。但如果调用方想使用新功能，需要修改自己的 Manifest 中的依赖版本号，重新发布 |
| 被依赖组件发布了 Major 更新（破坏性变更） | 调用方**必须**修改自己的 Manifest 中的依赖版本号，适配新 API，重新发布。遵循 002 §3.7"破坏性变更（Major）协同守则" |
| 调用方暂时不想升级 | 保持 Manifest 中的精确版本不变。多版本共存作为物理缓冲 |

**示例：**

```yaml
# 调用方 erp/backend 的 component.yaml
dependencies:
  components:
    - people/basic@1.0.0    # ← 精确版本，不会自动变为 2.0.0
```

即使 `people/basic` 发布了 2.0.0，`erp/backend` 仍然调用 `people-basic-1-0-0`。只有当 `erp/backend` 的开发者主动将依赖改为 `people/basic@2.0.0` 并发布新版本时，才会切换。

### 12.5 升级时 configSchema 变更的处理

| 变更类型 | 你需要做什么 |
| --- | --- |
| 新版本新增了配置项 | 无需操作。使用 configSchema 中的默认值。如需覆盖，在 brickkit.yaml 的 config 中添加 |
| 新版本删除了配置项 | 无需操作。brickkit.yaml 中对应的 config 覆盖值会被 CLI 静默忽略 |
| 新版本修改了配置项默认值 | 如果你之前没有覆盖，新默认值生效。如果你之前覆盖了，你的覆盖值继续生效 |

### 12.6 升级时 artifacts 的更新

| 升级方式 | artifacts 行为 |
| --- | --- |
| 修改 brickkit.yaml 版本号 → `brickkit up` | CLI 自动下载新版本的 artifacts 到 `.brickkit/artifacts/<新版本化服务名>/` |
| `brickkit add X@新版本` | CLI 自动下载新版本的 artifacts（与首次安装一致） |

**注意：** 旧版本的 artifacts 不会被删除。如果你需要基于新版本的 API 契约开发调用代码，请读取新版本目录中的文件：

```bash
# 查看新版本的 API 契约
ls .brickkit/artifacts/people-basic-1-1-0/api-contract/
```

### 12.7 升级注意事项

| # | 注意事项 | 说明 |
| --- | --- | --- |
| 1 | 升级前查看 Changelog | 了解新版本改了什么，是否有破坏性变更 |
| 2 | 升级前备份数据 | 虽然 `brickkit down` 不删除 volume，但迁移可能有风险 |
| 3 | 升级后检查调用方 | 如果有其他组件依赖被升级的组件，确认它们是否需要同步更新 Manifest |
| 4 | 迁移失败时查看日志 | `docker compose logs <服务名>-migration` 或 `kubectl logs job/<服务名>-migration` |
| 5 | 回滚时注意数据库 | 数据库迁移不可自动回滚。如果新版本执行了迁移，回滚到旧版本时数据库结构已变更 |
| 6 | 使用 `--dry-run` 预览 | `brickkit up --dry-run` 可以在不启动的情况下查看升级变更摘要 |

## 13. 数据库迁移

### 13.1 迁移触发条件

当组件 Manifest 中声明了 `migration` 字段时，CLI 在启动前自动执行迁移。

### 13.2 迁移失败处理

- 迁移成功（exit 0）→ 主服务正常启动
- 迁移失败（exit 非 0）→ 主服务不启动
- 不设超时限制（用户自己看日志判断）
- 不设重试（数据库 DDL 操作不应盲目重试）
- K8s 环境下，修复迁移脚本后重新执行 `brickkit up`，CLI 会自动清理旧的失败 Job 并重新执行迁移

### 13.3 查看迁移日志

```bash
# Docker 环境
docker compose -p brickkit-my-erp -f .brickkit/generated/docker-compose.yaml logs people-basic-1-1-0-migration

# K8s 环境
kubectl logs job/people-basic-1-1-0-migration -n brickkit-my-project
```

## 16. 批量操作

### 16.1 批量添加

安装连接组件时，CLI 自动批量拉取所有依赖。不需要手动逐个添加。

```bash
# 一条命令，自动拉取所有依赖 + 下载所有 artifacts
brickkit add erp/backend@1.0.0
```

### 16.2 批量启动/停止

```bash
# 一键启动所有组件
brickkit up

# 一键停止所有组件（不删除 volume）
brickkit down
```

### 16.3 只启动指定组件

```bash
# 只启动指定组件（及其依赖）
brickkit up --only people/basic,department/tree

# 只启动指定版本
brickkit up --only people/basic@1.0.0
```

### 16.4 禁用组件（不启动）

`enabled` 只回答一个问题：这个组件跑不跑。

| 写法 | 行为 |
| --- | --- |
| 不写 `enabled` 字段 | ✅ 启动 |
| `enabled: true` | ✅ 启动（与不写等价） |
| `enabled: false` | ❌ 不启动 |

关掉一个组件只有它自己不跑。如果有正在启动的组件**强依赖**它，`up` 会报错并点名依赖方——
要一起关就给它们也写上 `enabled: false`（003 §4.3）。

## 17. 排查安装问题

### 17.1 安装失败：强依赖缺失

```
❌ 添加失败：强依赖缺失
   组件：erp/backend@1.0.0
   缺失依赖：authorization/rbac@1.0.0
   原因：该组件在所有安装源中均未找到
```

**解决：** 检查安装源配置、确认组件是否在市场存在、确认版本号是否为 stable。

### 17.2 启动失败：资源依赖未满足

```
❌ 错误：资源依赖未满足
   people/basic@1.0.0：需要 kind: database、engine: postgresql（brickkit.yaml 的 resources 中未声明）
```

**解决：** 在 brickkit.yaml 的 resources 中添加资源并绑定（`kind` + `engine` 要与
组件声明的完全一致，`kind` 是封闭枚举，见 006 §2.1）。暂时不想跑这个组件的话，
给它写 `enabled: false`——不启动的组件不参与这条检查。

### 17.3 安装失败：健康检查超时

```
❌ 启动失败：健康检查超时
   组件：people-basic-1-0-0
   原因：120 秒内未通过健康检查
```

**解决：** 查看组件日志、检查环境变量、检查数据库连接、检查端口是否冲突。

### 17.4 clone 失败：闭源组件

```
❌ clone 失败：该组件为闭源组件
   组件：authorization/rbac@1.0.0
   来源类型：registry（闭源）
   原因：闭源组件没有 Git 仓库，无法 clone 源码
   💡 你仍然可以正常安装和使用该组件（不含 --repo）：
      brickkit add authorization/rbac@1.0.0
```

### 17.5 clone 失败：目录已存在

```
❌ clone 失败：目录已存在
   组件：people/basic@1.0.0
   目录：components/people/basic/
   原因：该目录已存在，可能包含你正在开发的组件源码
   建议：
   1. 如果是误操作，请先删除或重命名该目录
   2. 如果已有源码，无需再次 clone
```

### 17.6 镜像拉取失败（未授权）

```
❌ 镜像拉取失败（未授权）
   组件：people/basic@1.0.0
   镜像：registry.brickkit.io/people-basic:1.0.0
   错误：unauthorized: authentication required
```

**解决：**

```bash
docker login registry.brickkit.io
brickkit up
```

### 17.7 --only 指定了 enabled: false 的组件

```
❌ 无法启动指定的组件：
   组件 people/basic@1.0.0 在 brickkit.yaml 中被显式禁用（enabled: false）。
   如需启动，请先在 brickkit.yaml 中移除 enabled: false 或将其设为 enabled: true。
```

## 18. 安装约束总结

1. 安装前必须确认 CLI 已安装。
2. 安装前必须确认 Docker 可用。
3. 安装前必须初始化项目（`brickkit init`）。
4. 安装时自动解析和拉取依赖（精确版本）。
5. 安装时自动下载所有 artifacts（API 契约、SDK、文档等）到 `.brickkit/artifacts/`。CLI 不解析文件内容，只负责下载和存储。
6. `brickkit add` 自动添加的组件不写 `enabled` 字段（不写就是启动）。
7. 强依赖缺失时报错阻断；弱依赖缺失时警告但继续（完全不注入该环境变量）。
8. 弱依赖降级完全是组件自己的责任，必须使用 `os.environ.get()` 安全读取。
9. 多版本默认共存。brickkit.yaml 中有几个版本就启动几个容器，无需额外参数。多版本共存只是物理缓冲，不保证数据层兼容。
10. 资源必须在 brickkit.yaml 中声明并绑定。
11. 组件配置通过 `config` 字段覆盖 configSchema 默认值。CLI 不校验 config 值的类型。
12. CLI 在生成部署文件时注入环境变量（值带版本号）。
13. 数据库迁移由 CLI 在启动前自动执行（K8s Job / Docker 一次性 service）。
14. K8s 环境下，CLI 在执行迁移前自动清理同名旧 Job。
15. 迁移失败 = 主服务不启动。
16. 安装后必须通过健康检查（compose healthcheck / K8s probe）。
17. 更新前必须检查兼容性。
18. 更新失败必须可回滚（修改版本号 + `brickkit up`）。
19. 破坏性变更（Major）是组织协调问题，调用方必须协调同步升级。此守则同样适用于 API 契约文件的破坏性变更。
20. 卸载前必须检查强依赖方。
21. 卸载默认不删除数据。`brickkit down` 不删除 volume。
22. 多版本 remove 时必须指定版本 `brickkit remove <id>@<version>`。
23. 生产环境强制签名校验。
24. 本地调试使用 `local: true` + IDE debugger + 加载 `local-debug.<版本化服务名>.env`。
25. 启动顺序由依赖关系决定（拓扑排序）。
26. 停止顺序与启动顺序相反。
27. `enabled` 只有开关两种结果：不写与 `enabled: true` 都启动，只有 `enabled: false` 不启动。
28. `brickkit up --only` 支持 `@版本` 写法；遇到 `enabled: false` 的组件报错阻断。
29. `expose: true` 在 Docker 中映射端口到宿主机（可通过 `exposePort` 自定义）；在 K8s 中生成 Ingress（基于 `hostname` 域名路由）。
30. 所有组件都是 container（包括前端组件，使用 nginx 等 Web Server）。
31. 镜像拉取认证由用户手动 `docker login` 处理，CLI 检测登录状态并提示。
32. 市场访问认证通过 `brickkit login`（Token 存 `.brickkit/credentials`）或 `authToken` 处理。
33. 信任模型：安装组件即代表用户信任发布者，平台只做 `blocked` 下架。
34. 渐进式拼装：安装底层组件 → 获取契约 → 开发连接组件 → 发布 → 再安装。像搭积木一样，一块一块地加。
35. `brickkit add --repo` 只 clone 指定组件的 Git 仓库。闭源组件报错阻断。目标目录已存在报错阻断。
36. `brickkit add --repo-all` clone 所有递归依赖中开源组件的 Git 仓库。闭源组件跳过并提示。
37. `brickkit sync` 双向归档/激活组件源码。纯独立命令，不集成在 `brickkit up` 中。
38. `brickkit remove` 自动删除源码目录。
39. 一个组件 ID 在 `components/` 下只能有一个源码目录。
40. `components/` 目录不提交到项目 Git 仓库。
41. Git 权限（fork、remote、push）完全由用户自己处理，CLI 不管理。
42. 升级时 CLI 检查依赖兼容性（见 002 §7.7），但不检查 API 兼容性。
43. 升级被依赖组件后，调用方不会自动切换（精确版本，见 002 §7.8）。调用方需显式修改 Manifest 并重新发布。
44. 升级时 configSchema 变更由 CLI 静默处理（见 002 §7.9）。新增用默认值，删除静默忽略。
45. 升级时 artifacts 自动下载新版本，旧版本保留，按版本化服务名独立存储（见 002 §7.10）。

## 20. 总结

BrickKit 组件安装与拼装的核心可以用一句话概括：

> `brickkit add` 拉组件、下契约，`brickkit up` 一键启动。想改源码就加 `--repo`，想整理工作区就 `brickkit sync`。CLI 自动装好所有依赖，绑好资源，注入配置，执行迁移，按顺序启动。拼装就是这么简单。

| 维度               | 说明                                                                |
| ---------------- | ----------------------------------------------------------------- |
| 安装               | `brickkit add` + `brickkit up`                                    |
| 获取源码             | `brickkit add --repo`（单个）/ `--repo-all`（全部依赖）                     |
| 工作区管理            | `brickkit sync`（双向归档/激活，与 `up` 共用同一套启停判定）                          |
| 修改源码后上传          | CLI 不管 Git 权限，教程教用户（fork + remote / 删除原 remote + 添加自己的）           |
| artifacts        | 安装时自动下载产物文件到 `.brickkit/artifacts/`。CLI 不解析文件内容                   |
| 拼装               | 安装连接组件（自动拉取所有依赖）+ 安装前端组件                                          |
| 渐进式拼装            | 安装底层组件 → 获取契约 → 开发连接组件 → 发布 → 再安装                                 |
| 资源绑定             | brickkit.yaml 中静态声明 bindings                                      |
| 配置覆盖             | brickkit.yaml `config` 字段覆盖 configSchema 默认值。CLI 不校验 config 值类型   |
| 数据库迁移            | CLI 自动执行（K8s Job / Docker 一次性 service）；K8s 执行前自动清理旧 Job           |
| 本地调试             | `local: true` + IDE debugger + 加载 `local-debug.<版本化服务名>.env`      |
| 更新               | 修改版本号 + `brickkit up`                                             |
| 升级检查             | CLI 检查依赖可满足、资源已绑定、无循环依赖。不检查 API 兼容性                               |
| 升级后调用方           | 调用方 Manifest 中精确版本不变，不会自动切换。需显式修改并重新发布                            |
| 升级时 configSchema | 新增用默认值，删除静默忽略，修改类型不校验                                             |
| 升级时 artifacts    | 自动下载新版本，旧版本保留，按版本化服务名独立存储                                         |
| 破坏性变更            | Major 版本必须协同升级（组织协调问题）                                            |
| 回滚               | 改回旧版本号 + `brickkit up`（或 `git checkout brickkit.yaml`）             |
| 卸载               | `brickkit remove`（检查强依赖方 + 自动删除源码目录）；`brickkit down` 不删除 volume   |
| 多版本共存            | 默认行为。物理缓冲，不保证数据层兼容                                                |
| 多版本 remove       | 必须指定版本 `brickkit remove <id>@<version>`                           |
| 查看顺序             | `brickkit up --dry-run`                                                  |
| 查看状态             | `brickkit status`                                                 |
| 弱依赖              | 缺失时完全不注入环境变量，必须用 `os.environ.get()` 读取                            |
| 镜像认证             | 用户手动 `docker login`，CLI 检测并提示                                     |
| 市场认证             | `brickkit login` → `.brickkit/credentials`（优先于 `authToken`）       |
| 信任模型             | 安装即信任，平台只做 `blocked` 下架                                           |
| Git 权限           | CLI 不管理 Git 权限。clone 后的 fork、remote、push 操作完全由用户自己处理              |
| 一个组件一个仓库         | 每个组件对应一个独立的 Git 仓库。不支持 monorepo                                   |
| 组件源码目录           | `components/` 存放活跃源码，`components/.archived/` 存放归档源码。不提交到项目 Git 仓库 |
