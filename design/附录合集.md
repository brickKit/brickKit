## 附录 A：术语表

### A.1 平台核心概念

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| BrickKit CLI | BrickKit CLI | BrickKit 的核心工具。本地命令行工具，负责拉取组件、解析依赖、下载产物文件、生成部署文件、执行迁移、调用底层引擎。无常驻进程。 |
| 组件市场 | BrickKit Market | 独立的公共组件发布和发现平台。管理 Manifest、版本、权限、签名和产物存储。 |
| 项目配置 | brickkit.yaml | 项目级的声明式配置文件。描述项目包含哪些组件、资源绑定、配置覆盖、部署目标等。 |
| 安装源 | Source | CLI 获取组件的入口。可以是远程市场（market）、Git 仓库（git）或本地目录（local）。 |
| 部署目标 | Deploy Target | CLI 生成部署文件的格式。支持 `docker`（生成 docker-compose.yaml）和 `k8s`（生成 K8s YAML）。 |
| 版本化服务名 | Versioned Service Name | 带精确版本号的服务 DNS 名（如 `people-basic-1-0-0`），确保多版本共存和调用明确。 |
| 登录凭据 | Credentials | `brickkit login` 成功后生成的 Token 文件，存储在 `.brickkit/credentials`，用于访问 private 组件和发布组件。 |

### A.2 组件与版本

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 组件 | Component | BrickKit 中最基本的安装和运行单元。所有组件都是 container。 |
| 强依赖 | Required Dependency | 组件运行必须的依赖。缺失时 CLI 报错并阻断启动。 |
| 弱依赖 | Optional Dependency | 组件的增强功能依赖（`optional: true`）。缺失时 CLI 警告但继续启动，**完全不注入该环境变量**，降级由组件自己负责。 |
| Manifest | component.yaml | 组件的自我描述文件，定义元信息、精确版本依赖、部署方式、迁移命令和健康检查。 |
| 精确版本 | Exact Version | 组件版本格式，遵循 `major.minor.patch`，依赖声明不使用 `^` 或 `~` 范围约束。 |
| 数据库迁移 | Migration | 组件声明 `migration.command`，CLI 在部署前自动执行（K8s Job / Docker 一次性 service）。 |
| 破坏性变更协同守则 | Major Breaking Change Protocol | 当组件发布 Major 版本且包含破坏性操作（删字段/改表名/删 API）时，必须在 Changelog 强提示，调用方团队协调同步升级，平台不兜底数据层兼容。 |
| 额外端口 | Extra Ports | 组件除主端口外需要暴露的其他端口（如 gRPC 端口）。通过 `deployment.extraPorts` 声明，Docker 环境无需额外处理，K8s 环境 CLI 在 Service 中暴露。 |

### A.3 产物与 API 契约

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 产物/附件 | Artifacts | 组件附带的文件（API 契约、SDK、文档等）。通过 Manifest 的 `artifacts` 字段声明，发布时上传到市场，安装时由 CLI 自动下载。`type` 和 `format` 是自由字符串，不限枚举。市场不理解文件内容，只负责存储和分发。 |
| API 契约 | API Contract | 组件的 API 定义文件（proto / OpenAPI / GraphQL schema 等）。代码可以闭源，但 API 契约必须公开。闭源组件如果提供 API，必须在 artifacts 中声明至少一个 `type: api-contract` 的产物。 |
| 产物缓存 | Artifacts Cache | CLI 安装组件时下载的产物文件，存储在项目目录的 `.brickkit/artifacts/` 中。按 `<版本化服务名>/<type>/<文件路径>` 组织。 |
| 渐进式拼装 | Progressive Assembly | BrickKit 的开发模式：安装底层组件 → 获取 API 契约 → 基于契约开发连接组件 → 发布 → 再安装。像搭积木一样，一块一块地加。 |

### A.4 部署与运行

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 本地调试模式 | Local Debug Mode | 在 `brickkit.yaml` 中标记 `local: true`，CLI 不生成该组件容器，而是通过 `extra_hosts` 将其 DNS 映射到宿主机，供 IDE Debugger 使用。CLI 同时为 local 组件的依赖映射宿主机端口，并生成 `local-debug.<版本化服务名>.env` 供 IDE 加载。 |
| local-debug.env | local-debug.env | CLI 在存在 `local: true` 组件时自动生成的环境变量文件，存储在 `.brickkit/generated/` 中。文件名使用 版本化服务名（如 `local-debug.people-basic-1-0-0.env`），确保多版本共存时不冲突。包含组件自身的环境变量（依赖地址指向 `localhost:<映射端口>`），供 IDE 加载使用。 |
| 环境变量注入 | Env Injection | CLI 在生成部署文件时，将依赖地址（值带版本号）、资源连接和配置项（含 config 覆盖）写入容器的环境变量。 |
| 拓扑排序 | Topological Sort | CLI 根据组件间的依赖关系，计算出正确的启动顺序（被依赖方先启动）。 |
| 配置覆盖 | Config Override | 使用者在 brickkit.yaml 的 `config` 字段中提供值，覆盖 Manifest `configSchema` 中的默认值。**CLI 不校验 config 值的类型**。 |
| 资源配额 | Resource Quota | 组件在 Manifest 的 `deployment.resources` 中声明推荐的 CPU/内存限制，CLI 透传给 K8s/Docker。brickkit.yaml 可覆盖。 |

### A.5 资源与安全

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 基础资源 | Resource | 组件运行依赖的外部系统（如 PostgreSQL、Redis）。由运维部署，在 `brickkit.yaml` 中声明和绑定。 |
| 资源绑定 | Resource Binding | 在 `brickkit.yaml` 中将组件声明的资源依赖关联到具体的资源实例。 |
| 密钥引用 | Secret Reference | 在 `brickkit.yaml` 中使用 `${ENV_VAR}` 引用密码，实际值存储在 `.env` 文件（Docker）或 K8s Secret 中。 |
| 信任模型 | Trust Model | BrickKit 对第三方组件采用 **"安装即信任"** 原则。平台不做前置代码安全审查，只做最后的 `blocked` 下架。 |
| 保留变量 | Reserved Variables | 平台注入的环境变量（如 `COMPONENT_ID`、`*_ENDPOINT`、`DATABASE_*`），configSchema 配置项名称不得与之冲突。 |

### A.6 组件源码管理

| 术语       | 英文                     | 定义                                                                                                             |
| -------- | ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| 源码 clone | Source Clone           | 通过 `brickkit add --repo` 或 `--repo-all` 将开源组件的完整 Git 仓库 clone 到本地 `components/` 目录。仅对开源组件（`sourceType: git`）有效 |
| 工作区整理    | Workspace Sync         | `brickkit sync` 命令。根据级联计算结果，双向归档/激活组件源码。不启动的组件源码移到 `components/.archived/`，需要启动的移回 `components/`               |
| 归档目录     | Archived Directory     | `components/.archived/`。`brickkit sync` 将不启动的组件源码自动移入此目录。以 `.` 开头，文件管理器默认隐藏。归档的组件仍是完整的 Git 仓库（含 `.git`），可随时移回  |
| 一个组件一个仓库 | One Component One Repo | BrickKit 的基本假设。每个组件对应一个独立的 Git 仓库，不支持 monorepo 中拆分子目录。同一业务的多部分内容属于同一组件，一起移动、一起上传、一起发布                          |

## 附录 B：Manifest 完整参考（component.yaml）

### B.1 完整字段结构

```yaml
apiVersion: brickkit/v1
kind: Component

metadata:
  id: <scope>/<name>             # 必须，组件唯一标识
  name: <显示名称>                # 必须
  version: <major.minor.patch>   # 必须，精确版本
  description: <组件描述>         # 必须
  vendor: <发布者>                # 可选
  license: <许可证>               # 可选
  apiDocs: <API文档地址>          # 可选

tags:                            # 可选，用于市场搜索
  - <标签1>
  - <标签2>

# ===== 组件附带的产物/附件（可选）=====
artifacts:
  - type: <产物类型>             # 必须，自由字符串（如 api-contract, api-docs, sdk）
    format: <具体格式>           # 可选，自由字符串（如 protobuf, openapi, python）
    description: <描述>          # 可选
    files:                       # 必须，文件路径列表（相对于组件仓库根目录）
      - <文件路径>

dependencies:                    # 可选
  components:
    - <componentId>@<精确版本>    # 强依赖
    - id: <componentId>@<精确版本>
      optional: true              # 弱依赖
  resources:
    - kind: <资源类型>            # 如 database, cache
      engine: <资源引擎>          # 如 postgresql, redis

configSchema:                    # 可选，声明自身配置项（可被 brickkit.yaml config 覆盖）
  type: object                   # ⚠️ 注意：这是"配置说明书"，CLI 不校验使用者填写的 config 值类型
  properties:                    # ⚠️ 注意：配置项名称不得与平台保留变量冲突（见附录 C.6）
    <配置项名>:
      type: <类型>
      default: <默认值>
      description: <说明>
  required:
    - <必填配置项>

deployment:                      # 必须
  type: container                # 固定为 container（包括前端组件）
  image: <镜像地址>               # 必须
  port: <端口号>                  # 必须，主端口（健康检查 + _ENDPOINT 环境变量）
  extraPorts:                    # 可选，额外端口列表（如 gRPC 端口）
    - name: <端口名称>            # 必须，用于环境变量命名和 K8s Service 端口名
      port: <端口号>              # 必须，容器内端口号
  resources:                     # 可选，组件开发者给出推荐的资源配额
    requests:
      cpu: <CPU请求>             # 如 "100m"
      memory: <内存请求>          # 如 "128Mi"
    limits:
      cpu: <CPU上限>             # 如 "500m"
      memory: <内存上限>          # 如 "512Mi"

migration:                       # 可选，数据库迁移
  command: ["<命令>", "<参数>"]   # 数组格式

healthCheck:                     # 必须
  type: <http | tcp | none>
  path: <健康检查路径>            # http 必填
  # ⚠️ 健康检查只检查本进程存活，禁止检查数据库、依赖组件或任何外部系统（见附录 I.4）

observability:                   # 可选
  metrics: <boolean>              # 是否暴露 /metrics
  tracing: <boolean>              # 是否支持分布式追踪

compatibility:                   # 可选
  minCliVersion: <最低CLI版本>    # 如 1.0.0
```

### B.2 依赖声明规则（核心）

- 必须使用精确版本：`department/tree@1.0.0`（✅），`department/tree@^1.0.0`（❌）。
- 弱依赖标记：使用 `optional: true`，缺失时 CLI 警告但不阻断启动，且完全不注入对应的环境变量。
- 前端组件也是 container：没有 `static` 类型，前端组件使用 nginx 等 Web Server 容器，声明 `port: 80`。
- 额外端口（extraPorts）：`extraPorts` 是可选字段，用于声明额外端口（如 gRPC）。Docker 环境无需额外处理（Docker Network 内所有端口天然可达）；K8s 环境 CLI 在 Service 中暴露额外端口。额外端口注入为 `{组件ID前缀}_{NAME大写}_ENDPOINT` 环境变量。

### B.3 资源配额规则（deployment.resources）

| 规则 | 说明 |
| --- | --- |
| 纯推荐值，非强制 | CLI 透传给 K8s/Docker，但不校验合理性 |
| brickkit.yaml 可覆盖 | 项目管理员可在 `components[].resources` 中覆盖组件推荐值 |
| 不填则使用 CLI 默认值 | CLI 生成时给一个保守默认值（如 100m/128Mi），避免完全无限制 |
| Docker 环境也生效 | Docker Compose 支持 `deploy.resources.limits`（Compose v3+） |
| 市场不校验具体数值 | 市场只校验 `resources` 字段的格式合法性 |

CLI 优先级链：`brickkit.yaml resources` > `component.yaml resources` > `CLI 默认值`

### B.4 健康检查禁令

⚠️ `/healthz` 只检查本进程存活，禁止检查任何外部依赖。

健康检查中禁止检查数据库、缓存、依赖组件或任何外部系统。违反此原则会导致生产环境雪崩。

详见附录 I.4。

### B.5 artifacts 规则

| 规则 | 说明 |
| --- | --- |
| type 是自由字符串 | 市场不校验 type 的值，不限枚举。今天是 `api-contract`，明天可以是 `asyncapi-spec`，后天可以是 `ml-model`。市场不理解文件内容，只负责存储和分发 |
| format 是自由字符串 | 同上，市场不校验 |
| 闭源组件必须提供 API 契约 | 如果组件提供 gRPC 或 HTTP API，闭源组件必须在 artifacts 中声明至少一个 `type: api-contract` 的产物。**代码可以闭源，但 API 契约不能闭源** |
| artifacts 跟随组件版本 | 每个组件版本有自己独立的 artifacts。v1.0.0 的 proto 和 v1.1.0 的 proto 独立存储，互不覆盖 |
| CLI 安装时自动下载 | `brickkit add` 时，CLI 自动下载所有 artifacts 到 `.brickkit/artifacts/` 目录 |
| 平台不解析文件内容 | CLI 和市场都不解析 artifacts 中的文件内容，只负责存储和分发 |
| API 契约不需要独立版本管理 | proto 文件跟随组件版本走，与数据库 migration 使用完全相同的兼容性逻辑。向后兼容的变更自然兼容，破坏性变更遵循 "破坏性变更协同守则" |

### B.6 artifacts 示例

**gRPC 双协议组件：**

```yaml
artifacts:
  - type: api-contract
    format: protobuf
    description: "gRPC API 契约文件"
    files:
      - proto/department/v1/department.proto
  - type: api-docs
    format: openapi
    description: "HTTP REST API 文档（grpc-gateway 自动生成）"
    files:
      - openapi.json
```

**Python HTTP 组件：**

```yaml
artifacts:
  - type: api-docs
    format: openapi
    description: "HTTP REST API 文档（FastAPI 自动生成）"
    files:
      - openapi.json
```

**带 SDK 的组件：**

```yaml
artifacts:
  - type: api-contract
    format: protobuf
    description: "gRPC API 契约文件"
    files:
      - proto/people/v1/people.proto
  - type: sdk
    format: python
    description: "Python 客户端 SDK"
    files:
      - sdk/people-basic-client-1.0.0.tar.gz
  - type: api-docs
    format: openapi
    description: "HTTP REST API 文档"
    files:
      - openapi.json
```

### B.7 extraPorts 规则

**extraPorts 字段定义：**

```yaml
deployment:
  type: container
  image: registry.brickkit.io/people-basic:1.0.0
  port: 8080              # 主端口（健康检查 + _ENDPOINT 环境变量）
  extraPorts:             # 可选，额外端口列表
    - name: grpc          # 端口名称（用于环境变量命名 + K8s Service 端口名）
      port: 9090          # 容器内端口号
```

| extraPorts 子字段 | 类型 | 必须 | 说明 |
| --- | --- | --- | --- |
| name | string | ✅ | 端口名称。用于环境变量命名（`{组件ID前缀}_{NAME大写}_ENDPOINT`）和 K8s Service 端口名 |
| port | integer | ✅ | 容器内端口号 |

**extraPorts 行为：**

| 环境 | CLI 行为 |
| --- | --- |
| Docker | 不需要额外处理。Docker Network 内容器的所有端口天然可达，compose 中不需要暴露额外端口 |
| K8s | Service 中增加额外端口映射 |
| 环境变量注入 | 额外端口注入为 `{组件ID前缀}_{NAME大写}_ENDPOINT`（见附录 C.2） |
| 健康检查 | 仍然使用主端口 `deployment.port`，不变 |
| 保留变量保护 | 额外端口的 `_ENDPOINT` 变量同样受 `*_ENDPOINT` 保留模式保护 |

**K8s Service 生成示例：**

```yaml
spec:
  ports:
    - name: http
      port: 8080
      targetPort: 8080
    - name: grpc          # ← 来自 extraPorts[0].name
      port: 9090          # ← 来自 extraPorts[0].port
      targetPort: 9090
  type: ClusterIP
```

## 附录 C：环境变量命名规范

### C.1 核心原则

CLI 在生成部署文件（docker-compose.yaml / K8s YAML）时，自动注入环境变量。组件代码只需读取环境变量，不硬编码任何地址。

### C.2 依赖组件地址变量

**主端口命名规则：`{组件ID前缀}_ENDPOINT`**

转换规则：`/` 和 `-` 替换为 `_`，全部大写。

| 依赖组件 ID | 环境变量名 | 注入的值（带版本号） |
| --- | --- | --- |
| department/tree | DEPARTMENT_TREE_ENDPOINT | http://department-tree-1-0-0:8080 |
| people/basic | PEOPLE_BASIC_ENDPOINT | http://people-basic-1-2-0:8080 |
| infra/redis-event-bus | INFRA_REDIS_EVENT_BUS_ENDPOINT | http://infra-redis-event-bus-1-0-0:8080 |

**额外端口命名规则：`{组件ID前缀}_{NAME大写}_ENDPOINT`**

当依赖组件声明了 `deployment.extraPorts` 时，CLI 为每个额外端口注入独立的环境变量。

| 依赖组件 ID | extraPorts | 环境变量名 | 注入的值（带版本号） |
| --- | --- | --- | --- |
| people/basic | [{name: grpc, port: 9090}] | PEOPLE_BASIC_GRPC_ENDPOINT | http://people-basic-1-2-0:9090 |

**关键规则：**

- 主端口的环境变量保持不变：`{组件ID前缀}_ENDPOINT`（如 `PEOPLE_BASIC_ENDPOINT`）
- 额外端口的环境变量使用：`{组件ID前缀}_{NAME大写}_ENDPOINT`（如 `PEOPLE_BASIC_GRPC_ENDPOINT`）
- 额外端口的 ENDPOINT 变量同样受 `*_ENDPOINT` 保留模式保护
- 环境变量名不带版本号，环境变量值带版本号
- 如果弱依赖缺失，该组件的主端口和额外端口环境变量都完全不存在（CLI 不注入空字符串）。组件必须使用安全读取方式（如 Python 的 `os.environ.get()`），绝不能使用方括号 `os.environ["X"]` 访问，否则会抛出 `KeyError` 导致组件崩溃

### C.3 平台通用变量

| 环境变量 | 说明 | 示例值 |
| --- | --- | --- |
| COMPONENT_ID | 组件 ID | people/basic |
| COMPONENT_VERSION | 组件版本 | 1.2.0 |

### C.4 资源连接变量

| 资源类型 | 环境变量 |
| --- | --- |
| 数据库 | DATABASE_HOST, DATABASE_PORT, DATABASE_NAME, DATABASE_USER, DATABASE_PASSWORD |
| 缓存 | REDIS_HOST, REDIS_PORT, REDIS_PASSWORD |

### C.5 自身配置变量（含 config 覆盖）

`configSchema` 中声明的驼峰命名配置项，转为大写下划线格式注入。如果使用者在 `brickkit.yaml` 的 `config` 字段中提供了值，则注入覆盖后的值。

- `defaultPageSize` → `DEFAULT_PAGE_SIZE`
- `enableAudit` → `ENABLE_AUDIT`

### C.6 保留变量保护

以下环境变量由平台注入，configSchema 中的配置项名称不得与之冲突（转大写后匹配）：

| 保留模式 | 说明 | 匹配方式 |
| --- | --- | --- |
| COMPONENT_ID | 平台通用变量 | 精确匹配 |
| COMPONENT_VERSION | 平台通用变量 | 精确匹配 |
| *_ENDPOINT | 依赖组件地址（含额外端口） | 后缀匹配 |
| DATABASE_* | 数据库资源连接 | 前缀匹配 |
| REDIS_* | 缓存资源连接 | 前缀匹配 |
| MQ_* | 消息队列资源连接 | 前缀匹配 |
| STORAGE_* | 对象存储资源连接 | 前缀匹配 |
| SEARCH_* | 搜索引擎资源连接 | 前缀匹配 |
| SMTP_* | 邮件服务资源连接 | 前缀匹配 |
| {envPrefix}_* | 多资源前缀（如 `PRIMARY_`、`ARCHIVE_`） | 前缀匹配 |

**冲突处理（两层防御）：**

| 层次 | 时机 | 行为 |
| --- | --- | --- |
| 市场发布时校验 | 源头防御 | configSchema 配置项名称与保留变量冲突时，市场拒绝发布 |
| CLI 注入时检测 | 运行时防御 | config 覆盖的环境变量与保留变量冲突时，CLI 警告但跳过该配置项，平台注入的值优先 |

**冲突示例：**

- `departmentTreeEndpoint` → `DEPARTMENT_TREE_ENDPOINT` → 与 `*_ENDPOINT` 冲突 ❌
- `componentId` → `COMPONENT_ID` → 与 `COMPONENT_ID` 冲突 ❌
- `databaseHost` → `DATABASE_HOST` → 与 `DATABASE_*` 冲突 ❌
- `customPageSize` → `CUSTOM_PAGE_SIZE` → 无冲突 ✅

### D.1.1 enabled 字段三种状态

| 写法 | 含义 | 行为 |
| --- | --- | --- |
| `enabled: true`（显式写出） | **钉住**，必须运行 | 无论依赖链如何变化，该组件一定启动。不可被级联关闭 |
| 不写 `enabled` 字段 | **默认开启**，但可被级联关闭 | 如果没有启用中的组件需要它，CLI 自动跳过它 |
| `enabled: false` | **显式关闭** | 一定不启动 |

**级联逻辑：**

一个组件实际启动，当且仅当满足以下任一条件：它是显式钉住的（`enabled: true`）；它是根组件（即不被任何其他组件依赖的入口组件，通常是前端组件或连接组件）且未被显式关闭；至少有一个正在启动的组件强依赖它，且它未被显式关闭。

一个组件被级联跳过，当且仅当：它没有写 `enabled` 字段（不是钉住的）、它不是根组件、没有任何正在启动的组件依赖它。

`brickkit add` 自动添加的组件不写 `enabled` 字段。

### D.2 项目目录结构

CLI 会在项目根目录生成 `.brickkit/` 隐藏目录，组件源码存放在 `components/` 目录：

```
my-project/
├── brickkit.yaml                    # 项目配置（用户编辑）
├── .brickkit/
│   ├── credentials                  # brickkit login 生成的市场登录凭据
│   ├── manifests/                   # Manifest 缓存
│   ├── artifacts/                   # API 契约及其他产物缓存
│   │   ├── department-tree-1-0-0/
│   │   │   ├── api-contract/
│   │   │   │   └── proto/department/v1/department.proto
│   │   │   └── api-docs/
│   │   │       └── openapi.json
│   │   ├── people-basic-1-0-0/
│   │   │   └── api-docs/
│   │   │       └── openapi.json
│   │   └── authorization-rbac-1-0-0/
│   │       ├── api-contract/
│   │       │   └── proto/authorization/v1/rbac.proto
│   │       └── api-docs/
│   │           └── openapi.json
│   ├── backup/                      # 配置备份
│   └── generated/                   # CLI 生成的部署文件（勿手动编辑）
│       ├── docker-compose.yaml
│       ├── local-debug.people-basic-1-0-0.env    # 有 local: true 组件时生成（版本化服务名命名）
│       └── k8s/
├── components/                      # 组件源码目录
│   ├── people/
│   │   └── basic/                   # 活跃组件源码（自己开发的或通过 --repo clone 的）
│   │       ├── .git/                # 独立 Git 仓库
│   │       ├── component.yaml
│   │       └── app.py
│   ├── department/
│   │   └── tree/
│   │       ├── .git/
│   │       ├── component.yaml
│   │       └── main.go
│   └── .archived/                   # 归档目录（brickkit sync 自动管理，隐藏）
│       ├── authorization/
│       │   └── rbac/                # 被归档的组件（完整 Git 仓库）
│       └── infra/
│           └── redis-event-bus/
└── .gitignore
```

- `.brickkit/credentials`：`brickkit login` 生成的市场登录凭据。
- `.brickkit/manifests/`：Manifest 缓存。
- `.brickkit/artifacts/`：API 契约及其他产物缓存。CLI 安装组件时自动下载。按 `<版本化服务名>/<type>/<文件路径>` 组织。
- `.brickkit/generated/`：CLI 生成的部署文件（勿手动编辑）。包含 `docker-compose.yaml`（Docker 环境）或 `k8s/` 目录（K8s 环境）。如果项目中存在 `local: true` 的组件，还会生成 `local-debug.<版本化服务名>.env` 文件。
- `components/`：组件源码目录。自己开发的组件或通过 `brickkit add --repo` clone 的组件。每个组件是独立的 Git 仓库。
- `components/.archived/`：归档目录。`brickkit sync` 根据级联计算结果，将不启动的组件源码自动移入此目录。以 `.` 开头，文件管理器默认隐藏。

**关键规则：**
- 每个组件是独立的 Git 仓库（有自己的 `.git` 目录）
- 一个组件 ID 在 `components/` 下只能有一个源码目录
- `components/` 目录不提交到项目 Git 仓库（见 `.gitignore` 建议）
- `brickkit sync` 是双向的：根据级联计算结果，该归档的归档，该激活的移回来
- `brickkit remove` 时自动删除对应的源码目录

### D.3 资源配额覆盖规则

`components[].resources` 用于覆盖组件 Manifest 中 `deployment.resources` 的推荐值：

```yaml
components:
  - id: people/basic
    version: 1.2.0
    resources:                  # 覆盖组件推荐值
      limits:
        memory: "1Gi"           # 生产环境调大内存
```

CLI 优先级链：`brickkit.yaml resources` > `component.yaml deployment.resources` > `CLI 默认值（100m/128Mi）`

## 附录 E：CLI 命令完整参考

### E.1 命令总览

| 命令                      | 说明      | 核心行为                                                                                                                        |
| ----------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------- |
| `brickkit init [name]`  | 初始化项目   | 生成 `brickkit.yaml` 骨架和 `.brickkit/` 目录。不传项目名称时报错                                                                            |
| `brickkit add <id@ver>` | 添加组件    | 递归拉取依赖，下载 artifacts，写入 `brickkit.yaml`（不写 `enabled` 字段）。同 ID 不同版本时默认共存。支持 `--yes` 非交互模式。支持 `--repo` / `--repo-all` clone 源码 |
| `brickkit remove <id>`  | 移除组件    | 检查强依赖方，从 `brickkit.yaml` 移除，自动删除源码目录。多版本共存时必须指定版本                                                                           |
| `brickkit up`           | 一键启动    | 级联禁用计算，生成部署文件，生成 `local-debug.env`（如有 local: true），检测镜像权限，执行迁移，调用底层引擎                                                       |
| `brickkit down`         | 一键停止    | 调用底层引擎停止所有组件（⚠️ 不删除 volume，保留数据）                                                                                            |
| `brickkit status`       | 查看状态    | 读取底层引擎状态，展示组件运行表格（含多版本检测、级联跳过展示）                                                                                            |
| `brickkit order`        | 查看启动顺序  | 展示依赖拓扑排序结果                                                                                                                  |
| `brickkit sync`         | 整理源码工作区 | 根据级联计算结果，双向归档/激活组件源码。不启动的组件移到 `components/.archived/`，需要启动的移回 `components/`                                                 |
| `brickkit reset`        | 重置配置    | 恢复 `brickkit.yaml` 到初始备份                                                                                                    |
| `brickkit login`        | 登录市场    | 终端交互输入账密，Token 存 `.brickkit/credentials`。Token 过期报错提示重新登录                                                                   |
| `brickkit publish`      | 发布组件    | 上传 Manifest + 镜像引用 + 产物文件到市场（需先 `brickkit login`）                                                                           |

### E.2 常用参数

```bash
# 只启动指定组件（支持 @版本 写法）
brickkit up --only people/basic,department/tree
brickkit up --only people/basic@1.0.0

# 指定配置文件（多环境）
brickkit up --config brickkit.prod.yaml

# 启动前检查资源可达性
brickkit up --check-resources

# 只生成部署文件，不启动（用于审查）
brickkit up --dry-run

# 恢复到上一次操作前的备份
brickkit reset --last

# 强制重新拉取 Manifest 和 artifacts
brickkit add people/basic@1.0.0 --refresh

# 非交互模式（CI/CD 环境）
brickkit add people/basic@1.1.0 --yes

# 多版本共存时指定版本移除
brickkit remove people/basic@1.0.0

# clone 指定组件的完整 Git 仓库（仅开源组件）
brickkit add people/basic@1.0.0 --repo

# clone 所有递归依赖中开源组件的完整 Git 仓库
brickkit add erp/backend@1.0.0 --repo-all

# 整理源码工作区（双向归档/激活）
brickkit sync
```

**注意：**
- `brickkit up --only` 遇到 `enabled: false` 的组件时，CLI 报错阻断（不覆盖用户的显式声明）。
- `brickkit add` 遇到同 ID 不同版本时，默认共存（自动添加第二个条目），不覆盖。
- `brickkit add` 自动添加的组件不写 `enabled` 字段（即默认开启，可被级联关闭）。
- `brickkit add --repo` 仅对开源组件有效。闭源组件报错阻断。
- `brickkit add --repo-all` 遇到闭源组件时跳过并提示。
- `brickkit add --repo` / `--repo-all` 如果目标目录已存在，报错阻断。
- `brickkit sync` 是纯独立命令，不集成在 `brickkit up` 中。复用 `brickkit up` 的级联计算逻辑。
- `brickkit remove` 自动删除 `components/` 下对应的源码目录。

## 附录 F：生成的 docker-compose.yaml 示例

以下示例展示了 CLI 自动生成的 `docker-compose.yaml`，包含基础资源、数据库迁移（一次性 service）、正常组件、本地调试模式（extra_hosts）、前端组件（expose: true 映射端口）、以及资源配额的处理。

```yaml
# ============================================================
# 由 BrickKit CLI 自动生成，请勿手动编辑
# 生成时间：2026-08-08T10:00:00Z
# 项目：my-erp-project
# deploy.target: docker
# ============================================================

services:
  # ===== 基础资源 =====
  postgres:
    image: postgres:15
    environment:
      POSTGRES_USER: brickkit
      POSTGRES_PASSWORD: ${BRICKKIT_DB_PASSWORD:-dev}
    volumes:
      - postgres-data:/var/lib/postgresql/data
    networks:
      - brickkit-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U brickkit"]
      interval: 10s
      timeout: 5s
      retries: 3
    restart: unless-stopped

  # ===== 数据库迁移（一次性 service）=====
  people-basic-1-0-0-migration:
    image: registry.brickkit.io/people-basic:1.0.0
    # entrypoint 与 command 一起覆盖：镜像带 ENTRYPOINT 时只写 command 会参数错位，
    # 迁移容器会把服务启起来而不是执行迁移（002 §8.4）
    entrypoint: ["python"]
    command: ["manage.py", "migrate"]
    environment:
      - DATABASE_HOST=postgres
      - DATABASE_PORT=5432
      - DATABASE_NAME=people
      - DATABASE_PASSWORD=${PEOPLE_DB_PASSWORD}
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - brickkit-net
    restart: "no"              # 跑完就退出

  # ===== 组件（启动顺序：1）=====
  department-tree-1-0-0:
    image: registry.brickkit.io/department-tree:1.0.0
    environment:
      - COMPONENT_ID=department/tree
      - COMPONENT_VERSION=1.0.0
      - DATABASE_HOST=postgres
      - DATABASE_NAME=department
    depends_on:
      postgres:
        condition: service_healthy
    networks:
      - brickkit-net
    healthcheck:
      test: ["CMD-SHELL", "wget -q --spider http://localhost:8080/healthz || curl -fsS http://localhost:8080/healthz || exit 1"]
      interval: 10s
      timeout: 3s
      retries: 3
    deploy:
      resources:
        limits:
          cpus: "0.50"         # ← 来自 Manifest deployment.resources 或 CLI 默认值
          memory: 512M
    restart: unless-stopped

  # ===== 组件（启动顺序：2）=====
  # 注意：people/basic 在 brickkit.yaml 中标记为 local: true
  # 因此不生成容器，而是在其他容器中使用 extra_hosts 映射
  auth-rbac-1-0-0:
    image: registry.brickkit.io/auth-rbac:1.0.0
    extra_hosts:
      - "people-basic-1-0-0:host-gateway"   # 映射到宿主机
    environment:
      - COMPONENT_ID=authorization/rbac
      - PEOPLE_BASIC_ENDPOINT=http://people-basic-1-0-0:8081  # 本地端口
      - DATABASE_HOST=postgres
      - DATABASE_NAME=authorization
    depends_on:
      department-tree-1-0-0:
        condition: service_healthy
    networks:
      - brickkit-net
    restart: unless-stopped

  # ===== 组件（启动顺序：3，依赖迁移完成）=====
  people-basic-1-0-0:
    image: registry.brickkit.io/people-basic:1.0.0
    environment:
      - COMPONENT_ID=people/basic
      - DATABASE_HOST=postgres
      - DATABASE_NAME=people
      - DEFAULT_PAGE_SIZE=50    # 来自 brickkit.yaml config 覆盖
    depends_on:
      people-basic-1-0-0-migration:
        condition: service_completed_successfully  # 等待迁移成功
      department-tree-1-0-0:
        condition: service_healthy
    networks:
      - brickkit-net
    deploy:
      resources:
        # compose 用 reservations 表达 K8s 的 requests——字段名不一样，
        # 写成 requests 的话 Docker 不认，预留会**静默不生效**
        reservations:
          cpus: "0.10"         # ← 来自 Manifest deployment.resources.requests.cpu
          memory: 128M
        limits:
          cpus: "0.50"         # ← 来自 brickkit.yaml resources 覆盖（如有）
          memory: 512M
    restart: unless-stopped

  # ===== 前端组件（nginx 容器，expose: true 映射端口）=====
  portal-user-frontend-1-0-0:
    image: registry.brickkit.io/portal-user-frontend:1.0.0
    ports:
      # 默认使用 deployment.port (80) 映射到宿主机。
      # 若 brickkit.yaml 中配置了 exposePort: 8080，则生成为 "8080:80"。
      - "8080:80"
    environment:
      - COMPONENT_ID=portal/user-frontend
      - ERP_BACKEND_ENDPOINT=http://erp-backend-1-0-0:8080
    depends_on:
      people-basic-1-0-0:
        condition: service_healthy
    networks:
      - brickkit-net
    restart: unless-stopped

volumes:
  postgres-data:    # ⚠️ brickkit down 不会删除此 volume，数据安全

networks:
  brickkit-net:
    name: brickkit-my-erp-project-net
    driver: bridge
```

### G.2 Migration Job (CLI 串行控制等待)

⚠️ **幂等性保证：** CLI 在 `kubectl apply` 此 Job 前，会自动执行 `kubectl delete job/people-basic-1-0-0-migration --ignore-not-found` 清理可能残留的旧 Job（如上次迁移失败残留），确保重复执行 `brickkit up` 不会报错。

```yaml

kind: Job
metadata:
  name: people-basic-1-0-0-migration
  namespace: brickkit-my-erp-project
  labels:
    app: people-basic-1-0-0-migration    # 不能与组件本身同名，见 005 §6.3
    brickkit.io/component: people-basic
    brickkit.io/role: migration
spec:
  backoffLimit: 0            # 不重试，失败即终止
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migration
          image: registry.brickkit.io/people-basic:1.0.0
          # K8s 的 command 整体替换镜像的 ENTRYPOINT，因此**不需要**像 compose
          # 那样拆成两段，整条命令写在这里即可（002 §8.4）
          command: ["python", "manage.py", "migrate"]
          env:
            - name: DATABASE_HOST
              value: "postgres-main"
            - name: DATABASE_NAME
              value: "people"
            - name: DATABASE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: people-db-secret
                  key: password
```

### G.3 Deployment & Service

```yaml
apiVersion: apps/v1
kind: Deployment
```

## 附录 I：组件间通信推荐实践（非强制）

**定位：** 本附录为建议读、但不读也不影响使用的指导手册。BrickKit 平台不强制任何通信协议、超时策略或降级逻辑，但为了避免早期生态碎片化，提供以下业界最佳实践供组件开发者参考。

### I.1 推荐超时与重试策略

在微服务调用中，永远不要假设网络和依赖组件是 100% 可靠的。

| 场景 | 推荐超时时间 | 推荐重试策略 |
| --- | --- | --- |
| 同步 HTTP 查询（GET） | 3 - 5 秒 | 指数退避，最多 2 次 |
| 同步 HTTP 写入（POST/PUT） | 5 - 10 秒 | 不重试（防止重复提交，除非接口明确幂等） |
| 数据库查询 | 10 秒 | 不重试（由连接池管理） |
| 弱依赖调用（如发通知） | 2 秒 | 不重试，直接降级 |

**Python 示例 (Requests):**

```python
import requests
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

# 配置重试策略：仅对 GET 请求重试，最多 2 次，指数退避
retry_strategy = Retry(
    total=2,
    backoff_factor=1,
    status_forcelist=[429, 500, 502, 503, 504],
    allowed_methods=["GET"]
)
adapter = HTTPAdapter(max_retries=retry_strategy)

session = requests.Session()
session.mount("http://", adapter)
session.mount("https://", adapter)

response = session.get(f"{DEPT_ENDPOINT}/api/v1/departments", timeout=5)
```

建议组件在返回 HTTP 错误时，采用统一的 JSON 格式（参考 RFC 7807 Problem Details），方便调用方解析和前端展示。

### I.3 弱依赖降级代码模板

**核心原则：** 弱依赖（`optional: true`）缺失时，对应的环境变量完全不存在（CLI 不注入空字符串）。组件必须在代码中使用安全方式读取并执行降级（丢车保帅）。

**Python 示例**

```python
import os
import requests
import logging

logger = logging.getLogger(__name__)

# ⚠️ 必须使用 .get() 安全读取！
# 如果弱依赖没启动，这个环境变量完全不存在，使用 os.environ["X"] 会抛出 KeyError 导致组件崩溃。
EVENT_BUS_ENDPOINT = os.environ.get("INFRA_REDIS_EVENT_BUS_ENDPOINT")

def register_user(user_data):
    # 1. 核心主流程：无论如何都要执行
    db.save(user_data)

    # 2. 边缘流程（弱依赖）：尝试调用，失败则降级
    if EVENT_BUS_ENDPOINT:
        try:
            # 尝试发送注册成功事件，设置极短的超时（2秒）
            requests.post(
                f"{EVENT_BUS_ENDPOINT}/events",
                json={"type": "user.registered", "data": user_data},
                timeout=2
            )
        except Exception as e:
            # 【降级处理】：记录日志，不返回错误给客户端
            logger.warning(f"事件总线调用失败，降级处理: {e}")
    else:
        logger.info("未配置事件总线（弱依赖缺失），跳过事件发送")

    return {"status": "success"}
```

**Go 示例**

```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "time"
)

func registerUser(w http.ResponseWriter, r *http.Request) {
    // 1. 核心主流程
    saveToDatabase()

    // 2. 弱依赖降级
    // Go 的 os.Getenv 在变量不存在时返回空字符串 ""，因此直接判断是否为空即可
    eventBusEndpoint := os.Getenv("INFRA_REDIS_EVENT_BUS_ENDPOINT")
    if eventBusEndpoint != "" {
        // 设置 2 秒超时上下文
        ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
        defer cancel()

        req, _ := http.NewRequestWithContext(ctx, "POST", eventBusEndpoint+"/events", nil)
        client := &http.Client{}
        _, err := client.Do(req)
        if err != nil {
            // 【降级处理】：记录日志，不返回错误给客户端
            log.Printf("事件总线调用失败，降级处理: %v", err)
        }
    } else {
        log.Printf("未配置事件总线（弱依赖缺失），跳过事件发送")
    }

    w.Write([]byte(`{"status": "success"}`))
}
```

### I.4 健康检查最佳实践

健康检查端点（`/healthz`）用于底层引擎（K8s Probe / Docker healthcheck）判断容器是否存活。

⚠️ **核心原则：`/healthz` 只检查本进程存活，不检查任何外部依赖。**

健康检查失败 = 进程死了，需要重启。数据库挂了 ≠ 进程死了。

**✅ 推荐做法：**

- **快速返回**：响应时间必须在 1 秒以内，不做任何 I/O 操作。
- **只检查本进程存活**：返回 200，告诉底层引擎"我还活着"。
- **不检查数据库**：数据库挂了，业务 API 返回 500 即可，不应影响存活判断。
- **不检查依赖组件**：依赖组件挂了，调用方自行重试或降级，不应影响存活判断。
- **不检查弱依赖**：弱依赖（如 Redis 缓存、事件总线）挂了，组件依然可以降级运行。

**❌ 错误做法（全部禁止）：**

- 在健康检查中检查数据库连接（`db.ping()`）。
- 在健康检查中检查依赖组件的 `/healthz`。
- 在健康检查中检查 Redis / 缓存连接。
- 在健康检查中执行复杂的 SQL 统计查询。
- 在健康检查中调用其他外部第三方 API。
- 任何外部依赖不可用时返回非 200。

**为什么不能检查外部依赖（雪崩原理）：**

```
数据库短暂抖动（3秒）
  → 组件 A 的 /healthz 检查数据库
  → /healthz 返回 500
  → K8s livenessProbe 失败
  → Pod 被 kill
  → Pod 重启
  → 数据库仍在抖动
  → /healthz 再次返回 500
  → Pod 再次被 kill
  → CrashLoopBackOff
  → 组件 A 完全不可用
  → 依赖组件 A 的组件 B 也不可用
  → 级联雪崩：整个系统瘫痪
```

**正确的做法：**

- `/healthz` 只检查本进程存活（返回 200）
- 数据库挂了 → 业务 API 返回 500（这是正常的业务错误）
- 调用方组件收到 500 → 自行决定重试或降级
- 数据库恢复 → 业务 API 恢复正常
- 全程没有 Pod 被重启，没有雪崩。

### I.5 日志与链路追踪

在分布式组件调用中，强烈建议通过 HTTP Header 传递 `Trace-Id`，并在日志中打印，以便在日志系统中串联完整的调用链。

**调用方 (Component A):**

### I.6 gRPC 组件开发指导

如果组件需要提供 gRPC 服务（或 HTTP + gRPC 双协议），需要：

1. 在组件仓库中定义 `.proto` 文件
2. 在 `component.yaml` 的 `artifacts` 中声明 proto 文件
3. 在组件中实现 gRPC 服务
4. 发布时 proto 文件随 artifacts 上传到市场

**proto 文件在组件仓库中的位置：**

```
my-component/
├── component.yaml
├── Dockerfile
├── proto/                    ← proto 文件在组件仓库内部
│   └── mycomponent/
│       └── v1/
│           └── service.proto
├── main.go / app.py
├── migrations/               ← SQL 迁移文件（如有）
│   └── 001_init.sql
└── ...
```

**component.yaml 中声明：**

```yaml
# gRPC 组件必须提供 proto 文件作为 API 契约
artifacts:
  - type: api-contract
    format: protobuf
    description: "gRPC API 契约文件"
    files:
      - proto/mycomponent/v1/service.proto
  - type: api-docs
    format: openapi
    description: "HTTP REST API 文档（grpc-gateway 自动生成）"
    files:
      - openapi.json
```

**Go 组件（grpc-gateway 双协议）：**

Go 组件推荐使用 grpc-gateway，在同一个端口同时提供 HTTP 和 gRPC 服务。使用 `golang.org/x/net/http2/h2c` 支持 HTTP/2 cleartext。

Manifest 中不需要 extraPorts，因为 HTTP 和 gRPC 共用同一个端口（`deployment.port`）。

**Python 组件（grpcio 双端口）：**

Python 组件可以使用 grpcio 提供 gRPC 服务。由于 Python 的 grpcio 不支持与 HTTP 共用同一个端口，需要在 Manifest 中通过 `extraPorts` 声明额外的 gRPC 端口：

```yaml
deployment:
  type: container
  image: registry.brickkit.io/people-basic:1.0.0
  port: 8080              # 主端口（HTTP，健康检查用）
  extraPorts:             # 额外端口（gRPC）
    - name: grpc
      port: 9090
```

**CLI 行为：**

| 环境 | CLI 行为 |
| --- | --- |
| Docker | 不需要额外处理。Docker Network 内容器的所有端口天然可达 |
| K8s | CLI 在 Service 中暴露 9090 端口 |
| 环境变量注入 | CLI 为依赖该组件的组件注入 `PEOPLE_BASIC_GRPC_ENDPOINT=http://people-basic-1-0-0:9090` |

**关键规则：**

- proto 文件是"API 契约"，不是"实现代码"
- 代码可以闭源，但 API 契约必须公开
- 闭源组件必须在 artifacts 中声明至少一个 `type: api-contract` 的产物
- proto 文件跟随组件版本走，不需要独立的版本管理
- 向后兼容的 proto 变更（新增方法/字段），旧客户端代码自然兼容
- 破坏性的 proto 变更（删除方法/字段），遵循"破坏性变更协同守则"

**调用方获取 proto 文件：**

安装组件时，CLI 自动下载所有 artifacts 到 `.brickkit/artifacts/`：

```bash
brickkit add department/tree@1.0.0
# CLI 自动下载 proto 文件到 .brickkit/artifacts/department-tree-1-0-0/

# 查看下载的契约文件
ls .brickkit/artifacts/department-tree-1-0-0/api-contract/
# → proto/department/v1/department.proto
```

调用方可以基于下载的 proto 文件生成客户端代码：

```bash
# Go
protoc --go_out=. --go-grpc_out=. \
  .brickkit/artifacts/department-tree-1-0-0/api-contract/proto/department/v1/department.proto

# Python
python -m grpc_tools.protoc -I=. --python_out=. --grpc_python_out=. \
  .brickkit/artifacts/department-tree-1-0-0/api-contract/proto/department/v1/department.proto
```

### I.7 优雅关闭（SIGTERM）推荐实践

**定位：** 本节为推荐实践。平台不强制组件处理 SIGTERM（002 组件规范中列为"建议"），但为了避免在停止、更新组件时中断正在处理的请求，建议组件实现优雅关闭。

#### I.7.1 案例：不处理 SIGTERM 会发生什么

```text
用户执行 brickkit down（或 K8s 滚动更新）
  → 底层引擎向 erp-backend 容器发送 SIGTERM（"请收尾退出"）
  → 此时 erp-backend 正在处理第 500 个写订单请求
  → erp-backend 没有处理 SIGTERM，进程继续运行
  → 引擎等待宽限期（Docker 默认 10 秒 / K8s 默认 30 秒）
  → 引擎发送 SIGKILL 强杀进程（"直接拉闸断电"）
  → 第 500 个订单写了一半，事务不完整
  → 数据不一致 ❌
```

**处理了 SIGTERM（优雅关闭）：**

```text
用户执行 brickkit down
  → 底层引擎发送 SIGTERM
  → erp-backend 收到信号："哦，要关门了"
  → 停止接受新订单
  → 把第 500 个订单写完、提交事务
  → 关闭数据库连接
  → exit 0 正常退出 ✅
```

#### I.7.2 两个信号的区别

| 信号 | 含义 | 类比 | 何时发出 |
| --- | --- | --- | --- |
| SIGTERM | 请收尾后退出 | 餐厅"5 分钟后打烊"的通知 | 引擎停止容器时先发送 |
| SIGKILL | 强制杀死 | 直接拉闸断电 | 宽限期过后进程仍未退出时 |

#### I.7.3 代码示例

**Python 示例（标准库 http.server）：**

```python
import signal
import threading

def graceful_shutdown(signum, frame):
    log("info", "收到 SIGTERM，正在完成当前请求...")
    # 在独立线程中调用 shutdown：停止接受新请求，等待现有请求完成
    threading.Thread(target=server.shutdown).start()

signal.signal(signal.SIGTERM, graceful_shutdown)

server.serve_forever()   # shutdown() 被调用后，这里会返回
log("info", "已优雅退出")
```

**Go 示例：**

```go
srv := &http.Server{Addr: ":8080"}

sigCh := make(chan os.Signal, 1)
signal.Notify(sigCh, syscall.SIGTERM)

go func() {
    <-sigCh
    log.Printf("收到 SIGTERM，正在完成当前请求...")
    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    srv.Shutdown(ctx) // 停止接受新请求，等待现有请求完成（最多等 10 秒）
}()

srv.ListenAndServe()
```

#### I.7.4 要点

| 要点 | 说明 |
| --- | --- |
| 停止接受新请求 | 收到 SIGTERM 后不再接新请求 |
| 完成存量请求 | 等待正在处理的请求完成，但要设超时（如 10 秒），避免无限等待 |
| 释放资源 | 关闭数据库连接、缓存连接等 |
| 以 exit 0 退出 | 正常退出，引擎不会视为崩溃 |

**补充说明：** 多数现代框架（Spring Boot、uvicorn/FastAPI、Go 的 `http.Server`、Node.js 的 `server.close()` 等）已内置优雅关闭支持或默认处理。如果使用框架，先查阅框架文档，通常不需要自己写信号处理代码。

**一句话总结：** 优雅关闭 = 收到 SIGTERM 后停止接新请求、完成存量请求、在宽限期内自行退出，不要等引擎"拉闸"。

## 附录 J：渐进式拼装工作流

### J.1 什么是渐进式拼装

渐进式拼装是 BrickKit 的核心开发模式：先安装底层组件，获取 API 契约，基于契约开发连接组件，发布后再安装连接组件，自动拼装完整系统。像搭积木一样，一块一块地加。

### J.2 完整流程

```
第 1 步：底层组件开发者发布组件
    → 开发 department/tree 组件
    → 在 artifacts 中声明 proto 文件
    → brickkit publish 发布到市场

第 2 步：连接组件开发者安装底层组件（获取 API 契约）
    brickkit add department/tree@1.0.0
    → CLI 下载 Manifest + proto 文件到 .brickkit/artifacts/

第 3 步：连接组件开发者查看下载的契约文件
    ls .brickkit/artifacts/department-tree-1-0-0/api-contract/
    → proto/department/v1/department.proto

第 4 步：连接组件开发者基于契约开发连接组件
    → 读取 proto 文件，生成客户端代码
    → 开发连接组件业务逻辑
    → 在连接组件的 Manifest 中声明依赖 department/tree@1.0.0

第 5 步：连接组件开发者发布连接组件
    brickkit publish --path ./erp-backend --visibility public

第 6 步：最终用户安装连接组件（自动拼装）
    brickkit add erp/backend@1.0.0
    → CLI 自动递归拉取所有依赖 + 下载所有 artifacts
    brickkit up
    → 一键启动完整系统
```

### J.3 角色分工

| 角色 | 做什么 | 使用什么 |
| --- | --- | --- |
| 底层组件开发者 | 开发并发布底层组件（如部门组件） | `brickkit publish` |
| 连接组件开发者 | 安装底层组件 → 获取契约 → 开发连接组件 → 发布 | `brickkit add` + IDE + `brickkit publish` |
| 最终用户 | 安装连接组件 → 自动拼装完整系统 | `brickkit add` + `brickkit up` |

### J.4 核心原则

- **这个流程可以无限重复：** 每次有新的底层组件发布，连接组件开发者都可以安装它、获取契约、开发新的连接功能、发布、再被最终用户安装。
- **API 契约是"开发时"的辅助，不是"运行时"的依赖。** 产物文件下载失败不影响组件启动。
- **代码可以闭源，但 API 契约必须公开。** 否则调用方无法开发调用代码，组件就无法被集成。
- **proto 文件跟随组件版本走，不需要独立的版本管理。**
