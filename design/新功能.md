# 前端编排设计文档（v2.0）

---

## 第 1 章 · 功能概述

### 1.1 问题域

在 brickKit 的组件化架构中，一个业务组件的仓库可能同时包含后端代码和前端代码（前后端同仓）。当开发者在本地调试时，需要将多个组件的前端源码聚合到一个"壳应用"的工作区中，以实现跨组件的热更新开发。

手动管理这些路径（编辑 `pnpm-workspace.yaml`、建立软链接）繁琐且易错。本功能让 brickKit 基于装配清单（`brickkit.yaml`）自动完成这一聚合。

此外，不同客户对前端包的分发渠道有截然不同的合规要求：

- **互联网/SMB 客户**：默认发布至公开 npm registry（零基建成本）。
- **政企/金融/医疗客户**：安全审计要求所有业务代码（含前端）不得出现在公开 registry，必须使用私有 npm registry（如 Verdaccio、Nexus、Artifactory）或本地 tarball。

brickKit 必须在不改变任何组件代码的前提下，支持这两种模式的无缝切换。这意味着 brickKit 需要能够根据装配清单中的 registry 配置，自动生成正确的 `.npmrc` 路由文件，让 `pnpm install` 知道从哪里拉取 `@brick/*` 包。

### 1.2 功能边界（三不做）

- **不做包管理**：不执行 `npm publish` / `npm unpublish`，不操作 registry 中的包内容，不管理 npm 账号。
- **不做前端构建**：不内置 Node.js 运行时，不执行 `vite build` 或 `webpack`，不关心前端框架。
- **不做 CI/CD 编排**：不依赖任何远程流水线，所有操作在开发者本地完成。

brickKit 在本功能中做两件事：

1. 读取装配清单，将符合条件的本地组件前端路径，写入壳应用的 `pnpm-workspace.yaml`，并触发 `pnpm install`。
2. 根据装配清单中的 registry 配置，在壳应用前端目录下生成 `.npmrc` 文件，确保 `pnpm install` 能从正确的 registry（公开或私有）拉取 `@brick/*` 包。

### 1.3 适用场景

- 本地开发时，将某个组件切为 `local` 源，希望壳应用直接加载其前端源码以实现热更新。
- 同时存在 `local` 源和 `git` 源的混合场景：`local` 的走源码，`git` 的走 npm registry 包。
- 企业客户安全审计要求使用私有 npm registry，需要在不修改任何组件 `package.json` 的前提下，让壳应用的 `pnpm install` 自动从私有 registry 拉取 `@brick/*` 包。
- 开发者需要在公开 registry 和私有 registry 之间快速切换（如：开源贡献用公开，企业交付用私有）。
- 一个项目中存在多个前端壳应用（如管理后台 + 用户门户），需要对每个壳应用分别注入。

### 1.4 版本支持声明

| 能力 | v1（当前） | 未来版本 |
|---|---|---|
| 包管理器 | pnpm workspace | yarn workspace / npm workspace（通过 `workspace_type` 字段适配） |
| 壳应用数量 | 支持多个 `frontend-shell` | 同左 |
| registry 模式 | public / private | tarball（预留） |

v1 仅支持 **pnpm workspace**。若壳应用声明了 `workspace_type: yarn` 或 `workspace_type: npm`，`fe-link` 输出 `[WARN] workspace_type 'yarn' is not yet supported in v1, skipping` 并跳过该壳应用。

## 第 2 章 · 配置契约扩展

### 2.1 业务组件：`component.yaml` 新增 `frontend` 字段

该字段为可选。未声明的组件视为纯后端组件，`fe-link` 静默跳过。

```yaml
name: demo/catalog
version: 1.0.0
# ... 其他 brickKit 标准字段 ...
frontend:
  package: "@brick/biz-demo-catalog"   # 该组件前端代码对应的 npm 包名
  source_dir: "frontend/biz-ui"        # 前端源码在组件仓库中的相对路径
```

**`source_dir` 安全约束**：

- 必须是相对于组件仓库根目录的路径。
- 严禁包含 `..` 路径段。
- 严禁以 `/` 或盘符（如 `C:\`）开头。
- 违反任一条 → `fe-link` 输出 `[ERROR]` 并跳过该组件。

### 2.2 壳应用：`component.yaml` 新增 `role` 与 `frontend` 配置

壳应用是前端聚合的目标容器，必须通过 `role: frontend-shell` 标识。

```yaml
name: infra/web-shell
version: 1.0.0
role: frontend-shell
frontend:
  workspace_type: pnpm                                    # pnpm（默认）| yarn | npm（预留）
  workspace_file: "frontend/pnpm-workspace.yaml"          # 相对于组件根目录
```

字段说明：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `frontend.workspace_type` | string | 否 | `pnpm` | 工作区类型。v1 仅支持 `pnpm`，其他值输出警告并跳过 |
| `frontend.workspace_file` | string | 是 | — | 工作区配置文件相对于组件根目录的路径 |

**多壳应用规则**：一个项目中可以存在多个 `role: frontend-shell` 的组件（如管理后台壳 + 用户门户壳）。`fe-link` 对每个壳应用独立执行注入。

### 2.3 装配清单：`brickkit.yaml` 新增 `frontend` 顶级配置块

用于声明整个装配的前端 registry 策略。该配置块为可选，未声明时行为等同于 `mode: public`。

```yaml
deploy:
  target: docker

frontend:
  # 模式：public（默认） | private | tarball
  mode: private
  # 私有 registry 地址（mode=private 时必填，尾部斜杠可选，程序自动补全）
  registry: "https://npm.acme-corp.com/"
  # npm scope（默认 @brick，仅该 scope 的包走私有 registry，其他第三方包仍走公开 registry）
  scope: "@brick"
  # 认证 Token 的环境变量名（mode=private 时推荐，避免明文写入 .npmrc）
  auth_token_env: "NPM_TOKEN"

components:
  - name: infra/web-shell
    version: 1.0.0
    source:
      type: local
      path: ./components/infra-web-shell
  # ... 其他组件
```

字段说明：

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `frontend.mode` | string | 否 | `public` | `public` = 使用公开 npmjs.com；`private` = 使用私有 registry；`tarball` = 从本地 tarball 文件安装（预留，当前版本不实现） |
| `frontend.registry` | string | mode=private 时必填 | — | 私有 registry 的完整 URL。尾部斜杠可选，程序自动补全 |
| `frontend.scope` | string | 否 | `@brick` | 仅该 scope 的包路由到私有 registry，其他 scope（如 `@vue`、`lodash`）仍走公开 registry |
| `frontend.auth_token_env` | string | 否 | `NPM_TOKEN` | 认证 Token 通过环境变量注入，`.npmrc` 中写入 `${ENV_VAR}` 占位符而非明文 |

**设计决策：scope-only 路由**

只将 `@brick` scope 路由到私有 registry，而非全局替换 registry 地址。原因：

- 第三方依赖（react、vue、lodash 等）始终从公开 registry 拉取，不受私有 registry 可用性或同步延迟影响。
- 私有 registry 只需同步/存储 `@brick/*` 包，大幅降低运维负担。
- 切换时只需修改一个 scope 的路由，风险最小。

## 第 3 章 · 命令设计：`brickkit fe-link`

### 3.1 语义

读取当前目录的 `brickkit.yaml`，找到所有壳应用，将所有 `source.type == local` 且声明了 `frontend.source_dir` 的业务组件的前端路径，安全注入到每个壳应用的 `pnpm-workspace.yaml` 中；同时根据 `frontend` 配置块生成 `.npmrc` 文件，确保 registry 路由正确；然后在每个壳应用的前端目录执行 `pnpm install`。

### 3.2 执行算法

```
1. 解析当前目录的 `brickkit.yaml`
   若解析失败 → 输出 [ERROR]，退出码 1

2. 读取 `frontend` 顶级配置块（若不存在，视为 mode=public）
   若 mode=private 但 `registry` 未设置 → 输出 [ERROR]，退出码 1
   若 `registry` 不以 `/` 结尾 → 自动补全，输出 [INFO] 提示

3. 遍历 components，找到所有 `role == "frontend-shell"` 的组件 → 记为 ShellList
   若 ShellList 为空 → 输出 [ERROR]，退出码 1

4. 遍历 components，筛选出同时满足以下条件的组件 → 记为 BizList：
   a. `source.type == "local"`
   b. 存在 `frontend.source_dir` 字段
   c. `source_dir` 通过安全校验（见 3.2.1）
   d. 该 `source_dir` 目录在本地确实存在
      若不存在 → 输出 [WARN]，跳过该组件，继续

5. 对 ShellList 中的每个壳应用，执行以下操作：
   5.1 校验 `workspace_type`
       若不为 `pnpm` → 输出 [WARN]，跳过该壳应用
   5.2 计算壳应用的本地绝对路径，校验 `workspace_file` 是否存在
       若不存在 → 输出 [ERROR]，退出码 1
   5.3 读取 `workspace_file` 文本内容
   5.4 查找 `# BRICKKIT_FE_LINK_START` 和 `# BRICKKIT_FE_LINK_END` 标记行
       若找到 → 替换两行之间的内容为 BizList 的相对路径列表
       若未找到 → 在文件末尾追加标记块及路径列表
   5.5 路径计算规则：
       每个路径 = 从 `workspace_file` 所在目录到组件 `source_dir` 的相对路径
   5.6 将修改后的文本写回 `workspace_file`
   5.7 生成 `.npmrc` 文件（详见 3.4）
   5.8 若 mode=private，检查 `auth_token_env` 对应的环境变量是否存在
       若不存在 → 输出 [WARN]（不中断，但提示用户）
   5.9 在 `workspace_file` 所在目录执行 `pnpm install`
       若 pnpm 未安装 → 输出 [WARN]，不中断
       若 pnpm install 失败 → 输出 [WARN] + stderr 前 10 行，不中断

6. 输出结果摘要
```

#### 3.2.1 `source_dir` 安全校验

对每个组件的 `frontend.source_dir` 执行以下校验：

- 若包含 `..` 路径段 → 输出 `[ERROR] Component {name}: source_dir contains '..' (path traversal rejected). Skipped.`，跳过。
- 若以 `/` 开头（Unix 绝对路径）→ 输出 `[ERROR] Component {name}: source_dir must be a relative path. Skipped.`，跳过。
- 若匹配盘符模式（如 `C:\`）→ 同上。

### 3.3 幂等性

- 重复执行 `fe-link` 不会产生重复路径（每次替换整个 `BRICKKIT_FE_LINK` 区块）。
- 若 BizList 为空（没有任何 local 源组件声明了 frontend），则清空区块内容，但保留标记行。
- `.npmrc` 文件同样幂等：每次执行完全重写 `BRICKKIT_FE_LINK` 区块，不追加。

### 3.4 `.npmrc` 生成规则

#### 3.4.1 文件位置

在 `workspace_file` 所在目录（即壳应用前端根目录）下生成 `.npmrc` 文件。

#### 3.4.2 生成逻辑

根据 `brickkit.yaml` 中的 `frontend.mode` 分支处理：

**mode = public（或未声明 frontend 块）：**

```
# BRICKKIT_FE_LINK_START
# 以下内容由 brickkit fe-link 自动管理，请勿手动修改
# mode: public — 所有包从公开 registry 拉取
# BRICKKIT_FE_LINK_END
```

不写入任何 registry 配置，pnpm 使用默认行为（npmjs.com）。

**mode = private：**

```
# BRICKKIT_FE_LINK_START
# 以下内容由 brickkit fe-link 自动管理，请勿手动修改
# mode: private
@brick:registry=https://npm.acme-corp.com/
//npm.acme-corp.com/:_authToken=${NPM_TOKEN}
# BRICKKIT_FE_LINK_END
```

规则：

- 第一行：`{scope}:registry={registry_url}` — 仅该 scope 走私有 registry。
- 第二行：`//{registry_host}/:_authToken=${ENV_VAR}` — 认证 Token 使用环境变量占位符，严禁写入明文 Token。
- `registry_host` 从 `frontend.registry` URL 中提取（去掉协议头和尾部斜杠）。
- `ENV_VAR` 取自 `frontend.auth_token_env`，默认 `NPM_TOKEN`。
- 若 `frontend.registry` 不以 `/` 结尾，自动补全后输出 `[INFO] Registry URL normalized: {原值} → {补全值}`。

**mode = tarball（预留）：**

当前版本输出警告 `[WARN] mode 'tarball' is not yet implemented, falling back to public`，按 public 处理。

#### 3.4.3 文件修改策略

与 `pnpm-workspace.yaml` 相同：按行读取文本，使用 `# BRICKKIT_FE_LINK_START` / `# BRICKKIT_FE_LINK_END` 标记定位，文本级替换。保留用户在标记块之外手写的任何 `.npmrc` 配置（如 `strict-ssl=false`、代理设置等）。

若 `.npmrc` 文件不存在，则创建新文件并写入完整内容（含标记块）。

#### 3.4.4 安全约束

- 严禁将 Token 明文写入 `.npmrc`。始终使用 `${ENV_VAR}` 占位符。
- 若 `mode=private` 但未设置 `frontend.registry`，输出 `[ERROR]` 并终止（退出码 1）。
- 输出摘要中不打印 Token 值，仅提示 `Auth token will be read from env: $NPM_TOKEN`。

### 3.5 并发安全

`fe-link` 不支持并发执行。若多个终端同时运行 `fe-link`，可能导致文件写入冲突。

v1 不实现文件锁。文档中明确声明此约束。未来版本如有需求，可通过临时锁文件（如 `.brickkit-fe-link.lock`）实现。

## 第 6 章 · 实现注意事项

### 6.1 文件修改策略

由于 Go 的 `gopkg.in/yaml.v3` 在反序列化再序列化时会丢失 YAML 注释和格式，禁止使用 YAML 库读写 `pnpm-workspace.yaml`。

正确做法：按行读取文本文件，使用字符串匹配定位 `# BRICKKIT_FE_LINK_START` 和 `# BRICKKIT_FE_LINK_END`，进行文本级替换后写回。这样可 100% 保留用户手写的其他配置和注释。

### 6.2 相对路径计算

使用 Go 标准库 `filepath.Rel(basePath, targetPath)` 计算从 `workspace_file` 所在目录到组件 `source_dir` 的相对路径。注意将结果中的反斜杠（Windows）统一替换为正斜杠（YAML 标准）。

### 6.3 执行 pnpm install

使用 `os/exec.Command("pnpm", "install")` 在 `workspace_file` 所在目录执行。

- 捕获 stdout 和 stderr。
- 若命令失败：输出 `[WARN] pnpm install failed. First 10 lines of error output:`，随后输出 stderr 的前 10 行，最后输出 `Hint: You may run 'pnpm install' manually to see full output.`
- 不中断流程（因为链接已写入，用户可排查后手动执行）。

### 6.4 `.npmrc` 文件修改策略

与 `pnpm-workspace.yaml` 完全一致：按行读取文本，使用 `# BRICKKIT_FE_LINK_START` / `# BRICKKIT_FE_LINK_END` 标记定位，文本级替换。

关键细节：

- 若 `.npmrc` 文件不存在，使用 `os.Create` 创建新文件。
- 从 `frontend.registry` URL 中提取 host 时，使用 `net/url` 标准库解析，去掉协议头和尾部斜杠。例如 `https://npm.acme-corp.com/` → `npm.acme-corp.com`。
- 若 `frontend.registry` 不以 `/` 结尾，自动补全后输出 `[INFO]` 提示。
- Token 行格式严格遵循 npm 规范：`//{host}/:_authToken=${ENV_VAR}`。注意双斜杠开头，这是 npm 的标准格式。
- 写入完成后设置文件权限为 `0600`（仅所有者可读写），因为文件可能包含 Token 占位符引用。

### 6.5 安全审计要点

- 代码中任何位置不得将 Token 值写入日志、终端输出或文件。
- 终端输出仅显示 `Auth token will be read from env: $NPM_TOKEN`，不显示 Token 内容。
- `.npmrc` 文件权限设为 `0600`，防止同机器其他用户读取。
- 若未来支持 `tarball` 模式，tarball 文件路径不得包含 `..` 等路径穿越字符。

### 6.6 路径安全校验

对 `frontend.source_dir` 的校验逻辑（Go 伪代码）：

```go
func validateSourceDir(sourceDir string) error {
    // 禁止绝对路径
    if filepath.IsAbs(sourceDir) {
        return fmt.Errorf("source_dir must be a relative path")
    }
    // 禁止 Windows 盘符
    if len(sourceDir) >= 2 && sourceDir[1] == ':' {
        return fmt.Errorf("source_dir must be a relative path")
    }
    // 禁止路径穿越
    for _, seg := range strings.Split(filepath.ToSlash(sourceDir), "/") {
        if seg == ".." {
            return fmt.Errorf("source_dir contains '..' (path traversal rejected)")
        }
    }
    return nil
}
```

### 6.7 并发安全声明

`fe-link` 在 v1 中不实现文件锁。若多个终端同时执行 `fe-link`，可能导致 `pnpm-workspace.yaml` 或 `.npmrc` 文件写入冲突。

用户应确保同一时刻只有一个终端执行 `fe-link`。未来版本如有需求，可通过临时锁文件（如 `.brickkit-fe-link.lock`）实现互斥。
