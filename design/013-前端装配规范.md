## 1. 这份文档解决什么问题

### 1.1 一个组件带前端，麻烦在哪

BrickKit 里前端组件早就不是新鲜事：它是一个跑着 nginx 的普通 container，和后端组件在平台眼里没有区别（012 §2.10）。一个前端组件配一个后端组件，今天就能跑。

麻烦出在**多**上。

当你要拼的是一整套 ERP —— `mdm/customer`、`erp/sales`、`erp/purchase`、`erp/inventory`…… 每个组件都带自己的界面，而最终用户要看到的是**一个产品**：一套左侧菜单、一次登录、一个域名。这时按"一个前端组件一个 nginx 容器"来做，会得到 20 个互不相干的网站。

要把它们并成一个，前端只有一条路：**这些界面得被同一次打包收进同一个产物**。而一旦涉及打包，就冒出一串组件开发者不该操心的问题：

- 20 个组件的界面代码，怎么到达打包的那台机器？
- 装了哪些组件、每个什么版本，打包的时候怎么知道？
- 今天我只想调 `erp/sales`，另外 19 个的界面能不能别出现在我眼前？
- 部署的人手上只有 docker，他要不要装 Node？

### 1.2 答案：前端和后端是同一套模型

把后端那套已经跑通的东西照着镜子看一遍，答案是现成的：

| | 后端 | 前端 |
| --- | --- | --- |
| 产物是什么 | Docker 镜像 | npm 包 |
| 放在哪 | Docker registry | npm registry |
| 谁装的工具 | 用户装 docker | 用户装 npm / pnpm / yarn |
| 认证谁做 | 用户 `docker login` | 用户 `npm login` |
| 谁构建 | 组件的 `Makefile`，手动 | 组件的 `Makefile`，手动 |
| **BrickKit 做什么** | **解析依赖 → 翻译成 compose / K8s 清单 + 注入地址** | **解析依赖 → 翻译成一份包清单** |

BrickKit 从来不替后端组件跑 `go build`，也不替它跑 `docker build`。同理它不替前端跑 `pnpm install`，不替壳应用跑 `vite build`。

它只做一件后端那边也在做、而且只有它做得了的事：**把「这次装配包含哪些组件」翻译成一份机器可读的清单。**

后端那份清单叫 `docker-compose.yaml`，前端这份叫 `package.json`。

### 1.3 BrickKit 在这件事里只做一件事

> **读 BOM，生成一份前端依赖清单。**

清单里写着：这次装配包含哪些带界面的组件、每个是什么版本、哪些正在被本地改动。

然后你用自己的包管理器照着清单装。`brickkit add` 让清单多一条，`brickkit sync` 让清单少一条 —— **加载和卸载由 pnpm 执行，清单由 BrickKit 维护。** 和「compose 文件由 CLI 生成、镜像由 docker 拉」是同一件事。

**为此新增的东西：`component.yaml` 一个 `ui` 块，外加 CLI 顺手多生成两个文件。没有新命令。**

### 1.4 边界（三不做）

| 不做 | 原因 |
| --- | --- |
| 不执行任何前端命令（`npm install` / `pnpm build` / `vite`） | 与「不做数据库迁移工具」同源：CLI 只生成清单，不管工具的选择和逻辑（004 §2.2）。用 npm 还是 pnpm 还是 yarn 是使用者的选择 |
| 不管 npm registry 的认证 | 与「不自动 docker login」严格对称（004 §2.2）。用户自己 `npm login`，CLI 不生成 `.npmrc`、不碰 Token、不在 `brickkit.yaml` 里存凭据 |
| 不改用户手写的任何文件 | CLI 只写 `.brickkit/generated/` 下自己的目录。不做 `pnpm-workspace.yaml` 文本手术，不需要标记块，不需要幂等性特判 |

第三条值得多说一句。让 CLI 去用户的 `pnpm-workspace.yaml` 里插一段带标记的内容，会立刻长出三个必须回答的问题：重复执行会不会写重、用户手写在标记外的配置保不保得住、两个终端同时跑会不会写坏。**换成"CLI 只写自己的目录"，这三个问题一个都不存在。**

## 2. 契约：`component.yaml` 的 `ui` 块

`ui` 是可选块。不写的组件就是纯后端组件，前端装配完全绕开它，不产生任何输出。

### 2.1 业务组件

```yaml
apiVersion: brickkit/v1
kind: Component

metadata:
  id: mdm/customer
  name: 客户主数据
  version: 1.0.0
  vendor: acme

deployment:
  type: container
  image: registry.acme.com/mdm-customer:1.0.0
  port: 8080

healthCheck:
  type: http
  path: /healthz

# ===== 前端装配声明 =====
ui:
  package: "@acme/biz-mdm-customer"   # npm 包名
  dir: frontend                        # 前端工程在本仓库内的相对路径
```

| 字段 | 类型 | 必须 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `ui.package` | string | 业务组件必须 | — | 该组件界面对应的 npm 包名。版本恒等于 `metadata.version`（§2.5） |
| `ui.dir` | string | 否 | — | 前端工程在组件仓库内的相对路径。源码在活跃工作区时用它建本地链接（§3.4）。不写则该组件永远走 registry 包 |
| `ui.role` | string | 否 | — | 只有一个合法值 `shell`。见 §2.2 |

> **实现备注：** `ui` 块落地到 `internal/manifest` 之后，请给上表补一条字段表注解
> （写法照抄 003 里那些 HTML 注释），并把新结构体加进 `tests/docfields` 的
> `fieldTableTypes`。这样 `make check-doc-fields` 才会盯住这张表 —— 否则字段改了名，
> 文档不会有人提醒。

### 2.2 壳组件

壳是把各组件界面装到一起的那个容器。它**不声明 `ui.package`** —— 它不是被装的包，它是装包的地方。

```yaml
metadata:
  id: infra/web-shell
  name: PC 壳应用
  version: 1.0.0

deployment:
  type: container
  image: registry.acme.com/acme-erp-shell:1.0.0   # 装配方自己构建、自己推的镜像
  port: 80

healthCheck:
  type: http
  path: /

ui:
  role: shell
```

`ui.role: shell` 只有一个作用，但这个作用不可替代：**告诉 CLI「这个组件要能访问到本次装配里所有带界面的组件」。**

壳不能用 `dependencies` 声明这件事 —— 那样壳的版本就会被它装的每一个业务组件绑架，加一个组件就得发一版壳。所以：

> **壳的依赖集不是声明出来的，是装配算出来的：本次会启动的、声明了 `ui.package` 的组件全集。**

CLI 据此为壳做两件它本来就在为普通依赖做的事：

| 场景 | CLI 行为 |
| --- | --- |
| 壳作为容器运行 | 把这些组件的 `{组件ID前缀}_ENDPOINT` 环境变量注入壳容器（附录 C.2），nginx 反向代理据此配置 |
| 壳 `local: true`（003 §4.4） | 把这些组件的端口映射到宿主机，并写进 `local-debug.<壳的版本化服务名>.env`，供开发服务器代理 |

一个项目里可以有多个 `ui.role: shell` 的组件（PC 壳 + 管理后台壳）。它们共享同一份装配清单，各自决定渲染哪些菜单。

### 2.3 `ui.dir` 的安全约束

`ui.dir` 会被拼进生成的 `package.json` 里成为一个本地路径。它必须老实：

- 必须是相对于**组件仓库根目录**的路径。
- 严禁包含 `..` 路径段。
- 严禁以 `/` 开头，严禁以盘符（`C:\`）开头。

违反任一条 → CLI 输出 `[ERROR]` 并**跳过该组件**（不中断整体流程，其余组件照常装配）。

### 2.4 npm 包契约：两个导出

有界面的组件，其 npm 包必须提供 `./meta` 子路径导出；主入口 `.` 按需提供。

这条规矩的形状照抄 002 §2.3 里已有的那条 ——「闭源组件必须提供 `api-contract` 产物：代码可以闭源，但 API 契约不能闭源」。

| 导出 | 谁消费 | 装什么 | 加载方式 |
| --- | --- | --- | --- |
| `./meta` | **壳** | 菜单声明 + 路由声明 | **静态引入**（必须很小） |
| `.` | **其他组件** | 可复用的 Biz-UI 组件（如 `<CustomerSelector />`） | 按需 |

```js
// @acme/biz-mdm-customer/meta —— 必须存在，必须小
export const menus = [
  { key: 'mdm.customer', title: '客户主数据', path: '/mdm/customer', permission: 'mdm.customer.view' },
];

export const routes = [
  { path: '/mdm/customer',     name: 'mdm-customer-list',   component: () => import('./pages/List.js') },
  { path: '/mdm/customer/:id', name: 'mdm-customer-detail', component: () => import('./pages/Detail.js') },
];
```

**为什么必须拆成两个导出。** 壳要在首屏渲染出完整的左侧菜单，所以菜单声明必须能被静态引入 —— 否则壳就得先把 20 个包的实现代码全下载下来才知道菜单长什么样，懒加载彻底失效。而页面实现藏在 `routes[].component` 的 `() => import()` 里，点到才下载。

**`meta` 里只能放声明，不能放实现。** 它会被无条件打进首屏。

跨组件复用界面则完全不经过 BrickKit —— 那就是一条普通的 npm 依赖：

```json
// erp-sales/frontend/package.json
{ "dependencies": { "@acme/biz-mdm-customer": "1.0.0" } }
```

```js
import { CustomerSelector } from '@acme/biz-mdm-customer';
```

### 2.5 版本恒等

**npm 包的版本必须等于 `metadata.version`。**

一个组件仓库里前后端同仓，一起改、一起发、一起打 tag（002 §1.6）。三个产物 —— Docker 镜像、npm 包、市场上的 Manifest —— 共用同一个版本号：

```
metadata.version = 1.0.0
  → registry.acme.com/mdm-customer:1.0.0
  → @acme/biz-mdm-customer@1.0.0
  → 市场上的 mdm/customer@1.0.0
```

所以生成的清单里不需要、也不允许出现独立的前端版本号。这杜绝了「后端 1.0.1 配了前端 1.0.0 的界面」这类只能在运行时才发现的错配。

CLI **不校验** npm registry 上是否真的存在这个版本 —— 那与「CLI 不校验镜像是否存在」对称。装不上时 `pnpm install` 会报错，而它的报错比 CLI 转述得清楚。

## 3. 生成物

### 3.1 位置与内容

```
my-erp-project/
├── brickkit.yaml
├── .brickkit/
│   ├── manifests/
│   ├── artifacts/
│   └── generated/                 ← CLI 生成物，不进 Git（003 §11）
│       ├── docker-compose.yaml
│       ├── local-debug.infra-web-shell-1-0-0.env
│       └── frontend/              ← 前端装配清单
│           ├── package.json
│           ├── index.js
│           └── index.d.ts
└── components/
```

放在 `generated/` 下是因为它和 `docker-compose.yaml`、`local-debug.env` 是同一类东西：**由 BOM 推导、每次重算、人可审查、不进 Git**。

### 3.2 `package.json`

```json
{
  "name": "@brickkit/assembly-ui",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" },
  "types": "./index.d.ts",
  "dependencies": {
    "@acme/biz-erp-sales": "file:../../../components/erp/sales/frontend",
    "@acme/biz-mdm-customer": "1.0.0"
  }
}
```

两行依赖长得不一样，这正是重点：

- `@acme/biz-mdm-customer` 写版本号 → 从 npm registry 装。
- `@acme/biz-erp-sales` 写 `file:` 路径 → 从本地源码装，**改代码即时生效**。

依赖按组件 ID 字典序排列，保证重复生成的结果逐字节一致，可以放心 diff。

### 3.3 `index.js` 与 `index.d.ts`

```js
// 由 brickkit 生成，请勿手动修改。
// 来源：brickkit.yaml（4 个组件，2 个带界面）
import * as meta_erp_sales from "@acme/biz-erp-sales/meta";
import * as meta_mdm_customer from "@acme/biz-mdm-customer/meta";

export const components = [
  { id: "erp/sales",    version: "1.0.0", pkg: "@acme/biz-erp-sales",    meta: meta_erp_sales },
  { id: "mdm/customer", version: "1.0.0", pkg: "@acme/biz-mdm-customer", meta: meta_mdm_customer },
];
```

```ts
// 由 brickkit 生成，请勿手动修改。
export interface BrickMenu {
  key: string;
  title: string;
  path: string;
  icon?: string;
  permission?: string;
  order?: number;
}

export interface BrickRoute {
  path: string;
  name?: string;
  component: () => Promise<unknown>;
  meta?: Record<string, unknown>;
}

export interface BrickComponentMeta {
  menus?: BrickMenu[];
  routes?: BrickRoute[];
}

export interface BrickComponent {
  id: string;
  version: string;
  pkg: string;
  meta: BrickComponentMeta;
}

export declare const components: BrickComponent[];
```

**为什么要生成这个 `index.js`，光有 `package.json` 不够？** 因为 pnpm 的 node_modules 是严格的：壳只能 import 自己声明过的依赖。壳的 `package.json` 里只有 `@brickkit/assembly-ui` 这一条静态依赖（§4.3），够不到它下面的业务包。所以清单包必须把它们重新导出一次。

这十来行是**数据不是逻辑**。BrickKit 用到的只有 ESM 的 `import` 与 `import()` —— 语言特性，不是框架特性。它不认识 Vue、React 或任何打包器。

### 3.4 本地源码还是 registry 包

判据只有一条：

> **该组件的前端源码目录在活跃工作区里存在 → 走 `file:` 本地链接；否则 → 走 registry 版本号。**

具体检查的是 `components/<scope>/<name>/<ui.dir>/` 存不存在。

这条判据不需要任何新字段，因为「我现在关心哪几个组件」这件事，BrickKit 里早就有专门的表达方式了：

| 你做的事 | 结果 |
| --- | --- |
| `brickkit add erp/sales@1.0.0 --repo` | 源码进活跃工作区 → 前端走本地源码 |
| `brickkit sync`（该组件这次不启动） | 源码进 `components/.archived/` → 前端**整条从清单消失** |
| `brickkit remove erp/sales` | 源码删除 → 清单里也没有了 |
| 从没 clone 过源码 | 走 registry 包 |

判定结果每次都会原样打印出来，不留暗箱：

```
$ brickkit up
📦 前端装配清单已生成：.brickkit/generated/frontend/（3 个界面）
   erp/sales       → 本地源码  components/erp/sales/frontend
   mdm/customer    → registry  @acme/biz-mdm-customer@1.0.0
   infra/iam       → registry  @acme/biz-iam@1.0.0
   已归档，未纳入：crm/lead、hrm/payroll
   💡 清单变化后需在壳工程执行一次 pnpm install
```

### 3.5 何时重新生成

清单不需要专门的命令去刷新。**凡是会改变「这次装配包含哪些组件」的命令，顺手重算一次：**

| 命令 | 为什么它会影响清单 |
| --- | --- |
| `brickkit add` | 组件进来了 |
| `brickkit remove` | 组件出去了 |
| `brickkit sync` | 归档 / 激活改变了源码是否在活跃工作区（§3.4），也改变了启停判定 |
| `brickkit up` | 启停判定在这里发生 |

这四条本来就在维护装配状态 —— `brickkit.yaml` 也是它们在写。手工改了 `brickkit.yaml` 想立刻刷新清单，跑 `brickkit sync`：它本来就是「整理工作区」，前端清单是工作区的一部分。

生成是纯本地文件操作，不联网、不调用任何外部命令，代价可以忽略。

### 3.6 清单只包含"这次会启动的组件"

装配清单用的启停判据，和 `brickkit up` 起哪些容器、`brickkit sync` 留哪些源码，是**同一个判据**（003 §4.3）：

| | 判据 | 结果 |
| --- | --- | --- |
| `brickkit up` | 这次会不会启动 | 起不起容器 |
| `brickkit sync` | 同上 | 源码留在 `components/` 还是收进 `.archived/` |
| 前端装配清单 | 同上 | 界面进不进清单 |

于是一个被归档的组件：**容器不起、源码看不见、界面不在清单里、壳的菜单里没有它、端口也不给它映射。** 四处一致。

这正是本地调试想要的效果 —— `brickkit sync` 就是那个开关，把不关心的组件收起来，眼前只剩要调的那几个。

## 4. 壳组件怎么写

这一章是模板。照着抄，改掉名字就能用。

### 4.1 壳是装配方自己的组件

**壳不是一个可以跨客户复用的通用组件。**

原因很直接：壳镜像里打包的是「本次装配包含的那些界面」，而每个客户装的组件不一样。如果 `infra/web-shell@1.0.0` 这一个版本号在 Acme 和 Beta 手上对应着内容不同的两个镜像，那就违反了"版本即不可变产物"。

所以正确的做法是：**上游提供的是壳的模板仓库，装配方 fork 一份成为自己的组件。**

```
brickkit/web-shell-template   （上游模板，不发市场）
        │  fork
        ▼
acme/acme-erp-shell           （Acme 自己的组件仓库）
        │  改 logo、改主题、make build
        ▼
registry.acme.com/acme-erp-shell:1.0.0
```

Acme 的壳就是一个**再普通不过的 BrickKit 组件**：自己的仓库、自己的 `component.yaml`、自己构建的镜像、自己的版本节奏。平台不需要为它加任何特殊分支。

### 4.2 目录结构

```
acme-erp-shell/
├── component.yaml
├── Makefile
├── Dockerfile
├── scripts/
│   └── gen-nginx-conf.mjs        # 从装配清单生成 nginx location 块
└── frontend/
    ├── package.json
    ├── vite.config.ts
    ├── index.html
    └── src/
        ├── main.ts
        ├── App.vue
        └── router.ts
```

### 4.3 `package.json`：那一行静态依赖

```json
{
  "name": "acme-erp-shell",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  },
  "dependencies": {
    "@brickkit/assembly-ui": "file:../../../../.brickkit/generated/frontend",
    "vue": "^3.4.0",
    "vue-router": "^4.3.0"
  },
  "devDependencies": {
    "@vitejs/plugin-vue": "^5.0.0",
    "dotenv": "^16.4.0",
    "vite": "^5.2.0"
  }
}
```

**只有 `@brickkit/assembly-ui` 这一行和 BrickKit 有关，而它永远不变。**

业务组件的界面包一个都不出现在这里 —— 它们躺在生成的清单里，由 `@brickkit/assembly-ui` 传递进来。BOM 改了，这个文件一个字都不用动。

那串 `../../../../` 是从 `components/<scope>/<name>/frontend/` 数到项目根：`frontend` → `web-shell` → `infra` → `components` → 项目根。壳放在别的深度就相应调整，写一次，之后再不动。

### 4.4 消费装配清单：路由与菜单

```ts
// src/router.ts
import { createRouter, createWebHistory, type RouteRecordRaw } from 'vue-router';
import { components } from '@brickkit/assembly-ui';

// 所有组件的路由，一把摊平
const bizRoutes: RouteRecordRaw[] = components.flatMap(
  (c) => (c.meta.routes ?? []) as RouteRecordRaw[],
);

// 所有组件的菜单，按 order 排序（没写 order 的排在后面）
export const menus = components
  .flatMap((c) => c.meta.menus ?? [])
  .sort((a, b) => (a.order ?? 999) - (b.order ?? 999));

export const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/', redirect: menus[0]?.path ?? '/blank' },
    ...bizRoutes,
    { path: '/:pathMatch(.*)*', component: () => import('./NotFound.vue') },
  ],
});
```

```vue
<!-- src/App.vue -->
<script setup lang="ts">
import { menus } from './router';
</script>

<template>
  <div class="layout">
    <aside>
      <RouterLink v-for="m in menus" :key="m.key" :to="m.path">{{ m.title }}</RouterLink>
    </aside>
    <main><RouterView /></main>
  </div>
</template>
```

**壳的代码里没有任何一个业务组件的名字。** 装了什么就长出什么菜单，卸了就没了。

菜单的权限过滤（按 JWT claims 隐藏无权限的菜单项）是壳自己的业务，不在本规范范围内 —— 但要记住隐藏菜单不等于安全，鉴权必须由后端组件做（008）。

### 4.5 `vite.config.ts`：开发时后端地址从哪来

开发服务器跑在宿主机上，后端组件跑在 Docker 里。两者之间的地址翻译，BrickKit 已经做好了：给壳写上 `local: true`，`brickkit up` 就会把壳需要的组件端口映射到宿主机，并生成一份 env 文件（003 §4.4）。

```
# .brickkit/generated/local-debug.infra-web-shell-1-0-0.env
COMPONENT_ID=infra/web-shell
COMPONENT_VERSION=1.0.0
MDM_CUSTOMER_ENDPOINT=http://localhost:18080
ERP_SALES_ENDPOINT=http://localhost:18081
```

壳把这份文件读进来配代理即可：

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import dotenv from 'dotenv';
import { components } from './node_modules/@brickkit/assembly-ui/index.js';

// BrickKit 在 up 时生成；文件名 = local-debug.<壳的版本化服务名>.env
const env = dotenv.config({
  path: '../../../../.brickkit/generated/local-debug.infra-web-shell-1-0-0.env',
}).parsed ?? {};

// 组件 ID → 环境变量前缀：erp/sales → ERP_SALES（附录 C.2）
const envPrefix = (id: string) => id.replace(/[/-]/g, '_').toUpperCase();

// /api/<scope>/<name>/** → 该组件
const proxy = Object.fromEntries(
  components.map((c) => [
    `/api/${c.id}`,
    {
      target: env[`${envPrefix(c.id)}_ENDPOINT`],
      changeOrigin: true,
      rewrite: (p: string) => p.replace(`/api/${c.id}`, ''),
    },
  ]),
);

export default defineConfig({
  plugins: [vue()],
  // 关键：业务包与壳必须共用同一个 Vue 实例，否则 provide/inject、
  // pinia、全局指令全部失效，而且报错很难懂
  resolve: { dedupe: ['vue', 'vue-router'] },
  server: { port: 5173, proxy },
});
```

`resolve.dedupe` 那一行是踩过的坑：清单包和壳各自装一份 Vue 的话，页面能渲染出来，但跨组件的响应式状态莫名其妙地断掉。

### 4.6 Dockerfile 与 nginx

生产环境里壳是个 nginx 容器，反向代理到内网 DNS 地址（002 §4.3）。

`location` 块开多少个取决于装了哪些组件 —— **构建时才知道**；每个块代理到哪 —— **容器启动时由环境变量给出**（005 §4.4）。所以分两步：构建时生成带占位符的模板，启动时 envsubst 填值。

```js
// scripts/gen-nginx-conf.mjs —— 构建时执行
import { writeFileSync } from 'node:fs';
import { components } from '../frontend/node_modules/@brickkit/assembly-ui/index.js';

const envPrefix = (id) => id.replace(/[/-]/g, '_').toUpperCase();

const locations = components
  .map(
    (c) => `
  location /api/${c.id}/ {
    proxy_pass \${${envPrefix(c.id)}_ENDPOINT}/;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
  }`,
  )
  .join('\n');

writeFileSync(
  'dist-conf/default.conf.template',
  `server {
  listen 80;
  root /usr/share/nginx/html;
${locations}

  # SPA history 模式
  location / {
    try_files $uri $uri/ /index.html;
  }

  # 带 hash 的静态资源可以长缓存，index.html 绝对不行
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }
  location = /index.html {
    add_header Cache-Control "no-cache";
  }
}
`,
);
```

```dockerfile
# ---- 构建 ----
FROM node:20-alpine AS build
WORKDIR /app

# 装配清单必须先进来：壳的依赖里有 file:../../../../.brickkit/generated/frontend
COPY .brickkit/generated/frontend/ /.brickkit/generated/frontend/
COPY components/infra/web-shell/ /app/

# 本地源码链接的组件也要一起进来（走 registry 的不用，pnpm 自己下）
COPY components/ /components/

WORKDIR /app/frontend
RUN corepack enable && pnpm install --frozen-lockfile && pnpm build
WORKDIR /app
RUN mkdir -p dist-conf && node scripts/gen-nginx-conf.mjs

# ---- 运行 ----
FROM nginx:alpine
COPY --from=build /app/frontend/dist /usr/share/nginx/html
# nginx 官方镜像会对 /etc/nginx/templates/*.template 做 envsubst 后放进 conf.d
COPY --from=build /app/dist-conf/default.conf.template /etc/nginx/templates/
EXPOSE 80
```

⚠️ **构建上下文是项目根目录，不是壳目录。** 因为壳的依赖要够到项目根下的 `.brickkit/generated/frontend/`。`Makefile` 里体现为 `-f` 与上下文分开写。

### 4.7 `Makefile`

BrickKit 不执行这里的任何一条命令。这是壳自己的构建脚本，和后端组件的 `Makefile` 地位完全相同。

```makefile
IMAGE ?= registry.acme.com/acme-erp-shell
TAG   ?= 1.0.0
ROOT  ?= ../..          # 项目根（本组件位于 components/infra/web-shell/）

.PHONY: install dev build push

# 装配清单变了之后跑一次
install:
	cd frontend && pnpm install

# 本地调试：先 brickkit up（壳需 local: true）
dev: install
	cd frontend && pnpm dev

# 构建镜像。上下文是项目根，因为要带上 .brickkit/generated/frontend/
build:
	docker build -f Dockerfile -t $(IMAGE):$(TAG) $(ROOT)

push: build
	docker push $(IMAGE):$(TAG)
```

### 4.8 壳容器拿到哪些环境变量

壳没有声明 `dependencies`，但它照样拿得到地址 —— CLI 按 §2.2 的规则，把本次会启动的、带 `ui.package` 的组件全集当作壳的依赖来注入：

```yaml
# CLI 生成的 docker-compose.yaml 片段
infra-web-shell-1-0-0:
  image: registry.acme.com/acme-erp-shell:1.0.0
  ports: ["80:80"]
  environment:
    COMPONENT_ID: infra/web-shell
    COMPONENT_VERSION: 1.0.0
    MDM_CUSTOMER_ENDPOINT: http://mdm-customer-1-0-0:8080
    ERP_SALES_ENDPOINT: http://erp-sales-1-0-0:8080
```

这些变量和普通依赖注入走的是同一套机制、同一套命名规则、同一套保留变量保护（008）。壳这边唯一特别的是**这份依赖名单是算出来的，不是写出来的**。

### 4.9 推荐做法：包既能发布又能热更新

一个界面包有两种被消费的方式，理想的产物不一样：

| 消费方式 | 想要的产物 | 为什么 |
| --- | --- | --- |
| 从 registry 装（`"1.0.0"`） | 已构建的 ESM | 消费方的打包器不必编译 `.vue` 之类的源文件 |
| 从本地链接装（`file:`） | 源码 | 改一行就热更新，构建一次就没了 |

用 `exports` 的条件解析可以同时满足：

```json
{
  "name": "@acme/biz-mdm-customer",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".":      { "source": "./src/index.ts", "default": "./dist/index.js" },
    "./meta": { "source": "./src/meta.ts",  "default": "./dist/meta.js" }
  },
  "peerDependencies": { "vue": "^3.4.0" }
}
```

壳只在开发模式下打开 `source` 条件：

```ts
export default defineConfig(({ mode }) => ({
  resolve: {
    conditions: mode === 'development' ? ['source', 'import', 'module', 'browser', 'default'] : undefined,
    dedupe: ['vue', 'vue-router'],
  },
}));
```

**这是推荐做法，不是规范强制。** 本规范只强制一条：包必须导出 `./meta`（§2.4）。怎么组织构建，是组件与壳的前端工程问题，BrickKit 不参与。

## 5. 三种运行方式

### 5.1 部署运行：一条 `brickkit up`

前提：所有镜像和 npm 包都已经在各自的 registry 里，壳镜像已由装配方构建并推送。

```bash
brickkit up
```

完。

**部署机上不需要 Node，不需要碰 npm。** 壳镜像和别的镜像一样是拉下来的 —— 完全是 Docker 模型：部署者拉镜像，不构建镜像。

这一步里那份前端装配清单其实用不上（界面已经烤进壳镜像了），CLI 照样会生成它，因为代价是两个小文件，而永远保持最新比"有时是旧的"省心。

### 5.2 本地 Docker 运行（装配方出货前的自检）

装配方比部署者多干一件事：把壳镜像做出来。

```bash
brickkit init acme-erp
brickkit add infra/iam@1.0.0
brickkit add erp/sales@1.0.0                 # 递归带出 mdm/customer
brickkit add infra/web-shell@1.0.0 --repo    # 壳需要源码才能构建

# 装配清单已由 add 生成，现在构建壳镜像 —— 全部手动，BrickKit 不参与
cd components/infra/web-shell
make push

brickkit up          # → http://localhost
```

BOM 一变（加组件、升版本），重跑 `make push` 再 `brickkit up`。这和"加组件要重新生成 `docker-compose.yaml`"是同一件事。

### 5.3 本地 debug

目标：后端跑在容器里，壳跑在开发服务器上，改前端代码即时生效。

**第一步：把不关心的组件收起来。**

```yaml
# brickkit.yaml
components:
  - id: crm/lead
    version: 1.0.0
    enabled: false        # 这次不调它
```

```bash
brickkit sync
   📦 已归档：crm/lead → components/.archived/crm/lead
   📦 前端装配清单已更新（2 个界面，crm/lead 已移出）
```

眼前和清单里都只剩要调的那几个。

**第二步：把壳交给自己。**

```yaml
  - id: infra/web-shell
    version: 1.0.0
    local: true           # 平台别起它的容器，我自己跑
```

```bash
brickkit up
   ✅ 后端容器已启动（不含 infra/web-shell）
   🔌 已为 infra/web-shell 映射依赖端口：
      mdm/customer → localhost:18080
      erp/sales    → localhost:18081
   📄 已生成 .brickkit/generated/local-debug.infra-web-shell-1-0-0.env
   📦 前端装配清单已生成（2 个界面）
      erp/sales    → 本地源码  components/erp/sales/frontend
      mdm/customer → registry  @acme/biz-mdm-customer@1.0.0
```

**第三步：起开发服务器。全是你自己的包管理器。**

```bash
cd components/infra/web-shell/frontend
pnpm install          # 照着装配清单装
pnpm dev              # → http://localhost:5173
```

改 `components/erp/sales/frontend/` 下的任何文件 → 浏览器立刻更新。改 `mdm/customer` 的界面？给它也 clone 一份源码：

```bash
brickkit add mdm/customer@1.0.0 --repo   # 清单里那一条自动从版本号变成 file:
cd components/infra/web-shell/frontend && pnpm install
```

⚠️ `local: true` 只能配 `deploy.target: docker`（003 §4.4）—— K8s 集群里的 Pod 连不到你的笔记本。

### 5.4 三种方式对照

| | 部署者 | 装配方 | 组件开发者 |
| --- | --- | --- | --- |
| 机器上要有 | docker 或 kubectl | + Node、包管理器 | + Node、包管理器 |
| BrickKit 命令 | `up` | `add` → `up` | `sync` → `up` |
| 手动命令 | 无 | `make push`（壳） | `pnpm install` / `pnpm dev` |
| 壳怎么跑 | 容器（拉镜像） | 容器（本地构建的镜像） | 开发服务器（`local: true`） |

### 5.5 K8s 运行

和 Docker 完全一样，只改 `deploy.target`：

```yaml
deploy:
  target: k8s
  namespace: acme-prod
```

```bash
cd components/infra/web-shell && make push    # 镜像必须推到集群拉得到的仓库
brickkit up
```

壳在 K8s 下是个再普通不过的 Deployment + Service + Ingress（005 §5）。前端装配这件事在 K8s 下**没有任何特殊处理** —— 它发生在构建期，而构建期早就结束了。

⚠️ 壳需要 `expose: true` + `hostname`（003 §4.5），否则集群外访问不到。

## 6. 多端

### 6.1 第二个壳

多写一个 `ui.role: shell` 的组件即可。两个壳共享同一份装配清单，各自决定渲染哪些菜单：

```ts
// 管理后台壳只要 infra 域的界面
const admin = components.filter((c) => c.id.startsWith('infra/'));
```

两个壳在 Docker 下要各自的 `exposePort`，在 K8s 下要各自的 `hostname`（003 §4.5）。

### 6.2 移动端

移动端 App 不是容器，**因此它不是 BrickKit 组件**，不写进 `brickkit.yaml`，也不由 `brickkit up` 部署。它是装配仓库旁边的一个独立前端工程。

但它照样能消费同一份装配清单：

```json
// acme-erp-mobile/package.json
{ "dependencies": { "@brickkit/assembly-ui": "file:../acme-erp/.brickkit/generated/frontend" } }
```

```ts
// 同一份清单，移动端自己决定怎么渲染
import { components } from '@brickkit/assembly-ui';
```

**逻辑共享、视图分离**：菜单声明、路由声明、数据接口从同一份清单来；界面布局 PC 与移动端各写各的。

移动端只能走构建期装配 —— 编译进 App 包里的代码不可能在运行时去远程加载模块。这也正是本规范选择构建期聚合、而不是运行时模块联邦的决定性理由（§9 决策 3）。

### 7.4 测试用例

分两组。**A 组只看生成的文件，不需要 Node、不需要 registry、跑得飞快**，覆盖绝大多数判定逻辑；**B 组是端到端**，证明这套东西真能跑起来。

#### A 组：装配清单的生成（无外部依赖）

**A1 · 基础装配**

```bash
brickkit init brick-ui-test && brickkit add --local
```

断言 `.brickkit/generated/frontend/package.json`：

```json
{
  "name": "@brickkit/assembly-ui",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" },
  "types": "./index.d.ts",
  "dependencies": {
    "@demo/biz-hello": "file:../../../components/demo/hello/frontend",
    "@demo/biz-world": "file:../../../components/demo/world/frontend"
  }
}
```

要点：① `demo/quiet` 没有 `ui` 块，一个字都不出现；② `demo/shell` 是消费方不是包，不出现；③ 两个都走 `file:`，因为本地安装源下源码本来就在活跃工作区；④ 依赖按组件 ID 字典序排列。

断言 `index.js`：

```js
import * as meta_demo_hello from "@demo/biz-hello/meta";
import * as meta_demo_world from "@demo/biz-world/meta";

export const components = [
  { id: "demo/hello", version: "1.0.0", pkg: "@demo/biz-hello", meta: meta_demo_hello },
  { id: "demo/world", version: "1.0.0", pkg: "@demo/biz-world", meta: meta_demo_world },
];
```

**A2 · 幂等**

再跑一次 `brickkit sync`，两个文件逐字节不变。

**A3 · 归档收缩**

给 `demo/world` 写 `enabled: false`，`brickkit sync`。

断言：① `components/.archived/demo/world/` 出现；② 清单里只剩 `@demo/biz-hello`；③ `index.js` 里只剩一条 import；④ 输出里有一行 `已归档，未纳入：demo/world`。

**A4 · 归档恢复**

删掉 `enabled: false`，`brickkit sync`。清单回到 A1 的状态，逐字节一致。

**A5 · 从本地源码切回 registry**

把 `demo/hello` 的源码目录移出活跃工作区（模拟"只装了包，没 clone 源码"），`brickkit sync`。

断言：`"@demo/biz-hello": "1.0.0"` —— 从 `file:` 路径变成版本号。

**A6 · 一个界面都没有**

把 `demo/hello`、`demo/world` 都 `enabled: false`，`brickkit sync`。

断言：清单文件照常生成，`dependencies` 为 `{}`，`index.js` 里 `components` 为空数组。**不报错** —— 壳装了个空清单，只是没有菜单可渲染。

**A7 · 完全没有壳**

把 `demo/shell` 移出 `brickkit.yaml`。

断言：清单照常生成（它不依赖壳的存在），**不报错也不警告**。谁来消费这份清单不是 BrickKit 的事（移动端就是个例子，§6.2）。

**A8 · `ui.dir` 指向不存在的目录**

把 `demo/hello` 的 `ui.dir` 改成 `frontend-typo`。

断言：`[WARN] demo/hello 声明了 ui.dir 'frontend-typo'，但目录不存在，本次按 registry 包处理`，清单里该条为 `"1.0.0"`。不中断。

**A9 · 路径穿越防护**

把 `ui.dir` 改成 `../../../etc`。

断言：`[ERROR] demo/hello: ui.dir 不得包含 '..' 路径段，已跳过该组件`，清单里没有它，其余组件照常处理，退出码 0。

**A10 · 绝对路径防护**

`ui.dir: /usr/local/src`，断言同 A9，文案为「必须是相对路径」。

**A11 · 缺 `ui.package`**

写了 `ui.dir` 却没写 `ui.package`（且不是 `role: shell`）。

断言：`[ERROR] demo/hello: 声明了 ui 块但缺少 ui.package`，退出码 1 —— 这是 `component.yaml` 写错了，属于组件规范校验，当场拦下（002 §2.2.1）。

**A12 · 版本升级**

新增 `components/demo/hello@1.1.0`，改 `brickkit.yaml` 的版本号，`brickkit sync`。

断言：`index.js` 里 `version` 变成 `"1.1.0"`；若走 registry，依赖值同步变成 `"1.1.0"`。

**A13 · 多版本共存**

`demo/hello` 同时装 1.0.0 与 2.0.0（003 §4.8）。

断言：**报错**。`[ERROR] demo/hello 的两个版本都声明了 ui.package @demo/biz-hello，同一份清单里无法共存`，并提示给其中一个写 `enabled: false`。理由见 §9 决策 6。

**A14 · 多个壳**

再加一个 `demo/admin-shell`（`ui.role: shell`）。

断言：清单只有一份，内容与 A1 完全相同。两个壳共享它。

**B4 · registry 路径**

```bash

npm --registry http://localhost:4873 publish       # 在两个 frontend/ 目录下各跑一次
```

把两个组件的源码移出活跃工作区，`brickkit sync` → 清单变成版本号形式 → `pnpm install --registry http://localhost:4873` → `pnpm dev`，页面表现与 B1 完全一致。

## 8. 异常处理汇总

| 场景 | 行为 | 退出码 |
| --- | --- | --- |
| 组件没有 `ui` 块 | 静默跳过，无输出 | 0 |
| 组件这次不启动（`enabled: false` / 已归档） | 不进清单，摘要里列一行"已归档，未纳入" | 0 |
| `ui.dir` 指向的目录不存在 | `[WARN]`，本次按 registry 包处理 | 0 |
| `ui.dir` 含 `..` 或为绝对路径 | `[ERROR]`，跳过该组件，其余照常 | 0 |
| 写了 `ui` 块但缺 `ui.package`，且不是 `role: shell` | `[ERROR]`，当场拦下（002 §2.2.1） | 1 |
| `ui.role` 是 `shell` 以外的值 | `[ERROR]`，当场拦下 | 1 |
| 同一组件的多个版本都声明了 `ui.package` | `[ERROR]`，提示禁用其中一个（§9 决策 6） | 1 |
| 两个不同组件声明了同一个 `ui.package` | `[ERROR]`，包名必须唯一 | 1 |
| 本次一个带界面的组件都没有 | 照常生成空清单，不报错 | 0 |
| 项目里没有 `ui.role: shell` 的组件 | 照常生成清单，不报错也不警告 | 0 |
| `.brickkit/generated/frontend/` 写不进去（权限等） | `[ERROR]`，终止 | 1 |
| npm registry 上没有那个包 / 没有那个版本 | **BrickKit 不检测**。`pnpm install` 会报，且报得比转述清楚 | — |
| 壳源码不在活跃工作区 | **BrickKit 不检测**。它不构建壳，构建是使用者的事 | — |

## 9. 决策记录

| # | 决策 | 为什么 | 避免的坑 |
| --- | --- | --- | --- |
| 1 | 前端走 npm registry，与后端走 Docker registry 对称 | 同一套心智：产物、仓库、认证、构建各就各位 | 另造一套分发通道，最后发现它就是个功能更差的 npm |
| 2 | CLI 不生成 `.npmrc`、不碰 Token | 与「不自动 docker login」严格对称（004 §2.2） | 平台变成凭据管家；下一个来问"那 helm repo / pip index-url 呢"时没有立场 |
| 3 | 构建期聚合，不做运行时模块联邦 | 移动端 App 不可能在运行时远程加载模块，构建期聚合**必须存在**；再加一套运行时模型就是养两套心智、两套调试链路 | 为 PC 端单独造一套运行时组合，两个端行为不一致 |
| 4 | CLI 不执行任何前端命令 | 与「不做数据库迁移工具：只执行命令，不管工具的选择和逻辑」同源 | 平台被拖进前端工具链，还得替使用者决定用 npm 还是 pnpm |
| 5 | CLI 只写 `.brickkit/generated/` 下自己的目录 | 不碰用户手写文件，就不存在"写重了""覆盖了用户配置""并发写坏了"三类问题 | 去 `pnpm-workspace.yaml` 里插标记块，随后被迫补三章边界情况 |
| 6 | 同一组件多版本共存时，前端装配报错 | 后端多版本共存靠**版本化服务名**隔离（002 §5.3），而 npm 的 `dependencies` 一个包名只能有一个版本，没有对应的隔离手段 | 悄悄取其中一个版本，界面与后端错配，且只在运行时暴露 |
| 7 | npm 包版本恒等于 `metadata.version` | 前后端同仓、一起发（002 §1.6），三个产物共用一个版本号 | 独立的前端版本号 → "后端 1.0.1 配前端 1.0.0" |
| 8 | 界面包必须拆出 `./meta` 子路径导出 | 壳要在首屏渲染完整菜单；菜单声明不能藏在懒加载后面 | 壳被迫先下载全部实现代码才知道菜单长什么样，懒加载失效 |
| 9 | 壳的依赖集由装配算出，不由 `dependencies` 声明 | 壳一旦声明业务依赖，版本就被它装的每个组件绑架 | 加一个组件就得发一版壳 |
| 10 | 壳是装配方自己的组件，不是通用组件 | 壳镜像的内容取决于 BOM，同一个版本号在不同客户手上内容不同 | 违反"版本即不可变产物"；或者被迫给平台加"本地构建镜像"这一整类特殊分支 |
| 11 | 清单由 `add`/`remove`/`sync`/`up` 顺手生成，不给新命令 | 这四条本来就在维护装配状态，`brickkit.yaml` 也是它们写的 | 多一条使用者必须记住、且忘了就出错的命令 |
| 12 | 本地源码还是 registry，只看源码在不在活跃工作区 | `sync` / `--repo` 已经把"我现在关心哪几个组件"表达清楚了 | 再加一个字段，与 `sync` 各说各话，两处对不上时以谁为准 |
| 13 | 清单的启停判据与 `up` / `sync` 完全一致 | 容器、源码、界面、端口映射四处同进同退 | 归档了组件，菜单里却还挂着一个点开就 502 的入口 |
| 14 | 移动端工程不是 BrickKit 组件 | App 不是容器（001），也没有"部署"这一步 | 为了容纳它，给平台开一个"非容器组件"的口子 |
| 15 | CLI 不校验 npm 包是否存在 | 与「不校验镜像是否存在」对称；包管理器的报错比转述清楚 | 平台需要 npm 客户端和网络，才能给出一句更差的错误 |
