## 1. 这份文档解决什么问题

### 1.1 一个组件带前端，麻烦在哪

BrickKit 里前端组件早就不是新鲜事：它是一个跑着 nginx 的普通 container，和后端组件在平台眼里没有区别（012 §2.10）。一个前端组件配一个后端组件，今天就能跑。

麻烦出在多上。

当你要拼的是一整套 ERP —— `mdm/customer`、`erp/sales`、`erp/purchase`、`erp/inventory`…… 每个组件都带自己的界面，而最终用户要看到的是一个产品：一套左侧菜单、一次登录、一个域名。这时按"一个前端组件一个 nginx 容器"来做，会得到 20 个互不相干的网站。

要把它们并成一个，前端只有一条路：这些界面得被同一次打包收进同一个产物。而一旦涉及打包，就冒出一串组件开发者不该操心的问题：

- 20 个组件的界面代码，怎么到达打包的那台机器？
- 装了哪些组件、每个什么版本，打包的时候怎么知道？
- 今天我只想调 `erp/sales`，另外 19 个的界面能不能别出现在我眼前？
- 部署的人手上只有 docker，他要不要装 Node？

### 1.2 答案：前端和后端是同一套模型

把后端那套已经跑通的东西照着镜子看一遍，答案是现成的：

|  | 后端 | 前端 |
| --- | --- | --- |
| 产物是什么 | Docker 镜像 | npm 包 |
| 放在哪 | Docker registry | npm registry |
| 谁装的工具 | 用户装 docker | 用户装 npm / pnpm / yarn |
| 认证谁做 | 用户 `docker login` | 用户 `npm login` |
| 谁构建 | 组件的 `Makefile`，手动 | 组件的 `Makefile`，手动 |
| BrickKit 做什么 | 解析依赖 → 翻译成 compose / K8s 清单 + 注入地址 | 解析依赖 → 翻译成一份包清单 |

BrickKit 从来不替后端组件跑 `go build`，也不替它跑 `docker build`。同理它不替前端跑 `pnpm install`，不替壳应用跑 `vite build`。

它只做一件后端那边也在做、而且只有它做得了的事：把「这次装配包含哪些组件」翻译成一份机器可读的清单。

后端那份清单叫 `docker-compose.yaml`，前端这份叫 `package.json`。

### 1.3 BrickKit 在这件事里只做一件事

读 BOM，生成一份前端依赖清单。

清单里写着：这次装配包含哪些带界面的组件、每个是什么版本、哪些正在被本地改动。

然后你用自己的包管理器照着清单装。`brickkit add` 让清单多一条，`brickkit sync` 让清单少一条 —— 加载和卸载由 pnpm 执行，清单由 BrickKit 维护。和「compose 文件由 CLI 生成、镜像由 docker 拉」是同一件事。

为此新增的东西：`component.yaml` 一个 `ui` 块，外加 CLI 顺手多生成两个文件。没有新命令。

### 1.4 边界（三不做）

| 不做 | 原因 |
| --- | --- |
| 不执行任何前端命令（`npm install` / `pnpm build` / `vite`） | 与「不做数据库迁移工具」同源：CLI 只生成清单，不管工具的选择和逻辑（004 §2.2）。用 npm 还是 pnpm 还是 yarn 是使用者的选择 |
| 不管 npm registry 的认证 | 与「不自动 docker login」严格对称（004 §2.2）。用户自己 `npm login`，CLI 不生成 `.npmrc`、不碰 Token、不在 `brickkit.yaml` 里存凭据 |
| 不改用户手写的任何文件 | CLI 只写 `.brickkit/generated/` 下自己的目录。不做 `pnpm-workspace.yaml` 文本手术，不需要标记块，不需要幂等性特判 |

第三条值得多说一句。让 CLI 去用户的 `pnpm-workspace.yaml` 里插一段带标记的内容，会立刻长出三个必须回答的问题：重复执行会不会写重、用户手写在标记外的配置保不保得住、两个终端同时跑会不会写坏。换成"CLI 只写自己的目录"，这三个问题一个都不存在。

### 1.5 聚合不是唯一的路

本文档很容易被读成"BrickKit 的前端方案改了"。没有。**它加了一条路，没有拿走原来那条。**

| | 路 A：各自成站 | 路 B：装配聚合 |
| --- | --- | --- |
| 怎么声明 | **不写 `ui` 块** | 写 `ui` 块 |
| 前端是什么 | 一个跑 nginx 的普通组件，自己打包自己的完整站点 | 一个 npm 界面包，交给壳去打包 |
| 怎么访问 | 各自 `expose`，各自一个域名 / 宿主机端口（003 §4.5） | 一个域名，一套菜单，路径路由 |
| 框架 | **完全自由**。这个组件用 Vue，那个用 React，再一个用 htmx，互不相干 | 装配内必须统一（§10 决策 16） |
| 平台改动 | 零。这是 012 §2.10 一直以来的模型 | 本文档 |

**判据只有一句：终端用户该看到几个产品？**

- 几个互不相干的工具，各有各的用户和入口 → 路 A。语言与框架无关这条承诺在这里**完整成立**，一个字都没打折。
- 一整套 ERP，一套左侧菜单、一次登录、一个域名 → 路 B。

**框架统一不是平台强加的，是"合成一个产品"这个需求自带的。** 壳只有一个渲染器 —— Vue 的壳渲染不了 React 的页面，这是浏览器的物理现实，换任何平台都一样。不想付这个代价，路 A 一直在那儿。

而且这个代价在真实场景里几乎不产生：**一个项目通常就一个前端**（拼装好的那一个）。既然是一个前端，它当然是一种框架写的。

所以市场上一个组件可以同时发两样东西 —— 镜像（任何语言都行）和界面包（某个框架）。拿到它的人如果框架对不上，走路 A 自己写一个界面，调的还是同一套 API 契约。**组件的通用性落在镜像和契约上，从来不在界面上。**

## 2. 契约：`component.yaml` 的 `ui` 块

`ui` 是可选块。不写的组件就是纯后端组件，前端装配完全绕开它，不产生任何输出。

### 2.1 业务组件

```yaml
apiVersion: brickkit/v1
kind: Component
metadata:
  id: mdm/customer
  name: 客户主数据
  version: 3.2.0                       # 组件版本，跟着后端走
  vendor: acme
deployment:
  type: container
  image: registry.acme.com/mdm-customer:3.2.0
  port: 8080
healthCheck:
  type: http
  path: /healthz
# ===== 前端装配声明 =====
ui:
  package: "@acme/biz-mdm-customer"   # npm 包名
  version: 1.4.0                       # 该包的精确版本，与组件版本各走各的（§2.5）
  dir: frontend                        # 前端工程在本仓库内的相对路径
```

| 字段 | 类型 | 必须 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| ui.package | string | 业务组件必须 | — | 该组件界面对应的 npm 包名 |
| ui.version | string | 写了 `ui.package` 就必须 | — | 该 npm 包的**精确**版本，与 `metadata.version` 各走各的（§2.5）。不接受 `^` / `~` / `latest` |
| ui.dir | string | 否 | — | 前端工程在组件仓库内的相对路径。源码在活跃工作区时用它建本地链接（§3.4）。不写则该组件永远走 registry 包 |
| ui.role | string | 否 | — | 只有一个合法值 `shell`。见 §2.2 |

实现备注：`ui` 块落地到 `internal/manifest` 之后，请给上表补一条字段表注解（写法照抄 003 里那些 HTML 注释），并把新结构体加进 `tests/docfields` 的 `fieldTableTypes`。这样 `make check-doc-fields` 才会盯住这张表 —— 否则字段改了名，文档不会有人提醒。

### 2.2 壳组件

壳是把各组件界面装到一起的那个容器。它不声明 `ui.package` —— 它不是被装的包，它是装包的地方。

```yaml
metadata:
  id: infra/web-shell
  name: PC 壳应用
  version: 1.0.0
deployment:
  type: container
  image: registry.acme.com/acme-erp-shell:1.0.0   # 装配方自己构建、自己推的镜像
  port: 80
healthCheck:
  type: http
  path: /
ui:
  role: shell
```

`ui.role: shell` 只有一个作用，但这个作用不可替代：告诉 CLI「这个组件要能访问到本次装配里所有带界面的组件」。

壳不能用 `dependencies` 声明这件事 —— 那样壳的版本就会被它装的每一个业务组件绑架，加一个组件就得发一版壳。所以：

**壳的依赖集不是声明出来的，是装配算出来的：本次会启动的、声明了 `ui.package` 的组件全集。**

CLI 据此为壳做两件它本来就在为普通依赖做的事：

| 场景 | CLI 行为 |
| --- | --- |
| 壳作为容器运行 | 把这些组件的 `{组件ID前缀}_ENDPOINT` 环境变量注入壳容器（附录 C.2），nginx 反向代理据此配置 |
| 壳 `local: true`（003 §4.4） | 把这些组件的端口映射到宿主机，并写进 `local-debug.<壳的版本化服务名>.env`，供开发服务器代理 |

一个项目里可以有多个 `ui.role: shell` 的组件（PC 壳 + 管理后台壳）。它们共享同一份装配清单，各自决定渲染哪些菜单。

### 2.3 `ui.dir` 的安全约束

`ui.dir` 会被拼进生成的 `package.json` 里成为一个本地路径。它必须老实：

- 必须是相对于组件仓库根目录的路径。
- 严禁包含 `..` 路径段。
- 严禁以 `/` 开头，严禁以盘符（`C:\`）开头。

违反任一条 → CLI 输出 `[ERROR]` 并跳过该组件（不中断整体流程，其余组件照常装配）。

### 2.4 npm 包契约：两个导出

有界面的组件，其 npm 包必须提供 `./meta` 子路径导出；主入口 `.` 按需提供。

这条规矩的形状照抄 002 §2.3 里已有的那条 ——「闭源组件必须提供 `api-contract` 产物：代码可以闭源，但 API 契约不能闭源」。

| 导出 | 谁消费 | 装什么 | 加载方式 |
| --- | --- | --- | --- |
| `./meta` | 壳 | 菜单声明 + 路由声明 | 静态引入（必须很小） |
| `.` | 其他组件 | 可复用的 Biz-UI 组件（如 `<CustomerSelector />`） | 按需 |

```js
// @acme/biz-mdm-customer/meta —— 必须存在，必须小
export const menus = [
  { key: 'mdm.customer', title: '客户主数据', path: '/mdm/customer', permission: 'mdm.customer.view' },
];
export const routes = [
  { path: '/mdm/customer',     name: 'mdm-customer-list',   component: () => import('./pages/List.js') },
  { path: '/mdm/customer/:id', name: 'mdm-customer-detail', component: () => import('./pages/Detail.js') },
];
```

**为什么必须拆成两个导出。** 壳要在首屏渲染出完整的左侧菜单，所以菜单声明必须能被静态引入 —— 否则壳就得先把 20 个包的实现代码全下载下来才知道菜单长什么样，懒加载彻底失效。而页面实现藏在 `routes[].component` 的 `() => import()` 里，点到才下载。

**`meta` 里只能放声明，不能放实现。** 它会被无条件打进首屏。

建议：装配方在组件 CI 中为 meta 产物加一道体积门禁（如 gzip 后 < 8 KB），防止有人把实现偷偷塞进首屏。这是推荐做法，不是平台强制（与 §4.9 同性质）。

### 2.4.1 跨组件复用界面：两条约束

复用别的组件的 Biz-UI 不经过 BrickKit —— 那就是一条普通的 npm 依赖：

```js
import { CustomerSelector } from '@acme/biz-mdm-customer';
```

但有两条约束，少一条就会把 §2.6「一个装配一份界面」变成一句空话。

**① 必须写成 `peerDependencies`，不能写成 `dependencies`。**

```json
// erp-sales/frontend/package.json
{
  "peerDependencies": { "@acme/biz-mdm-customer": ">=1.4.0" }
}
```

写成 `dependencies` 并钉死一个版本，一旦装配清单里那个包是别的版本，包管理器会**安安静静地装第二份**。于是同一个客户选择器在同一个页面上有两份实现、两套状态，而 §2.6 那条规矩在纸面上还好端端写着。`peerDependencies` 把版本决定权交回给装配清单 —— 那里永远只有一份。

peer 的范围写法（`>=1.4.0`）是 npm 的语义，不是 BrickKit 的依赖解析。**最终装上去的永远是装配清单里那个精确版本**，BrickKit 从不往清单里写范围。

**② 必须配套声明强依赖。**

```yaml
# erp-sales/component.yaml
dependencies:
  components:
    - mdm/customer@3.2.0
```

理由在 §3.6：清单只装「这次会启动的组件」。`mdm/customer` 一旦被归档，`@acme/biz-mdm-customer` 就从清单里消失，而 `erp/sales` 的界面还 import 着它 —— **构建当场失败，报一句 `Cannot find module`**。有强依赖声明，BrickKit 在归档那一步就拦下来了，错误发生在正确的地方。

换句话说：**用了别人的界面，就得承认自己强依赖它。** 这与后端调用别人的 API 必须声明强依赖，是同一条规矩（002 §3.1）。

### 2.5 前端版本与组件版本各走各的

**声明了 `ui.package`，就必须声明 `ui.version`。**

它和 `deployment.image` 后面那个 tag 是同一类东西：**发布物的坐标，写明，不推导。**

```yaml
metadata:
  version: 3.2.0                                  # 组件版本，跟着后端走
deployment:
  image: registry.acme.com/mdm-customer:3.2.0     # 镜像坐标：写明
ui:
  package: "@acme/biz-mdm-customer"
  version: 1.4.0                                  # 包坐标：写明，独立演进
  dir: frontend
```

**为什么不让它恒等于 `metadata.version`。** 现实里后端在不停迭代 —— 加字段、改算法、修数据、调性能 —— 而界面几个版本都不用动一行。强行同号意味着每次后端发版都要发一个内容一模一样的 npm 包：版本号涨了，内容没变，所有装配还得重装一遍。这是纯粹的浪费，而且掩盖了真实信息（"这次界面到底改没改"）。

**那"哪个前端配哪个后端"怎么查？Manifest 就是那份记录。** `mdm/customer@3.2.0` 这**一个**坐标里同时钉死了镜像 tag 和 npm 包版本，而 Manifest 在市场里按版本不可变存储（007）。想知道 3.2.0 用的是哪版界面，读它的 Manifest，一行就在那儿。所以"记录哪个前端配哪个后端"这件事不需要新机制 —— 组件版本号本来就是那个记录的编号。

**`ui.version` 必须是精确版本。** 不接受 `^1.4.0`、`~1.4.0`、`latest` —— 与「不做版本范围解析，杜绝隐式升级」（004 §1.3）同一条规矩。

CLI 不校验 npm registry 上是否真的存在这个版本 —— 那与「CLI 不校验镜像是否存在」对称。装不上时 `pnpm install` 会报错，而它的报错比 CLI 转述得清楚。

### 2.6 一个装配里，一个组件只有一份界面

**同一组件多版本共存时（003 §4.8），界面只取一份：组件版本号最高的那个所声明的 `ui`。其余版本的 `ui` 声明被忽略。**

理由有两层，第二层才是真正的理由。

**机械那层：** npm 的 `dependencies` 里一个包名只能有一个版本 —— 这和「环境变量名基于组件 ID、不带版本号」（002 §3.6）是同一种约束。清单里不可能同时写两条 `@acme/biz-mdm-customer`。

**业务那层：** 老版本的容器还活着，是**为了老的调用方，不是为了终端用户**。那些调用方各自在自己的 Manifest 里声明了精确依赖，各自拿各自的地址，谁也不受影响。而人坐在浏览器前面看到的，就该是这个组件当前的样子 —— 那才是真正更新过的东西。

所以壳这边一并取最新，两者必须一致：

| 取什么 | 取哪一个 |
| --- | --- |
| 界面包 | 组件版本号最高的那个版本声明的 `ui.package@ui.version` |
| 壳容器里的 `{组件ID前缀}_ENDPOINT` | 版本号最高的那个版本的容器地址 |

**最新的界面连最新的后端。** 错开的话，界面会拿着新字段去问一个不认识它的旧后端。

CLI 把这件事打印出来，不留暗箱：

```
📦 mdm/customer 有 2 个版本在跑（1.0.0、3.2.0）
   界面取 3.2.0 声明的 @acme/biz-mdm-customer@1.4.0
   壳的 MDM_CUSTOMER_ENDPOINT → http://mdm-customer-3-2-0:8080
   💡 1.0.0 的容器照常运行，供仍声明着 mdm/customer@1.0.0 的老调用方使用
```

⚠️ **多版本共存只是物理缓冲，不保证数据层兼容**（002 §3.6）。界面只反映最新那一套的数据视图 —— 如果两个版本各绑各的库，老版本里的数据在界面上是看不见的。这是多版本共存本身的性质，不是前端装配引入的。

**两个不同组件声明了同一个 `ui.package`，仍然是报错。** 那不是多版本，那是撞名 —— 两个组件抢一个包名，无论取谁都是错的。

### 2.7 闭源组件的界面

002 §2.3 那条「代码可以闭源，但 API 契约不能闭源」，到了前端要补一刀：**前端没有技术意义上的闭源。**

后端的闭源是真的 —— 镜像里是编译产物，而且它从不下发到终端。前端不是：无论走哪条路，JS 最后都躺在用户的浏览器里。两条路的区别只在**消费方拿到的形态**：

| | 路 A：独立容器（§1.5） | 路 B：界面包 |
| --- | --- | --- |
| 消费方拿到什么 | 运行时下发的 JS —— 能扒，但没有工程结构、没有类型、没有再分发的授权 | 一个 npm 包 —— 装在自己机器上，能读、能改、能重新发布 |
| 靠什么保护 | 混淆 + 服务条款 | 混淆 + **License** + 私有 registry 只对授权客户开放 |

**这不是 BrickKit 引入的限制，是浏览器的性质。** 商业前端组件（AG Grid Enterprise、Highcharts 这一类）一直就是这么卖的：代码可读，靠 License 收钱。

所以闭源商业组件有两条路可选，取决于它卖的到底是什么：

- **界面必须进客户的统一门户** → 走路 B。发一个带 License 的界面包到私有 registry，只给授权客户。**接受代码可读**。
- **绝不把界面代码交出去** → 走路 A。自己一个容器、一个域名。代价是它在客户眼里是"另一个系统"，进不了那套统一菜单 —— 而这往往正是客户最在意的东西。

**平台不提供、也不打算提供任何前端代码保护机制**（混淆、授权校验、水印、许可证心跳）。那是 License 和商务的事，不是编排工具的事 —— 与「不做第三方组件安全审查」（012 §2.11）是同一条边界。

### 2.8 界面包的运行时契约

§2.4 定的是**构建期**契约（壳怎么知道有哪些页面）。页面跑起来之后要调后端，那是**运行时**契约，同样必须定死 —— 否则 20 个包会有 20 种做法，而其中 19 种会在换环境时断掉。

三条，缺一不可。

**① 只发相对路径请求，前缀固定为 `/api/{组件ID}/`。**

```js
// ✅ 对
fetch('/api/mdm/customer/list')

// ❌ 错：把自己钉死在一套环境上
fetch('http://localhost:18080/list')
fetch(import.meta.env.VITE_CUSTOMER_API + '/list')
```

**包永远不知道后端在哪。** 开发时是 `localhost:18080`（`brickkit up` 分配的宿主机端口），生产时是 `http://mdm-customer-3-2-0:8080`（内网 DNS）—— 这两个地址的翻译分别由开发服务器的 proxy（§4.5）和 nginx 的 `location`（§4.6）完成，两边都从 BrickKit 注入的 `{组件ID前缀}_ENDPOINT` 拿值。包只要写对前缀，两套环境自动都对。

前缀必须是组件 ID，理由和路由前缀一样（§4.4）：撞不了，而且和 nginx 的 `location` 划分自动对齐。

**② 不碰鉴权。**

包不读 token、不加 `Authorization` 头、不处理 401 跳登录。

那是壳的事 —— 同域下 Cookie 浏览器自动带；用 Bearer 的话壳装一个统一的 fetch 拦截器。鉴权失败的处理也归壳：401 清凭据跳登录页、403 显示"无权限"。

理由有两条。**一条是维护成本**：20 个包各写一遍读 token 的代码，token 格式一变就有 20 个地方要改。**另一条更要紧** —— 008 §1.3 写着「BrickKit 不做用户权限管理、不做复杂的 OAuth/OIDC，那是组件的事」。也就是说**换一套鉴权方案是装配方的正当权利**，而界面包一旦自己读 token，就把某一套具体实现焊死在了包里。包不该知道这个装配用的是 Cookie 还是 Bearer、用的是哪个鉴权组件。

⚠️ 隐藏菜单不等于安全。壳按权限过滤菜单只是体验，**真正的鉴权必须由后端组件做**（008 §1.3：业务面的安全是组件自己的事）。

**③ 用标准 `fetch`，不依赖任何 BrickKit 特有的全局对象。**

不要 `globalThis.__brickkit.request()` 这类东西。

理由是这条契约里最值钱的一句：**这样同一份界面代码既能进壳（路 B），也能被组件自己的独立站直接用（路 A，§1.5）。** 包里没有一行"我知道自己在壳里"的代码，两条路才共用得起来 —— 否则组件想同时支持两条路就得维护两份界面。

---

这三条加上 §2.4 的两个导出，就是界面包契约的全部。**注意它们全都不是 BrickKit 特有的东西** —— 一个相对路径的 `fetch`、两个 ESM 导出。包拿到别的地方也是个正常的 npm 包。

### 3.1 位置与内容

```
my-erp-project/

├── .brickkit/
│   ├── manifests/
│   ├── artifacts/
│   └── generated/                 ← CLI 生成物，不进 Git（003 §11）
│       ├── docker-compose.yaml
│       ├── local-debug.infra-web-shell-1-0-0.env
│       └── frontend/              ← 前端装配清单
│           ├── package.json
│           ├── index.js
│           └── index.d.ts
└── components/
```

放在 `generated/` 下是因为它和 `docker-compose.yaml`、`local-debug.env` 是同一类东西：由 BOM 推导、每次重算、人可审查、不进 Git。

### 3.2 `package.json`

```json
{
  "name": "@brickkit/assembly-ui",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" },
  "types": "./index.d.ts",
  "dependencies": {
    "@acme/biz-erp-sales": "file:../../../components/erp/sales/frontend",
    "@acme/biz-mdm-customer": "1.4.0"
  }
}
```

两行依赖长得不一样，这正是重点：

- `@acme/biz-mdm-customer` 写版本号 → 从 npm registry 装。这个 `1.4.0` 来自组件的 `ui.version`，**不是** `mdm/customer` 这个组件的版本号（那是 `3.2.0`，见 §2.5）。
- `@acme/biz-erp-sales` 写 `file:` 路径 → 从本地源码装，改代码即时生效。此时 `ui.version` 不参与：本地源码是什么就是什么。

依赖按组件 ID 字典序排列，保证重复生成的结果逐字节一致，可以放心 diff。

### 3.3 `index.js` 与 `index.d.ts`

```js
// 由 brickkit 生成，请勿手动修改。
// 来源：brickkit.yaml（4 个组件，2 个带界面）
import * as meta_erp_sales from "@acme/biz-erp-sales/meta";
import * as meta_mdm_customer from "@acme/biz-mdm-customer/meta";

export const components = [
  { id: "erp/sales",    version: "1.0.0", uiVersion: "0.9.2", pkg: "@acme/biz-erp-sales",    meta: meta_erp_sales },
  { id: "mdm/customer", version: "3.2.0", uiVersion: "1.4.0", pkg: "@acme/biz-mdm-customer", meta: meta_mdm_customer },
];
```

`version` 是组件版本（后端），`uiVersion` 是界面包版本。两个都给出来，是因为壳经常要在"关于"页面里把它们列全 —— 出问题时第一句话就是"你装的是哪一版"。

```ts
// 由 brickkit 生成，请勿手动修改。
export interface BrickMenu {
  key: string;
  title: string;
  path: string;
  icon?: string;
  permission?: string;
  order?: number;
}
export interface BrickRoute {
  path: string;
  name?: string;
  component: () => Promise<unknown>;
  meta?: Record<string, unknown>;
}
export interface BrickComponentMeta {
  menus?: BrickMenu[];
  routes?: BrickRoute[];
}
export interface BrickComponent {
  id: string;
  version: string;
  uiVersion: string;
  pkg: string;
  meta: BrickComponentMeta;
}
export declare const components: BrickComponent[];
```

**为什么生成这个 `index.js`，光有 `package.json` 不够？** 因为 pnpm 的 node_modules 是严格的：壳只能 import 自己声明过的依赖。壳的 `package.json` 里只有 `@brickkit/assembly-ui` 这一条静态依赖（§4.3），够不到它下面的业务包。所以清单包必须把它们重新导出一次。

这十来行是数据不是逻辑。BrickKit 用到的只有 ESM 的 `import` 与 `import()` —— 语言特性，不是框架特性。它不认识 Vue、React 或任何打包器。

**框架中立与装配层现实。** 平台层（CLI 与清单）只认 ESM、不认框架 —— React 团队拿同一份清单，可以装配出全 React 的产品，清单一个字节都不用改。但要注意装配层的物理现实：壳是唯一渲染者，**同一个装配内框架必须统一**（Vue 壳渲染不了 React 页面；混装意味着双运行时、双状态世界，以及给每个外来页面写挂载适配器）。因此：框架由装配方（壳的拥有者）选择，写进装配方自己的设计书；平台不强制任何框架，不提供跨框架适配器，也不禁止装配方自写适配器（§10 决策 16）。本文档通篇以 Vue 举例，那是例子，不是规范（§4）。

### 3.4 本地源码还是 registry 包

判据只有一条：

**该组件的前端源码目录在活跃工作区里存在 → 走 `file:` 本地链接；否则 → 走 registry 版本号。**

具体检查时，先按活跃 sources 映射（003）解析出组件的实际根目录，再检查 `<组件根目录>/<ui.dir>/` 存不存在。默认 `./components` 布局下，它就是 `components/<scope>/<name>/<ui.dir>/`；sources 使用自定义 path 的装配，按其 path 解析。不得硬编码 `components/` 前缀。

这条判据不需要任何新字段，因为「我现在关心哪几个组件」这件事，BrickKit 里早就有专门的表达方式了：

| 你做的事 | 结果 |
| --- | --- |
| `brickkit add erp/sales@1.0.0 --repo` | 源码进活跃工作区 → 前端走本地源码 |
| `brickkit sync`（该组件这次不启动） | 源码进 `components/.archived/` → 前端整条从清单消失 |
| `brickkit remove erp/sales` | 源码删除 → 清单里也没有了 |
| 从没 clone 过源码 | 走 registry 包 |

判定结果每次都会原样打印出来，不留暗箱：

```
$ brickkit up
📦 前端装配清单已生成：.brickkit/generated/frontend/（3 个界面）
   erp/sales       → 本地源码  components/erp/sales/frontend
   mdm/customer    → registry  @acme/biz-mdm-customer@1.4.0
   infra/iam       → registry  @acme/biz-iam@1.0.0
   已归档，未纳入：crm/lead、hrm/payroll
   💡 清单变化后需在壳工程执行一次 pnpm install
```

### 3.5 何时重新生成

清单不需要专门的命令去刷新。凡是会改变「这次装配包含哪些组件」的命令，顺手重算一次：

| 命令 | 为什么它会影响清单 |
| --- | --- |
| `brickkit add` | 组件进来了 |
| `brickkit remove` | 组件出去了 |
| `brickkit sync` | 归档 / 激活改变了源码是否在活跃工作区（§3.4），也改变了启停判定 |
| `brickkit up` | 启停判定在这里发生 |

这四条本来就在维护装配状态 —— `brickkit.yaml` 也是它们在写。手工改了 `brickkit.yaml` 想立刻刷新清单，跑 `brickkit sync`：它本来就是「整理工作区」，前端清单是工作区的一部分。

生成是纯本地文件操作，不联网、不调用任何外部命令，代价可以忽略。

### 3.6 清单只包含"这次会启动的组件"

装配清单用的启停判据，和 `brickkit up` 起哪些容器、`brickkit sync` 留哪些源码，是同一个判据（003 §4.3）：

|  | 判据 | 结果 |
| --- | --- | --- |
| `brickkit up` | 这次会不会启动 | 起不起容器 |
| `brickkit sync` | 同上 | 源码留在 `components/` 还是收进 `.archived/` |
| 前端装配清单 | 同上 | 界面进不进清单 |

于是一个被归档的组件：容器不起、源码看不见、界面不在清单里、壳的菜单里没有它、端口也不给它映射。**四处一致。**

这正是本地调试想要的效果 —— `brickkit sync` 就是那个开关，把不关心的组件收起来，眼前只剩要调的那几个。

## 4. 壳组件怎么写

这一章是模板。照着抄，改掉名字就能用。

模板以 Vue 为例；其他框架（React 等）的装配方参照同样的结构替换实现 —— 平台强制的只有清单的形状（§3），没有框架（§10 决策 16）。

### 4.1 壳是装配方自己的组件

壳不是一个可以跨客户复用的通用组件。

原因很直接：壳镜像里打包的是「本次装配包含的那些界面」，而每个客户装的组件不一样。如果 `infra/web-shell@1.0.0` 这一个版本号在 Acme 和 Beta 手上对应着内容不同的两个镜像，那就违反了"版本即不可变产物"。

所以正确的做法是：上游提供的是壳的模板仓库，装配方 fork 一份成为自己的组件。

```
brickkit/web-shell-template   （上游模板，不发市场）
        │  fork
        ▼
acme/acme-erp-shell           （Acme 自己的组件仓库）
        │  改 logo、改主题、make build
        ▼
registry.acme.com/acme-erp-shell:1.0.0
```

Acme 的壳就是一个再普通不过的 BrickKit 组件：自己的仓库、自己的 `component.yaml`、自己构建的镜像、自己的版本节奏。平台不需要为它加任何特殊分支。

```
├── Makefile
├── Dockerfile
├── scripts/
│   └── gen-nginx-conf.mjs        # 从装配清单生成 nginx location 块
└── frontend/
    ├── package.json
```

### 4.3 `package.json`：那一行静态依赖

```json

    "build": "vite build"
  },
```

### 4.4 消费装配清单：路由与菜单

```ts
// src/router.ts
import { createRouter, createWebHistory, type RouteRecordRaw } from 'vue-router';
import { components } from '@brickkit/assembly-ui';

// 所有组件的路由，一把摊平
const bizRoutes: RouteRecordRaw[] = components.flatMap(
  (c) => (c.meta.routes ?? []) as RouteRecordRaw[],
);

// 所有组件的菜单，按 order 排序（没写 order 的排在后面）
export const menus = components
  .flatMap((c) => (c.meta.menus ?? []))
  .sort((a, b) => (a.order ?? 999) - (b.order ?? 999));

export const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/', redirect: menus[0]?.path ?? '/blank' },
    ...bizRoutes,
    { path: '/:pathMatch(.*)*', component: () => import('./NotFound.vue') },
  ],
});
```

```vue
<!-- src/App.vue -->
<script setup lang="ts">
import { menus } from './router';
</script>
<template>
  <div class="layout">
    <aside>
      <RouterLink v-for="m in menus" :key="m.key" :to="m.path">{{ m.title }}</RouterLink>
    </aside>
    <main><RouterView /></main>
  </div>
</template>
```

壳的代码里没有任何一个业务组件的名字。装了什么就长出什么菜单，卸了就没了。

#### 路由撞车：平台管不了，壳必须自检

两个组件都声明了 `/erp/sales` 会怎样？**BrickKit 检查不到。** `meta` 在 npm 包里，不在 `component.yaml` 里 —— 平台读不到它，也不该为了读它去装一个 npm 客户端（§10 决策 4）。

所以约定加自检，两手都要：

- **约定：路由前缀必须是组件 ID。** `mdm/customer` 的路由全部挂在 `/mdm/customer/**` 底下。这样撞车在设计上就不可能发生，也顺带让 §4.6 里 nginx 的 `location` 划分和路由划分对齐。
- **自检：壳启动时扫一遍，撞了当场喊。** 十行代码，别省：

```ts
const seen = new Map<string, string>();
for (const c of components) {
  for (const r of c.meta.routes ?? []) {
    const prev = seen.get(r.path);
    if (prev) throw new Error(`路由 ${r.path} 被 ${prev} 与 ${c.id} 同时声明`);
    seen.set(r.path, c.id);
  }
}
```

不检查的后果很难查：两条一样的 path 注册进 router，后注册的赢，表现是"点这个菜单进了另一个组件的页面"—— 而两边组件的代码都没有任何毛病。菜单 `key` 同理。

菜单的权限过滤（按 JWT claims 隐藏无权限的菜单项）是壳自己的业务，不在本规范范围内 —— 但要记住隐藏菜单不等于安全，鉴权必须由后端组件做（008）。

### 4.5 `vite.config.ts`：开发时后端地址从哪来

开发服务器跑在宿主机上，后端组件跑在 Docker 里。两者之间的地址翻译，BrickKit 已经做好了：给壳写上 `local: true`，`brickkit up` 就会把壳需要的组件端口映射到宿主机，并生成一份 env 文件（003 §4.4）。

```bash
# .brickkit/generated/local-debug.infra-web-shell-1-0-0.env
COMPONENT_ID=infra/web-shell
COMPONENT_VERSION=1.0.0
MDM_CUSTOMER_ENDPOINT=http://localhost:18080
ERP_SALES_ENDPOINT=http://localhost:18081
```

壳把这份文件读进来配代理即可：

```ts
// vite.config.ts
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import dotenv from 'dotenv';
import { components } from './node_modules/@brickkit/assembly-ui/index.js';

// BrickKit 在 up 时生成；文件名 = local-debug.<壳的版本化服务名>.env
const env = dotenv.config({
  path: '../../../../.brickkit/generated/local-debug.infra-web-shell-1-0-0.env',
}).parsed ?? {};

// 组件 ID → 环境变量前缀：erp/sales → ERP_SALES（附录 C.2）
const envPrefix = (id: string) => id.replace(/[/-]/g, '_').toUpperCase();

// /api/<scope>/<name>/** → 该组件。这个前缀是契约不是壳的自由（§2.8 ①）：
// 界面包里写死了它，壳改了前缀，所有包一起断
const proxy = Object.fromEntries(
  components.map((c) => [
    `/api/${c.id}`,
    {
      target: env[`${envPrefix(c.id)}_ENDPOINT`],
      changeOrigin: true,
      rewrite: (p: string) => p.replace(`/api/${c.id}`, ''),
    },
  ]),
);

export default defineConfig({
  plugins: [vue()],
  // 关键：业务包与壳必须共用同一个 Vue 实例，否则 provide/inject、
  // pinia、全局指令全部失效，而且报错很难懂
  resolve: { dedupe: ['vue', 'vue-router'] },
  server: { port: 5173, proxy },
});
```

`resolve.dedupe` 那一行是踩过的坑：清单包和壳各自装一份 Vue 的话，页面能渲染出来，但跨组件的响应式状态莫名其妙地断掉。（其他框架有同构的坑与同构的解法，本质都是"同一装配内共享同一份运行时实例"，见 §10 决策 16。）

### 4.6 Dockerfile 与 nginx

生产环境里壳是个 nginx 容器，反向代理到内网 DNS 地址（002 §4.3）。

`location` 块开多少个取决于装了哪些组件 —— 构建时才知道；每个块代理到哪 —— 容器启动时由环境变量给出（005 §4.4）。所以分两步：构建时生成带占位符的模板，启动时 envsubst 填值。

```js
// scripts/gen-nginx-conf.mjs —— 构建时执行
import { writeFileSync } from 'node:fs';
import { components } from '../frontend/node_modules/@brickkit/assembly-ui/index.js';

const envPrefix = (id) => id.replace(/[/-]/g, '_').toUpperCase();

const locations = components
  .map(
    (c) => `
  location /api/${c.id}/ {
    proxy_pass \${${envPrefix(c.id)}_ENDPOINT}/;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
  }`,
  )
  .join('\n');

writeFileSync(
  'dist-conf/default.conf.template',
  `server {
  listen 80;
  root /usr/share/nginx/html;
${locations}

  # SPA history 模式
  location / {
    try_files $uri $uri/ /index.html;
  }
  # 带 hash 的静态资源可以长缓存，index.html 绝对不行
  location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }
  location = /index.html {
    add_header Cache-Control "no-cache";
  }
}
`,
);
```

```dockerfile
# ---- 构建 ----
FROM node:20-alpine AS build
WORKDIR /app
# 装配清单必须先进来：壳的依赖里有 file:../../../../.brickkit/generated/frontend
COPY .brickkit/generated/frontend/ /.brickkit/generated/frontend/
COPY components/infra/web-shell/ /app/
# 本地源码链接的组件也要一起进来（走 registry 的不用，pnpm 自己下）
COPY components/ /components/
WORKDIR /app/frontend
RUN corepack enable && pnpm install --frozen-lockfile && pnpm build
WORKDIR /app
RUN mkdir -p dist-conf && node scripts/gen-nginx-conf.mjs

# ---- 运行 ----
FROM nginx:alpine
COPY --from=build /app/frontend/dist /usr/share/nginx/html
# nginx 官方镜像会对 /etc/nginx/templates/*.template 做 envsubst 后放进 conf.d
COPY --from=build /app/dist-conf/default.conf.template /etc/nginx/templates/
EXPOSE 80
```

⚠️ **构建上下文是项目根目录，不是壳目录。** 因为壳的依赖要够到项目根下的 `.brickkit/generated/frontend/`。`Makefile` 里体现为 `-f` 与上下文分开写。

💡 上面这份为了讲清楚而写成一次 COPY 一次 install。真用的时候按 §9.1 拆成两层 —— 只改壳自己代码时 `pnpm install` 整层跳过。

### 4.7 Makefile

BrickKit 不执行这里的任何一条命令。这是壳自己的构建脚本，和后端组件的 `Makefile` 地位完全相同。

```makefile
IMAGE ?= registry.acme.com/acme-erp-shell
TAG   ?= 1.0.0
ROOT  ?= ../..          # 项目根（本组件位于 components/infra/web-shell/）

.PHONY: install dev build push

# 装配清单变了之后跑一次；BOM 变化后必须先跑它并提交 lockfile（§5.2）
install:
	cd frontend && pnpm install

# 本地调试：先 brickkit up（壳需 local: true）
dev: install
	cd frontend && pnpm dev

# 构建镜像。上下文是项目根，因为要带上 .brickkit/generated/frontend/
build:
	docker build -f Dockerfile -t $(IMAGE):$(TAG) $(ROOT)

push: build
	docker push $(IMAGE):$(TAG)
```

### 4.8 壳容器拿到哪些环境变量

壳没有声明 `dependencies`，但它照样拿得到地址 —— CLI 按 §2.2 的规则，把本次会启动的、带 `ui.package` 的组件全集当作壳的依赖来注入：

```yaml
# CLI 生成的 docker-compose.yaml 片段
infra-web-shell-1-0-0:
  image: registry.acme.com/acme-erp-shell:1.0.0
  ports: ["80:80"]
  environment:
    COMPONENT_ID: infra/web-shell
    COMPONENT_VERSION: 1.0.0
    MDM_CUSTOMER_ENDPOINT: http://mdm-customer-3-2-0:8080
    ERP_SALES_ENDPOINT: http://erp-sales-1-0-0:8080
```

这些变量和普通依赖注入走的是同一套机制、同一套命名规则、同一套保留变量保护（008）。壳这边唯一特别的是这份依赖名单是算出来的，不是写出来的。

### 4.9 推荐做法：包既能发布又能热更新

一个界面包有两种被消费的方式，理想的产物不一样：

| 消费方式 | 想要的产物 | 为什么 |
| --- | --- | --- |
| 从 registry 装（`"1.0.0"`） | 已构建的 ESM | 消费方的打包器不必编译 `.vue` 之类的源文件 |
| 从本地链接装（`file:`） | 源码 | 改一行就热更新，构建一次就没了 |

用 `exports` 的条件解析可以同时满足：

```json
{
  "name": "@acme/biz-mdm-customer",
  "version": "1.4.0",
  "type": "module",
  "exports": {
    ".":      { "source": "./src/index.ts", "default": "./dist/index.js" },
    "./meta": { "source": "./src/meta.ts",  "default": "./dist/meta.js" }
  },
  "peerDependencies": { "vue": "^3.4.0" }
}
```

壳只在开发模式下打开 `source` 条件：

```ts
export default defineConfig(({ mode }) => ({
  resolve: {
    conditions: mode === 'development' ? ['source', 'import', 'module', 'browser', 'default'] : undefined,
    dedupe: ['vue', 'vue-router'],
  },
}));
```

**这是推荐做法，不是规范强制。** 本规范只强制一条：包必须导出 `./meta`（§2.4）。怎么组织构建，是组件与壳的前端工程问题，BrickKit 不参与。

## 5. 三种运行方式

### 5.1 部署运行：一条 `brickkit up`

前提：所有镜像和 npm 包都已经在各自的 registry 里，壳镜像已由装配方构建并推送。

```bash
brickkit up
```

完。

**部署机上不需要 Node，不需要碰 npm。** 壳镜像和别的镜像一样是拉下来的 —— 完全是 Docker 模型：部署者拉镜像，不构建镜像。

这一步里那份前端装配清单其实用不上（界面已经烤进壳镜像了），CLI 照样会生成它，因为代价是两个小文件，而永远保持最新比"有时是旧的"省心。

### 5.2 本地 Docker 运行（装配方出货前的自检）

装配方比部署者多干一件事：把壳镜像做出来。

```bash
brickkit init acme-erp
brickkit add infra/iam@1.0.0
brickkit add erp/sales@1.0.0                 # 递归带出 mdm/customer
brickkit add infra/web-shell@1.0.0 --repo    # 壳需要源码才能构建

# 装配清单已由 add 生成，现在构建壳镜像 —— 全部手动，BrickKit 不参与
cd components/infra/web-shell
make push
brickkit up          # → http://localhost
```

BOM 一变（加组件、升版本），重跑 `make push` 再 `brickkit up`。这和"加组件要重新生成 `docker-compose.yaml`"是同一件事。

⚠️ **lockfile 仪式**：BOM 变化后，先在壳工程跑一次 `make install`（让 pnpm 按新清单更新 lockfile），**把 lockfile 提交进壳仓库**，再 `make push`。否则 Dockerfile 里的 `--frozen-lockfile` 会因 lockfile 与清单不匹配而报出难懂的错误。lockfile 编码的是"本次构建的 BOM 状态"，是壳镜像可复现性的一部分 —— 壳本来就是装配方自己的组件，BOM 变了壳就该重新提交一次。

⚠️ **出货镜像必须在"全 registry"状态下构建。** 清单里只要还剩一条 `file:` 路径（§3.4），打进壳镜像的就是**你本地工作区那份还没发布的代码**。换台机器、换个人重新构建，出来的镜像内容不一样，而版本号一模一样 —— 这是最难查的一类事故，因为一切看起来都对。

出货前把要发的改动 `npm publish` 掉，把源码移出活跃工作区（或直接 `brickkit sync` 归档），确认清单里全是版本号，再 `make push`。

CLI 在清单里存在 `file:` 条目时提醒一句，但**不阻断** —— 本地源码链接正是 debug 时的正常状态，拦下来会挡住一个完全正当的流程：

```
⚠️ 前端装配清单里有 1 条本地源码链接：erp/sales
   用它构建出的壳镜像不可复现（含未发布的本地改动）
   出货前请确认这不是你要的
```

### 5.3 本地 debug

目标：后端跑在容器里，壳跑在开发服务器上，改前端代码即时生效。

**第一步：把不关心的组件收起来。**

```yaml
# brickkit.yaml
components:
  - id: crm/lead
    version: 1.0.0
    enabled: false        # 这次不调它
```

```
brickkit sync
   📦 已归档：crm/lead → components/.archived/crm/lead
   📦 前端装配清单已更新（2 个界面，crm/lead 已移出）
```

眼前和清单里都只剩要调的那几个。

**第二步：把壳交给自己。**

```yaml
  - id: infra/web-shell
    version: 1.0.0
    local: true           # 平台别起它的容器，我自己跑
```

```
brickkit up
   ✅ 后端容器已启动（不含 infra/web-shell）
   🔌 已为 infra/web-shell 映射依赖端口：
      mdm/customer → localhost:18080
      erp/sales    → localhost:18081
   📄 已生成 .brickkit/generated/local-debug.infra-web-shell-1-0-0.env
   📦 前端装配清单已生成（2 个界面）
      erp/sales    → 本地源码  components/erp/sales/frontend
      mdm/customer → registry  @acme/biz-mdm-customer@1.4.0
```

**第三步：起开发服务器。全是你自己的包管理器。**

```bash
cd components/infra/web-shell/frontend
pnpm install          # 照着装配清单装
pnpm dev              # → http://localhost:5173
```

改 `components/erp/sales/frontend/` 下的任何文件 → 浏览器立刻更新。改 `mdm/customer` 的界面？给它也 clone 一份源码：

```bash
brickkit add mdm/customer@3.2.0 --repo   # 清单里那一条自动从版本号变成 file:
cd components/infra/web-shell/frontend && pnpm install
```

⚠️ `local: true` 只能配 `deploy.target: docker`（003 §4.4）—— K8s 集群里的 Pod 连不到你的笔记本。

### 5.4 三种方式对照

|  | 部署者 | 装配方 | 组件开发者 |
| --- | --- | --- | --- |
| 机器上要有 | docker 或 kubectl | + Node、包管理器 | + Node、包管理器 |
| BrickKit 命令 | `up` | `add` → `up` | `sync` → `up` |
| 手动命令 | 无 | `make push`（壳） | `pnpm install` / `pnpm dev` |
| 壳怎么跑 | 容器（拉镜像） | 容器（本地构建的镜像） | 开发服务器（`local: true`） |

### 5.5 K8s 运行

和 Docker 完全一样，只改 `deploy.target`：

```yaml
deploy:
  target: k8s
  namespace: acme-prod
```

```bash
cd components/infra/web-shell && make push    # 镜像必须推到集群拉得到的仓库
brickkit up
```

壳在 K8s 下是个再普通不过的 Deployment + Service + Ingress（005 §5）。前端装配这件事在 K8s 下没有任何特殊处理 —— 它发生在构建期，而构建期早就结束了。

⚠️ 壳需要 `expose: true` + `hostname`（003 §4.5），否则集群外访问不到。

## 6. 多端

### 6.1 第二个壳

多写一个 `ui.role: shell` 的组件即可。两个壳共享同一份装配清单，各自决定渲染哪些菜单：

```js
// 管理后台壳只要 infra 域的界面
const admin = components.filter((c) => c.id.startsWith('infra/'));
```

两个壳在 Docker 下要各自的 `exposePort`，在 K8s 下要各自的 `hostname`（003 §4.5）。

### 6.2 移动端

移动端 App 不是容器，因此它不是 BrickKit 组件，不写进 `brickkit.yaml`，也不由 `brickkit up` 部署。它是装配仓库旁边的一个独立前端工程。

但它照样能消费同一份装配清单：

```json
// acme-erp-mobile/package.json
{ "dependencies": { "@brickkit/assembly-ui": "file:../acme-erp/.brickkit/generated/frontend" } }
```

```js
// 同一份清单，移动端自己决定怎么渲染
import { components } from '@brickkit/assembly-ui';
```

逻辑共享、视图分离：菜单声明、路由声明、数据接口从同一份清单来；界面布局 PC 与移动端各写各的。

移动端只能走构建期装配 —— 编译进 App 包里的代码不可能在运行时去远程加载模块。这也正是本规范选择构建期聚合、而不是运行时模块联邦的决定性理由（§10 决策 3）。

### 7.4 测试用例

分两组。A 组只看生成的文件，不需要 Node、不需要 registry、跑得飞快，覆盖绝大多数判定逻辑；B 组是端到端，证明这套东西真能跑起来。

#### A 组：装配清单的生成（无外部依赖）

**A1 · 基础装配**

```bash
brickkit init brick-ui-test && brickkit add --local
```

断言 `.brickkit/generated/frontend/package.json`：

```json
{
  "name": "@brickkit/assembly-ui",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./index.js" },
  "types": "./index.d.ts",
  "dependencies": {
    "@demo/biz-hello": "file:../../../components/demo/hello/frontend",
    "@demo/biz-world": "file:../../../components/demo/world/frontend"
  }
}
```

要点：① `demo/quiet` 没有 `ui` 块，一个字都不出现；② `demo/shell` 是消费方不是包，不出现；③ 两个都走 `file:`，因为本地安装源下源码本来就在活跃工作区；④ 依赖按组件 ID 字典序排列。

断言 `index.js`：

```js
import * as meta_demo_hello from "@demo/biz-hello/meta";
import * as meta_demo_world from "@demo/biz-world/meta";
export const components = [
  { id: "demo/hello", version: "1.0.0", pkg: "@demo/biz-hello", meta: meta_demo_hello },
  { id: "demo/world", version: "1.0.0", pkg: "@demo/biz-world", meta: meta_demo_world },
];
```

**A2 · 幂等**

再跑一次 `brickkit sync`，两个文件逐字节不变。

**A3 · 归档收缩**

给 `demo/world` 写 `enabled: false`，`brickkit sync`。

断言：① `components/.archived/demo/world/` 出现；② 清单里只剩 `@demo/biz-hello`；③ `index.js` 里只剩一条 import；④ 输出里有一行 `已归档，未纳入：demo/world`。

**A4 · 归档恢复**

删掉 `enabled: false`，`brickkit sync`。清单回到 A1 的状态，逐字节一致。

**A5 · 从本地源码切回 registry**

把 `demo/hello` 的源码目录移出活跃工作区（模拟"只装了包，没 clone 源码"），`brickkit sync`。

断言：`"@demo/biz-hello": "0.3.0"` —— 从 `file:` 路径变成版本号，而且是 `ui.version`（`0.3.0`）**不是**组件版本（`1.0.0`）。这一条专门盯 §2.5 那条"各走各的"有没有真的实现。

**A6 · 一个界面都没有**

把 `demo/hello`、`demo/world` 都 `enabled: false`，`brickkit sync`。

断言：清单文件照常生成，`dependencies` 为 `{}`，`index.js` 里 `components` 为空数组。不报错 —— 壳装了个空清单，只是没有菜单可渲染。

**A7 · 完全没有壳**

把 `demo/shell` 移出 `brickkit.yaml`。

断言：清单照常生成（它不依赖壳的存在），不报错也不警告。谁来消费这份清单不是 BrickKit 的事（移动端就是个例子，§6.2）。

**A8 · `ui.dir` 指向不存在的目录**

把 `demo/hello` 的 `ui.dir` 改成 `frontend-typo`。

断言：`[WARN] demo/hello 声明了 ui.dir 'frontend-typo'，但目录不存在，本次按 registry 包处理`，清单里该条为 `"1.0.0"`。不中断。

**A9 · 路径穿越防护**

把 `ui.dir` 改成 `../../../etc`。

断言：`[ERROR] demo/hello: ui.dir 不得包含 '..' 路径段，已跳过该组件`，清单里没有它，其余组件照常处理，退出码 0。

**A10 · 绝对路径防护**

`ui.dir: /usr/local/src`，断言同 A9，文案为「必须是相对路径」。

**A11 · 缺 `ui.package`**

写了 `ui.dir` 却没写 `ui.package`（且不是 `role: shell`）。

断言：`[ERROR] demo/hello: 声明了 ui 块但缺少 ui.package`，退出码 1 —— 这是 `component.yaml` 写错了，属于组件规范校验，当场拦下（002 §2.2.1）。

**A12 · 版本升级**

新增 `components/demo/hello@1.1.0`，改 `brickkit.yaml` 的版本号，`brickkit sync`。

断言：`index.js` 里 `version` 变成 `"1.1.0"`；若走 registry，依赖值同步变成 `"1.1.0"`。

**A13 · 多版本共存时界面取最新**

`demo/hello` 同时装 1.0.0（`ui.version: 0.9.0`）与 2.0.0（`ui.version: 1.1.0`），003 §4.8。

断言：① 清单里只有一条 `"@demo/biz-hello": "1.1.0"` —— 取的是组件版本高的那个（2.0.0）声明的 `ui.version`，**不是** `ui.version` 数字大的那个；② `index.js` 里 `version: "2.0.0"`、`uiVersion: "1.1.0"`；③ 输出里有一段说明取了哪个、老版本容器照常跑；④ **不报错**。理由见 §2.6 与 §10 决策 6。

**A13.1 · 多版本时壳的地址也取最新**

同 A13 的配置，`demo/shell` 不写 `local: true`。

断言：生成的 compose 里壳容器的 `DEMO_HELLO_ENDPOINT` 指向 `http://demo-hello-2-0-0:8080`，与界面取的版本一致（§2.6）。`demo-hello-1-0-0` 容器照常运行。

**A13.2 · 撞包名仍然报错**

给 `demo/world` 把 `ui.package` 改成 `@demo/biz-hello`（与 `demo/hello` 相同）。

断言：`[ERROR] @demo/biz-hello 被 demo/hello 与 demo/world 同时声明，包名必须唯一`，退出码 1。这不是多版本，是撞名。

**A14 · 多个壳**

再加一个 `demo/admin-shell`（`ui.role: shell`）。

断言：清单只有一份，内容与 A1 完全相同。两个壳共享它。

**A15 · 自定义 sources 路径**

把 `sources[0].path` 改为 `./srcs`，并将组件物理移动到 `srcs/demo/...`，`brickkit sync`。

断言：清单中 `file:` 路径按 `srcs/` 解析（如 `file:../../../srcs/demo/hello/frontend`），不因硬编码 `components/` 前缀而误判为 registry 包（§3.4）。

## 9. 已知边界

这一章列的是**设计自带的代价**，不是待修的缺陷。写下来是为了将来有人把它们当 bug 报的时候，能直接指过来。

### 9.1 壳的构建时间随组件数线性增长，且没有增量

BOM 一变，壳镜像就得全量重建：`pnpm install` 装全部界面包，`vite build` 打全部页面。装了 20 个组件就是 20 个包一起来，没有"只重建改动的那一个"这回事。

**为什么不能增量。** 产物是**一个** bundle。跨组件的 tree-shaking、公共依赖去重、chunk 划分 —— 这些正是构建期聚合换来的好处（§10 决策 3），而它们成立的前提就是"一次看到全部代码"。想要增量，就得回到运行时组合，那会丢掉移动端。**这是同一枚硬币的两面，不是可以两头占的。**

**能缓解到什么程度：Dockerfile 分层。** 把清单的 `package.json` 与 lockfile 单独先 COPY，让 `pnpm install` 成为独立一层：

```dockerfile
# 先只拷依赖清单 —— BOM 没变时这一层命中缓存，install 整个跳过
COPY .brickkit/generated/frontend/package.json /.brickkit/generated/frontend/
COPY components/infra/web-shell/frontend/package.json \
     components/infra/web-shell/frontend/pnpm-lock.yaml /app/frontend/
WORKDIR /app/frontend
RUN corepack enable && pnpm install --frozen-lockfile

# 再拷源码 —— 只改壳自己的代码时，上面那层不动
COPY .brickkit/generated/frontend/ /.brickkit/generated/frontend/
COPY components/ /components/
COPY components/infra/web-shell/ /app/
RUN pnpm build
```

分层之后剩下两种情况：**只改壳自己的代码** → install 层命中缓存，只重跑 build；**BOM 变了** → 全量。后者是躲不掉的，因为依赖清单真的变了。

⚠️ 注意 `COPY components/` 会让**任何**组件源码的改动都击穿这一层。如果装配里 local 源码组件多，考虑只 COPY 清单里真正用到 `file:` 的那几个目录。

### 9.2 首屏体积随组件数线性增长

每个组件的 `meta` 都是**静态引入**（§2.4）—— 它们全部进首屏 chunk。这是"菜单必须在首屏就渲染出来"换来的，躲不掉。

量级上大致是这样：

| 组件数 | meta 首屏占用（gzip，按典型 0.5 KB/个） | 判断 |
| --- | --- | --- |
| 10 | ~5 KB | 忽略不计 |
| 30 | ~15 KB | 舒服 |
| 100 | ~50 KB | 开始要看着点 |
| 300 | ~150 KB | 撑不住了 |

§2.4 那道 gzip 8 KB 的门禁挡的是"有人把实现偷偷塞进 meta"，**不是**典型值 —— 一份只有菜单和路由声明的 `meta` 通常在 0.5 KB 上下。真按 8 KB 顶格写 20 个，首屏就 160 KB，那说明门禁该收紧了，不是这里算错了。

**真到了撑不住的量级，逃生通道是已知的：把 `menus` 从 npm 包上移到 `component.yaml`。** 这样 BrickKit 可以直接生成一份纯 JSON 的菜单清单，壳静态引入那一个 JSON，而各包的 `meta` 改成懒加载。代价是**平台要多知道一件事**（菜单长什么样），而本规范一路的取舍都是让平台尽量少知道（§10 决策 4）。

**现在不做。** 几十个组件的量级下它不解决任何真问题，却要现在就把菜单结构钉进平台契约 —— 而那正是最容易改的那部分。留在这里是为了：真撞上的那天，不用重新想一遍。

## 10. 决策记录

| # | 决策 | 为什么 | 避免的坑 |
| --- | --- | --- | --- |
| 1 | 前端走 npm registry，与后端走 Docker registry 对称 | 同一套心智：产物、仓库、认证、构建各就各位 | 另造一套分发通道，最后发现它就是个功能更差的 npm |
| 2 | CLI 不生成 `.npmrc`、不碰 Token | 与「不自动 docker login」严格对称（004 §2.2） | 平台变成凭据管家；下一个来问 "那 helm repo / pip index-url 呢" 时没有立场 |
| 3 | 构建期聚合，不做运行时模块联邦 | 移动端 App 不可能在运行时远程加载模块，构建期聚合必须存在；再加一套运行时模型就是养两套心智、两套调试链路 | 为 PC 端单独造一套运行时组合，两个端行为不一致 |
| 4 | CLI 不执行任何前端命令 | 与「不做数据库迁移工具：只执行命令，不管工具的选择和逻辑」同源 | 平台被拖进前端工具链，还得替使用者决定用 npm 还是 pnpm |
| 5 | CLI 只写 `.brickkit/generated/` 下自己的目录 | 不碰用户手写文件，就不存在 "写重了" "覆盖了用户配置" "并发写坏了" 三类问题 | 去 `pnpm-workspace.yaml` 里插标记块，随后被迫补三章边界情况 |
| 6 | 一个装配里一个组件只有一份界面；多版本共存时取组件版本最高的那份，壳的地址一并取最新 | 老版本容器活着是为了老的调用方，不是为了终端用户 —— 人在浏览器前看到的就该是当前的样子。机械上 npm 的 `dependencies` 一个包名也只能有一个版本，同 "变量名不带版本"（002 §3.6） | 让界面也多版本 → 同一个选择器在页面上有两份实现、两套状态；或者取了旧界面去连新后端 |
| 7 | 前端版本与组件版本各走各的，`ui.version` 必填且精确 | 后端在迭代而界面几版不动是常态；强行同号等于每次后端发版都发一个内容一样的 npm 包。"哪个前端配哪个后端" 由 Manifest 记录 —— 组件版本号本来就是那条记录的编号 | 恒等 → 大量空版本号；可选默认 → 忘了改就静默用了后端版本号 |
| 8 | 界面包必须拆出 `./meta` 子路径导出 | 壳要在首屏渲染完整菜单；菜单声明不能藏在懒加载后面 | 壳被迫先下载全部实现代码才知道菜单长什么样，懒加载失效 |
| 9 | 壳的依赖集由装配算出，不由 `dependencies` 声明 | 壳一旦声明业务依赖，版本就被它装的每个组件绑架 | 加一个组件就得发一版壳 |
| 10 | 壳是装配方自己的组件，不是通用组件 | 壳镜像的内容取决于 BOM，同一个版本号在不同客户手上内容不同 | 违反"版本即不可变产物"；或者被迫给平台加"本地构建镜像"这一整类特殊分支 |
| 11 | 清单由 `add`/`remove`/`sync`/`up` 顺手生成，不给新命令 | 这四条本来就在维护装配状态，`brickkit.yaml` 也是它们写的 | 多一条使用者必须记住、且忘了就出错的命令 |
| 12 | 本地源码还是 registry，只看源码在不在活跃工作区 | `sync` / `--repo` 已经把"我现在关心哪几个组件"表达清楚了 | 再加一个字段，与 `sync` 各说各话，两处对不上时以谁为准 |
| 13 | 清单的启停判据与 `up` / `sync` 完全一致 | 容器、源码、界面、端口映射四处同进同退 | 归档了组件，菜单里却还挂着一个点开就 502 的入口 |
| 14 | 移动端工程不是 BrickKit 组件 | App 不是容器（001），也没有"部署"这一步 | 为了容纳它，给平台开一个"非容器组件"的口子 |
| 15 | CLI 不校验 npm 包是否存在 | 与「不校验镜像是否存在」对称；包管理器的报错比转述清楚 | 平台需要 npm 客户端和网络，才能给出一句更差的错误 |
| 16 | 平台对框架盲视；一个装配内框架必须统一，由装配方选。不接受这个代价的走 §1.5 路 A | 平台层只认 ESM，React 团队拿同一份清单能装出全 React 的产品。但壳是唯一渲染者 —— Vue 壳渲染不了 React 页面，混装意味着双运行时、双状态世界。而框架统一是"合成一个产品"自带的代价，不是平台强加的：不聚合就不用付 | 平台钦定框架 → 挡住半个生态；放任混装 → 每个外来页面都要写挂载适配器；把聚合说成唯一的路 → 显得平台收窄了"语言无关"的承诺 |
| 17 | 界面包之间互相依赖必须用 `peerDependencies`，且配套声明强依赖 | `dependencies` 钉死版本会让包管理器安静地装第二份，把决策 6 变成空话；不声明强依赖，归档掉被依赖组件时构建才炸 | 同一个选择器在页面上有两份实现、两套状态；或者归档一个组件之后，另一个组件的界面构建不出来 |
| 18 | 出货镜像必须在"全 registry"状态下构建，CLI 只提醒不阻断 | 清单里剩一条 `file:` 就等于把未发布的本地代码打进了带版本号的镜像，换台机器构建结果不同。阻断则会挡住 debug 这个完全正当的流程 | 版本号一样而镜像内容不同 —— 一切看起来都对，最难查的一类事故 |
| 19 | 前端没有技术闭源，平台不提供任何前端代码保护机制 | 无论走哪条路 JS 最后都在浏览器里，这是浏览器的性质不是平台引入的。商业前端组件历来靠 License 而非技术保护 | 平台去做混淆 / 授权校验 / 许可证心跳 —— 越过「不做第三方组件安全审查」那条边界，还给了一个技术上兑现不了的承诺 |
| 20 | 界面包只发 `/api/{组件ID}/` 相对请求、不碰鉴权、不依赖 BrickKit 全局对象 | 地址翻译归壳与 nginx，凭据归壳；包里没有一行"我知道自己在壳里"的代码，同一份界面才能同时供路 A 与路 B 使用 | 包写死绝对地址 → 换环境就断；20 个包各写一遍读 token → token 格式一变要改 20 处，且把某一套鉴权实现焊死在包里，而换鉴权方案本是装配方的正当权利（008 §1.3） |
