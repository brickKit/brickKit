# RFC：BrickKit 配置管理、部署体系与无 Market 组件分发重构（完整版）

**状态：** Draft
**影响范围：** `brickkit.yaml`、`component.yaml`、`deploy.yaml`、`deploy.local.yaml`、`config/`、组件分发机制、CLI 全部配置与部署相关命令

---

## 一、摘要

本提案对 BrickKit 进行一次结构性重构，涵盖三大领域：

1. **配置与部署管理：** 建立三层文件架构，让组件声明、部署配置、业务配置彻底分离。
2. **外壳（Shell）机制：** 建立规范的外壳声明与成员关系管理，实现优雅的组件合并部署（单体进程模型）。
3. **无 Market 组件分发：** 在不部署 Market 服务器的前提下，通过 Git 仓库 + Git tag + 本地缓存实现"随时随地拉取特定版本"。

核心是建立三层文件架构：

| 层 | 文件 | 职责 | 进 Git |
| --- | --- | --- | --- |
| 组件声明 | `brickkit.yaml` | 有什么组件、什么版本、谁是外壳 | ✅ |
| 部署配置 | `deploy.yaml` / `deploy.local.yaml` | 怎么部署：target、mode、端口、k8s、外壳成员、环境变量覆盖 (`vars`) | ✅ / ❌ |
| 业务配置 | `config/*.yaml` + `config/vars.yaml` | 每个组件的环境变量（连接串、密钥、开关）+ 公共变量 | ✅ |

同时彻底废除 `resources` 抽象，用 `deploy.local.yaml` 取代原 `override.yaml`，引入 `$var:` 显式引用机制解决共享配置冗余，并建立完整的无 Market 组件分发与版本管理体系。

## 二、动机：当前痛点

### 2.1 `brickkit.yaml` 职责过载

当前 `brickkit.yaml` 同时承担：组件声明、业务配置（`config`）、资源绑定（`resources`）、部署策略（`deploy`、`mode`、`expose`、端口）、本地调试状态。组件数达到 20+ 时文件极其臃肿，Git diff 难读，多人协作频繁冲突。

### 2.2 `resources` 抽象过度

`resources` 本质只是把 `host` / `port` / `user` / `password` 拼成连接串注入环境变量。组件真正需要的只是那几个环境变量。中间那层"资源绑定"是平台在替组件做决定——它假设"一个组件只能连一个数据库"、"连接方式只有一种"。读写分离、多实例等场景无法优雅表达。

### 2.3 配置无版本感知

组件升级后 `configSchema` 可能变化，但没有机制帮用户迁移配置值，只能在 `up` 时才发现缺失必填项。

### 2.4 配置冲突静默丢失

升级后配置字段变化时，没有明确的冲突提示，用户的配置值可能被悄悄覆盖。

### 2.5 本地调试与团队配置混杂

`mode: debug`、`localPort` 等个人调试状态与团队共享配置混在一起，职责不清。

### 2.6 缺少 Market 时的版本管理

当前组件分发依赖 Market 服务器。若不部署 Market，则无法可靠地拉取特定历史版本，用户"不想升到最新、只想用特定版本"的需求无法满足。

### 2.7 共享配置冗余

多个组件连接同一中间件（如 Redis、PostgreSQL）时，每个组件的配置文件都要重复填写相同的连接信息。当中间件地址变更时，需要修改所有相关文件，极易漏改。

### 2.8 外壳机制缺少配置注入规范

外壳将多个组件合并为单体进程部署，但缺乏对配置注入机制的规范定义，尤其是特殊字符（如多行密钥）对 JSON 序列化的破坏问题。

### 2.9 数据库迁移机制与 `resources` 耦合

当前平台通过 `resources` 自动拼装数据库连接串并执行迁移。废除 `resources` 后，需要明确迁移机制如何在新架构下继续工作，尤其是多版本共存时的迁移顺序控制。

### 2.10 无 Market 时镜像来源不明

废除 Market 后，组件的 Docker 镜像来源（预构建拉取还是本地构建）缺乏明确定义，导致 `brickkit up` 无法确定如何获取组件镜像。

## 三、核心设计原则

所有设计决策均遵循以下原则，与 BrickKit 现有哲学一脉相承：

1. **大声失败（Loud Failure）：** 配置冲突、必填缺失、重复 key、推送失败必须在操作时暴露，绝不静默忽略。
2. **平台极简：** 平台不做语义推断（不猜重命名、不做类型转换、不做依赖范围求解），只做机械操作。
3. **所见即所得：** 没有隐式环境变量覆盖、没有配置继承链。看到的文件就是实际生效的配置。
4. **组件自治：** 组件需要什么配置由自己的 `configSchema` 声明，平台不理解配置语义。
5. **职责单一：** 每个文件只管一件事，不跨层混杂。
6. **原子性操作：** 发布、升级等关键操作要么完全成功，要么完全回滚，不留中间状态。
7. **显式优于隐式：** 共享配置通过 `$var:` 显式引用，不引入隐式 Fallback 查找。
8. **概念一致性：** 无论项目规模大小（2 个组件或 200 个组件），心智模型永远是"声明、部署、配置"三层。不提供"单文件模式"或"合并模式"，不引入因项目规模不同而需要切换的额外概念。用户学会一次，终身受用。项目从小长大时，不需要任何"重构"或"拆分"操作，架构天然平滑扩展。
9. **构建与部署分离：** `brickkit up` 绝不自动执行 `docker build`。构建是用户的显式动作，部署是平台的机械操作。
10. **按需检索优于全量合并：** 三层文件各司其职，AI 和人类均按需读取对应文件，不引入"合并视图"命令。每个文件信息密度极高且职责纯粹，避免全量上下文中的噪音干扰。

## 四、三层文件架构（核心）

### 4.1 总体结构

```
my-shop/
├── brickkit.yaml              # 组件声明（进 Git）
├── deploy.yaml                # 团队部署配置（进 Git）
├── deploy.local.yaml          # 个人本地部署配置（不进 Git，可选）
├── config/                    # 业务配置目录（进 Git）
│   ├── vars.yaml              # 公共变量定义（进 Git）
│   ├── erp-backend.yaml
│   ├── people-basic.yaml
│   └── .archive/              # 归档目录（不进 Git）
├── .gitignore
└── .brickkit/                 # 缓存与本地状态（不进 Git）
    ├── repos/                 # Git 仓库缓存（bare repo）
    └── manifests/             # 组件 Manifest 永久缓存
```

### 4.2 职责划分总表

| 信息类型 | 归属文件 | 示例字段 |
| --- | --- | --- |
| 项目名 | `brickkit.yaml` | `project` |
| 组件 id、version | `brickkit.yaml` | `components[].id` / `version` |
| 外壳标记 | `brickkit.yaml` | `components[].kind: shell` |
| 组件源地址 | `brickkit.yaml` | `sources`、`components[].source` |
| 部署目标 | `deploy.yaml` | `target: docker/k8s` |
| 运行模式 | `deploy.yaml` | `mode: enabled/disable/local` |
| 调试模式 | `deploy.local.yaml` | `mode: debug` |
| 端口、暴露、k8s 细节 | `deploy.yaml` | `expose`、`exposePort`、`hostname`、`replicas` |
| 外壳成员关系 | `deploy.yaml` | 外壳条目的 `members` |
| 环境级变量覆盖 | `deploy.yaml` / `deploy.local.yaml` | `vars:` |
| 公共变量 | `config/vars.yaml` | `REDIS_HOST`、`DB_PASSWORD` |
| 业务环境变量 | `config/*.yaml` | `DB_HOST`、`DB_PASSWORD`、功能开关 |

判断一个字段放哪的核心问题：

- 它是"组件是什么" → `brickkit.yaml`
- 它是"怎么部署/编排"或"环境级变量覆盖" → `deploy.yaml`
- 它是"组件进程要读的环境变量" → `config/`
- 它是"多个组件共享的公共值" → `config/vars.yaml`

### 4.3 AI 与人类的检索路径

三层文件各司其职，AI 和人类均按需读取对应文件：

| 想知道什么 | 读哪个文件 |
| --- | --- |
| 项目有什么组件、什么版本 | `brickkit.yaml` |
| 组件怎么部署的（端口、模式、外壳成员） | `deploy.yaml`（或 `deploy.local.yaml`） |
| 组件的环境变量（连接串、密钥、开关） | `config/<component-id>.yaml` |
| 公共变量定义 | `config/vars.yaml` |
| 组件的依赖、能力声明、`configSchema` | `.brickkit/manifests/` 或源码里的 `component.yaml` |

不提供 `brickkit inspect` 等"合并视图"命令。每个文件信息密度极高且职责纯粹，按需读取比全量合并更高效，避免上下文中的噪音干扰。

## 五、`brickkit.yaml` 详细设计

### 5.1 瘦身后只保留组件声明

```yaml
project: my-shop
sources:
  - name: default
    type: git
    baseUrl: https://github.com/myorg/
components:
  - id: erp/shell
    version: 1.0.0
    kind: shell              # 外壳标记（自动生成）
  - id: erp/backend
    version: 2.0.0           # 精确版本，无 kind，默认普通组件
  - id: erp/frontend
    version: 1.0.0
  - id: people/basic
    version: 1.0.0
```

### 5.2 从 `brickkit.yaml` 移除的字段

| 移除字段 | 去向 |
| --- | --- |
| `components[].config` | → `config/` 目录 |
| `resources` | → 废除，走 `config/` |
| `deploy` / `deploy.target` | → `deploy.yaml` |
| `components[].mode` | → `deploy.yaml` / `deploy.local.yaml` |
| `components[].localPort` | → `deploy.yaml` / `deploy.local.yaml` |
| `components[].expose` / `exposePort` / `hostname` / `tlsSecret` | → `deploy.yaml` |
| `components[].serviceAccountName` / `replicas` / `resources` / `labels` | → `deploy.yaml` |
| `components[].servedBy` | → 废除，用 `deploy.yaml` 的 `members` |

### 5.3 新增 `kind` 字段

- `kind: shell` 标记外壳组件，自动生成（`brickkit add` 时从 `component.yaml` 推导）
- 普通组件不写 `kind`
- 作用：只看 `brickkit.yaml` 就能区分外壳和普通组件
- 未来可扩展其他值（如 `kind: connector`）

为什么 `kind` 只是标记，不参与成员关系推导：成员关系唯一来源是 `deploy.yaml` 的 `members`。`kind: shell` 只用于可视化识别，避免两处维护同一关系。

### 5.4 版本管理与多版本共存规则

- `brickkit.yaml` 中的 `version` 必须且只能是精确版本（如 `1.0.0`），不支持范围约束（如 `^1.0.0`）。
- `brickkit.yaml` 实际上充当了项目的 Lock File 角色：写进去的那一刻，版本就被锁定，保证可复现。
- 组件的 `component.yaml` 中的 `dependencies` 也写精确版本（作者开发时使用的版本），作为推荐配置和快照记录。
- **多版本共存：** 当组件 A 声明依赖 B@1.0.0，而项目 `brickkit.yaml` 中已有 B@2.0.0 时，CLI 不会报错，而是自动将 B@1.0.0 加入项目并拉取。利用 BrickKit 精确版本化服务名（如 `people-basic-1-0-0` vs `people-basic-2-0-0`）的天然隔离特性，实现多版本自动共存，直到依赖方升级。

### 5.5 `brickkit add` 的版本行为

| 用户命令 | CLI 行为 |
| --- | --- |
| `brickkit add erp/backend` | 查找远端仓库最新 Tag，将精确版本写入 `brickkit.yaml` |
| `brickkit add erp/backend@1.0.0` | 锁死 `1.0.0`，写入 `brickkit.yaml` |
| 依赖组件 | 同样拉取最新 Tag（或指定版本），写入 `brickkit.yaml`，**支持多版本自动共存** |

## 六、`deploy.yaml` 与 `deploy.local.yaml` 详细设计

### 6.1 `deploy.yaml`：团队部署配置

```yaml
target: docker
vars:                      # 可选：环境级变量覆盖，覆盖 config/vars.yaml 中的同名变量
  DB_PASSWORD: "${PROD_DB_PASSWORD}"
components:
  - id: erp/shell
    expose: true
    exposePort: 8080
    members:                    # 外壳成员关系（唯一来源）
      - erp/backend
      - erp/frontend
  - id: erp/backend             # 成员也有完整部署配置
    mode: enabled
  - id: erp/frontend
    mode: enabled
  - id: people/basic
    mode: enabled
    expose: true
    exposePort: 3000
```

关键点：每个组件（包括外壳成员）始终有完整的部署配置，无论是否在外壳里。`members` 只决定配置"怎么被应用"（独立容器 vs 合并进外壳），不改变配置本身。

### 6.2 `deploy.local.yaml`：个人本地部署配置

- 不进 Git（在 `.gitignore` 中）
- 由 `brickkit local on` 自动生成（从 `deploy.yaml` 完整复制）
- **完整替换：** 开启本地模式后，CLI 只读 `deploy.local.yaml`，完全不看 `deploy.yaml`
- 可以覆盖任何部署字段，包括 `vars` 覆盖（如本地调试密码）和把 `docker` 升级成 `k8s`（只要补齐 k8s 所需字段）

为什么是完整替换而非属性覆盖：属性覆盖需要定义复杂的合并规则（数组怎么合、对象怎么覆盖），增加心智负担。完整替换简单可预测：开启本地模式后只看 `deploy.local.yaml`，所见即所得。对于 AI 来说，读取一个完整文件比解析差异文件更直接。

### 6.3 严格一致性校验

核心规则：`deploy.local.yaml` 中定义的组件列表，必须与 `brickkit.yaml` 中声明的组件列表完全一致（不多、不少）。

触发命令：`brickkit up`、`down`、`status`、`graph`、`lint`。

校验逻辑：

1. 读取 `brickkit.yaml`，获取当前项目声明的所有组件列表。
2. 读取 `deploy.local.yaml`（若本地模式已开启），获取其中定义的组件列表。
3. 对比两者：
   - 缺失组件：`brickkit.yaml` 中有，但 `deploy.local.yaml` 中没有 → 大声失败。
   - 多余组件：`deploy.local.yaml` 中有，但 `brickkit.yaml` 中没有 → 大声失败。

报错信息示例：

```
❌ 部署文件不一致：检测到 `deploy.local.yaml` 已过期！

项目 `brickkit.yaml` 中存在以下组件，但在 `deploy.local.yaml` 中未定义：
  - crm/backend
  - auth/basic

原因：你开启了本地模式（local on），且团队在 `deploy.yaml` 中新增了组件，
      但你的本地部署文件没有同步。

👉 解决方案：
   方案 A（推荐）：运行 `brickkit local refresh` 重新生成最新的本地配置（会自动备份旧文件）
   方案 B：手动在 `deploy.local.yaml` 中补充上述缺失组件的配置
   方案 C：运行 `brickkit local off` 关闭本地模式，直接使用团队配置
```

为什么坚持完整替换 + 严格校验，而非深度融合（Deep Merge）：

深度融合看似美好，但会导致"最终生效状态"不可见。用户（以及 AI）在排查问题时，无法通过查看单一文件来确定实际配置，必须在脑中执行一遍"合并算法"。这直接违背了"所见即所得"原则。完整替换意味着 `deploy.local.yaml` 就是本地环境的唯一真理（Single Source of Truth），只要它存在，系统状态就是 100% 确定的。

### 6.4 `mode` 的拆分

| mode 值 | 放哪 | 原因 |
| --- | --- | --- |
| `enabled` / `disable` | `deploy.yaml` | 团队决策 |
| `local` + `localPort` | `deploy.yaml` | 项目级，BrickKit 托管的本地进程 |
| `debug` | 只能 `deploy.local.yaml` | 开发者级，IDE 调试，不该进 Git |

为什么 `mode: debug` 只能放 `deploy.local.yaml`：`debug` 是"我个人此刻在调试"的状态，是个人事实，不是团队评审 `deploy.yaml` 时需要看到的。它和 `localPort`（调试端口）一样，属于个人本地状态。

### 6.5 `deploy.target` 升级问题

原 `override.yaml` 禁止 `docker → k8s` 升级。本提案放开此限制：

- `deploy.local.yaml` 可以把 `target` 改成任何值，包括 `docker → k8s`
- 前提：用户必须补齐 k8s 所需字段（如 `expose: true` 时的 `hostname`）
- CLI 校验：缺字段则报错（大声失败）

为什么放开：`deploy.local.yaml` 是个人本地文件，开发者有权在本地用任何 target 测试。只要字段完整，就不该限制。

### 6.6 `brickkit local` 命令

```
brickkit local on        # 开启本地模式（不存在则从 deploy.yaml 完整复制）
brickkit local off       # 关闭本地模式
brickkit local status    # 查看当前状态
brickkit local refresh   # 重新生成（备份旧文件，见下文）
```

`brickkit local refresh` 命令行为：

1. 读取最新的 `deploy.yaml`。
2. 将当前旧的 `deploy.local.yaml` 重命名为 `deploy.local.yaml.bak`。
3. 基于 `deploy.yaml` 生成全新的 `deploy.local.yaml`。
4. 输出智能 Diff 摘要：CLI 对比 `.bak` 文件与新生成的文件，在终端列出所有"非团队标准"的本地修改项，辅助用户快速合并。

输出示例：

```
✅ 已生成最新的本地部署配置。旧配置已备份至 `deploy.local.yaml.bak`。
ℹ️ 检测到旧配置中有 3 处本地修改，请手动将它们合并至新的 `deploy.local.yaml` 中：
   - [erp/backend] mode: debug (当前为 `enabled`)
   - [erp/backend] localPort: 8081 (当前未设置)
   - [vars] DB_PASSWORD: "local_dev_pwd" (当前为 `${PROD_DB_PASSWORD}`)
```

为什么需要 `refresh`：当严格校验发现 `deploy.local.yaml` 过期时，用户需要修复。如果直接 `rm` 再 `local on`，之前辛苦配置的 `mode: debug`、`localPort` 等本地状态会全部丢失。`refresh` 通过物理备份保护用户的本地调试资产，同时保持"完整替换"的纯粹性（CLI 不做任何属性合并）。

补充一次性参数：`brickkit up --no-local`（本次忽略 `deploy.local.yaml`）。

### 6.7 `add/remove/upgrade` 自动同步 `deploy.yaml`

| 操作 | `deploy.yaml` 变化 |
| --- | --- |
| `brickkit add erp/backend@1.0.0` | 新增部署条目，用默认值 |
| `brickkit remove erp/backend` | 删除部署条目 |
| `brickkit upgrade` | 更新对应字段；冲突字段用重复 key |

完全同步：`deploy.yaml` 始终与 `brickkit.yaml` 的组件列表保持一致，不出现"组件删了但 deploy 里还有残留"。

## 七、`config/` 目录详细设计

### 7.1 废除 `resources`，全部走 `config`

外部资源连接（数据库、缓存、消息队列）全部通过组件的 `configSchema` 声明，以环境变量注入。

```yaml
# 变更前（brickkit.yaml 的 resources）：
resources:
  - id: main-db
    kind: postgresql
    host: pg.internal
    port: 5432

# 变更后（组件 configSchema + config/ 文件）：
# component.yaml
configSchema:
  properties:
    DB_HOST: { type: string }
    DB_PORT: { type: integer, default: 5432 }
    DB_PASSWORD: { type: string }
  required: [DB_HOST, DB_PASSWORD]

# config/erp-backend.yaml
DB_HOST: $var:DB_HOST        # 显式引用公共变量
DB_PORT: 5432
DB_PASSWORD: $var:DB_PASSWORD
```

为什么这样做：

- 组件只读环境变量，不需要知道"资源"概念
- 读写分离、多实例自然支持（声明 `DB_WRITE_HOST`、`DB_READ_HOST` 即可）
- 平台不替组件做决定，组件完全自治

### 7.2 公共变量与 `$var:` 显式引用

#### 7.2.1 `config/vars.yaml`：公共变量定义文件

采用扁平 KV 结构。变量名由项目管理者完全自定义，无需与组件内部变量名一致，彻底解决同名冲突。

```yaml
# config/vars.yaml
# 存放项目级公共变量，供各组件配置显式引用
REDIS_HOST: "redis.internal"
REDIS_PORT: 6379
ERP_DB_HOST: "pg-erp.internal"       # 自定义变量名，解决同名冲突
CRM_DB_HOST: "pg-crm.internal"
DB_PASSWORD: "${SECRET_DB_PASSWORD}" # 支持进一步引用环境变量
FEATURE_FLAG_X: true
```

#### 7.2.2 组件配置中的显式引用

```yaml
# config/erp-backend.yaml
# Component: erp/backend@2.0.0
# === Required ===
DB_HOST: $var:ERP_DB_HOST          # 显式绑定到 vars.yaml 中的自定义变量
DB_PASSWORD: $var:DB_PASSWORD
# === Optional ===
DB_PORT: 5432                  # 也可以直接写死值，不引用
LOG_LEVEL: "info"
```

#### 7.2.3 `$var:` 语法规则

| 语法 | 含义 |
| --- | --- |
| `$var:VAR_NAME` | 从 `config/vars.yaml` 中读取变量值 |
| `${VAR_NAME}` | 从操作系统环境变量读取（原有行为不变） |
| `file://path` | 从本地文件读取（原有行为不变） |

#### 7.2.4 引用规则

- **不允许循环引用：** `vars.yaml` 中的值不能引用其他 `vars` 变量（如 `$var:OTHER_VAR`），但允许引用环境变量（如 `${SECRET_DB_PASSWORD}`）。
- **显式引用：** 组件配置文件必须显式写出 `$var:XXX`，不存在隐式查找。打开任何组件配置文件，能看到它所有的 Key，以及每个 Key 是直接写死的值还是引用了公共变量。
- **自包含：** 每个组件配置文件列出所有 Key，不依赖"去别处找"。

#### 7.2.5 `brickkit add` 生成骨架时的 `$var:` 提示

当 `brickkit add erp/backend@1.0.0` 生成 `config/erp-backend.yaml` 骨架时：

- 如果 `config/vars.yaml` 中已有与 `configSchema` 同名的变量（如 `DB_HOST`），CLI 提示用户："检测到 `config/vars.yaml` 中已有 `DB_HOST`，是否引用？"
- 用户确认后，骨架中该字段写为 `$var:DB_HOST`
- 用户拒绝或 `vars.yaml` 中无同名变量，则按原规则留空或抄默认值

#### 7.2.6 为什么不用隐式 Fallback（如 `global.yaml` 兜底）

隐式 Fallback 会导致"组件配置文件里没写 `DB_HOST`，但实际生效了，因为去别处找了"。这违背了"所见即所得"和"自包含"原则。`$var:` 显式引用保证了：打开组件配置文件，所有 Key 一目了然，引用关系清晰可见。

### 7.3 文件命名与版本感知

组件 ID `scope/name` 映射为 `scope-name.yaml`（`/` 替换为 `-`）。

| 文件名 | 含义 |
| --- | --- |
| `config/erp-backend.yaml` | 无版本号，跟随 `brickkit.yaml` 当前锁定版本 |
| `config/erp-backend@1.0.0.yaml` | 带版本号，专属于该版本 |

解析顺序：先找带版本文件 → 再找无版本文件 → 都没有则用 `configSchema` 默认值（缺 `required` 报错）。

多版本共存：`brickkit.yaml` 同时有 `erp/backend@1.0.0` 和 `@2.0.0` 时，各自用对应的带版本配置文件。

### 7.4 敏感值引用

| 语法 | 含义 |
| --- | --- |
| `${VAR_NAME}` | 从环境变量读取 |
| `file://path` | 从本地文件读取（路径相对项目根，文件应在 `.gitignore`） |
| `$var:VAR_NAME` | 从 `config/vars.yaml` 读取 |

重要原则：不做隐式环境变量覆盖。`config/` 里写了 `DB_HOST: pg.internal`，即使环境变量有 `DB_HOST=localhost` 也不会覆盖。环境变量只有通过 `${DB_HOST}` 显式引用才参与。理由：所见即所得，避免"看文件不知道实际生效值"。

### 7.5 解析优先级

1. `deploy.local.yaml` (或 `--file` 指定文件) 中的 `vars:` 覆盖 ← 环境级最高优
2. `config/<component-id>.yaml` ← 组件级绑定（支持 `$var:` 引用）
3. `config/vars.yaml` ← 公共变量（被 `$var:` 引用时解析）
4. `configSchema` 的 `default` ← 组件作者兜底（最低优）

`①` 和 `②` 都支持 `${ENV_VAR}`、`file://` 和 `$var:`。

### 7.6 `brickkit add` 自动生成配置骨架

`brickkit add erp/backend@1.0.0` 时，若组件有 `configSchema`，自动生成 `config/erp-backend.yaml`：

```yaml
# config/erp-backend.yaml
# Component: erp/backend@1.0.0
# === Required（必填，缺失阻止启动）===
DB_HOST: ""               # string | 数据库地址
DB_PASSWORD: ""           # string | 数据库密码
# === Optional（可选，已有默认值）===
DB_PORT: 5432             # integer | 数据库端口
MAX_RETRIES: 3            # integer | 最大重试次数
```

- `required` 且无默认 → 留空标必填
- 有默认值 → 抄默认值进去
- 可选无默认 → 注释掉
- 无 `configSchema` 的组件不生成文件
- 若 `config/vars.yaml` 中有同名变量 → 提示是否引用（见 7.2.5）

### 7.7 `config/.archive/` 归档机制

触发归档：

| 事件 | 归档内容 |
| --- | --- |
| `brickkit upgrade` | 旧版本配置文件 |
| `brickkit remove` | 被移除组件的配置文件 |
| 多版本中某版本不再被依赖 | 该版本配置文件 |

**恢复：** 降级或重新 `add` 时，CLI 先查 `.archive/`，找到则按 12.2 节"配置迁移算法"和 12.3 节"冲突处理机制"进行迁移，而非直接复制文件。归档恢复与升级在本质上是完全一样的：都是"手里有一份旧版本的配置文件，现在要适配新版本的 `configSchema`"。

具体流程：

1. 确定旧版本：从归档文件名（如 `erp-backend@1.0.0.yaml`）或文件头注释中提取旧版本号。
2. 获取旧 `configSchema`：从 `.brickkit/manifests/` 缓存或本地 bare repo 中读取旧版本的 `component.yaml`。
3. 获取新 `configSchema`：读取当前要 `add` 的版本的 `component.yaml`。
4. 执行配置迁移算法（12.2 节）：对比新旧 `configSchema`，机械地迁移配置值。
5. 执行冲突处理（12.3 节）：处理默认值变更等冲突，必要时生成重复 key。
6. 生成新配置文件。

Git 策略：`.archive/` 建议加入 `.gitignore`。

## 八、外壳（Shell）机制

### 8.1 外壳的本质：单体进程模型

外壳是一个单体进程，内部通过并发（如 Go 的 goroutine）运行多个组件模块。被承载的组件不再生成自己的容器。

**关键事实（基于 `be-shell-go` 真实落地案例）：** 外壳不是"一个容器里跑多个独立进程"，而是"一个进程内加载多个模块"。所有成员模块共享同一个进程空间，通过 JSON 配置注入获取各自的配置。

外壳与组件是 1:N 关系（一个外壳承载多个组件，一个组件只属于一个外壳）。

为什么是 1:N：外壳的语义是"组件代码被编入外壳进程"，这是物理包含关系。一份代码不可能同时编进两个不同进程。若某组件需在两个外壳提供类似功能，应是两个不同组件，或通过依赖（而非 `members`）共享逻辑。

**外壳成员的独立镜像要求：** 被收编进外壳的成员，必须保留独立镜像构建能力（`image` 字段或 `build` 配置）。这不是"最佳实践"，而是外壳机制在物理层面能工作的硬性前提——迁移容器需要用它跑迁移、移出外壳后需要用它独立运行、外壳升级时成员被自动移出也需要用它兜底。`brickkit add` 将成员加入外壳时会校验此条件，不满足则大声失败。

#### 外壳成员的独立镜像要求（硬性前提）

**规则 1：外壳成员必须保留独立镜像构建能力**

每个被收编进外壳的成员，**必须**满足以下至少一条：

- 有自己的 `Dockerfile`（`build` 字段）
- 有预构建镜像地址（`image` 字段）

| 场景 | 需要独立镜像 |
|------|:---:|
| 迁移容器运行 | ✅ |
| 移出外壳后独立运行 | ✅ |
| `--ignore-served-by` 验证 | ✅ |
| 外壳升级时成员被自动移出 | ✅ |

**规则 2：迁移容器使用成员的独立镜像**

迁移容器 = 成员的独立镜像 + 成员的 `migration.command`。即使成员被编入外壳，它的迁移容器依然用**成员自己的镜像**跑，而非外壳的镜像。因为成员的迁移脚本和运行时环境在成员的镜像里，外壳镜像不保证包含这些。

**规则 3：`brickkit add` 时的校验**

当用户把一个组件加入外壳的 `members` 时（无论是手动还是自动），CLI 必须校验该组件是否有 `image` 字段或 `build` 配置。如果两者都没有 → **大声失败**，报错提示"外壳成员必须保留独立镜像"。

### 8.2 外壳的配置注入机制：JSON 注入

当多个组件被合并进外壳时，BrickKit CLI 将所有被收编成员的信息序列化为一个 JSON 数组，注入到外壳容器的单一环境变量中。

注入的环境变量名：`BRICKKIT_SERVED_MEMBERS_CONFIG`

JSON 结构：

```json
[
  {
    "componentId": "erp/backend",
    "version": "2.0.0",
    "httpPort": 8080,
    "extraPorts": [],
    "config": {
      "DB_HOST": "pg.internal",
      "DB_PORT": "5432",
      "DB_PASSWORD": "secret123",
      "LOG_LEVEL": "info"
    },
    "configEnvVarName": "ERP_BACKEND_CONFIG"
  },
  {
    "componentId": "erp/frontend",
    "version": "1.0.0",
    "httpPort": 3000,
    "extraPorts": [],
    "config": {
      "API_BASE_URL": "http://localhost:8080"
    },
    "configEnvVarName": "ERP_FRONTEND_CONFIG"
  }
]
```

外壳的职责：

1. 外壳组件的启动代码（如 `main.go`）负责读取并解析 `BRICKKIT_SERVED_MEMBERS_CONFIG`。
2. 在进程内部将配置分发给各个模块。
3. 根据需要将特定值（如依赖的 `_ENDPOINT`）通过 `os.Setenv` 注入到当前进程环境中，供底层 SDK 读取。

为什么不存在环境变量命名冲突：因为外壳是单体进程模型，所有配置通过 JSON 结构天然隔离（每个成员有自己的 `config` 对象），不存在"两个进程抢同一个 `PORT` 环境变量"的物理冲突。

### 8.3 特殊字符处理与求值时机契约

真实踩坑案例（来自 `be-shell-go`）：当 `config/*.yaml` 中包含 `${APP_TOKEN_SIGNING_KEY_PEM}` 这种多行字符串（PEM 密钥）时，Docker Compose 在读取 `docker-compose.yaml` 时会进行文本替换，导致裸换行符直接嵌入 JSON 字符串中，破坏 JSON 结构。

为解决此问题并兼容 K8s 原生能力，CLI 在生成部署文件时，对 `${VAR}` 和 `file://` 的求值时机严格区分两种场景：

**场景 A：外壳 JSON 注入（必须 CLI 提前求值）**

对于注入到外壳容器的 `BRICKKIT_SERVED_MEMBERS_CONFIG` 环境变量：

- **行为：** CLI 必须在生成部署文件前，自己先完成所有 `${VAR}` 和 `file://` 的解析。
- **处理：** 将解析后的纯文本值进行安全的 JSON 编码（转义换行符为 `\n`、制表符为 `\t` 等），然后**直接硬编码**进 `docker-compose.yaml` / K8s Manifest 的环境变量字段中。不依赖底层引擎的二次替换。
- **大声失败：** 如果解析后的配置值包含无法安全编码的控制字符，CLI 在 `brickkit up --dry-run` 或 `brickkit lint` 时必须报错阻断。

**场景 B：普通组件的普通环境变量（引擎透传）**

对于普通组件（或非外壳 JSON 注入的字段）的普通环境变量：

- **行为：** CLI **保留 `${VAR}` 原样输出**到部署文件中。
- **理由：** 在 K8s 环境下，`${VAR}` 可能需要由 K8s 引擎在 Pod 启动时从 Secret 或 ConfigMap 中动态解析注入。CLI 提前求值会剥夺 K8s 的原生能力。
- **例外 (`file://`)：** 由于 `file://` 指向本地物理文件，底层引擎无法直接读取，CLI 仍需提前读取文件内容并硬编码进部署文件（若未来 K8s 需要 Secret，由组件自行声明或平台后续扩展，当前阶段硬编码）。

### 8.4 外壳声明：能力声明与实际关系

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 能力声明 | 外壳的 `component.yaml` | "我能承载这些组件" |
| 实际关系 | `deploy.yaml` 的 `members` | "这些组件确实在这个外壳里" |

外壳的 `component.yaml`：

```yaml
metadata:
  id: erp/shell
  version: 1.0.0
shell:
  kind: shell
  members:                    # 能力声明：能承载哪些组件
    - erp/backend
    - erp/frontend
    - erp/worker
```

`brickkit.yaml`（`kind: shell` 自动标记）：

```yaml
components:
  - id: erp/shell
    version: 1.0.0
    kind: shell
  - id: erp/backend
    version: 2.0.0
```

`deploy.yaml`（`members` 实际关系）：

```yaml
components:
  - id: erp/shell
    expose: true
    exposePort: 8080
    members:                  # 实际成员关系（唯一来源）
      - erp/backend
      - erp/frontend
  - id: erp/backend
    mode: enabled
  - id: erp/frontend
    mode: enabled
```

### 8.5 外壳自动化操作

`brickkit add` 外壳：

1. 读取外壳 `component.yaml`，发现 `shell.kind: shell`
2. 在 `brickkit.yaml` 加 `kind: shell` 标记
3. 在 `deploy.yaml` 生成 `members` 列表（只含项目里实际存在的组件）
4. 给已存在的兼容成员自动加入 `members`

`brickkit add` 可被承载的成员：

1. 读取成员 `component.yaml`，发现可被某外壳承载
2. 检查该外壳是否在项目里
3. 有 → 校验成员是否有独立镜像（`image` 或 `build`）→ 有则自动加入 `members`；**无则大声失败**，报错"该组件缺少独立镜像，不能作为外壳成员"
4. 无 → 提示用户是否同时添加外壳

### 8.6 外壳升级

```
brickkit upgrade erp/shell@2.0.0
```

1. 找到所有在该外壳 `members` 里的组件
2. 外壳版本更新为 `2.0.0`
3. 成员组件自身版本不变
4. 成员的 `mode`（包括 `debug`）保留
5. 若新外壳 `members` 能力列表不再包含某成员 → 自动将该成员移出 `members`，变成独立组件

外壳单版本约束：同一外壳只能有一个版本。升级外壳是"全有或全无"，所有成员一起切到新版本。

### 8.7 外壳删除与成员变动

核心原则：组件部署配置原封不动，只动 `members` 关联。

| 操作 | `deploy.yaml` 变化 |
| --- | --- |
| 组件加入外壳 | 加入外壳 `members`，组件配置不变 |
| 组件移出外壳 | 从 `members` 移除，组件配置不变，直接独立运行 |
| 删除外壳 | 删外壳条目，所有成员移出 `members`，成员配置保留 |
| 外壳新版不支持某成员 | 该成员移出 `members`，配置保留，独立运行 |

为什么配置能"原封不动"：每个组件在 `deploy.yaml` 里始终有完整部署配置。`members` 只决定配置"怎么应用"（独立容器 vs 合并进外壳）。移出外壳时配置直接生效，无需临时生成。

**"直接独立运行"的物理前提：** 成员移出外壳后能"直接独立运行"，前提是该成员有独立镜像。这是外壳成员的硬性要求（见 8.1 节），不是可选的。如果成员没有独立镜像，它从一开始就不应该被加入外壳。

### 8.8 外壳自身配置：外壳也是一个组件

对 BrickKit 而言，外壳就是一个普通组件。它有自己的 `component.yaml`、自己的 `configSchema`、自己的配置文件（`config/erp-shell.yaml`）。BrickKit 对待它和对待 `erp/backend` 没有任何区别——生成容器、注入环境变量、处理生命周期。

外壳自身的配置注入：

```yaml
# config/erp-shell.yaml
# Component: erp/shell@1.0.0
# 外壳自身的全局配置（如日志级别、健康检查端口等）
SHELL_LOG_LEVEL: "info"
SHELL_HEALTH_PORT: 9090
```

CLI 在生成外壳容器的部署文件时，会将 `config/erp-shell.yaml` 中的配置作为普通环境变量注入外壳容器（与成员配置通过 `BRICKKIT_SERVED_MEMBERS_CONFIG` JSON 注入是并存的）。

外壳内部的通信与配置分发：外壳进程内部的一切（成员之间怎么通信、进程内部地址怎么路由、配置怎么分发）都是外壳自己的实现细节，由外壳作者在启动代码里处理。BrickKit 只负责：

1. 把各成员的配置序列化成 JSON → 注入 BRICKKIT_SERVED_MEMBERS_CONFIG
2. 把外壳自身的配置（如果有）→ 像普通组件一样注入环境变量
3. 网络拓扑层的 _ENDPOINT 地址重写（见下文）
不介入外壳进程内部的路由逻辑。

**`_ENDPOINT` 的处理（网络拓扑重写与进程内路由的分离）：**
BrickKit 在底层严格区分“网络拓扑层的地址指向”与“进程内部的流量分发”：
1. **网络拓扑层（CLI 负责，自动重写）**：CLI 在依赖解析阶段会在内存中构建“成员 → 外壳”的反向索引（Reverse Index）。当任何组件（无论是外部独立组件，还是外壳内的其他模块）依赖被收编的成员时，CLI 会自动将该成员的 `_ENDPOINT` 物理地址重写为**其所属外壳的地址**（例如将 `http://b-1-0-0:8080` 重写为 `http://erp-shell-1-0-0:8080`）。这确保了微服务拓扑在物理 DNS 和网络层面绝不发生断裂。
2. **进程内部层（外壳作者负责，路由分发）**：外壳作者无需（也无法）篡改外部组件的环境变量。外壳作者的职责是在外壳进程内部启动一个路由器（如 Go 的 `http.ServeMux` 或网关模块），监听外壳端口，并根据请求的 Path/Host（例如 `/api/b/...`），将流量分发给内部的对应模块。
**结论**：平台负责把路修到外壳门口（地址重写），外壳作者负责在院子里分发快递（进程内路由）。两者职责严格解耦。
### 8.9 数据库迁移（Migration）机制

#### 8.9.1 当前问题

当前 BrickKit 平台在 `brickkit up` 时，会自动生成一个 `migration-as-a-service`（一次性的迁移容器），执行组件的 `migration.command`。平台通过 `resources` 拼装数据库连接串，注入给迁移容器。

废除 `resources` 后，平台不再知道"哪个配置是数据库连接串"，也就无法自动拼装连接串。

#### 8.9.2 设计方案：透传所有配置环境变量

核心原则：平台继续生成 Migration Service，但不再拼装连接串，而是"透传"所有配置环境变量。

组件声明（`component.yaml`）：

```yaml
# component.yaml
metadata:
  id: erp/backend
  version: 2.0.0
migration:
  command: ["sh", "-c", "./migrate -path /migrations -database postgres://$DB_USER:$DB_PASSWORD@$DB_HOST:$DB_PORT/$DB_NAME?sslmode=disable up"]
  # 平台不需要知道哪些字段是数据库相关的，
  # 它只需要把 config/erp-backend.yaml 里的所有 key 变成环境变量
  # 注入给这个 migration 容器即可。
```

CLI 行为：

1. 读取组件的 `migration.command` 字段。
2. 为组件生成一个名为 `<component-id>-<version>-migration` 的一次性迁移容器（`compose.yaml` 中的 service，或 K8s 中的 InitContainer/Job）。
3. 将 `config/<component-id>.yaml` 中解析出的所有环境变量，原封不动地注入给这个迁移容器。
4. 迁移容器执行 `migration.command`，由组件自己的脚本负责从这些环境变量中读取所需信息（如自行拼装连接串），并执行迁移。
5. 主组件的 service `depends_on` 这个迁移容器，确保迁移成功后主组件才启动。

多版本顺序控制（Migration Chain）：当项目里同时存在 `erp/backend@1.0.0` 和 `@2.0.0` 时，CLI 会强制 `2.0.0` 的迁移容器 `depends_on` `1.0.0` 的迁移容器（且条件为 `service_completed_successfully`）。这保证了旧版本的迁移先跑完，新版本的迁移再跑，防止并发竞争破坏数据库 Schema。

```yaml
# 生成的 compose.yaml（简化示意）
services:
  erp-backend-1-0-0-migration:
    image: ...
    command: ["sh", "-c", "./migrate ..."]
    environment:
      DB_HOST: pg.internal
      DB_PORT: "5432"
      # ... 所有 config 环境变量
  erp-backend-2-0-0-migration:
    image: ...
    command: ["sh", "-c", "./migrate ..."]
    environment:
      DB_HOST: pg.internal
      DB_PORT: "5432"
      # ... 所有 config 环境变量
    depends_on:
      erp-backend-1-0-0-migration:
        condition: service_completed_successfully
  erp-backend-2-0-0:
    image: ...
    depends_on:
      erp-backend-2-0-0-migration:
        condition: service_completed_successfully
```

#### 8.9.3 为什么不让组件自己跑迁移

如果让组件在 `main()` 函数或 entrypoint 脚本里自己跑迁移：

- 多版本共存时会冲突：`1.0.0` 和 `2.0.0` 的容器同时启动并同时尝试跑 migration，极易发生并发锁冲突或 schema 破坏。
- 主容器可能在迁移还没跑完时就启动并报错。
- 失去平台级的顺序控制能力。

因此，保留平台生成 Migration Service 的能力，但将"理解数据库连接串"的职责下放给组件自己的迁移脚本。

#### 8.9.4 与外壳机制的交互

当组件被合并进外壳时，迁移容器的生成逻辑不变。外壳成员的迁移容器依然独立生成（不合并进外壳进程），确保迁移在组件代码加载前完成。

**迁移容器的镜像来源：** 使用成员自己的独立镜像（`image` 字段或 `build` 构建），而非外壳的镜像。因为成员的迁移脚本和运行时环境在成员的镜像里，外壳镜像不保证包含这些。这也是为什么外壳成员必须保留独立镜像构建能力（见 8.1 节）。

## 九、无 Market 组件分发与版本管理

### 9.1 核心思路：Git 仓库 + Git tag + 本地缓存

- **组件存储：** 每个组件一个 Git 仓库（符合"一个组件一个仓库"原则）
- **版本管理：** 用 Git tag 标记版本（`1.0.0`、`2.0.0`...）
- **拉取机制：** 本地维护 Bare Repo，增量 `git fetch`
- **本地缓存：** 拉取后缓存到 `.brickkit/`，支持离线复用

为什么 Git 能完美满足"随时随地拉特定版本"：

- Git tag 是不可变的版本快照，`1.0.0` 永远是 `1.0.0`
- 本地维护仓库后，所有历史版本都可通过 `git show` 离线读取
- 不依赖任何中心化服务器，只要有 Git 仓库访问权限就能拉

### 9.2 组件仓库结构与命名

每个组件一个独立的 Git 仓库：

```
erp-backend/                    # 一个组件 = 一个仓库
├── component.yaml              # Manifest（依赖、configSchema、shell 声明、artifacts）
├── src/                        # 源码
├── Dockerfile                  # 镜像构建
└── migrations/                 # 数据库迁移脚本
```

组件 ID 到仓库名的映射：`erp/backend` → `erp-backend`（`/` 替换为 `-`）。

版本用 Git tag 标记：`1.0.0`、`2.0.0`（不带 `v` 前缀，与 `metadata.version` 一致）。tag 指向的 commit 就是该版本的完整快照。组件作者发版 = 打 tag。

映射冲突时（极小概率），通过 `source.repo` 显式覆盖解决（见 9.3）。

### 9.3 组件地址解析

在 `brickkit.yaml` 里配置 `source` 基础地址：

```yaml
sources:
  - name: default
    type: git
    baseUrl: https://github.com/myorg/   # 组件仓库的组织地址
```

组件 `erp/backend` 自动推导为 `https://github.com/myorg/erp-backend`。

特殊情况可显式覆盖：

```yaml
components:
  - id: third-party/payment
    version: 1.0.0
    source:
      type: git
      repo: https://github.com/other-org/payment-gateway
```

### 9.4 拉取特定版本的流程（Bare Repo 增量机制）

本地在 `.brickkit/repos/` 下维护 Bare Repo，而非每次 `git clone` 临时目录：

```
.brickkit/
├── repos/                          ← Git 仓库（增量更新的源头）
│   └── erp-backend.git/            ← bare repo
└── manifests/                      ← 解析后的 component.yaml 快照（读取的快路径）
    └── erp/backend/
        ├── 1.0.0/component.yaml
        └── 2.0.0/component.yaml
```

读取优先级：

| 优先级 | 来源 | 网络开销 | 场景 |
| --- | --- | --- | --- |
| 1 | `.brickkit/manifests/` 缓存 | 零 | 该版本已被使用过 |
| 2 | `.brickkit/repos/` 本地 `git show` | 零 | 仓库已克隆但版本未缓存 |
| 3 | `git fetch --tags`（增量） | 极小 | 仓库已克隆但需要新 tag |
| 4 | `git clone --bare`（首次） | 一次完整传输 | 仓库从未克隆过 |

具体流程：

1. 解析组件地址：`erp/backend` → `https://github.com/myorg/erp-backend`
2. 检查 `.brickkit/manifests/erp/backend/1.0.0/` → 有：直接用缓存的 `component.yaml`（秒级，离线可用）→ 无：继续下一步
3. 检查 `.brickkit/repos/erp-backend.git/` 是否存在 → 存在：进入该目录，执行 `git fetch origin --tags`（增量）→ 不存在：`git clone --bare <repo-url> .brickkit/repos/erp-backend.git`
4. 从本地 bare repo 读取 `component.yaml`：`git show 1.0.0:component.yaml`
5. 缓存到 `.brickkit/manifests/erp/backend/1.0.0/`
6. 解析依赖、生成配置、更新部署文件

为什么用 Bare Repo 而非每次 `git clone`：

- 将 N 次完整 `clone` 变成 N 次极快的 `fetch`，大幅减少网络 I/O
- 支持离线操作（只要本地有该 tag）
- 对用户完全透明，不增加心智负担

### 9.5 本地缓存设计

缓存是"随时随地"的关键，且是解决"特定版本找不到"的核心。

```
.brickkit/manifests/
└── erp/backend/
    ├── 1.0.0/component.yaml    ← 永久保留
    ├── 2.0.0/component.yaml    ← 永久保留
    └── 3.0.0/component.yaml
```

缓存规则：

- Manifest 永久缓存，不设过期。因为精确版本不可变，`1.0.0` 永远是 `1.0.0`，缓存不会失效。
- 只要某版本被用过一次，其 manifest 就永远在本地。之后无论离线、换网络、源仓库变动，依赖解析都不受影响。
- 镜像打不可变 tag（`erp-backend:1.0.0`），构建一次后保留在本地，不覆盖。

这直接解决"用户 pin 特定版本找不到信息"的问题：只要项目曾经跑起来过一次，所有 pin 版本的 manifest 和镜像都在本地，随时能复现。

### 9.6 本地源：纯开发态

关键决策：本地源是纯粹的"当前开发态"，不强制独立 Git 仓库，不缓存历史版本。

```
./components/
├── erp-backend/              ← 本地源目录（可以是 Monorepo 的子目录）
│   ├── component.yaml
│   ├── src/
│   └── Dockerfile
└── infra-logger/
    ├── component.yaml
    └── src/
```

`brickkit.yaml` 中的声明：

```yaml
components:
  - id: erp/backend
    version: local              # 特殊标记，表示使用本地源
    source:
      type: local
      path: ./components/erp-backend
```

规则：

- CLI 只读取当前工作区的 `component.yaml`，它代表的就是"未发布的最新版"。
- 不强制独立 Git 仓库：本地源目录可以是 Monorepo（如大仓库下的 `packages/xxx`）里的一个子目录。
- 不做历史版本缓存：对于本地源，CLI 不做任何版本缓存。`brickkit.yaml` 里引用本地源时，永远指向当前目录的最新状态。
- 开发者想看历史版本，自己用 Git 切分支/Tag 即可，BrickKit 不插手。

为什么这样设计：

- 本地源是给开发人员用的，代表"我正在改的代码"。
- 正式部署环境靠 Docker/K8s 部署，不依赖 `local` 源。
- 强制独立 Git 仓库会导致 Monorepo 场景下的嵌套仓库问题。
- 不需要为"离线切换本地源历史版本"这种伪需求增加复杂度。

#### 9.6.1 多组件工作区的自动巡逻与初始化（Auto-Workspace Init）

在大型项目（如 Monorepo）中，`components/` 或 `shell/` 下可能存在数十个本地源组件。为了避免手动进入每个子目录执行 `brickkit init`，CLI 提供自动巡逻与初始化机制。

触发方式：

```
brickkit add --local --init
```

CLI 巡逻逻辑：

1. 扫描 `components/` 和 `shell/` 下的所有子目录。
2. 识别包含 `component.yaml` 的目录。
3. 检测缺失：若该目录缺少 `brickkit.yaml`（即未初始化工作台），CLI 自动为其执行**补全式初始化**（底层调用与 `brickkit init` 相同的补全原语，见 11.5 节），生成：
   - `brickkit.yaml`（`project` 名默认为组件 ID，继承顶级项目的 `sources` 配置）。
   - `deploy.yaml` 和 `config/` 骨架。
4. 自动解析依赖：读取该子组件 `component.yaml` 中的 `dependencies`，自动将其依赖拉取并写入该子组件自己的 `brickkit.yaml` 中。
5. 将该子组件以 `source: local` 加入顶级项目的 `brickkit.yaml`。

设计收益：

- **一键联调：** 执行完毕后，开发者可以直接 `cd components/erp-backend && brickkit up`，在子组件内部独立拉起它的依赖树进行联调。
- **分形架构的完美体现：** 子组件在物理上是顶级项目的子目录，但在逻辑上，它通过自动生成的 `brickkit.yaml` 拥有了自己完整的"项目视角"。

#### 9.6.2 批量发布本地源组件

当在顶级项目中同时修改了多个本地源组件并希望批量发布时，提供批量发布命令。

触发方式：

```
brickkit release --local
```

CLI 行为：

1. 巡逻所有 `source: local` 的组件。
2. 依次对每个组件执行 `release` 流程（校验、Git 状态检查、打 Tag、Push）。
3. **原子性与大声失败：** 若在巡逻过程中发现任何一个组件工作区不干净、有未推送 commit 或推送失败，立即中断整个批量发布流程并报错。已发布的组件 Tag 保留，未发布的组件保持原状，绝不留"半成品"状态。

#### 外壳的目录约定

外壳通常由用户自己实现（`local` 源），建议放在项目的 `shell/` 目录下（与 `components/` 同级）：

```
my-shop/
├── components/ # 普通组件
│ ├── erp-backend/
│ └── erp-frontend/
└── shell/ # 外壳（项目特有，用户自己实现）
    └── erp-shell/
        ├── component.yaml
        ├── main.go
        └── Dockerfile
```

这只是目录组织约定，CLI 通过 `source.path` 感知，不关心组件源码放在哪个目录。`brickkit add --local` 同时扫描 `components/` 和 `shell/`（如果存在）。

`brickkit new` 支持 `--shell` 参数，生成外壳骨架：

```
brickkit new erp/shell --shell --path ./shell/erp-shell
```

`--shell` 参数在 `component.yaml` 中生成 `shell.kind: shell` 和 `shell.members` 占位。这不是一个新命令，只是 `brickkit new` 加一个参数。

### 9.7 组件发现

第一版采用约定 + 文档：

- 约定：`erp/backend` → `{baseUrl}/erp-backend`
- 文档：团队维护一份组件清单
- 不做注册表（后期有需要再说）

### 9.8 升级时获取旧版本依赖

升级 `erp/backend` 从 `1.0.0` → `2.0.0` 时：

| 版本 | 用途 | 来源 |
| --- | --- | --- |
| `1.0.0` | 旧依赖关系、旧 `configSchema` | 本地缓存 `.brickkit/manifests/`，缓存没有则从本地 `.brickkit/repos/` 的 bare repo 中 `git show` |
| `2.0.0` | 新依赖关系、新 `configSchema` | 从本地 bare repo 中 `git show`（若没有该 tag 则先 `git fetch --tags`） |

拿到新旧两份 `component.yaml` 后做集合对比（新增/移除/保留依赖，迁移配置）。

### 9.9 私有仓库鉴权

核心规则：BrickKit CLI 不处理任何鉴权逻辑。

CLI 底层调用的是系统 `git` 命令（`git clone --bare`、`git fetch --tags`）。鉴权完全由宿主机的 Git 配置承担：

- SSH：`~/.ssh/id_rsa` 或 `~/.ssh/config`
- HTTPS：`git credential-helper`（如 `store`、`cache`、`osxkeychain`、`manager`）
- CI/CD 环境：`GIT_ASKPASS`、`.netrc`、或 CI 系统注入的 Token

鉴权失败时的行为：CLI 透传 `git` 命令的错误信息并给出友好提示：

```
❌ 拉取组件失败：erp/backend

Git 错误：Permission denied (publickey).
         或: fatal: Authentication failed for 'https://github.com/myorg/erp-backend'

👉 请检查你的宿主机 Git 鉴权配置：
   - SSH: 确认 ~/.ssh/ 下有对应的 key，且已添加到仓库托管平台
   - HTTPS: 确认已配置 git credential-helper
   - CI/CD: 确认环境变量中已注入 Token
```

为什么这样做：

- **零开发成本：** 不需要在 CLI 里写任何鉴权代码。
- **安全：** 平台不接触凭据，不存在"凭据泄露"风险。
- **灵活：** 不同团队成员可以用不同的鉴权方式，CLI 无感知。
- **CI/CD 友好：** CI 环境通常已经配置好了 `git` 鉴权，BrickKit 直接复用。

### 9.10 镜像分发与构建策略（重构）

#### 9.10.1 核心原则：构建与部署分离

`brickkit up` **绝不**自动执行 `docker build`。它只负责拉取和部署。构建是用户的显式动作。

#### 9.10.2 `component.yaml` 中的镜像声明

```yaml
# component.yaml
metadata:
  id: erp/backend
  version: 1.0.0

# 可选：预构建镜像地址（如果组件作者推送了镜像）
image: ghcr.io/myorg/erp-backend

# 可选：本地构建配置（如果组件作者没有推送镜像，或者用户想本地构建）
build:
  context: .
  dockerfile: Dockerfile
```

#### 9.10.3 CLI 在 `brickkit up` 时的行为逻辑

对于 `local` 源：

1. 检查本地是否已有镜像（如 `erp-backend:local` 或 `erp-backend:1.0.0`）。
2. 有则直接使用。
3. 无则大声失败，提示用户执行 `brickkit build`。

对于 `git` 源：

1. 检查本地是否已有镜像（如 `erp-backend:1.0.0`）。有则直接使用。
2. 若无，且 `component.yaml` 中有 `image` 字段，执行 `docker pull`。
3. 若无 `image` 字段或拉取失败，大声失败，提示用户执行 `brickkit build`。

为什么 `local` 源也不自动构建：贯彻"构建与部署分离"原则。`up` 的职责是"拉取和部署"，不是"构建和部署"。用户修改了本地源代码后，应显式执行 `brickkit build --force` 重新构建，然后再 `up`。这避免了在 70 个本地源组件的场景下，每次 `up` 都触发 70 次不必要的构建。

#### 9.10.4 镜像 Tag 对齐规则

当 CLI 执行本地构建（或用户执行 `brickkit build`）时，生成的镜像 tag 必须严格与组件 `component.yaml` 中的 `metadata.version` 保持一致（如 `erp-backend:1.0.0`）。这保证了 Git tag、镜像 tag、`brickkit.yaml` 声明的版本三者完全对齐，单一事实来源。

## 十、`fetch` 与 `release` 命令

### 10.1 `brickkit fetch`：只取产物，不装进项目

```
brickkit fetch infra/notifier@1.0.0    # 只取产物（跨项目调用，不装进项目）
```

取什么：

- Manifest（`component.yaml`）
- 契约文件（由 `component.yaml` 中的 `artifacts` 字段声明）

`artifacts` 字段（`component.yaml` 原生支持）：

```yaml
# component.yaml
metadata:
  id: erp/backend
  version: 1.0.0
artifacts:
  - type: openapi
    format: yaml
    files:
      - ./docs/api.yaml
    description: "ERP Backend REST API"
  - type: grpc
    files:
      - ./proto/erp.proto
```

`artifacts` 字段结构：

- `type`：必填，字符串（如 `openapi`、`grpc`、`docs`、`sdk`），平台不理解其语义，只透传给消费者。
- `files`：必填，字符串数组，文件路径相对于组件仓库根目录。
- `format`：可选（如 `yaml`、`json`、`proto`）。
- `description`：可选。

不取什么：不取镜像（镜像很大，且在 `brickkit up` 时才需要，届时再拉取或构建）。

不装进项目：不加进 `brickkit.yaml` 的 `components`，不参与依赖解析和部署。

用途：

- 跨项目调用：项目 A 想调用项目 B 的组件，拉其契约文件生成客户端代码或喂给 AI
- 本地集成测试：拉契约了解接口，但不把组件纳入本项目架构
- 无 Market 时：`fetch` 走 git / local 源，逻辑与 `add` 的取 Manifest 部分一致，只是不落进项目。

### 10.2 `brickkit release`：无 Market 的组件发布

"发布组件" = "给组件仓库打个规范的 tag 并推送"，彻底摆脱 Market。

前提：

- 组件源码在本地（`add --repo` 克隆或直接写在 `components/` 下）
- 组件目录是 Git 仓库，配置了远端
- 工作区干净（更改已提交）
- 本地代码已推送到远端分支

流程：

1. 用户执行：`brickkit release --path ./components/erp-backend`
2. CLI 后台动作：
   1. 读取 `component.yaml` 的 `metadata.version` → `"1.1.0"`
   2. 校验 `component.yaml` 的格式和依赖是否合法
   3. 执行 `git status`，工作区不干净 → 报错并停止 ❌
   4. 检查分支同步：本地是否有未推送到远端的 commit
      → 有未推送的 commit → 报错并停止 ❌
      （防止 Tag 指向的 commit 不在远端分支历史中）
   5. 在本地打 tag：`git tag 1.1.0`
   6. 尝试推送：`git push origin 1.1.0`
      ├── 推送成功 → 提示成功 ✅
      └── 推送失败 → 立即执行 `git tag -d 1.1.0`（删除本地 tag，回滚）→ 报错提示 ❌

第 4 步（分支同步校验）的详细说明：检查当前分支是否有未推送到远端上游分支（upstream）的 commit。如果发现未推送的 commit，大声失败，直接中断 `release` 流程（不打 tag）：

```
❌ 发布失败：当前分支有未推送到远端的 commit。
👉 请先执行 git push，确保代码已进入远端分支历史，然后再执行 brickkit release。
```

为什么：保证"Tag 指向的 commit 必然已经存在于远端的分支历史中"。防止出现"孤岛 Tag"（tag 存在但对应代码不在任何远端分支上），维护 Git 历史的连贯性。

三个关键设计决策：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 版本号来源 | 读 `component.yaml` 的 `metadata.version` | 单一事实来源，不替人做决定 |
| 工作区不干净 | 严格模式，报错停止 | 防止误提交敏感/临时文件进 tag |
| 推送失败 | 回滚本地 tag（原子性） | 不留"本地有、远端没有"的中间状态 |

原子性保证：`release` 要么完全成功（本地 + 远端都有 tag），要么完全回滚（就像从没执行过）。

### 10.3 消费侧流程

生产侧（组件作者）：

```
brickkit new erp/backend              # 生成 component.yaml 骨架
... 写代码 ...
修改 component.yaml 的 metadata.version → 1.1.0
git add . && git commit && git push   # 提交并推送代码
brickkit release --path ./components/erp-backend    # 校验 + 打 tag + push
```

消费侧（使用者）：

```
brickkit add erp/backend@1.1.0        # 走 git 源，fetch tag，缓存
```

### 11.1 `brickkit deps`（新增）

`brickkit.yaml` 瘦身后看不出依赖关系，新增命令打印依赖拓扑树：

```
brickkit deps              # 全项目依赖树
brickkit deps erp/backend  # 单组件依赖链
```

为什么不把依赖写进 `brickkit.yaml`：依赖是组件内在属性，写在 `component.yaml`。若 `brickkit.yaml` 也写一遍，两边不一致时 CLI 不知听谁的，破坏单一事实来源。查看用 `deps` 命令，不侵入配置文件。

### 11.2 `brickkit build`（新增）

构建所有需要本地构建的组件镜像。

```
brickkit build              # 构建所有需要本地构建的组件
brickkit build erp/backend  # 构建指定组件
brickkit build --force      # 强制重新构建所有组件（忽略缓存）
brickkit build erp/backend --force  # 强制重新构建指定组件
```

行为：

- 遍历 `brickkit.yaml` 中所有组件，对于没有 `image` 字段的组件（或 `local` 源），从源码构建镜像。
- 构建出的镜像 tag 与组件 `component.yaml` 的 `metadata.version` 严格一致。
- **默认复用缓存：** 如果镜像已存在且版本未变，跳过构建。
- **`--force` 参数：** 强制重新构建，忽略已有镜像。用于用户修改了 `local` 源代码后需要重建的场景。

为什么默认复用缓存：在大规模本地源场景下（如 70 个组件），如果每次都强制重新构建，体验会是灾难性的。构建是用户的显式动作，平台应信任用户知道何时需要重建。

### 11.3 `brickkit lint` 扩展

| 检查项 | 说明 |
| --- | --- |
| 必填项检查 | `config/` 里 `required` 字段是否都有值 |
| 重复 key 检查 | 升级冲突遗留的重复 key |
| 孤儿配置检查 | `config/` 里有但 `brickkit.yaml` 没有的组件配置 |
| 引用检查（`--strict`） | `${ENV_VAR}` 是否存在、`file://` 文件是否存在、`$var:` 引用的变量是否在 `vars.yaml` 中定义 |
| 部署一致性检查 | `deploy.yaml` 组件列表与 `brickkit.yaml` 是否一致 |
| 本地部署文件一致性检查 | `deploy.local.yaml`（若存在）组件列表与 `brickkit.yaml` 是否一致 |
| 外壳成员一致性检查 | `deploy.yaml` 的 `members` 中的组件是否都在 `brickkit.yaml` 中 |
| 特殊字符检查 | 配置值是否包含会破坏 JSON 序列化的控制字符（外壳场景） |

### 11.5 `brickkit init`

#### 两种模式

| 模式 | 命令 | 语义 | 典型场景 |
| --- | --- | --- | --- |
| 创建式 | `brickkit init <name>` | 新建目录 + 生成骨架 | 从零开始的新项目 |
| 补全式 | `brickkit init`（当前目录） | 缺什么补什么，已有不动 | 已有项目接入、组件内初始化工作台 |

两种模式底层共用同一套**补全原语**：扫描当前目录，对照"完整项目"的文件清单，缺失的创建，已有的跳过（`.gitignore` 除外，见下文安全校验）。9.6.1 节的自动巡逻（`add --local --init`）本质上就是对多个子目录批量调用此原语。

#### 创建式行为

生成目录结构：

```
my-shop/
├── .gitignore
├── brickkit.yaml
├── deploy.yaml             # 默认 target: docker 的空骨架
└── config/
    ├── .gitkeep
    └── vars.yaml           # 空的公共变量文件骨架
```

- 不生成 `deploy.local.yaml`（由 `brickkit local on` 按需生成）
- `.gitignore` 自动包含：`deploy.local.yaml`、`.secrets/`、`.brickkit/`、`config/.archive/`

#### 补全式行为

在当前目录执行 `brickkit init`（不带参数）：

**项目名来源：**

- 若当前目录已有 `brickkit.yaml` 且包含 `project` 字段 → 沿用
- 否则 → 默认取当前目录名（`basename`）
- `--name <name>` 可显式覆盖

**文件处理规则：**

| 文件 | 已存在时的行为 |
| --- | --- |
| `brickkit.yaml` / `deploy.yaml` / `config/vars.yaml` | 跳过，提示"已存在，跳过" |
| `.gitignore` | **安全校验**（见下文） |
| `config/.gitkeep` | 跳过 |

**`.gitignore` 安全校验（核心防线）：**

`.gitignore` 不能简单跳过。CLI 检查其是否包含必需的安全条目：

- `deploy.local.yaml`
- `.secrets/`
- `.brickkit/`
- `config/.archive/`

若缺失任何条目，**大声警告**并列出缺失项，提示用户手动补充。绝不静默放过——否则个人本地配置和密钥可能被误提交到 Git。

**交互确认：**

在非空目录执行时，先打印补全计划再执行：

```
检测到当前目录已有文件，brickkit init 将：
  ✅ 创建  deploy.yaml
  ✅ 创建  config/vars.yaml
  ⏭️  跳过  brickkit.yaml（已存在）
  ⚠️   .gitignore 缺少条目：.brickkit/
继续？[y/N]
```

`--yes` 跳过确认（CI/CD 用）。

**收尾校验：**

补全完成后自动执行一次轻量级 `lint`，确认项目达到"可 `up`"的完整状态。若校验失败，输出具体缺失项和修复建议。

#### 与分形架构的关系

补全式 `init` 是分形开发模式（16.1.1 节）的基础操作：组件作者在组件仓库内执行 `brickkit init`，即可为组件创建本地联调工作台。此时组件目录同时拥有 `component.yaml`（组件身份）和 `brickkit.yaml`（项目工作台），CLI 按 16.1.1 节的身份识别规则处理。

### 11.6 全局参数扩展

所有读取部署配置的命令（`up`, `down`, `status`, `sync` 等）新增 `-f, --file <path>` 参数。

- 不传参时：按原有逻辑执行（检查 `local` 状态，读取 `deploy.yaml` 或 `deploy.local.yaml`）。
- 传入参数时：强制且仅读取该文件（如 `deploy.prod.yaml`），完全忽略 `deploy.local.yaml` 和 `local on/off` 状态。如果指定的文件不存在，直接报错。

## 十二、配置迁移与升级

### 12.1 `brickkit upgrade` 命令形式

```
brickkit upgrade                        # 全部组件升到最新
brickkit upgrade erp/backend            # 单个升到最新
brickkit upgrade erp/backend@2.0.0      # 单个升到指定版本
```

全量升级：按拓扑排序逐个升级，遇不兼容立即报错停止（不跳过、不继续、不留半成品）。支持 `--dry-run`。

### 12.2 配置迁移算法

对比新旧 `configSchema`，只做机械 key 集合对比：

| 情况 | 处理 |
| --- | --- |
| 新旧都有该 key | 旧值抄到新文件 |
| 新有旧没有 | 有 `default` 填默认，没有留空 |
| 旧有新没有 | 不管，旧值留在归档文件 |

不做：不猜重命名、不做类型转换、不做语义分析。

### 12.3 冲突处理：重复 key 机制 + 注释 + CLI 友好报错

场景：用户改过某字段值，同时组件开发者在新版本也改了该字段 `default`。

判断逻辑：

| 情况 | 处理 |
| --- | --- |
| 只有开发者改 `default`，能确认用户没改 | 直接更新为新 `default` |
| 只有开发者改 `default`，确认不了 | 写两行重复 key |
| 用户改过，开发者也改了 | 写两行重复 key |
| 用户改过，开发者没改 | 保留用户值 |

重复 key 效果（带注释）：

```yaml
# ⚠️ 配置冲突：升级 erp/backend 到 2.0.0 时发现默认值变更。
# 请保留你需要的一行，删除另一行（及本注释），否则无法启动。
LOG_LEVEL: "debug"    # ← 你之前的值 (1.0.0)
LOG_LEVEL: "warn"     # ← 新版本建议值 (2.0.0)
```

YAML 解析器遇重复 key 直接报错，用户必须手动解决。

CLI 友好报错：当 `brickkit up` 或 `brickkit lint` 捕获到 `duplicate key` 的解析错误时，不打印冷冰冰的 Go 原始报错，而是拦截并格式化输出：

```
❌ 启动失败：检测到未解决的配置冲突！

文件: config/erp-backend.yaml
字段: LOG_LEVEL
  - 旧值: "debug" (你之前的值)
  - 新值: "warn" (erp/backend@2.0.0 建议值)

👉 你的 IDE 可能会将此文件标红为"语法错误"，这是正常的！
   这是 BrickKit 故意生成的合并冲突标记。
   请打开文件，保留一个值并删除多余行，然后重试。
```

为什么用重复 key 而非注释：注释是 passive 的，用户可能不看；重复 key 是 active 的，解析直接报错，不可能忽略。宁可 `up` 跑不了，也不让配置被悄悄覆盖。符合"大声失败"。

为什么在重复 key 旁加注释：让用户在 IDE 中看到红线时，能立刻明白"这是配置冲突"而非"BrickKit 生成了 Bug"。注释标明哪个是旧值、哪个是新值、怎么解决。

技术前提：YAML 解析器（`gopkg.in/yaml.v3`）需开启严格模式，显式拒绝重复 key。

**生态兼容性警告与 lint 拦截**

**生态风险：** YAML 规范对重复 Key 是未定义行为。部分第三方工具（如 `yq`、某些 IDE 的 YAML 格式化插件、Python `PyYAML`）在读取或保存包含重复 Key 的文件时，可能会**静默丢弃**其中一个值，或直接崩溃。这会导致 BrickKit 故意制造的"大声失败"被第三方工具悄悄抹平。

**防御机制：**

1. **文档警告：** 在故障排除文档中明确警告，解决配置冲突时**务必使用纯文本编辑器**（如 VSCode 纯文本模式、Vim、Sublime），切勿使用会自动格式化/保存 YAML 的工具。
2. **`brickkit lint` 精准识别：** `lint` 命令不能仅仅抛出底层的 `yaml: unmarshal errors (line X: mapping key "LOG_LEVEL" already defined)`。它必须能精准识别 BrickKit 故意生成的"带注释的重复 Key 冲突标记"，并输出友好的修复指引：

```
❌ 检测到未解决的升级冲突！

文件: config/erp-backend.yaml
字段: LOG_LEVEL

👉 你的 IDE 可能会将此文件标红，这是正常的。
   请务必使用**纯文本编辑器**打开文件，保留你需要的一行并删除多余行。
   ⚠️ 警告：切勿使用 `yq` 或 IDE 的 "Format Document" 功能，这会导致配置静默丢失！
```

### 12.4 `brickkit remove` 配置归档

移除组件时，配置文件不直接删除，移入 `config/.archive/`。重新 `add` 时可恢复（按 12.2 和 12.3 的迁移算法处理，见 7.7 节）。

## 十三、常见疑问与解答（FAQ）

### 配置与部署

**Q1: 为什么不保留 `resources`？**
A: `resources` 本质只是拼连接串注入环境变量。组件真正需要的只是那几个环境变量。中间那层是平台替组件做决定，限制了读写分离、多实例等场景。废除后组件只读环境变量，更灵活。

**Q2: 多个组件共享同一数据库，每个 config 都写一遍不冗余吗？**
A: 通过 `config/vars.yaml` + `$var:` 显式引用解决。公共值（如 `DB_HOST`、`REDIS_PASSWORD`）定义在 `vars.yaml` 中，各组件配置文件通过 `$var:DB_HOST` 显式引用。修改公共值只需改 `vars.yaml` 一处。同时每个组件配置文件依然列出所有 Key，保持自包含和可见性。

**Q3: 字段重命名了怎么办（如 `MAX_RETRIES` → `RETRY_COUNT`）？**
A: BrickKit 不检测重命名。对它来说就是"删了一个、加了一个"。旧值留在归档文件，新字段有 `default` 走 `default`，没有就留空。`required` 无默认则 `up` 拒绝启动（大声失败）。不做相似度猜测，猜错比不猜更危险。

**Q4: 为什么用重复 key 而不是注释标记冲突？**
A: 注释被动，用户可能不看；重复 key 主动，解析直接报错，不可能忽略。宁可 `up` 跑不了，也不让配置被悄悄覆盖。重复 key 旁边的注释用于引导用户理解冲突内容，而非替代报错。

**Q5: 只有开发者改了 `default`，用户没改，怎么处理？**
A: 能确认用户没改（当前值==旧版本 `default`）→ 直接更新为新 `default`。确认不了 → 写重复 key 让用户选。不猜。

**Q6: 全量升级遇不兼容怎么办？**
A: 立即报错停止，不跳过不继续。按拓扑序升级，依赖升失败则后续无意义。用户已被告知是毁灭性操作。

**Q7: `deploy.local.yaml` 会不会被误提交到生产？**
A: 不会。它在 `.gitignore` 里，且需 `brickkit local on` 显式开启。生产环境不存在此文件，也不会有开启状态。

**Q8: 为什么 `deploy.local.yaml` 是完整替换而非属性覆盖？**
A: 属性覆盖需要定义复杂的合并规则（数组怎么合、对象怎么覆盖），增加心智负担。完整替换简单可预测：开启本地模式后只看 `deploy.local.yaml`。对于 AI 来说，读取一个完整文件比解析差异文件更直接，不需要额外理解"父文件 + 差异文件 = 最终状态"。

**Q9: 为什么 `mode: debug` 只能放 `deploy.local.yaml`？**
A: `debug` 是"我个人此刻在调试"的状态，是个人事实，不该进 Git 被团队评审。`mode: local`（BrickKit 托管的本地进程）是项目级决策，可以进 `deploy.yaml`。

**Q10: 为什么不把端口和 k8s 配置放 `config/`？**
A: `config/` 是"组件进程要读的环境变量"（如 `DB_HOST`）。端口（`exposePort`）、`hostname`、`replicas` 是"编排器怎么部署"的配置，组件进程无感知。判断标准：这个值是注入给组件当环境变量，还是告诉编排器怎么部署？前者进 `config/`，后者进 `deploy.yaml`。

**Q11: `$var:` 和 `${}` 有什么区别？**
A: `$var:XXX` 从 `config/vars.yaml` 读取（项目级公共变量）。`${XXX}` 从操作系统环境变量读取（运行时环境）。两者语义完全不同，不可混用。

**Q12: `vars.yaml` 中的值能否引用其他变量？**
A: 允许引用环境变量（如 `${SECRET_DB_PASSWORD}`），不允许引用其他 `vars` 变量（如 `$var:OTHER_VAR`）。这避免了复杂的依赖图解析，保持极简。

**Q13: 多环境（Dev/Staging/Prod）怎么切换？**
A: 保持文件扁平，不引入 overlay。通过 `--file deploy.prod.yaml`（或 `-f`）参数显式指定读取的部署文件，该文件可包含 `vars:` 覆盖生产环境的变量值。

**Q14: 为什么不为小项目提供"单文件模式"？**
A: 概念一致性远比文件数量重要。如果引入"单文件模式"，用户需要理解两个概念（"小项目用单文件，大项目用三层"），需要记住额外的转换命令，需要判断"我的项目长大了吗"。坚持强制三层架构，无论项目规模大小，心智模型永远是"声明、部署、配置"三层。用户学会一次，终身受用。项目从小长大时，不需要任何"重构"或"拆分"操作，架构天然平滑扩展。对于小项目，`deploy.yaml` 可能只有 5 行，`config/` 里可能只有一个 10 行的文件。物理上多点开两个文件，换来的是职责边界的绝对清晰。

**Q15: `deploy.local.yaml` 过期了怎么办？**
A: 严格一致性校验会在 `up` 等命令执行前拦截并报错，告知缺失了哪些组件。用户可执行 `brickkit local refresh` 重新生成最新的本地配置（旧文件自动备份为 `.bak`），然后手动将之前的 `debug` 或 `localPort` 配置合并回来。

### 外壳机制

**Q16: 外壳和组件为什么是 1:N？**
A: 外壳的语义是"组件代码被编入外壳进程"，是物理包含关系。一份代码不能同时编进两个进程。若需两个外壳提供类似功能，应是两个组件或通过依赖共享逻辑。

**Q17: 为什么 `members` 放 `deploy.yaml` 而不是 `brickkit.yaml`？**
A: 成员关系本质是"部署分组"（哪些组件一起跑在一个进程里），属于部署层职责。`brickkit.yaml` 只管"有什么组件"，职责纯粹。避免两处维护同一关系。

**Q18: 为什么 `servedBy` 被 `members` 取代？**
A: `servedBy`（成员视角"我被谁承载"）和 `members`（外壳视角"我承载谁"）描述同一关系。保留两个需维护一致性。选 `members` 因为它在 `deploy.yaml`（部署层），且从外壳角度看分组更自然。`brickkit.yaml` 用 `kind: shell` 标记外壳即可。

**Q19: 外壳里多个组件的环境变量会冲突吗？**
A: 不会。外壳是单体进程模型，配置通过 JSON 注入（`BRICKKIT_SERVED_MEMBERS_CONFIG`）。每个成员的配置在 JSON 数组中是独立的对象，天然隔离。外壳启动代码在进程内部分发配置，不存在"两个进程抢同一个环境变量"的问题。

**Q20: 外壳配置中的多行密钥（如 PEM）会不会破坏 JSON？**
A: CLI 在生成部署文件前，会先完成所有 `${VAR}` 和 `file://` 的解析，并对值进行安全的 JSON 编码（转义控制字符）。如果值包含无法安全编码的字符，CLI 会在 `lint` 或 `up --dry-run` 时大声失败，而不是等到容器启动后崩溃。

**Q21: 外壳自身有配置吗？**
A: 有。外壳对 BrickKit 来说就是一个普通组件，可以拥有自己的 `configSchema` 和配置文件（`config/erp-shell.yaml`）。外壳自身的配置通过普通环境变量注入外壳容器，与成员配置通过 `BRICKKIT_SERVED_MEMBERS_CONFIG` JSON 注入是并存的。外壳内部的通信、配置分发由外壳作者在启动代码中处理，BrickKit 平台不介入。

### 无 Market 分发

**Q22: 没有 Market 怎么拉特定版本？**
A: 每个组件一个 Git 仓库，版本用 Git tag 标记。本地维护 Bare Repo，通过 `git fetch --tags` 增量更新，`git show <tag>:component.yaml` 读取。Git tag 不可变，任意历史版本都能拉。

**Q23: 本地源为什么不需要是独立 Git 仓库？**
A: 本地源是纯粹的"当前开发态"，代表"我正在改的代码"。CLI 只读当前工作区的 `component.yaml`。开发者想看历史版本自己用 Git 切分支/Tag。强制独立 Git 仓库会导致 Monorepo 场景下的嵌套仓库问题，且"离线切换本地源历史版本"是伪需求。

**Q24: 为什么不做跨机器复现（Lock File）？**
A: 精确版本不可变 + 永久缓存 + Git tag 已能保证版本可复现。`brickkit.yaml` 实际上充当了 Lock File 的角色（写死精确版本）。引入额外 Lock File 多一份要维护的文件，可能和 `brickkit.yaml` 不同步。

**Q25: `fetch` 为什么不取镜像？**
A: 镜像很大，`fetch` 语义是"取元数据"。镜像在 `brickkit up` 时才需要，届时再拉取或构建。`fetch` 只取 Manifest 和契约文件（`artifacts`），保持轻量。

**Q26: `release` 推送失败为什么回滚本地 tag？**
A: 为了原子性。若保留本地 tag，会留下"本地有、远端没有"的中间状态，造成混乱。回滚后用户可直接重试 `release`，代码和版本号都还在，不会丢。

**Q27: `release` 为什么要求代码已推送到远端分支？**
A: 防止"孤岛 Tag"：tag 指向的 commit 不在远端任何分支历史中。这会导致别人通过分支看不到该版本的代码，破坏 Git 历史连贯性，给后续热修复和代码审查带来困扰。

**Q28: 私有组件仓库怎么鉴权？**
A: BrickKit CLI 不处理鉴权。完全依赖宿主机的 Git 配置（SSH key、credential helper、`.netrc`、CI Token 等）。鉴权失败时，CLI 透传 `git` 的错误信息并给出友好提示。

**Q29: `brickkit add erp/backend` 不指定版本，拉的是哪个版本？**
A: 远端仓库的最新 Tag。CLI 查找所有 tag，取版本号最高的，将精确版本写入 `brickkit.yaml`。如果用户想要特定版本，使用 `brickkit add erp/backend@1.0.0`。

**Q30: 依赖版本不一致会报错吗？**
A: 不会。BrickKit 支持多版本共存。如果组件 A 依赖 B@1.0.0，而项目已有 B@2.0.0，CLI 会自动拉取 B@1.0.0。利用精确版本化服务名（`b-1-0-0` vs `b-2-0-0`）天然隔离，互不干扰。

### 数据库迁移

**Q31: 废除 `resources` 后，数据库迁移怎么办？**
A: 平台继续生成 Migration Service（一次性迁移容器），但不再拼装连接串。CLI 将组件的所有配置环境变量原封不动地注入给迁移容器，由组件自己的 `migration.command` 脚本负责从这些环境变量中读取所需信息并执行迁移。多版本共存时的迁移顺序控制（`depends_on` 链条）依然由平台负责。

**Q32: 为什么不让组件自己在 `main()` 里跑迁移？**
A: 多版本共存时（如 `1.0.0` 和 `2.0.0` 同时运行），如果组件自己跑迁移，会并发竞争导致数据库 schema 损坏。平台生成独立的迁移容器并通过 `depends_on` 控制顺序，能优雅地解决这个问题。

### 镜像分发与构建

**Q33: 没有 Market，组件的 Docker 镜像从哪里来？**
A: 采用"预构建镜像为可选，本地构建为显式动作"的策略。`brickkit up` 绝不自动 build。若无预构建镜像，用户需显式执行 `brickkit build`。构建出的镜像 tag 严格与 `component.yaml` 的 `metadata.version` 对齐。

**Q34: 本地构建会不会很慢？**
A: `brickkit build` 是显式命令，用户可以选择在合适的时机执行（如首次拉取项目时）。构建出的镜像会缓存在本地，后续 `brickkit up` 直接复用，不会重复构建。当组件作者推送了预构建镜像（声明 `image` 字段）后，用户无需再执行 `brickkit build`。

**Q35: 修改了本地源代码，`brickkit build` 为什么没有重新构建？**
A: `brickkit build` 默认复用缓存（镜像已存在且版本未变则跳过）。修改代码后需显式执行 `brickkit build <component-id> --force` 强制重新构建。这是"构建是用户的显式动作"原则的体现——平台不替用户判断"代码是否变了"。

### 归档恢复

**Q36: 归档恢复和升级是什么关系？**
A: 本质完全一样。都是"手里有一份旧版本的配置文件，现在要适配新版本的 `configSchema`"。归档恢复完全复用升级的"配置迁移算法"（12.2 节）和"冲突处理机制"（12.3 节），而非直接复制文件。这保证了跨版本恢复时的安全性。

### AI 友好性

**Q37: 三层架构会不会让 AI 更难理解项目？**
A: 不会。三层文件各司其职，AI 按需读取对应文件即可：想知道有什么组件 → 读 `brickkit.yaml`；想知道怎么部署 → 读 `deploy.yaml`；想知道环境变量 → 读 `config/*.yaml`。每个文件信息密度极高且职责纯粹，比在一个巨大的合并视图里寻找信息更高效。`AGENTS.md` 会提供清晰的"文件职责地图"，引导 AI 按需检索。

### 补全式初始化

**Q38: `brickkit init` 不带参数在已有目录执行会怎样？**
A: 执行补全式初始化：缺什么补什么，已有文件不动。`.gitignore` 例外——若已存在但缺少安全条目（如 `deploy.local.yaml`、`.brickkit/`），CLI 会大声警告而非静默跳过，防止个人本地配置被误提交到 Git。补全完成后自动跑一次轻量 `lint` 确认项目完整性。在非空目录执行时会先打印补全计划并等待确认（`--yes` 可跳过）。

## 十四、不在本提案范围内的事项

| 事项 | 理由 |
| --- | --- |
| 配置继承 / overlay / 多环境合并 | 违背"每个环境一份完整配置"哲学，通过 `--file` 显式切换替代 |
| 配置热更新 / 动态推送 | 违背"没有配置中心"哲学 |
| 字符串插值（`"postgres://${USER}@host"`） | 增加复杂度，组件代码自行拼接 |
| 隐式共享配置引用（Fallback 查找） | 违背"所见即所得"和"自包含"原则，用 `$var:` 显式引用替代 |
| 重命名检测 / 类型转换 | 平台不做语义推断 |
| 全量升级依赖链求解 | 第一版按拓扑序逐个升，不兼容就停 |
| `configSchema` 值的类型校验 | 维持"说明书，不是安检机" |
| 多版本外壳共存 | 外壳单版本约束 |
| 跨机器复现（额外 Lock File） | `brickkit.yaml` 已充当 Lock File 角色 |
| Market 服务器部署 | 本提案前提是不部署 Market |
| 组件注册表 | 第一版靠约定 + 文档 |
| Semver 范围约束与依赖树求解 | 平台极简，不做范围计算，`brickkit.yaml` 写死精确版本 |
| 本地源历史版本缓存 | 本地源是纯开发态，历史版本由开发者自己用 Git 管理 |
| `repoTemplate` 自定义映射 | 极小概率冲突，用 `source.repo` 显式覆盖即可 |
| BrickKit 自行处理鉴权 | 依赖宿主机 Git 环境，平台不接触凭据 |
| 外壳内部网络通信模型 | 外壳作者自己负责，平台不介入 |
| 单文件模式 / 项目规模自适应 | 违背"概念一致性"原则，所有项目统一三层架构 |
| `deploy.local.yaml` 深度融合 / 属性覆盖 | 违背"所见即所得"原则，坚持完整替换 + 严格校验 |
| `brickkit up` 自动构建镜像 | 违背"构建与部署分离"原则 |
| 合并视图命令（如 `brickkit inspect`） | 违背"按需检索"原则，增加不必要的复杂度 |

## 十五、总结

本提案的核心思想：

1. **三层各司其职：** `brickkit.yaml` 管"有什么"，`deploy.yaml` 管"怎么部署与环境覆盖"，`config/` 管"组件需要什么环境变量"。
2. **配置有版本、有归档、有冲突检测、有敏感值保护、有公共变量显式引用（`$var:`）。**
3. **部署有团队方案与个人本地方案的清晰分离，** 通过 `--file`（或 `-f`）优雅支持多环境切换，不引入复杂合并逻辑。`deploy.local.yaml` 坚持完整替换，通过严格一致性校验防止静默缺失，通过 `local refresh` 保护用户本地调试资产。
4. **外壳机制是单体进程模型，** 通过 JSON 注入传递配置，不存在环境变量冲突。`members` 实现优雅的分组与解组。
5. **数据库迁移机制在废除 `resources` 后依然有效：** 平台透传所有配置环境变量，由组件自己的迁移脚本负责执行，并保证多版本迁移顺序。
6. **无 Market 时通过 Git 仓库 + Git tag + Bare Repo 增量 fetch + 永久缓存实现可靠的特定版本分发。**
7. **镜像分发采用双模式策略且职责分离：** 预构建镜像为可选，本地构建为显式动作（`brickkit build`），`brickkit up` 绝不自动构建。镜像 Tag 与组件版本严格对齐。
8. **版本管理不做 Semver 求解，** `brickkit.yaml` 写死精确版本，充当项目的 Lock File，并天然支持多版本共存。
9. **归档恢复等同于升级，** 完全复用配置迁移算法和冲突处理机制，确保跨版本恢复的安全性。
10. **概念一致性：** 无论项目规模大小，心智模型永远是三层。不提供单文件回退，不引入因规模不同而需要切换的额外概念。
11. **按需检索优于全量合并：** 三层文件各司其职，AI 和人类均按需读取，不引入合并视图命令。
12. **补全式初始化：** `brickkit init` 支持在当前目录执行（不带参数），缺什么补什么，已有不动。`.gitignore` 安全校验确保敏感文件不被遗漏。补全原语与分形架构的组件内初始化、9.6.1 的自动巡逻共用同一套逻辑。
13. **平台不做语义推断、不做隐式覆盖、不做鉴权、不做依赖范围计算、不做自动构建，** 一切冲突大声暴露，并提供友好的 CLI 引导。

这不是给 BrickKit 加功能，而是把已有能力重新组织，让开发者的心智负担从"一个巨大的 YAML 文件"变成"三个职责清晰的层"，并在不依赖 Market 的前提下依然能可靠地管理和分发特定版本的组件。

## 十六、组件文档规范与分形架构（套娃机制）

### 16.1 分形架构的本质

BrickKit 规范是分形（递归）的：

- **开发态（项目视角）：** 一个组件仓库在独立开发时，它就是一个完整的 BrickKit 项目，可以拥有自己的 `brickkit.yaml`、`deploy.yaml` 和 `components/`（用于本地联调依赖）。
- **消费态（组件视角）：** 当该组件被发布（`release`）并被其他主项目引用（`add`）时，主项目**只将其视为一个叶子节点**。主项目不会去解析子组件内部的 `brickkit.yaml` 或 `components/`，而是只读取它的 `component.yaml`（契约）和组件文档。
- **物理不套娃，规范套娃：** 主项目的 `components/` 目录下平铺着各个本地源组件，但这些组件内部遵循着与主项目完全相同的 BrickKit 规范。

#### 16.1.1 分形开发模式（Component as a Project）

BrickKit 规范是分形（递归）的：一个组件在独立开发时，它本身就是一个完整的 BrickKit 项目。

**开发态（本地工作台）：**
组件作者在组件仓库根目录执行 `brickkit init`（**补全式**，见 11.5 节）。由于组件仓库已有 `component.yaml`、源码等文件，补全式 `init` 会跳过已有文件，只补充缺失的 `brickkit.yaml`、`deploy.yaml` 和 `config/`。作者可以通过 `brickkit add` 引入该组件的依赖（如 `infra/db`），在本地拉起完整的依赖树进行联调。此时，`brickkit.yaml` 是作者的"本地工作台"。

**消费态（黑盒契约）：**
当主项目通过 `brickkit add` 引入该组件时，CLI 只读取远端 Git Tag 对应的 `component.yaml`（契约）和 `BRICKKIT.md`（文档）。主项目**完全无视**组件内部的 `brickkit.yaml` 及其本地联调环境。主项目根据 `component.yaml` 中的 `dependencies` 字段自行解析依赖树。

**CLI 身份识别与 `release` 行为：**

当一个仓库同时存在 `component.yaml` 和 `brickkit.yaml` 时：

- 执行 `up`、`add` 等命令时，CLI 将其视为"项目"，操作的是本地工作台。
- 执行 `release` 命令时，CLI 强制以 `component.yaml` 为准进行校验和打 Tag，完全忽略 `brickkit.yaml` 中的内容。这保证了发布的纯粹性，本地联调用的临时组件不会被污染到发布的版本中。

`.brickkit/` 缓存不进 Git：`.brickkit/` 是可再生的缓存目录（在 `.gitignore` 中）。第一次 `git clone` 项目后，`.brickkit/` 不存在，数据由 CLI 在执行 `add`、`up` 等命令时自动从组件的远端 Git 仓库按需拉取（见 9.4 节读取优先级）。这与 `package.json` 进 Git 但 `node_modules` 不进 Git 的逻辑完全一致。

### 16.2 组件文档规范（`BRICKKIT.md`）

为了让 AI 和人类在消费组件时能快速理解其边界、配置和用法，任何遵循 BrickKit 规范的组件，必须在其仓库根目录提供 `BRICKKIT.md`（或在 `README.md` 中包含明确的 `## BrickKit` 区块）。

`BRICKKIT.md` 的标准结构：

1. **组件定位：** 一句话说明该组件解决什么业务问题。
2. **依赖说明：** 它强/弱依赖了哪些其他组件（人类可读的解释，而非冷冰冰的 YAML）。
3. **配置指南（核心）：** 对 `configSchema` 中关键环境变量的业务含义进行解释（特别是那些 `default` 无法表达清楚的复杂配置）。
4. **契约索引：** 指向 `artifacts` 中声明的 OpenAPI / Proto 等契约文件的路径。
5. **外壳声明（可选）：** 如果它是一个外壳（`kind: shell`），说明它能承载哪些类型的成员，以及成员需要满足什么条件。

#### 16.2.1 规范的分形放置

组件文档规范本身也是分形的，存在于三个层级：

| 层级 | 文件 | 职责 | 谁生成 |
| --- | --- | --- | --- |
| 定义层（平台级） | `AGENTS.md` § 组件文档规范 | 规范的"宪法"：定义 `BRICKKIT.md` 的标准结构、字段、AI 读取规则 | 平台维护 |
| 实例层（项目级） | 每个项目根目录的 `BRICKKIT.md` | 规范在该项目的"实例化"：列出当前项目的所有组件及其文档位置 | `brickkit init` 自动生成 |
| 内容层（组件级） | 每个组件仓库根目录的 `BRICKKIT.md` | 规范在该组件的"内容填充"：组件定位、依赖、配置指南、契约索引 | `brickkit new` 自动生成骨架，作者填写 |

AI 的读取路径（三层路由）：

1. 读 `AGENTS.md`（平台级）→ 理解"文档规范是什么"、"三层文件架构"、"套娃读取规则"
2. 读项目的 `BRICKKIT.md`（项目级）→ 理解"这个项目有哪些组件"、"每个组件的文档在哪"
3. 按需读组件的 `BRICKKIT.md`（组件级）→ 理解"这个组件怎么用"

### 16.3 CLI 行为：文档级联缓存

当用户执行 `brickkit add` 或 `brickkit fetch` 时，CLI 不仅拉取 `component.yaml`，还会自动拉取并缓存 `BRICKKIT.md`（如果存在）。

缓存路径：`.brickkit/manifests/<scope>/<name>/<version>/BRICKKIT.md`

这保证了即使离线，或者组件作者更新了远端文档，本地依然有一份与当前锁定版本（`brickkit.yaml` 中的版本）严格对应的文档快照。

### 16.4 AI 路由表更新（套娃读取）

基于分形架构，AI 的检索路径扩展为：

1. 想知道当前主项目有什么组件？ → 读主项目的 `brickkit.yaml`。
2. 想知道当前主项目怎么部署的？ → 读主项目的 `deploy.yaml`。
3. 想知道某个依赖组件（如 `erp/backend@2.0.0`）的具体配置含义或 API 用法？ → 直接读 `.brickkit/manifests/erp/backend/2.0.0/BRICKKIT.md`，无需翻阅源码，也无需主项目作者重复编写依赖的文档。

| A7 | CLI 提前求值的值落在哪 | 外壳 JSON、`file://` 等 CLI 提前解析的值不明文写进 `compose.yaml`：Docker 写入 `.brickkit/` 下 0600 的 env 文件（转义 `$`），K8s 进 Secret |
| A8 | 本地源版本号 | 本地源条目写 `component.yaml` 里的真实版本 + `source: local`，不用字面量 `version: local`（否则依赖精确匹配失败） |
| A9 | monorepo 子目录 `release` | 组件目录不是仓库根时，tag 用 `<scope>-<name>/<version>` 命名空间，拉取端同样识别。需实测确认 |

| A13 | 文档 | 按"文档修改-布局.md"结构，一篇只讲一件事、靠路由快速定位；过薄的篇目写完后再议合并。`tutorials/` 先只建目录 |
| A14 | CLI 侧 Market 功能 | **继续可用**：`sources[].type: market` 作为可选源与 git/local 并存；`publish` 保留（发布到 market），`release` 新增（Git tag）；`login`/`logout` 照常工作；签名配置 `installer`（`requireSignature` / `publicKeys`）留在 `brickkit.yaml`。更正 11.0 "publish → release 重命名" |
| A15 | 其他既有字段去向 | `networkPolicy`、`serviceAccount`、`podSecurity`、`imagePullSecrets`、`ingressClass/Annotations`、`namespace`、`createNamespace`、组件 `labels` / `resources` 配额 → `deploy.yaml`。`target: podman` 在 `deploy.yaml` 与 `deploy.local.yaml` 均可写，原"只能降级"限制随 `override.yaml` 一起取消 |
| A16 | `local on/off` 状态 | `off` 不删 `deploy.local.yaml`，只停止读取；开关状态记在 `.brickkit/` |
| A17 | 旧格式迁移 | 不提供旧 `brickkit.yaml` → 三层文件的迁移命令（尚无外部用户） |
| A18 | 外壳成员的 `mode` | 外壳成员**必须可以**设置 `mode: debug` / `mode: local`（该成员改为裸进程运行，具体语义——如何从外壳的服务成员中移出、`_ENDPOINT` 如何指向——在 P3 设计） |
| A19 | `deploy.yaml` 中 K8s 字段的位置 | 项目级 K8s 设置（context、namespace、网络策略等）放顶层 `k8s:` 块；组件级 K8s 字段（`replicas`、`hostname`、`tlsSecret`、`serviceAccountName`、`resources`）仍写在各自组件条目上。`target` 不是 k8s 时这些字段只给警告、命令照常执行 |
| A20 | 默认版本与 `requiredBy` | 同一个组件 ID 在 `brickkit.yaml` 里恰好有一行不带 `requiredBy`，那就是**默认版本**：本地仓库（有的话）就是这个版本，外壳承载它，部署文件的裸 ID 条目与无版本号配置文件都指它。只因别的组件依赖而存在的版本写 `requiredBy: [<依赖它的组件 ID>]`，一眼可知它为兼容而在（可能比默认版本新）。维护规则：`add` 为依赖加入另一个版本时写上 `requiredBy`；`upgrade` 把默认版本升到一个原本带 `requiredBy` 的版本时去掉它，旧的默认版本若仍被依赖就加上 `requiredBy`，否则移除；依赖方升级或移除后没人再要的版本由 `upgrade` / `remove` 清掉（配置归档）。部署文件的裸 ID 条目只覆盖默认版本，其余版本必须有自己的 `id@version` 条目 |
| A21 | 外壳成员在部署文件里的写法 | 成员作为**完整部署条目**嵌在外壳条目的 `members` 下面（只嵌一层），文件里每个组件版本只出现一次。外壳在跑：下面的成员都在外壳进程里，不单独启动（多版本兼容的其他版本在顶层独立部署）；外壳不跑：成员按自己条目里的字段（`expose`、`mode`、K8s 字段……）独立部署——这些字段在外壳跑着时暂不生效，也不警告。取代 §6.1/§8.4 示例里"`members` 是 ID 列表、成员条目写在顶层"的写法 |
| A22 | 本地仓库版本必须等于默认版本 | 代码从本地仓库运行时（`mode: local` / `mode: debug` 的组件、以裸进程运行的外壳的成员），`up` 检查 `brickkit.yaml` 默认版本与本地仓库 `component.yaml` 的 `metadata.version` 一致，不一致即报错并提示 `brickkit upgrade <id>@<仓库版本>` 或把仓库切到对应 tag（P4 实现）。容器部署拉镜像，不查。文档（P9）写明：使用外壳时升级后要自己检查成员兼容性——外壳调用的是本地仓库里的成员代码，而仓库版本跟着 `brickkit.yaml` 走 |
