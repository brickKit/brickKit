## 二、AGENTS.zh.md（完全重写）

````markdown
# BrickKit（中文版）

> 如果你是 AI 助手，这是你理解整个平台的唯一入口。读完这一份文件，
> 你就知道该去哪里找什么、不该读什么、以及这个平台的设计边界在哪里。

## §1 平台定位（一段话）

BrickKit 是一个声明式组件组装平台，基于三层文件架构：
- `brickkit.yaml`：组件声明（有什么组件、什么版本）
- `deploy.yaml` / `deploy.local.yaml`：部署配置（怎么部署）
- `config/`：业务配置（组件需要什么环境变量）

声明组件和依赖，CLI 派生其余一切（启动顺序、服务地址、环境变量、部署文件），
然后交给 Docker 或 Kubernetes 执行，自身退出。
无注册中心、无配置中心、无网关、无守护进程。

## §2 核心设计原则（十条）

1. **大声失败**：配置冲突、必填缺失、重复 key、推送失败必须在操作时暴露
2. **平台极简**：不做语义推断，只做机械操作
3. **所见即所得**：没有隐式覆盖，看到的文件就是实际生效的配置
4. **组件自治**：组件需要什么配置由自己的 configSchema 声明
5. **职责单一**：每个文件只管一件事
6. **原子性操作**：关键操作要么完全成功，要么完全回滚
7. **显式优于隐式**：$var: 显式引用，不引入隐式 Fallback
8. **概念一致性**：无论项目规模，永远是三层
9. **构建与部署分离**：up 绝不自动 build
10. **按需检索优于全量合并**：不做合并视图命令

## §3 三层文件架构

### 3.1 文件检索地图

| 想知道什么 | 读哪个文件 |
|-----------|-----------|
| 项目有什么组件、什么版本 | `brickkit.yaml` |
| 组件怎么部署的（端口、模式、外壳成员） | `deploy.yaml`（或 `deploy.local.yaml`） |
| 组件的环境变量（连接串、密钥、开关） | `config/<component-id>.yaml` |
| 公共变量定义 | `config/vars.yaml` |
| 组件的依赖、能力声明、configSchema | `.brickkit/manifests/` 或源码里的 `component.yaml` |
| 依赖组件的用法和配置含义 | `.brickkit/manifests/<id>/<version>/BRICKKIT.md` |

### 3.2 关键规则

- `deploy.local.yaml` 是完整替换，不是属性覆盖
- `mode: debug` 只能放 `deploy.local.yaml`，不进 Git
- `$var:XXX` 从 `config/vars.yaml` 读取，`${XXX}` 从环境变量读取
- 不做隐式环境变量覆盖
- 不做合并视图命令
- `brickkit up` 绝不自动构建镜像
- `brickkit init`（不带参数）支持补全式初始化：缺什么补什么，已有不动，`.gitignore` 缺失安全条目时大声警告

### 3.3 分形架构（套娃机制）

- **开发态**：组件仓库就是一个完整的 BrickKit 项目（有自己的三层文件）
- **消费态**：主项目只读组件的 `component.yaml`（契约）和 `BRICKKIT.md`（文档）
- **物理不套娃，规范套娃**
- `brickkit add` 时自动缓存 `BRICKKIT.md` 到 `.brickkit/manifests/`

### 3.4 AI 三层路由

1. 读本文件（`AGENTS.zh.md`）→ 理解规范和检索路径
2. 读项目的 `BRICKKIT.md` → 知道有哪些组件、文档在哪
3. 按需读组件的 `BRICKKIT.md`（`.brickkit/manifests/` 下）→ 理解具体组件

## §4 外壳机制速查

- 单体进程模型，1:N 关系
- 配置通过 `BRICKKIT_SERVED_MEMBERS_CONFIG` JSON 注入
- `members` 在 `deploy.yaml`（唯一来源），`kind: shell` 在 `brickkit.yaml`（只是标记）
- 外壳自身也是一个组件，有自己的 `configSchema` 和配置文件
- `_ENDPOINT` 平台底层自动重写为外壳地址（反向索引机制），外壳作者仅负责进程内的路由分发
- 多行密钥（PEM）由 CLI 预解析 + JSON 编码，控制字符大声失败

## §5 命令集（20 个 + version + lang）

| 命令 | 核心行为 |
|------|----------|
| `init` | 生成三层文件骨架（创建式）或在当前目录补全缺失文件（补全式，不带参数） |
| `skills` | 管理 AI 助手技能 |
| `graph` | 依赖拓扑（Mermaid） |
| `lint` | 离线检查（八项） |
| `new` | 组件骨架（`--shell` 生成外壳） |
| `add` | 拉取组件，写入三层文件 |
| `remove` | 移除组件，配置归档 |
| `fetch` | 只取 Manifest 和契约 |
| `upgrade` | 升级 + 配置迁移 + 冲突处理 |
| `up` | 生成部署文件 → 迁移 → 起容器（绝不自动 build） |
| `down` | 停止容器（不删 volume） |
| `status` | 运行状态表格 |
| `sync` | 源码目录归档/激活 |
| `local` | 管理 `deploy.local.yaml`（on/off/status/refresh） |
| `restore` | 还原到最后一次提交 |
| `deps` | 依赖拓扑树 |
| `build` | 显式构建镜像（`--force`） |
| `release` | 校验 + 打 Git tag + push（原子性） |
| `login` | 登录市场（预留） |
| `logout` | 退出市场（预留） |

### 全局参数

| 参数 | 说明 |
|------|------|
| `-f, --file <path>` | 强制指定部署配置文件 |
| `--no-local` | 本次忽略 `deploy.local.yaml` |
| `--dry-run` | 只生成不执行 |
| `--log-level <level>` | 日志级别 |

### 废除的命令和参数

| 废除 | 替代 |
|------|------|
| `override` | `deploy.local.yaml` + `brickkit local` |
| `publish` → `release` | 校验 + 打 Git tag + push |
| `up --context` | `--file` 指定不同部署文件 |
| `--deploy-file` → `-f, --file` | 更简洁 |

## §6 "不做"清单

| 不做 | 理由 |
|------|------|
| 服务注册/发现 | DNS 就是服务发现 |
| 长驻守护进程 | CLI 跑完就退出 |
| 健康检查轮询 | K8s probes / Compose healthchecks 原生做 |
| API 网关 | 组件直接 DNS 通信 |
| 配置中心/热更新 | 改 `deploy.yaml` 然后 `up` |
| 熔断/限流 | 组件自己的业务逻辑 |
| 版本范围（`^1.0.0`） | 精确版本是契约 |
| 多环境覆盖继承 | 每个环境一份完整文件 |
| 自动构建镜像 | 构建是用户的显式动作 |
| 合并视图命令 | 按需检索优于全量合并 |
| 单文件模式 | 概念一致性，永远是三层 |
| 隐式配置覆盖 | 所见即所得 |
| 鉴权处理 | 依赖宿主机 Git 配置 |

## §7 配置迁移与冲突处理

- 升级 = 对比新旧 `configSchema`，机械 key 集合对比
- 冲突 = 重复 key（YAML 解析器报错，大声失败）
- 归档恢复 = 升级（走同一套迁移算法）
- 不猜重命名、不做类型转换、不做语义分析

## §8 无 Market 分发

- Git 仓库 + Git tag + Bare Repo 增量 fetch
- `.brickkit/repos/`（bare repo）+ `.brickkit/manifests/`（永久缓存）
- 四级读取优先级（缓存 → 本地 show → 增量 fetch → 首次 clone）
- CLI 不处理鉴权，透传 `git` 错误
- `brickkit release` = 校验 + 打 tag + push（原子性）
- `brickkit release --local` = 批量发布，遇错立即停止
````
