## 全局参数

所有读取部署配置的命令（`up`、`down`、`status`、`sync`、`lint`）均支持：

| 参数 | 说明 |
| --- | --- |
| `-f, --file <path>` | 强制指定部署配置文件（如 `deploy.prod.yaml`），完全忽略 `deploy.local.yaml` 和 `local on/off` 状态。文件不存在则报错。 |
| `--no-local` | 本次运行忽略 `deploy.local.yaml`（一次性，不改变 `local` 状态） |
| `--dry-run` | 只生成部署文件，不实际执行（供审查） |
| `--log-level <level>` | 日志级别：`off` / `warn`（默认）/ `info` / `debug` |

## 各命令详细说明

### 1. `brickkit init [<name>]`

创建新项目，或在当前已有目录中补全三层架构骨架。

```bash
# 模式 A：创建式（新建目录）
brickkit init my-shop

# 模式 B：补全式（在当前已有项目目录中执行）
brickkit init
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--name <name>` | 补全模式下显式指定项目名（若不传，默认取当前目录名） |
| `--no-skills` | 跳过装入 AI 助手技能 |
| `--yes` | 非交互模式，跳过补全前的确认提示（CI/CD 用） |

**关键行为（创建式）：**

- 新建 `<name>` 目录并生成三层骨架（目录结构见下文）
- 不生成 `deploy.local.yaml`（由 `brickkit local on` 按需生成）
- `.gitignore` 自动包含：`deploy.local.yaml`、`.secrets/`、`.brickkit/`、`config/.archive/`

**关键行为（补全式）：**

- **缺什么补什么，已有不动**：若 `brickkit.yaml` 等已存在则跳过并提示"已存在，跳过"
- **`.gitignore` 安全校验（核心防线）**：若 `.gitignore` 已存在，CLI 检查是否包含必需安全条目（`deploy.local.yaml`、`.brickkit/` 等）。若缺失，**大声警告**并列出缺失项，提示手动补充
- **交互确认**：在非空目录执行时，先打印补全计划（哪些创建、哪些跳过、哪些警告），等待确认（`--yes` 可跳过）
- **收尾校验**：补全完成后自动执行一次轻量级 `lint`，确认项目达到"可运行"的完整状态

**生成的目录结构（创建式）：**

```
my-shop/
├── .gitignore              # 含 deploy.local.yaml、.brickkit/、config/.archive/
├── brickkit.yaml           # 组件声明（空骨架）
├── deploy.yaml             # 部署配置（默认 target: docker）
└── config/
    ├── .gitkeep
    └── vars.yaml           # 公共变量（空骨架）
```

### 2. `brickkit skills`

查看/刷新装进项目的 AI 助手技能。

```bash
brickkit skills status      # 查看当前技能状态
brickkit skills update      # 刷新技能文件
```

### 3. `brickkit graph`

把项目的依赖拓扑画成 Mermaid 文本，打印到 stdout。

```bash
brickkit graph                        # 全项目依赖拓扑
brickkit graph > graph.mmd            # 存成文件（GitHub 直接渲染）
brickkit graph --ignore-served-by     # 把每个组件画成独立部署
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--ignore-served-by` | 忽略外壳成员关系，把每个组件画成独立部署 |

**关键行为：**

- 实线 = 强依赖，虚线 = 弱依赖
- 置灰节点 = 本次不会启动的组件
- `kind: shell` 外壳把成员画在自己内部
- stdout 里只有 Mermaid 文本，无其他输出

### 4. `brickkit lint`

离线、只读地检查所有 YAML 的结构与一致性。不联网，不需要 Docker / K8s。

```bash
brickkit lint                 # 标准检查
brickkit lint --strict        # 警告也算失败（给 CI 门禁用）
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--strict` | 警告也算失败（退出码 `1`），给 CI 门禁用 |
| `-f, --file <path>` | 指定部署配置文件 |

**检查项：**

| 检查项 | 说明 |
| --- | --- |
| 必填项检查 | `config/` 里 `required` 字段是否都有值 |
| 重复 key 检查 | 升级冲突遗留的重复 key |
| 孤儿配置检查 | `config/` 里有但 `brickkit.yaml` 没有的组件配置 |
| 引用检查（`--strict`） | `${ENV_VAR}` 是否存在、`file://` 文件是否存在、`$var:` 引用的变量是否在 `vars.yaml` 中定义 |
| 部署一致性检查 | `deploy.yaml` 组件列表与 `brickkit.yaml` 是否一致 |
| 本地部署文件一致性检查 | `deploy.local.yaml`（若存在）组件列表与 `brickkit.yaml` 是否一致 |
| 外壳成员一致性检查 | `deploy.yaml` 的 `members` 中的组件是否都在 `brickkit.yaml` 中 |
| 特殊字符检查 | 配置值是否包含会破坏 JSON 序列化的控制字符（外壳场景） |

### 5. `brickkit new <scope>/<name>`

生成一个组件的最小骨架。

```bash
brickkit new erp/backend                          # 默认写到 components/erp/backend/
brickkit new erp/backend --path ./my-repo         # 写到别处（独立组件仓库用）
brickkit new erp/backend --contract openapi       # 同时生成 OpenAPI 契约占位文件
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--path <dir>` | 写到别处，不再套一层目录（独立组件仓库用） |
| `--contract <type>` | 生成契约占位文件并登记进 `artifacts`（如 `openapi`、`proto`） |
| `--shell` | 生成外壳骨架（包含 `shell.kind: shell` 和 `shell.members` 占位） |

**关键行为：**

- 生成一份已通过校验的 `component.yaml`
- 不生成 Dockerfile，不生成源码——平台不替你选语言
- 不自动执行 `add`

### 6. `brickkit add <id>[@ver]`

递归拉取组件及其依赖，写入三层文件。

```bash
brickkit add erp/backend                    # 拉最新 Tag，写入精确版本
brickkit add erp/backend@1.0.0              # 锁死 1.0.0
brickkit add --local                        # 把本地安装源里的组件一次全部添加
brickkit add erp/backend@1.0.0 --repo-all   # clone 所有开源依赖的源码
brickkit add erp/backend@1.0.0 --yes        # 非交互（CI/CD）
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--local` | 把本地安装源里的组件一次全部添加 |
| `--repo` / `--repo-all` | clone 依赖的源码 |
| `--yes` | 非交互模式（CI/CD 用） |
| `--init` | 配合 `--local` 使用。自动巡逻 `components/` 和 `shell/`，为缺少 `brickkit.yaml` 的子组件自动初始化本地联调工作台（生成骨架并拉取其自身依赖）。 |

**关键行为：**

| 动作 | 说明 |
| --- | --- |
| 写入 `brickkit.yaml` | 精确版本落盘 |
| 同步 `deploy.yaml` | 新增部署条目，用默认值 |
| 生成 `config/` 骨架 | 按 `configSchema` 生成，`required` 留空标必填 |
| `$var:` 提示 | 若 `vars.yaml` 中有同名变量，提示是否引用 |
| 外壳自动处理 | 发现 `shell.kind: shell` → 自动标记 `kind: shell`，生成 `members` |
| 依赖递归 | 递归拉取所有依赖，支持多版本自动共存 |

### 7. `brickkit remove <id>[@ver]`

检查强依赖方后移除组件，配置自动归档。

```bash
brickkit remove erp/backend                 # 单版本时直接移除
brickkit remove erp/backend@1.0.0           # 多版本共存时指定版本
brickkit remove erp/backend@1.0.0 --force   # 有未提交改动也照样删源码目录
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--force` | 有未提交/未推送的改动也照样删源码目录 |

**关键行为：**

- 配置文件不直接删除，移入 `config/.archive/`
- `deploy.yaml` 中对应的部署条目同步删除
- 若被删的是外壳，成员从 `members` 移出，配置保留，变成独立组件
- 多版本共存时必须指定版本

### 8. `brickkit fetch <id>[@ver]`

只下载组件的产物，不装进项目。

```bash
brickkit fetch infra/notifier@1.0.0
```

**取什么：**

- Manifest（`component.yaml`）
- 契约文件（`artifacts` 字段声明的文件）

**不取什么：**

- 不取镜像
- 不写入 `brickkit.yaml`，不参与依赖解析和部署

### 9. `brickkit upgrade` 🆕

升级组件，执行配置迁移与冲突处理。

```bash
brickkit upgrade                          # 全项目按拓扑序升级
brickkit upgrade erp/backend              # 单个升到最新
brickkit upgrade erp/backend@2.0.0        # 单个升到指定版本
brickkit upgrade --dry-run                # 预览迁移结果，不实际执行
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--dry-run` | 预览迁移结果，不实际执行 |

**关键行为：**

| 步骤 | 说明 |
| --- | --- |
| 1. 拉取新版本 | 从本地缓存或 `git fetch --tags` 获取新版本 `component.yaml` |
| 2. 对比 `configSchema` | 新旧 key 集合机械对比 |
| 3. 迁移配置 | 旧值抄到新文件，新增字段填 `default`，删除字段留归档 |
| 4. 冲突处理 | 用户改过 + 开发者改了 → 写重复 key，大声失败 |
| 5. 旧配置归档 | 旧配置文件移入 `config/.archive/` |
| 6. 更新 `deploy.yaml` | 对应字段同步更新 |

**全量升级：** 按拓扑排序逐个升级，遇不兼容立即报错停止。

**外壳升级：** 外壳版本更新，成员组件自身版本不变。若新外壳不再支持某成员，该成员自动移出 `members`。

### 10. `brickkit up`

生成部署文件 → 跑迁移 → 起容器。

```bash
brickkit up                                   # 标准启动
brickkit up --dry-run                         # 只生成部署文件，供审查
brickkit up --file deploy.prod.yaml           # 指定部署文件（多环境）
brickkit up --no-local                        # 本次忽略 deploy.local.yaml
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--dry-run` | 只生成部署文件，不实际执行 |
| `-f, --file <path>` | 强制指定部署配置文件 |
| `--no-local` | 本次忽略 `deploy.local.yaml` |

**关键行为：**

| 步骤 | 说明 |
| --- | --- |
| 1. 一致性校验 | 若 `local` 模式开启，校验 `deploy.local.yaml` 与 `brickkit.yaml` 组件集合是否一致，不一致则大声失败 |
| 2. 启停判定 | 根据依赖图和 `mode` 决定哪些组件启动、哪些停止 |
| 3. 镜像检查 | 检查所有组件镜像是否存在（**绝不自动** `docker build`） |
| 4. 生成部署文件 | 生成 `compose.yaml` 或 K8s Manifest |
| 5. 执行迁移 | 运行迁移容器（按版本顺序） |
| 6. 调用引擎 | `docker compose up` 或 `kubectl apply` |

**镜像检查逻辑（绝不自动构建）：**

| 源类型 | 行为 |
| --- | --- |
| `local` 源 | 检查本地是否已有镜像。有则直接使用，无则大声失败，提示执行 `brickkit build` |
| `git` 源 | 检查本地是否已有镜像。有则直接使用。无则尝试 `docker pull`（若有 `image` 字段）。拉取失败则大声失败 |

### 14. `brickkit local` 🆕

管理 `deploy.local.yaml`（个人本地部署配置）。

```bash
brickkit local on           # 开启本地模式（从 deploy.yaml 完整复制）
brickkit local off          # 关闭本地模式
brickkit local status       # 查看当前状态
brickkit local refresh      # 重新生成（备份旧文件）
```

**`local on`：**

- 若 `deploy.local.yaml` 不存在，从 `deploy.yaml` 完整复制
- 若已存在，报错提示（防止覆盖用户本地修改）

**`local refresh`：**

1. 读取最新的 `deploy.yaml`
2. 将旧的 `deploy.local.yaml` 重命名为 `deploy.local.yaml.bak`
3. 基于 `deploy.yaml` 生成全新的 `deploy.local.yaml`
4. 输出智能 Diff 摘要：对比 `.bak` 与新文件，列出所有本地修改项，辅助快速合并

输出示例：

```
✅ 已生成最新的本地部署配置。旧配置已备份至 `deploy.local.yaml.bak`。
ℹ️ 检测到旧配置中有 3 处本地修改，请手动将它们合并至新的 `deploy.local.yaml` 中：
   - [erp/backend] mode: debug (当前为 `enabled`)
   - [erp/backend] localPort: 8081 (当前未设置)
   - [vars] DB_PASSWORD: "local_dev_pwd" (当前为 `${PROD_DB_PASSWORD}`)
```

### 17. `brickkit build` 🆕

显式构建需要本地构建的组件镜像。构建是用户的显式动作，`up` 绝不自动执行。

```bash
brickkit build                          # 构建所有需要本地构建的组件
brickkit build erp/backend              # 构建指定组件
brickkit build --force                  # 强制重新构建所有组件（忽略缓存）
brickkit build erp/backend --force      # 强制重新构建指定组件
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--force` | 强制重新构建，忽略已有镜像 |

**关键行为：**

- 遍历 `brickkit.yaml` 中所有组件，对于没有 `image` 字段的组件（或 `local` 源），从源码构建镜像
- 构建出的镜像 tag 与组件 `component.yaml` 的 `metadata.version` 严格一致
- **默认复用缓存：** 如果镜像已存在且版本未变，跳过构建

### 18. `brickkit release` 🔄（原 `publish`）

无 Market 的组件发布："发布组件" = "给组件仓库打个规范的 tag 并推送"。

```bash
brickkit release --path ./components/erp-backend
```

**参数：**

| 参数 | 说明 |
| --- | --- |
| `--path <dir>` | 组件源码目录 |
| `--local` | 批量发布所有本地源组件。依次执行校验、打 Tag 和 Push，遇错立即停止。 |

**流程：**

| 步骤 | 动作 | 失败处理 |
| --- | --- | --- |
| 1 | 读取 `component.yaml` 的 `metadata.version` | — |
| 2 | 校验 `component.yaml` 格式和依赖 | 报错停止 ❌ |
| 3 | `git status` 检查工作区 | 不干净 → 报错停止 ❌ |
| 4 | 检查分支同步（是否有未推送 commit） | 有未推送 → 报错停止 ❌ |
| 5 | `git tag <version>` | — |
| 6 | `git push origin <version>` | 推送失败 → 回滚本地 tag ❌ |

**原子性保证：** 要么完全成功，要么完全回滚。

### 19. `brickkit login`

终端交互登录市场，Token 存 `.brickkit/credentials`。

```bash
brickkit login
brickkit login --market https://market.example.com/api/v1
```

**保留原因：** 虽然当前提案核心是"无 Market 的 Git 分发"，但 BrickKit 的长远架构中 Market 依然是一个可选的高级基础设施。保留此命令保证未来 Market 上线时 CLI 结构的稳定性。

### 20. `brickkit logout`

先调市场作废 Token，再删本地的 `.brickkit/credentials`。

```bash
brickkit logout
brickkit logout --keep-remote   # 只删本地凭据，不调市场（离线时用）
```

## 常用命令速查

```bash
# 项目生命周期
brickkit init my-shop && brickkit add erp/backend@1.0.0 && brickkit up

# 多环境切换
brickkit up --file deploy.prod.yaml

# 本地调试
brickkit local on
brickkit up
brickkit local refresh      # 团队新增组件后，同步本地部署配置
brickkit local off

# 构建与升级
brickkit build erp/backend --force    # 修改代码后重建
brickkit upgrade erp/backend@2.0.0    # 升级 + 配置迁移

# 检查与诊断
brickkit lint --strict
brickkit deps erp/backend
brickkit graph > graph.mmd
brickkit up --dry-run

# 发布
brickkit release --path ./components/erp-backend

# 只取契约（跨项目）
brickkit fetch infra/notifier@1.0.0
```

## 与现有版本的变更摘要

### 命令变更

| 变更类型 | 命令 | 说明 |
| --- | --- | --- |
| 🗑️ 废除 | `override` | 被 `deploy.local.yaml` + `brickkit local` 取代 |
| 🔄 重命名 | `publish` → `release` | 从"上传到 Market"变为"校验 + 打 Git tag + push" |
| 🆕 新增 | `local` | 子命令：`on` / `off` / `status` / `refresh` |
| 🆕 新增 | `deps` | 打印依赖拓扑树 |
| 🆕 新增 | `build` | 显式构建本地源镜像 |
| 🆕 新增 | `upgrade` | 独立顶层命令，承载配置迁移与冲突处理 |
| 🔄 扩展 | `init` | 新增补全式模式（不带参数，在当前目录缺什么补什么），新增 `--name` / `--yes` 参数 |
| ✅ 保留 | `login` / `logout` | 为未来 Market 预留，当前不影响无 Market 工作流 |

### 参数变更

| 变更类型 | 参数 | 说明 |
| --- | --- | --- |
| 🗑️ 移除 | `up --context <name>` | 原用于覆盖 `deploy.context`（指定 K8s 集群）。违背"所见即所得"原则，属于运行时覆盖单个配置字段。用户需要切换集群时，通过 `--file` 指定不同的部署文件即可（如 `deploy.cluster-a.yaml`） |
| 🔄 重命名 | `--deploy-file` → `-f, --file` | 更简洁，符合 `docker compose -f` 的肌肉记忆 |
| 🆕 新增 | `--no-local` | 本次运行忽略 `deploy.local.yaml`（一次性） |
| 🆕 新增 | `build --force` | 强制重新构建，忽略已有镜像 |
| 🆕 新增 | `upgrade --dry-run` | 预览迁移结果，不实际执行 |
