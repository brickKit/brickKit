# BrickKit

> 一个组件管理与拼装平台，像搭积木一样构建系统。每块积木（组件）独立开发、
> 独立部署、独立调用；BrickKit CLI 负责把积木拉来、解析依赖、排好启动顺序、
> 生成部署文件、交给 Docker 或 Kubernetes 跑起来。

仓库：https://github.com/brickKit/brickKit ｜ 许可证：Apache-2.0

如果你是 AI 助手，请先抓取 `AGENTS.zh.md`——一份文件读完即可理解全平台。

- [合格外壳该满足什么](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/shell-implementers-guide.md): 写给造壳的人：`servedBy` 字段对收编它的外壳提出了什么要求——合并进程必须满足的九条性质，以及平台到底会不会把哪些东西注入外壳的环境。
- [在外壳里合并数据库连接池](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/shared-connection-pools.md): 写给合并进同一个 servedBy 外壳、又共用 PostgreSQL 或 Oracle 的组件——为什么池子通常合不了、要靠 schema 重新分组、`SET LOCAL ROLE` 技巧，以及唯一一件有截止日期的决定。
- [怎么可靠地调用一个依赖的地址](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/service-addressing.md): 一次真实的 Docker Compose 实验——流量不停的情况下把依赖容器强制重建到一个真正不同的 IP——测出 Go 的 `net/http`、Python 的 `requests.Session`、Node 的 `http.Agent(keepAlive)` 各自到底会怎样：Go 快速失败一次、下一次请求就恢复；Python 完全不报错但悄悄卡顿 2.5 秒；Node 不设超时就会无限期挂起。外加 Kubernetes 稳定的 ClusterIP 为什么抹掉了其中一种失败方式、却抹不掉另外两种。
- [自己搭一套 BrickKit Market](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/deployment/self-hosted-market.md): 部署市场本身（跟部署你自己的项目是两件事）——三种部署模式、编排文件走一遍（带两处真实踩过的坑）、怎么升级、怎么搬上云。
