# BrickKit

> 一个组件管理与拼装平台，像搭积木一样构建系统。每块积木（组件）独立开发、
> 独立部署、独立调用；BrickKit CLI 负责把积木拉来、解析依赖、排好启动顺序、
> 生成部署文件、交给 Docker 或 Kubernetes 跑起来。

仓库：https://github.com/brickKit/brickKit ｜ 许可证：Apache-2.0

如果你是 AI 助手，请先抓取 `AGENTS.zh.md`——一份文件读完即可理解全平台。

- [多项目共享](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/guide/12-multi-project-sharing.md): 教程第 12 篇，系列最后一篇——两个真正独立的项目共享一个基于 Redis 的事件总线、一个配置字段把共享变成隔离、一个必填且无默认值的 configSchema 字段把组件当成别人的 API 来对待，以及一个早先的跨项目便利字段为什么被删掉。
- [依赖解析与启动顺序](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/architecture/dependency-resolution.md): 把架构总览里的级联与解析两个阶段往难处推——一个真实的菱形依赖、一个靠一条弱边放行/没有弱边就拒绝的循环依赖，以及为什么真正决定 `up` 要跑多久的是最长强依赖链而不是组件数量。
- [部署文件是怎么生成出来的](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/architecture/deployment-generation.md): 同一个两组件项目，两个目标各生成一遍，原样呈现——Compose 的迁移独立成服务、配额要换算单位，对照 Kubernetes 的三段式启动探针、密码走 Secret 引用，以及两边唯一一字不差的那个地址字符串。
- [资源绑定的实际机制](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/architecture/resource-binding.md): 绑定槽位写错、同类资源没区分开这两种真实校验错误，然后是配额链三层（CLI 默认值、Manifest、项目覆盖）逐字段合并而不是整块替换的真实验证，每一层都有真实生成的输出。
- [签名与信任模型](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/architecture/signing-and-trust.md): 为什么 Manifest 签的是规范化载荷而不是原始字节、为什么签名需要 cosign 而验签完全不需要、为什么公钥必须放在自己项目里而不能来自市场，以及一个真实验证过的保留变量冲突警告。
- [组件设计准则](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/component-design.md): 设计自己的领域模型之前怎么参考成熟实现、一批值得设计规避的结构性失败模式，以及"这个特性该做成一组可互换组件，而不是一个配置开关"这个信号该怎么识别。
- [基于 BrickKit 的组件该怎么分层测试](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/testing.md): 契约/业务规则/单元/集成四层怎么分工，以及一个真实生产部署踩过的权限边界与幂等性陷阱。
- [怎么规划种子数据与测试数据](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/data-construction.md): 两条必须物理隔离、永不共用存储的路径——种子/演示数据（幂等、持久、组件间可复用）和测试现场构造的数据（唯一后缀、从不清理）——以及怎么设计才能让种子数据真正够用来演示和探索。
- [闭源组件的镜像安全规范](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/closed-source-image-hardening.md): 拉取镜像就等于交出它将来会跑的每一个字节——这跟私有 Git 仓库不是同一种保证。Docker 镜像卫生习惯、按语言分类的加固上限，以及这些手段一个都防不住的事。
- [合格外壳该满足什么](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/shell-implementers-guide.md): `servedBy` 字段对收编它的外壳提出了什么要求——合并进程必须满足的九条性质，以及平台到底会不会把哪些东西注入外壳的环境。
- [怎么声明 servedBy：部署方检查清单](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/servedby-deployment-checklist.md): 写给在自己项目里声明 `servedBy` 的人，而不是造壳的人——什么时候该用、写之前的检查清单、哪些写法会被拒绝、哪些事平台会自动做好。
- [在外壳里合并数据库连接池](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/shared-connection-pools.md): 写给合并进同一个 servedBy 外壳、又共用 PostgreSQL 或 Oracle 的组件——为什么池子通常合不了、要靠 schema 重新分组、`SET LOCAL ROLE` 技巧，以及唯一一件有截止日期的决定。
- [自己搭一套 BrickKit Market](https://raw.githubusercontent.com/brickKit/brickKit/main/docs/zh/patterns/deployment/self-hosted-market.md): 部署市场本身（跟部署你自己的项目是两件事）——三种部署模式、编排文件走一遍（带两处真实踩过的坑）、怎么升级、怎么搬上云。
